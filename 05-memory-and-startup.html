PART 1 / 7

Three kinds of storage: Flash, SRAM and registers

A microcontroller (MCU) is a whole computer on one chip: a CPU core, two kinds of memory, and peripherals (GPIO, UART, timers…). Our reference part is the STM32F407: an ARM Cortex-M4 core at up to 168 MHz, 512 KB Flash and 128 KB SRAM (some variants have 1 MB Flash).

1. Flash — the "printed book"

What it physically is: billions of transistors, each with a tiny isolated "floating gate" that can trap electrons. Trapped charge stays for 10–20+ years without power, so Flash is non-volatile (it remembers).

  • Reading is fairly fast: about 30 ns, which is 6 CPU cycles at 168 MHz (hidden by a cache, see the .text region).
  • Writing is slow and awkward: you can only change bits from 1 to 0 (about 16 µs per word), and changing a 0 back to 1 requires erasing a whole sector of 16–128 KB (taking up to 1–2 seconds). The CPU cannot write Flash with an ordinary store instruction.
  • So Flash holds what never changes while running: program code, constant tables, string literals, and the starting values of variables.

2. SRAM — the "whiteboard"

What it physically is: Static RAM. Each bit is a small circuit of 6 transistors (two cross-coupled inverters) that holds a 0 or 1 as long as power is applied. "Static" = no refresh needed (unlike the DRAM in your PC).

  • Read and write in a single cycle at full CPU speed.
  • Volatile: when power is removed the value is lost. At the next power-up every bit settles randomly — SRAM starts as garbage, not zeros.
  • So SRAM holds everything that changes: variables, the stack, the heap.
  • F407 detail: 112 KB SRAM1 + 16 KB SRAM2, contiguous at 0x2000_0000. Plus 64 KB CCM ("core-coupled memory") at 0x1000_0000, which only the CPU can reach (DMA cannot).

3. Registers — the "hands"

"Register" means two different things in embedded work:

  1. Core registers: 16 storage cells of 32 bits inside the CPU (R0–R12, SP, LR, PC) plus status registers. The CPU can only calculate on values in registers: to add two variables it must load them from SRAM into registers, add, then store the result back. ARM is a "load/store architecture".
  2. Peripheral registers: control cells inside peripherals (e.g. GPIOA's output register). They are given addresses like memory, so writing to address 0x4002_0014 changes pin voltages. This is called memory-mapped I/O.

PART 2 / 7

What is an address?

An address is the number of a byte. Every byte the CPU can reach — in Flash, in SRAM, or in a peripheral — has its own unique number. Reading or writing memory always means "give the bus an address, get or put a value".

1. How many addresses are there?

The Cortex-M4 uses 32-bit addresses. 32 bits can represent 232 different numbers:

2^32 = 4,294,967,296 addresses = 4 GB of address space lowest = 0x0000_0000 highest = 0xFFFF_FFFF

The chip does not have 4 GB of memory. Most addresses are unused; the memory and peripherals that do exist are placed at chosen addresses. This placement is the memory map.

2. Reading hex addresses

Addresses are written in hexadecimal (base 16, digits 0–9 and A–F), prefixed with 0x. Each hex digit is exactly 4 bits, so 8 hex digits = 32 bits. The underscore is only for readability.

0x2000_0000 = 2 × 16^7 = 536,870,912 (decimal) ← start of SRAM 0x2002_0000 = 0x2000_0000 + 0x2_0000 = start + 131,072 = start + 128 KB ← end of SRAM + 1 1 KB = 1024 = 0x400 64 KB = 0x1_0000 128 KB = 0x2_0000

3. Bytes, words and little-endian

Each address holds one byte (8 bits). A 32-bit value (a "word") needs 4 consecutive addresses. Cortex-M stores multi-byte values little-endian: the lowest (least significant) byte at the lowest address.

uint32_t *p = (uint32_t *)0x20000000;   /* p holds an address */
*p = 0x12345678;                        /* store 4 bytes there */

An address is the number of a byte in the CPU's 32-bit, 4 GB address space; memory and peripherals are placed at fixed addresses, which is the memory map. A pointer in C is just an address. Cortex-M is little-endian, so a 32-bit word at 0x2000_0000 has its least significant byte at 0x2000_0000, and words are naturally aligned to multiples of four.

PART 4 / 7

From C file to firmware: what the compiler and the linker do

The compiler turns each .c file into machine code but does not know any final addresses. The linker combines all those pieces, decides where every function and variable lives, and patches in the real addresses. The linker script (.ld file) is the instruction sheet that tells the linker which memory exists and what goes where.

 main.c ──compile──> main.o ─┐
 uart.c ──compile──> uart.o ─┼──LINK (with STM32F407.ld)──> firmware.elf ──objcopy──> firmware.bin
 startup.s ─assemble> startup.o ┤                               │                      (raw bytes,
 libc.a (printf, memcpy) ──────┘                               └─> firmware.map        flashed at
                                                                    (where everything    0x0800_0000)
                                                                     ended up)

1. Terms

Object file (.o)
The compiler's output for one source file: machine code and data, split into named sections, plus a symbol table and a list of "holes" to fill in.
Symbol
A name with an address: every function and global variable is a symbol (main, baud). The linker script can also create symbols (_estack, _sdata).
Relocation
A "hole" in the machine code where an address must be written once it is known.
ELF
Executable and Linkable Format: the file format of .o and .elf files. It contains sections, symbols and debug info. The debugger reads the .elf.
.bin / .hex
Just the raw bytes to program into Flash (no symbols).
Map file
A text report from the linker: the address and size of every section and symbol. Your best friend when debugging memory.

2. What the linker does, step by step

  1. Read the MEMORY block of the linker script: "FLASH starts at 0x0800_0000, 512 KB; RAM starts at 0x2000_0000, 128 KB".
  2. Collect input sections from every .o file and library: all the .text.*, .rodata.*, .data.*, .bss.* pieces.
  3. Place them in order following the SECTIONS block: vector table first in Flash, then code, then constants; variables in RAM. Each piece gets a final address.
  4. Define symbols like _sdata, _edata, _estack from the script.
  5. Resolve references: wherever main.o used baud, write the final address 0x2000_0000 into the hole (relocation).
  6. Optionally delete unused sections (--gc-sections) — which is why the vector table needs KEEP().
  7. Check sizes: if code does not fit, it stops with "region FLASH overflowed by N bytes".

Before and after linking (the same instruction that loads baud's address):

main.o   (not linked):  ldr r3, [pc, #12]   ; literal = 0x00000000  + relocation "baud"
firmware.elf (linked):  ldr r3, [pc, #12]   ; literal = 0x20000000  (baud's final address)

The compiler produces relocatable object files whose code and data are split into sections but have no final addresses. The linker, driven by the linker script, collects those sections, places them into the Flash and RAM regions declared in MEMORY, defines symbols like _sdata and _estack, patches every reference with the final address, and can garbage-collect unused sections. The map file shows the result.

What is a "section", and which one does my variable go in?

A section is a named bucket of bytes that share the same purpose and rules. The compiler sorts everything into four main buckets, and the linker script places each bucket in the right memory.

The decision, as questions

 Is it a function (code)? ─────────────── yes ─> .text
        │ no
 Is it const (and, for pointers, are the pointers const too)? ── yes ─> .rodata
        │ no
 Is it a local variable without 'static'? ─ yes ─> stack (or just a register)
        │ no (global, or 'static')
 Is its initial value non-zero? ─────────── yes ─> .data   (Flash image + RAM copy)
        │ no (zero or none)
        └──────────────────────────────────────────> .bss    (RAM only, zeroed at boot)

 Memory from malloc()/new ──────────────────────────> heap

Common mistake: "a static variable inside a function is on the stack". No — static means it exists for the whole program, so it goes to .data or .bss. Only the name is limited to the function.

Code goes to .text and const data to .rodata, both in Flash. Globals and statics with a non-zero initialiser go to .data, which has a load image in Flash and a live copy in RAM; zero or uninitialised ones go to .bss, which is RAM only and zeroed at boot. Automatic locals use the stack or registers, and malloc memory comes from the heap.

PART 7 / 7

The reset sequence, end to end

Now everything connects. Here is what happens from the moment power is applied until main() runs, and then what happens when the first interrupt arrives. The Startup Sequence tab lets you step through it instruction by instruction.

  1. Power on. VDD ramps up; the reset supervisor holds the CPU in reset until the supply is stable. SRAM fills with random values. [hardware]
  2. Clock and boot mode. The 16 MHz internal RC oscillator starts; BOOT0 = 0 is sampled, so Flash (0x0800_0000) is mirrored at address 0. [hardware]
  3. Fetch the stack pointer. The core reads address 0x0000_0000 → 0x2002_0000 → MSP. [hardware]
  4. Fetch the reset vector. The core reads 0x0000_0004 → 0x0800_0199 → PC = 0x0800_0198, Thumb bit set. [hardware]
  5. Reset_Handler starts. First software instruction: reload SP from _estack. [software]
  6. Copy .data. 12 bytes from Flash 0x0800_4A10 to RAM 0x2000_0000: now baud = 115200, offset = −5, calls = 1. [software]
  7. Zero .bss. 68 bytes from 0x2000_000C to 0x2000_0050: now rx_buf and tick_count are 0. [software]
  8. SystemInit. Enable the FPU, set VTOR, (optionally) start the PLL to run at 168 MHz with 5 Flash wait states. [software]
  9. Constructors. __libc_init_array() runs C++ global constructors. [software]
  10. bl main. Your code runs, with every C guarantee in place. [software]
  11. Later: SysTick fires (exception 15). The core pushes R0–R3, R12, LR, PC, xPSR (32 bytes) onto the stack, reads the handler address at VTOR + 15 × 4 = 0x0800_003C, and jumps to SysTick_Handler at 0x0800_0F20, which increments tick_count at 0x2000_004C. On return, the core pops the 8 registers and resumes exactly where it was. [hardware + software]
 time ─────────────────────────────────────────────────────────────────────────>
 [ POR ][HSI][read SP][read PC][ Reset_Handler: copy .data | zero .bss ][SystemInit][ctors][ main() ...
  hardware only ─────────────────┘ └── software (your startup.s) ─────────────────────────┘
                                                                    SysTick ─> [push][handler][pop] ─> main continues

At reset the Cortex-M4 loads the initial stack pointer from word 0 and the reset handler address from word 1 of the vector table, which on STM32 is reached through the boot alias at address 0. Reset_Handler then copies .data from its load address in Flash to RAM, zeroes .bss, calls SystemInit for the FPU, vector table and clocks, runs the C++ constructors and finally calls main. When an interrupt occurs, the hardware stacks eight registers and fetches the handler from VTOR plus four times the exception number.

VMA (virtual/run address) is where code expects the variable to be. LMA (load address) is where the programmer writes its bytes. For flash-resident code they are equal. For .data they differ, and > RAM AT> FLASH is how you say so.

USING LINKER SYMBOLS FROM C
/* A linker symbol is an ADDRESS with no storage. */
extern uint32_t _sidata, _sdata, _edata, _sbss, _ebss;

void copy_and_zero(void) {
    uint32_t *src = &_sidata;          // ✅ take the address
    uint32_t *dst = &_sdata;
    while (dst < &_edata) *dst++ = *src++;
    for (dst = &_sbss; dst < &_ebss; ) *dst++ = 0;
}

uint32_t n = _edata - _sdata;          // ❌ reads RAM contents!
uintptr_t n = (uintptr_t)&_edata
            - (uintptr_t)&_sdata;      // ✅ size in bytes

Tip: declaring them as extern uint8_t _sdata[]; makes the name decay to the address and removes the temptation to read through it.

  • Static RAM = data + bss = 5 196 B — plus heap + stack reservations
  • The classic trap: forgetting that data appears in both sums.
KEEP() & --gc-sections

With -ffunction-sections -fdata-sections every function/variable gets its own input section, and -Wl,--gc-sections deletes any section not reachable from ENTRY() or a KEEP().

  • Must KEEP: .isr_vector, .init_array/.fini_array, .init/.fini, version/header blocks read by a bootloader.
  • Nothing in C references the vector table — only the hardware does. That is exactly why the linker thinks it is dead.
  • Check with -Wl,--print-gc-sections or the map file's "Discarded input sections".
NOLOAD — VARIABLES THAT SURVIVE RESET
.noinit (NOLOAD) :
{
  . = ALIGN(4);
  *(.noinit*)
} > RAM

__attribute__((section(".noinit")))
uint32_t crash_magic, crash_pc;

Not copied, not zeroed. After a watchdog or software reset, RAM still holds the last values, so a HardFault handler can store the faulting PC and the next boot can report it. Validate with a magic word: on cold power-up the contents are random.
