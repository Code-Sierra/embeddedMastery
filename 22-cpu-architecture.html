01What problem does a CPU solve?

A CPU is a machine that reads a list of very small orders from memory and carries them out, one after another, as fast as possible.

When you compile sum += a[i];, the compiler turns it into a few instructions. An instruction is one tiny order, such as "load the 32-bit word at this address into a register" or "add these two registers". Each instruction is stored in memory as a number. On a Cortex-M4 the instruction ADDS r3, r1, r2 is stored as the 16-bit value 0x188B.

The CPU repeats the same loop forever:

  1. Fetch. Read the instruction stored at the address held in the program counter (PC). The PC is a register that always points at the next instruction to run.
  2. Decode. Work out what the bits mean: which operation, which registers, which constant.
  3. Execute. Do the work: add, compare, compute an address.
  4. Access memory if the instruction is a load or a store.
  5. Write back the result into a register, and move the PC on to the next instruction (or to a branch target).

That is the whole job. Everything else in this topic (pipelines, caches, branch predictors, out-of-order execution, MMUs) exists for one of two reasons:

  • Speed. Do this loop for more instructions per second. A Cortex-M4 at 168 MHz completes up to 168 million simple instructions per second. A phone core completes billions.
  • Correctness and safety. Make sure the right instruction sees the right data, even when the hardware is doing several things at once, and stop one program from damaging another.

The central difficulty is that memory is much slower than the core. A desktop core can do an addition in 0.25 ns, but fetching a value from DRAM takes about 100 ns, four hundred times longer. On an STM32F407 at 168 MHz, the flash memory that holds your program needs about 30 ns per read, while one clock cycle lasts 5.95 ns. Most of CPU architecture is about hiding that gap.

Check yourself: If a CPU does nothing clever and every instruction needs one flash read of 30 ns, how many instructions per second can it run? Answer: 1 / 30 ns ≈ 33 million, no matter how fast the clock is. That is why the F407 needs an accelerator (the ART cache) to reach 168 million.

02The physical picture: what is inside the chip

Before any theory, here are the boxes and wires you are reasoning about. The example is an STM32H743 (Cortex-M7 core, 480 MHz), because it has every feature this page covers: a pipeline, a branch predictor, caches, tightly coupled memory and an MPU.

Read the diagram from left to right, the way a load instruction travels:

  1. The PC says which instruction is next. The branch predictor guesses where the PC goes after a branch, so fetching never has to wait.
  2. The pipeline (fetch, decode, execute, memory, write) works on several instructions at once, like an assembly line. Each box holds a different instruction during the same clock cycle.
  3. The register file is a set of 32-bit storage slots inside the core. Reading a register costs nothing extra. Arithmetic only ever happens between registers.
  4. When a load needs data, it first asks the L1 D-cache, a small fast memory that keeps copies of recently used data. If the copy is there (a hit), the data arrives in about 1 cycle. If not (a miss), the cache fetches a 32-byte block from SRAM or flash through the bus matrix, which takes many cycles.
  5. The TCMs (tightly coupled memories) are a second kind of fast memory with no cache involved: always 0 wait states, always predictable. You choose what goes there with the linker script.
  6. The peripherals (UART, GPIO, timers) appear as addresses too. Writing to address 0x5802_0014 on an H743 writes GPIOA's output data register (ODR), which drives the pins. The CPU must never cache those addresses or read them early, and the memory-type rules make sure it does not.
  7. The DMA controller is a second bus master that copies data while the CPU does something else. It reads and writes SRAM directly, so it cannot see what is in the CPU's D-cache. This one fact causes a whole family of real bugs (Section 7 and the Scenarios tab).

A smaller chip such as the STM32F407 (Cortex-M4) has the same picture without the L1 caches and the TCMs: a 3-stage pipeline, a flash accelerator (ART) in front of flash, and SRAM directly on the bus. A phone or Raspberry Pi chip (Cortex-A) adds more cache levels (L2, L3), several cores that must keep their caches consistent, and an MMU that translates addresses.

Check yourself: Which two boxes in the diagram can both write SRAM? The CPU (through the D-cache) and the DMA controller. If the CPU holds a newer copy in its cache than SRAM does, the two disagree. That is the "cache coherency" problem in one sentence.

03The key words, defined one at a time

Every card on this page uses these words. Each one has a plain definition and a concrete example. Come back here whenever a word is unclear.

InstructionOne encoded order for the CPU. Example: LDR r1, [r2] means "read the 32-bit word at the address in r2 into r1".
ISA (instruction set architecture)The rulebook: which instructions exist, what they do, which registers there are. ARMv7E-M is the ISA of the Cortex-M4 and M7. Software is written against the ISA.
MicroarchitectureOne particular hardware design that obeys the ISA. Cortex-M4 (3-stage, no cache) and Cortex-M7 (6-stage, caches) are two microarchitectures for the same ISA.
RegisterA 32-bit storage slot inside the core (r0–r12, SP, LR, PC on Cortex-M). Arithmetic works only on registers; memory must be loaded into a register first.
PC (program counter)The register holding the address of the instruction being fetched. A branch is simply an instruction that writes a new value into the PC.
Clock cycleOne tick of the clock. At 480 MHz one cycle is 1 / 480 000 000 s = 2.083 ns. Hardware does one step of work per cycle.
Pipeline stageOne step of instruction processing (fetch, decode, execute…) with its own hardware. With 5 stages, 5 different instructions are in flight at once.
CPI / IPCCycles per instruction and its inverse, instructions per cycle. A perfect simple pipeline has CPI = 1. Stalls push CPI above 1. Wide cores reach IPC above 1.
HazardA situation where the next instruction cannot proceed in the next cycle: it needs a result that is not ready (data hazard), a branch has not decided yet (control hazard), or two instructions need the same hardware (structural hazard).
Stall / bubbleA cycle in which a stage does no useful work because of a hazard. The pipeline inserts an empty "bubble" (a NOP) and the instructions behind it wait.
Forwarding (bypassing)Wires that pass a result straight from the end of the execute stage to the input of the next instruction, without waiting for it to be written into the register file. It removes most data stalls.
Branch predictionGuessing whether a branch is taken, and where it goes, before it is decided, so fetching can continue. A wrong guess means throwing away the wrongly fetched instructions (a flush).
CacheA small, fast memory next to the core that keeps copies of recently used memory. Hardware decides what to keep; software normally does not see it.
Cache lineThe unit a cache stores and moves: 32 bytes on Cortex-M7, 64 bytes on most phone and PC cores. Reading one byte brings in the whole line.
Hit / missHit: the data is in the cache (fast). Miss: it is not, so the line must be fetched from the next, slower level.
Tag / index / offsetThe three fields a cache cuts an address into. Offset = which byte inside the line, index = which set to look in, tag = the rest, stored to recognise which memory block the line holds.
Ways (associativity)How many lines one set can hold. 1 way = direct-mapped. The M7 D-cache is 4-way: any address can go into one of 4 slots of its set.
Write-back / write-throughWrite-back: a store only updates the cache and marks the line "dirty"; memory is updated later. Write-through: every store also goes to memory.
TCM (tightly coupled memory)Fast on-chip RAM wired straight to the core, 0 wait states, never cached. Used for code and data that must have predictable timing.
Memory-mapped I/OPeripheral registers are addresses. *(volatile uint32_t*)0x40020014 = 1; writes the GPIOA output register on an STM32F4.
Memory type (Normal / Device)An attribute attached to an address range. Normal memory (RAM) may be cached, read early and reordered. Device memory (peripherals) may not.
Barrier (DMB / DSB / ISB)Instructions that force order: DMB orders memory accesses, DSB waits for them to finish, ISB throws away already-fetched instructions.
MMU / MPU / TLBMMU: translates virtual addresses to physical ones and checks permissions (Cortex-A, Linux). MPU: checks permissions only, no translation (Cortex-M/R). TLB: the cache of recent MMU translations.
CoherencyThe guarantee that all caches and masters agree on the value of a memory location. Multi-core Cortex-A chips do it in hardware; the Cortex-M7 D-cache and DMA do not.
Out-of-order (OoO)A core that runs later independent instructions while an earlier one waits for memory, then puts results back in program order. Phone and PC cores do this; Cortex-M does not.

04One instruction, start to finish

Follow ADDS r3, r1, r2 on a simple non-pipelined CPU. The instruction is stored at address 0x0800_0200 as the 16-bit value 0x188B. Before it runs, r1 = 5 and r2 = 7.

Step by step

  1. Fetch. The PC holds 0x0800_0200. The core puts that address on the instruction bus and flash returns the halfword 0x188B. Because this is a 16-bit instruction, the PC advances by 2 to 0x0800_0202.
  2. Decode. The bits are split into fields. 0x188B in binary is 0001100 010 001 011. The first 7 bits (0001100) mean "ADDS register, register". The next three fields are Rm = 010 = r2, Rn = 001 = r1, Rd = 011 = r3. The decoder also reads r1 and r2 from the register file: 5 and 7.
  3. Execute. The ALU adds 5 + 7 = 12. Because this is ADDS (with S for "set flags"), it also updates the condition flags: N = 0 (not negative), Z = 0 (not zero), C = 0, V = 0.
  4. Memory. Nothing to do: ADDS is not a load or a store.
  5. Write back. The value 12 is written into r3.
FieldBitsValueMeaning
opcode15–90001100ADDS Rd, Rn, Rm (Thumb encoding T1)
Rm8–6010second source = r2
Rn5–3001first source = r1
Rd2–0011destination = r3

If each of those five steps takes one cycle and the CPU starts the next instruction only when the previous one is finished, then every instruction takes 5 cycles. At 168 MHz that is 5 × 5.95 ns = 29.8 ns per instruction, about 34 million instructions per second. Section 5 shows how to get five times more out of the same hardware.

Check yourself: In which step is the PC changed for a branch instruction such as B loop? In execute (or decode on some cores), when the target address is known. Until then the CPU does not know for sure what to fetch next. That uncertainty is the "control hazard" in Section 6.

05Pipelining: the assembly line

Instead of finishing one instruction before starting the next, start a new instruction every cycle and let each stage work on a different one.

Think of a laundry with a washer, a dryer and an ironing board. Doing one load at a time, three loads take 3 × 3 = 9 hours. If you put load 2 in the washer while load 1 is in the dryer, three loads take 3 + 2 = 5 hours. Each load still takes 3 hours (latency is unchanged), but a load finishes every hour (throughput is three times higher).

cycle:           1   2   3   4   5   6   7   8   9
ADD  r1,r2,r3    IF  ID  EX  MEM WB
SUB  r4,r5,r6        IF  ID  EX  MEM WB
LDR  r7,[r8]             IF  ID  EX  MEM WB
STR  r9,[r8,#4]              IF  ID  EX  MEM WB
ADD  r0,r0,#1                    IF  ID  EX  MEM WB

5 instructions finish in 9 cycles, not 5 × 5 = 25.
Formula: k stages, N instructions → k + (N − 1) cycles = 5 + 4 = 9.
  1. In cycle 1 only ADD is in the pipe (in IF). The other stages are empty: this is the fill.
  2. From cycle 5 on, every stage holds a different instruction, and one instruction completes every cycle. In steady state the CPI is 1.
  3. For 1000 instructions: 5 + 999 = 1004 cycles, so CPI = 1004 / 1000 ≈ 1.004. Without pipelining it would be 5000 cycles. Speed-up ≈ 4.98, close to the number of stages.
  4. Each stage now does only one fifth of the work, so the clock can also run faster. That is the second benefit.

Real cores: the Cortex-M0+ has 2 stages, the Cortex-M3/M4 have 3 (fetch, decode, execute), the Cortex-M7 has 6 and can issue two instructions per cycle, phone and PC cores have 13 to 20. The 5-stage IF/ID/EX/MEM/WB pipeline drawn above is the standard teaching model (from the MIPS processors), and the Pipeline Lab simulates exactly that model.

Check yourself: A 5-stage pipeline runs 100 instructions with no stalls. How many cycles? 5 + 99 = 104. CPI = 1.04.

06Hazards: when the assembly line has to wait

The pipeline only reaches CPI = 1 if every instruction can move forward every cycle. Three things stop it.

1. Data hazard: a result is not ready yet

LDR r1, [r2]      IF  ID  EX  MEM WB          the value of r1 arrives at the END of MEM (cycle 4)
ADD r3, r1, r4        IF  ID  **  EX  MEM WB  ADD needs r1 at the START of EX
                              ^ one bubble: ADD waits one cycle in ID
  1. ADD wants to execute in cycle 4, but r1 only exists at the end of cycle 4, when LDR finishes reading memory.
  2. The hazard detection unit in the decode stage sees "the instruction ahead is a load whose destination (r1) is one of my sources". It freezes the PC and the decode stage for one cycle and sends an empty bubble into EX.
  3. In cycle 5 the loaded value is forwarded straight from the memory stage output into the ALU input, and ADD executes.
  4. For two ALU instructions in a row (ADD then SUB using its result) there is no stall at all with forwarding, because the ALU result exists at the end of EX, just in time for the next instruction's EX.

The compiler can hide the remaining bubble by moving an independent instruction between the load and its user. This is called instruction scheduling, and it is one of the things -O2 does.

2. Control hazard: which instruction comes next?

A branch decides its direction in EX. By then the pipeline has already fetched the next two instructions. If the branch is taken, those two are wrong and are thrown away (flushed): a 2-cycle penalty. A branch predictor guesses the outcome early so that, most of the time, the right instructions are already in the pipe. For a loop that runs 1000 times, a simple 2-bit predictor guesses wrong only once (at loop exit).

3. Structural hazard: two instructions need the same hardware

If instructions and data come from the same single-port memory, a load in MEM and a fetch in IF cannot both happen in the same cycle, so the fetch waits. Separate instruction and data paths (separate buses or separate I- and D-caches) remove this. This is why nearly every modern CPU is "modified Harvard".

Check yourself: A program has 20% loads, and half of them are immediately followed by an instruction that uses the loaded value. Branches are 15% of instructions, 10% of them are mispredicted, and each mispredict costs 2 cycles. CPI = 1 + 0.20 × 0.5 × 1 + 0.15 × 0.10 × 2 = 1 + 0.10 + 0.03 = 1.13.

07Memory is slow: caches and their side effects

A cache keeps copies of recently used memory close to the core. It works because programs reuse data (temporal locality) and use neighbouring data (spatial locality).

How a cache finds data, with the Cortex-M7 D-cache of the STM32H743

The D-cache is 16 KB, 4-way set-associative, with 32-byte lines. That gives 16 384 / 32 = 512 lines, grouped into 512 / 4 = 128 sets of 4 lines each. A 32-bit address is cut into three fields:

offset = log2(32 bytes per line) = 5 bits   → address bits [4:0]
index  = log2(128 sets)          = 7 bits   → address bits [11:5]
tag    = 32 − 7 − 5              = 20 bits  → address bits [31:12]

Address 0x2400_0124:
  offset = 0x124 & 0x1F         = 0x04 = byte 4 of the line
  index  = (0x124 >> 5) & 0x7F  = 9    → look only in set 9
  tag    = 0x2400_0124 >> 12    = 0x24000 → compare with the 4 tags stored in set 9
  1. The index picks one set (set 9). Only that set is searched, which is what makes the cache fast.
  2. The four stored tags in set 9 are compared with 0x24000 at the same time. If one matches and its valid bit is set: hit, the data comes back in about 1 cycle.
  3. If none matches: miss. The cache picks one of the 4 ways to reuse (the least recently used one), fetches the whole 32-byte block 0x2400_0120–0x2400_013F from SRAM, and then returns the word. This takes tens of cycles.
  4. The next seven words (0x2400_0128, 0x2400_012C, …) are in the same line, so they hit. Reading an int32_t array in order: 1 miss then 7 hits per line, a hit rate of 7/8 = 87.5%.

The side effects you must manage on an MCU

  • DMA cannot see the cache. With a write-back cache, a value the CPU wrote may still be only in the cache when the DMA reads SRAM (it sends old data), and data the DMA wrote to SRAM may be hidden behind an old cached copy (the CPU reads old data). Software fixes it with "clean" (push dirty lines to memory) and "invalidate" (drop stale lines), or by marking DMA buffers non-cacheable with the MPU.
  • Timing becomes variable. The same function takes 2350 cycles when its code is cached and 4700 when it is not. For hard real-time code, put it in TCM instead.
  • Peripherals must never be cached. Reading a UART data register removes a byte from its FIFO, so a cache line fill that reads 32 bytes around it would destroy data. The memory map marks peripheral addresses as "Device" memory so this cannot happen.
Check yourself: 1 cycle for a hit, 20 cycles extra for a miss, hit rate 87.5%. Average memory access time = 1 + 0.125 × 20 = 3.5 cycles. Formula: AMAT = hit time + miss rate × miss penalty.

ISA vs microarchitecture: the contract and the implementation

▶

1.What is it?

The ISA (instruction set architecture) is the rulebook that software is written against: which instructions exist, what each one does to the registers and memory, how they are encoded as bits, and what happens on an interrupt or a fault. The microarchitecture is one particular piece of hardware that follows that rulebook: how many pipeline stages it has, whether it has caches, how it predicts branches.

An analogy: the ISA is the driving code (what the pedals and the steering wheel must do); a microarchitecture is one specific car. Every car obeys the same controls, but a sports car and a small city car reach 100 km/h in very different times.

Two terms you will meet: ARMv7E-M is an ISA (the "E" adds DSP instructions to ARMv7-M). Cortex-M4 and Cortex-M7 are processors (microarchitectures) that implement it.

2.How does it work, step by step?

  1. You choose the ISA at build time. -mcpu=cortex-m4 tells GCC "emit only ARMv7E-M instructions, and order them to suit the M4 pipeline".
  2. The binary contains ISA encodings. For example ADDS r3, r1, r2 becomes the 16-bit value 0x188B. That encoding is defined by the ISA, so every ARMv7-M core decodes it the same way.
  3. Each core produces the same architectural result. After the instruction, r3 holds r1 + r2 and the flags are set the same way on an M4 and an M7. This is the contract.
  4. Each core takes its own time. The M4 runs it in a 3-stage pipeline with no cache; the M7 may issue it together with another instruction in the same cycle. The ISA does not say how many cycles anything takes.

3.Worked example: the same binary on two cores

Dhrystone is a standard small benchmark. Arm publishes its score per MHz for each core: about 1.25 DMIPS/MHz for the Cortex-M4 and about 2.14 DMIPS/MHz for the Cortex-M7.

STM32F407 (M4) at 168 MHz:  168 × 1.25 = 210  DMIPS
STM32H743 (M7) at 480 MHz:  480 × 2.14 = 1027 DMIPS

The ISA is the contract between software and hardware: instructions, encodings, registers, the memory model and the exception model. Can two CPUs with the same ISA give different results for the same program?

Architecturally visible results must match (that is the contract), except where the ISA marks behaviour UNPREDICTABLE / IMPLEMENTATION DEFINED, and timing-dependent code (races, polling loops, uninitialised reads) which can behave differently. Performance can differ by 10× or more.

von Neumann vs Harvard vs modified Harvard (and what Cortex-M really is)

▶

1.What is it?

These three names describe how instructions and data reach the CPU. Every instruction must be fetched from memory, and many instructions also read or write data in memory. The question is whether those two kinds of traffic share one path or have separate paths.

  • von Neumann: one memory and one bus for both instructions and data. Simple and cheap.
  • Harvard: two separate memories with two separate buses, often with separate address spaces (address 0x0010 in program memory and address 0x0010 in data memory are different places).
  • Modified Harvard: separate paths (buses or caches) for instructions and data, but one shared address space. Any address can hold code or data; the split exists only to double the bandwidth. Almost every modern CPU, including every Cortex-M3 and above, is modified Harvard.

2.How does it work, step by step?

Consider one cycle in which instruction I2 must be fetched while the earlier instruction LDR r1, [r0] needs to read data.

  1. von Neumann: both requests want the single bus. One must wait. The fetch is delayed by a cycle. This conflict is a structural hazard, and the general limit it creates is called the "von Neumann bottleneck". The Cortex-M0 and M0+ have one AHB-Lite bus master, so at the bus level they behave like this.
  2. Harvard (8051, AVR, PIC): the fetch goes to program flash on one bus while the load goes to data RAM on the other. Both finish in the same cycle. But because the address spaces are separate, an ordinary load cannot read program memory: AVR needs the special LPM instruction to read a constant from flash.
  3. Modified Harvard (Cortex-M3/M4): the core has three bus masters. I-Code fetches instructions from the code region (0x0000_0000–0x1FFF_FFFF, where flash lives). D-Code does data reads (literal pools, const tables) from the same region. System handles everything at 0x2000_0000 and above (SRAM and peripherals). A fetch from flash and a load from SRAM run in parallel, yet a normal LDR can still read flash, because it is one address space.
  4. Modified Harvard (Cortex-M7, Cortex-A): the split happens at the L1 caches: a separate I-cache and D-cache, both backed by the same memory.

3.Worked example: why copying code to SRAM can make it slower on an M4

Take a loop on an STM32F407 that does one load from SRAM for every three other instructions.

  1. Code in flash. Instructions arrive on I-Code. The ART accelerator reads flash 128 bits (8 Thumb-16 instructions) at a time and caches 64 such lines, so a loop that fits in the ART runs with effectively 0 wait states. The SRAM load uses the System bus. The two never collide.
  2. Code copied to SRAM. Now the instruction fetches also use the System bus, because SRAM sits above 0x2000_0000. Every time the load and a fetch want the System bus in the same cycle, one of them waits. In a simple model where each load collides with one fetch, a 4-instruction iteration that took 5 cycles (LDR = 2 cycles) now takes about 6: 20% slower.
  3. When SRAM code does help: code with many random branches that keep missing the 64-line ART cache, or code that must keep running while the flash bank it lives in is being erased or programmed (flash cannot be read during its own erase).

Two STM32F4-specific details: the 64 KB CCM RAM at 0x1000_0000 is connected only to the D-bus, so it can hold data and stacks but cannot execute code. And SYSCFG can remap SRAM1 to address 0x0, which puts it on the I-Code/D-Code buses and removes the contention.

Von Neumann shares one bus for instructions and data, so a fetch and a load collide. Harvard has separate memories and address spaces, like AVR, where reading flash constants needs LPM. Cortex-M3 and above are modified Harvard: separate I-Code, D-Code and System buses, or split L1 caches on the M7, but one flat 4 GB address space. Faster only when flash has a cache miss problem (random branches) or you are erasing the same flash bank.

RISC vs CISC, and why the distinction blurred

▶

1.What is it?

RISC and CISC are two philosophies for designing an ISA. RISC (reduced instruction set computer) uses many simple instructions that each do one small thing, and only loads and stores touch memory. CISC (complex instruction set computer) has instructions that can do several things at once, such as reading memory, adding, and writing memory back, in one instruction.

2.How does it work, step by step? The same C statement on both

/* C */
a[i] += x;

; x86-64 (CISC): one instruction
add   DWORD PTR [rdi + rsi*4], edx

; ARM Thumb-2 (RISC): three instructions
ldr   r3, [r0, r1, lsl #2]     ; load a[i]
add   r3, r3, r2               ; add x
str   r3, [r0, r1, lsl #2]     ; store a[i]
  1. The x86 decoder reads a variable-length instruction (here 3 bytes) and must first find where it ends before it can start on the next one.
  2. Inside the core, the x86 instruction is split into simpler micro-operations (µops): a load, an add and a store. Some of them are fused back together for bookkeeping, but they execute as separate steps.
  3. The ARM core decodes three fixed-format instructions, each of which is already one simple step.
  4. So both machines end up doing load, add, store. The difference is where the splitting happens: in the compiler (RISC) or in the decoder (CISC).

3.Worked example: the Iron Law decides, not the label

The Iron Law of performance is: time = instructions × CPI × clock period. CPI means cycles per instruction.

CISC version: 1 instruction × CPI 3 × 0.25 ns = 0.75 ns
RISC version: 3 instructions × CPI 1 × 0.25 ns = 0.75 ns   → identical

Code size:  x86 3 bytes   ·   Thumb-2 2 + 2 + 2 = 6 bytes (16-bit forms)
            A32 (classic 32-bit ARM) 3 × 4 = 12 bytes

RISC trades more instructions for a lower CPI and a simpler pipeline; CISC the reverse. With modern implementations both reach similar instructions per cycle. What really still differs is decode cost (fixed-width AArch64 lets Apple decode 8 instructions per cycle cheaply; x86 needs extra length-decoding logic and a µop cache) and the memory model (ARM is weakly ordered; x86 is TSO, total store order, which forbids most reordering).

Thumb-2 on Cortex-M mixes 16-bit and 32-bit encodings. It gives roughly the density of the old 16-bit Thumb with the capability of 32-bit ARM, typically about a quarter smaller than A32 code. Cortex-M executes only Thumb, which is why vector-table entries and function pointers have bit 0 set to 1.

RISC is a load/store design with simple fixed-width instructions and many registers, built to pipeline well. CISC lets ALU instructions use memory operands and has variable-length encodings. Is RISC always faster than CISC?

No. Performance = instructions × CPI × cycle time (Iron Law). RISC trades more instructions for lower CPI and simpler, faster pipelines; CISC trades the reverse. Modern implementations of both reach similar IPC; the ISA mainly affects decode width, power and code size.

Endianness: byte order in memory

▶

1.What is it?

Memory is addressed in bytes, but a CPU register holds 4 bytes. Endianness is the rule for which byte of a multi-byte number goes at the lowest address. Little-endian stores the least significant byte (the "little end") first. Big-endian stores the most significant byte first. Cortex-M, x86 and RISC-V are little-endian; network protocols ("network byte order") and many CAN signal definitions are big-endian.

2.How does it work, step by step?

Execute STR r0, [r1] with r0 = 0x12345678 and r1 = 0x2000_0000:

  1. The register holds the number 0x12345678. The most significant byte is 0x12, the least significant is 0x78.
  2. The store writes 4 bytes to addresses 0x2000_0000 to 0x2000_0003.
  3. On a little-endian CPU, byte 0x78 goes to the lowest address, then 0x56, 0x34, 0x12.
  4. A later LDR of the same address puts them back the same way, so a CPU reading its own data always gets 0x12345678. Endianness only matters when bytes cross between systems or between byte arrays and wider types.
Address+0+1+2+3
Little-endian (Cortex-M, x86, RISC-V)78563412
Big-endian (network order, PowerPC, 68k, CAN DBC "Motorola")12345678
  • ARM supports both in the architecture. On ARMv7-M endianness is fixed at reset (the BIGEND input; AIRCR.ENDIANNESS is read-only) and most MCUs, including all STM32, are little-endian only. ARMv7-A/v8-A can use BE8 (byte-invariant big-endian) for data; instruction fetches stay little-endian.
  • Endianness applies to multi-byte scalars in memory. It does not affect the bit order inside a register, the shift operators, or the order of elements in a byte array.

3.Worked example: reading a big-endian field from a packet

A sensor sends a 32-bit big-endian value of 300 (0x0000012C). On the wire the bytes arrive as 00 00 01 2C and land in buf[0..3].

Correct value:  (0x00 << 24) | (0x00 << 16) | (0x01 << 8) | 0x2C = 0x0000012C = 300

Wrong (cast on a little-endian CPU): *(uint32_t *)buf
  little-endian load: buf[0] | buf[1] << 8 | buf[2] << 16 | buf[3] << 24
                   = 0x00 | 0x00 | 0x01 << 16 | 0x2C << 24
                   = 0x2C010000 = 738 263 040

A value of 738 263 040 when you expected 300 is the classic signature of a byte-order mistake: the low bytes of the true value appear as the high bytes.

Memory-mapped I/O, buses and wait states

▶

1.What is it?

Memory-mapped I/O (MMIO) means that peripheral registers (GPIO, UART, timers) appear as ordinary addresses. To set a pin you store a value to an address, exactly as you would store to a variable. ARM has no special I/O instructions (x86 has IN/OUT for a separate port space). What makes a peripheral address different from RAM is the memory type attached to it: Device or Strongly-ordered memory, which the CPU may not cache, may not read early (speculatively), may not merge, and may not reorder against other accesses to the same device.

Two more words: a wait state is an extra clock cycle the CPU waits because a memory is too slow to answer in one cycle. A write buffer lets the CPU continue with the next instruction before a store has actually reached its destination.

2.How does it work, step by step? GPIOA->BSRR = 1u << 5; on an STM32F407

  1. The compiler emits STR r1, [r0] with r0 = 0x4002_0018 (GPIOA base 0x4002_0000 + BSRR offset 0x18) and r1 = 0x0000_0020.
  2. The core issues a write on the System bus. The bus matrix decodes the address: 0x4002_xxxx belongs to AHB1, running at 168 MHz.
  3. The default memory map says 0x4000_0000–0x5FFF_FFFF is Device memory, execute-never. So the write is not cached and not merged with neighbouring writes.
  4. The core's write buffer accepts the store and the core continues with the next instruction while the bus transaction completes.
  5. GPIOA receives the write. Writing 1 to BSRR bit 5 sets output bit 5 (bit 21 would reset it). Pin PA5 goes high.
  6. A write to a peripheral on APB1 (for example USART2 at 0x4000_4400) also crosses an AHB-to-APB bridge. APB1 runs at 42 MHz, so one APB clock is 4 core clocks, and the access costs several core cycles.

3.Worked example: addresses and flash wait states

GPIOA base           0x4002_0000
  ODR  offset 0x14 → 0x4002_0014   output data register
  BSRR offset 0x18 → 0x4002_0018   bits 0–15 set, bits 16–31 reset

Flash wait states at 168 MHz (2.7–3.6 V):
  one CPU cycle      = 1 / 168 MHz            = 5.95 ns
  flash access time  ≈ 30 ns  (0 WS allowed up to 30 MHz → 1 / 30 MHz = 33 ns)
  cycles needed      = ceil(33 / 5.95)          = 6 cycles
  wait states        = 6 − 1                    = 5   → FLASH_ACR.LATENCY = 5

Five wait states means every fresh flash read costs 6 cycles. The ART accelerator hides this by reading 128 bits (8 Thumb-16 instructions) per access and keeping 64 such lines in a small instruction cache plus 8 lines for data, so loops run at close to 0 wait states.

  2. The core executes the exception return immediately.
  3. The NVIC still sees TIM2's interrupt line high, because the flag has not actually been cleared yet.
  4. The NVIC takes the interrupt again. The ISR runs a second time with no new event.

Peripherals on ARM are memory-mapped: a register is just an address, and LDR or STR to it becomes a bus transaction. What makes it safe is the memory type, Device, which forbids caching, speculative reads, merging and reordering. volatile only constrains the compiler. Because of the write buffer a store may not have reached the peripheral when the next instruction runs, so I clear interrupt flags early or add a DSB, and I use BSRR rather than read-modify-write on ODR.
Why must peripheral pointers be volatile, and is volatile enough?

volatile forces the compiler to emit every access in program order relative to other volatile accesses. It does not stop the hardware from buffering or reordering (that is the memory type plus barriers), and does not make read-modify-write atomic.

Pipelining fundamentals: CPI, IPC and the Iron Law

▶

1.What is it?

A pipeline splits the work of executing one instruction into stages, and lets each stage work on a different instruction in the same clock cycle, like an assembly line. Between stages sit pipeline registers (also called latches): banks of flip-flops that hold everything the next stage needs (the instruction, the register values read, the ALU result) and pass it on at each clock edge.

Pipelining improves throughput (how many instructions finish per second). It does not reduce latency (how long one instruction takes from start to finish); latency actually rises slightly, because each latch adds a little delay.

MEM — memoryD-cache read (LDR) or write (STR); other instructions pass throughMEM/WB: loaded data or ALU result
WB — write-backWrite the result into the register file (first half of the cycle, so ID can read it in the second half of the same cycle)—
  1. Cycle 1: instruction I1 is fetched. The other four stages are empty.
  2. Cycle 2: I1 moves to ID (its bits are now in the IF/ID register); I2 is fetched.
  3. Cycles 3–4: the pipe keeps filling. I1 reaches MEM in cycle 4.
  4. Cycle 5: I1 writes back; I2 is in MEM, I3 in EX, I4 in ID, I5 in IF. All five stages are busy: the pipeline is full.
  5. From then on one instruction completes every cycle, as long as nothing stalls.

3.Worked examples with real numbers

(a) Cycle count. N instructions in a k-stage pipeline with no stalls take k + (N − 1) cycles: k cycles for the first one to come out, then one more per instruction.

N = 1000, k = 5:  pipelined   = 5 + 999  = 1004 cycles   (CPI = 1.004)
                  unpipelined = 5 × 1000 = 5000 cycles
                  speed-up    = 5000 / 1004 = 4.98  → approaches k as N grows

(b) CPI with stalls. CPI (cycles per instruction) = 1 + average stall cycles per instruction. IPC (instructions per cycle) = 1 / CPI. Suppose 20% of instructions are loads, half of which are followed by a dependent instruction (1 stall each), and 15% are branches, 10% of them mispredicted at 2 cycles each:

CPI = 1 + 0.20 × 0.5 × 1  +  0.15 × 0.10 × 2
    = 1 + 0.10            +  0.03            = 1.13      IPC = 1 / 1.13 = 0.88

(c) Why not 100 stages? Suppose all the logic for one instruction takes 10 ns, and every pipeline register adds 0.5 ns.

stages   logic per stage   + latch   = cycle time   clock
   1        10.0 ns          0.5        10.5 ns       95 MHz
   5         2.0 ns          0.5         2.5 ns      400 MHz
  20         0.5 ns          0.5         1.0 ns        1 GHz
 100         0.1 ns          0.5         0.6 ns      1.67 GHz   ← latch overhead dominates

Going from 20 to 100 stages only gains 1.67×, while the branch-mispredict penalty (proportional to the depth before branch resolution) grows 5×. Intel's 31-stage Prescott (2004) is the cautionary tale; designs settled at roughly 14–20 stages.

(d) The Iron Law. CPU time = instructions × CPI × Tclk. Every optimisation attacks one term, often at the expense of another: a deeper pipeline lowers Tclk but raises CPI through bigger penalties; loop unrolling lowers the instruction count but grows code size and can raise I-cache misses.

Your cycle estimate for a filter is off by 2×: either you counted every stage for every instruction (too high), or you ignored stall cycles (too low).
A pipeline overlaps instructions: k stages, one instruction entering per cycle, so N instructions take k plus N minus 1 cycles and steady-state CPI is 1 plus the stall cycles per instruction. It raises throughput and allows a faster clock, but does not shorten a single instruction's latency. Deeper pipelines hit diminishing returns because latch overhead is fixed per stage and the branch-mispredict penalty grows with depth. Performance is the Iron Law: instructions times CPI times clock period.
Does pipelining reduce the time to execute one instruction?

No. Each instruction still passes through every stage, plus latch delay. Pipelining raises throughput (instructions completed per cycle) and allows a higher clock because each stage does less work.

Real pipelines: M0+ → M4 → M7 → out-of-order application cores

▶

1.What is it?

The 5-stage IF/ID/EX/MEM/WB pipeline is a teaching model. Real cores choose their depth and width to suit their job. Microcontroller cores keep pipelines short so that branches and interrupts are cheap and timing is predictable. Application cores (phones, PCs) use long, wide, out-of-order pipelines to get the most instructions per second. Two new words: superscalar or dual-issue means the core can start more than one instruction in the same cycle; in-order means instructions still execute in program order.

2.How does it work, step by step? The Cortex-M4's 3 stages

  1. Fetch. The core reads 32 bits at a time over I-Code (two 16-bit instructions or one 32-bit one) into a small prefetch buffer of a few words, so it usually has instructions ready before decode needs them.
  2. Decode. The instruction is decoded and register operands are read. If it is a branch, the core starts fetching the branch target speculatively from here, which is why a taken branch costs only "1 + P" cycles instead of a full flush.
  3. Execute. ALU work, address generation, load/store, multiply (single-cycle 32 × 32 on M4), and write-back of the result all happen in this stage (and a second cycle for loads).
  4. No predictor. Every taken branch pays the refill cost P (1 to 3 cycles, depending on the target's alignment and on flash wait states), whether or not the branch is "predictable".
  5. Interrupt entry is 12 cycles (M3/M4/M7; M0+ is 15): the NVIC stacks 8 registers on the System bus while fetching the vector on I-Code in parallel. A late-arriving higher-priority interrupt can take over stacking already in progress. Long instructions such as LDM, STM and SDIV are abandoned or resumed (using the ICI bits in xPSR) so they do not add latency.

3.Worked example: the cost of a loop branch on an M4, and unrolling

Loop body: 3 single-cycle ALU instructions + BNE (taken), P = 1 (ART hit)
  per iteration = 3 + (1 + P) = 3 + 2 = 5 cycles    → branch overhead 2/5 = 40%

Unrolled ×4: 12 ALU instructions + 1 BNE per 4 elements
  per 4 elements = 12 + 2 = 14 cycles = 3.5 cycles per element   → 30% faster

Interrupt latency at 168 MHz: 12 cycles × 5.95 ns = 71 ns  (plus flash wait states
on the vector fetch if the ART misses)

On the M7 the same loop behaves differently: the branch predictor makes the back-edge almost free once it has learned it, and the core may issue two ALU instructions per cycle, so the gain from unrolling is smaller and less predictable. That is why M7 timing must be measured, not computed from a table.

5.What goes wrong if…

…you say "the Cortex-M4 has a 5-stage pipeline"? It has 3. The interviewer concludes you learned the textbook but never read a Cortex-M manual. …you assume the M4 predicts branches? It does not, so a well-predicted branch still costs 1 + P cycles when taken. …you compute M7 timing from a cycle table? Dual-issue pairing, branch prediction and cache state make it vary.

On an M7, a function measured at 2 350 cycles in a unit test takes up to 4 700 cycles in the full system; on the M4 the same function always took 6 100 cycles. The M7 is faster on average and much less predictable.
The Cortex-M0+ has a 2-stage pipeline, the M3 and M4 have 3 stages with branch speculation in decode but no predictor, and the M7 has a 6-stage dual-issue in-order pipeline with a branch predictor and L1 caches. Application cores such as the A72 are 15-plus-stage out-of-order designs. MCUs keep pipelines short and in-order because interrupt latency and worst-case timing matter more than peak IPC; an M3 or M4 enters an interrupt in 12 cycles.
"The Cortex-M4 has a 5-stage pipeline." No: 3 stages. The 5-stage IF/ID/EX/MEM/WB pipeline is the textbook model (MIPS R2000/R3000 family), used to teach hazards.
Why is interrupt latency 12 cycles on M3/M4 regardless of the pipeline?

The NVIC stacks the 8-word frame in parallel with fetching the vector (separate buses), and a late-arriving higher-priority IRQ can take over the in-progress stacking. Multi-cycle instructions like LDM/STM/SDIV are abandoned or continued (ICI bits) so they do not add latency. On M7 the figure is similar but caches and memory latency add variance.

Hazards: structural, data (RAW/WAR/WAW), control; forwarding and the load-use stall

▶

1.What is it?

A hazard is anything that stops the next instruction from entering the next stage in the next cycle. There are three kinds:

  • Structural: two instructions need the same piece of hardware in the same cycle (for example one memory port for both a fetch and a load).
  • Data: an instruction needs a value that an earlier instruction has not produced yet.
  • Control: the CPU does not yet know which instruction comes next, because a branch has not been decided.

Data hazards have three names. RAW (read after write) is a true dependence: I2 reads what I1 writes. WAR (write after read) and WAW (write after write) are name dependences: they exist only because two different values happen to use the same register name.

TypePatternIn-order 5-stage?Out-of-order?

WAR (anti-dependence)I1 reads r1, I2 writes r1No: reads (ID) always happen before later writes (WB)Yes: removed by register renaming
WAW (output dependence)I1 writes r1, I2 writes r1No: writes happen in order in WBYes: removed by renaming; ROB retires in order

2.How does it work, step by step? Forwarding and the load-use stall

Without forwarding, a result is usable only after it is written to the register file in WB. Because the register file is written in the first half of a cycle and read in the second half, an instruction in ID can read a value written in WB in the same cycle.

no forwarding:      1   2   3   4   5   6   7   8
ADD r1, r2, r3      IF  ID  EX  ME  WB
SUB r4, r1, r5          IF  ID  ID  ID  EX  ME  WB      SUB reads r1 in ID of cycle 5
                                ^^  ^^ 2 stall cycles    (same cycle as ADD's WB)

With forwarding (also called bypassing), multiplexers in front of the ALU inputs can take a value straight from the EX/MEM or MEM/WB pipeline register instead of the register file:

with forwarding:    1   2   3   4   5   6
ADD r1, r2, r3      IF  ID  EX  ME  WB
SUB r4, r1, r5          IF  ID  EX  ME  WB      r1 taken from EX/MEM in cycle 4: 0 stalls

LDR r1, [r2]        IF  ID  EX  ME  WB
ADD r3, r1, r4          IF  ID  **  EX  ME  WB  data exists only at the END of MEM (cycle 4)
                                                → forwarded MEM/WB → EX in cycle 5: 1 stall
  1. The ALU result of ADD exists at the end of cycle 3 (EX). SUB needs it at the start of cycle 4 (its EX). The forwarding unit sees "EX/MEM's destination is r1, and SUB's source is r1" and selects the EX/MEM value: no stall.
  2. A load's value comes from the D-cache, at the end of MEM (cycle 4). The dependent ADD would need it at the start of cycle 4. No wire can send a value back in time, so one bubble is unavoidable in hardware.
  3. The hazard detection unit sits in ID. When the instruction in EX is a load whose destination matches a source of the instruction in ID, it (a) holds the PC, (b) holds the IF/ID register, and (c) turns the control signals going into ID/EX into zeros, which injects a bubble (NOP) into EX.
  4. The compiler removes the bubble by scheduling an independent instruction into the slot after the load (instruction scheduling, done at -O2).

With full forwarding, which dependency still stalls a 5-stage pipeline, and how does the compiler hide it?

The load-use dependency: a load's data is available only at the end of MEM, so a dependent ALU op in the next slot waits one cycle. The compiler schedules an independent instruction between them (or unrolls loops to create independent work).

Branch prediction: static, 1-bit, 2-bit, BTB, return stack, modern predictors

▶

1.What is it?

A branch predictor guesses, at fetch time, whether a branch will be taken and where it will go, so the pipeline can keep fetching without waiting for the branch to be decided. If the guess is right, the branch costs nothing. If it is wrong (a misprediction), every instruction fetched after the branch is thrown away (flushed) and fetching restarts at the correct address.

Two separate questions are predicted: the direction (taken or not) and the target (where to). A BTB (branch target buffer) is a small cache indexed by the fetch address that answers "is this a branch, and where does it go?" before the instruction is even decoded.

2.How does it work, step by step? From simple to modern

  • Static: always not-taken (no hardware), always taken, or BTFN (backward taken, forward not taken: loop back-edges go back, error checks jump forward). The compiler lays out code to suit it: __builtin_expect / likely() moves the cold path out of line.
  • 1-bit: one bit per branch remembers the last outcome.
  • 2-bit saturating counter: states 00 strong-NT, 01 weak-NT, 10 weak-T, 11 strong-T; predict taken if the value is ≥ 2; add 1 when taken, subtract 1 when not, stopping at 0 and 3. One surprise does not flip a strong state.
  • BTB: gives the target in the IF stage. Without it, "predict taken" cannot be acted on until decode computes the target.
  • RAS (return address stack): pushed on BL, popped on BX LR / POP {PC} / RET. A function returns to many different places, so a BTB predicts returns badly; a RAS is nearly perfect until it overflows (deep recursion).
  • Correlating / global: gshare (fetch PC XOR a global history register of recent outcomes indexes the counter table), tournament predictors (Alpha 21264), TAGE (several tables using geometrically longer histories; state of the art), perceptron predictors (AMD Zen). Indirect predictors handle virtual calls and switch tables.

3.Worked example: a 4-iteration loop run twice

The loop's back-edge branch has the outcome pattern T T T N (taken three times, then falls through), and the loop is entered twice. Both predictors start in "not taken".

Outcome1-bit: predict → new✓/✗2-bit: predict (state) → new✓/✗

run 1 · TT → T✓T (10) → 11✓

In steady state the 1-bit predictor misses twice per loop execution (at the exit, and again on re-entry because the exit flipped it). The 2-bit counter misses once (only the exit), because the exit only drops it from 11 to 10, which still predicts taken.

The cost of a misprediction is roughly the number of stages between fetch and the stage where the branch is resolved: 2 cycles in the textbook pipeline resolving in EX, 1–3 on a Cortex-M4 (no predictor: every taken branch pays refill), about 8 on a Cortex-A53, about 13–20 on big out-of-order cores.

Data-dependent branch on random data, 4 GHz core, 17-cycle penalty:
  mispredict rate ≈ 50%  → average cost = 0.5 × 17 = 8.5 cycles per iteration
                          = 8.5 × 0.25 ns = 2.1 ns   (more than an L2 cache hit)
Same data sorted       → rate ≈ 0%  → ≈ 0 cycles

5.What goes wrong if…

…a hot loop branches on random data? Half the branches flush the pipeline. …you use a function-pointer table for a state machine with random events? The indirect predictor cannot guess the target. …you recurse deeply? The RAS (often 8–32 entries) overflows and returns start mispredicting.

    if (d[i] >= 128) s += d[i];

On a Cortex-M4 the picture is different: there is no predictor, so a taken branch costs 1 + P cycles whether the data is sorted or not, and branchless code helps only by removing the taken-branch refill.

A branch predictor guesses the direction and target at fetch so the pipeline does not wait. A 2-bit saturating counter per branch adds hysteresis, so a loop mispredicts once per execution instead of twice with a 1-bit scheme. The BTB supplies the target in the fetch stage, a return stack predicts returns, and modern cores use global-history predictors such as TAGE. A mispredict costs about the depth to branch resolution, roughly 15 to 20 cycles on a big core, so for unpredictable data I make the code branchless with a mask or a conditional select.
Why does a 2-bit counter beat a 1-bit predictor on loops?

A 1-bit predictor mispredicts on the loop exit and again on the first iteration of the next run, because the exit flipped it. A 2-bit counter in strong-taken only drops to weak-taken on the exit, so the next run's first iteration is still predicted taken: one mispredict per loop instead of two.

The memory hierarchy and the latency numbers every engineer should know

▶

1.What is it?

The memory hierarchy is the stack of memories between the core and the bulk storage: registers, L1 cache, L2, L3, DRAM, flash or disk. It exists because of a physical trade-off: memory that is big is slow and far away; memory that is fast is small and close. A hierarchy gives you, most of the time, the speed of the small memory with the size of the big one.

It works because programs have locality. Temporal locality: data used now is likely to be used again soon (a loop counter, a stack frame). Spatial locality: data near what was just used is likely to be used next (the next array element, the next instruction).

2.How does it work, step by step? One load on a desktop core

  1. The load looks in L1. Hit: about 4–5 cycles (≈ 1 ns). Done.
  2. L1 miss: the request goes to L2. Hit: about 12–16 cycles (≈ 3–4 ns). The line is copied into L1.
  3. L2 miss: L3 (shared by the cores). Hit: about 40–70 cycles (≈ 10–20 ns).
  4. L3 miss: the memory controller opens a DRAM row and reads the line: about 80–100 ns, i.e. 300–400 cycles at 4 GHz.
  5. Each level keeps a copy on the way back, betting on locality.

3.Worked example: latency versus bandwidth

How much work fits in one DRAM miss?
  100 ns × 4 GHz = 400 cycles;  4-wide core → up to 1 600 instruction slots lost

Walking a linked list of 1 000 000 nodes, cold:
  each node's address comes from the previous load (a "pointer chase")
  → misses cannot overlap: 1 000 000 × 100 ns = 100 ms

Reading an array of 1 000 000 × 8-byte values sequentially:
  8 MB / ~20 GB/s (one DRAM channel, prefetcher streaming) ≈ 0.4 ms   → 250× faster

The array and the list hold the same amount of data. The array is fast because its addresses are predictable, so the hardware prefetcher fetches lines ahead and many misses are in flight at once (memory-level parallelism). The list is slow because each address is known only after the previous load returns: pure latency.

Cache organisation: direct-mapped, set-associative, fully associative; tag/index/offset

▶

1.What is it?

A cache stores fixed-size blocks of memory called lines: 32 bytes on the Cortex-M7, 64 bytes on most application cores. For each line it also stores a tag (which memory block the line holds), a valid bit (does this slot hold anything?) and, for write-back caches, a dirty bit (has the line been changed since it was loaded?). Lines are grouped into sets. A given address may be stored only in one particular set, but in any of that set's ways (slots).

OrganisationWays per setProsCons
Direct-mapped1One tag compare, fastest hit, cheapestConflict misses: two hot addresses that map to the same set evict each other ("ping-pong")
N-way set-associativeN (2–16)Most conflicts disappear by 4–8 waysN comparators, way multiplexer, replacement state
Fully associativeall lines (1 set)No conflict missesCompare every tag: used only for small structures (TLBs, BTBs, victim caches)

2.How does it work, step by step? One lookup

lines     = cache_size / line_size
sets      = lines / ways
offset    = log2(line_size)            // which byte within the line
index     = log2(sets)                 // which set
tag       = address_bits - index - offset

| ←────────── tag ──────────→ | ←─ index ─→ | ← offset → |
  1. Split the address. The low offset bits select a byte inside a line, the next index bits select the set, and the remaining high bits are the tag.
  2. Read the set. The index addresses a small SRAM that returns all N ways of that set at once: N tags, N valid bits, N lines of data.
  3. Compare tags in parallel. N comparators check each stored tag against the address tag. A way with a match and valid = 1 is a hit.
  4. Select the data. The matching way's line goes through a multiplexer, and the offset picks the bytes.
  5. On a miss, the cache chooses a way to replace (see the next card), writes it back first if it is dirty, fetches the whole line from the next level (a line fill, often "critical word first" so the requested word arrives first), and stores the new tag.

3.Worked examples

Cortex-M7 STM32H743 D-cache: 16 KB, 4-way, 32 B lines, 32-bit addresses.

The index bits [11:6] lie entirely inside the 12-bit page offset, which is the same in the virtual and the physical address. So the L1 can start indexing with the virtual address while the TLB translates in parallel, and compare against the physical tag: VIPT (virtually indexed, physically tagged) without aliasing. That is why L1 caches grow by adding ways rather than sets.

Overhead: each line costs tag + valid + dirty (+ replacement) bits. For the H743 example: 512 × (20 + 1 + 1) = 11 264 bits ≈ 1.4 KB of tag SRAM to manage 16 KB of data.

With 4 KB direct-mapped, addresses 4096 bytes apart have the same index and different tags. a[i] loads its line, b[i] evicts it, a[i+1] (same line as a[i]) misses again: every access misses, 0% hit rate, even though the data (8 KB) would fit in an 8 KB cache. With 2 ways, both lines live in the same set side by side.

A dot-product runs at one-quarter of the expected speed for array sizes that are powers of two, and at full speed if you change the size to 1000 elements.
A cache is organised as sets of N ways of fixed-size lines. Offset is log2 of the line size, index is log2 of the number of sets, and the tag is what is left. Lookup uses the index to read one set, compares all N tags in parallel, and the offset selects the bytes. For the Cortex-M7's 16 KB 4-way cache with 32-byte lines, that is 128 sets, so 5 offset bits, 7 index bits and a 20-bit tag. More ways mean fewer conflict misses but more comparators; doubling the ways at the same size moves one bit from the index into the tag.
You double the associativity but keep size and line size. What happens to the tag and index widths?

Sets halve, so index loses one bit and the tag gains one bit. Offset unchanged. Hit time may rise slightly (more comparators and a wider way mux), conflict misses fall.

Replacement and write policies; inclusive vs exclusive; I-cache vs D-cache

▶

1.What is it?

A cache needs three policies. The replacement policy decides which way of a full set to throw out on a miss. The write-hit policy decides whether a store updates memory immediately (write-through) or only the cache (write-back, memory updated later when the dirty line is evicted). The write-miss policy decides whether a store that misses first brings the line into the cache (write-allocate) or just writes memory around the cache (no-write-allocate).

2.How does it work, step by step?

Replacement:

  • LRU (least recently used): evict the way unused for the longest time. Exact LRU for N ways needs log2(N!) bits per set (5 bits for 4-way, 16 for 8-way) and an update on every hit: expensive above 4 ways.
  • Pseudo-LRU (tree-PLRU): N − 1 bits per set form a binary tree whose bits point away from the most recently used half. 3 bits for 4-way. A good approximation, used widely in L1/L2.
  • FIFO / round-robin: evict the oldest fill, ignoring hits. Cheap; suffers Belady's anomaly (more ways can give more misses for some traces).
  • Random: needs only an LFSR (a cheap pseudo-random generator). Surprisingly close to LRU at high associativity and immune to the pathological case where a loop is one line larger than the cache (LRU gets 0% hits there; random does not).
  • Modern last-level caches use adaptive schemes (RRIP, DRRIP) that resist one-off scans.
Write policyOn write hitOn write missNotes
Write-back + write-allocateUpdate the line, set dirty; memory updated only on evictionFetch the line (allocate), then writeLeast bus traffic. Default for Normal memory (Cortex-M7 SRAM region). Memory is stale until clean/evict: DMA danger.
Write-through + no-write-allocateUpdate line and memory (via write buffer)Write memory only ("write-around")Memory always current; more bus traffic. Cortex-M7 default for the Code region (0x0–0x1FFF_FFFF) and 0x8000_0000 external RAM.
Write-through + write-allocateBothAllocate then write throughLess common.

A write buffer holds pending stores so the core does not stall on write-through; write-combining merges adjacent stores to the same line (allowed for Normal and Device-GRE memory, not for Device-nGnRE/nGnRnE).

Multi-level policies: Inclusive: every L1 line is also in L2/L3; snoops can be filtered by the last-level cache alone, but capacity is duplicated and evicting from L3 forces back-invalidation of L1 (historically Intel client L3). Exclusive: a line is in L1 or L2, never both; total capacity = sum; L2 acts as a victim cache (AMD's L3 is a victim cache of L2). NINE (non-inclusive non-exclusive): no guarantee either way; most modern designs.

I-cache vs D-cache: a split L1 doubles bandwidth (fetch and load in the same cycle) and lets each be tuned: the I-cache is read-only (no dirty bits, no write-back) and often has fewer ways (M7: I-cache 2-way, D-cache 4-way). The cost: on ARM the I-cache is not coherent with data stores. Code written as data (bootloader copy, JIT, flash patch) needs explicit D-clean + I-invalidate + barriers.

  stores: 8 misses → 8 line fills (8 × 16 B = 128 B read), all later stores hit, lines dirty
  loads : 32 hits

    if (way < 2) { plru |=  1u;  plru = (way == 0) ? (plru | 2u) : (plru & ~2u); }
    else         { plru &= ~1u;  plru = (way == 2) ? (plru | 4u) : (plru & ~4u); }
}

    if (plru & 1u) return (plru & 4u) ? 3 : 2;   // root says "go right"
    else           return (plru & 2u) ? 1 : 0;   // root says "go left"
}

Replacement picks the victim on a miss: true LRU is ideal but costs log2 of N factorial bits per set, so hardware uses tree pseudo-LRU with N minus 1 bits, or random at high associativity. Write-back with write-allocate keeps traffic low but leaves memory stale until a dirty line is evicted, which is why DMA buffers need cleaning or invalidating. When would you choose write-through over write-back?

When memory must always be current for another observer without software cleaning (DMA, another non-coherent master, a debugger reading RAM), when the line may be lost (power-fail logging), or for simpler coherency. Cost: every store goes on the bus, so write-heavy code becomes bandwidth-bound.

Cache misses: the 3 Cs, AMAT, and the performance cliff

▶

1.What is it?

Every cache miss has a cause, and the cause tells you the fix. Mark Hill's 3C model sorts misses into three groups, and AMAT (average memory access time) turns a miss rate into the number that actually matters: cycles.

Miss typeDefinitionReduce with
Compulsory (cold)First ever access to the line. Would miss even in an infinite cache.Larger lines, prefetching
CapacityMisses that a fully associative cache of the same size (LRU) would also take: the working set does not fit.Bigger cache, tiling/blocking, smaller data types
ConflictThe remaining misses: a fully-associative cache would hit, but this set is full.More ways, padding arrays, changing strides, victim cache
Coherence (4th C)Line invalidated by another core's write.Avoid sharing/false sharing

2.How does it work, step by step? Classifying one miss

  1. Is this the first time this line address has ever been touched? Yes → compulsory.
  2. Otherwise, imagine a fully associative LRU cache with the same number of lines, fed the same access stream. Would that cache also miss? Yes → capacity (too many distinct lines were used since the last touch).
  3. Otherwise (the ideal cache would have hit) → conflict: the line was evicted only because its set has too few ways.

The Cache Lab classifies every miss with exactly this procedure by running a shadow fully associative LRU cache alongside the real one.

3.Worked example: AMAT and CPI

AMAT = HitTimeL1 + MissRateL1 × MissPenaltyL1
MissPenaltyL1 = HitTimeL2 + MissRateL2,local × MissPenaltyL2

e.g. 1 + 0.05 × (10 + 0.20 × 100) = 1 + 0.05 × 30 = 2.5 cycles
global L2 miss rate = 0.05 × 0.20 = 1% of all accesses go to DRAM

CPIeff = CPIbase + (mem refs / instr) × MissRate × MissPenalty
  1. L1 hit time 1 cycle. 5% of accesses miss L1.
  2. Those go to L2, which takes 10 cycles. 20% of them (the L2's local miss rate) miss again and pay 100 cycles to DRAM.
  3. So an L1 miss costs on average 10 + 0.2 × 100 = 30 cycles, and AMAT = 1 + 0.05 × 30 = 2.5 cycles.
  4. With 1.3 memory references per instruction and a base CPI of 1: CPI = 1 + 1.3 × 0.05 × 30 = 1 + 1.95 = 2.95. Two-thirds of the time is waiting for memory.
  5. Without the L2: AMAT = 1 + 0.05 × 100 = 6 cycles. The L2 more than halves it.

Line size trade-off: bigger lines reduce compulsory misses (more spatial locality per miss) but increase the miss penalty and, for a fixed cache size, reduce the number of lines, raising conflict and capacity misses. Miss rate versus line size is U-shaped.

The cliff: time per element versus array size is a staircase: flat while the array fits in L1, a jump at the L1 size, another at L2 and L3, then DRAM. With LRU and a loop that streams over an array slightly larger than the cache, every access misses, because LRU always evicts exactly the line needed next.

4.Code, line by line: AMAT as a function

double amat(double ht1, double mr1, double ht2, double mr2_local, double mem) {
    double penalty1 = ht2 + mr2_local * mem;   // cost of going below L1
    return ht1 + mr1 * penalty1;               // average per access
}
double cpi_eff(double cpi0, double refs_per_instr, double mr1, double penalty1) {
    return cpi0 + refs_per_instr * mr1 * penalty1;
}
/* amat(1, 0.05, 10, 0.20, 100) = 2.5   cpi_eff(1, 1.3, 0.05, 30) = 2.95 */

The other classic mistake is fixing the wrong C: padding arrays (a conflict fix) when the working set simply does not fit (capacity), or buying a bigger cache when the problem is a power-of-two stride (conflict).

You add padding and nothing improves: the misses were capacity misses. You double the cache in a simulation and only one kernel improves: its misses were capacity; the others were conflict or compulsory.
I classify misses with the 3C model: compulsory is the first touch, capacity is what a fully associative cache of the same size would also miss, and conflict is the rest, caused by too few ways. Each has its own fix: prefetch or bigger lines, tiling or a bigger cache, more ways or padding. I never quote a miss rate alone; I convert it to AMAT, hit time plus miss rate times miss penalty, or to stall CPI. With 1 cycle hits, 5% misses, a 10-cycle L2 and 20% local L2 misses to 100-cycle DRAM, AMAT is 2.5 cycles.
A loop's miss rate is 2%. Is that good?

It depends on the penalty and the access rate. With a 100-cycle penalty and one memory reference per instruction, 2% adds 2 cycles per instruction, tripling CPI from 1 to 3. Always convert miss rate into AMAT or stall cycles.

Cortex-M7: TCM vs cache, enabling caches, and cache maintenance

▶

1.What is it?

The Cortex-M7 offers two kinds of fast memory. The L1 caches (I-cache and D-cache) automatically keep copies of whatever was used recently; you do nothing, but you cannot control what stays. TCM (tightly coupled memory) is ordinary SRAM wired directly to the core: ITCM for instructions, DTCM for data. It always answers in 0 wait states at the core clock, it is never cached and never evicted, and you decide what lives there through the linker script.

Three cache-maintenance words you need: clean = write any dirty lines in a range back to memory (the cache keeps them); invalidate = mark lines in a range as invalid, discarding their contents; clean + invalidate = both.

2.How does it work, step by step?

Getting code into ITCM:

  1. Mark the function with a section attribute, e.g. __attribute__((section(".itcm_text"))).
  2. The linker script places that section at the ITCM address (0x0000_0000) for execution, but stores its bytes in flash (the "load address"), because ITCM is RAM and loses its contents at power-off.
  3. The startup code copies the bytes from the flash load address to ITCM before main(), exactly as it copies .data.
  4. After the copy: __DSB(); __ISB(); so that no stale prefetched instructions are used.
  5. Calls to the function now jump to ITCM and run at 0 wait states every time.

Enabling the caches (what the CMSIS functions do):

  1. SCB_EnableICache(): invalidate the whole I-cache (write ICIALLU), DSB + ISB, set CCR.IC (bit 17), DSB + ISB.
  2. SCB_EnableDCache(): read CCSIDR to learn the geometry, invalidate every line by set/way (DCISW) because the cache contents are random after reset, DSB, set CCR.DC (bit 16), DSB + ISB.

(b) Why DMA buffers must be line-aligned. A 100-byte RX buffer at 0x2400_0F14:

  0x2400_0F00–0x2400_0F13 (20 bytes before the buffer) and
  0x2400_0F78–0x2400_0F7F (8 bytes after it)
→ if a neighbouring variable there was dirty in the cache, its new value is lost.

Fix: align the buffer to 32 and round its size up: ceil(100 / 32) × 32 = 128 bytes.

Invalidate RX buffers before starting the DMA as well as after: a dirty line evicted during the transfer would overwrite fresh DMA data with stale CPU data.
Your 20 kHz motor-control ISR shows 3 µs jitter on an STM32H7. What do you change?

Place the ISR and its data in ITCM/DTCM (linker sections), put its stack in DTCM, make sure the vector table is in ITCM or a cache-hot area, and avoid accesses to slow AXI/AHB memories in the ISR. Cache hits are fast but a miss to flash costs tens of cycles; TCM is deterministic.

DSP extensions, SIMD, MAC and the FPU

▶

1.What is it?

Signal processing (filters, FFTs, motor control) is mostly multiply and add. The Cortex-M4 and M7 add instructions for that:

  • MAC (multiply-accumulate): acc = acc + a × b in one instruction, one cycle on the M4 (MLA, SMLAL for 32 × 32 + 64-bit). The M3 needs 3–7 cycles for long multiplies.
  • Packed SIMD (single instruction, multiple data): treat one 32-bit register as two 16-bit or four 8-bit numbers ("lanes") and operate on all of them at once.
  • Saturation: if a result overflows, clip it to the maximum instead of wrapping around to a large negative number.
  • FPU (floating-point unit): hardware for float (M4: FPv4-SP single precision; M7: FPv5, single or double).

Q15 is the common fixed-point format: a 16-bit signed integer that represents value / 32 768, so 0x4000 = 16 384 = 0.5 and 0x7FFF ≈ 0.99997.

2.How does it work, step by step? SMLAD

r0 = 0x2000_4000   → high lane a1 = 0x2000 (0.25), low lane a0 = 0x4000 (0.5)
r1 = 0x4000_2000   → high lane b1 = 0x4000 (0.5),  low lane b0 = 0x2000 (0.25)
SMLAD r2, r0, r1, r2     ; r2 = r2 + a0·b0 + a1·b1
  1. Multiply the low halves as signed 16-bit numbers: 16 384 × 8 192 = 134 217 728 (0x0800_0000).
  2. Multiply the high halves: 8 192 × 16 384 = 134 217 728.
  3. Add both products to the 32-bit accumulator r2 in the same cycle: two MACs per instruction.
  4. Q15 × Q15 gives a Q30 result: 0x0800_0000 / 230 = 0.125 ✓ (0.5 × 0.25). Shift right by 15 at the end to return to Q15.
  • Other SIMD instructions: SADD16, UADD8, QADD16 (saturating), SMUAD, USAD8 (sum of absolute differences), SEL with GE flags, PKHBT (pack halfwords).
  • Saturation: SSAT/USAT, QADD/QSUB; the Q flag in APSR is sticky (stays set until cleared) so you can check after a block whether anything clipped.
  • FPU timing on M4: VADD/VMUL 1 cycle, VFMA 3, VDIV/VSQRT 14. 32 single-precision registers S0–S31. When an ISR uses the FPU, exception stacking reserves 18 more words; lazy stacking (FPCCR.LSPEN) skips the actual save unless the ISR executes an FP instruction.
  • NEON (Cortex-A): 32 × 128-bit registers in AArch64, 4 × f32 or 16 × u8 per instruction. Helium/MVE (Cortex-M55/M85): 128-bit vectors on M-profile.

3.Worked examples

  0x7000 (0.875) + 0x2000 (0.25) = 0x9000
  plain 16-bit add wraps:   0x9000 = −28 672 = −0.875   ← sign flips: a loud click in audio
  QADD16 saturates:         0x7FFF = +32 767 ≈ +0.99997

What is the difference between SIMD and VLIW?

SIMD: one instruction, the same operation on several data lanes. VLIW: one wide instruction word containing several different operations for different functional units, scheduled by the compiler. Hexagon is VLIW with SIMD (HVX) units.

Performance analysis: DWT cycle counter, PMU counters, the roofline

▶

1.What is it?

You cannot optimise what you have not measured. On Cortex-M3/M4/M7 the DWT (data watchpoint and trace unit, part of the debug hardware) contains CYCCNT, a 32-bit counter that increments every core clock cycle, plus small counters that say where extra cycles went. On Cortex-A, the PMU (performance monitoring unit) counts events such as cache refills and branch mispredictions; Linux exposes it through perf. The roofline model tells you whether a kernel is limited by computation or by memory bandwidth.

2.How does it work, step by step?

  1. Set DEMCR.TRCENA (0xE000_EDFC bit 24) to power up the DWT and ITM blocks. Without it, DWT registers read as zero.
  2. On the Cortex-M7, unlock software access with DWT->LAR = 0xC5ACCE55 (lock access register at 0xE000_1FB0).
  3. Zero CYCCNT (0xE000_1004) and set CTRL.CYCCNTENA (0xE000_1000 bit 0).
  4. Read CYCCNT before and after the code, subtract as uint32_t.
  5. For finer detail, the 8-bit event counters say where extra cycles went: CPICNT (extra cycles of multi-cycle instructions and fetch stalls), EXCCNT (exception entry/exit overhead), SLEEPCNT, LSUCNT (extra load/store cycles), FOLDCNT (instructions that took zero cycles because they were folded). Arm gives: instructions ≈ CYCCNT − CPICNT − EXCCNT − SLEEPCNT − LSUCNT + FOLDCNT. The 8-bit counters wrap every 256 events, so use them over short intervals.

3.Worked examples

Cycles to time:      4 800 cycles at 480 MHz = 4 800 / 480e6 = 10.0 µs
CYCCNT wrap period:  2^32 / 480e6 = 8.95 s  (STM32H7)   ·   2^32 / 168e6 = 25.6 s (STM32F4)

Wrap-safe subtraction:
  t0 = 0xFFFF_FF00, t1 = 0x0000_0100 (the counter wrapped in between)
  t1 − t0 as uint32_t = 0x0000_0200 = 512 cycles ✔   (as signed or 64-bit maths: wrong)

Roofline (example machine: 100 GFLOP/s peak, 20 GB/s DRAM):
  ridge point = 100 / 20 = 5 FLOP per byte
  vector add c[i] = a[i] + b[i]: 1 FLOP per 12 bytes (two 4-byte loads, one store) = 0.083 FLOP/B
  attainable  = min(100, 0.083 × 20) = 1.7 GFLOP/s   → memory-bound; vectorising will not help
Attainable FLOP/s = min( Peak FLOP/s , Arithmetic Intensity × Memory Bandwidth )
Arithmetic Intensity (AI) = FLOPs / bytes moved from memory
Ridge point            = Peak / Bandwidth      // AI where you stop being memory-bound

Below the ridge, reduce bytes (tiling, smaller types, fusing loops); above it, vectorise and increase instruction-level parallelism.

Loop optimisation for caches: row vs column major, interchange, blocking/tiling

▶

1.What is it?

The order in which a loop walks memory decides how well it uses each cache line. C stores 2-D arrays row-major: a[i][j] and a[i][j+1] are neighbours in memory, and a whole row comes before the next row. (Fortran, MATLAB and Eigen's default are column-major.) If the innermost loop moves along a row, consecutive accesses fall in the same line. If it moves down a column, each access jumps a whole row ahead.

Three techniques: loop interchange (swap the loops so the inner one walks contiguous memory), padding (add a few unused elements per row so rows do not all map to the same cache sets), and blocking or tiling (work on small square tiles that fit in the cache, so each line is reused many times before it is evicted).

2.How does it work, step by step?

float a[N][N];             // N = 1024 → 4 KB per row
for (i = 0; i < N; i++)     // row-major walk: stride 4 B, one miss per 16 floats (64 B line)
  for (j = 0; j < N; j++) s += a[i][j];

for (j = 0; j < N; j++)     // column walk: stride 4096 B, every access touches a new line
  for (i = 0; i < N; i++) s += a[i][j];   // and a power-of-two stride maps to few sets → conflicts
  1. Address of an element: &a[i][j] = base + (i × N + j) × 4.
  2. Row walk: j increases by 1, the address increases by 4 bytes. A 64-byte line holds 16 floats: 1 miss, then 15 hits.
  3. Column walk: i increases by 1, the address increases by N × 4 = 4096 bytes. Every access is in a different line.
  4. Those lines would be reused when j moves to j + 1 (the next float in each line), but only if they are still in the cache 1024 accesses later.

3.Worked example: why the column walk misses every time

L1D: 32 KB, 8-way, 64-B lines → 64 sets; index = (address >> 6) & 63

column walk, stride 4096 B = 64 lines
  index changes by 64 mod 64 = 0 per step → ALL 1024 elements of the column map to ONE set
  that set holds 8 lines → after 8 rows the first line is already evicted
  when j+1 comes back, every line is gone → miss rate ≈ 100%

row walk: miss rate = 1/16 = 6.25%   → ~16× fewer misses for the same instructions

padding: declare a[N][N + 16] → stride 4160 B = 65 lines
  index changes by 65 mod 64 = 1 per row → the column spreads over all 64 sets

blocking a matrix multiply in the same 32 KB L1:
  need 3 tiles (A, B, C) × BS² × 4 B ≤ 32 768  →  BS² ≤ 2 730  →  BS ≤ 52
  choose BS = 32 → 3 × 32 × 32 × 4 = 12 KB, leaving room for everything else

C arrays are row-major, so the innermost loop should walk the last index. A column walk with a power-of-two row size is the worst case: every access is a new line, and the whole column maps to one or a few sets, so lines are evicted before they are reused. I fix it by interchanging loops, padding the row to break the power-of-two stride, or blocking into tiles where three times BS squared times the element size fits in L1, BS equals 32 for a 32 KB cache. Same instruction count, ten times different CPI.
Why can a column-wise loop be 10× slower even though it executes exactly the same instructions?

Same instruction count, different CPI. Row-wise uses all 16 floats of each 64-byte line (1 miss per 16 accesses, and the prefetcher streams ahead). Column-wise uses 4 bytes per line fetched and, with power-of-two row stride, maps to a handful of sets, so lines are evicted before the next column reuses them: nearly every access misses.

Superscalar and out-of-order execution: renaming, reservation stations, ROB

▶

1.What is it?

Superscalar means the core fetches, decodes and issues more than one instruction per cycle. Out-of-order (OoO) means it executes each instruction as soon as its inputs are ready, rather than strictly in program order, and then retires (commits) results in program order, so that from the program's point of view nothing looks reordered. The point is to keep the execution units busy while an earlier instruction waits, typically for a cache miss.

Four structures make this work. Register renaming: a table, the RAT (register alias table), maps each architectural register (r0–r15) to one of many more physical registers (128+). Reservation stations (or issue queues): waiting rooms where instructions sit until their operands arrive. The ROB (reorder buffer): a queue of all in-flight instructions in program order. The load/store queue: tracks memory operations so loads and stores to the same address stay correct.

2.How does it work, step by step? The life of one instruction

  1. Fetch and predict several instructions per cycle, following the branch predictor.
  2. Decode them (x86 cracks them into micro-ops here).
  3. Rename: look up each source register in the RAT to find which physical register holds its newest value; take a free physical register from the free list for the destination and update the RAT; allocate a ROB entry.
  4. Dispatch to a reservation station, with the physical register numbers ("tags") of its sources, each marked ready or not.
  5. Wake-up and select: when an execution unit finishes, it broadcasts the result's tag on the common data bus (CDB). Every waiting instruction that needs that tag marks it ready. Each cycle, select logic sends the oldest ready instructions to free units. This is Tomasulo's algorithm (IBM 360/91, 1967).
  6. Execute and write the result into the physical register.
  7. Retire from the head of the ROB, in program order, only when the instruction and everything older has finished without a fault. Only now does the result become "architectural". The physical register that held the previous value of that architectural register goes back to the free list.
  8. On a mispredict or exception: everything younger than the faulting instruction is squashed, the RAT is restored, and fetch restarts. That gives precise exceptions.

An out-of-order core renames architectural registers onto a larger physical file, which removes WAR and WAW so only true dependences remain. Renamed instructions wait in reservation stations until their operand tags are broadcast, then the oldest ready ones issue, so independent work runs during a cache miss. The reorder buffer retires in program order, which gives precise exceptions and lets a mispredict squash everything younger. The window size, a few hundred instructions, limits how much of a 400-cycle DRAM miss it can hide.
If execution is out of order, how are interrupts and exceptions precise?

Results are written to physical registers but become architectural only at retirement, in program order, from the ROB. When an exception is raised, the core waits until the faulting instruction is the oldest, discards all younger work, and restores the architectural map, so the state looks as if instructions ran one at a time.

ADVANCED

VLIW and DSPs: Qualcomm Hexagon, TI C6000

▶

1.What is it?

VLIW (very long instruction word) moves the job of finding parallel work from the hardware to the compiler. The compiler bundles several independent operations into one wide instruction (a packet or bundle), one per functional unit. The hardware issues the whole packet in one cycle with no dependency checking, renaming or reordering. That makes the core small and power-efficient, which is why DSPs use it.

  • Qualcomm Hexagon (the DSP in Snapdragon SoCs): packets of up to 4 instructions written in braces; hardware multithreading (several hardware threads interleaved) hides memory latency instead of OoO; HVX vector extension with 1024-bit (128-byte) vectors for imaging and ML. Used for audio, sensor hubs, camera pipelines and low-power neural-network inference.
  • TI C6000 (C66x/C674x): 8 functional units (.L1 .S1 .M1 .D1 and the same on side 2), up to 8 instructions per cycle; software pipelining of loops by the compiler is the key to performance.

2.How does it work, step by step? Software pipelining

A dot-product iteration needs: load x[i], load h[i], multiply, add to the accumulator. On a C6000, a word load (LDW) has a latency of 5 cycles (4 delay slots) and a 16-bit multiply (MPY) 2 cycles.

  1. Naive schedule: the compiler issues the loads, waits 5 cycles, multiplies, waits 2, adds. One iteration every ~8 cycles, and most units sit idle.
  2. Software pipelining: the compiler overlaps iterations. While iteration i is being added, iteration i+1 is being multiplied and iteration i+5 is being loaded. In steady state each cycle's packet contains one stage of several different iterations.
  3. The number of cycles between the start of consecutive iterations is the initiation interval (ii). The resource limit here is two loads per iteration and two load units (.D1, .D2), so ii = 1 is possible: one iteration per cycle.
  4. The loop needs a prolog (filling the pipeline) and an epilog (draining it), which the compiler generates.

VLIW lets the compiler pack independent operations into one wide packet, up to four on Hexagon and eight on TI C6000, and the hardware issues it with no dependency checks, renaming or reordering. Speculative execution, Spectre and Meltdown (concept level)

▶

1.What is it?

Speculative execution means running instructions before the core knows they should run: past a predicted branch, or before a permission check has finished. If the guess was wrong, the results are thrown away and the registers and memory look untouched. But microarchitectural state, especially which lines are now in the cache, is not rolled back. A side channel is a way to read that hidden state indirectly, here by timing how long a load takes (fast = the line is cached).

Spectre (2018) uses misprediction to make the victim's own code speculatively read a secret and leave a cache footprint that depends on it. Meltdown uses the fact that some cores let a user-mode load of a kernel address deliver data to later instructions before the permission fault is taken.

2.How does it work, step by step? Spectre v1 (bounds-check bypass)

  1. Train: the attacker calls the victim function many times with in-bounds x, so the predictor learns "the if is taken".
  2. Flush: the attacker evicts array1_size and every line of the probe array array2 from the cache (Flush+Reload uses clflush on x86; on Arm, eviction by filling the cache).
  3. Attack: call with an out-of-bounds x chosen so that array1 + x points at a secret byte. Loading array1_size misses, so the branch takes ~100+ cycles to resolve. The predictor says "taken", so the core speculatively runs the body.
  4. Leak: the speculative load reads the secret byte s, then loads array2[s × 4096], bringing exactly one probe line into the cache.
  5. Squash: the branch resolves as not taken; the registers are rolled back; the probe line stays cached.
  6. Reload: the attacker times a load of array2[k × 4096] for k = 0…255. One of them is fast: k = s. The secret byte is recovered. Repeat for the next byte.

3.Worked example: the numbers

probe array: 256 possible byte values × 4096 B stride = 1 MB
  why 4096? each value lands in a different page and a different line,
  so the hardware prefetcher cannot pull in neighbours and blur the result

timing (illustrative desktop numbers):
  cached probe line   ≈ 40 cycles
  uncached probe line ≈ 200–300 cycles
  scan finds one fast entry, say k = 0x53 → secret byte = 0x53 = 'S'

Published proof-of-concept rates: tens to hundreds of kB/s of leaked memory.
  • Spectre v2 (branch target injection): the attacker trains the indirect branch predictor to send the victim's indirect jump to a "gadget". Mitigations: retpoline, IBRS/eIBRS on x86, Arm CSV2 and branch-history clearing on context switch.
  • Meltdown (rogue data cache load): mitigated by KPTI (kernel page-table isolation: the kernel is unmapped while user code runs, at a cost on every system call) and by fixed silicon. Affected many Intel cores and the Arm Cortex-A75.
  • Embedded relevance: Arm's published list of affected processors contains Cortex-A and some Cortex-R cores; no Cortex-M cores are listed, because M-profile speculation is shallow and caches are absent (M3/M4) or small. The concept matters for TrustZone-A, hypervisors and automotive SoCs with Cortex-A cores (IVI, ADAS).

If mis-speculated instructions are squashed, how can they leak anything?

Squashing restores architectural state (registers, memory), not microarchitectural state. The speculative load brought a line into the cache; that line stays. Measuring access time afterwards reveals which line was touched, and the line index was computed from the secret.

Cache coherency: MESI/MOESI, snooping vs directory, false sharing, DMA

▶

1.What is it?

When several cores each have their own cache, the same memory line can be copied in several places. Cache coherency guarantees that all of them agree: once a core writes a location, no core can keep reading the old value, and all cores see writes to that one location in the same order. The memory consistency model is a different, wider rule: in what order may writes to different locations become visible (sequential consistency, x86 TSO, Arm's weak model).

Coherency works on whole lines, using a state per line. In MESI the states are:

S — SharedClean copy; others may have it; write requires invalidating them firstNoMaybe

  • Snooping: every miss is broadcast and all caches check their tags. Simple and fast, but traffic grows with the number of cores; practical up to about 8–16 cores (Arm CCI with ACE).
  • Directory: a home node records which caches hold each line and sends messages only to them. Scales to many cores (Arm CHI meshes, server CPUs); costs directory storage and an extra hop. Snoop filters are a hybrid.

Coherency keeps every cache's copy of a line consistent. In MESI, a line is Modified, Exclusive, Shared or Invalid; Exclusive lets private data be written without any bus message, and a write to a Shared line first invalidates the other copies. MOESI adds Owned so dirty data can be shared without a write-back. Snooping broadcasts and works up to about 16 cores; directories scale further. Because coherency works on lines, two cores writing different variables in the same 64-byte line cause false sharing, which I fix by padding to the line size. Cortex-M7 caches are not coherent with DMA or another core, so there I clean and invalidate in software.
What is the E state for; why not just use S?

For the common case of private data: a line read with no other sharers can later be written without any bus transaction (E→M silently). With only MSI, every first write to freshly read private data would need an invalidate broadcast.

Virtual memory: MMU, multi-level page tables (ARMv8 4 KB granule), TLB, ASID, page faults

▶

1.What is it?

Virtual memory gives every program its own private view of memory. The addresses a program uses are virtual addresses (VA). On every access the MMU (memory management unit) translates the VA into a physical address (PA), the real location in RAM, and checks permissions (read/write/execute, user/kernel) and memory attributes (cacheable, Device). The translation rules live in page tables in RAM; recent translations are cached in the TLB (translation lookaside buffer), so most accesses never read the tables.

What it buys: process isolation (one program cannot touch another's memory), the same layout for every process, demand paging (memory allocated only when first touched), copy-on-write after fork(), memory-mapped files, and the ability to build a large contiguous VA region out of scattered physical pages.

  2. Miss: start a table walk. Bits [47:39] index the L0 table whose base address is in TTBR0_EL1; read that 8-byte descriptor.

  4. Bits [29:21] index L2: a 2 MB block or a pointer to an L3 table.
  5. Bits [20:12] index L3: the leaf descriptor gives the physical page base, AttrIndx (an index into MAIR_EL1 for the memory type), AP (permissions), SH (shareability), AF (access flag), nG (not global), PXN/UXN (execute-never).
  6. PA = page base | VA[11:0]. The result goes into the TLB.

The MMU translates virtual to physical addresses and checks permissions and memory type using page tables, cached by the TLB. On ARMv8-A with a 4 KB granule, a 48-bit VA is four 9-bit indices plus a 12-bit offset; each table is 512 eight-byte entries, exactly one page, and L1 and L2 entries can be 1 GB or 2 MB blocks. Why multi-level page tables instead of one flat table?

A flat table for a 48-bit VA with 4 KB pages needs 2^36 entries × 8 B = 512 GB per process. Multi-level tables are sparse: only the subtrees covering mapped regions exist, so a small process needs a few pages of tables. The cost is more memory reads per walk, which the TLB hides.

▶

1.What is it?

An MPU (memory protection unit) checks every access against a small set of regions held in registers and raises a fault if the access is not allowed. It does no address translation: the address the program uses is the physical address. An MMU translates as well, using page tables in RAM. MCUs and safety controllers (Cortex-M, Cortex-R) use MPUs; Linux-class processors (Cortex-A) use MMUs.

2.How does it work, step by step? (ARMv7-M, e.g. STM32F4/F7/H7)

  1. Write the region number to MPU_RNR (0xE000_ED98).
  2. Write the base address to MPU_RBAR (0xE000_ED9C). The base must be aligned to the region size.
  3. Write MPU_RASR (0xE000_EDA0): XN bit 28, AP bits [26:24] (permissions), TEX [21:19], S 18, C 17, B 16 (memory type), SRD [15:8] (disable any of 8 equal sub-regions), SIZE [5:1] (region size = 2SIZE+1 bytes), ENABLE bit 0.
  4. Repeat for the other regions, then enable with MPU_CTRL (0xE000_ED94): ENABLE, and PRIVDEFENA to let privileged code use the default map where no region matches.
  5. __DSB(); __ISB(); so that the next accesses use the new settings.
  6. On every access, all regions are checked in parallel with the access itself. If the highest-numbered matching region forbids it: a MemManage fault, with the cause in MMFSR (CFSR bits [7:0]) and the address in MMFAR.

Memory types and ordering: Strongly-ordered, Device, Normal; DMB / DSB / ISB

▶

1.What is it?

Every address range has a memory type that tells the core what it may do with accesses there. Normal memory (RAM, flash) behaves like storage: reading twice gives the same value and reading has no side effects, so the core may cache it, read it early (speculatively), merge stores, and reorder accesses. Device memory (peripheral registers) is the opposite: a read may pop a FIFO or clear a flag, and the order of writes matters, so none of that is allowed. A barrier instruction forces an ordering point.

The letters: G = gathering (merging several accesses into one), R = reordering, E = early write acknowledgement (an intermediate buffer may say "done" before the device has the write). "nG" means "not allowed".

2.How does it work, step by step? A 4-byte read of a FIFO register

  1. Mapped as Device: the core sends exactly one 4-byte read on the bus. The peripheral returns one FIFO entry and removes it. One read, one pop.
  2. Mapped as Normal write-back (the bug): the load misses in the cache, so the core issues a line fill: a 64-byte burst covering 16 registers around the FIFO address. Each read of the FIFO address inside that burst pops an entry the program never sees.
  3. Later reads of the "status register" hit the cached line and return the old value forever ("sticky" status).
  4. Two stores, LEN then GO, may be merged or reordered in the write buffer, so the device may see GO before LEN.
  5. The core may also read Normal memory speculatively, e.g. down a mispredicted path, popping FIFOs at random.

Cortex-M default map (no MPU): 0x4000_0000–0x5FFF_FFFF and 0xA000_0000–0xDFFF_FFFF are Device and XN; 0xE000_0000 and above is Strongly-ordered; SRAM and Code are Normal. A known Cortex-M7 trap (ST AN4838): the FMC bank at 0x6000_0000 is Normal by default, so the M7 may issue speculative reads to an external NOR/PSRAM/LCD interface; fix with an MPU region (Strongly-ordered / Device, or no access for unused space).

3.Worked example: barriers, which one and why

  • DMB (data memory barrier): accesses before it are observed before accesses after it. Ordering only; the core does not wait. Use between writing a DMA descriptor (Normal memory) and writing the "go" register, and in lock/unlock code.
  • DSB (data synchronisation barrier): the core waits until all earlier memory accesses (and cache/TLB maintenance) have completed. Use before WFI, after clearing an interrupt flag at the end of an ISR, after cache maintenance.
  • ISB (instruction synchronisation barrier): flush the pipeline so that later instructions are fetched again with the new context. Use after writing CONTROL, VTOR, the MPU, CPACR or SCTLR, or after writing new code.

Normal memory may be cached, read speculatively, merged and reordered, which is fine for RAM. Device memory forbids all of that, because reading a register can have side effects and write order matters; the nG, nR and nE letters say whether gathering, reordering and early acknowledgement are allowed. If MMIO is mapped as Normal you get line fills that pop FIFOs, stale cached status, and reordered writes. For ordering I use DMB between a Normal-memory descriptor and a Device doorbell, DSB when the access must have completed, such as before WFI or after clearing an IRQ flag, and ISB after changing context like VTOR, CONTROL or the MPU.
Is volatile sufficient to order a DMA descriptor write before the doorbell register write on a Cortex-A?

No. The descriptor is in Normal memory and the doorbell in Device memory; volatile stops compiler reordering but the CPU may let the Device write overtake the buffered Normal write. You need a DMB (Linux: wmb(), or use writel() which includes the barrier) between them. And if the descriptor is cacheable and the DMA is not coherent, a cache clean too.

ADVANCED

Self-modifying code, JIT and I-cache coherency

▶

1.What is it?

Self-modifying code is any case where a program writes bytes to memory and then executes them as instructions: a bootloader copying a routine into RAM, a JIT compiler, loading a module, applying a patch. On ARM, the instruction side is not coherent with data stores. A store goes through the D-cache (and the write buffer). Instruction fetch goes through the I-cache and the prefetch buffer, which may still hold the old bytes. Nothing in hardware connects the two, so software must. (x86 snoops stores against the instruction stream in hardware, which is why x86 programmers rarely meet this.)

2.How does it work, step by step? The five-step recipe

  1. Write the code with ordinary stores (memcpy). On a write-back D-cache the new bytes may exist only in dirty D-cache lines.
  2. Clean the D-cache over the range, to the point of unification (PoU: the level where the instruction and data sides see the same memory). The new bytes are now visible to instruction fetch.
  3. DSB: wait until the clean has completed.
  4. Invalidate the I-cache over the range (or all of it), discarding old copies of those addresses.
  5. DSB then ISB: wait for the invalidate, then flush the pipeline so instructions already fetched (old bytes) are discarded and fetched again.

On multi-core systems the invalidate must be broadcast (the "IS" Inner Shareable variants), and every core that will run the code needs its own ISB (Linux sends an IPI).

3.Worked example: copying a 1 KB flash routine on an STM32H743

routine size   1 024 bytes, copied to AXI SRAM at 0x2400_0000

call address   0x2400_0000 | 1 = 0x2400_0001   (bit 0 = Thumb state)

without maintenance: SRAM may still hold the PREVIOUS version for any of the 32 lines

Why is ISB needed after invalidating the I-cache?

The core may already have fetched and decoded the following instructions (old bytes) into its pipeline or prefetch buffer. The cache invalidate does not touch those; ISB flushes the pipeline so the next instructions are fetched again from the now-correct memory.

60-SECOND REVISION
  • ISA = contract; microarchitecture = implementation. ARMv7E-M is the ISA of M4 and M7.
  • Modified Harvard: split I/D paths, one address space. M4 has I-Code, D-Code, System buses.
  • Iron Law: time = instr × CPI × T. Pipelining improves throughput, not latency.
  • 5 stages: IF ID EX MEM WB. M0+ = 2, M3/M4 = 3, M7 = 6 dual-issue.
  • Hazards: structural, data (RAW true; WAR/WAW name), control. Forwarding fixes ALU→ALU; load-use = 1 bubble.
  • Branch prediction: 2-bit counter = 1 miss per loop; BTB gives target in IF; RAS predicts returns; penalty ≈ resolve depth.
  • Speculation leaves cache footprints → Spectre (v1 bounds bypass, v2 BTI), Meltdown (permission check late) → KPTI.
  • OoO: rename (kills WAR/WAW), reservation stations (wait for operands), ROB (in-order retire, precise exceptions).
  • VLIW: compiler schedules packets; Hexagon 4-wide packets + HVX; great for DSP loops.
  • Cache: offset = log2(line), index = log2(sets), tag = rest. Lines = size/line, sets = lines/ways.
  • 3C: compulsory, capacity (FA would miss too), conflict (FA would hit). AMAT = HT + MR × MP.
  • Write-back + allocate = low traffic, stale memory. Write-through = memory current, more traffic.
  • M7: 32-B lines, I 2-way / D 4-way; TCM = deterministic 0-WS, uncached; DMA needs clean/invalidate or non-cacheable MPU region.
  • MESI: E allows silent write; MOESI's O shares dirty data. Snooping ≤ ~16 cores, directory scales. False sharing → pad to 64 B.
  • MMU: 4-level 4 KB granule, 9 bits/level, TLB caches translations, ASID avoids flushes, page fault → OS.
  • MPU: regions, no translation, deterministic: safety MCUs.
  • Memory types: Device = no speculation/merge/reorder; Normal = anything goes. DMB order, DSB complete, ISB refetch.
  • Loops: inner loop on contiguous dimension; tile so 3·B²·elem ≤ cache; DWT CYCCNT to measure.
