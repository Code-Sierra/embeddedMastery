1What problem does debugging solve?

A microcontroller has no screen, no keyboard and no operating system that prints "Segmentation fault, line 57". When firmware misbehaves, all you see from the outside is a symptom: an LED stops blinking, a value on a display is wrong, the device reboots every few hours. Debugging is the work of going from that symptom to the exact cause — which instruction, at which address, did what, and why.

Three things make this harder than on a PC:

  1. The program talks to hardware. A bug may be in your code, in how you configured a peripheral, or in the board itself (noise, a weak power supply). You must be able to tell these apart.
  2. Timing matters. Interrupts arrive at any moment. Stopping the CPU or adding a print statement changes the timing — and can make the bug vanish (a "heisenbug").
  3. Devices are far away. Once thousands of units are installed in the field you cannot plug a cable into the one that failed. You only learn what the firmware recorded and reported.

2The hardware picture: what is connected to what

Before any command makes sense you need a picture of the physical setup. Here is a typical bench: your PC, a USB debug probe, and the target board with an STM32F407 (an ARM Cortex-M4F microcontroller by ST).

Follow one request through the picture, step by step:

  1. You type print guard in GDB. GDB looks up guard in the ELF file and finds its address, 0x2000_0110.
  2. GDB sends "read 4 bytes at 0x2000_0110" over a TCP socket to OpenOCD, the program that knows how to drive your probe.
  3. OpenOCD sends USB commands to the probe, which turns them into electrical pulses on two wires: SWDIO (data) and SWCLK (clock). That is SWD, Serial Wire Debug.
  4. Inside the chip the DAP (Debug Access Port) receives them. Its AHB-AP part is a bus master — like a tiny DMA controller under remote control — so it reads SRAM address 0x2000_0110 through the bus matrix, even while the CPU keeps running.
  5. The 4 bytes travel back the same way and GDB prints the value.

The four small boxes inside the core are what make debugging possible: the FPB (6 hardware breakpoint comparators), the DWT (4 watchpoint comparators and a cycle counter), the ITM (trace output through the SWO pin), and the SCB (System Control Block) whose registers record why the CPU faulted. Notice the DMA controller is a separate bus master: the core's debug units do not see what it writes — that will matter later.

Say it like this: "The probe talks SWD to the chip's Debug Access Port; its AHB access port can read and write any address while the core runs. Inside the core, the FPB gives hardware breakpoints, the DWT watchpoints and a cycle counter, the ITM streams trace out of SWO, and the SCB fault registers record why a crash happened."

3Key terms, defined one by one

Every later section uses these words. Read each definition once; come back here whenever a term is unclear.

The CPU's own registers

Register
A 32-bit storage cell inside the CPU. The Cortex-M has R0–R12 for general data, plus the special ones below.
PC (R15)
Program Counter: the address of the instruction being executed. "Where is the CPU?"
LR (R14)
Link Register: the return address saved by a function call (BL). Its bit 0 is 1 because Cortex-M code is "Thumb" code. Inside an exception handler LR holds a special EXC_RETURN value instead.
SP (R13)
Stack Pointer: address of the top of the current stack. There are two: MSP (Main SP, used at reset, in interrupts and in bare-metal code) and PSP (Process SP, used by RTOS tasks).
xPSR
Program Status Register: condition flags, the T bit (bit 24, must be 1) and IPSR (bits 8:0 = number of the exception being handled; 0 = normal code).
Stack
RAM area used like a pile of plates: function calls push return addresses and local variables, returns pop them. On Cortex-M it grows from high to low addresses.

Exceptions and faults

Exception / interrupt
An event that makes the CPU pause normal code and run a handler function. Peripheral interrupts (UART, timer) and faults are both exceptions.
Vector table
An array of addresses at the start of flash: entry 0 = initial MSP, entry 1 = reset handler, entry 3 = HardFault handler, … The CPU reads it to find each handler.
Fault
An exception the CPU raises itself because an instruction cannot be executed safely (bad address, illegal instruction, divide by zero with trapping on).
HardFault
The catch-all fault (exception number 3). Other faults are "escalated" to it if they are disabled.
MemManage / BusFault / UsageFault
The three specific faults (numbers 4, 5, 6): memory-protection violation / bus returned an error / illegal instruction or state.
CFSR, HFSR
Configurable Fault Status Register (0xE000_ED28) and HardFault Status Register (0xE000_ED2C): bit-by-bit records of why the CPU faulted.
MMFAR, BFAR
Fault Address Registers: the data address that caused a MemManage or BusFault — valid only when CFSR says so.
Exception frame
The 8 registers (R0–R3, R12, LR, PC, xPSR) the CPU pushes onto the stack automatically when any exception starts. For a crash, this is the snapshot of the moment it happened.
EXC_RETURN
Magic value (e.g. 0xFFFF_FFFD) put in LR at exception entry. Bit 2 tells which stack (MSP or PSP) holds the frame.
Lockup
The CPU stops completely because a fault happened while it was already handling (or entering) HardFault.

Build outputs

ELF file
app.elf: the compiled program plus symbol names and debug information that map every address to a source line.
Map file
app.map: the linker's list of where every function and variable was placed, with sizes.
addr2line
Tool that turns an address (from a crash) into a function name and file:line using the ELF.
.noinit
A RAM section the startup code does not clear, so data written there survives a reset — used for crash records.

Debug tools

Debug probe
USB box (ST-LINK, J-Link) that converts PC commands into SWD or JTAG signals.
SWD / JTAG
Wire protocols into the chip's debug port. SWD = 2 wires (SWDIO, SWCLK); JTAG = 4–5 wires, can chain several chips.
GDB, GDB server
GDB is the debugger you type into; the GDB server (OpenOCD, J-Link GDB Server) drives the probe for it.
Breakpoint
"Stop when this instruction is reached." Hardware breakpoints use the FPB (6 on Cortex-M4).
Watchpoint
"Stop when this memory address is read/written." Uses the DWT (4 on Cortex-M4); sees CPU accesses only, not DMA.
ITM / SWO
Hardware that streams log messages out of one pin (SWO) with very little CPU cost.
RTT
SEGGER Real-Time Transfer: logging through a RAM buffer that the probe reads in the background.
Semihosting
Target borrows the PC's console via the debugger (a BKPT instruction). Hangs without a debugger.
Watchdog
Hardware timer that resets the chip if software stops "kicking" it — guarantees recovery from hangs.
Reset reason
Flags in a register (STM32F4: RCC_CSR) that say whether the last reset was power-on, brown-out, watchdog, software or the reset pin.

4Reading register values: hex, bits and byte order

Fault analysis is mostly reading 32-bit numbers. Three skills make that easy.

Skill 1 — hex digit to bits

Each hexadecimal digit is exactly 4 bits. Digit position k (counting from the right, starting at 0) holds bits 4k to 4k+3.

Worked example — which bit is set in 0x0200_0000? Write the digits with their positions:

value:     0    2    0    0  _ 0    0    0    0
position:  7    6    5    4    3    2    1    0
bits:    31-28 27-24 23-20 19-16 15-12 11-8 7-4  3-0
digit '2' at position 6 = binary 0010 → its bit 1 is set → bit 4·6 + 1 = bit 25

CFSR bit 25 is DIVBYZERO. With practice you will read 0x0200_0000 as "divide by zero" instantly.

Two bits at once — 0x82: 8 = 1000 (bit 3 of the upper digit → bit 7), 2 = 0010 (bit 1). So 0x82 = bits 7 and 1. In CFSR's low byte that is MMARVALID + DACCVIOL.

Skill 2 — fields inside a register

Registers pack several fields. To extract bits [15:8] of a value: shift right by 8, then AND with 0xFF. Example: CFSR = 0x0000_8200 → (0x8200 >> 8) & 0xFF = 0x82 = the BusFault status byte.

Skill 3 — little-endian byte order

ARM Cortex-M stores the lowest byte of a word at the lowest address. The word 0xCAFE_F00D at address 0x2000_0110 is stored as:

address:  0x20000110  0x20000111  0x20000112  0x20000113
byte:        0D          F0          FE          CA

So if a 2-byte write of 0x00A3 hits address 0x2000_0110, it replaces the bytes 0D F0 with A3 00, and the word becomes 0xCAFE_00A3. You will see exactly this in the GDB Playground.

Say it like this: "Each hex digit is four bits, so digit k covers bits 4k to 4k+3 — 0x0200_0000 is bit 25. Fields come out with shift-and-mask, and Cortex-M is little-endian, so the low byte of a word sits at the lowest address."

5What a crash does inside the CPU, step by step

When an instruction cannot be executed safely, the Cortex-M does not just stop. It performs a fixed sequence in hardware — knowing this sequence is the key to reading any crash dump.

  1. The bad instruction is detected. Example: ldr r3, [r0, #16] with R0 = 0 tries to read address 0x0000_0010.
  2. The CPU classifies the problem and sets bits in CFSR: here the memory protection unit forbids that address → MemManage, bit DACCVIOL, and it writes the address 0x10 into MMFAR (bit MMARVALID).
  3. It decides which handler runs. If MemManage is disabled (the default after reset), the fault is escalated to HardFault and HFSR bit 30 FORCED is set.
  4. It saves the evidence on the stack: it pushes R0, R1, R2, R3, R12, LR, PC, xPSR — 8 words, 32 bytes — onto the stack that was in use (PSP for an RTOS task).
  5. It marks how to return: LR gets EXC_RETURN (0xFFFF_FFFD = "came from thread mode, frame is on PSP").
  6. It jumps to the handler: the address stored in vector-table entry 3 (offset 3 × 4 = 0x0C, i.e. flash 0x0800_000C), and IPSR becomes 3.
  7. Your HardFault handler runs. It is the only code that sees all the evidence; its job is to copy it somewhere safe and reset.

Three exceptions to "the stacked PC is where it crashed" — memorise them now, they appear in every interview:

  • Imprecise bus fault (CFSR bit 10): a store went into a write buffer and failed later; the PC is after the culprit.
  • Stacking error (STKERR / MSTKERR): the push in step 4 itself failed (usually stack overflow), so the frame is garbage.
  • INVSTATE: the PC is the target of a bad jump; the instruction there is innocent.

6Worked example: one crash, from symptom to fix, with real numbers

Symptom. A sensor device running FreeRTOS on an STM32F407 crashes right after a remote configuration reload. The firmware has a good HardFault handler that saves registers to .noinit and resets. On the next boot it uploads this record:

CFSR  = 0x00000082     HFSR = 0x40000000
MMFAR = 0x00000010     BFAR = 0x00000010
EXC_RETURN = 0xFFFFFFFD          PSP = 0x20003F60
stacked: R0=0x00000000 R1=0x20001A3C R2=0x00000004 R3=0x00000000
         R12=0x00000001 LR=0x08003B11 PC=0x08003B12 xPSR=0x01000000
build-id = 9f3c…            (matches archived app.elf)

The relevant source code:

typedef struct {
    uint32_t id;      /* offset  0 */
    uint32_t rate;    /* offset  4 */
    uint32_t mode;    /* offset  8 */
    uint32_t flags;   /* offset 12 */
    uint32_t gain;    /* offset 16 = 0x10 */
} cfg_t;

cfg_t *active_cfg;                       /* swapped during a config reload */

void sensor_apply_cfg(cfg_t *cfg) {      /* src/sensor.c:54 */
    adc_lock();
    adc_set_gain(cfg->gain);             /* src/sensor.c:57 */
}

Now decode it exactly as an expert would:

  1. HFSR = 0x4000_0000. Digit '4' at position 7 = 0100 → bit 4·7 + 2 = bit 30 = FORCED. Meaning: some configurable fault was escalated; the real reason is in CFSR.
  2. CFSR = 0x0000_0082. Only the low byte (MMFSR) is non-zero. 0x82 = bits 7 and 1 → MMARVALID + DACCVIOL: a data access violated the MPU, and MMFAR holds the address.
  3. MMFAR = 0x0000_0010 — valid. BFAR shows the same number, but BFARVALID (bit 15) is 0, and on Cortex-M4 the two are one physical register: ignore BFAR.
  4. EXC_RETURN = 0xFFFF_FFFD. Low byte 0xFD = 1111 1101: bit 2 = 1 → frame on PSP; bit 3 = 1 → was running in thread mode (a task); bit 4 = 1 → basic 8-word frame.
  5. Locate the frame. PSP = 0x2000_3F60. Stacked PC is at +0x18 → 0x2000_3F78 → 0x0800_3B12. LR at +0x14 → 0x0800_3B11. xPSR = 0x0100_0000: T bit set, IPSR = 0 (task code, not an ISR).
  6. Turn the PC into source. arm-none-eabi-addr2line -f -e app.elf 0x08003B12 → sensor_apply_cfg, src/sensor.c:57. Disassembly at that address: ldr r3, [r0, #16] — "load the word at R0 + 16".
  7. Connect the numbers. Stacked R0 = 0, so the address was 0 + 16 = 0x10 — exactly MMFAR. And offsetof(cfg_t, gain) = 16. So cfg was NULL and the code read cfg->gain.
  8. Why did it fault at all? The firmware programs an MPU region over 0x0000_0000–0x0000_03FF as no-access (a "NULL guard"). Without it, on STM32 address 0x10 is an alias of flash 0x0800_0010 — vector-table word 4, the MemManage handler address — and the load would have silently returned a number like 0x0800_0A31 as the "gain". No crash, just a wildly wrong sensor gain.
  9. Root cause. During a reload, active_cfg is set to NULL while the new config is built, and the sensor task can run in that window.
  10. Fix. Build the new config completely in a separate buffer, then publish it with one aligned 32-bit pointer store (atomic on Cortex-M); never publish NULL; add ASSERT(cfg != NULL) at the API boundary.
  11. Prove it. A HIL test hammers config reloads 10 000 times while the sensor task runs at 1 kHz: before the fix it faulted within a few hundred reloads; after, zero faults.
Say it like this: "HFSR said FORCED, so I read CFSR: 0x82 is DACCVIOL plus MMARVALID, and MMFAR was 0x10. EXC_RETURN bit 2 pointed me at PSP; the stacked PC addr2lined to a load at offset 16 with R0 equal to zero — NULL plus offsetof gain. The config pointer was published as NULL during a reload; the fix is an atomic swap to a fully built config, plus the MPU NULL guard that made the bug visible at all."

7Worked example: a field reset you cannot touch

Not every failure leaves a fault record. Some devices simply reboot. Every STM32F4 reset sets flags in RCC_CSR (address 0x4002_3874, flags in bits 31:24). Good firmware reads them at every boot, clears them, and uploads them.

Data from 1 200 station controllers over 7 days:

CSR >> 24BINARYFLAGSBOOTS
0x060000 0110bit 26 PIN + bit 25 BOR2 940
0x0E0000 1110bit 27 POR + PIN + BOR310
0x240010 0100bit 29 IWDG + PIN41
0x140001 0100bit 28 SFT + PIN12
  1. Ignore PIN at first. On STM32, every internal reset drives the NRST pin low, so PINRSTF accompanies every cause. It only means "external reset" when it is alone (0x04).
  2. POR + BOR + PIN (0x0E) is a genuine power-on: the supply went away completely. 310 boots ≈ normal installs and mains interruptions.
  3. BOR + PIN without POR (0x06): the supply dipped below the brown-out threshold but did not fall to zero. 2 940 / 3 303 ≈ 89 % of all boots.
  4. Correlate. 91 % of those boots happen within 50 ms of the log entry "modem_tx_start". Logged minimum VDD on affected units is 2.61 V; the BOR threshold (option bytes BOR_LEV = 3) is about 2.70 V.
  5. Physics check. An LTE modem transmit burst can draw about 2 A. Through 0.3 Ω of cable and connector resistance that is a drop of V = I × R = 2 × 0.3 = 0.6 V. A rail that should be 3.3 V briefly sees ~2.7 V or less → brown-out reset.
  6. Conclusion: a power-supply design problem, not a firmware bug. Fix with bulk capacitance at the modem, a separate regulator, lower-resistance wiring. The 41 watchdog resets are a separate, smaller firmware issue — look at their crash records next.
Say it like this: "I read and clear RCC_CSR at every boot and upload it. Brown-out without power-on means the rail dipped but didn't collapse; correlated with modem transmit bursts and a logged VDD minimum below the BOR level, that's a supply problem. PINRSTF is set for every internal reset on STM32, so it only counts when it's alone."

8How the pieces connect

Every debugging session moves through the same stages. Each stage uses different tools, and each tab of this page trains one of them.

  1. Start from the symptom stated as a fact — the Decision Tree tab walks you from there.
  2. Gather evidence that already exists — fault registers and reset flags cost nothing to read. The Forensics Lab trains you to decode them.
  3. If you need more, add the least intrusive tool. A watchpoint finds who writes a variable; a GPIO toggle plus a logic analyser shows timing; RTT/ITM log cheaply. The GDB Playground lets you practise breakpoints and watchpoints on a real bug.
  4. Commit to a hypothesis and test it. The Scenarios tab gives you realistic field cases to practise that judgement.
  5. Fix, prove and prevent — and be able to explain it out loud. The Interview Q&A and Cheat Sheet tabs drill exactly that.
