// 08 — DMA · LEARN: BIG PICTURE

DMA from zero: a guided tutorial

Read this tab from top to bottom before you open the Concepts cards. It assumes you know what a CPU, a register and RAM are, and nothing else. The examples use the STM32F407 (an ARM Cortex-M4 microcontroller at 168 MHz, documented in ST's reference manual RM0090).

STEP 1 · THE PROBLEM

Why would a chip need a second "data mover"?

Imagine a microcontroller receiving data from a GPS module over a serial port (UART = Universal Asynchronous Receiver/Transmitter, the two-wire TX/RX serial link). The GPS sends at 115200 baud. "Baud" is bits per second on the wire. Each byte travels as 10 bits: 1 start bit, 8 data bits and 1 stop bit (this format is called "8N1").

115200 bits/s ÷ 10 bits per byte = 11 520 bytes per second 1 s ÷ 11 520 = 86.8 µs between bytes

The UART hardware has only one receive data register (called DR, the "data register"). When a byte arrives, the UART sets a flag called RXNE ("Receive register Not Empty"). Something must read DR before the next byte finishes arriving 86.8 µs later. If nobody reads it in time, the next byte has nowhere to go, the UART sets ORE (OverRun Error) and a byte is lost.

Without DMA, the "something" is the CPU. Every single byte causes an interrupt: the CPU stops what it was doing, saves its registers, runs a small function (an ISR, Interrupt Service Routine) that copies DR into an array, restores its registers and returns. On a Cortex-M4 that costs roughly 60–80 clock cycles per byte.

11 520 interrupts/s × 70 cycles = 806 400 cycles/s 806 400 ÷ 168 000 000 cycles/s = 0.48 % of the CPU

0.48 % sounds harmless. Now raise the speed to 3 Mbaud (300 000 bytes/s): the CPU spends 12.5 % of its time just copying bytes, and the deadline per byte shrinks to 3.3 µs. Any piece of code that disables interrupts for more than 3.3 µs (a flash write, a long critical section) loses data. For an ADC (Analog-to-Digital Converter) producing 2.4 million samples per second, the deadline is 417 ns, which is 70 cycles. The CPU would spend 100 % of its time copying and still fail.

The idea of DMA (Direct Memory Access): add a small, dumb, dedicated piece of hardware whose only job is "when the peripheral says it has data, copy it from address A to address B and move B forward by one". The CPU configures it once, then goes away and does real work. The CPU is interrupted only when a whole block is finished.

An everyday analogy: the CPU is a chef. Without DMA the chef walks every single plate from the kitchen to the table. With DMA a waiter (the DMA controller) carries plates, and the chef only hears a bell when a table of 128 plates has been served.

STEP 2 · THE HARDWARE PICTURE

What is physically inside the chip

Inside an STM32F407, everything talks over buses. A bus is a set of wires that carries an address ("where"), data ("what") and control signals ("read or write, how many bytes"). Two kinds of thing sit on a bus:

  • Bus masters start transfers. They put an address on the bus and say "read" or "write". The CPU is a master. The DMA controller is also a master. That is the whole trick: DMA is a second master that can read and write memory on its own.
  • Bus slaves answer transfers. Flash memory, SRAM (Static RAM, the chip's working memory) and peripherals (UART, SPI, ADC, timers) are slaves. A slave never starts anything; it just responds when addressed.

Between masters and slaves sits the bus matrix, a crossbar switch. It connects any master to any slave it is wired to, and it lets two masters work at the same time as long as they talk to different slaves. If two masters want the same slave in the same cycle, the matrix makes them take turns (round-robin).

Notice the extra green wire. Each peripheral has a DMA request line going to the DMA controller. When the UART has a byte, it raises this wire. The DMA sees it, does one read of the UART's DR and one write into SRAM. Reading DR automatically clears the request. Then the DMA waits for the next request. No software runs at all for this.

(On the F4 the DMA1 controller's peripheral side is actually wired straight to the APB1 peripheral bus rather than through the matrix; the Concepts card 06 explains that detail. The picture above is the right mental model.)

The vocabulary you need

DMA controllerA hardware block that copies data between addresses on its own. The F407 has two: DMA1 and DMA2.
StreamOne independent copy engine inside a controller. Each controller has 8 streams (0–7). Each stream has its own set of configuration registers. Think "one waiter".
Channel (CHSEL)Each stream can listen to one of 8 request wires; "channel" picks which one. The wiring is fixed in silicon and listed in the reference manual (RM0090 tables 42/43).

M0ARMemory 0 Address Register. Holds the memory-side address, e.g. the start of your array in SRAM. (M1AR is a second one used in double-buffer mode.)
NDTRNumber of Data To Transfer. You write how many items to move. The hardware counts it down by one per item. Reading it tells you how many are left.
CRConfiguration Register of the stream: channel, direction, data sizes, increments, circular mode, priority, interrupt enables, and EN (enable, bit 0).
Direction (DIR)Peripheral→memory (P2M, e.g. receive), memory→peripheral (M2P, transmit), or memory→memory (M2M, a hardware memcpy).
PSIZE / MSIZEData size on the peripheral side / memory side: byte (8-bit), half-word (16-bit) or word (32-bit).
PINC / MINCPeripheral / Memory INCrement. If set, that address moves forward by one item after each transfer. Receive usually uses PINC=0 (DR stays the same address) and MINC=1 (walk through the array).
Normal vs circularNormal: stop when NDTR reaches 0. Circular (CIRC): reload NDTR and restart at the beginning of the buffer, forever, with no gap.
HT / TCHalf Transfer and Transfer Complete. Flags (HTIF, TCIF) the hardware sets when half / all of the items have been moved. Each can raise an interrupt.
TETransfer Error. Set when the DMA hit a bus error (bad address). The hardware then turns the stream off.
FIFOFirst In, First Out. A small 16-byte holding buffer inside each stream, used for size conversion and bursts. "Direct mode" means the FIFO is bypassed.
Cache / coherencyOn faster chips (Cortex-M7) the CPU keeps copies of RAM in a cache. The DMA does not see the cache, so the two can disagree. Keeping them in agreement is called coherency.

4.3 What happens for one byte (no software involved)
  1. The GPS byte '$' (0x24) finishes arriving on the RX pin. The UART puts 0x24 in DR and raises its DMA request line.
  2. DMA1 Stream 5 sees the request on channel 4. The DMA arbiter picks Stream 5 (no other stream is busy).
  3. The DMA reads address 0x40004404 (USART2->DR) and gets 0x24. Reading DR drops the request.
  4. The DMA writes 0x24 to address 0x20000100 (M0AR + 0, because this is the first item).
  5. The internal memory pointer advances by 1 byte (MINC=1, MSIZE=byte) to 0x20000101. PAR stays at 0x40004404 (PINC=0).
  6. NDTR goes from 256 to 255. The "write position" is 256 − 255 = 1: the next byte goes to rx[1].

STEP 5 · WHAT CAN GO WRONG (PREVIEW)

The five classic DMA bugs

  1. Consumer too slow (overrun). If nmea_feed() takes longer than 11.1 ms, the DMA comes back into rx[0..127] while the parser still reads it. Data is silently overwritten. Try it in the DMA Simulator tab.
  2. Buffer on the stack. If rx[] were a local variable in a function that returns, the DMA would keep writing into memory that now belongs to other functions. Random crashes follow (Concepts card 15).
  3. Wrong stream/channel. USART1 is on DMA2, not DMA1. Copying the stream number from another UART gives a stream that waits forever (Scenario 07).
  4. Memory the DMA cannot reach. The F4's 64 KB CCM RAM is wired only to the CPU. A DMA pointed there gets a bus error (TE) and stops (card 19).
  5. Cache disagreement (Cortex-M7). On an STM32F7/H7 the CPU may read an old cached copy of rx[] that the DMA updated behind its back (cards 16–17, and the Cache & Load Lab).
STEP 6 · HOW THE PIECES CONNECT

The whole story in one flow

  1. Choose the controller, stream and channel from the mapping table (cards 03, 06).
  2. Place the buffer in memory the DMA can reach, with a lifetime longer than the transfer, aligned for cache lines on an M7 (cards 15, 16, 19).
  3. Configure PAR, M0AR, NDTR, CR: direction, widths, increments, mode, interrupts (cards 03, 04, 05, 12).
  4. Clear old flags, set EN, then enable the peripheral's DMA request (cards 10, 11).
  5. The hardware moves data, competing for the bus with the CPU (cards 07, 08).
  6. At HT/TC the CPU processes the finished part within the deadline T_half (cards 05, 09, 13, 14).
  7. On error (TE/FE/DME) the stream stops; handle it (card 10).
  8. Advanced: caches and barriers (16–18), descriptor-based DMA (20–21), low power (22), Linux (23).
DMA is a second bus master that copies data between a peripheral and memory each time the peripheral raises a request, so the CPU does not run a load and a store per byte. I configure the source, destination, count, sizes and mode once, and I only get interrupts at half-transfer, transfer-complete or error. // 08 — DMA · CONCEPTS

Direct Memory Access, from first principles to cache coherency

The reference part is the STM32F407 (Cortex-M4, RM0090) unless a card says otherwise. Cortex-M7 cache material uses the STM32F7/H7. Linked-list DMA uses the STM32U5/H5 GPDMA and NXP eDMA. Each card is a lesson with numbered parts: what it is, how it works step by step, a worked example with real numbers, code explained line by line, what goes wrong, and a model answer to say out loud. New to DMA? Read the Learn: Big Picture tab first. Opened cards count toward progress.

1. What is it?

A DMA controller (Direct Memory Access controller) is a piece of hardware that copies data from one address to another without the CPU running any instructions for each item. It is a second bus master (a device allowed to start reads and writes on the chip's buses). The CPU programs it once with source, destination, count, data width, increment rules and trigger. After that, each DMA request from the peripheral (for example "RXNE: a byte arrived in the UART" or "EOC: the ADC finished a conversion") makes the DMA move one item. The CPU is only interrupted at milestones: half-transfer (HT), transfer-complete (TC) or error (TE).

2. How does the CPU-only approach cost time, step by step?

Without DMA, each received item costs one interrupt. On a Cortex-M4 one interrupt goes like this:

  1. The peripheral sets its flag; the NVIC (Nested Vectored Interrupt Controller, the Cortex-M interrupt manager) signals the core.
  2. The core pushes 8 registers (R0–R3, R12, LR, PC, xPSR) onto the stack: about 12 cycles of hardware "stacking".
  3. The ISR body runs: read the status register, read DR, store the byte into a ring buffer, update the index: 30–60 cycles.
  4. Exception return pops the 8 registers: about 10 cycles.

So one item costs roughly 60–80 cycles; we use 70 below.

4. The deadline, which matters more than the percentage

The percentage is not the main point. With per-byte interrupts at 3 Mbaud, any interrupt-disabled region or higher-priority ISR longer than 3.3 µs loses a byte, because the F4 USART has only one receive data register. The next byte sets ORE (overrun error). DMA turns a hard per-item deadline into a soft per-block deadline: with a 1024-byte circular buffer at 3 Mbaud, each half lasts 512 × 3.33 µs = 1.7 ms, so the CPU has 1.7 ms to service each half.

Per-byte IRQ:   |b|b|b|b|b|b|b|b|b|b|b|b|b|b|b|b|   CPU must react within 3.3 µs, every time
DMA + HT/TC:    |------- half A -------|------- half B -------|
                                       ^HT                     ^TC   CPU reacts within 1.7 ms, twice a lap
5. What goes wrong if… you think DMA is "faster"?
"DMA makes transfers faster." The peripheral sets the data rate, not the DMA. DMA saves CPU cycles, removes the per-item deadline, and makes timing deterministic. For a 16-byte copy, a CPU memcpy usually finishes before you could configure and arm a stream.

When not to use DMA:

  • Tiny or rare transfers, where setup cost (10–20 register writes plus an interrupt) is bigger than the work.
  • Every item needs a decision within a microsecond, e.g. a protocol state machine that must answer each byte. Even then DMA plus character-match or IDLE detection often wins.
  • Not enough streams, or the request-mapping table makes two peripherals compete for the same stream.
  • Data lives in memory the DMA cannot reach: CCM RAM on F4, DTCM on H7 for DMA1/2.
You chose per-byte interrupts at 3 Mbaud. In the lab it works. In the field, when a flash erase disables interrupts for 20 µs, the UART's ORE flag sets and roughly 6 bytes are lost each time; the protocol layer sees CRC errors that "come and go".
6. Say it like this
DMA is a second bus master that moves one item per peripheral request, so the CPU does not pay 60–80 cycles of interrupt overhead per byte. At 2.4 MSPS an interrupt per sample would need 100 % of a 168 MHz M4, while DMA with HT/TC interrupts costs about 0.2 %. More importantly it converts a deadline of hundreds of nanoseconds per item into a deadline of milliseconds per half-buffer. It does not make the peripheral itself faster.
1. What is it?

A master is a block that starts bus transactions (puts an address on the bus and says "read" or "write"). A slave only responds when addressed. DMA exists because a second master can move data while the first master (the CPU) does something else.

On the STM32F407 the masters are: the Cortex-M4 I-bus (instruction fetch from flash), D-bus (data loads/stores to flash and CCM), S-bus (system bus: SRAM and peripherals), the DMA1 memory port, the DMA2 memory port, the DMA2 peripheral port, the Ethernet MAC DMA and the USB OTG HS DMA. The slaves are flash (via ICode/DCode), SRAM1 (112 KB at 0x2000_0000), SRAM2 (16 KB at 0x2001_C000), the AHB1 and AHB2 peripherals and the FSMC (external memory controller).

2. How does a DMA access work, step by step?
  1. The DMA's own address generator holds the current source and destination addresses (copied from PAR and M0AR when you set EN).
  2. When a request arrives, the DMA's peripheral port drives the source address on its bus and reads one item.
  3. The DMA's memory port drives the destination address and writes the item. (In FIFO mode these two steps are decoupled by the 16-byte FIFO.)
  4. The bus matrix routes each access to the addressed slave, waiting if another master is using that slave.
3. What the DMA does NOT see
  • CPU registers. If your data is still in R0, it does not exist for the DMA.
  • The CPU's write buffer: a store may take a few cycles to reach SRAM.
  • On Cortex-M7: the CPU's L1 data cache. Data in a dirty cache line is invisible to the DMA (card 16).
  • Any slave the bus matrix does not connect to its port. CCM RAM (0x1000_0000, on the core D-bus only) is unreachable for DMA on the F4.
4. Worked example: two ports, one transfer

Each F4 DMA has two AHB master ports: a memory port and a peripheral port. For ADC1 → SRAM (P2M on DMA2):

5. What goes wrong if… you forget the DMA is a separate master?
You fill a TX buffer with sprintf on an STM32H7 and start the DMA immediately. The UART sends the previous message. In the debugger the buffer looks right, because the debugger and the CPU view go through the cache, while the DMA read SRAM.

The DMA is just another master on the interconnect, with its own address generator and its own bus ports. 5. What goes wrong if…
  • M2M: the "peripheral" port reads memory, so PAR is the source and M0AR the destination. Circular mode and direct mode are not allowed in M2M; setting them is a configuration error.
  • Two streams on one request: only one stream may serve a given peripheral request at a time. Two enabled streams on the same request give undefined behaviour (both may fire, or one may get nothing).
  • You set DMAT before EN: on TX the first TXE request may be missed, so the transfer never starts. Arm first.
6. Say it like this
Each F4 stream has PAR, M0AR, NDTR, CR and FCR. DIR selects peripheral-to-memory, memory-to-peripheral or memory-to-memory; in M2M PAR becomes the source. I program everything with EN at zero, set EN last, and only then enable the peripheral's DMA request bit, so the first request finds an armed stream.
1. What is it?

The DMA must know how many bytes one "item" is on each side, and whether each address moves after every item. These are four fields in SxCR.

2. How does it work, step by step?
  1. Alignment: PAR must be aligned to PSIZE and M0AR to MSIZE (a half-word address must be even, a word address a multiple of 4), or the stream raises a transfer error.
  2. Each request moves one PSIZE item from the peripheral side.
  3. NDTR decreases by 1 per PSIZE item. It does not count bytes and does not count memory-side items.
  4. If PINC=1 the peripheral address advances by PSIZE; if MINC=1 the memory address advances by MSIZE.

4. Packing (FIFO mode only), with numbers

With PSIZE=byte and MSIZE=word, the FIFO collects 4 bytes from the peripheral and writes one 32-bit word to SRAM. Receiving bytes 0x11, 0x22, 0x33, 0x44 produces one memory write of 0x44332211 (little-endian: first byte at the lowest address). That is a quarter of the memory-side bus transactions. NDTR still counts bytes: for 64 bytes you write NDTR = 64, not 16. NDTR must be a multiple of MSIZE/PSIZE = 4, or the last partial word is never written.

5. Wrong vs right code
WRONG

In the wrong version MSIZE=word writes 4 bytes per sample into a 2-byte-per-element array, so the DMA runs past the end of the array by N×2 bytes. In direct mode MSIZE is ignored (forced equal to PSIZE), so this bug is hidden until someone enables the FIFO.

After a colleague enables the FIFO "for performance", every other array element reads 0 and a variable placed after adc_buf gets corrupted.
6. Say it like this
PSIZE and MSIZE set the item width on each side, and PINC/MINC say whether each address advances. For receive I use PINC=0, MINC=1. NDTR always counts peripheral-size items. Width conversion such as bytes in, words out only happens in FIFO mode, and then NDTR must be a multiple of the packing ratio.
1. What is it?

The mode decides what happens when NDTR reaches zero. Normal mode stops. Circular mode (CIRC, bit 8 of SxCR) starts again at the beginning of the buffer immediately, so data flows forever without a gap.

2. How does it work, step by step?

Normal mode:

  1. NDTR counts down to 0.
  2. TCIF (Transfer Complete Interrupt Flag) sets.
  3. The hardware clears EN: the stream is off.
  4. Software must reprogram NDTR (and addresses if needed), clear flags and set EN again. Data arriving during this re-arm gap is lost (UART: ORE).

Circular mode:

  1. At NDTR = N/2, HTIF (Half Transfer flag) sets.
  2. At NDTR = 0, TCIF sets, NDTR reloads to N, and the address pointers reset to M0AR.
  3. The stream keeps running; the very next request writes element 0 again.

4. Why DMA1 cannot do memory-to-memory

On the F4, the DMA1 peripheral port is wired directly to the APB1 bus, not to the bus matrix. M2M uses the peripheral port to read the source from memory, and DMA1's peripheral port cannot reach SRAM or flash. So M2M is DMA2-only. The DMA2 peripheral port is on the bus matrix, so it serves APB2 (USART1/6, SPI1, ADCs), AHB peripherals (DCMI, CRYP, HASH) and memory.

Rule of thumb: APB1 peripherals (USART2/3, UART4/5, SPI2/3, I2C, DAC, TIM2–7) use DMA1. APB2 and AHB peripherals and M2M use DMA2. Always confirm in the reference manual's request-mapping table. Copying a stream number from another part's example is a classic bug (see Scenario 07).

Newer families replace the fixed table with a DMAMUX (DMA request multiplexer): STM32G0/G4/L4+/H7/WB and NXP eDMA+DMAMUX. Any request can go to any channel, configured by writing a request ID into a mux register.

1. What is it?

The bus matrix is the switch that connects every master (CPU buses, DMAs, Ethernet, USB) to every slave (flash, SRAM banks, peripheral bridges). It decides who gets a slave when two masters want it at the same time. Arbitration is the name for that decision.

2. How does arbitration work, step by step?
  1. Each cycle, every master that wants to access a slave presents its address to the matrix.
  2. For each slave independently, the matrix looks at which masters are asking for it.
  3. If only one master asks, it gets the slave immediately. Different masters on different slaves all proceed in parallel: the matrix is a crossbar.
  4. If several masters ask for the same slave, the matrix grants them in round-robin order. The losers wait (their bus stalls).
  5. A granted master keeps the slave for the whole single transfer or burst before the next arbitration.
3. Two levels of arbitration
  1. Inside one DMA controller: the stream arbiter picks the next stream to serve using the software priority PL[17:16] (00 low, 01 medium, 10 high, 11 very-high). Ties go to the lower stream number. It re-arbitrates after every single transfer or burst, so a long INCR16 burst holds the port.
  2. Between masters (CPU, DMA1, DMA2, ETH, USB): the bus matrix round-robin decides per slave. Stream priority has no effect here.
4. Worked example: same bank vs different banks
Case A: CPU stack in SRAM1, DCMI DMA buffer in SRAM1
  cycle:  1    2    3    4    5    6
  CPU   : LD   wait LD   wait LD   wait     ← CPU load takes ~2× longer
  DMA2  : wait WR   wait WR   wait WR

Case B: CPU stack in SRAM1, DMA buffer in SRAM2
  CPU   : LD   LD   LD   LD   LD   LD       ← both at full speed
  DMA2  : WR   WR   WR   WR   WR   WR

Measured effect: a CPU loop that does 1 000 000 SRAM loads might take 1.0 M cycles alone and up to ~2 M cycles while a heavy DMA hits the same bank. Measure it with the DWT cycle counter (DWT->CYCCNT) before and after moving the buffer.

  • Classic F4 tip: place high-bandwidth DMA buffers (camera/DCMI, Ethernet) in SRAM2, or in SRAM1 with the CPU data in CCM. Keep in mind that CCM itself cannot be a DMA target.

1. What is it?

Each F4 stream has a small FIFO (First In, First Out buffer) of 4 words = 16 bytes between its peripheral port and its memory port. In direct mode the FIFO is bypassed and each request is one read immediately followed by one write. In FIFO mode the peripheral side fills the FIFO and the memory side empties it in chunks. The register is DMA_SxFCR: DMDIS (bit 2, 1 = FIFO mode), FTH[1:0] (threshold ¼, ½, ¾, full), FS[5:3] (fill status, read-only), FEIE (bit 7, FIFO error interrupt enable).

2. How does FIFO mode work, step by step? (P2M, PSIZE=byte, MSIZE=word, FTH=½)
  1. A request arrives; the DMA reads one byte from the peripheral and pushes it into the FIFO (fill = 1 byte).
  2. More requests: fill grows to 2, 3, … bytes. Nothing is written to memory yet.
  3. When the fill reaches the threshold (½ = 8 bytes), the memory port requests the bus and writes 2 words (8 bytes) to SRAM.
  4. If the memory side has to wait for the bus matrix, the peripheral side keeps filling: the FIFO absorbs the delay.
  5. At the end of the transfer (NDTR = 0) or on disable, the remaining bytes are flushed to memory.

3. Burst rules (RM0090 §9.3.11), with arithmetic
  • MBURST[24:23] / PBURST[22:21]: 00 single, 01 INCR4, 10 INCR8, 11 INCR16 beats. A beat is one item of MSIZE (or PSIZE).
  • A burst must not cross a 1 KB address boundary, because the AHB protocol forbids it. Align buffers accordingly.
  • The burst must fit the threshold: beats × MSIZE must be ≤ and divide the FIFO threshold level in bytes. A forbidden combination raises FEIF at enable time and the stream does not start.
MBURST=INCR4, MSIZE=word: 4 × 4 B = 16 B → needs FTH = full (16 B) MBURST=INCR4, MSIZE=half-word: 4 × 2 B = 8 B → FTH = ½ (8 B) or full (16 B) MBURST=INCR8, MSIZE=half-word: 8 × 2 B = 16 B → FTH = full only MBURST=INCR16, MSIZE=word: 16 × 4 B = 64 B → larger than the 16 B FIFO → forbidden

Bursts cut arbitration overhead (one arbitration per 4–16 beats) but hold the bus longer, which adds latency for other masters.

1. What is it?

DBM (Double Buffer Mode, bit 18 of SxCR) gives the stream two memory pointers, M0AR and M1AR. CT (bit 19, "Current Target") says which one the DMA is writing now: CT=0 → M0AR, CT=1 → M1AR. It is like circular mode, except the two halves are two separate buffers at independent addresses. DBM forces circular behaviour and is not available in M2M.

2. How does it work, step by step?
  1. You set M0AR = bufA, M1AR = bufB, NDTR = BLK (the size of one buffer), DBM=1, CT=0, EN=1.
  2. The DMA fills bufA. NDTR counts BLK → 0.
  3. At 0: TCIF sets, NDTR reloads to BLK, CT toggles to 1, and the DMA continues straight into bufB with no gap.
  4. Your TC ISR runs. CT=1 now, so the buffer that just finished is M0 (bufA).
  5. While CT=1 you may rewrite M0AR with a fresh buffer pointer from a pool. At the next TC, CT toggles back to 0 and the DMA uses the new pointer.
time ─────────────────────────────────────────────────▶
DMA:  [ fill M0=bufA ][ fill M1=bufB ][ fill M0=bufC ][ fill M1=bufD ]
CT :        0                1               0               1
TC :              ^ M0 done        ^ M1 done       ^ M0 done
ISR:              swap M0AR←bufC   swap M1AR←bufD   ...
CPU:                [process bufA ][process bufB ][process bufC ]
3. Worked example with numbers

SPI2 at 10.5 Mbit/s receives 8-bit items: 10.5e6 / 8 = 1.3125 M bytes/s. With BLK = 1024 bytes each buffer fills in 1024 / 1.3125e6 = 780 µs. That is the deadline to swap the idle pointer and the time the consumer has to release a buffer if the pool has only two buffers. With a pool of 8 buffers the consumer can fall behind by up to 6 × 780 µs = 4.7 ms without losing data.

2. Each flag, defined
  • TCIF (Transfer Complete): NDTR reached 0. Also set when you abort by clearing EN.
  • HTIF (Half Transfer): NDTR reached half of its programmed value.
  • TEIF (Transfer Error): a bus error on either port (unreachable address such as CCM, a reserved region, or a misaligned pointer), or a write to the in-use M0AR/M1AR in DBM. Hardware clears EN, so the stream stops. If TEIE is off you get silence.
  • DMEIF (Direct Mode Error): in direct mode, a new request arrived before the previous data was written, or the stream was enabled in a forbidden configuration.
  • FEIF (FIFO Error): underrun/overrun, or a threshold/burst combination that is not allowed. In P2M with DMDIS=1 a FIFO overrun is the symptom of severe bus starvation.

1. What is it?

NDTR[15:0] (Number of Data To Transfer) holds the number of PSIZE items remaining. The maximum is 65 535. Writing 0 means nothing transfers. It is writable only when EN=0. Reading it while the stream runs tells you where the DMA is.

2. How is it used, step by step?
  1. You write N (e.g. 256) with EN=0.
  2. It decrements after each peripheral-side transfer.
  3. In P2M, pos = N − NDTR is the index of the next element the DMA will write. In direct mode everything before it is already in RAM. In FIFO mode some of it may still be in the FIFO.
  4. In circular/DBM mode it reloads automatically at 0. Treat a read of N − NDTR == N as position 0 (you caught it exactly at the reload edge).
  5. For a normal-mode abort, NDTR tells you how many items did not transfer.

4. Worked timing example

5. What goes wrong if…
  • Order reversed (ADC DMA bit before EN): the first request arrives with no stream ready. For ADC that is OVR (overrun) and the ADC stops issuing requests; for UART it is lost bytes.
  • No DDS: the ADC stops generating DMA requests after the DMA's last transfer, so circular mode runs exactly one lap and then silently stops.
  • Late ISR: HTIF and TCIF can both be set at once. The handler above posts both halves in order. If it is that late you have probably overrun anyway, so count it.
Without DDS: the first 1024 samples arrive, HT and TC fire once, and then nothing, while the ADC's OVR flag sets. Without TEIE: a bad address gives no interrupt at all.

1. What is it?

Ping-pong buffering means splitting a buffer into two parts: while the DMA fills one ("ping"), the CPU processes the other ("pong"), then they swap. It is how circular + HT/TC and double-buffer mode are used in practice. The one rule that makes it work is about ownership: at any moment each half belongs to exactly one side.

2. How does the timing work, step by step?
  1. At HT, half A is complete. Ownership of half A passes to the CPU; the DMA owns half B.
  2. The ISR runs (ISR latency), then wakes a task (task wake-up latency).
  3. The task may wait behind higher-priority tasks (blocking/preemption time).
  4. The task processes half A (processing time = items × cycles per item ÷ clock).
  5. Half A must be handed back before the DMA re-enters it, which happens exactly T_half = (N/2) / R after HT.

DMA :  [AAAA]|[BBBBBBBBBBBBBBBBBBBBBBB]|[AAAA... DMA re-enters half A here
CPU :        |<-lat->[ process A ]     |
             |<-------- T_half ------->|
             half A must be released before TC, i.e. within T_half of HT

  • If processing alone is ≥ 100 % (R·c_proc ≥ f), no buffer size helps. You need a faster algorithm or a lower rate.

"Just copy the half out in the ISR so the DMA can overwrite it." That works, but you now pay a full-block memcpy in interrupt context, and the copy still has to finish within T_half. It hides the problem. A deeper buffer or DBM with a buffer pool is usually better.
The average CPU load is 60 % and the system "works", but once every few seconds a block is corrupted: a spike in an FFT, a click in audio, a CRC failure. That is a worst-case latency longer than T_half, and without ownership flags it is silent.
With ping-pong the CPU owns the finished half for exactly one half-period, T_half equals N over 2 divided by the rate. Worst-case latency plus processing must fit inside it, which gives N/2 ≥ L·R / (1 − R·c/f). I add ownership flags so that an overrun is counted instead of silently corrupting data.
1. What is it?

A plain HAL_UART_Receive_DMA(buf, 64) only finishes when exactly 64 bytes have arrived. Real protocols send variable-length frames (Modbus RTU, NMEA, AT command responses), so a short frame sits in the buffer until enough later bytes push the count to 64. The standard fix: circular DMA forever, plus the USART IDLE interrupt. IDLE (idle-line detected) sets when the RX line stays high for one full character time after at least one byte was received.

2. How does it work, step by step?
  1. The DMA runs in circular mode into rx[256] and never stops.
  2. Three events call the same function rx_check(): HT, TC and IDLE.
  3. rx_check() reads NDTR once and computes pos = 256 − NDTR (the next write index).
  4. It hands the bytes between the last position old_pos and pos to the parser, in one chunk, or in two if the ring wrapped past the end.
  5. It stores old_pos = pos.
3. Worked example: a wrapped frame
RX_SZ = 256, old_pos = 250, a 12-byte frame arrives, then the line goes idle
DMA writes rx[250..255] (6 bytes) then wraps and writes rx[0..5] (6 bytes)
NDTR = 250 → pos = 256 − 250 = 6
pos (6) < old_pos (250) → wrapped:
   consume(&rx[250], 256 − 250 = 6)
   consume(&rx[0],   6)
old_pos = 6

Timing: at 115200 baud one character is 86.8 µs, so IDLE fires about 87 µs after the last stop bit.

5. What goes wrong if…
  • No HT/TC: a continuous stream with no pause never triggers IDLE, so the ring laps unnoticed. HT/TC guarantee a check at least every RX_SZ/2 bytes.
  • Ring too small: the ring cannot detect overflow by itself. If more than RX_SZ bytes arrive between two checks, data is silently overwritten. Size it: worst-case latency × byte rate. At 115200 (11.5 kB/s) and a 10 ms worst case, that is 115 bytes, so 256 is fine.
  • Different priorities for the USART and DMA IRQs: one can preempt the other in the middle of rx_check() and corrupt old_pos.

Alternatives: HAL_UARTEx_ReceiveToIdle_DMA() (its RxEventCallback(Size) gives the position, not a length, in circular mode), the receiver-timeout RTOR on newer USARTs (F7/L4/H7, configurable in bit times), or character match (CMF) for delimiter-based protocols.

1. What is it?

From the moment you set EN until TC (or a confirmed abort), the buffer belongs to the DMA. The CPU must not write a TX buffer (half-old, half-new frames get sent) and must not trust an RX buffer. The buffer must also exist for the whole transfer. "Lifetime" is the C term for how long a variable's memory is reserved. A local variable (automatic storage) lives only until its function returns.

2. What happens with a stack buffer, step by step?
  1. send_status() runs. frame[32] is placed on the stack at, say, 0x2001FF80.
  2. The DMA is started on 0x2001FF80 and the function returns at once.
  3. The next function called (e.g. log_flush()) gets a stack frame at the same addresses and stores its locals and its saved LR (return address) there.
  4. TX: the DMA sends those locals instead of your frame. RX: the DMA writes received bytes over log_flush()'s saved LR.
  5. log_flush() returns to the corrupted address → HardFault far from the real cause.

4. Worked example: the "magic" crash value

If an SPI sensor returns the pattern 0x5A 0xA5 and the HardFault frame shows a stacked PC of 0x0000A55A, that value is sensor data. Two received bytes landed on a saved return address. Seeing your own payload in a fault register is the fingerprint of a DMA lifetime bug (Scenario 04).

5. What goes wrong if… (other cases)
  • RX from the stack is worse than TX: the DMA corrupts locals and saved LR values. You get a HardFault far from the cause.
  • On Linux, never DMA to or from stack memory. With CONFIG_VMAP_STACK the stack is vmalloc'd and not physically contiguous.
  • RTOS: if a task allocates a DMA buffer and is deleted mid-transfer, the same bug happens. Abort the stream in the cleanup path.
  • Modifying a static TX buffer while the DMA is still sending gives a frame that is half old and half new.

1. What is it?

The Cortex-M7 has an optional L1 D-cache (data cache): 4 KB on STM32F74x/75x, 16 KB on F76x/H7. A cache is a small fast memory next to the CPU that keeps copies of recently used RAM. It is organised in lines of 32 bytes: the cache always copies or discards whole 32-byte blocks. The default memory attributes make SRAM write-back, write-allocate: a CPU store updates only the cached copy and marks the line dirty; SRAM is updated later, when the line is evicted or cleaned. The DMA writes and reads SRAM directly and never looks in the cache. Coherency means the CPU and the DMA see the same values. That gives two failure modes, which are mirror images of each other:

DirectionHazardMaintenanceWhen
CPU → DMA (TX)CPU's new bytes sit in dirty cache lines. DMA reads old SRAM.Clean (write back dirty lines)After filling the buffer, before enabling the stream
DMA → CPU (RX)CPU reads stale lines cached before the DMA wrote SRAMInvalidate (discard lines)After completion, before reading. Also before starting.
2. How does the TX failure happen, step by step?
  1. CPU writes "NEW" into tx_buf. Write-back: only the cache line changes, marked dirty. SRAM still holds "OLD".
  2. The DMA is started and reads SRAM: "OLD".
  3. The UART sends "OLD". The debugger shows "NEW" because it reads through the core.
  4. Fix: SCB_CleanDCache_by_Addr writes the dirty line to SRAM before EN.
3. Why invalidate before AND after RX
  • Before: if any line of the RX buffer is dirty (you memset it, or it held old data), a later eviction writes it back to SRAM, on top of what the DMA just wrote. Invalidating (or clean+invalidating) first removes dirty lines.
  • After: the M7 can speculatively read normal memory and allocate lines while the DMA is running, for example after a branch prediction or a loop that touches nearby addresses. An invalidate only before the transfer is therefore not enough. Invalidate after TC, then read.
4. The alignment rule, with arithmetic

Cache operations work on whole 32-byte lines. If an RX buffer shares a line with another variable, invalidating the buffer also discards that variable's dirty update (Scenario 02). Cleaning it during RX writes the CPU's stale copy of the buffer bytes over the DMA data. So the buffer must start on a 32-byte boundary and occupy a multiple of 32 bytes.

1. What is it?

The MPU (Memory Protection Unit) lets you assign attributes to address ranges, including whether they are cacheable. Instead of maintaining the cache on every transfer, mark a dedicated RAM region Normal, non-cacheable (TEX=001, C=0, B=0) and put all DMA buffers and descriptors there. Coherency problems disappear because the CPU never caches those addresses. The cost is that CPU accesses to that region go to SRAM at bus speed.

2. How do you set it up, step by step?
  1. Choose a region: base address aligned to its size, size a power of two ≥ 32 bytes.
  2. Disable the MPU while you change it.
  3. Program the region attributes: TEX=001, C=0, B=0 (Normal, non-cacheable).
  4. Re-enable the MPU with the default map as background (PRIVDEFENA).
  5. Tell the linker to place DMA buffers in that address range.

1. What is it?

A memory barrier is an instruction that forces memory operations before it to complete (or be ordered) before those after it. ARM has DMB (Data Memory Barrier: orders memory accesses), DSB (Data Synchronization Barrier: waits until all earlier memory accesses have completed) and ISB (Instruction Synchronization Barrier: flushes the pipeline). Barriers matter for DMA because the "consumer" of your stores is another bus master, which the compiler and the CPU do not know about.

2. Two kinds of reordering
  1. Compiler ordering: the compiler may sink buffer stores past the register write that starts the DMA, because it does not know the register write "reads" the buffer. A volatile register write orders only against other volatile accesses. Use __DMB() (which is also a compiler barrier in CMSIS) or __COMPILER_BARRIER().
  2. Hardware ordering: ARMv7-M does not order Normal-memory stores against a later Device-memory store unless you use a barrier. Cortex-M4 is in-order with a small write buffer, so it rarely matters there. On the M7 (AXI bus, out-of-order transactions, write buffers) it does. Pattern: fill buffer → clean (M7) → __DSB() → set EN.

  4. The stream sets TEIF and the hardware clears EN. NDTR does not move.

5. What goes wrong if…

Symptom pattern: "the DMA never completes, no callback". You enabled TC interrupts but not TE, and the stream died on its first beat. Always enable TEIE in bring-up code, and assert on the buffer address range. On the H7, check the map file: if your buffer's address starts with 0x2000xxxx it is in DTCM and DMA1/DMA2 will fail.

6. Say it like this
Not every memory is wired to every master. On the F4 the 64 KB CCM is only on the core D-bus, and on the H7 DMA1 and DMA2 cannot reach DTCM; only MDMA can, and BDMA only reaches SRAM4. A DMA aimed there gets a bus error, TEIF sets and the stream is disabled, which is silent if TEIE is off. So I always enable TE interrupts and assert buffer addresses.
1. What is it?

A simple DMA (an STM32F4 stream) holds one transfer description in registers. Chaining transfers takes CPU work at each boundary, and the hardware sits idle while you re-arm. Linked-list (scatter-gather) DMA keeps a list of descriptors in memory. A descriptor is a small struct holding the register values for one block: source, destination, length, and a pointer to the next descriptor. At the end of each block the engine fetches the next descriptor itself, with no CPU and no gap. "Gather" = collect pieces from many places into one stream; "scatter" = spread one stream into many places.

2. How does it work, step by step?
  1. Software builds descriptors in RAM: D0 (header, 8 bytes) → D1 (payload, 512 bytes) → D2 (CRC, 4 bytes) → end.
  2. Software points the channel at D0 and enables it.
  3. The engine loads D0 into its registers and transfers the header.
  4. At the end of D0's block it reads the link field, loads D1 from memory and continues immediately.
  5. After D2 the link is 0: the channel stops and raises one TC interrupt.
  RAM:  [D0: src=hdr  len=8   next=D1]──▶[D1: src=pay len=512 next=D2]──▶[D2: src=crc len=4 next=0]
             │                                 │                               │
             ▼                                 ▼                               ▼
  SPI TX: hdr(8) ─────────────────────────── payload(512) ─────────────────── crc(4)   = 524 bytes, 1 IRQ
3. STM32U5 / H5 GPDMA
  • Per channel: CTR1 (widths, increments, bursts), CTR2 (request select, trigger), CBR1 (block bytes), CSAR (source), CDAR (destination), CLLR (link register).
  • A linked-list item (LLI) is simply the next values of those registers, stored in memory. CLLR holds update bits UT1 UT2 UB1 USA UDA ULL that say which registers the next LLI reloads, plus LA[15:2], the low 16 bits of the next LLI address. CLBAR gives the high 16 bits, so all LLIs of a list must sit in the same 64 KB page. LA = 0 ends the list. Pointing the last LLI back at the first gives a circular list.
typedef struct { uint32_t CTR1, CTR2, CBR1, CSAR, CDAR, CLLR; } gpdma_lli_t;   // full-update LLI, linear channel
#define LLI_ALL (DMA_CLLR_UT1|DMA_CLLR_UT2|DMA_CLLR_UB1|DMA_CLLR_USA|DMA_CLLR_UDA|DMA_CLLR_ULL)
hdr.CLLR = LLI_ALL | ((uint32_t)&payload & 0xFFFCu);   // header frame, then the payload LLI
payload.CLLR = 0;                                        // end of list: TC fires once at the end

4. NXP eDMA (Kinetis, i.MX RT, S32K): Transfer Control Descriptors
typedef struct {                 // 32 bytes, 32-byte aligned
    uint32_t SADDR;              // source address
    int16_t  SOFF;  uint16_t ATTR;   // src offset per read; SMOD|SSIZE|DMOD|DSIZE
    uint32_t NBYTES;             // MINOR loop: bytes moved per request
    int32_t  SLAST;              // src adjust after the major loop
    uint32_t DADDR;
    int16_t  DOFF;  uint16_t CITER;  // current MAJOR iteration count
    int32_t  DLAST_SGA;          // dest adjust, OR next TCD address when CSR.ESG = 1
    uint16_t CSR;   uint16_t BITER;  // START, INTMAJOR, INTHALF, DREQ, ESG, MAJORELINK...
} edma_tcd_t;
  • Two-level loop: each hardware request runs one minor loop (NBYTES). CITER counts the major loop. At major-loop completion the engine applies SLAST/DLAST, can interrupt (INTMAJOR, plus INTHALF at the midpoint), and with ESG = 1 (Enable Scatter Gather) loads a whole new TCD from DLAST_SGA. That is scatter-gather. MAJORELINK/ELINK chain to another channel.
Worked example: 256 UART bytes, 1 byte per request NBYTES = 1, SOFF = 0 (fixed data register), DOFF = +1, CITER = BITER = 256 DLAST_SGA = −256 → after 256 requests the destination rewinds to the start = circular buffer INTHALF fires at CITER = 128, INTMAJOR at 0 → the eDMA equivalent of HT/TC
5. What goes wrong if…
The descriptors are read by the DMA from RAM. All the coherency rules apply to them too: clean after writing them on an M7, or place them in non-cacheable memory. A GPDMA list that crosses a 64 KB page, or an eDMA TCD that is not 32-byte aligned, makes the engine load garbage and raise a transfer/configuration error.

Uses: gather a header and a payload from different places into one SPI/UART frame with no memcpy; queue N buffers so the DMA never stops; drive a peripheral's register sequence (a write to CS, then data, then a write to CS) without the CPU.

6. Say it like this
A simple DMA holds one transfer in registers, so chaining needs an ISR at every block and leaves a gap. Linked-list DMA keeps descriptors in memory and the engine loads the next one itself, which gives gap-free chaining and native gather or scatter. On the GPDMA the items are register images linked through CLLR within one 64 KB page; on NXP eDMA they are 32-byte TCDs chained with the ESG bit. Descriptors need cache coherency like any DMA data.
1. What is it?

Every high-throughput peripheral with its own DMA (Ethernet, USB HS, SDMMC IDMA, PCIe NICs) uses descriptor rings: an array of descriptors in memory, used in a circle, shared by the CPU and the DMA. Who may touch each descriptor is decided by an OWN bit: OWN=1 means the DMA owns it, OWN=0 means the CPU owns it. Zero-copy means the data is never memcpy'd: buffers are passed by pointer between the hardware and the software stack.

typedef struct {
    volatile uint32_t des0;   // TX: bit31 OWN (1 = DMA owns), bit29 LS, bit28 FS, bit21 TER (end of ring), bit20 TCH (chained)
    volatile uint32_t des1;   // buffer 1 size [12:0] (and buffer 2 size)
    volatile uint32_t des2;   // buffer 1 address
    volatile uint32_t des3;   // buffer 2 address, or next descriptor (chain mode)
} eth_desc_t;
2. RX ring, step by step
  1. At init the CPU fills every descriptor with an empty 1536-byte buffer and sets OWN=1.
  2. A frame arrives. The MAC DMA writes it into the next descriptor's buffer, writes status and length into des0, and clears OWN.
  3. The driver sees OWN=0, takes that buffer and passes it up the stack by pointer (lwIP pbuf_custom, Linux build_skb).
  4. The driver attaches a fresh empty buffer to the descriptor, barrier, sets OWN=1 again.
  5. If the DMA had suspended (no owned descriptor), the driver writes the RX poll-demand register DMARPDR.
ring of 4:   [d0 OWN=0 ✓frame] [d1 OWN=0 ✓frame] [d2 OWN=1 empty] [d3 OWN=1 empty]
              ^ CPU next to read                   ^ DMA next to fill
if the CPU is slow: all OWN=0 → RBUS (receive buffer unavailable) → frames dropped
3. Worked example: ring depth
100 Mbit/s, minimum frames: 64 B + 20 B preamble/IFG = 84 B = 672 bits → 148 800 frames/s one frame every 6.72 µs. Driver task can be delayed 1 ms → 1000 / 6.72 = 149 frames ring of 8 descriptors survives only 8 × 6.72 = 54 µs of delay at line rate → under a min-size flood with 1 ms latency you WILL drop frames; size for the real traffic mix

5. What goes wrong if…
  • Zero-copy only works if buffers stay alive until the hardware is done: on TX, free the pbuf in the TX-complete path, not right after setting OWN.
  • On an H7 the descriptors and buffers must be coherent; ST's examples place them at 0x3004_0000 in an MPU non-cacheable region.
  • Missing DMB: the MAC can see OWN=1 before the length field is written.

The same idea in UART/SPI terms: DBM with a buffer pool, so the DMA fills buffer k while the application holds buffer k−1 by pointer.

6. Say it like this
High-throughput peripherals use descriptor rings in RAM, with an OWN bit saying whether the DMA or the CPU may touch each descriptor. On receive the MAC fills a buffer and clears OWN; the driver passes that buffer up by pointer and re-arms the descriptor with a fresh one, so nothing is copied. It needs a barrier before setting OWN, buffers that live until the hardware is done, and coherent descriptor memory.
1. What is it?

Low-power modes switch off clocks to save energy. Whether the DMA keeps working depends on which clocks are off. On the STM32F4: Sleep stops only the CPU clock; Stop stops all clocks in the 1.2 V core domain; Standby powers the core domain down.

2. The classic pattern, step by step
  1. Start a long circular ADC or UART RX DMA.
  2. Call __WFI() (Wait For Interrupt): the CPU clock stops, but HCLK (the bus clock) keeps running in Sleep.
  3. The DMA and the peripheral keep moving data while the CPU sleeps.
  4. HT or TC wakes the CPU; it processes one block and goes back to sleep.
  • The RCC AHB1LPENR.DMAxLPEN and SRAMxLPEN bits must stay set (they are set at reset), or the DMA/SRAM clocks stop in Sleep.
  • Stop mode on F4: all clocks in the 1.2 V domain stop, so no DMA. An in-flight transfer freezes. Finish or abort before entering Stop, and re-check NDTR after wake-up.
  • Newer parts move the line: STM32L4/U5 LPUART can wake from Stop. The STM32U5 has LPDMA + LPBAM (Low-Power Background Autonomous Mode), which runs linked-list DMA autonomously in Stop 2 (e.g. collect ADC samples into SRAM4 with the core powered down).
3. Worked example: energy
Logger: 1 kSPS ADC. Wake cost ≈ 20 µs at 30 mA, sleep current 8 mA (Sleep mode, DMA running) per-sample IRQ: 1000 wakes/s × 20 µs = 20 ms awake per second (2 %) DMA, 512-sample halves: 1000/512 ≈ 2 wakes/s × 20 µs = 40 µs awake per second (0.004 %) average current ≈ 8 mA + 0.02 × 22 mA = 8.44 mA vs 8 mA + 0.00004 × 22 mA ≈ 8.00 mA

Energy rule: energy ≈ wake-ups × wake cost + active time. Larger DMA blocks mean fewer wake-ups, at the price of latency and RAM. (Numbers above are illustrative; measure your board.)

4. Code

for (;;) {
    __WFI();                           // Sleep: DMA keeps running
    if (half_ready) { half_ready = 0; process(half_ptr); }
}

HAL_PWR_EnterSTOPMode(PWR_LOWPOWERREGULATOR_ON, PWR_STOPENTRY_WFI);
5. What goes wrong if…
After adding Stop mode to save power, the UART occasionally loses the first bytes after wake-up and an in-progress SPI frame comes out truncated. The DMA was frozen mid-transfer when the clocks stopped.
6. Say it like this
In Sleep only the CPU clock stops, so the DMA and peripherals keep running and I wake once per block instead of once per byte. In F4 Stop mode the core-domain clocks stop and the DMA freezes, so I finish or abort transfers first. Newer parts like the STM32U5 have an LPDMA that runs autonomously in Stop 2.
1. What is it?

Under an OS with an MMU (Memory Management Unit) the CPU uses virtual addresses, which mean nothing to a device. A driver must hand the device a dma_addr_t, a bus address (an IOVA, I/O Virtual Address, if an IOMMU is present), obtained only from the kernel's DMA API. The API also does the cache maintenance for you.

2. A streaming RX transfer, step by step
  1. buf = kmalloc(2048, GFP_KERNEL): ordinary kernel memory.
  2. h = dma_map_single(dev, buf, 2048, DMA_FROM_DEVICE): the kernel invalidates the cache lines and returns the bus address.
  3. Check dma_mapping_error(dev, h).
  4. Program the device with h and start it. The device now owns the buffer: the CPU must not touch it.
  5. On completion, dma_unmap_single(dev, h, 2048, DMA_FROM_DEVICE): ownership returns to the CPU (with any needed invalidate).
  6. Now the CPU reads buf.

4. IOMMU, masks, barriers
  • IOMMU / SMMU (System MMU on Arm): translates device addresses, so it can stitch non-contiguous pages into one range, and it isolates devices. A buggy or malicious bus master (Thunderbolt/PCIe) can only touch pages that were mapped for it.
  • dma_set_mask_and_coherent(dev, DMA_BIT_MASK(32)) declares the device's addressing limit (here 32 bits = 4 GB). Memory above that limit gets bounce buffers (swiotlb): the kernel copies through low memory, which is slow and silent. Check for them in profiling.
  • Barriers: dma_wmb() between filling descriptor fields and setting OWN; dma_rmb() between reading OWN and reading the rest.
5. What goes wrong if…
  • You pass virt_to_phys(buf) instead of using the DMA API: works on one board, breaks with an IOMMU or a non-identity bus offset.
  • You map stack or vmalloc memory with dma_map_single: not physically contiguous (with VMAP_STACK), corrupts random pages.
  • You read the buffer before unmapping or syncing for CPU: stale cache data, just like the M7 case.
6. Say it like this
In Linux a device needs a dma_addr_t from the DMA API, never a virtual pointer. I use dma_alloc_coherent for long-lived shared structures like descriptor rings and dma_map_single for per-transfer streaming buffers, where the device owns the buffer between map and unmap and the API does the cache maintenance. An IOMMU translates and isolates device accesses, and the DMA mask tells the kernel the device's address width.

NEVER DO THIS
  • DMA into or out of a local (stack) array from a function that returns before TC.
  • Put DMA buffers in F4 CCM RAM or H7 DTCM (DMA1/2).
  • Leave TEIE disabled in bring-up. A dead stream is then silent.
  • |= into LIFCR/HIFCR, or clear another stream's flags with a wide mask.
  • Reconfigure a stream without waiting for EN to read 0.
  • Re-enable without clearing old flags.
  • Write the in-use MxAR in DBM (TEIF, stream stops).
  • Invalidate a buffer that is not 32-B aligned and sized (neighbour data lost).
  • Forget the cache clean before M7 TX, or the invalidate after M7 RX.
  • Trust volatile to fix cache coherency.
  • Use fixed-length DMA RX for variable-length UART frames without IDLE/RTO.
  • Process a half in a task without checking that it finished before the DMA came back.
  • Copy a stream/channel number from a different part's example.
  • Let a burst cross a 1 KB boundary.
  • Enable the peripheral's DMA request before the stream is armed.

60-SECOND REVISION
  • DMA is a second bus master. It saves CPU cycles and turns per-item deadlines into per-block deadlines. It does not make the peripheral faster.
  • F4: 2 controllers × 8 streams. Each stream picks 1 of 8 request channels (fixed table). M2M only on DMA2.
  • Program PAR, M0AR, NDTR, CR (CHSEL, DIR, sizes, INC, CIRC, PL, IE). Set EN last. Then enable the peripheral's DMA request.
  • NDTR = remaining PSIZE items. P2M write position = N − NDTR.
  • Circular + HT/TC = ping-pong. The CPU owns the finished half for exactly T_half.
  • DBM: M0AR/M1AR, CT = buffer being filled. Rewrite only the idle pointer.
  • FIFO (16 B): packing, bursts, required for M2M, absorbs bus latency. Direct: exact positions, MSIZE=PSIZE.
  • Flags: TC, HT, TE, DME, FE in LISR/HISR at bases 0/6/16/22. Clear with W1C writes.
  • TE: unreachable address or misalignment. HW disables the stream. Always enable TEIE.
  • Bus matrix: round-robin per slave. Spread CPU and DMA data across SRAM banks.
  • UART variable frames: circular DMA + IDLE (or RTO) + a ring reader driven by HT/TC/IDLE.
  • M7: clean before TX. Invalidate before and after RX. 32-B aligned and sized. Or use an MPU non-cacheable region.
  • Barriers: DMB between data and an OWN/EN write, DSB before kicking the hardware.
  • Linked-list DMA (GPDMA LLI, eDMA TCD + ESG): HW chains blocks, no re-arm gap, gather/scatter.
  • Descriptor rings + OWN bit = zero-copy networking. Descriptors must be coherent too.
  • Sleep: DMA keeps running (wake per block). F4 Stop: DMA frozen. U5 LPBAM: DMA in Stop 2.
  • Linux: dma_alloc_coherent for rings, dma_map_single for packets. IOMMU = translation + isolation.
