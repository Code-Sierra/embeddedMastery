Interrupts from zero: a guided tutorial

Read this tab top to bottom before anything else. It assumes you know C and roughly what a microcontroller is, and nothing about interrupts. Every term is defined the first time it appears. The reference chip is the STM32F407 (an Arm Cortex-M4F core running at 168 MHz), the same part used in the rest of the page.

STEP 1What problem does an interrupt solve?

A microcontroller's CPU can do only one thing at a time: it fetches one instruction, runs it, fetches the next. But the world outside the chip does many things at once. A byte arrives on a serial cable, a button is pressed, a timer runs out, a sensor finishes a measurement. The CPU needs some way to notice these events quickly without spending all of its time watching for them.

There are two ways to notice an event:

Way 1: Polling (keep checking)Your program reads a status register again and again in a loop: "Has a byte arrived yet? No. Has a byte arrived yet? No. Has a byte arrived yet? Yes!" It is like getting up every 10 seconds to look out of the window for the postman.
Way 2: Interrupts (be told)Your program does other work. When the event happens, the hardware itself stops your program, runs a special function that deals with the event, and then puts your program back exactly where it was. It is like a doorbell: you keep working and the bell tells you when to go to the door.

Real numbers. A UART (Universal Asynchronous Receiver/Transmitter, the serial port peripheral) running at 115200 baud sends 10 bits per byte (1 start bit + 8 data bits + 1 stop bit). So a new byte can arrive every

10 bits ÷ 115 200 bits/s = 86.8 µs per byte 86.8 µs × 168 000 000 cycles/s = 14 583 CPU cycles between bytes

If the CPU polls, it either wastes all of those 14 583 cycles checking a flag, or it goes off to do other work and risks coming back too late (the UART on the STM32F4 holds just one received byte; if a second byte finishes arriving before you read the first, the first is overwritten and an overrun error is flagged). With an interrupt, the hardware gets the CPU into your handler in about 12 cycles (71 ns), the handler takes perhaps 30 cycles, and returning takes about 10. That is roughly 52 cycles of every 14 583, or 0.36 % of the CPU, and the rest of the time the CPU is free or even asleep.

The trade-off in one line: interrupts give fast response and low CPU and power use, but they make your program concurrent: code can be stopped between any two instructions, which creates a new class of bugs (shared data, priorities, stack usage). The rest of this page teaches you to handle both sides.

STEP 2The hardware picture: who talks to whom

An interrupt passes through four pieces of hardware. Look at the diagram first, then read the description of each box.

Box 1: the peripheral (here USART1)

A peripheral is a hardware block on the chip next to the CPU: UARTs, timers, ADCs, GPIO ports. Each peripheral has status flags (bits that say "something happened", such as RXNE = "Receive data register Not Empty") and interrupt-enable bits (such as RXNEIE = "RXNE Interrupt Enable"). When a flag is 1 and its enable bit is 1, the peripheral drives its interrupt request line high. If the enable bit is 0, the flag still gets set, but nobody is told; you would have to poll it.

Box 2: the NVIC

The NVIC (Nested Vectored Interrupt Controller) is a block built into every Cortex-M core. It receives all the request lines (82 of them on the STM32F407, numbered IRQ0 to IRQ81) and for each one keeps three things: an enable bit (is this interrupt allowed at all?), a pending bit (has it been requested and not yet served?), and an 8-bit priority value (how urgent is it?). Its job is to decide, every cycle, whether the most urgent pending interrupt is more urgent than whatever the CPU is doing right now. "Nested" means one interrupt handler can itself be interrupted by a more urgent one. "Vectored" means the hardware jumps straight to the right handler for each source, with no software lookup.

Box 3: the core

The core is the CPU itself. When the NVIC says "take this one", the core saves a few of its registers onto the stack (a region of RAM used as last-in-first-out storage; the register SP, Stack Pointer, holds the address of the top), looks up the handler's address, and starts executing it. The core also has mask registers (PRIMASK, BASEPRI) that software can set to temporarily hold interrupts back.

Box 4: memory (vector table in flash, stack in SRAM)

The vector table is an array of 32-bit addresses in flash, one entry per possible exception. The core reads entry number N at address VTOR + 4 × N to find the handler for exception N. (VTOR = Vector Table Offset Register, holds the table's base address; on our STM32 build it is 0x0800_0000.) The stack lives in SRAM and receives the saved registers.

STEP 3The key terms, one by one

These words appear everywhere on this page and in interviews. Read each definition once; come back here whenever a word feels fuzzy.

Exception
Arm's general word for "anything that makes the core stop normal code and run a handler". Includes reset, faults (errors), system calls, and interrupts.
Interrupt (IRQ)
An exception caused by a signal from outside the core, normally from a peripheral. IRQ = Interrupt ReQuest. Every interrupt is an exception; not every exception is an interrupt.
ISR / handler
Interrupt Service Routine: the C function that runs when the exception is taken, for example USART1_IRQHandler(). It takes no arguments and returns nothing.
Exception number
The index of an exception in the vector table. 1 = Reset, 2 = NMI, 3 = HardFault, …, 15 = SysTick, 16 and up = peripheral interrupts.
IRQn
The number CMSIS (Arm's standard C header layer) uses for an interrupt: IRQn = exception number − 16. USART1 is IRQn 37, so its exception number is 53. System exceptions get negative IRQn values (SysTick = −1).
Vector table
Array of handler addresses in memory. Word 0 is special: the initial stack pointer. Word N (N ≥ 1) is the address of the handler for exception N, with bit 0 set to 1 (the "Thumb bit", explained in card 03).
NVIC
Nested Vectored Interrupt Controller. Holds enable, pending, active and priority state for every interrupt and decides what runs.
Pending
"Requested but not started yet". One bit per interrupt. It is a latch, not a counter: two requests while pending = one handler run.
Active
"Its handler has started and not yet returned". It stays active even while a more urgent handler has interrupted it.
Priority
An 8-bit number per interrupt. Lower number = more urgent. The STM32F4 implements only the top 4 bits, so there are 16 levels (0 to 15), stored as 0x00, 0x10, … 0xF0.
Preemption
A more urgent interrupt stopping a less urgent handler in the middle. The interrupted handler resumes later.
Nesting
Several handlers interrupted inside each other at the same time, like function calls stacked up. Each level costs stack space.
Stacking / stack frame
On entry the hardware pushes 8 registers (32 bytes) to the stack: R0, R1, R2, R3, R12, LR, PC, xPSR. That group of 8 words is the exception stack frame. Popping it back on exit is unstacking.
R0–R12, LR, PC, xPSR
The core's registers. R0–R12 are general-purpose. LR (Link Register, R14) holds a return address. PC (Program Counter, R15) holds the address of the instruction being executed. xPSR (Program Status Register) holds the condition flags, the Thumb bit and the current exception number.
MSP / PSP
Main Stack Pointer and Process Stack Pointer: the core has two stack pointer registers. Handlers always use MSP. An RTOS (Real-Time Operating System) gives each task its own stack through PSP.
Thread / Handler mode
Thread mode = running normal code (main, RTOS tasks). Handler mode = running an exception handler. The core switches automatically.
EXC_RETURN
A magic value (such as 0xFFFF_FFF9) the hardware puts into LR on exception entry. When the handler "returns" to that address, the core recognises it and performs the exception return.
Masking
Temporarily blocking interrupts. PRIMASK = 1 blocks all configurable ones; BASEPRI = x blocks only those with priority number ≥ x. A masked interrupt stays pending and runs later.
Latency
Time from the event (flag set) to the first instruction of the handler. 12 cycles on a Cortex-M4 at best; more if something is masking or a more urgent handler is running.
Tail-chaining
A shortcut: if another interrupt is waiting when a handler finishes, the core goes straight to it without popping and re-pushing the frame. 6 cycles instead of about 22.
Fault
An exception raised because something went wrong: bad memory address, undefined instruction, divide by zero (if enabled). HardFault is the catch-all fault handler.

STEP 4One interrupt, end to end, with real numbers

Let's follow one byte, the letter 'A' (0x41), arriving on USART1 of an STM32F407 running at 168 MHz. The main loop is busy computing something. We will see every register and address that changes.

4a. Setting it up (done once in main)

RCC->APB2ENR |= RCC_APB2ENR_USART1EN;   // 1. give USART1 its clock
USART1->BRR   = 0x2D9;                   // 2. 115200 baud from the 84 MHz APB2 clock
USART1->CR1   = USART_CR1_UE | USART_CR1_RE | USART_CR1_RXNEIE; // 3. enable UART, receiver, RX interrupt
NVIC_SetPriority(USART1_IRQn, 2);        // 4. priority 2 (fairly urgent)
NVIC_ClearPendingIRQ(USART1_IRQn);       // 5. forget any old request
NVIC_EnableIRQ(USART1_IRQn);             // 6. open the NVIC gate

4b. The byte arrives: what happens, cycle by cycle

Assume the main loop is executing an instruction at address 0x0800_0528, the next one is at 0x0800_052A, and SP (which is MSP, since we are in main with no RTOS) is 0x2001_FFE8.

t = 0 · The UART finishes receiving the stop bitIt copies 0x41 into its data register DR and sets SR.RXNE = 1. Because RXNEIE = 1, the IRQ37 line goes high.
t = 0 · The NVIC latches the requestISER1 bit 5 is 1, so the NVIC sets the pending bit ISPR1 bit 5 = 1. It compares priority 2 with the current execution priority. main() is Thread mode, which has no exception priority at all ("lower than everything"), PRIMASK = 0 and BASEPRI = 0, so the interrupt wins.
t = 0…11 · Stacking and vector fetch (12 cycles)The core pushes 8 words onto the MSP. In parallel, over a separate bus, it reads the vector table entry for exception 16 + 37 = 53 at 0x0800_0000 + 4 × 53 = 0x0800_00D4. That word contains 0x0800_0F31: the address of USART1_IRQHandler (0x0800_0F30) with bit 0 set to mark Thumb code.
t = 12 · Handler startsThe core sets PC = 0x0800_0F30, SP = 0x2001_FFC8, LR = 0xFFFF_FFF9 (EXC_RETURN meaning "return to Thread mode, use MSP, basic frame"), IPSR = 53 (the exception number field of xPSR). The NVIC clears pending and sets active (IABR1 bit 5 = 1). 12 cycles at 168 MHz = 71 ns after the byte landed.
t = 12…41 · Handler body (about 30 cycles)It reads DR (that read clears RXNE, so the request line drops), stores the byte in a ring buffer, and returns.
t = 42…51 · Unstacking (about 10 cycles)The handler's final BX LR branches to 0xFFFF_FFF9. The core sees the magic pattern, pops the 8 words back into R0–R3, R12, LR, PC, xPSR, clears the active bit, and SP returns to 0x2001_FFE8.
t = 52 · main() continuesat 0x0800_052A with every register exactly as before. It has no idea it was interrupted, except that 52 cycles (0.31 µs) of wall-clock time have passed.

Why these 8 registers and not all 16? Because of the C calling convention (the AAPCS, Arm Architecture Procedure Call Standard): any C function is allowed to overwrite R0–R3, R12 and LR, and must preserve R4–R11 itself. By saving exactly the "may be overwritten" set, the hardware lets the handler be an ordinary C function. If the handler uses R4–R11, the compiler saves them in the handler's own prologue.

4d. The timeline as a picture

4e. Now add a second interrupt (nesting)

Suppose TIM2 (a timer, IRQn 28) has priority 6 and its handler is running when the byte arrives. The NVIC compares USART1's priority 2 against the current execution priority 6. 2 is a smaller number, so it is more urgent, and USART1 preempts TIM2: the core pushes a second 32-byte frame (now 64 bytes of frames on MSP), runs USART1_IRQHandler, unstacks, and TIM2 continues where it stopped. The LR inside USART1's handler is now 0xFFFF_FFF1, meaning "return to Handler mode", because it returns into another handler, not into main.

If instead USART1 also had priority 6, it would not preempt (equal priority never preempts). It would stay pending until TIM2 finished, and then the core would tail-chain into it in 6 cycles, without popping and re-pushing the frame. USART1's latency would be "the rest of TIM2's handler + 6 cycles".

Five beginner misconceptions to drop now

  1. "Priority 15 is the most urgent." No. On Arm, lower number = more urgent; 0 is the most urgent configurable level.
  2. "If the interrupt fires twice, the handler runs twice." Not necessarily. The pending bit is a single latch; two requests before the handler starts give one run.
  3. "volatile makes shared variables safe." It stops the compiler caching the value, but count++ is still three instructions and can be torn by an interrupt.
  4. "Disabling interrupts loses them." No. Masking only delays them; they stay pending and run when unmasked.
  5. "The CPU finds main() by itself." No. It reads the reset vector from the table; the startup code calls main().
Say it like this: "An interrupt is a hardware request that makes the Cortex-M core stop its current code, save eight caller-saved registers to the stack, fetch the handler address from the vector table at VTOR + 4 × exception number, and run the handler in Handler mode, all in 12 cycles on an M4. The NVIC decides which request wins using priorities where a lower number is more urgent, and only a strictly more urgent group priority can preempt. The handler should do the minimum and clear its flag, and on return the hardware either unstacks or tail-chains straight into the next pending interrupt."

Polling vs interrupts: what problem an interrupt solves

▶
1. What is it?

There are two ways for software to find out that hardware needs attention. Polling means the CPU keeps reading a status flag in a loop until it changes. Interrupts mean the peripheral raises a request line, and the hardware itself stops the current code, runs a handler function, and then resumes the stopped code. Interrupts exist so the CPU can do useful work (or sleep) instead of watching flags, and still react within a fraction of a microsecond.

2. How does each one work, step by step?
Polling a UART byte
  1. The CPU reads USART2->SR (the Status Register).
  2. It tests bit 5, RXNE ("Receive data register Not Empty").
  3. If it is 0, it jumps back to step 1. This repeats millions of times per second.
  4. When it is 1, the CPU reads USART2->DR (the Data Register) and continues.
Interrupt-driven UART byte
  1. main() does other work or sleeps with WFI (Wait For Interrupt).
  2. The byte lands; RXNE = 1; because RXNEIE = 1 the IRQ line goes high.
  3. The NVIC accepts it; the core saves 8 registers and jumps to USART2_IRQHandler (12 cycles).
  4. The handler reads DR, stores the byte, returns; main resumes.
3. Worked example: what does each cost?

STM32F407 at 168 MHz, UART at 115200 baud: one byte every 10 / 115200 = 86.8 µs = 14 583 cycles.

Interrupt cost per byte ≈ 12 (entry) + 30 (handler) + 10 (exit) = 52 cycles CPU share = 52 / 14 583 = 0.36 % Polling share = 100 % while waiting (or late if the loop goes off doing other work)

Now the opposite case: an SPI bus at 21 Mbit/s delivers a byte every 8 bits / 21 MHz = 0.38 µs = 64 cycles. An interrupt per byte costs ~52 of those 64 cycles: 81 % of the CPU is overhead. Here interrupts are the wrong tool; use DMA (Direct Memory Access, a hardware engine that copies data without the CPU) or a tight polling loop.

5. When is polling the right answer, and what goes wrong if you choose badly?
  • The event rate is so high that entry/exit overhead dominates (the SPI example above). Use DMA, or poll in a tight loop.
  • Very short waits during init, such as waiting for RCC_CR_HSERDY (the external crystal is stable). Always add a timeout: if the crystal is missing, an unbounded loop hangs the board forever with no error.
  • Hard real-time loops built as a fixed-rate cyclic executive (common in automotive), where jitter matters more than latency.
  • Bootloaders and fault handlers, where interrupts may be disabled or untrustworthy.

Wrong choice symptoms: polling a rare event drains the battery (the CPU never sleeps; you measure ~40 mA instead of µA). Interrupting on a very fast event starves main (a scope on a GPIO toggled in main shows long gaps). A polling superloop that grows over time silently increases response latency until a UART overrun error (ORE) appears.

Hybrid patterns are common: an interrupt signals the first byte and the handler polls the rest of a burst, or an interrupt only sets a flag that the main loop polls.

6. Say it like this
Say it like this: "Interrupts are better for rare or asynchronous events and for low power, because the core can sleep and still respond in about 12 cycles. Polling or DMA is better when events are so frequent that the roughly 50 cycles of per-event overhead dominate, and for fixed-rate deterministic loops. Interrupts also carry a concurrency cost: shared data, atomicity and priority design."

The journey of one interrupt: pin → peripheral → NVIC → core

▶
1. What is it?

An interrupt is not one switch; it is a chain of hardware stages, and each stage has its own enable. If any one stage is closed, the interrupt silently never happens. Knowing the chain is how you debug "my interrupt doesn't fire".

Peripheral event
(RXNE=1)→Peripheral IRQ line

vs execution priority→Stacking 8 words

2. How does it work, step by step? (the gates)
  1. Clock gate (RCC). RCC = Reset and Clock Control. Every STM32 peripheral starts with its clock off to save power. Until you set its bit in an RCC_xxxENR register, writes to its registers are silently dropped and reads return 0.
  2. Pin gate (GPIO alternate function). For a UART, the RX pin must be switched to the UART's alternate function (for USART2 on PA3: MODER = 10, AFR[0] = 7). Otherwise the bytes never reach the peripheral.
  3. Peripheral gate. The peripheral's own interrupt-enable bit, for example USART_CR1_RXNEIE or TIM_DIER_UIE. The status flag can be 1 while the request line stays low.
  4. NVIC gate. NVIC_EnableIRQ(USART2_IRQn) sets one bit in NVIC_ISER1 (USART2 is IRQ38: register 38/32 = 1, bit 38 mod 32 = 6).
  5. Core gate (priority and masks). PRIMASK, BASEPRI and FAULTMASK must allow the interrupt's priority, and the current execution priority must be numerically higher (less urgent) than the interrupt's.
  6. Name gate (the vector table). The handler name must exactly match the weak symbol in startup_stm32f407xx.s: USART2_IRQHandler. Then the linker puts your function's address in the vector table entry.

5. What goes wrong if…
  • …the clock is off: you write CR1 = 0x202C and read back 0x0000. Nothing fires. Symptom: registers in the debugger all show 0.
  • …RXNEIE is 0: SR.RXNE goes to 1 (you can see it), but ISPR stays 0.
  • …ISER is not set: the NVIC ignores the line. With some peripherals the pending bit still sets, so ISPR = 1 and IABR = 0 forever.
  • …the name is wrong: the first byte sends the CPU into Default_Handler's infinite loop. Halting shows the PC inside Default_Handler and IPSR = 54 (USART2's exception number). The rest of the system freezes, including the watchdog kick.
6. Say it like this
Say it like this: "When an interrupt never fires I walk the chain in order: the RCC clock, the GPIO alternate function, the peripheral's interrupt-enable bit, the NVIC ISER bit, the priority against PRIMASK and BASEPRI, the handler symbol in the map file, and finally that VTOR points at the table I think it does. Reading ISPR tells me which half of the chain is broken."

The Cortex-M exception model: numbers, system exceptions vs IRQs

▶
1. What is it?

In Arm terminology, everything that diverts the core to a handler is an exception. An interrupt (IRQ) is one kind of exception: one raised by a signal from outside the core. Every exception has a fixed exception number, which is also its index in the vector table. Knowing the numbering lets you compute any handler address and read crash dumps.

2. How does the numbering work, step by step?
  1. Numbers 1–15 are system exceptions, defined by Arm and identical on every Cortex-M3/M4 chip.
  2. Numbers 16 and up are external interrupts, defined by the chip vendor (ST). On the STM32F407 there are 82: exception 16 (IRQ0, WWDG window watchdog) to exception 97 (IRQ81, FPU).
  3. The vector address of exception N is VTOR + 4 × N, because each entry is one 32-bit word.
  4. CMSIS (Cortex Microcontroller Software Interface Standard) numbers interrupts as IRQn = N − 16, so the first vendor interrupt is IRQn 0 and system exceptions have negative IRQn values.
  5. The core records which exception is running in IPSR (Interrupt Program Status Register, the low 9 bits of xPSR). IPSR = 0 means Thread mode.

Pending vs active, level vs edge

▶
1. What is it?

The NVIC tracks every interrupt with two bits: pending ("it has been requested and is waiting") and active ("its handler has started and not finished"). Separately, a request line can behave as level (stays high until the cause is cleared) or pulse/edge (a short blip that is remembered once). These two ideas explain lost events, double runs and interrupt storms.

2. How does it work, step by step?
INACTIVE
request →
PENDING
ISPR=1
taken →
ACTIVE
IABR=1
request again →
ACTIVE + PENDING
  1. The request arrives: the NVIC sets the pending bit (readable in NVIC_ISPR, Interrupt Set-Pending Register).
  2. When its priority wins, the core takes it: hardware clears pending and sets active (readable in NVIC_IABR, Interrupt Active Bit Register).
  3. If the same source requests again while the handler runs, pending is set again: state ACTIVE + PENDING.
  4. When the handler returns, active is cleared. If pending is set, the handler runs again immediately (by tail-chain).
  5. An exception can never preempt itself (it would need a priority higher than its own), so the same ISR is never nested inside itself on Cortex-M.

The pending bit is a single latch, not a counter. Three requests while pending give one handler run.

3. Worked example: three requests, one run
t=10   TIM2 request    → pending=1                      (event #1)
t=10–21 stacking       → t=22 handler starts: pending=0, active=1
t=25   TIM2 request    → pending=1 (ACTIVE+PENDING)       (event #2, remembered)
t=30   TIM2 request    → pending already 1 → nothing changes (event #3 LOST)
t=52   handler returns → tail-chain, runs once more for #2
Result: 3 events, 2 handler runs.

That is why you never count events by counting ISR entries. Count in hardware: the UART FIFO level, a DMA transfer counter (NDTR), or a timer in external-clock mode.

4. Level vs pulse at the NVIC

The NVIC samples the IRQ line. If the line is still high when the handler returns, it pends the interrupt again. That is level-sensitive behaviour, and almost all STM32 peripheral interrupts work like this: the line stays high as long as the status flag (RXNE, UIF, TC…) and its enable are 1. So the handler must clear the cause. A pulse is latched into pending once, and does not need to be cleared at the source to stop re-entry.

  • …you forget to clear a level source: the CPU spends 100 % of its time entering and leaving the ISR. Symptom: main stops, the watchdog resets the chip, a GPIO toggled in the ISR shows a continuous square wave.
  • …you count edges in software at high rate: your count is lower than reality whenever two edges arrive before the handler starts.

ISR design rules (and why each exists)

▶
1. What is it?

An ISR (Interrupt Service Routine) runs at a moment the rest of your program did not choose, and while it runs it blocks every interrupt of equal or lower priority and every task. These rules keep ISRs from damaging the timing and data of the rest of the system. Each rule has a concrete failure behind it.

2. The rules, step by step
  1. Keep it short and bounded. While an ISR runs, everything at its priority level and below is blocked, so its run time is added directly to their latency. Target a few µs.
  2. Defer the work. In the ISR: grab the data, clear the flag, signal. Do the processing in a task or the main loop through a flag, a ring buffer, or xTaskNotifyFromISR/queue. This is the "top half / bottom half" split.
  3. No blocking. No HAL_Delay() (it waits on SysTick, which may be lower priority, so it never returns). No waiting on a mutex. No printf (slow and not reentrant). No malloc (not reentrant, unbounded time).
  4. Variables shared with main are volatile so the compiler re-reads them every time. Make them atomic as well: volatile alone does not stop torn reads or lost updates (card 13).
  5. Clear the interrupt flag early, not as the last instruction, or follow the clear with __DSB() or a read-back (explained in step 3 below).
  6. Check which source fired in shared vectors. EXTI9_5_IRQHandler serves lines 5–9, and USART has RXNE, TXE, TC, ORE and IDLE on a single vector.
  7. Handle the error flags too. USART ORE (OverRun Error) keeps the IRQ asserted when RXNEIE=1. If it is not cleared (read SR then DR), the result is a storm.
  8. Don't use floating point unless you need to on the M4F. The first FP instruction triggers the lazy save of 18 more words (card 11).
3. Worked example: why "clear last" runs the ISR twice
  1. The handler's last C statement is TIM6->SR = ~TIM_SR_UIF;. The CPU issues the store and immediately executes BX LR.
  2. The store sits in the core's write buffer, then crosses the AHB→APB1 bridge. APB1 runs at 42 MHz, a quarter of the 168 MHz core, so the write needs several core cycles to reach TIM6.
  3. Meanwhile the exception-return logic samples the TIM6 request line. UIF is still 1, so the line is still high.
  4. The NVIC re-pends TIM6. The handler runs a second time, finds UIF = 0, and does nothing useful (or worse, counts a tick twice).

Measured symptom: 20 000 ISR entries per second for 10 000 timer events. Only at -O2, because -O0's slower epilogue gives the write time to land.

NVIC registers at register level

▶
1. What is it?

The NVIC is controlled through memory-mapped registers: special addresses where a load or store talks to the hardware instead of RAM. They live in the System Control Space (SCS, 0xE000_E000–0xE000_EFFF), and the addresses are the same on every Cortex-M3/M4/M7, whichever vendor made the chip. CMSIS functions like NVIC_EnableIRQ are thin wrappers that write these registers.

2. How does addressing work, step by step?
  1. Each enable/pending/active register is 32 bits wide and covers 32 interrupts. There are up to 8 of each (0–7), covering 256 IRQs.
  2. For IRQ n: register index = n >> 5 (n divided by 32) and bit = n & 31 (n mod 32).
  3. Priority registers are different: one byte per IRQ, at 0xE000_E400 + n.
  4. System exceptions (SysTick, PendSV, SVCall, faults) have their priorities in the SCB (System Control Block) SHPR registers, not in the NVIC IPR.

5. Why set/clear pairs, and what goes wrong if you use read-modify-write?

Enable and pending state can be changed from several contexts. Priority bits, PRIGROUP, preemption vs sub-priority

▶
1. What is it?

Every interrupt has an 8-bit priority field. A lower number means more urgent. Vendors implement only the top N bits of it (the STM32F4 has N = 4, so 16 levels stored as 0x00, 0x10 … 0xF0). The field can further be split by PRIGROUP into a group (preemption) priority, which decides who can interrupt whom, and a sub-priority, which only decides the order of waiting interrupts.

2. How does it work, step by step?
  1. You choose a logical priority, e.g. 5. CMSIS shifts it into the implemented MSBs: 5 << (8 − 4) = 0x50.
  2. AIRCR.PRIGROUP (bits 10:8) places a "binary point". Bits [7 : PRIGROUP+1] are the group priority, bits [PRIGROUP : 0] are the sub-priority.
  3. When something is pending, the NVIC asks: is its group strictly lower (numerically) than the group of what is running? If yes, preempt. If equal or higher, wait.
  4. When several are waiting with the same group, the lowest sub-priority goes first; if those are equal too, the lowest exception number goes first.

Why MSBs? Software written for 8 bits still orders correctly on a chip with fewer bits, because dropping low bits preserves order. The cost: you must shift, and forgetting gives priority 0.

Masking: PRIMASK, BASEPRI, FAULTMASK

▶
1. What is it?

Masking means temporarily raising the core's "current priority" so that some or all interrupts must wait. It is how you build a critical section: a short piece of code that must not be interrupted, for example while updating data shared with an ISR. Cortex-M has three mask registers with different reach.

2. How does each mask work, step by step?

  2. A pending exception is taken only if its group priority is strictly more urgent than that.
  3. Masked exceptions stay pending. When the mask drops, the most urgent one is taken immediately. Nothing is lost (apart from the "pending is not a counter" effect).

  • …critical sections are long: they add directly to worst-case latency. A 200 µs flash-write inside __disable_irq() loses UART bytes (overrun) at 115200 baud, because two bytes arrive in that window.
  • …you use BASEPRI on a Cortex-M0: it doesn't exist; the code won't assemble. M0 only has PRIMASK.
  • …you think cpsid i blocks everything: NMI and HardFault still run. On the M7 r0p1, erratum 837070 means raising BASEPRI may not take effect for one instruction, so FreeRTOS wraps it in cpsid i / cpsie i on that core.
6. Say it like this
Say it like this: "PRIMASK blocks all configurable interrupts, leaving NMI and HardFault; BASEPRI blocks only those at or below a threshold, which is how an RTOS keeps its fastest ISRs at zero added latency; FAULTMASK also blocks HardFault. Masking only delays: the pending bits stay set. I always save and restore the previous mask so nested critical sections are safe, and keep them a few instructions long."

Exception entry: stacking, vector fetch, EXC_RETURN

▶
1. What is it?

"Exception entry" is the fixed sequence the hardware performs between "the NVIC decided to take this exception" and "the first instruction of the handler". It saves just enough state that the handler can be a normal C function and the interrupted code can later resume as if nothing happened. On the Cortex-M3/M4 it takes 12 cycles with zero-wait-state memory.

2. How does it work, step by step?
  1. Stacking: pushes 8 words onto the current stack (MSP, or PSP if Thread mode was using PSP). This is the AAPCS caller-saved set, so the handler can be a plain C function.
  2. Vector fetch: reads the handler address from VTOR + 4×exc#. It goes over the I-Code bus while stacking uses the D-Code/System bus, which is why the two overlap in time.
  3. Updates SP, sets IPSR to the exception number, and loads LR = EXC_RETURN. Switches to Handler mode and MSP.
  4. Starts executing at the fetched address (with bit 0 removed; bit 0 = 1 only means "Thumb").
  5. On return, the handler executes BX LR. Because LR holds a magic 0xFFFF_FFxx value, the core performs unstacking instead of a normal branch.

3. Worked example: alignment padding

The AAPCS requires SP to be 8-byte aligned at function calls. With CCR.STKALIGN = 1 (reset default on the M4) the hardware keeps that promise for handlers:

The stacked PC is the return address. For an interrupt, it is the next instruction to execute. For a precise fault, it is the address of the faulting instruction, which is what makes post-mortem debugging possible (card 19).

Latency, tail-chaining, late arrival, pop pre-emption

▶
1. What is it?

Interrupt latency is the time from the hardware event to the first instruction of its handler. Cortex-M has a fixed best case (12 cycles on M3/M4) plus three hardware optimisations that avoid wasted pushes and pops when interrupts arrive close together: tail-chaining, late arrival and pop pre-emption.

CoreEntry latency (0 WS)Notes
Cortex-M016 cyclesv6-M, no BASEPRI
Cortex-M0+15 cycles
Cortex-M3 / M412 cyclesExit ≈ 10 cycles; tail-chain 6 cycles
Cortex-M712 cycles (typ.)Cache and TCM placement matter a lot
2. How does each optimisation work, step by step?

Tail-chaining

  1. Handler A finishes (BX LR). Interrupt B is already pending with enough priority.
  2. Normal path would be: pop 8 words (10 cycles), then push the same 8 words again (12 cycles). The values would be identical, since they are the interrupted code's registers.
  3. So the core skips both and only fetches B's vector: 6 cycles instead of ~22.

Late arrival

  1. Low-priority A has been accepted; the core is mid-stacking.
  2. Higher-priority B arrives. The frame being pushed is the same whichever handler runs.
  3. The core keeps stacking but switches the vector fetch to B. B runs first; A stays pending and runs afterwards by tail-chain.

Pop pre-emption

  1. The core is unstacking after the last handler.
  2. A new interrupt arrives. The frame is still in memory.
  3. The core abandons the pop and tail-chains into the new handler.

B: stack 12 + body 20 + unstack 10  B: tail-chain 6 + body 20 + unstack 10
total = 104 cycles                  total = 88 cycles

  • Flash wait states: STM32F4 at 168 MHz needs 5 WS. The ART accelerator hides most, but not on a cold miss.

  • Bus contention: DMA on the same bus matrix slave, or stacking to slow memory.
  • Masking: the longest PRIMASK/BASEPRI critical section, plus the longest equal-or-higher-priority ISR.
  • Sleep: waking from STOP mode needs regulator and clock restart (µs to tens of µs).
  • Peripheral synchronisation: an EXTI edge passes through synchronisers, and APB clocks may be divided.

FPU context: 26-word frames and lazy stacking

▶
1. What is it?

The Cortex-M4F has a floating-point unit (FPU) with its own registers S0–S31 and a status register FPSCR. If interrupted code was using floating point, those registers must be saved too, otherwise a handler that uses float would corrupt them. The hardware handles this with an extended frame of 26 words (104 bytes) and an optimisation called lazy stacking that only saves the FP registers if the handler actually needs them.

2. How does it work, step by step?
  1. When code executes any FP instruction, the core sets CONTROL.FPCA = 1 ("FP Context Active").
  2. On exception entry, if FPCA = 1, the frame is extended: the 8 basic words + S0–S15 + FPSCR + 1 reserved word = 26 words.
  3. With lazy stacking (FPCCR.LSPEN = 1, the reset default together with ASPEN = 1), the hardware only reserves the 104 B, records the slot address in FPCAR (0xE000_EF38) and sets FPCCR.LSPACT. Latency stays 12 cycles.
  4. If the handler executes an FP instruction, the core first stalls and writes S0–S15/FPSCR into the reserved slot (about 17 extra cycles).
  5. If the handler never uses the FPU, the registers are never written, and the reserved space is simply dropped on return.
  6. EXC_RETURN bit 4 = 0 tells the return logic which frame type to pop.
3. Worked example: stack cost of FP nesting
basic frame = 8 words × 4 = 32 B extended frame = 26 words × 4 = 104 B (+4 alignment pad worst case = 108 B) 3 nested levels, no FP : 3 × 32 = 96 B of frames on MSP 3 nested levels, FP : 3 × 108 = 324 B of frames on MSP difference = 228 B → size MSP for the FP case

Registers involved: CPACR 0xE000_ED88 (Coprocessor Access Control; CP10/CP11 = 0b11 enables the FPU; without it the first FP instruction raises a NOCP UsageFault), FPCCR 0xE000_EF34 (ASPEN[31], LSPEN[30], LSPACT[0]).

5. What goes wrong if…
  • …stacks are sized for 32-byte frames but one task uses float: a printf("%f") makes that task FP-active, every interrupt into it costs 104 B instead of 32 B, and the task stack overflows only under interrupt load. Symptom: rare HardFault with STKERR/MSTKERR.
  • …the FPU is not enabled before startup code using -mfloat-abi=hard: immediate UsageFault NOCP (CFSR bit 19) before main.
  • …a "fast" ISR calls a library function that uses float: a surprise 17-cycle lazy-save stall appears in its latency.
6. Say it like this
Say it like this: "If the interrupted code has an active FP context, the M4F's frame grows from 8 to 26 words, 104 bytes. Lazy stacking only reserves that space and records it in FPCAR, so entry stays 12 cycles, and the FP registers are written only if the handler executes an FP instruction. The cost is stack space per nesting level, and an RTOS context switch checks EXC_RETURN bit 4 to also save S16 to S31."

EXTI on STM32F4: GPIO edges into the NVIC

▶
1. What is it?

GPIO pins don't connect to the NVIC directly. On STM32 they go through the EXTI (EXTernal Interrupt/event controller), which detects rising and/or falling edges on 23 "lines" (on the F407) and turns them into NVIC requests. Lines 0–15 are GPIO; 16 = PVD (voltage detector), 17 = RTC alarm, 18 = USB OTG FS wakeup, 19 = Ethernet wakeup, 20 = USB OTG HS wakeup, 21 = RTC tamper/timestamp, 22 = RTC wakeup.

2. How does it work, step by step?
  1. Pick the port for the line. SYSCFG_EXTICRx (SYSCFG at 0x4001_3800, needs RCC_APB2ENR.SYSCFGEN) selects which port's pin n drives line n. Only one port per line: PA0 and PB0 cannot both be interrupts.
  2. Choose edges. EXTI_RTSR/FTSR: rising/falling trigger select (both can be set).
  3. Unmask. EXTI_IMR bit = 1 enables the interrupt. EXTI_EMR is the event mask (wakes WFE without an ISR). EXTI_SWIER triggers by software.
  4. Edge detected → EXTI_PR bit = 1. PR (Pending Register) is rc_w1: clear it by writing 1.
  5. NVIC request. While PR = 1 the NVIC line stays high, so seen from the NVIC it behaves like a level source until you clear PR.
  6. Vectors. EXTI0…EXTI4 each have their own (IRQ 6–10). EXTI9_5 (IRQ 23) and EXTI15_10 (IRQ 40) are shared, so the handler must test PR bits.
3. Worked example: user button on PC13, falling edge
line 13 → EXTICR4 (lines 12..15), field bits [7:4] for line 13
port C code = 0b0010           → SYSCFG->EXTICR[3] = (EXTICR[3] & ~0x00F0) | (2 << 4)
FTSR bit 13 = 1, IMR bit 13 = 1 → mask value 1 << 13 = 0x2000
vector: EXTI15_10_IRQn = 40, exception 56, offset 0xE0

  • …the input floats with both edges enabled: noise and mains pickup toggle it at kHz–MHz rates: an interrupt storm that starves the main loop and the watchdog kick (Scenario 06).   • …a mechanical switch is not debounced: one press produces 10–100 edges in a few ms.

Say it like this: "On STM32 a GPIO interrupt goes through EXTI: SYSCFG_EXTICR chooses which port drives line n, so PA0 and PB0 can't both interrupt; RTSR and FTSR pick edges, IMR unmasks, and the PR bit holds the NVIC line high until I clear it by writing 1, never with |=. Lines 5–9 and 10–15 share vectors, so the handler checks PR. Floating inputs and switch bounce cause storms, so I use pulls and debounce."

Shared data, atomicity, critical sections

▶
1. What is it?

An ISR can run between any two instructions of the main code. If both touch the same variable, an update can be lost or a value read half-old, half-new ("torn"). An operation is atomic if it cannot be split by an interrupt. A critical section is code during which interrupts are masked so a non-atomic sequence becomes effectively atomic.

2. How does the race happen, step by step?
// counter++;  with counter shared with an ISR, compiles to:
ldr  r3, [r2]      // ← ISR fires here and also does counter++
adds r3, #1
str  r3, [r2]      // ← writes back the stale value + 1: the ISR's increment is LOST
  1. main loads counter = 41 into R3.
  2. The interrupt fires. Hardware saves R3 (= 41) in the stack frame.
  3. The ISR loads 41, adds 1, stores 42, returns. R3 is restored to 41.
  4. main adds 1 → 42 and stores 42. Two increments happened; the value rose by one.
3. What is atomic on Cortex-M4 (worked through)
  • Atomic: aligned 8-, 16- and 32-bit single loads or stores (LDR/STR/LDRH/LDRB). One instruction, one bus transaction.
  • Not atomic: any read-modify-write, 64-bit (uint64_t, double) accesses (two transactions; LDRD/LDM can be interrupted and restarted), bitfields, unaligned accesses, struct copies.
uint64_t t = 0x0000_0001_FFFF_FFFF; ISR changes it to 0x0000_0002_0000_0000 main reads low word first: 0xFFFF_FFFF (old) ISR runs and writes both halves main reads high word next : 0x0000_0002 (new) main sees 0x0000_0002_FFFF_FFFF → 4 294 967 295 too large
4. Tools, from cheapest to strongest, with code
  1. Design it away: single-writer data. A SPSC (single-producer single-consumer) ring buffer where the ISR writes only head and main writes only tail needs no locks.
  2. Hardware atomic registers: GPIO BSRR, NVIC ISER/ICER, and bit-banding (M3/M4: alias 0x2200_0000 for SRAM and 0x4200_0000 for peripherals; a single-bit RMW becomes one store).
  3. LDREX/STREX (C11 atomic_fetch_add): the exclusive monitor is cleared on every exception entry and exit, so if an ISR intervened, STREX fails and the loop retries. Never masks interrupts. Not on M0/M0+.
  4. Read-twice loops for counters an ISR increments.
  5. Critical section: BASEPRI if only certain ISRs share the data, PRIMASK otherwise. Keep it to a few instructions.
#include <stdatomic.h>
static atomic_uint events;
void EXTI0_IRQHandler(void) { EXTI->PR = 1u; atomic_fetch_add_explicit(&events, 1, memory_order_relaxed); }
// compiles to: 1: ldrex r3,[r2]; adds r3,#1; strex r1,r3,[r2]; cmp r1,#0; bne 1b

Say it like this: "An ISR can run between any two instructions, so a read-modify-write like count++ or a 64-bit read can be torn. Reentrancy, interrupt storms, and priority inversion through ISRs

▶
1. What is it?

Three ways interrupts break a system that looks correct in a single-threaded mental model: a function is entered a second time before the first call finishes (reentrancy), an interrupt fires so often the CPU does nothing else (storm), or less urgent work delays more urgent work (priority inversion).

2. Reentrancy, step by step

A function is reentrant if it can be interrupted midway, called again from the interrupting context, and both calls still produce correct results.

  1. main calls log_msg("boot"); it writes into a static buffer and is halfway through.
  2. An ISR calls log_msg("ovf"); it overwrites the same static buffer and returns.
  3. main resumes and prints "bovf" or garbage.

Rules: no unprotected static/global mutable state, no pointers to static buffers returned, only reentrant callees. Offenders: strtok, rand, newlib printf/malloc without _reent/locks, errno, a HAL handle whose State field is changed from both main and an ISR.

NOT REENTRANT
char *fmt_hex(uint32_t v) {
    static char s[11];          // shared!
    sprintf(s, "0x%08lX", v);
    return s;
}
REENTRANT
void fmt_hex(uint32_t v, char s[11]) {
    static const char h[] = "0123456789ABCDEF";
    s[0]='0'; s[1]='x';
    for (int i = 0; i < 8; i++) s[2+i] = h[(v >> (28-4*i)) & 0xF];
    s[10] = 0;                  // caller owns the buffer
}
3. Interrupt storms, with numbers

A storm is an interrupt that keeps firing faster than it can be handled. Worked example: a floating pin triggering EXTI at 200 kHz.

period = 168 MHz / 200 kHz = 840 cycles per event: 12 entry + 40 handler + 10 exit = 62 cycles (7 % … fine) at 3 MHz noise: period = 56 cycles < 62 cycles → CPU never leaves Handler mode → main starves, watchdog not kicked, no sleep, battery drains

Causes: an uncleared level source (USART ORE, I2C BERR, or the wrong flag cleared); a floating or noisy EXTI input or switch bounce; a flag cleared too late (one spurious re-entry per event); a timer with ARR = 0. Detect by counting ISR entries per second in telemetry, toggling a GPIO in the ISR and scoping it, or reading ICSR.VECTACTIVE when you halt. Mitigate with rate limiting (disable the source after N events per window, re-arm from a timer), hardware filtering, and always handling every enabled flag.

4. Priority inversion via ISRs
  1. Long low-urgency ISRs at high NVIC priority. A "debug UART" ISR at priority 0 that formats strings delays the motor-control loop. NVIC priority should follow deadline urgency (rate-monotonic or deadline-monotonic: shorter deadline = higher priority), not "importance".
  2. Any interrupt beats every task. Even the lowest-priority ISR preempts the highest-priority RTOS task, so heavy ISR processing inverts the task priority design. Deferral to a task fixes it.
  3. Shared resource locked by low-priority code. A task holding a long PRIMASK critical section delays a high-priority ISR for its whole length. ISRs must never wait on a mutex.
Response-time analysis (fixed priority):
R_i = C_i + B_i + Σ_{j ∈ hp(i)} ⌈R_i / T_j⌉ · C_j
Example: CAN ISR C=8 µs, blocking B=3 µs, higher prio TIM1 C=4 µs every T=50 µs
R0 = 8+3 = 11 → R1 = 11 + ⌈11/50⌉·4 = 15 → R2 = 11 + ⌈15/50⌉·4 = 15  converged: 15 µs
5. What goes wrong if…
  • …a shared logging function is called from main and an ISR: interleaved, corrupted log lines; occasionally a HardFault if a pointer in the static state was half-updated.
  • …you only lengthen the watchdog during a storm: the reset stops but the battery still drains and real events are delayed.
6. Say it like this
Say it like this: "Reentrant means a function can be interrupted and called again with both calls correct, so no unprotected static state. A storm is an interrupt firing faster than it can be serviced, usually an uncleared level flag or a floating EXTI input; I detect it by counting entries per second and guard against it by rate limiting. Priority should follow deadlines, not importance, because any ISR beats every task; I verify with response-time analysis."

Nested interrupt stack usage (bare metal and RTOS)

▶
1. What is it?

Every time an interrupt preempts another, the core pushes another frame on the MSP, and the handler then uses more stack for its own locals and calls. If you don't size the main stack for the worst-case nesting, it silently overflows into other RAM, and you get random corruption or a fault only under heavy interrupt load.

2. How does the stack grow, step by step?
MSP_worst = Σ over each preemption level L   ( frame_L + max_handler_stack_L )
frame = 32 B (basic) | 104 B (+4 pad) when FP context active
levels ≤ number of distinct GROUP priorities actually in use (≤ 2^preempt_bits)
  1. main runs with its own stack usage on MSP.
  2. IRQ at group 8 arrives: +32 B frame, + its handler's stack.
  3. IRQ at group 4 preempts it: +32 B, + its handler's stack.
  4. …each strictly more urgent group can add one more level. Equal groups never nest.
3. Worked example
F4, no FP, 4 group levels used, worst handler stack 96 B each: 4 × (32 + 96) = 512 B on top of main's own stack same with FP active: 4 × (108 + 96) = 816 B same 4 IRQs placed in ONE group (sub-priorities only): max nesting 1 → 128 B

PRIGROUP is a stack-sizing tool: fewer preemption levels, fewer frames.

4. Under an RTOS (PSP for tasks, MSP for ISRs)
Task A stack (PSP)            Main stack (MSP)
┌──────────────┐              ┌──────────────┐
│ task locals  │              │ ISR2 locals  │ ← nested ISR
│ ...          │              │ frame #2 32B │
│ frame #1 32B │ ← first IRQ  │ ISR1 locals  │

  • When an interrupt preempts a task, the first frame is pushed on that task's PSP, because stacking uses the current stack. The handler then runs on MSP; nested frames go on MSP.
  • So every task stack needs room for one exception frame (32 or 104 B) and nothing more for interrupts; the MSP must hold all nesting. On FreeRTOS/STM32 the MSP is reset to _estack when the scheduler starts, reclaiming main()'s stack.
  • A stack overflow during stacking gives MSTKERR/STKERR (and with no room even for the fault frame, lockup).

Vector table relocation (VTOR)

▶
1. What is it?

SCB->VTOR (Vector Table Offset Register, 0xE000_ED08) holds the base address of the vector table. It resets to 0 on the M3/M4; the STM32 BOOT pins alias flash, system ROM or SRAM at address 0. Changing VTOR lets a different table take over, which you need for: (1) a bootloader + application, where the app's table lives at its own flash offset, e.g. 0x0800_8000; (2) a RAM vector table, to install handlers at run time; (3) A/B firmware slots.

2. How does it work, step by step? (bootloader → app jump)
  1. Disable interrupts (__disable_irq()).
  2. Stop SysTick (SysTick->CTRL = 0) and every peripheral the bootloader started.
  3. Disable and clear all NVIC interrupts: write 0xFFFF_FFFF to every ICER and ICPR.
  4. Set SCB->VTOR = 0x0800_8000, then __DSB(); __ISB();.
  5. Load the app's MSP from its word 0: __set_MSP(*(uint32_t*)0x08008000).
  6. Branch to the app's reset handler from its word 1.
  7. Re-enable interrupts in the app once it has configured them.
3. Worked example: alignment

On Armv7-M the base must be aligned to the table size rounded up to a power of two, and to at least 128 bytes.

STM32F407 table = 98 vectors × 4 B = 392 B next power of two ≥ 392 = 512 = 0x200 → VTOR must be a multiple of 0x200 0x0800_8000 / 0x200 = 0x4_0040 (no remainder) ✔ aligned 0x0800_8100 / 0x200 = 0x4_0040.8 ✖ low bits not implemented → reads back as 0x0800_8000: the core uses the WRONG table

5. What goes wrong if…
  • …the app never sets VTOR: its interrupts run the bootloader's handlers. Classic symptom: HAL_Delay() hangs forever because the bootloader's SysTick handler increments the bootloader's tick variable, not the app's (Scenario 09).
  • …the bootloader leaves SysTick running: the first SysTick fires before the app has set VTOR or its stack, often a HardFault right after the jump.
  • …VTOR points at erased flash: HFSR.VECTTBL on the first exception.

Cortex-M0 has no VTOR: copy the app's table to the start of SRAM and remap SRAM to address 0 (STM32F0: SYSCFG_CFGR1.MEM_MODE = 0b11). The M0+ has an optional VTOR.

Say it like this: "VTOR holds the vector table base; I relocate it for bootloader plus application, RAM tables or A/B slots. SVC and PendSV: how an RTOS uses exceptions

▶
1. What is it?

Two system exceptions exist mainly for operating systems. SVCall (exception 11) is raised synchronously by the instruction SVC #imm8: it is a deliberate "call into the kernel", used for system calls from unprivileged tasks and to start the first task. PendSV (exception 14) is raised by software setting a pending bit and runs asynchronously when priorities allow; RTOSes put it at the lowest priority and perform the context switch (swapping one task's registers and stack for another's) inside it.

2. How does each work, step by step?

SVC

  1. Task code executes svc #0. The exception is taken immediately (it cannot stay pending).
  2. Hardware stacks R0–R3, R12, LR, PC, xPSR on the task's PSP. Arguments the task put in R0–R3 are now in the frame.
  3. The handler finds the SVC number by reading the instruction itself: the stacked PC points just after the 2-byte SVC opcode, whose low byte is the immediate: ((uint8_t *)stacked_pc)[-2].
  4. To return a value, the handler writes it into the stacked R0 (frame[0]); unstacking loads it into the task's R0.

PendSV context switch

  1. SysTick (or any ISR that wakes a higher-priority task) decides a switch is needed and just writes SCB->ICSR = SCB_ICSR_PENDSVSET_Msk (bit 28).
  2. Because PendSV is lowest (0xF0), it runs only after every other active ISR finishes, by tail-chain.
  3. PendSV saves R4–R11 of the current task onto its PSP, stores the PSP in the task's TCB (Task Control Block), asks the scheduler for the next task, loads that task's PSP and R4–R11.
  4. BX LR with EXC_RETURN 0xFFFF_FFFD unstacks the new task's hardware frame from the new PSP: the new task resumes.
3. Worked example: why lowest priority matters
t0  Task A running
t1  UART ISR (prio 6) running; SysTick, wrongly configured at prio 5, preempts it
t2  SysTick decides "switch to task B" and switches right here:
    returns to Task B ... but UART ISR's frame is still on the MSP, half-done.
    → "return to Thread mode with an exception still active" → INVPC / corrupted state
With PendSV at 15: SysTick only pends PendSV; UART ISR finishes; THEN PendSV runs once.
Five ISRs that each request a switch → still exactly one context switch.

Fault exceptions: MemManage, BusFault, UsageFault, HardFault escalation

▶
1. What is it?

A fault is an exception the core raises when an instruction cannot complete correctly: an access to a bad address, an undefined opcode, an illegal state. Cortex-M3/M4 has three specific fault classes (MemManage, BusFault, UsageFault) plus the catch-all HardFault. Status registers record exactly what went wrong, so a fault is a debugging gift if you read them.

2. How does escalation work, step by step?
  1. An instruction faults, e.g. a load from an unclocked peripheral → BusFault condition.
  2. Is BusFault enabled (SHCSR.BUSFAULTENA, bit 17)? At reset all three are disabled.
  3. If disabled, or its priority can't preempt the current execution priority (fault inside a higher-priority ISR, or masked by PRIMASK/BASEPRI): escalate to HardFault and set HFSR.FORCED = 1. Synchronous faults can't wait.
  4. Either way, the specific cause is recorded in CFSR (Configurable Fault Status Register); for some faults the address is recorded in BFAR/MMFAR.
  5. If the fault happens inside the HardFault handler itself → lockup.

Don't hunt at that PC; set DISDEFWBUF and reproduce.

Lockup: a fault while executing the HardFault or NMI handler, or during HardFault stacking, has nowhere to escalate. The core stops and drives the LOCKUP signal. The STM32 does not reset itself; the watchdog or debugger must recover it.

Writing a HardFault handler that finds the faulting PC

▶
1. What is it?

A default HardFault handler is an infinite loop that tells you nothing. A useful one reads the stacked frame the hardware pushed (which contains the PC of the faulting instruction and the LR of its caller) plus the fault status registers, saves them somewhere that survives a reset, and reboots. That turns "the unit rebooted in the field" into "line 214 of cmd.c".

2. How does it work, step by step?
  1. On fault entry, LR = EXC_RETURN. Bit 2 says where the frame is: 0 = MSP, 1 = PSP.
  2. This must be read in assembly before any C prologue pushes registers or changes SP/LR, hence a naked function (no compiler-generated prologue).
  3. Pass the frame address (R0) and EXC_RETURN (R1) to a C function.
  4. Copy PC, LR, xPSR, CFSR, HFSR and BFAR/MMFAR (if valid) into a .noinit RAM struct that startup code doesn't zero.
  5. If a debugger is attached, breakpoint; otherwise reset. On the next boot, report the record and clear its magic.
  6. Map the PC to source with addr2line.
3. Code, line by line
__attribute__((naked)) void HardFault_Handler(void)
{
    __asm volatile(
        "tst   lr, #4          \n"   // EXC_RETURN bit 2: which SP was in use?
        "ite   eq              \n"
        "mrseq r0, msp         \n"   // r0 = &frame (arg 1)
        "mrsne r0, psp         \n"
        "mov   r1, lr          \n"   // r1 = EXC_RETURN (arg 2)
        "b     hardfault_c     \n");
}

    NVIC_SystemReset();                     // next boot: report g_crash, then clear magic
}

Beyond Cortex-M: the Arm GIC (Cortex-A/R) and RISC-V PLIC/CLIC

▶
1. What is it?

The NVIC is specific to Cortex-M microcontrollers. Application processors (Cortex-A, as in phones and SoCs) use the GIC (Generic Interrupt Controller), and RISC-V chips use the PLIC (Platform-Level Interrupt Controller) or the newer CLIC (Core-Local Interrupt Controller). Big-tech SoC interviews often ask you to contrast them: the core idea is "how much does hardware do for you".

2. How does a GIC interrupt work, step by step?
  1. A peripheral raises SPI (Shared Peripheral Interrupt) 75. The Distributor (global: enable, priority, target CPU, edge/level) routes it to CPU 2.
  2. CPU 2's CPU interface (GICv3: Redistributor + ICC_*_EL1 system registers) signals IRQ to the core if its priority beats the PMR (priority mask, like BASEPRI).
  3. The core takes the single IRQ exception at VBAR_ELx + offset. No hardware stacking, no per-IRQ vector: software saves registers.
  4. Software reads IAR (Interrupt Acknowledge Register) → returns 75 and marks it active.
  5. Software calls handler[75] from a table, then writes 75 to EOIR (End Of Interrupt). Forgetting EOI blocks that priority level forever.
  6. Nesting is opt-in: the handler must re-enable IRQs itself. Latency is hundreds of cycles and non-deterministic (caches, MMU, OS).

IDs: SGI 0–15 (software-generated, inter-processor), PPI 16–31 (per-core private: generic timer, PMU), SPI 32–1019, 1020–1023 special (1023 = spurious), GICv3 LPIs ≥ 8192 (message-based via the ITS). BPR (Binary Point Register) splits group from sub-priority like PRIGROUP.

3. RISC-V, step by step
  • Base privileged spec: three causes per hart (hardware thread): software (MSI), timer (MTI), external (MEI), with mie/mip enable/pending CSRs. mtvec is direct (one handler) or vectored (base + 4×cause). mcause bit XLEN−1 = interrupt. Return with mret.
  • On a trap, mstatus.MIE is copied to MPIE and cleared: no nesting unless software re-enables it. No hardware register stacking: GCC's __attribute__((interrupt)) generates a prologue saving every caller-saved register it uses (up to 16 on RV32I).
  • CLINT/ACLINT: machine timer (mtime/mtimecmp) and software interrupts.
  • PLIC: many sources → MEI. Per-source priority (0 = never interrupt, higher number = more urgent, the opposite of Arm), per-context threshold, and claim/complete (read = claim the highest pending ID, write the ID back = complete). Very GIC-like, no hardware preemption.
  • CLIC (Smclic; check ratification status and your vendor's version): per-interrupt level/priority, hardware preemption by level, selective hardware vectoring, mintthresh. Closest to the NVIC. Vendor variants: Nuclei ECLIC, Espressif CLIC (ESP32-C6/P4), WCH PFIC (WCH's "HPE" adds hardware stacking).
  • Application-class RISC-V uses AIA (APLIC + IMSIC, MSI-based).

  • …you forget EOIR / complete: that interrupt (and on GIC, everything at or below its priority) never fires again. Symptom: device works for one event, then goes silent.

6. Say it like this
Say it like this: "The NVIC is tightly coupled to one core and does hardware stacking, per-IRQ vectoring, implicit acknowledge and hardware nesting, so latency is 12 deterministic cycles. The RISC-V PLIC is similar with claim and complete and higher-number-is-more-urgent, while the CLIC adds NVIC-like hardware preemption."

Sleep and interrupts: WFI, sleep-on-exit, and the lost-wakeup race

▶
1. What is it?

WFI (Wait For Interrupt) stops the core clock until an interrupt needs service, cutting power from tens of mA to a few mA (Sleep mode) or µA (Stop mode with SLEEPDEEP). The danger is the lost-wakeup race: if you check "is there work?" and then sleep, an interrupt arriving between the check and the WFI leaves you asleep with work waiting.

2. How does it work, step by step?
  1. WFI sleeps until an interrupt would be taken or is pending, even while PRIMASK masks it. This detail is what makes the fix work.
  2. With PRIMASK = 1, the core wakes but doesn't run the ISR yet; the next instruction after WFI executes.
  3. When you clear PRIMASK, the pending ISR runs immediately.
  4. Sleep-on-exit (SCB->SCR |= SCB_SCR_SLEEPONEXIT_Msk): when the last ISR returns to Thread mode, the core goes back to sleep without unstacking. The next interrupt then needs no stacking, because the frame is still there.
  5. SEVONPEND (SCR bit 4) lets even disabled interrupts wake a WFE (Wait For Event).
3. Worked example: the race on a timeline
main:  ldrb r0,[g_flag]  → 0 ("no work")
              ← EXTI ISR runs here, sets g_flag = 1, returns
main:  WFI                → sleeps. g_flag is 1 but nobody looks.
       ... next interrupt might be in 10 minutes → button press ignored for 10 min
4. Code, line by line
BROKEN
/* ISR can set the flag between the check and WFI */
while (!g_flag) { __WFI(); }
CORRECT
for (;;) {
    __disable_irq();
    if (!g_flag) __WFI();     // still wakes on the pending IRQ despite PRIMASK=1
    __enable_irq();           // ISR runs here
    if (g_flag) { g_flag = 0; process(); }
}
CodeMeaning
__disable_irq()From now on no ISR can run, so g_flag can't change behind our back.
if (!g_flag) __WFI()Check and sleep form one uninterruptible decision. If the IRQ became pending after the check, WFI returns immediately.
__enable_irq()The pending ISR runs here and sets g_flag.
if (g_flag) …Now handle the work in Thread mode.
5. What goes wrong if…
  • …you use the broken loop: rare, timing-dependent "missed button press" or "late packet" bugs that disappear with a debugger attached (the debugger often keeps the core clock running).
  • …you use sleep-on-exit with work in main: main never runs again after the first interrupt; it suits fully interrupt-driven designs only.
  • …SLEEPDEEP is set: wake-up takes µs (regulator, PLL restart) and the system clock falls back to HSI; reconfigure clocks after waking from Stop.
6. Say it like this
Say it like this: "The race is checking the flag, then an interrupt sets it, then WFI sleeps with work pending. The fix is to disable interrupts with PRIMASK, check the flag, execute WFI, then re-enable; it works because WFI wakes on a pending interrupt even when PRIMASK masks it, and the ISR runs as soon as I unmask. WFE with the event register is another race-free option, and sleep-on-exit suits fully interrupt-driven designs."

60-SECOND REVISION

Model. Everything is an exception. IRQn = exc# − 16. Reset −3, NMI −2 and HardFault −1 are fixed. Everything else is configurable 0–255, with only the top N bits implemented (F4: 4). A lower value is more urgent.

Priority. PRIGROUP splits group from sub-priority. Only the group decides preemption, and it must be strictly higher. Sub-priority and then the IRQ number only order the pending queue.

States. Inactive → pending → active → active+pending. The pending bit is a latch, not a counter. Taking the exception clears pending and sets active.

Entry. 12 cycles: 8 words (26 with FP) pushed to the current SP while the vector is fetched in parallel. LR = EXC_RETURN. The stacked PC is the faulting instruction for precise faults.

Optimisations. Tail-chain (6 cycles, no unstack/restack). Late arrival (switch vector during stacking). Pop pre-emption (abandon unstack). Lazy FP stacking (reserve space, save only on use).

Masking. PRIMASK = all configurable. BASEPRI = threshold, the RTOS critical section. FAULTMASK = also HardFault. Masking delays, it does not drop.

ISR rules. Short; defer work; clear the flag early (or DSB); volatile + atomic shared data; no blocking or printf/malloc; FromISR APIs only at or below the syscall priority.

Faults. Enable SHCSR 16–18. HFSR.FORCED → read CFSR. BFAR/MMFAR only if VALID. EXC_RETURN bit 2 selects MSP/PSP; frame[6] = PC. IMPRECISERR → DISDEFWBUF. A fault inside HardFault → lockup.

RTOS. SVC = synchronous system call / first task. PendSV = lowest priority, context switch after all ISRs. The task PSP holds the first frame, and MSP holds the nesting.

Elsewhere. GIC: IAR/EOIR, SGI/PPI/SPI, software save. RISC-V PLIC: claim/complete, high = urgent. CLIC: NVIC-like preemption.
