How to Ace the Live C Coding Round

The process at Apple, Google, Qualcomm and NVIDIA, the talk-aloud method demonstrated on one full problem as a word-for-word transcript, the C edge-case checklist, the style interviewers reward, how to test code by hand, and how to spend your 45 minutes. Click any card to open it.

BEGINNER

1. What the C coding round actually is (and how it is graded)

▶

1. What is it?

The coding round is a 45 to 60 minute session where an engineer gives you a small, self-contained programming problem and watches you solve it live, usually in a shared text editor (CoderPad, a Google Doc, an internal tool) or on a whiteboard. For embedded and firmware roles the language is almost always C, sometimes C++ "written like C". The interviewer is not only checking whether your final code works; they are watching how you think, because that is what they will see every day if they hire you.

A key point people miss: in many of these rounds there is no compiler. Google phone screens are commonly done in a plain shared document; whiteboard onsites obviously have no compiler; even CoderPad sessions often have "run" disabled or the interviewer asks you to reason before running. That means you must be able to run your code in your head (the "Trace & Predict" tab trains exactly this).

Processes change and differ by team, so treat this as the commonly reported shape, not a contract:

3. How you are graded (the four axes)

  1. Problem solving: did you clarify ambiguity, find a correct approach, and know its trade-offs? Jumping straight to typing is a negative signal.
  2. Coding: is the C correct, idiomatic, readable, free of undefined behaviour (UB = code the C standard gives no meaning to, so the compiler may do anything)? Do you handle edge cases?
  3. Verification: did you test your own code by tracing it with concrete inputs, and find your own bugs before the interviewer does?
  4. Communication: could the interviewer follow your reasoning the whole time? Did you take hints well?

Worked example of how this plays out: two candidates both produce a working ring buffer. Candidate A typed silently for 25 minutes and said "done". Candidate B asked whether it is single-producer/single-consumer and whether an ISR is involved, chose a power-of-two size so the index wraps with a mask, explained why one slot is wasted, traced a full/empty sequence by hand, and caught an off-by-one herself. B gets "strong hire"; A gets "lean no hire" despite identical final code, because the interviewer has no evidence of how A reasons.

You solve it silently and fast: the interviewer cannot write positive evidence in the feedback form, and any bug you leave looks like carelessness instead of a slip you would have caught. Silence is the most common reason good coders fail this round.
"I'm going to talk through my thinking as I go. First I'd like to clarify the inputs and the expected behaviour on bad input, then I'll walk an example by hand, propose an approach with its complexity, code it, and test it by tracing a few cases including the edge cases."

2. The talk-aloud method: Clarify → Examples → Approach → Code → Test → Complexity

▶

1. What is it?

A fixed six-step routine you run for every problem, so that under stress you never skip the steps that interviewers grade. It works because each step produces visible evidence on the feedback form.

  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────┐   ┌──────┐   ┌────────────┐
  │ CLARIFY  │──▶│ EXAMPLES │──▶│ APPROACH │──▶│ CODE │──▶│ TEST │──▶│ COMPLEXITY │
  │  ~3 min  │   │  ~3 min  │   │  ~6 min  │   │~15min│   │~8 min│   │  ~2 min    │
  └──────────┘   └──────────┘   └──────────┘   └──────┘   └──────┘   └────────────┘
       ▲                                                      │
       └──────────── bug found? go back, fix, re-test ────────┘

2. Each step, in order

  1. Clarify. Restate the problem in your own words. Ask about: input types and sizes (int or uint32_t? max length?), who owns memory (does the caller allocate the output buffer?), what to do on bad input (NULL pointer, empty string, overflow), whether it runs in an ISR or multiple threads, and whether there are memory/time limits (embedded: "no malloc", "8 KB RAM"). Write the agreed function signature down first.
  2. Examples. Write 2–3 small concrete inputs with expected outputs, including one edge case. This exposes misunderstandings before you write code, and these same examples become your tests later.
  3. Approach. Say the brute-force idea and its cost in one sentence, then the better idea. Explain it on the example ("I keep two indices; on this input they move like this..."). Get a nod from the interviewer before coding. If you are stuck, say what you are considering out loud; interviewers give hints only to candidates who show where they are.
  4. Code. Write clean C: meaningful names, const on inputs, fixed-width types for hardware data, small helper functions. Narrate the why of non-obvious lines ("I compare before multiplying so this can't overflow").
  5. Test. Trace your code line by line with your examples, writing variable values in a small table (see card 5). Then run the edge-case checklist (card 4). Fix bugs calmly: "I see, when n is 0 this loop reads a[-1]; I'll guard that."
  6. Complexity. State time and extra space in Big-O (Big-O = how the cost grows as input size n grows, ignoring constants), and mention embedded-relevant constants: stack depth, whether it allocates, whether it is ISR-safe.
You skip Clarify: you implement strncpy semantics when they wanted strlcpy, or you return -1 on error when the caller can't distinguish it from a valid -1. You discover it at minute 35 and have no time to restructure.
"Let me restate: I'm writing int my_atoi(const char *s); leading spaces are skipped, an optional sign is allowed, parsing stops at the first non-digit, and on overflow I clamp to INT_MAX or INT_MIN. Is that the behaviour you want?"

3. Full worked transcript: "Implement atoi" done the right way

▶

Below is a realistic, word-for-word 40-minute session. Read it once straight through, then read only the CANDIDATE lines and notice that every phase of the method appears. Violet notes explain what the interviewer is writing down.

PHASE 1 — CLARIFY (min 0–4)
INTERVIEWER
Please implement atoi: convert a string to an integer.
CANDIDATE
Sure. Before I code, a few questions so I build the right thing. One: should I skip leading whitespace, like the standard atoi? Two: is a leading + or - allowed? Three: what if I hit a non-digit in the middle, like "12ab": stop and return 12, or report an error? Four, the important one: what should happen on overflow, say "99999999999"? The real atoi has undefined behaviour there, which I'd rather not copy.
INTERVIEWER
Skip spaces and tabs, allow one sign, stop at the first non-digit, and on overflow clamp to INT_MAX or INT_MIN. NULL input returns 0.
CANDIDATE
Great. So the signature is int my_atoi(const char *s), const because I won't modify the string. I'll assume 32-bit int, but I'll use INT_MAX from limits.h so it's portable.
NOTE
Interviewer writes: "Clarified whitespace, sign, invalid chars and overflow unprompted. Spotted that standard atoi has UB on overflow." That's two strong signals in 3 minutes.
PHASE 2 — EXAMPLES (min 4–7)
CANDIDATE
Let me write examples I'll test with later:
"42" → 42 · " -42abc" → -42 · "+7" → 7 · "" → 0 · "-" → 0 · "2147483647" → 2147483647 · "2147483648" → clamps to 2147483647 · "-2147483648" → -2147483648, which is the tricky one because +2147483648 doesn't fit in an int.
NOTE
The candidate already identified the asymmetric range of two's complement (−2³¹ … 2³¹−1). Most candidates find this bug only after the interviewer points at it.
PHASE 3 — APPROACH (min 7–12)
CANDIDATE
The core idea is the classic one: walk the digits left to right and do acc = acc*10 + digit. For "427": 0→4→42→427. The hard part is overflow. If I multiply first and check afterwards, the overflow has already happened, and signed overflow is undefined behaviour in C, so the compiler is allowed to delete my check. So I'll check before multiplying: the update is safe only if acc*10 + d ≤ limit, which rearranges to acc ≤ (limit − d)/10. That uses only subtraction and division, which can't overflow.
CANDIDATE
For the sign, I'll accumulate the magnitude in an unsigned int, whose limit is 2147483647 for positive numbers and 2147483648 for negative ones; 2147483648 fits in a 32-bit unsigned. At the end I negate. One subtle part: I can't write -(int)acc when acc is 2147483648, because converting that to int doesn't fit. So I special-case it and return INT_MIN directly.
INTERVIEWER
Why not use a long long accumulator and compare against INT_MAX?
CANDIDATE
That works for int, and I'd accept it in production. Two reasons I prefer the pre-check: it generalizes to parsing into the widest type, where there's no wider type to hide in, and on a Cortex-M0 64-bit multiply is a library call, so it's slower. It's also O(n) time, O(1) space either way.
INTERVIEWER
Fine, go ahead.
PHASE 4 — CODE (min 12–25)
CANDIDATE
I'll narrate as I type. 
#include <limits.h>   // INT_MAX, INT_MIN
#include <stddef.h>   // NULL

int my_atoi(const char *s)
{
    if (s == NULL) return 0;                   // agreed: NULL → 0

    while (*s == ' ' || *s == '\t') s++;       // 1. skip leading blanks

    int neg = 0;
    if (*s == '+' || *s == '-') {              // 2. at most one sign
        neg = (*s == '-');
        s++;
    }

    /* 3. largest magnitude we may build: 2147483647 or 2147483648 */
    unsigned limit = neg ? (unsigned)INT_MAX + 1u : (unsigned)INT_MAX;
    unsigned acc = 0;

    while (*s >= '0' && *s <= '9') {           // 4. digits only; '\0' stops it
        unsigned d = (unsigned)(*s - '0');     //    '7' - '0' == 7
        if (acc > (limit - d) / 10u)            // 5. would acc*10+d exceed limit?
            return neg ? INT_MIN : INT_MAX;       //    yes → clamp, no UB
        acc = acc * 10u + d;                    //    safe: proven ≤ limit
        s++;
    }

    if (neg)                                    // 6. apply the sign
        return (acc == limit) ? INT_MIN : -(int)acc;  // 2147483648 has no +int form
    return (int)acc;                             // acc ≤ INT_MAX here
}
NOTE
The comments are short and explain why, not what. Note '0'..'9' instead of isdigit(): isdigit(*s) with a negative char (e.g. byte 0xE9 on a signed-char platform) is undefined behaviour unless cast to unsigned char — a detail worth mentioning.
PHASE 5 — TEST BY HAND (min 25–35)
CANDIDATE
Let me trace " -42a". The while skips two spaces, s points at '-'. neg=1, s at '4'. limit=2147483648, acc=0.
*sd(limit−d)/10acc > that?acc after
'4'42147483640 > … no4
'2'22147483644 > … no42
'a'loop condition false, exit
neg, acc=42 ≠ limit, return -42. Correct.
CANDIDATE
Now the boundary "2147483648": limit = 2147483647. After nine digits acc = 214748364. Last digit d=8: (2147483647 − 8)/10 = 2147483639/10 = 214748363. Is 214748364 > 214748363? Yes, so return INT_MAX. Correct clamp.
And "-2147483648": limit = 2147483648, last digit d=8: (2147483648 − 8)/10 = 214748364. 214748364 > 214748364? No, so acc = 2147483648 = limit, return INT_MIN. Correct, and I never formed +2147483648 as an int.
CANDIDATE
Edge cases from my checklist: NULL → 0 ✓. Empty string: the blank loop sees '\0', no sign, digit loop doesn't run, returns 0 ✓. Just "-": returns -(int)0 = 0 ✓. "+-5": one sign consumed, then '-' isn't a digit → 0 ✓, matches "at most one sign". Leading zeros "0007" → 7 ✓. Also, limit - d never underflows because d ≤ 9 and limit is huge.
INTERVIEWER
What if the caller needs to know that the input was invalid or overflowed?
CANDIDATE
Then the int-only return is the wrong interface, because 0 and INT_MAX are valid results. I'd change it to bool parse_int(const char *s, int *out, const char **end): return false on no digits or overflow, write the value through out, and report where parsing stopped through end, which is what strtol does with endptr and errno = ERANGE.
PHASE 6 — COMPLEXITY & WRAP-UP (min 35–40)
CANDIDATE
Time O(n) in the string length, one pass. Space O(1): three locals, no allocation, no recursion, so it's safe to call from an ISR and it's reentrant, meaning two callers can run it at the same time because it touches no shared state. On a Cortex-M3/M4 the divide per digit is a hardware UDIV (2–12 cycles); on an M0 without a divider I'd precompute the threshold limit/10 and compare against that plus the last digit to avoid a division per character.
NOTE
Final feedback: "Strong hire. Clarified, avoided UB deliberately, tested boundaries without being asked, discussed interface design and target-specific cost."
"I accumulate the magnitude in an unsigned and check acc > (limit − d)/10 before every multiply, so the arithmetic can never overflow; the limit is INT_MAX for positive and INT_MAX+1 for negative numbers, and I return INT_MIN directly for the one value that has no positive counterpart."

4. The C edge-case checklist (run it on every solution)

▶

Before you say "done", walk this list out loud. Each item below says what it is, how it bites, and the fix.

1. NULL pointers

What: a pointer that points to nothing. Dereferencing it (reading *p) is undefined behaviour; on Cortex-M, address 0 is usually the start of Flash or the vector table, so a NULL read silently returns the initial stack pointer value instead of crashing, and a NULL write may HardFault, or do nothing.

Do: agree the contract in Clarify ("caller guarantees non-NULL" vs "return error"). If you check, check once at the top. Mention assert() for programmer errors vs error codes for runtime conditions.

2. Empty input

What: length 0 string ("", just the terminator), n == 0 arrays, an empty list (head == NULL). How it bites: loops like for (i = 0; i <= n - 1; i++) with size_t n = 0: n - 1 wraps to 4294967295 (on 32-bit) and you read past the array. Fix: write i < n, never i <= n - 1.

3. Integer overflow

What: a result that doesn't fit in the type. For unsigned types the result wraps modulo 2N (well defined). For signed types it is undefined behaviour; the optimizer may assume it never happens and delete your check.

WRONG
int mid = (lo + hi) / 2;     // lo+hi can exceed INT_MAX
if (a + b < a) { /* overflow */ }  // signed: UB, may be removed
RIGHT
int mid = lo + (hi - lo) / 2;      // never exceeds hi
if (b > 0 && a > INT_MAX - b) { /* would overflow */ }

Also: integer promotion. Arithmetic on uint8_t/uint16_t is done in int. uint16_t a = 0xFFFF; a * a is computed as int 65535×65535 = 4294836225, which overflows a 32-bit int: UB. Cast to uint32_t first.

4. Alignment

What: a 4-byte uint32_t must normally sit at an address divisible by 4. How it bites: *(uint32_t *)(buf + 1) on a byte buffer. Cortex-M3/M4 handle unaligned single LDR in hardware (slower), but LDRD/LDM fault, Cortex-M0 HardFaults on any unaligned word access, and it is UB in C regardless. Fix: memcpy(&v, buf + 1, 4) (compilers turn this into the best legal load) or assemble bytes with shifts.

5. Endianness

What: the byte order of multi-byte values in memory. 0x12345678 stored little-endian (Cortex-M, x86) is bytes 78 56 34 12 at increasing addresses; big-endian (network order) is 12 34 56 78. How it bites: casting a received byte buffer to a struct. Fix: build values with shifts, which are endian-independent: v = (uint32_t)b[0] << 24 | (uint32_t)b[1] << 16 | (uint32_t)b[2] << 8 | b[3];

6. Signedness

What: whether a type can hold negative numbers. Plain char is signed on x86 and unsigned on ARM (GCC default for ARM EABI). How it bites: char c = 0xFF; if (c == 0xFF) is false on x86 (c is −1) and true on ARM. Comparing int with unsigned converts the int to unsigned: -1 < 1u is false. Fix: use uint8_t for bytes, keep sizes in size_t, and never mix signed and unsigned in comparisons (enable -Wsign-compare).

7. Aliasing

What: two pointers that refer to the same or overlapping memory. How it bites (a): memcpy(dst, src, n) with overlapping regions is UB; use memmove. (b): the strict aliasing rule lets the compiler assume an int * and a float * never point at the same object, so type punning through casts can be "optimized" into wrong code. (c): a swap like *a ^= *b; *b ^= *a; *a ^= *b; zeroes the value when a == b. Fix: ask "can these overlap?", use restrict only when you can promise they don't, and use memcpy or a union for type punning.

8. Off-by-one

What: one iteration too many or too few, the single most common bug. Typical spots: forgetting the '\0' (allocate strlen(s) + 1), <= vs <, ring buffer full/empty, binary search bounds, "last index is n − 1". Fix: pick a convention (half-open ranges [lo, hi)), and test sizes 0, 1, 2.

9. Reentrancy and concurrency

What: a function is reentrant if it can be interrupted in the middle and called again (from an ISR or another thread) without corrupting anything. strtok is the classic non-reentrant function: it keeps its position in a hidden static variable. How it bites: a static buffer returned by itoa is overwritten when an ISR calls the same function. Fix: no hidden static state, caller-provided buffers, strtok_r-style explicit context, and for shared data between ISR and main: volatile + atomic access or a critical section.

CHECKLIST SAY-ALOUD ORDER
 N  NULL         – what if a pointer is NULL?
 E  Empty        – n = 0, "", head == NULL
 O  Overflow     – sums, products, n-1 on size_t, INT_MIN
 A  Alignment    – any cast of byte buffers to wider types?
 E  Endianness   – any multi-byte value crossing a wire/file?
 S  Signedness   – char, mixed int/unsigned compares, >> on negatives
 A  Aliasing     – can src and dst overlap? a == b?
 O  Off-by-one   – sizes 0, 1, 2, exact boundary
 R  Reentrancy   – static state? ISR or thread calling in?
"Let me run my checklist: NULL is handled by contract, empty input returns 0 without touching memory, the index math can't overflow because I use lo + (hi − lo)/2, there are no casts so alignment and endianness don't apply, I use size_t consistently, the buffers can't overlap because the caller passes distinct ones, I tested sizes 0, 1 and 2, and there's no static state, so it's reentrant."

5. Testing your code by hand (the trace-table method)

▶

1. What is it?

Without a compiler, the only way to prove your code works is to execute it yourself, on paper, like a CPU. Do it with a trace table: one column per variable, one row per loop iteration or important line. Interviewers love seeing this because it is exactly how you debug firmware on a target with no printf.

2. Step by step

  1. Pick the smallest interesting input (2–4 elements). Big inputs waste time; tiny ones reveal off-by-ones.
  2. Draw columns for every variable that changes, plus the loop condition.
  3. Read your code as written, not as you meant it. Put your finger on the line. Evaluate the condition with the current values.
  4. Write the new values in the next row. Draw memory (arrays, list nodes) as boxes and update arrows when pointers change.
  5. When the function returns, compare with the expected output from your Examples step.
  6. Then run 2–3 edge inputs (empty, single element, boundary value) more quickly, focusing on loop entry/exit.

3. Worked example: reverse an array in place

void reverse(int *a, size_t n) {
    if (n < 2) return;               // 0 or 1 element: nothing to do
    size_t i = 0, j = n - 1;          // safe: n ≥ 2 so no wrap
    while (i < j) {                   // stop when the indices meet/cross
        int t = a[i]; a[i] = a[j]; a[j] = t;
        i++; j--;
    }
}

Input a = {1,2,3,4}, n = 4:

rowiji<jarray after swap
start03yes{4,2,3,1}
212yes{4,3,2,1}
321no → exit{4,3,2,1} ✓

Edge inputs: n = 0 → returns at the guard. Without the guard, j = n - 1 wraps to SIZE_MAX and i < j is true, so you would swap a[0] with a[SIZE_MAX]: a wild memory write. n = 1 → guard. n = 3 {1,2,3}: swap 0↔2, then i = j = 1, loop exits, middle untouched ✓.

You test only the "happy path" example you designed the algorithm on. It always works, by construction. The bugs live at n = 0, n = 1, the exact overflow boundary, and the last loop iteration.
"Let me trace it with a four-element array. I'll keep a table of i, j and the array... Now the edge cases: with n equal to 0 the guard returns before computing n − 1, which matters because n is a size_t and would wrap."

▶

Style is not decoration: readable code is easier for you to trace and debug in the remaining minutes, and interviewers explicitly score "would I accept this in code review?".

7. Time management for a 45-minute round

▶

Most rounds are 45 minutes of which ~5 are introductions and ~5 are your questions at the end, so you really have about 35 minutes of problem time, sometimes for two problems (a warm-up and a main one).

min  0 ─┬─ intros (don't ramble: 60-second "about me")
     5 ─┼─ CLARIFY + EXAMPLES ............ ~5 min
    10 ─┼─ APPROACH (brute force → better) ~5 min   ◀ get agreement here
    15 ─┼─ CODE .......................... ~12–15 min
    30 ─┼─ TEST by trace + edge cases .... ~6–8 min
    37 ─┼─ COMPLEXITY + follow-up ......... ~3 min
    40 ─┴─ your questions for them
  1. Checkpoint at minute 15: if you have no approach yet, say the brute force and code it. A working O(n²) beats an unfinished O(n).
  2. Checkpoint at minute 30: if code isn't finished, stub the remaining helper with a clear comment (// TODO: handle wrap-around; same as head update) and move to testing what you have. Interviewers prefer tested partial code to untested complete code.
  3. When stuck for more than 2 minutes: say exactly where: "I have the pointer update but I'm unsure how to detect the end when the list has a cycle." This invites a hint, and taking a hint well is a positive signal.
  4. Two-problem rounds: the first one is a warm-up (strlen, count bits). Do it in 8–10 minutes, still with a quick test, and don't over-engineer it.

Use the 45-min mock in the Problem Arena to rehearse exactly this pacing; the timer turns red at 5 minutes left.

"I have a working O(n²) version in mind; given the time, let me code that first, and then I'll explain how a hash or two-pointer approach brings it to O(n) if we have time left."

8. Embedded-specific signals that separate you from algorithm-only candidates

▶

Firmware teams ask the same "implement a ring buffer" question to everyone. What distinguishes candidates is volunteering the embedded constraints unprompted:

  1. No dynamic allocation: "On the MCU I'd use a static array sized at compile time; malloc can fragment and its timing isn't deterministic." Then offer a pool allocator if needed.
  2. ISR safety: "If the producer is the UART RX interrupt and the consumer is the main loop, a single-producer single-consumer ring buffer needs no lock as long as each index is written by only one side and the index updates are atomic, which a 32-bit aligned store is on Cortex-M. I'd mark the indices volatile, or better use C11 atomics, and on a multi-core or out-of-order system add a memory barrier between writing the data and publishing the index."
  3. Determinism and WCET: worst-case execution time matters more than average. A hash table with O(1) average but O(n) worst case may be rejected for a control loop.
  4. Cost on the actual core: "Cortex-M0 has no divide instruction, so % size is a library call of dozens of cycles; with a power-of-two size I use & (size − 1), a single-cycle AND."
  5. Hardware data: fixed-width types, explicit endianness, alignment, volatile for registers, and never bit-fields for register layouts (their bit order is implementation-defined).
  6. Stack depth: recursion is usually banned (MISRA C Rule 17.2); say "I'll do it iteratively so the stack use is bounded."
"Since this runs on a microcontroller, I'll avoid malloc and recursion, size the buffer as a power of two so wrap-around is a single AND, and make it single-producer single-consumer so the UART ISR can push without disabling interrupts."

EDGE-CASE CHECKLIST (SAY IT ALOUD: "NEOAESAOR")
  • NULL pointers: contract agreed? checked once at the top?
  • Empty: n = 0, "", head == NULL. No n − 1 on size_t.
  • Overflow: sums, products, lo + hi, INT_MIN negation, shift ≥ width.
  • Alignment: any (uint32_t *) cast of a byte buffer? use memcpy/shifts.
  • Endianness: multi-byte values crossing a wire/file/Flash: explicit byte order.
  • Signedness: plain char, int vs unsigned compares, >> of negatives, ctype casts.
  • Aliasing: can src and dst overlap? a == b in swap? strict aliasing casts?
  • Off-by-one: terminator (+1), < vs <=, full vs empty, sizes 0/1/2.
  • Reentrancy: static state? ISR/thread callers? shared variables volatile + atomic?

10 MOST-ASKED EMBEDDED C CODING PROBLEMS
  1. memmove with overlap — direction choice by address comparison.
  2. Ring buffer (ISR producer) — power-of-2, one writer per index, no shared count.
  3. atoi / itoa — pre-multiply overflow check; INT_MIN via unsigned magnitude.
  4. Reverse a linked list — save next before flipping; return prev.
  5. Count / reverse bits, power of two — x & (x−1), mask-swap, RBIT.
  6. Set/clear a register field — mask without 32-bit shift UB, RMW races.
  7. Endian swap / read_be32 — shifts, never pointer casts.
  8. CRC-16/32 — shift/XOR loop, table variant, check value.
  9. Memory pool / aligned malloc — free list in blocks; stash the raw pointer.
  10. Debounce / software timer / state machine — periodic sampling, wrap-safe ticks, table FSM.
NEVER DO THIS IN THE ROUND
  • Start typing before clarifying inputs, errors and constraints.
  • Check overflow after a signed operation.
  • Return a pointer to a local array, or use a hidden static buffer.
  • Use sizeof on a pointer parameter as a buffer size.
  • strncpy without forcing a terminator; malloc(strlen(s)).
  • Cast uint8_t * buffers to wider pointer types.
  • for (unsigned i = n - 1; i >= 0; i--).
  • Read p->next after free(p).
  • Share a count variable between ISR and main.
  • Compare ticks with now >= deadline.
  • Unparenthesised macros or macros with side-effect arguments.
  • Recursion or malloc in an embedded answer without saying why it's OK.
  • Say "done" without tracing a test case and the edge cases.

60-SECOND REVISION

Run the method out loud: clarify → examples → approach → code → test → complexity. Agree the signature and error behaviour first. Say brute force, then the better idea, and get a nod. In C, the bugs live at the boundaries: terminators, n = 0, INT_MIN, size_t wrap, overlap, promotion, signed overflow. Avoid UB deliberately and say so: pre-check overflow, cast before shifting, use unsigned for bits, memcpy instead of type-punning casts. For embedded, volunteer constraints: no malloc (pools, static arrays), no recursion, power-of-two buffers with masks, single-writer indices for ISR sharing, volatile for hardware and ISR flags (but not as atomicity), critical sections that restore PRIMASK, wrap-safe time compares, explicit endianness. Trace your code with a table on the smallest input, then edge cases, then state time, space, stack and ISR safety. If stuck, say exactly where you are stuck.
