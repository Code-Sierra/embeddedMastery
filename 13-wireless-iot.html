dBm and decibels: the language of RF power

BEGINNER▶

1. WHAT IS IT?

Radio power spans a huge range: a transmitter puts out about a milliwatt, and the receiver at the other end may only catch a ten-billionth of that. Writing those numbers in watts is clumsy, so RF engineers use a logarithmic scale called the decibel. Every datasheet number you will read for a radio (TX power, sensitivity, RSSI, antenna gain, path loss) is in decibels, so this is the first thing to get comfortable with.

2. TERMS

dB
decibel. A ratio between two powers: dB = 10 × log10(P2 / P1). It has no unit. +3 dB means "about twice", +10 dB means "ten times", −10 dB means "one tenth".
dBm
decibels relative to 1 milliwatt. An absolute power: P(dBm) = 10 × log10(P / 1 mW). 0 dBm = 1 mW.
dBi
antenna gain relative to an ideal isotropic antenna (one that radiates equally in all directions).
TX power
transmit power, the power delivered by the radio into the antenna, in dBm.

3. HOW TO CONVERT, STEP BY STEP

  1. To go from milliwatts to dBm: divide by 1 mW, take log10, multiply by 10. 2 mW → log10(2) = 0.301 → +3.0 dBm.
  2. To go from dBm back to milliwatts: divide by 10, raise 10 to that power. −90 dBm → 10^(−9) mW = 1 picowatt.
  3. Gains and losses in dB simply add and subtract, because multiplying ratios becomes adding logarithms. That is the whole point of the scale.
  4. You may add dB to dBm (power × ratio = power). You may not add dBm to dBm: two powers are combined in milliwatts, not in logs.
A Nordic nRF52840 transmits at 0 dBm (1 mW). Its antenna has +2 dBi gain. The signal loses 80 dB travelling through the room. The phone antenna has 0 dBi.
Received power = 0 + 2 − 80 + 0 = −78 dBm = 10^(−7.8) mW ≈ 1.6 × 10⁻⁸ mW = 16 picowatts.
Two separate 0 dBm signals added together: 1 mW + 1 mW = 2 mW = +3 dBm, not "0 + 0 = 0 dBm" and not "0 dBm + 0 dBm = 0 dBm doubled to 0".

4. CODE: AVERAGING RSSI (WRONG vs RIGHT)

RSSI (Received Signal Strength Indicator) readings arrive in dBm. If you want the true mean power, you must average in linear units.

✖ WRONG — averaging logarithms
int8_t rssi_avg(const int8_t *r, int n) {
    int sum = 0;
    for (int i = 0; i < n; i++)
        sum += r[i];          // adds dBm values
    return sum / n;           // geometric mean, biased low
}
// samples -50 and -90 dBm → returns -70 dBm
✔ RIGHT — average power in mW
#include <math.h>
float rssi_avg(const int8_t *r, int n) {
    double mw = 0;
    for (int i = 0; i < n; i++)
        mw += pow(10.0, r[i] / 10.0); // dBm → mW
    return 10.0 * log10(mw / n);      // mean mW → dBm
}
// -50 and -90 dBm → 1e-5 and 1e-9 mW
// mean 5.0e-6 mW → -53.0 dBm

Note: for link-quality trending many stacks deliberately use a cheap exponential moving average of the dBm values (e.g. avg += (x - avg) / 8). That is fine as an indicator; just do not call the result "average power".

5. WHAT GOES WRONG IF…

…you add dBm to dBm. A junior adds TX power (+4 dBm) and receiver sensitivity (−95 dBm) to get "−91" and calls it a margin. The two numbers are both absolute powers; their difference (+4 − (−95) = 99 dB) is the allowed path loss. Mixing them up makes range estimates nonsense.
…you think "−100 dBm is just a bit less than −90 dBm". It is 10 times less power. Every 10 dB on a link budget is a factor of 10, so a "small" 6 dB loss from a badly placed antenna halves your range in free space.

dBm is absolute power referenced to 1 mW, and dB is a ratio, so on a link budget you start from TX power in dBm and then add gains and subtract losses in dB. Path loss and the link budget: how far will it reach?

BEGINNER▶

1. WHAT IS IT?

A link budget is a bookkeeping sheet for a radio link. You start with the power that leaves the transmitter, add every gain, subtract every loss, and see whether what reaches the receiver is still above the weakest signal the receiver can decode. The biggest loss is path loss: the signal spreads out over a growing sphere, so the power per square metre drops with distance.

2. TERMS

Pt, Pr
transmitted and received power, in dBm.
Gt, Gr
transmit and receive antenna gain, dBi.
FSPL
Free-Space Path Loss: loss with no obstacles, only spreading. FSPL(dB) = 20·log10(d_km) + 20·log10(f_MHz) + 32.44.
Sensitivity
the lowest received power at which the receiver still meets a stated error rate (BLE: 30.8 % packet error with 37-byte packets per the spec test; vendors usually quote it for 0.1 % bit error rate).
MAPL
Maximum Allowable Path Loss = Pt + Gt + Gr − cable/matching losses − sensitivity.
Fade margin
extra dB you keep in reserve for walls, bodies, multipath fading and ageing. Typically 10–20 dB indoors.
n
path-loss exponent in the log-distance model. 2 = free space, 2.7–3.5 = office/home, 4–6 = through floors and dense buildings.

3. THE CALCULATION, STEP BY STEP

  1. Write the link equation: Pr = Pt + Gt + Gr − L_misc − PL(d).
  2. Find the loss at a 1 m reference distance with FSPL. At 2440 MHz: 20·log10(0.001) = −60, 20·log10(2440) = 67.75, plus 32.44 → 40.2 dB.
  3. Extend to distance d with the log-distance model: PL(d) = PL(1 m) + 10·n·log10(d).
  4. Compute MAPL from the datasheets, subtract the fade margin, and solve for d.
nRF52840 at 0 dBm, both antennas 0 dBi, 1 dB matching loss, receiver sensitivity −95 dBm (BLE 1M PHY).
MAPL = 0 + 0 + 0 − 1 − (−95) = 94 dB. Keep 15 dB fade margin → usable path loss = 79 dB.
Free space (n = 2): 79 = 40.2 + 20·log10(d) → log10(d) = 1.94 → d ≈ 87 m.
Indoors (n = 3): 79 = 40.2 + 30·log10(d) → log10(d) = 1.293 → d ≈ 20 m.
Switch to Coded PHY S=8 (sensitivity −103 dBm, 8 dB better): 87 dB usable → indoors log10(d) = 1.56 → d ≈ 36 m. Eight decibels bought 1.8× range at n = 3 (10^(8/30) = 1.85), but costs 8× airtime.

4. CODE

/* Estimate range from a link budget (log-distance model). */
#include <math.h>
typedef struct {
    float pt_dbm;      // TX power, e.g. 0
    float gt_dbi;      // TX antenna gain
    float gr_dbi;      // RX antenna gain
    float loss_db;     // cables, matching, enclosure
    float sens_dbm;    // receiver sensitivity, e.g. -95
    float margin_db;   // fade margin, e.g. 15
    float f_mhz;       // carrier, e.g. 2440
    float n;           // path-loss exponent, 2..4
} link_t;

float fspl_1m(float f_mhz) {                 // loss at d = 1 m
    return 20.0f*log10f(0.001f) + 20.0f*log10f(f_mhz) + 32.44f;
}
float range_m(const link_t *l) {
    float mapl = l->pt_dbm + l->gt_dbi + l->gr_dbi - l->loss_db - l->sens_dbm;
    float usable = mapl - l->margin_db;      // what we may spend on distance
    float extra  = usable - fspl_1m(l->f_mhz); // beyond the 1 m point
    if (extra < 0) return 0;                  // cannot even reach 1 m
    return powf(10.0f, extra / (10.0f * l->n));
}

5. WHAT GOES WRONG IF…

…you plan with n = 2 indoors. The datasheet says "100 m range" (line of sight, free space). The product ships into homes, where n ≈ 3 and a human body adds 3–10 dB at 2.4 GHz. Field range is 15–20 m and support tickets say "keeps disconnecting".
…you forget frequency. FSPL grows with 20·log10(f). The same distance costs 9 dB more at 2440 MHz than at 868 MHz (20·log10(2440/868) = 8.98 dB). That is one reason LoRa (sub-GHz) reaches kilometres.

I start from the transmit power, add both antenna gains, subtract matching and enclosure losses, and compare with the receiver's sensitivity; the difference is the maximum allowable path loss. I keep 10 to 20 dB of fade margin and convert what is left into distance with a log-distance model, using an exponent around 3 indoors rather than the free-space 2. For example 0 dBm with −95 dBm sensitivity gives 95 dB, about 20 m indoors after margin, and the 8 dB extra sensitivity of Coded PHY roughly doubles that.

RSSI vs SNR (and RSRP/RSRQ/SINR in cellular)

BEGINNER▶

1. WHAT IS IT?

Engineers often judge a link by its signal strength, but a receiver actually needs the wanted signal to stand out from the noise and interference around it. A loud signal in a loud room can be less usable than a quiet signal in a silent room. RSSI measures loudness; SNR measures how much the signal stands out.

2. TERMS

RSSI
Received Signal Strength Indicator: the total power the receiver measures in the channel, in dBm. It includes the wanted signal plus noise plus any interference.
Noise floor
the power of random thermal noise in the receiver bandwidth: −174 dBm/Hz + 10·log10(bandwidth in Hz) + NF.
NF
Noise Figure, how much noise the receiver's own electronics add, typically 3–8 dB.
SNR
Signal-to-Noise Ratio = signal power − noise power, in dB. SINR adds interference to the denominator.
RSRP
Reference Signal Received Power (LTE): average power of one reference-signal resource element, dBm. The LTE equivalent of "how strong is the cell".
RSRQ
Reference Signal Received Quality (LTE) = N × RSRP / RSSI, in dB; drops when the cell is busy or interfered.

3. WHY STRENGTH ALONE IS NOT ENOUGH, STEP BY STEP

  1. A demodulator needs a minimum SNR to decode a given modulation: roughly 8–12 dB for BLE GFSK, about 25 dB for 64-QAM Wi-Fi, and as low as −20 dB for LoRa SF12 (it decodes below the noise thanks to spreading).
  2. Sensitivity is therefore noise floor + required SNR. For BLE 1M: −174 + 60 (1 MHz) + NF 6 = −108 dBm noise; + ~13 dB needed → ≈ −95 dBm sensitivity.
  3. Interference raises the effective floor. If Wi-Fi traffic adds −85 dBm of power into a BLE channel, the floor is now −85 dBm, and a −90 dBm BLE packet has SNR of −5 dB: lost, even though "−90 dBm RSSI" looks usable.
  4. So when debugging, log both: RSSI tells you about distance/antenna, SNR or packet error rate tells you about interference.
LoRa SX1276, 125 kHz bandwidth: noise = −174 + 10·log10(125 000) = −174 + 51 = −123 dBm, plus NF 6 → −117 dBm. SF12 decodes at SNR = −20 dB → sensitivity ≈ −137 dBm, matching the datasheet.
Cellular: AT+CSQ returns +CSQ: 18,99. RSSI index 18 → dBm = −113 + 2 × 18 = −77 dBm. Index 99 means "not known or not detectable": it must never be converted to dBm.

4. CODE: PARSING AT+CSQ (WRONG vs RIGHT)

✖ WRONG
int csq_to_dbm(const char *line) {
    int rssi, ber;
    sscanf(line, "+CSQ: %d,%d", &rssi, &ber);
    return -113 + 2 * rssi;   // 99 → +85 dBm (!)
}                             // and no check sscanf matched
✔ RIGHT
#include <stdbool.h>
bool csq_to_dbm(const char *line, int *dbm) {
    int rssi, ber;
    if (sscanf(line, "+CSQ: %d,%d", &rssi, &ber) != 2)
        return false;          // malformed / other line
    if (rssi == 99 || rssi < 0 || rssi > 31)
        return false;          // 99 = unknown
    *dbm = -113 + 2 * rssi;    // 0 → -113, 31 → -51 (or more)
    return true;
}

For LTE-M/NB-IoT, AT+CSQ is a legacy indicator; prefer the LTE metrics (Quectel: AT+QCSQ returns RSSI, RSRP, SINR and RSRQ for the serving technology).

5. WHAT GOES WRONG IF…

…you only log RSSI. Field devices in a factory show RSSI −65 dBm yet 30 % packet loss. The culprit is a nearby Wi-Fi access point or a variable-frequency drive creating interference; SNR (or packet error rate / CRC error counters) would have told you immediately.
RSSI is the total power the receiver sees in the channel, signal plus noise plus interference, so it mostly tells me about distance and antennas. What decides whether a packet decodes is SNR or SINR, the margin of the signal over the noise floor, which is minus 174 dBm per hertz plus ten log bandwidth plus the noise figure. A link with good RSSI can still fail in an interfered environment, so I log packet error rate or SINR as well; in LTE I look at RSRP for strength and RSRQ/SINR for quality.

Antennas and impedance matching for firmware engineers

INTERMEDIATE▶

1. WHAT IS IT?

The antenna turns electrical power into radio waves. To transfer the most power, the radio output, the PCB trace and the antenna must all present the same impedance, almost always 50 Ω. A small network of inductors and capacitors (the matching network) corrects the antenna's impedance after it has been detuned by the enclosure, battery and ground plane. Firmware engineers meet this when range is bad and someone asks "is it the code or the antenna?".

2. TERMS

Impedance (Z)
the AC "resistance" of a circuit, a complex number R + jX. 50 Ω means 50 + j0.
Γ (gamma)
reflection coefficient = (Z_load − Z0) / (Z_load + Z0). The fraction of voltage reflected back.
VSWR
Voltage Standing Wave Ratio = (1 + |Γ|) / (1 − |Γ|). 1:1 is perfect.
Return loss
−20·log10|Γ| dB. Bigger is better: 10 dB return loss = 10 % power reflected.
Pi network
a matching footprint shaped like π: shunt part, series part, shunt part. Layouts always include one so it can be tuned later.
VNA
Vector Network Analyser, the instrument used to measure and tune the match.

3. HOW AN ANTENNA GETS TUNED, STEP BY STEP

  1. Layout follows the antenna vendor's reference: keep-out area (no copper or ground under a chip/PCB antenna), required ground-plane length, 50 Ω controlled-impedance trace (coplanar waveguide).
  2. Build the board in its final enclosure, with the battery and cables in place; plastic, metal and even a hand shift the resonant frequency down.
  3. Connect a VNA through a pigtail at the matching network, measure S11 (reflection) across 2.40–2.48 GHz.
  4. Pick pi-network L/C values that move the impedance to 50 Ω at band centre (Smith chart work, or the vendor's tuning service).
  5. Verify radiated performance in a chamber (TRP = total radiated power, TIS = total isotropic sensitivity). Firmware supplies test modes (Nordic DTM, Direct Test Mode; constant carrier; fixed-channel TX) for this and for certification (FCC, CE RED).
VSWR 2:1 → |Γ| = (2 − 1)/(2 + 1) = 0.333 → reflected power Γ² = 0.111 = 11 %. Mismatch loss = −10·log10(1 − 0.111) = 0.51 dB. Return loss = −20·log10(0.333) = 9.5 dB.
VSWR 5:1 (badly detuned) → |Γ| = 0.667, Γ² = 0.444 → mismatch loss = 2.55 dB, on both TX and RX → 5.1 dB of link budget gone; at n = 3 that is 10^(5.1/30) → range × 0.68.
Quarter-wave monopole at 2.44 GHz: λ = c / f = 3×10⁸ / 2.44×10⁹ = 0.123 m → λ/4 = 30.7 mm in air (shorter on FR4 because of the dielectric).

4. CODE: SETTING TX POWER (WRONG vs RIGHT)

Radios accept only discrete TX power steps. On an nRF52832 the SoftDevice accepts −40, −20, −16, −12, −8, −4, 0, +3 and +4 dBm.

✖ WRONG
sd_ble_gap_tx_power_set(BLE_GAP_TX_POWER_ROLE_ADV,
                        adv_handle, 5);
// +5 dBm is not a supported step:
// returns NRF_ERROR_INVALID_PARAM, the
// return value is ignored, power stays 0 dBm
✔ RIGHT
static const int8_t steps[] = {-40,-20,-16,-12,-8,-4,0,3,4};
int8_t pick_tx(int8_t want) {          // largest step ≤ want
    int8_t best = steps[0];
    for (unsigned i = 0; i < sizeof steps; i++)
        if (steps[i] <= want) best = steps[i];
    return best;
}
uint32_t err = sd_ble_gap_tx_power_set(
    BLE_GAP_TX_POWER_ROLE_ADV, adv_handle, pick_tx(5));
APP_ERROR_CHECK(err);                   // never ignore it

5. WHAT GOES WRONG IF…

…the antenna is tuned on a bare board. Symptom: lab range 30 m, product range 8 m. The plastic housing and the coin cell detuned the antenna by 100+ MHz, so it now resonates near 2.3 GHz and the match at 2.44 GHz is poor. Fix: retune the pi network in the final mechanical build.
…firmware raises TX power to "fix" range. +8 dBm on an nRF52840 draws about 14.8 mA vs 4.8 mA at 0 dBm (DC/DC on) — 3× the radio current — and may push the product outside its certified limits. Fix the antenna first.

The radio, the trace and the antenna all need to be 50 ohms, and the enclosure, battery and hand detune the antenna, so every design has a pi matching network that is tuned with a VNA in the final mechanical build. A VSWR of 2:1 only costs about half a dB, but a detuned 5:1 antenna costs over 2.5 dB each way. As a firmware engineer I provide test modes like DTM and constant carrier for tuning and certification, and I check antenna performance before turning up TX power, which costs current.

2.4 GHz coexistence: BLE, Wi-Fi, Thread/Zigbee and microwaves

INTERMEDIATE▶

1. WHAT IS IT?

BLE, Wi-Fi, Zigbee, Thread and microwave ovens all share the same licence-free band from 2400 to 2483.5 MHz. Coexistence is the set of tricks each technology uses so they can work side by side: careful channel placement, frequency hopping that avoids busy channels, and, inside combo chips, hardware arbitration of who may transmit.

2. TERMS

ISM band
Industrial, Scientific and Medical band, usable without a licence.
BLE channels
40 channels, 2 MHz apart, from 2402 to 2480 MHz. Channels 37, 38, 39 are advertising channels; 0–36 are data channels.
AFH
Adaptive Frequency Hopping: the connection hops over data channels, skipping the ones marked bad in the channel map.
Channel map
37-bit mask of usable data channels, sent in CONNECT_IND and updated with LL_CHANNEL_MAP_IND by the central. At least 2 channels must remain enabled.
PTA
Packet Traffic Arbitration (IEEE 802.15.2): wires (REQUEST, PRIORITY, GRANT) between a Wi-Fi chip and a BLE/802.15.4 chip so they do not transmit at the same time.

3. HOW THE BAND IS SHARED, STEP BY STEP

  1. Wi-Fi in 2.4 GHz uses 20 MHz-wide channels; non-overlapping ones are 1 (2412), 6 (2437) and 11 (2462 MHz).
  2. BLE puts its three advertising channels at 2402 (ch 37), 2426 (ch 38) and 2480 MHz (ch 39): at the lower edge, in the gap between Wi-Fi 1 and 6, and above Wi-Fi 11. So discovery survives even in a busy office.
  3. After connecting, BLE hops across 37 data channels using a channel selection algorithm (CSA #1: next = (last + hop) mod 37, hop 5–16; CSA #2 from Bluetooth 5 uses a pseudo-random sequence). Channels removed from the map are remapped to good ones.
  4. 802.15.4 (Zigbee/Thread) uses 16 channels 11–26 at 2405 + 5·(k − 11) MHz, 2 MHz wide. Channels 15 (2425), 20 (2450), 25 (2475) and 26 (2480) fall between or above Wi-Fi 1/6/11 — that is why Zigbee installers prefer them.
  5. Combo chips (ESP32, many phone SoCs) have one radio; a software/hardware coexistence scheduler time-slices it between Wi-Fi and BLE. Two-chip designs wire PTA lines between the radios.
An access point sits on Wi-Fi channel 6 (occupies roughly 2427–2447 MHz).
BLE data channel frequency: index 0–10 → 2404 + 2k MHz; index 11–36 → 2428 + 2(k − 11) MHz.
2428 to 2446 MHz → indices 11 through 20 → 10 channels overlap. With AFH the central marks them bad, leaving 27 good channels. Without AFH about 10/37 = 27 % of connection events would collide with Wi-Fi bursts.

4. CODE: BLE CHANNEL INDEX → FREQUENCY (WRONG vs RIGHT)

✖ WRONG — treats index as linear
uint16_t ble_ch_mhz(uint8_t ch) {
    return 2402 + 2 * ch;   // ch 37 → 2476 (!)
}
✔ RIGHT — advertising channels are interleaved
uint16_t ble_ch_mhz(uint8_t ch) {
    if (ch == 37) return 2402;            // adv
    if (ch == 38) return 2426;            // adv
    if (ch == 39) return 2480;            // adv
    if (ch <= 10) return 2404 + 2 * ch;   // data 0..10
    return 2428 + 2 * (ch - 11);          // data 11..36
}

5. WHAT GOES WRONG IF…

…an ESP32 runs Wi-Fi scans while holding a BLE connection with a 7.5 ms interval. The single radio is away on Wi-Fi channels for tens of milliseconds per scanned channel, so BLE connection events are missed in bursts. With a tight supervision timeout the BLE link drops. Fixes: longer supervision timeout, avoid active scans while connected, raise BLE priority in the coexistence settings, or use a two-radio design.
…a Zigbee network is put on channel 13 next to Wi-Fi channel 1. Wi-Fi transmits at up to 20 dBm with wide bandwidth; Zigbee frames (+0 to +8 dBm) get trampled; mesh routes flap. Move to channel 15, 20 or 25.

Everything at 2.4 GHz shares 83.5 MHz, so BLE puts its advertising channels at 2402, 2426 and 2480, which sit at the edge and in the gaps of Wi-Fi channels 1, 6 and 11, and uses adaptive frequency hopping on the 37 data channels so the central can mark channels under a Wi-Fi AP as bad. Choosing a wireless technology (the landscape)

BEGINNER▶

1. WHAT IS IT?

No radio is best at everything. Each trades off range, data rate, power, cost (module + subscription) and infrastructure (does it need a phone, a gateway, an access point or a cell tower?). Interviewers love "which radio would you choose for X and why?" because the answer shows you understand all five.

2. TERMS

LPWAN
Low-Power Wide-Area Network: LoRaWAN, NB-IoT, LTE-M, Sigfox. Kilometres of range, small payloads, years on a battery.
PAN
Personal Area Network: BLE, Classic Bluetooth — metres, usually talks to a phone.
Mesh
devices relay each other's packets (Thread, Zigbee, BLE Mesh), extending coverage across a building.
MCL
Maximum Coupling Loss, the cellular way of stating the largest path loss a link tolerates. LTE ~144 dB, LTE-M ~156 dB, NB-IoT ~164 dB.

3. HOW TO DECIDE, STEP BY STEP

  1. Where is the other end? A phone in the user's hand → BLE. A home router → Wi-Fi or Thread via a border router. Nothing local, device in the field → cellular or LoRaWAN.
  2. How much data, how often? Audio/video or firmware images daily → Wi-Fi / LTE Cat-1. A 50-byte reading every 15 min → LPWAN.
  3. Power source? Mains → anything. Coin cell for years → BLE or 802.15.4 sleepy end device. AA cells for 10 years in a field → NB-IoT/LTE-M with PSM, or LoRaWAN.
  4. Mobility and latency? NB-IoT has no connected-mode handover and seconds of latency; LTE-M supports mobility and ~100 ms; LoRaWAN Class A can only receive right after it transmits.
  5. Cost and regulation? Cellular needs a SIM plan and certification per operator; LoRaWAN needs gateways (yours or a network's) and obeys duty-cycle limits in Europe.

…you pick NB-IoT for a vehicle tracker. NB-IoT has no handover in connected mode; at highway speed the device keeps dropping and re-establishing RRC connections, so latency and power explode. LTE-M (Cat-M1) supports mobility.

I choose a radio by asking where the other end is, how much data and how often, what the power source is, whether the device moves, and what the recurring cost is. Phone-centric and coin-cell means BLE; home automation on a mesh means Thread or Zigbee, increasingly under Matter; mains-powered with heavy data means Wi-Fi or LTE Cat-1; tiny reports from the field for years means NB-IoT or LTE-M with PSM, or LoRaWAN if I can own the gateways. I would never put NB-IoT on something fast-moving because it has no connected-mode handover.

BLE stack layers: PHY, LL, HCI, L2CAP, ATT, GATT, GAP, SMP

BEGINNER▶

1. WHAT IS IT?

Bluetooth Low Energy (BLE) is built as a stack of layers. Each layer solves one problem and hands its result to the layer above: the bottom ones move bits over the air on time, the top ones decide what those bits mean (a heart-rate value, a button press). When an interviewer asks "where does X happen in BLE?", they are checking that you know this map.

2. TERMS (bottom to top)

PHY
Physical layer: the radio and modulation (GFSK). Options: LE 1M (1 Msym/s), LE 2M (2 Msym/s, Bluetooth 5), LE Coded (1 Msym/s with forward error correction, S=2 → 500 kbps or S=8 → 125 kbps, for long range).
LL
Link Layer: packet format, advertising, connection timing, channel hopping, acknowledgements and retransmission, encryption (AES-CCM). Runs in the controller with hard real-time timing.
HCI
Host Controller Interface: a standard command/event protocol between the host (upper layers, often on the application CPU) and the controller (PHY + LL). Over UART/USB in two-chip designs; a function-call interface when both run on one SoC.
L2CAP
Logical Link Control and Adaptation Protocol: multiplexes channels (fixed CIDs: 0x0004 ATT, 0x0005 LE signalling, 0x0006 SMP) and fragments/reassembles upper-layer packets bigger than one LL packet. Adds a 4-byte header (length + channel ID).
ATT
Attribute Protocol: client/server protocol to read and write attributes (a handle, a type UUID, a value, permissions). Opcodes like Read Request, Write Command, Handle Value Notification.
GATT
Generic Attribute Profile: organises attributes into services and characteristics and defines procedures (discovery, notifications).
GAP
Generic Access Profile: roles (broadcaster, observer, peripheral, central), advertising/scanning modes, connection establishment, addresses and privacy.
SMP
Security Manager Protocol: pairing, key generation and key distribution.

3. LIFE OF A NOTIFICATION, STEP BY STEP

  1. App calls e.g. bt_gatt_notify() (Zephyr) with 20 bytes of sensor data.
  2. GATT knows which characteristic value handle this is (say 0x0012) and checks the client subscribed.
  3. ATT builds the PDU: opcode 0x1B (Handle Value Notification) + 2-byte handle + 20 bytes = 23 bytes.
  4. L2CAP prepends 4 bytes (length = 23, CID = 0x0004) → 27 bytes.
  5. Through HCI (as an ACL data packet) to the controller.
  6. LL puts it in a data PDU: 2-byte header + 27-byte payload (+4-byte MIC if encrypted) + 3-byte CRC, waits for the next connection event, transmits on the hopped channel, retransmits until acknowledged.
  7. PHY modulates it: at 1M, (1 preamble + 4 access address + 2 + 27 + 3) bytes × 8 µs = 296 µs on air.

5. WHAT GOES WRONG IF…

…you think "MTU" is one thing. There are two sizes: the ATT MTU (largest ATT PDU, negotiated by ATT Exchange MTU; default 23) and the LL max payload (Data Length Extension, 27 default up to 251). A 247-byte ATT MTU with 27-byte LL packets works, but L2CAP fragments every notification into 10 LL packets. Interviewers check you can separate them.
BLE splits into a controller and a host joined by HCI. The controller has the PHY, which can be 1M, 2M or Coded, and the Link Layer, which owns timing, hopping, acknowledgements and encryption. The host has L2CAP for channel multiplexing and fragmentation, ATT for reading and writing handles, GATT for organising them into services and characteristics, GAP for roles and advertising, and SMP for pairing. A 20-byte notification grows by 3 bytes of ATT header, 4 of L2CAP, then the LL header, MIC and CRC.

BLE advertising: channels 37/38/39, intervals, PDUs, scan response

BEGINNER▶

1. WHAT IS IT?

Before two BLE devices connect, one of them has to announce itself. Advertising is a short broadcast packet, repeated at a regular interval on three special channels, that says "I exist, here is my name/service, and (maybe) you can connect to me". Beacons (iBeacon, Eddystone, Apple Find My) never connect at all; they only advertise.

2. TERMS

Advertiser / Scanner
the device sending advertisements (usually the peripheral) and the device listening (usually the phone, the central).
Advertising event
one round of transmissions: the same packet sent on channel 37, then 38, then 39, a few hundred µs apart.
advInterval
time between the starts of advertising events: 20 ms to 10.24 s, in steps of 0.625 ms.
advDelay
a random 0–10 ms the controller adds to every interval so two advertisers with the same interval do not collide forever.
AD structure
the format inside advertising data: [length][AD type][data]. Types: 0x01 Flags, 0x03 Complete 16-bit UUID list, 0x09 Complete Local Name, 0x0A TX Power Level, 0xFF Manufacturer Specific Data.
Scan response
a second 31-byte packet the advertiser sends only when an active scanner asks with SCAN_REQ.

4. ONE ADVERTISING EVENT, STEP BY STEP

  1. The controller wakes, starts the crystal and ramps up the radio (~40–140 µs on nRF52).
  2. Transmits ADV_IND on channel 37 (2402 MHz). With 31 bytes of AdvData the PDU is 2 (header) + 6 (AdvA address) + 31 = 39 bytes; on air at 1M: (1 + 4 + 39 + 3) × 8 µs = 376 µs.
  3. Switches to receive for ~150 µs (T_IFS, the inter-frame space) plus a short window, listening for SCAN_REQ or CONNECT_IND.
  4. Repeats on channel 38 (2426) and channel 39 (2480).
  5. Sleeps until the next event: advInterval + random advDelay later.
  6. A scanner listening on one channel for its scan window (e.g. 30 ms every 300 ms scan interval) hears the packet only if the advertiser happens to transmit on that channel during the window. That is why discovery time is probabilistic.

Extended and periodic advertising (Bluetooth 5)

INTERMEDIATE▶

1. WHAT IS IT?

Legacy advertising is limited to 31 bytes, the 1M PHY and the three crowded primary channels. Bluetooth 5 added extended advertising: a short header on the primary channels that points to the real (bigger) payload sent on one of the 37 ordinary data channels, on any PHY. It is how you get long-range (Coded PHY) discovery and payloads up to 1650 bytes.

2. TERMS

Primary channels
37, 38, 39 — still used, but only for a tiny ADV_EXT_IND header.
Secondary channels
data channels 0–36, used for the payload (AUX_ADV_IND).
AuxPtr
a field in ADV_EXT_IND giving the channel, PHY and time offset of the auxiliary packet.
AUX_CHAIN_IND
continuation packets when data does not fit in one (up to 254 bytes of AdvData per PDU, 1650 total).
Advertising set
an independent advertising configuration; a controller can run several at once (e.g. a connectable set + a beacon set).
Periodic advertising
advertising at a fixed interval that scanners can synchronise to and receive without connecting (used by LE Audio broadcast / Auracast for its control info).

3. HOW IT WORKS, STEP BY STEP

  1. Advertiser sends ADV_EXT_IND on 37, 38, 39. It carries no user data, just header fields including AuxPtr ("payload on channel 22, 2M PHY, in 2.4 ms").
  2. Scanner that understands extended advertising tunes to channel 22 at that time and receives AUX_ADV_IND with up to 254 bytes.
  3. If more data follows, AUX_ADV_IND contains another AuxPtr to AUX_CHAIN_IND, and so on.
  4. For Coded PHY, both the primary and secondary packets can be sent on LE Coded, so the whole discovery works at long range. Legacy PDUs cannot use Coded.
Sending 200 bytes of manufacturer data:
Legacy: impossible (31 B max, 62 with scan response).
Extended, secondary on 2M: AUX_ADV_IND ≈ header ~12 B + 200 B → (2 + 4 + 2 + 212 + 3) × 4 µs ≈ 0.9 ms on air, sent once per event on one channel, plus three tiny ADV_EXT_IND packets (~ 100–150 µs each at 1M). Same data with legacy would need several devices or connections.

…you switch a product to extended advertising only. Older phones (pre-Bluetooth 5 controllers) cannot see it at all: they only parse legacy PDUs. Typical solution: run two advertising sets — a legacy connectable one for compatibility and an extended one for long range / big payloads.

BLE connections: interval, peripheral latency, supervision timeout

INTERMEDIATE▶

1. WHAT IS IT?

Once connected, the two devices do not stay awake. They agree on a schedule and meet at regular moments called connection events, exchange a few packets, and sleep in between. Three numbers define that schedule: how often they meet (connection interval), how many meetings the peripheral may skip (peripheral latency), and how long silence may last before the link is declared dead (supervision timeout). Nearly every BLE power, latency and disconnect question comes back to these three.

2. TERMS

Central / Peripheral
the device that initiated the connection and runs the timing (usually the phone) / the device that advertised (the sensor). Older spec text says master/slave.
connInterval
time between two connection events. 7.5 ms to 4 s in units of 1.25 ms (value 6 to 3200).
Anchor point
the start of a connection event, where the central transmits first.
connPeripheralLatency
(old name slave latency) number of consecutive events the peripheral may skip when it has nothing to send. 0 to 499.
connSupervisionTimeout
maximum time between two valid received packets before the link is considered lost. 100 ms to 32 s in units of 10 ms.
SCA
Sleep Clock Accuracy, the ppm error of the 32 kHz clock used while sleeping. Causes window widening: the receiver opens its window early to cover clock drift.

3. THE RULES, STEP BY STEP

  1. The central sends CONNECT_IND with Interval, Latency, Timeout, a channel map, a hop increment and an access address.
  2. Every connInterval an event happens. The central always transmits at the anchor; the peripheral replies 150 µs (T_IFS) after each central packet.
  3. If the peripheral has nothing to send, it may sleep through up to Latency events. Its effective listening period becomes (1 + Latency) × connInterval. It must wake earlier if it has data.
  4. Each side resets its supervision timer whenever it receives a valid packet. If the timer reaches connSupervisionTimeout, the link drops (HCI reason 0x08, "Connection Timeout").
  5. The spec rule: connSupervisionTimeout (ms) > (1 + Latency) × connInterval (ms) × 2. Otherwise the peripheral could legally skip events long enough to time itself out. The values are validated by the controller; a central must reject a parameter request that breaks this.
  6. Either side can change parameters later: the peripheral asks with an L2CAP Connection Parameter Update Request or LL_CONNECTION_PARAM_REQ; the central applies it with LL_CONNECTION_UPDATE_IND at a chosen future event (the "instant").
Interval 30 ms, Latency 4, Timeout 400 ms.
Effective listen period = (1 + 4) × 30 = 150 ms. Rule: 2 × 150 = 300 ms < 400 ms → valid.
Worst-case latency for a write from the phone to reach a sleeping peripheral = 150 ms (plus processing).
Change Latency to 10: (1 + 10) × 30 × 2 = 660 ms > 400 ms → invalid; the controller rejects it, or (on buggy stacks) the link drops after a single interfered event.
Window widening with a 32 kHz RC oscillator (±500 ppm) and a 50 ppm central over 150 ms: (550 × 10⁻⁶) × 150 ms = 82.5 µs each side of the anchor, plus 16 µs jitter. With a ±20 ppm crystal: (70 × 10⁻⁶) × 150 = 10.5 µs. The RC oscillator costs ~8× more receive time per event.

4. APPLE ACCESSORY GUIDELINES (summary)

Apple's Accessory Design Guidelines list connection-parameter rules an accessory must respect when requesting an update (check the current revision for exact wording): Interval Min ≥ 15 ms and a multiple of 15 ms; Interval Max ≥ Interval Min + 15 ms (or both 15 ms); Peripheral Latency ≤ 30; Supervision Timeout between 2 s and 6 s; Interval Max × (Latency + 1) ≤ 2 s; Interval Max × (Latency + 1) × 3 < Supervision Timeout. iOS may reject or ignore requests that break them.

…the timeout is only just above the rule. The rule allows one missed opportunity. Inside a connection event: packets, T_IFS, SN/NESN and the MD bit

ADVANCED▶

1. WHAT IS IT?

A connection event is a short conversation: the central speaks, the peripheral answers, and they may keep alternating while either has more data. The Link Layer's acknowledgement scheme guarantees every data packet is delivered in order and exactly once, without a separate ACK packet.

2. TERMS

T_IFS
Inter Frame Space: exactly 150 µs between the end of one packet and the start of the reply.
Empty PDU
a data packet with zero payload, sent just to keep the exchange going or to acknowledge. 80 µs at 1M.
SN
Sequence Number, 1 bit in the LL header, toggles for each new packet.
NESN
Next Expected Sequence Number, 1 bit: "I have received up to here, send me the next one". Acts as the acknowledgement.
MD
More Data bit: "I have more to send, keep the event open".
CE length
maximum event duration the controller schedules; also limited by other links and radio activity.

3. HOW AN EVENT RUNS, STEP BY STEP

  1. At the anchor point the central transmits (data or empty PDU) on this event's channel.
  2. The peripheral, already listening (window widening), receives it and 150 µs later replies.
  3. Each side checks the other's NESN: if NESN ≠ the SN of my last packet, my packet was acknowledged → send a new one; otherwise retransmit the old one.
  4. If either sent MD = 1 (and the CRC was good), the central sends again 150 µs after the reply. The event continues.
  5. The event closes when neither has MD set, when a CRC error happens twice in a row, or when the scheduled CE length or next anchor is near.
  6. Both sleep until the next anchor; the next event uses the next hop channel.
Peripheral streams full packets (251-byte LL payload) at 2M PHY, central sends empty PDUs:
Data PDU 2M = (2 preamble + 4 AA + 2 header + 251 + 3 CRC) × 4 µs = 1048 µs. Empty PDU 2M = 11 × 4 = 44 µs.
One exchange = 44 + 150 + 1048 + 150 = 1392 µs. In a 7.5 ms interval: floor(7500 / 1392) = 5 exchanges (if the phone allows that many). Each carries 244 bytes of notification value → 5 × 244 × 8 / 7.5 ms = 1.30 Mbps.

4. CODE: THE ACK LOGIC (pseudo-C of what the LL does)

struct ll { uint8_t sn, nesn; pdu_t *tx_head; };

void on_rx(struct ll *l, const pdu_hdr_t *h, bool crc_ok) {
    if (!crc_ok) return;                       // no ack info usable
    if (h->nesn != l->sn) {                    // peer acked my last PDU
        l->sn ^= 1;                            // next PDU gets new SN
        dequeue(&l->tx_head);                  // free it
    }                                          // else: resend same PDU
    if (h->sn == l->nesn) {                    // new data from peer
        deliver(h);                            // hand to L2CAP
        l->nesn ^= 1;                          // ack it in my next PDU
    }                                          // else: duplicate, drop
}

5. WHAT GOES WRONG IF…

…you expect "N notifications queued = N sent this event". The phone decides how long events last. Many phones allow only a handful of packets per event, and while Wi-Fi coexistence or another BLE link is active it may be 1–2. If your app queues one notification per event, throughput is capped at payload/interval regardless of PHY.

A connection event starts with the central transmitting at the anchor, and the two then alternate with exactly 150 microseconds between packets. Acknowledgement is built into every header: the SN bit identifies a packet and the NESN bit says which one I expect next, so a packet is retransmitted until the peer's NESN moves on, and duplicates are dropped. The MD bit keeps the event open, so throughput depends on how many exchanges fit in the event — at 2M with full 251-byte packets one exchange takes about 1.4 ms.

BLE throughput math: MTU, Data Length Extension, packets per event

INTERMEDIATE▶

1. WHAT IS IT?

"BLE is 1 or 2 Mbps" is only the raw symbol rate. What the application actually gets depends on how many useful bytes fit in each packet, how long each packet and its reply take on air, and how many packets the phone lets you send each connection event. This card is the classic whiteboard calculation.

2. TERMS

ATT_MTU
largest ATT packet. Default 23 → notification value max 23 − 3 = 20 bytes. Negotiated with ATT Exchange MTU (up to 517).
DLE
Data Length Extension (Bluetooth 4.2): raises the LL payload from 27 to up to 251 bytes, negotiated with LL_LENGTH_REQ/RSP.
Overhead per LL packet
1M: 1 preamble + 4 access address + 2 header + 3 CRC = 10 bytes; 2M: 2-byte preamble → 11 bytes; +4 MIC if encrypted.
PPE
packets per connection event.

3. THE FORMULA, STEP BY STEP

  1. Useful bytes per notification = ATT_MTU − 3 (opcode + handle).
  2. Bytes per LL payload = notification + 4 (L2CAP header). If that exceeds the DLE size, it is fragmented across several LL packets.
  3. Time per LL packet on air = (overhead + payload) × 8 µs at 1M, × 4 µs at 2M.
  4. Time per exchange = data packet + T_IFS + empty packet from the central + T_IFS.
  5. PPE = min(floor(usable event time / exchange time), limit set by the phone/stack).
  6. Throughput = PPE × useful bytes per packet × 8 / connInterval.
throughput = PPE × (MTU−3) × 8 / CI (when one notification = one LL packet)
Default (no MTU exchange, no DLE), 1M, CI = 30 ms, phone allows 4 PPE:
Value 20 B; LL payload 20 + 3 + 4 = 27 B. Data packet = (10 + 27) × 8 = 296 µs; empty = 80 µs. Exchange = 296 + 150 + 80 + 150 = 676 µs.
4 × 20 × 8 bits / 30 ms = 21.3 kbps (2.7 kB/s). Link mostly idle: 4 × 676 = 2.7 ms of 30 ms used.

MTU 247 + DLE 251, 2M, CI = 15 ms, phone allows 6 PPE:
Value 244 B; LL payload 244 + 3 + 4 = 251 B. Exchange = 1048 + 150 + 44 + 150 = 1392 µs. floor(15000 / 1392) = 10 → limited to 6.
6 × 244 × 8 / 15 ms = 781 kbps (≈ 98 kB/s) — a 37× improvement from parameters alone.

Trap: MTU 247 but DLE 27: each 251-byte L2CAP frame becomes ceil(251 / 27) = 10 LL packets, 9 full + 1 of 8 B. 10 exchanges per notification, so PPE limits now count fragments, not notifications.

4. CODE: COMPUTE IT (whiteboard solution)

#include <stdint.h>
/* phy: 1 = 1M, 2 = 2M. Returns app throughput in bit/s. */
static uint32_t air_us(uint16_t payload, int phy, int mic) {
    uint16_t ovh = (phy == 2 ? 11 : 10) + (mic ? 4 : 0);
    return (uint32_t)(ovh + payload) * (phy == 2 ? 4 : 8);
}
uint32_t ble_tput(uint16_t mtu, uint16_t dle, int phy, int mic,
                  uint32_t ci_us, uint16_t ppe_limit) {
    uint16_t value  = mtu - 3;                 // ATT notify value
    uint16_t l2cap  = mtu + 4;                 // SDU incl. L2CAP hdr
    uint16_t frags  = (l2cap + dle - 1) / dle; // LL packets per notify
    uint16_t last   = l2cap - (frags - 1) * dle;
    uint32_t t_empty = air_us(0, phy, 0);      // central's empty PDU (no MIC on empty)
    uint32_t t_notif = (frags - 1) * (air_us(dle, phy, mic) + 300 + t_empty)
                     + (air_us(last, phy, mic) + 300 + t_empty);
    uint32_t t_pkt   = t_notif / frags;        // average per LL packet
    uint32_t ppe = (ci_us - 150) / t_pkt;      // what fits in the interval
    if (ppe > ppe_limit) ppe = ppe_limit;      // phone / stack limit
    /* bytes per event = (ppe/frags) notifications × value */
    return (uint32_t)((uint64_t)ppe * value * 8u * 1000000u / frags / ci_us);
}

(300 = 2 × T_IFS. Empty PDUs never carry a MIC. A real event cannot overrun the next anchor, so the margin of one T_IFS is a simplification; the BLE simulator tab runs the exact event-by-event version.)

5. WHAT GOES WRONG IF…

…the peripheral never requests a bigger MTU and the phone never offers one. You get 20-byte notifications forever. Both sides must support it; on iOS the central initiates the MTU exchange automatically, on Android the app must call requestMtu(517). Always read the negotiated value in the MTU-exchanged callback and size notifications to mtu − 3.
…you use Write With Response for an upload. Each write waits for a Write Response from the server: at most one write per ~1–2 connection intervals. Use Write Without Response (Write Command) with flow control at the application level.
Throughput is packets per event times useful bytes per packet divided by the connection interval. Useful bytes are MTU minus 3 for the ATT header, and the L2CAP SDU of MTU plus 4 must fit in the LL payload set by Data Length Extension, otherwise it fragments. At 2M with MTU 247 and DLE 251 an exchange takes about 1.4 ms and carries 244 bytes, so the ceiling is around 1.3 to 1.4 Mbps, while defaults of MTU 23, no DLE and a few packets per event give only tens of kbps; the real limiter is usually how many packets per event the phone allows.

GATT: services, characteristics, descriptors and handles

BEGINNER▶

1. WHAT IS IT?

GATT (Generic Attribute Profile) is how a BLE device presents its data: like a small database with numbered rows. A phone app discovers the rows, then reads, writes or subscribes to them. A heart-rate strap, for example, exposes a "Heart Rate service" containing a "Heart Rate Measurement characteristic".

2. TERMS

Attribute
one row: handle (16-bit row number), type (a UUID saying what the row is), value, and permissions (readable? encrypted only?).
UUID
Universally Unique Identifier. 16-bit ones (e.g. 0x180D Heart Rate) are assigned by the Bluetooth SIG; custom services use random 128-bit UUIDs.
Service
a group of related characteristics, declared by a row of type 0x2800 (Primary Service).
Characteristic
one data item. Declared by a row of type 0x2803 holding its properties (Read 0x02, Write Without Response 0x04, Write 0x08, Notify 0x10, Indicate 0x20), the value handle and the UUID; followed by the value row.
Descriptor
extra rows describing a characteristic. The important one is the CCCD (0x2902, Client Characteristic Configuration Descriptor).
GATT server / client
the device holding the table (usually the peripheral) / the device using it (usually the phone). Server/client is independent of central/peripheral.

3. HOW A PHONE USES IT, STEP BY STEP

  1. After connecting, the client does service discovery (ATT Read By Group Type for 0x2800) to list services and their handle ranges.
  2. Characteristic discovery (Read By Type 0x2803) inside each range → properties and value handles.
  3. Descriptor discovery (Find Information) to find CCCDs.
  4. Read/write the value handle, or write the CCCD to subscribe.
  5. Bonded clients may cache the table (GATT caching). If your firmware update changes the table, indicate the Service Changed characteristic (0x2A05) or the phone will use stale handles.

CCCD, notifications vs indications, write vs write-without-response

INTERMEDIATE▶

1. WHAT IS IT?

A server cannot push data to a client that has not asked for it. The client opts in by writing to the characteristic's CCCD. After that the server can send notifications (fire-and-forget at the ATT level) or indications (each one confirmed by the client before the next).

2. TERMS

CCCD
Client Characteristic Configuration Descriptor, UUID 0x2902, 2 bytes little-endian: bit 0 = notifications enabled (0x0001), bit 1 = indications enabled (0x0002). Stored per client; kept across reconnections only for bonded clients.
Notification
ATT opcode 0x1B, no ATT-level reply. Still reliable at the Link Layer (retransmitted until acked) while the link is up.
Indication
ATT opcode 0x1D; the client must reply with Handle Value Confirmation (0x1E). Only one indication may be outstanding at a time.
Write Request / Write Command
0x12 (needs Write Response 0x13) vs 0x52 (no response, "write without response").

3. WHAT HAPPENS, STEP BY STEP

  1. Phone app calls setNotifyValue(true) (iOS) or writes 01 00 to the CCCD (Android: writeDescriptor).
  2. The server's stack stores 0x0001 for this connection and calls your callback.
  3. Firmware checks the subscription, then calls notify. If not subscribed the stack refuses (e.g. Nordic SoftDevice sd_ble_gatts_hvx returns NRF_ERROR_INVALID_STATE; with system attributes missing after a reconnect, BLE_ERROR_GATTS_SYS_ATTR_MISSING).
  4. For indications the stack waits for the confirmation; the next indication is blocked until then (ATT transaction timeout is 30 s).
Rate limit of indications: send at one event, confirmation comes back in the next event at the earliest. With CI = 30 ms → at most 1 indication per ~60 ms → ~16 per second, × 20 bytes = 2.7 kbps (default MTU). Notifications at 6 PPE in the same interval: 6 × 20 B / 30 ms = 32 kbps, 12× more.

4. CODE (WRONG vs RIGHT)

✖ WRONG — notify regardless

    // nobody notices

✔ RIGHT — check subscription and result

        return;                     // buffer it or wait for CCCD write
    int err = bt_gatt_notify(conn, a, &v, sizeof v);
    if (err == -ENOMEM)             // TX buffers full
        retry_later();              // back-pressure, don't drop
}

5. WHAT GOES WRONG IF…

…the device is not bonded. The CCCD value is reset on every new connection. The app subscribed yesterday, reconnects today without re-subscribing and receives nothing. Fix: app re-enables notifications on every connection (iOS CoreBluetooth requires this anyway), or bond so the server restores CCCDs.
…you think notifications are "unreliable UDP". Within a live connection the Link Layer retransmits until acknowledged, so a notification is not lost silently over the air. It can be lost if your TX buffer was full (API error) or the link drops before it is sent. Indications add an application-level confirmation that the client's ATT layer received it.
The client opts in by writing the CCCD, 0x2902: 0x0001 for notifications, 0x0002 for indications, and it is stored per client and only remembered across connections when bonded. Notifications have no ATT-level reply but are still retransmitted by the Link Layer, so they are fast and reliable while the link is up; indications need a confirmation and allow only one outstanding, so they are limited to about one per two connection intervals. In firmware I check the subscription before notifying and handle out-of-buffer errors as back-pressure.

Pairing and bonding: Just Works, Passkey, Numeric Comparison, OOB, LE Secure Connections

ADVANCED▶

1. WHAT IS IT?

Pairing is how two BLE devices agree on encryption keys. Bonding is saving those keys so next time they can encrypt immediately without pairing again. The interesting part is protecting against an attacker who listens (eavesdropping) or sits in the middle relaying packets (MITM, man-in-the-middle).

2. TERMS

LE Legacy Pairing
Bluetooth 4.0/4.1 method based on a 128-bit Temporary Key (TK). Just Works uses TK = 0, so a passive sniffer recording the pairing can brute-force the key (tool "crackle").
LE Secure Connections (LESC)
Bluetooth 4.2+: uses ECDH (Elliptic Curve Diffie-Hellman on curve P-256). Each side sends a public key; both compute the same shared secret that an eavesdropper cannot.
Association model
how the user confirms there is no MITM: Just Works (no confirmation, no MITM protection), Passkey Entry (6 digits typed), Numeric Comparison (both show 6 digits, user taps "yes"), OOB (Out Of Band, e.g. NFC tag exchanges data).
IO capabilities
what each device can do: DisplayOnly, DisplayYesNo, KeyboardOnly, NoInputNoOutput, KeyboardDisplay. The pair of capabilities picks the model.
LTK, IRK, CSRK
Long Term Key (encryption), Identity Resolving Key (privacy, resolves random addresses), Connection Signature Resolving Key (data signing).

3. THE PHASES, STEP BY STEP

  1. Phase 1 – Feature exchange: Pairing Request / Pairing Response carry IO capabilities, OOB flag, AuthReq (bonding? MITM? SC?), max key size and which keys to distribute.
  2. Phase 2 – Key generation: with LESC both send P-256 public keys, compute the DH shared key, run the chosen association model (confirm values, nonces), derive the LTK with function f5, and verify with f6 (DHKey check).
  3. The link is encrypted with the LTK (AES-CCM, 4-byte MIC on every packet).
  4. Phase 3 – Key distribution over the encrypted link: identity information (IRK + identity address), optionally CSRK.
  5. If bonding was requested, both store keys in non-volatile memory. Next connection: central sends LL_ENC_REQ → encryption starts in a few packets.

Privacy: Resolvable Private Addresses (RPA) and address types

ADVANCED▶

1. WHAT IS IT?

Every advertisement contains the sender's address. If that address never changed, anyone with a scanner could track a person's earbuds or watch through a city. BLE privacy makes devices advertise with an address that changes every few minutes, while bonded peers can still recognise them using a shared secret key.

2. TERMS

Public address
IEEE-assigned 48-bit address, fixed (like a MAC).
Random static
random 48-bit address, top two bits 11, may change only at power cycle.
RPA
Resolvable Private Address: top two bits 01, 22 random bits (prand) + 24-bit hash = ah(IRK, prand). Changes periodically (spec recommends 15 minutes).
NRPA
Non-Resolvable Private Address: top two bits 00, cannot be resolved by anyone (beacons that must never be tracked).
IRK
Identity Resolving Key, 128 bits, exchanged during bonding.
Resolving list
table of peer IRKs inside the controller so it can resolve RPAs in hardware (LL Privacy, Bluetooth 4.2), e.g. to auto-accept a bonded phone in a filter accept list.

3. HOW RESOLUTION WORKS, STEP BY STEP

  1. Device picks 22 random bits and sets the top two bits to 01 → 24-bit prand.
  2. Computes hash = ah(IRK, prand) = lowest 24 bits of AES-128(IRK, padding‖prand).
  3. Address = prand (upper 24 bits) ‖ hash (lower 24 bits). Advertises with it.
  4. A scanner that knows the IRK (bonded) takes the upper 24 bits, recomputes ah(IRK, prand) for each IRK in its list, and compares with the lower 24 bits. A match identifies the device.
  5. Every ~15 minutes (configurable), the device generates a new prand → new address. Strangers see unrelated addresses.
Address 5A:3F:C1:8E:22:07: top byte 0x5A = 0101 1010 → top bits 01 → RPA.
prand = 0x5A3FC1, hash = 0x8E2207. Resolve: AES-128(IRK, 0x00…005A3FC1) → take lowest 24 bits; if they equal 0x8E2207 it's our bonded peer.
Address D4:...: 0xD4 = 1101 0100 → bits 11 → random static.

4. CODE

#include <stdbool.h>
#include <string.h>
/* addr[0] = least significant byte (as on air). aes128_ecb from your crypto lib. */
bool rpa_resolve(const uint8_t irk[16], const uint8_t addr[6]) {
    if ((addr[5] & 0xC0) != 0x40) return false;   // top bits must be 01
    uint8_t in[16] = {0}, out[16];
    in[13] = addr[5]; in[14] = addr[4]; in[15] = addr[3]; // prand, big-endian into block
    aes128_ecb(irk, in, out);                     // e(k, r')
    // ah = lowest 24 bits of result
    return out[15] == addr[0] && out[14] == addr[1] && out[13] == addr[2];
}

(Byte ordering of the key and block follows the spec's big-endian convention for the AES function; stacks provide this as e.g. bt_rpa_irk_matches() in Zephyr — use the stack's version in production.)

5. WHAT GOES WRONG IF…

…the peripheral whitelists the phone by address. iPhones and Android phones use RPAs that rotate. Yesterday's address never shows up again, so the filter list blocks the bonded phone. Fix: add the peer's IRK to the controller's resolving list and filter by identity address.
…you put a fixed serial number in manufacturer data. Privacy is defeated: the address rotates, the payload does not. Apple's Find My protocol rotates its payload keys too.
To prevent tracking, devices advertise with a resolvable private address: the top two bits are 01, 22 random bits form prand, and the lower 24 bits are a hash of prand with the identity resolving key, ah equals AES of IRK. A bonded peer that has the IRK recomputes the hash and recognises the device, while strangers just see a new address roughly every 15 minutes. That's why filtering by address breaks with phones; you add the IRK to the controller's resolving list instead, and you must not leak a fixed identifier in the payload.

BLE power optimisation: where the microamps go

ADVANCED▶

1. WHAT IS IT?

A BLE device's average current is the sleep current plus the charge of every radio event divided by time. The radio itself draws only ~5 mA for ~1 ms, but if that happens 100 times a second it dominates. Power optimisation is mostly about doing fewer, shorter, fuller radio events.

2. TERMS

Charge per event (µC)
current × time integrated over one advertising or connection event, including wake-up, crystal start-up, ramp-up, RX/TX and processing.
Average current
I_avg = I_sleep + Σ(Q_event) / T.
DC/DC
switching regulator inside the SoC (nRF52: enable REG1 DCDC) that reduces radio current by ~40 % versus the LDO.
HFXO
High-Frequency Crystal Oscillator (32 MHz), needed for the radio; takes ~0.3–1 ms to start.

3. THE KNOBS, IN ORDER OF IMPACT

  1. Interval: advertising and connection interval set how many events per second. Doubling interval halves the event term.
  2. Peripheral latency: skip events when idle without slowing the phone's ability to send data eventually.
  3. Fewer, fuller packets: batch samples into one 244-byte notification instead of twelve 20-byte ones (fixed per-event overhead is paid once).
  4. 2M PHY: half the airtime per byte → less TX/RX time (but slightly less range).
  5. Sleep clock: a 32.768 kHz crystal (±20 ppm) instead of RC (±250–500 ppm) shrinks window widening.
  6. TX power: only as high as the link needs; enable DC/DC.
  7. Sleep current: GPIO leakage, RAM retention, peripherals left on.
nRF52840-class device (3 V, DC/DC): sleep 2 µA. Connection event ≈ 0.4 ms CPU/HFXO overhead at ~2.5 mA + 0.14 ms ramp + 0.3 ms RX + 0.1 ms TX at ~5 mA ≈ ~3.7 µC (rough).
CI = 30 ms, latency 0: 3.7 µC / 0.030 s = 123 µA + 2 µA ≈ 125 µA → CR2032 220 mAh → 1760 h ≈ 73 days.
CI = 500 ms, latency 0: 7.4 + 2 = 9.4 µA → ~2.7 years (before self-discharge).
CI = 100 ms, latency 9 (effective 1 s): ~3.7 + 2 = 5.7 µA, while writes from the phone still arrive within 1 s.
The BLE simulator tab computes this event-by-event for your parameters.

4. CODE: BATCHING (WRONG vs RIGHT)

✖ WRONG — one notify per sample at 100 Hz

    // needs CI ≤ 10 ms → 100 events/s
}

        n = 0;                    // one notify per 400 ms
    }
}

5. WHAT GOES WRONG IF…

…you measure average current with a multimeter. The meter averages badly over µs-length 5 mA spikes and its burden voltage disturbs them. Use a power profiler (Nordic PPK2, Otii, Joulescope) that samples at ≥100 kHz.
…you sleep but leave UART logging on. The UART peripheral keeps the HFCLK requested: sleep current jumps from 2 µA to ~500 µA. Disable logging or use RTT in production builds.
Average current is sleep current plus charge per radio event times events per second, so I attack the number of events first: longer advertising and connection intervals, peripheral latency when idle, and batching data so each event carries a full MTU. Then I shorten each event with the 2M PHY, a crystal sleep clock to reduce window widening, the DC/DC regulator and only the TX power the link budget needs, and I verify with a power profiler rather than a multimeter. For example going from a 30 ms interval to 100 ms with latency 9 takes a sensor from about 125 µA to under 10 µA.

LE Audio and isochronous channels (brief)

INTERMEDIATE▶

1. WHAT IS IT?

Classic Bluetooth audio (A2DP for music, HFP for calls) runs on BR/EDR, the older non-LE radio. LE Audio (Bluetooth 5.2+) carries audio over Bluetooth Low Energy using isochronous channels — time-scheduled streams where data has a deadline — and the new LC3 codec. It enables lower power, multi-stream true wireless earbuds, hearing aids and public broadcast ("Auracast").

2. TERMS

Isochronous
data that is only useful if delivered within a time window; late audio is dropped instead of retransmitted forever.
CIS / CIG
Connected Isochronous Stream (point-to-point, acknowledged) grouped in a Connected Isochronous Group (e.g. left + right earbud from one phone).
BIS / BIG
Broadcast Isochronous Stream / Group: one-to-many, unacknowledged; Auracast broadcast audio.
LC3
Low Complexity Communication Codec: better quality than SBC at the same bitrate (e.g. 7.5 or 10 ms frames, 16–345 kbps).
Flush timeout / retransmission number
how many chances a packet gets before its deadline passes.

3. HOW A STEREO STREAM IS SET UP, STEP BY STEP

  1. The phone connects to each earbud over ordinary ACL BLE connections and uses GATT-based profiles (BAP, Basic Audio Profile; PACS for capabilities; ASCS for stream control) to configure codec and QoS.
  2. It creates a CIG with two CISes (left, right) with an ISO interval such as 10 ms.
  3. Every ISO interval each CIS gets subevents: audio frame sent, acked, retransmitted if needed until the flush point.
  4. Both earbuds render the frame at the same presentation time, giving synchronised stereo without relaying between buds.
LC3 at 48 kHz, 10 ms frames, 96 kbps per channel → 96 000 × 0.010 / 8 = 120 bytes per frame per earbud every 10 ms. At 2M PHY that packet is (11 + 120 + 4 MIC + ~4 ISO header) × 4 µs ≈ 0.56 ms — small, leaving time for retransmissions inside the same interval.

4. WHAT GOES WRONG IF…

…you treat audio like a file transfer. Reliable ACL notifications retransmit indefinitely; under interference latency balloons and the audio buffer underruns. Isochronous channels bound latency by dropping late packets and letting the codec's packet-loss concealment hide the gap.

LE Audio moves Bluetooth audio from BR/EDR onto Low Energy using isochronous channels, which are time-scheduled streams with a deadline: connected isochronous streams for earbuds and broadcast isochronous streams for Auracast. It uses the LC3 codec, which gives better quality than SBC at lower bitrate, and each earbud gets its own synchronised stream from the phone, so there is no relaying between buds. The key idea is bounded latency: a late packet is flushed and concealed rather than retransmitted forever.

Wi-Fi on an MCU: the ESP32 stack, station and access-point modes

BEGINNER▶

1. WHAT IS IT?

Putting Wi-Fi on a microcontroller means running, on a few hundred kB of RAM, the same steps a laptop does: find the network, authenticate, get an IP address, open TCP sockets. On the Espressif ESP32 the vendor provides the Wi-Fi driver (closed-source binary), the TCP/IP stack (lwIP) and the WPA supplicant; your firmware drives them through an event loop.

2. TERMS

STA
Station mode: the device joins an existing access point (your router) as a client.
AP / SoftAP
Access Point mode: the device creates its own network (used for setup/provisioning).
SSID / BSSID
network name / the AP's MAC address.
WPA2-PSK / WPA3-SAE
security modes: Pre-Shared Key (4-way handshake) / Simultaneous Authentication of Equals (resistant to offline password guessing).
lwIP
lightweight IP: a small open-source TCP/IP stack used by ESP-IDF and many RTOSes.
DHCP
Dynamic Host Configuration Protocol: the AP/router hands out an IP address, gateway and DNS server.
NVS
Non-Volatile Storage, ESP-IDF's key-value store in flash (credentials, calibration).

3. CONNECTING, STEP BY STEP

  1. Init: esp_netif_init(), create the default event loop, esp_wifi_init() (allocates driver buffers in RAM).
  2. Configure: mode STA, SSID/password, auth threshold; esp_wifi_start() → event WIFI_EVENT_STA_START.
  3. Connect: esp_wifi_connect() → scan → 802.11 authentication + association → WPA2 4-way handshake → WIFI_EVENT_STA_CONNECTED.
  4. IP: the DHCP client runs → IP_EVENT_STA_GOT_IP. Only now may you open sockets / start MQTT.
  5. Lose link: WIFI_EVENT_STA_DISCONNECTED carries a reason code (e.g. 201 NO_AP_FOUND, 15 4WAY_HANDSHAKE_TIMEOUT = wrong password often). Reconnect with backoff.
Typical ESP32 timings and currents (Espressif datasheet / docs, 3.3 V): association + DHCP 1–3 s; RX ~95–100 mA; TX 802.11b at 19.5 dBm ~240 mA (peaks higher). A cold connect of 2 s at ~120 mA average = 240 mC = 0.067 mAh. Doing that every 5 minutes: 288 × 0.067 = 19 mAh/day just for connecting, before any data. This is why battery Wi-Fi devices keep the association alive in power-save mode or reuse a static IP and cached channel/BSSID to shorten reconnects.

4. CODE: EVENT-DRIVEN CONNECT (WRONG vs RIGHT)

✖ WRONG — race with DHCP, tight retry
esp_wifi_connect();
vTaskDelay(pdMS_TO_TICKS(2000));  // "should be up"
mqtt_start();                      // fails if DHCP slow

void on_disc(...) {
    esp_wifi_connect();            // immediate retry storm
}
✔ RIGHT — wait for GOT_IP, back off
static EventGroupHandle_t eg;
#define GOT_IP BIT0
static int attempt;

static void h(void *arg, esp_event_base_t base, int32_t id, void *data) {
  if (base == WIFI_EVENT && id == WIFI_EVENT_STA_START) {
    esp_wifi_connect();
  } else if (base == WIFI_EVENT && id == WIFI_EVENT_STA_DISCONNECTED) {
    wifi_event_sta_disconnected_t *d = data;
    ESP_LOGW("wifi", "disc reason %d", d->reason); // log it!
    xEventGroupClearBits(eg, GOT_IP);
    schedule_reconnect(backoff_ms(attempt++));     // timer, jittered
  } else if (base == IP_EVENT && id == IP_EVENT_STA_GOT_IP) {
    attempt = 0;
    xEventGroupSetBits(eg, GOT_IP);
  }
}
/* app task */
xEventGroupWaitBits(eg, GOT_IP, pdFALSE, pdTRUE, portMAX_DELAY);
mqtt_start();

5. WHAT GOES WRONG IF…

…the 3.3 V rail cannot supply the TX peak. Symptom: "Brownout detector was triggered" and a reboot exactly when connecting. The Wi-Fi TX burst draws 300–500 mA for a few ms; a small LDO or long thin USB cable sags. Fix: regulator rated ≥ 500 mA, 10–22 µF + 100 µF bulk close to the module.
…you run heavy work in the event-loop callback. The default event loop task is shared; blocking it (e.g. doing a TLS connect inside the handler) delays every other Wi-Fi/IP event. Post to your own task instead.
START ─► connect() ─► [scan/auth/assoc/4-way] ─► CONNECTED ─► [DHCP] ─► GOT_IP ─► app sockets
  ▲                                                   │                              │
  └──── backoff timer ◄──── DISCONNECTED(reason) ◄────┴──────────────────────────────┘
On an ESP32 the Wi-Fi driver, lwIP and the supplicant are driven through events: start, connect, the association and WPA2 four-way handshake give STA_CONNECTED, but the application must wait for IP_EVENT_STA_GOT_IP before opening sockets because DHCP comes after. On disconnect I log the reason code and reconnect from a timer with jittered exponential backoff rather than calling connect in a tight loop. Hardware-wise the TX bursts are hundreds of milliamps, so brownouts on connect point to the power rail, not the code.

Wi-Fi power save: beacons, DTIM, modem sleep and light sleep

INTERMEDIATE▶

1. WHAT IS IT?

A Wi-Fi station cannot simply turn off its radio, because the access point might have data for it. 802.11 power save lets the station sleep and tell the AP "buffer my packets"; the AP announces in its periodic beacons who has data waiting. The station wakes only for the beacons it must hear.

2. TERMS

Beacon
management frame the AP broadcasts periodically, by default every 100 TU (Time Units; 1 TU = 1024 µs) = 102.4 ms.
TIM
Traffic Indication Map in every beacon: a bitmap of stations (by association ID) with buffered unicast frames.
DTIM
Delivery TIM: every Nth beacon (N = DTIM period, set on the AP, often 1–3); after a DTIM beacon the AP sends buffered broadcast/multicast frames.
Listen interval
how many beacon intervals the station may sleep, announced at association; the AP must buffer at least that long.
Modem sleep (ESP32)
radio off between DTIMs, CPU keeps running. WIFI_PS_MIN_MODEM wakes every DTIM; WIFI_PS_MAX_MODEM wakes every listen_interval.
Light sleep
CPU also clock-gated between beacons (ESP-IDF automatic light sleep with power management enabled).

3. HOW IT WORKS, STEP BY STEP

  1. Station sets the Power Management bit in a frame to the AP → AP starts buffering its unicast frames.
  2. Station sleeps, wakes slightly before the next beacon it needs (DTIM beacon for MIN_MODEM).
  3. Reads the TIM. If its bit is set it sends a PS-Poll (or a null frame with PM = 0) to retrieve data.
  4. If no bit set and no multicast pending → sleep again immediately (~ a few ms awake).
  5. Latency for incoming data = up to one DTIM (or listen) interval. A TCP server on the device responds slowly; ARP requests (broadcast) are only delivered after DTIM beacons.
Beacon interval 102.4 ms, DTIM period 3 → the station wakes every 307.2 ms ≈ 3.3 times per second. If each wake costs ~3 ms at ~60 mA (RX + overhead) = 0.18 mC → 0.18 mC × 3.26 /s ≈ 0.59 mA average from beacons, plus sleep floor (~0.8 mA in ESP32 light sleep with RAM retention) → about 1.4 mA. DTIM 1 would wake 9.8 times/s → ~2.6 mA. Same AP, same firmware, the DTIM setting alone nearly halves current — but you do not control the customer's router.

4. CODE (ESP-IDF)

wifi_config_t cfg = {
    .sta = {
        .ssid = "plant-ap", .password = "********",
        .listen_interval = 10,      // MAX_MODEM: wake every 10 beacons (~1 s)
        .threshold.authmode = WIFI_AUTH_WPA2_PSK,
    },
};
ESP_ERROR_CHECK(esp_wifi_set_config(WIFI_IF_STA, &cfg));
ESP_ERROR_CHECK(esp_wifi_set_ps(WIFI_PS_MAX_MODEM));  // or WIFI_PS_MIN_MODEM (DTIM)

esp_pm_config_t pm = {                     // automatic light sleep
    .max_freq_mhz = 160, .min_freq_mhz = 40,
    .light_sleep_enable = true,            // needs CONFIG_PM_ENABLE + tickless idle
};
ESP_ERROR_CHECK(esp_pm_configure(&pm));

5. WHAT GOES WRONG IF…

…listen_interval is long and the AP drops you. Some APs ignore long listen intervals or age out sleeping stations; others discard buffered frames. Symptom: device "online" but misses commands, or frequent disassociations. Test on the actual router models; use MIN_MODEM (DTIM) when reliability matters.
…you expect a TCP server on the device to be fast. Each incoming packet waits for the next DTIM wake: 300 ms+ per round trip. Push-based protocols (device opens an MQTT connection) behave much better.
beacons  │B   │B   │D   │B   │B   │D   │   (D = DTIM, period 3)
station   z z z z z z ▲ z z z z z z z ▲     ▲ = wake, read TIM, maybe fetch data
          |◄──── 307.2 ms ────►|
In 802.11 power save the station tells the AP to buffer its traffic and sleeps, waking for beacons: the TIM in each beacon flags buffered unicast frames and every DTIM beacon is followed by buffered broadcast traffic. On the ESP32, minimum modem sleep wakes every DTIM, maximum modem sleep wakes every listen interval, and automatic light sleep also gates the CPU. With a 102.4 ms beacon and DTIM 3 the device wakes every 307 ms, giving around one to a few milliamps average, at the cost of up to a DTIM period of downlink latency.

Wi-Fi provisioning: getting credentials into a headless device

INTERMEDIATE▶

1. WHAT IS IT?

A smart plug has no keyboard. Provisioning is how the user's phone securely hands it the home network's SSID and password (and often an account token). Done badly, it either fails for many users or leaks the Wi-Fi password to anyone nearby.

2. TERMS

SoftAP provisioning
device starts its own AP; the phone joins it and sends credentials over HTTP(S).
BLE provisioning
phone sends credentials over a BLE GATT service. ESP-IDF's wifi_provisioning uses "protocomm" with Security 1 (X25519 key exchange + proof-of-possession, AES-CTR) or Security 2 (SRP6a + AES-GCM).
PoP
Proof of Possession: a secret printed on the device/QR code proving the user physically has it.
SmartConfig / ESP-Touch
phone encodes credentials in the lengths of broadcast UDP packets on the user's network; the device sniffs in promiscuous mode. Simple but weakly protected and unreliable on modern routers.
WAC
Apple's Wireless Accessory Configuration (MFi program) for HomeKit/AirPlay devices.

3. BLE PROVISIONING, STEP BY STEP

  1. Device has no stored credentials → advertises "PROV_XXXX" with the provisioning service.
  2. App scans the QR code (device name + PoP), connects over BLE.
  3. Session establishment: X25519 key exchange; both derive a session key mixed with the PoP. An attacker without the PoP cannot complete it.
  4. App optionally asks the device to scan for Wi-Fi networks and shows the list.
  5. App sends SSID + password encrypted with the session key; device stores them in NVS (encrypted if NVS encryption + flash encryption are on).
  6. Device tries to connect and reports success or a precise failure (wrong password vs AP not found) back over BLE; then stops BLE to free RAM.
Why "report the failure reason" matters: 2.4 GHz-only ESP32 + user selects a 5 GHz SSID → reason 201 (NO_AP_FOUND). Wrong password → reason 15 (4WAY_HANDSHAKE_TIMEOUT) or 204 (HANDSHAKE_TIMEOUT). Telling the user "Wrong password" vs "Your router's 2.4 GHz network was not found" cuts provisioning support calls dramatically.

4. CODE: STORING CREDENTIALS (WRONG vs RIGHT)

✖ WRONG
printf("Got SSID %s PASS %s\n", ssid, pass); // logs secrets
nvs_set_str(h, "pass", pass);                 // plaintext flash
// never verifies before committing:
// a typo bricks the device until factory reset
✔ RIGHT
if (try_connect(ssid, pass, 15000) == OK) {   // verify first
    nvs_set_str(h, "ssid", ssid);
    nvs_set_str(h, "pass", pass);    // NVS encryption enabled
    nvs_commit(h);
    report(PROV_OK);
} else {
    report(last_disconnect_reason()); // app shows why
    // stay in provisioning mode, keep old creds
}

5. WHAT GOES WRONG IF…

…the SoftAP uses an open network and plain HTTP. Anyone within range sniffs the home Wi-Fi password. Use WPA2 on the SoftAP with a per-device password from the label, or BLE with a PoP-authenticated session.
Provisioning gets the SSID and password into a device with no UI. The robust modern choice is BLE provisioning: the app scans a QR code containing a proof-of-possession, establishes an encrypted session with a key exchange bound to that PoP, sends the credentials, and the device verifies them by actually connecting and reports a specific failure reason before committing them to encrypted NVS. SoftAP works too if the AP is secured, while SmartConfig-style broadcast encoding is convenient but weak and unreliable.

802.15.4, Thread, Zigbee and Matter

INTERMEDIATE▶

1. WHAT IS IT?

IEEE 802.15.4 is a low-power 2.4 GHz radio standard with small frames. Zigbee and Thread are two different network layers built on it that form mesh networks, where mains-powered devices relay messages for others. Matter is an application layer (common device language) that runs over IP — on Thread, Wi-Fi or Ethernet — so a light bulb works with Apple Home, Google Home and Alexa at once.

2. TERMS

802.15.4 PHY
2.4 GHz, O-QPSK, 250 kbps, 16 channels (11–26), maximum frame 127 bytes.
6LoWPAN
IPv6 over Low-power WPAN: compresses IPv6/UDP headers and fragments packets to fit 127-byte frames.
Thread roles
Leader (one per network, manages router IDs), Router (up to 32, forward traffic), REED (Router-Eligible End Device), End Device: MED (always-on RX), SED (Sleepy End Device, polls its parent), SSED (synchronised sleepy, CSL).
Border Router
connects the Thread mesh to Wi-Fi/Ethernet IP networks (an Apple TV or HomePod mini acts as one).
Zigbee
own non-IP network layer; roles Coordinator, Router, End Device; application data model ZCL (Zigbee Cluster Library), e.g. On/Off cluster 0x0006.
Matter
data model of endpoints → clusters → attributes/commands/events (derived from ZCL), secure commissioning, multi-admin fabrics.

3. MATTER COMMISSIONING OVER BLE + THREAD, STEP BY STEP

  1. User scans the device's QR code (contains discriminator + 27-bit setup passcode).
  2. Phone connects over BLE and runs PASE (Passcode-Authenticated Session Establishment, SPAKE2+) using the passcode → encrypted session.
  3. Device attestation: phone reads the Device Attestation Certificate (DAC), chained to a Product Attestation Intermediate (PAI) and Authority (PAA), and checks it is a certified genuine product.
  4. Phone sends a CSR request; the commissioner's fabric CA issues a NOC (Node Operational Certificate) for this fabric.
  5. Phone sends the Thread network credentials (operational dataset) over the PASE session; device joins the mesh via the border router.
  6. From now on, controllers talk to it over IPv6 with CASE (Certificate-Authenticated Session Establishment) sessions. A second ecosystem can be added as another fabric (multi-admin).
Why header compression matters: IPv6 header 40 B + UDP 8 B = 48 B. 802.15.4 frame: 127 B max − MAC header (~9–23 B) − MIC (4–16 B) − FCS 2 B leaves roughly 81–102 B. Without compression half the frame would be headers. 6LoWPAN IPHC typically squeezes IPv6+UDP to ~6–10 B when addresses derive from link-layer addresses, leaving ~75–90 B for the Matter message.
Time on air: 127-byte frame + 6-byte PHY header = 133 B × 32 µs/byte (250 kbps) = 4.26 ms — compare 0.3 ms for a 27-byte BLE packet.

4. CODE: A SLEEPY END DEVICE POLL PERIOD (OpenThread)

otLinkModeConfig mode = {
    .mRxOnWhenIdle = false,     // sleepy: radio off between polls
    .mDeviceType   = false,     // minimal Thread device (not FTD)
    .mNetworkData  = false,     // only stable network data subset
};
otThreadSetLinkMode(instance, mode);
otLinkSetPollPeriod(instance, 30000);  // ask parent for queued data every 30 s
// downlink latency = up to 30 s; parent buffers frames meanwhile

5. WHAT GOES WRONG IF…

…a battery sensor is configured as a router. Routers must keep their receiver on to forward traffic: a coin cell lasts days. Battery devices must be SEDs/SSEDs; mains devices (bulbs, plugs) act as routers.
…someone switches off all the smart bulbs at the wall. They were the mesh routers; sleepy sensors lose their parents and the network partitions until power returns. Classic Zigbee/Thread installation issue.
  Phone/Hub ── Wi-Fi/Ethernet ── [Border Router] ))) R ─── R ─── R
                                                    │     │      └─ SED (sensor, polls)
                                                    SED   R ─ SED
  Matter = app layer over IPv6 · Thread = IPv6 mesh · 802.15.4 = radio
802.15.4 is a 250 kbps, 127-byte-frame radio at 2.4 GHz. Zigbee builds its own non-IP mesh and ZCL clusters on it; Thread builds an IPv6 mesh using 6LoWPAN compression, with routers that keep their radios on, sleepy end devices that poll a parent, and border routers bridging to Wi-Fi. Matter is the application layer on top of IP that unifies ecosystems: commissioning over BLE with a SPAKE2+ passcode session, attestation with a device certificate, then an operational certificate per fabric and CASE sessions, so one device can belong to Apple, Google and Amazon at once.

Cellular IoT: LTE Cat-1, LTE-M and NB-IoT

BEGINNER▶

1. WHAT IS IT?

Cellular IoT uses the mobile operators' LTE network, so a device works anywhere there is coverage with no local gateway. Because phones' LTE is overkill for a meter sending 100 bytes a day, 3GPP defined cheaper, lower-power device categories. The module (e.g. Quectel EC200U for Cat-1, BG95/BG77 for LTE-M/NB-IoT) contains the modem; your MCU talks to it over UART with AT commands.

2. TERMS

UE
User Equipment: the device (module) in 3GPP language. The base station is the eNB.
LTE Cat-1
Category 1: up to 10 Mbps down / 5 up, full LTE bandwidth (up to 20 MHz), full mobility, low latency. Cat-1 bis = single antenna variant. Good replacement for 2G/3G.
LTE-M (Cat-M1)
1.4 MHz bandwidth, ~1 Mbps peak, supports mobility/handover and VoLTE, PSM/eDRX, coverage enhancement (~+15 dB).
NB-IoT (Cat-NB1/NB2)
180 kHz (one LTE resource block), ~26 kbps (NB1) to ~127 kbps (NB2) down, no connected-mode handover, deepest coverage (+20 dB, MCL 164 dB), high latency (seconds).
RRC
Radio Resource Control state: CONNECTED (radio link active, high current) or IDLE (just listening to paging).
Attach / PDP context
registering with the core network and getting an IP bearer (APN = Access Point Name selects it).
CE level
Coverage Enhancement: repetitions of each transmission (up to 2048× in NB-IoT) to reach deep indoor devices, at the cost of airtime and energy.

3. LIFE OF A REPORT, STEP BY STEP

  1. Module powers on (PWRKEY pulse), sends RDY, checks SIM (+CPIN: READY).
  2. Scans bands, finds a cell, attaches and registers: +CEREG: 1 (home) or 5 (roaming).
  3. Activates a PDP context on the APN → gets an IP.
  4. Opens TCP/TLS to the server, sends data → RRC CONNECTED at tens to hundreds of mA.
  5. After the network's RRC inactivity timer (often 10–20 s, operator-controlled) the eNB releases the connection → RRC IDLE, listening for paging every DRX cycle (1.28 or 2.56 s), ~1–3 mA average.
  6. With PSM granted, after the active timer the module enters PSM: µA, unreachable until its next uplink or periodic TAU (next card).
Daily energy for one 200-byte report on LTE-M (illustrative numbers — measure your own module/network):
CONNECTED transfer 3 s × 100 mA = 300 mC; RRC tail 10 s × 15 mA = 150 mC; total ≈ 450 mC = 0.125 mAh per report.
Idle in DRX the rest of the day: 1.2 mA × 24 h = 28.8 mAh/day — dominates if you never reach PSM.
With PSM at 5 µA: 0.12 mAh/day. One report/hour = 24 × 0.125 = 3 mAh + 0.12 ≈ 3.1 mAh/day → 2400 mAh pack ≈ 2 years. The Cellular & RF Calc tab does this for you.

4. WHAT GOES WRONG IF…

…you choose a module by peak data rate only. A Cat-4 module in a parking sensor idles at several mA and has no PSM; the battery dies in weeks. Categories are about power states and coverage as much as speed.
…LTE-M/NB-IoT is not deployed in the target country (or the operator disabled roaming on it). The device never registers. Check operator coverage maps and roaming agreements; many designs use multi-mode modules (LTE-M + NB-IoT + 2G fallback, e.g. Quectel BG95-M3).

Cellular IoT trades speed for power and coverage. Cat-1 gives up to 10 Mbps with full mobility and is the usual 2G/3G replacement for mains-powered devices; LTE-M uses 1.4 MHz, around 1 Mbps, keeps mobility and adds PSM, eDRX and about 15 dB of coverage enhancement; NB-IoT uses 180 kHz, tens of kbps, no connected-mode handover, but reaches the deepest indoor locations at 164 dB coupling loss. Battery life is dominated not by the transmission but by the RRC inactivity tail and whether the device idles in DRX or gets into PSM.

PSM and eDRX: T3412, T3324, paging cycles

ADVANCED▶

1. WHAT IS IT?

Even when idle, an LTE device must wake every paging cycle (1.28–2.56 s) to check whether the network is calling it. PSM (Power Saving Mode) lets it stop listening entirely for hours while staying registered; eDRX (extended Discontinuous Reception) stretches the paging cycle to tens of seconds to hours. Both are requested by the device and granted (or not, or modified) by the network.

2. TERMS

TAU
Tracking Area Update: a periodic "I'm still here" message to the network.
T3412 (extended)
periodic TAU timer: how long until the device must report in. With PSM it can be up to 413 days (320 h × 31).
T3324
Active Time: how long the device stays in idle (reachable by paging) after leaving RRC CONNECTED, before entering PSM.
PSM
device keeps its registration and IP context but turns off the receiver; it cannot be paged until it wakes. Current ≈ a few µA (module dependent).
eDRX cycle
long paging cycle (LTE-M 5.12 s to 2621.44 s; NB-IoT 20.48 s to 10485.76 s). Device listens during a PTW (Paging Time Window) of normal DRX cycles, then sleeps until the next eDRX cycle.
AT+CPSMS / AT+CEDRXS
3GPP 27.007 commands to request PSM timers and eDRX values.

3. HOW PSM WORKS, STEP BY STEP

  1. Device requests timers in its Attach/TAU Request (via AT+CPSMS=1,,,"T3412","T3324").
  2. Network replies with the granted values in Attach/TAU Accept — possibly different, possibly no PSM at all.
  3. After an uplink and the RRC release, the device idles for T3324 (reachable for server replies/commands).
  4. T3324 expires → PSM. Radio off. The network keeps the context.
  5. Device wakes on its own (MCU wants to send) or when T3412 expires (sends TAU). No re-attach needed: much cheaper than a fresh power-on.
  6. Firmware must read back what was granted: AT+CEREG=4 makes +CEREG report include the granted Active-Time and Periodic-TAU bit strings.

Bits 5-1 hold the multiplier 0–31. Value = unit × multiplier.

Want TAU every 24 h: unit 1 h = 001, multiplier 24 = 11000 → "00111000".
Want active time 60 s: unit 2 s = 000, multiplier 30 = 11110 → "00011110" (or 1 min × 1 = "00100001").

Network answers in +CEREG: 4,1,"1A2B","01A2B3C4",7,,,"00000101","00100110" → Active-Time 00000101 = 2 s × 5 = 10 s (not 60!), Periodic-TAU 00100110 = 1 h × 6 = 6 h (not 24!). The network shortened both; your power model must use the granted values.
eDRX LTE-M 81.92 s = value 0101: AT+CEDRXS=1,4,"0101" (4 = E-UTRAN WB-S1 i.e. LTE-M; 5 = NB-S1 i.e. NB-IoT).

5. CODE: ENCODER + CHECK (WRONG vs RIGHT)

✖ WRONG — set and forget
at_cmd("AT+CPSMS=1,,,\"00111000\",\"00011110\"");
// assume PSM works; product spec claims
// 5-year battery life based on 5 µA sleep
✔ RIGHT — encode, request, verify granted
/* T3412 ext: units in seconds, index = bits 8-6 */
static const uint32_t u3412[7] = {600, 3600, 36000, 2, 30, 60, 1152000};
void enc_t3412(uint32_t sec, char out[9]) {
    int best = -1; uint32_t bv = 0, berr = UINT32_MAX;
    for (int u = 0; u < 7; u++) {
        uint32_t m = (sec + u3412[u] - 1) / u3412[u];  // round up
        if (m > 31) continue;
        uint32_t err = m * u3412[u] - sec;
        if (err < berr) { berr = err; best = u; bv = m; }
    }
    uint8_t b = (uint8_t)((best << 5) | bv);           // unit | multiplier
    for (int i = 0; i < 8; i++) out[i] = (b & (0x80 >> i)) ? '1' : '0';
    out[8] = 0;
}
/* after registration: */
at_cmd("AT+CEREG=4");                // URCs/reads include granted timers
psm_t g = parse_cereg_timers();      // active, tau or "not granted"
if (!g.granted) telemetry_flag(PSM_NOT_GRANTED); // fallback plan

6. WHAT GOES WRONG IF…

…the network does not grant PSM. Symptom: lab units (on a test SIM/network) last 5 years on paper, field units die in 3 months; current probe shows a steady ~1–2 mA with DRX spikes every 1.28 s. Fix: verify the granted timers in firmware and report them in telemetry; fall back to powering the modem down completely (PWRKEY off) between infrequent reports, accepting the cost of a full attach.
…the server sends a command while the device is in PSM. It cannot be paged; the command waits (or is lost) until the device's next uplink. Design for "device pulls": the server queues commands and the device checks after each uplink, within the T3324 window.
uplink ─► RRC CONNECTED ─► RRC IDLE (DRX) ──T3324──► PSM (µA) ──────── T3412 ───► TAU / next uplink
          [mA×s]          [paging every 1.28 s]     [unreachable]
eDRX alt: IDLE ─► PTW: ▲ ▲ ▲ ─── sleep ─── PTW: ▲ ▲ ▲ ─── sleep ─── (reachable once per eDRX cycle)
PSM lets an LTE-M or NB-IoT device stay registered but stop listening: after an uplink it stays reachable for the active time T3324, then sleeps at microamps until its next uplink or until the periodic TAU timer T3412 expires. eDRX instead stretches the paging cycle, so the device is reachable every eDRX cycle with a short paging window. Both are only requests in AT+CPSMS and AT+CEDRXS; the network decides, so firmware must read the granted values, for example with AT+CEREG=4, and the product must have a plan when PSM is not granted.

AT commands, final result codes and URCs

INTERMEDIATE▶

1. WHAT IS IT?

Most cellular (and many Wi-Fi/BLE) modules are controlled over a UART with text AT commands. The MCU sends a command, the module answers with zero or more information lines and then a final result code. Unfortunately the module may also send unsolicited lines at any moment — even in the middle of a response. A robust AT parser is a classic interview whiteboard question.

2. TERMS

Command
text starting with AT, ended by \r (CR). E.g. AT+CSQ\r.
Information response
line(s) belonging to the command, usually prefixed with the command name: +CSQ: 18,99.
Final result code
ends the command: OK, ERROR, +CME ERROR: <n>, +CMS ERROR: <n>; some commands end with SEND OK, SEND FAIL, NO CARRIER, CONNECT.
URC
Unsolicited Result Code: a line the module sends on its own, e.g. RDY, +CEREG: 5, +QIURC: "recv",0, +QIOPEN: 0,0, RING.
Echo
modules echo the command back unless you send ATE0.
Prompt
for data-sending commands (Quectel AT+QISEND) the module answers > without CR/LF, then waits for the raw bytes.

3. HOW A ROBUST PARSER WORKS, STEP BY STEP

  1. A UART RX interrupt/DMA pushes bytes into a ring buffer; one parser task consumes it (never parse in the ISR).
  2. The parser assembles lines terminated by \r\n, skipping empty lines.
  3. Special cases before line assembly: the > prompt (no CRLF) when a send command is pending; and length-prefixed binary data (e.g. after +QIRD: 12 read exactly 12 raw bytes, even if they contain "OK\r\n").
  4. Classify each complete line: (a) final result code → completes the pending command; (b) line starting with the pending command's expected prefix → response data; (c) line matching the URC table → dispatch to its handler whether or not a command is pending; (d) anything else → log as unexpected.
  5. Only one command is in flight at a time (protected by a mutex). Each command has its own timeout: AT 300 ms, AT+COPS=? up to 180 s, Quectel AT+QIOPEN up to 150 s.
  6. Asynchronous results arrive as URCs: AT+QIOPEN returns OK immediately and the real result comes later as +QIOPEN: 0,0 (socket 0, error 0).
Byte stream after sending AT+CSQ\r:
\r\n+CSQ: 18,99\r\n\r\n+QIURC: "closed",0\r\n\r\nOK\r\n
Robust: line 1 matches pending prefix "+CSQ:" → response (RSSI −77 dBm); line 2 matches URC "+QIURC:" → socket 0 closed callback; line 3 "OK" → command complete.
Naive (collect everything until OK): response = 2 lines; code takes the last line before OK and fails to parse; the "closed" event is lost; the app keeps writing to a dead socket.

4. CODE: LINE CLASSIFIER (WRONG vs RIGHT)

✖ WRONG — everything before OK is "the response"
int at_send(const char *cmd, char *resp, size_t n) {
    uart_write(cmd);
    resp[0] = 0;
    for (;;) {
        char line[128];
        uart_readline(line, sizeof line);   // blocks on '\n'
        if (strstr(line, "OK"))  return 0;  // "SEND OK", data "OK"…
        if (strstr(line, "ERROR")) return -1;
        strncat(resp, line, n);             // URCs swallowed here
    }   // no timeout; '>' prompt never ends a line → hangs
}
✔ RIGHT — classify each line
typedef void (*urc_fn)(const char *line);
static const struct { const char *pfx; urc_fn fn; } urcs[] = {
    {"+QIURC:", on_qiurc}, {"+QIOPEN:", on_qiopen},
    {"+CEREG:", on_cereg}, {"RDY", on_rdy}, {"+CPIN:", on_cpin},
};
static bool is_final(const char *l, int *rc) {
    if (!strcmp(l, "OK") || !strcmp(l, "SEND OK")) { *rc = 0; return true; }
    if (!strcmp(l, "ERROR") || !strcmp(l, "SEND FAIL")) { *rc = -1; return true; }
    if (!strncmp(l, "+CME ERROR:", 11)) { *rc = -atoi(l + 11) - 1000; return true; }
    return false;
}
void on_line(const char *l) {
    int rc;
    if (pending && is_final(l, &rc)) { complete(pending, rc); return; }
    if (pending && pending->pfx && !strncmp(l, pending->pfx, strlen(pending->pfx))) {
        pending->on_resp(l);                      // belongs to the command
        return;
    }
    for (size_t i = 0; i < ARRAY_SIZE(urcs); i++)
        if (!strncmp(l, urcs[i].pfx, strlen(urcs[i].pfx))) { urcs[i].fn(l); return; }
    log_warn("unexpected: %s", l);
}

Exact string compare for final codes (not strstr), prefix-first for responses, URCs handled any time. The MQTT & AT Lab tab animates this byte by byte against a naive parser.

5. WHAT GOES WRONG IF…

…the parser runs in the UART ISR. String compares and callbacks in interrupt context delay other interrupts and make URC handlers unable to block or send commands. ISR → ring buffer → task.
…a URC handler sends an AT command synchronously. It is called from the parser task, which is the task that would have to read the reply → deadlock. Handlers post events to the application task.
UART RX ─ISR/DMA─► ring buffer ─► parser task ─┬─ final code  ─► complete(pending cmd) ─► wake caller
                                               ├─ resp prefix ─► pending->on_resp()
                                               ├─ URC prefix  ─► post event to app queue
                                               └─ '>' / +QIRD: n ─► raw mode (prompt / n bytes)
An AT command produces zero or more information lines and then a final result code like OK, ERROR or +CME ERROR, but URCs can arrive at any time, including in the middle of a response. So I put received bytes into a ring buffer from the ISR and run a parser task that assembles lines and classifies each one: final code completes the single pending command, a line with the pending command's prefix is its response, a known URC prefix is dispatched to a handler, and I special-case the send prompt without CRLF and length-prefixed binary reads. Each command has its own timeout, and URC handlers only post events so they never deadlock the parser.

PPP vs the module's internal TCP/IP stack, CMUX, SIM and eSIM

ADVANCED▶

1. WHAT IS IT?

Once the cellular module has an IP connection, who runs TCP and TLS? Either the module (you use vendor AT commands like AT+QIOPEN / AT+QSSLOPEN), or the MCU (the module becomes a modem carrying IP packets over PPP, and your MCU runs lwIP + mbedTLS). This is a key architecture decision for any cellular product.

2. TERMS

PPP
Point-to-Point Protocol: frames IP packets over a serial line. Started with ATD*99# (or AT+CGDATA); module answers CONNECT and switches the UART to data mode.
Internal stack
the module's own TCP/IP and TLS, exposed via AT commands; data moves through AT command payloads.
CMUX
3GPP TS 27.010 multiplexer: several virtual serial channels over one UART, so you can run PPP on one channel and AT commands (signal quality, SMS) on another.
Transparent mode
vendor mode where the UART carries one socket's raw bytes; leave it with +++ surrounded by ≥1 s guard time.
UICC / eUICC
the SIM card platform / an embedded SIM whose operator profiles can be downloaded remotely.
MFF2
soldered SIM package (5 × 6 mm), vibration-proof, for industrial devices.

5. SIM AND eSIM

  1. Plastic SIM in a holder: cheap, swappable, but contacts fret under vibration (vehicles) → intermittent +CPIN: NOT READY.
  2. MFF2 soldered SIM: robust, industrial temperature range.
  3. eUICC (eSIM): profiles downloaded over the air. M2M standard SGP.02 (operator-driven, SMS-based push); newer IoT standard SGP.32 lets the device's own manager fetch profiles — avoiding lock-in to one operator for a 10-year product.
  4. Firmware duties: SIM detect pin, PIN handling (AT+CPIN), ICCID reporting (AT+QCCID), handling "SIM removed" URCs, and roaming permission settings.
What goes wrong if the AT parser keeps reading after CONNECT: PPP frames start with 0x7E and contain arbitrary bytes, including 0x0D 0x0A. The parser produces garbage "lines" and the PPP negotiation never completes (LCP timeout). The UART must have exactly one owner per mode.
With the module's internal stack I use vendor socket and SSL AT commands, which saves MCU RAM and flash but ties me to that vendor's command set and its TLS implementation and cert storage. With PPP the module just carries IP packets, my MCU runs lwIP and mbedTLS with standard sockets and full control of keys, at the cost of 100 kB-plus of footprint, and I need CMUX or a second port to keep issuing AT commands while connected. For SIMs in industrial devices I prefer soldered MFF2, and eSIM with SGP.32 to avoid operator lock-in.

LoRa and LoRaWAN: spreading factor, ADR, classes A/B/C, duty cycle

INTERMEDIATE▶

1. WHAT IS IT?

LoRa is a sub-GHz radio modulation (Semtech) that trades data rate for enormous range: kilometres from a few tens of milliwatts. LoRaWAN is the network protocol on top: devices broadcast uplinks, any gateway in range forwards them to a network server, which de-duplicates, decrypts and passes data to your application.

2. TERMS

CSS
Chirp Spread Spectrum: each symbol is a frequency sweep ("chirp") across the bandwidth.
SF
Spreading Factor 7–12: each symbol carries SF bits and lasts 2^SF / BW seconds. One SF step ≈ doubles airtime and gains ~2.5 dB sensitivity.
BW
bandwidth, usually 125 kHz.
CR
Coding Rate 4/5 to 4/8, forward error correction overhead.
ADR
Adaptive Data Rate: network server tells each device which SF/TX power to use based on its received SNR history.
Class A / B / C
A: device can only receive in two short windows (RX1 1 s, RX2 2 s) after each uplink — lowest power. B: additional scheduled ping slots synchronised to gateway beacons. C: receiver always on (mains powered).
Duty cycle
EU868 regulation: a device may transmit at most 1 % of the time per sub-band (36 s per hour).
OTAA / ABP
Over-The-Air Activation (join with DevEUI, JoinEUI, AppKey → session keys) vs Activation By Personalisation (keys pre-programmed, frame counters must persist).

3. TIME ON AIR, STEP BY STEP (Semtech formula)

  1. Symbol time T_sym = 2^SF / BW.
  2. Preamble time = (n_preamble + 4.25) × T_sym (8 preamble symbols in LoRaWAN).
  3. Payload symbols = 8 + max(ceil((8·PL − 4·SF + 28 + 16·CRC − 20·IH) / (4·(SF − 2·DE))) × (CR + 4), 0), where PL = PHY payload bytes, CRC = 1, IH = 0 (explicit header), DE = 1 (low data rate optimisation) when T_sym ≥ 16 ms (SF11/12 at 125 kHz), CR = 1 for 4/5.
  4. ToA = preamble + payload symbols × T_sym.
PL = 20 bytes (LoRaWAN header 13 + 7 app bytes), BW 125 kHz, CR 4/5.
SF7: T_sym = 128 / 125 000 = 1.024 ms. Preamble 12.25 × 1.024 = 12.54 ms. (160 − 28 + 28 + 16) / 28 = 6.29 → 7 × 5 = 35 → 43 symbols = 44.03 ms. ToA = 56.6 ms.
SF12 (DE=1): T_sym = 4096 / 125 000 = 32.77 ms. Preamble 401.4 ms. (160 − 48 + 28 + 16) / 40 = 3.9 → 4 × 5 = 20 → 28 symbols = 917.5 ms. ToA = 1318.9 ms — 23× longer.
1 % duty cycle = 36 s per hour → SF12: 36 / 1.319 = 27 uplinks/hour; SF7: 636/hour. The Things Network fair-use policy (30 s/day uplink airtime) → SF12: only 22 per day.
Sensitivity (SX1276, 125 kHz): SF7 −123 dBm … SF12 −137 dBm = 14 dB more link budget, roughly 2.5× range at n = 3.5.

4. CODE: DUTY-CYCLE GATE (WRONG vs RIGHT)

✖ WRONG — send whenever data is ready
void on_alarm(void) {
    lmic_send(payload, 20);   // burst of retries at SF12
                              // violates 1 % → illegal in EU,
                              // gateway/network may drop
}
✔ RIGHT — account airtime per sub-band
static uint32_t next_ok_ms[NUM_SUBBANDS];
bool can_send(int sb, uint32_t now, uint32_t toa_ms) {
    return (int32_t)(now - next_ok_ms[sb]) >= 0;
}
void mark_sent(int sb, uint32_t now, uint32_t toa_ms) {
    next_ok_ms[sb] = now + toa_ms * 99;  // 1 %: off-time = 99 × ToA
}
// SF12, 1319 ms ToA → wait 130.6 s on that sub-band

(Production stacks — LoRaMac-node, LMIC — implement this; the point is to know why your uplink is "delayed".)

5. WHAT GOES WRONG IF…

…ADR is enabled on a moving device. ADR assumes a stable link; the server lowers SF while the device is near a gateway, the device moves away, and every uplink is lost until it falls back. Disable ADR (or use the device-side backoff) for mobile assets.
…an ABP device resets its frame counter to 0 after a reboot. The network server rejects the replayed counters as a security measure: the device goes silent. Persist counters in NVM or use OTAA (new session keys and counters at join).
freq ▲   ╱│  ╱│  ╱│        up-chirps (preamble), then data chirps with
     │  ╱ │ ╱ │ ╱ │         cyclic shifts that encode SF bits per symbol
     │ ╱  │╱  │╱  │
     └───────────────► time   T_sym = 2^SF / BW
LoRa spreads each symbol into a chirp; the spreading factor 7 to 12 sets how long a symbol lasts, 2 to the SF over bandwidth, so each SF step doubles airtime and buys about 2.5 dB, letting SF12 decode 20 dB below the noise floor. LoRaWAN adds a star-of-stars network where gateways forward to a network server, ADR to pick SF per device, and classes A, B and C trading downlink availability for power. In Europe the 1 % duty cycle matters: a 20-byte uplink at SF12 takes 1.3 seconds, so you get only about 27 per hour.

MQTT basics: broker, CONNECT, keep-alive, clean session, retained, LWT

BEGINNER▶

1. WHAT IS IT?

MQTT (Message Queuing Telemetry Transport) is a small publish/subscribe protocol over TCP. Devices do not talk to each other directly; they all keep one connection to a broker (AWS IoT Core, Mosquitto, EMQX, HiveMQ). A device publishes messages to a named topic; anyone subscribed to that topic receives them. Because the device opens the connection outward, it works behind NAT and firewalls — ideal for cellular and home Wi-Fi.

2. TERMS

Client ID
unique name of the connection. A second connection with the same ID kicks the first one off (the broker's takeover rule).
Keep-alive
seconds the client promises not to be silent longer than. If nothing else is sent it sends PINGREQ; the broker replies PINGRESP. The broker disconnects a client silent for 1.5 × keep-alive.
Clean Session (3.1.1) / Clean Start + Session Expiry (5.0)
whether the broker keeps the client's subscriptions and queued QoS 1/2 messages while it is offline.
Retained message
the broker stores the last message with the retain flag per topic and immediately gives it to new subscribers ("last known state").
LWT
Last Will and Testament: a message registered at CONNECT that the broker publishes if the client disappears without a clean DISCONNECT.
Fixed header
every MQTT packet starts with 1 byte type/flags + 1–4 bytes "remaining length". A PINGREQ is just 2 bytes: C0 00.

3. A DEVICE SESSION, STEP BY STEP

  1. TCP connect, then TLS handshake (port 8883).
  2. Send CONNECT: client ID stn-0042, keep-alive 60 s, clean session 0, will topic fleet/stn-0042/status payload {"online":false} retained.
  3. Broker replies CONNACK (return code 0 = accepted; session-present flag says whether old state was kept).
  4. Publish {"online":true} retained to the same status topic (overwrites the will's message for new subscribers).
  5. SUBSCRIBE to fleet/stn-0042/cmd/#; broker replies SUBACK with the granted QoS.
  6. Exchange PUBLISH messages. If idle for 60 s, send PINGREQ.
  7. Power loss: no DISCONNECT; after 1.5 × 60 = 90 s of silence the broker publishes the will → dashboards show "offline".
Overhead of a QoS 0 PUBLISH of 20 bytes to topic fleet/stn-0042/telemetry (24 chars): fixed header 2 B + topic length 2 B + topic 24 B + payload 20 B = 48 B of MQTT, plus TLS record overhead (~29 B with AES-GCM in TLS 1.2: 5 header + 8 explicit nonce + 16 tag) plus TCP/IP 40 B → ~117 B on the wire for 20 B of data. Short topics (or MQTT 5 topic aliases) matter on metered cellular links.
Keep-alive cost on LTE-M: a PINGREQ every 60 s wakes the radio 1440 times/day → kills PSM. Battery devices use long keep-alives (e.g. 1200 s, the AWS IoT maximum) or disconnect between reports.

4. CODE: CONNECT OPTIONS (WRONG vs RIGHT)

✖ WRONG
cfg.client_id   = "esp32";        // same on every unit!
cfg.keepalive   = 5;              // radio never sleeps
cfg.clean_session = true;         // queued cmds lost offline
// no LWT → server can't tell offline from quiet
✔ RIGHT (esp-mqtt style)

  .broker.address.uri = "mqtts://xxxx-ats.iot.ap-south-1.amazonaws.com",
  .credentials.client_id = thing_name,          // unique per device
  .session.keepalive = 300,                     // s; broker drops at 450 s
  .session.disable_clean_session = true,        // persistent session
  .session.last_will = {
      .topic = "fleet/stn-0042/status",
      .msg = "{\"online\":false}", .qos = 1, .retain = 1 },
};

5. WHAT GOES WRONG IF…

…two devices share a client ID (copied config, cloned flash image). Each connection kicks the other off: both reconnect, both kick again. Symptom: endless connect/disconnect loop every few seconds, broker logs "duplicate client ID". Derive client ID from a unique hardware ID / thing name.
…keep-alive is longer than a NAT timeout. Many cellular carrier NATs drop idle TCP mappings after a few minutes. The device thinks it is connected; downlink messages never arrive. Keep-alive must be shorter than the path's NAT idle timeout — measure it per operator.
device ──TCP/TLS──► BROKER ◄──TCP/TLS── app / dashboard
  PUBLISH fleet/stn-0042/telemetry ─►│─► to every subscriber of fleet/+/telemetry
  ◄─ PUBLISH fleet/stn-0042/cmd/reboot ◄─ published by backend
MQTT is publish-subscribe over a single outbound TCP or TLS connection to a broker, which suits NATed cellular and Wi-Fi devices. The CONNECT carries a unique client ID, a keep-alive — the broker drops a client silent for one and a half times it — a clean-session flag that decides whether subscriptions and queued messages survive disconnects, and a last will the broker publishes if the device vanishes. Retained messages give new subscribers the last known state, so a retained online flag plus a retained will of offline is the classic presence pattern.

MQTT QoS 0, 1 and 2: the packet flows and the duplicate problem

INTERMEDIATE▶

1. WHAT IS IT?

QoS (Quality of Service) is the delivery promise for one hop — sender to broker, or broker to subscriber. QoS 0 = at most once (may be lost). QoS 1 = at least once (never lost while the session lives, but may be duplicated). QoS 2 = exactly once (a 4-packet handshake removes duplicates on that hop).

2. TERMS

Packet Identifier
16-bit ID (1–65535) in QoS 1/2 PUBLISH, used to match acknowledgements.
PUBACK
QoS 1 acknowledgement.
PUBREC / PUBREL / PUBCOMP
QoS 2: publish received → publish release → publish complete.
DUP flag
set on a re-sent PUBLISH. Informational only — the receiver cannot rely on it to dedup at QoS 1.
Effective QoS
broker → subscriber uses min(publisher's QoS, subscription QoS).

3. THE FLOWS, STEP BY STEP

  1. QoS 0: PUBLISH → done. No ID, no storage, no retry.
  2. QoS 1: sender stores the message, sends PUBLISH(id=7). Receiver processes it and sends PUBACK(7). Sender deletes it. If the PUBACK never arrives, the sender re-sends PUBLISH(id=7, DUP=1) — in MQTT 3.1.1/5 only after reconnecting with a persistent session. The receiver must treat it as a new message → duplicate.
  3. QoS 2: PUBLISH(7) → receiver stores "id 7 seen" and delivers it, replies PUBREC(7) → sender (now knows it was received) sends PUBREL(7) → receiver forgets id 7, replies PUBCOMP(7). A re-sent PUBLISH(7) while "id 7 seen" is stored is not delivered again.
  4. Retries happen on reconnect with Clean Session = 0 / Clean Start = 0. With a clean session the in-flight state is discarded — QoS guarantees only exist inside one session.
Command "start charging slot 3" sent broker → device at QoS 1 on cellular:
t=0 s broker sends PUBLISH(id 42). Device executes, sends PUBACK. The cell drops before PUBACK reaches the broker.
t=95 s device reconnects (session present = 1). Broker re-sends PUBLISH(id 42, DUP=1). Device executes again → slot 3 started twice (or a "toggle" command toggles back!).
Fix: each command carries an application-level cmd_id; device keeps the last N executed IDs (in RAM + flash) and skips repeats. QoS 2 would remove the duplicate on this hop, but not if the device crashes after executing and before saving state, and not on the backend → broker hop — end-to-end idempotency is still needed.

4. CODE: IDEMPOTENT COMMAND HANDLER (WRONG vs RIGHT)

✖ WRONG
void on_cmd(const char *topic, const cmd_t *c) {
    if (c->op == OP_TOGGLE_RELAY)
        relay_toggle(c->slot);   // dup → toggles back
}
✔ RIGHT
#define SEEN_N 32
static uint32_t seen[SEEN_N]; static unsigned seen_i;
static bool already_done(uint32_t id) {
    for (unsigned i = 0; i < SEEN_N; i++) if (seen[i] == id) return true;
    return false;
}
void on_cmd(const char *topic, const cmd_t *c) {
    if (already_done(c->cmd_id)) {       // duplicate delivery
        publish_ack(c->cmd_id, ACK_DUP); // re-ack, do nothing
        return;
    }
    relay_set(c->slot, c->state);        // absolute, not toggle
    seen[seen_i++ % SEEN_N] = c->cmd_id;  // (persist if it must survive reset)
    publish_ack(c->cmd_id, ACK_OK);
}

5. WHAT GOES WRONG IF…

…you use QoS 2 everywhere "to be safe". 4 packets per message (2 round trips) and broker state per in-flight message; on NB-IoT with 1–2 s RTT that is 2–4 s per message. And many brokers (AWS IoT Core included) do not support QoS 2 at all. Use QoS 1 + idempotency.
QoS1: S ─PUBLISH(7)─► R   (R delivers)        QoS2: S ─PUBLISH(7)─► R (store 7, deliver)
      S ◄──PUBACK(7)── R                            S ◄──PUBREC(7)── R
      lost? → reconnect, PUBLISH(7,DUP) → DELIVERED AGAIN   S ─PUBREL(7)─► R (forget 7)
                                                    S ◄─PUBCOMP(7)── R
QoS 0 is fire and forget, QoS 1 is at least once with PUBLISH and PUBACK, and QoS 2 is exactly once on that hop with the PUBLISH, PUBREC, PUBREL, PUBCOMP handshake where the receiver remembers the packet ID until PUBREL. With QoS 1 a lost PUBACK means the message is re-sent with DUP set after reconnect and delivered again, so commands must be idempotent: I give each command an ID, keep a table of executed IDs and make actions absolute rather than toggles. QoS applies per hop and only within a persistent session, so even QoS 2 does not replace end-to-end idempotency.

MQTT topic design for a fleet

INTERMEDIATE▶

1. WHAT IS IT?

Topic names are the API of an MQTT system. A good hierarchy lets the backend subscribe to "all telemetry from all devices" with one wildcard, lets the broker's access policy say "a device may only publish under its own name", and lets you evolve the payload format without breaking old devices.

2. TERMS

Level
part between slashes: fleet/v1/stn-0042/telemetry has 4 levels.
+
single-level wildcard (subscriptions only): fleet/v1/+/telemetry.
#
multi-level wildcard, last level only: fleet/v1/stn-0042/#.
$-topics
topics starting with $ are reserved by the broker ($SYS/…, AWS $aws/things/<name>/shadow/…).
Policy variable
AWS IoT policies can use ${iot:Connection.Thing.ThingName} so one policy restricts each device to its own topics.

3. DESIGN RULES, STEP BY STEP

  1. Start with a product/namespace and a version: fleet/v1/… — a v2 payload can live in parallel.
  2. Put the device ID at a fixed level so wildcards and access policies work.
  3. Separate direction: device → cloud (telemetry, event, status) and cloud → device (cmd), plus responses (cmd/<id>/ack).
  4. No leading slash (creates an empty first level), no spaces, no personal data (topics appear in logs).
  5. Keep it short on metered links; respect broker limits (AWS IoT Core: topic ≤ 256 bytes, at most 7 slashes in publish/subscribe topics).
  6. Devices never subscribe to #: they would receive every other device's traffic (and the policy should forbid it).
fleet/v1/{deviceId}/telemetry — periodic data, QoS 0 or 1
fleet/v1/{deviceId}/event/{type} — alarms (door_open, overtemp), QoS 1
fleet/v1/{deviceId}/status — retained online/offline + LWT
fleet/v1/{deviceId}/cmd/{cmdId} — commands to the device, QoS 1
fleet/v1/{deviceId}/cmd/{cmdId}/ack — result from device
Backend subscribes fleet/v1/+/telemetry and fleet/v1/+/event/#. Device stn-0042 subscribes only fleet/v1/stn-0042/cmd/+.
AWS policy resource for publish: arn:aws:iot:ap-south-1:123456789012:topic/fleet/v1/${iot:Connection.Thing.ThingName}/*.

4. CODE: TOPIC BUILDER + MATCHER

#include <stdio.h>
#include <stdbool.h>
/* build: never format user strings without bounds */
int topic_cmd_ack(char *out, size_t n, const char *dev, unsigned cmd) {
    int k = snprintf(out, n, "fleet/v1/%s/cmd/%u/ack", dev, cmd);
    return (k > 0 && (size_t)k < n) ? 0 : -1;    // truncated → error
}
/* match a topic against a filter with + and # (whiteboard classic) */
bool topic_match(const char *f, const char *t) {
    while (*f) {
        if (*f == '#') return true;                 // matches rest (incl. parent)
        if (*f == '+') {                             // skip one level in topic
            while (*t && *t != '/') t++;
            f++;
        } else {
            if (*f != *t) return false;
            f++; t++;
        }
        if (*f == '/' && f[1] == '#' && *t == 0) return true; // "a/#" matches "a"
    }
    return *t == 0;
}

5. WHAT GOES WRONG IF…

…the device ID is the last level and the message type is in the payload (fleet/telemetry/stn-0042 carrying both alarms and readings). The backend cannot subscribe to just alarms, every consumer parses every message, and you cannot give alarms QoS 1 and readings QoS 0. Put the type in the topic.
I version the namespace, put the device ID at a fixed level, and split by direction and message type, for example fleet/v1/deviceId/telemetry, event/type, a retained status topic paired with the last will, and cmd/cmdId with a matching ack topic. That lets the backend use single-level wildcards, lets the broker policy restrict each device to its own subtree with a thing-name variable, and lets me pick QoS per message type. Devices never subscribe to a bare hash, and topics stay short and free of personal data.

CoAP and HTTP(S) on constrained devices

INTERMEDIATE▶

1. WHAT IS IT?

MQTT is not the only option. CoAP (Constrained Application Protocol, RFC 7252) is "HTTP for tiny devices" over UDP: request/response with GET/POST/PUT/DELETE, but a 4-byte header and no connection to keep alive. HTTP(S) is heavy but universal — perfect for downloading firmware from a CDN.

2. TERMS

CON / NON / ACK / RST
CoAP message types: Confirmable (needs ACK, retransmitted), Non-confirmable, Acknowledgement, Reset.
Message ID
16-bit, detects duplicates and matches ACKs.
Token
0–8 bytes chosen by the client to match responses to requests.
Observe
RFC 7641 option: subscribe to a resource; the server sends a notification whenever it changes.
Block-wise
RFC 7959: transfers large bodies in blocks (16–1024 B), e.g. firmware.
DTLS
Datagram TLS, TLS adapted to UDP. LwM2M (Lightweight M2M, OMA) is a device-management standard built on CoAP + DTLS.
HTTP Range
header Range: bytes=65536- to resume a download.

3. A CoAP CONFIRMABLE REQUEST, STEP BY STEP

  1. Client sends CON POST /t with Message ID 0x7D34, token 0xA1, payload 6 bytes.
  2. If no ACK within ACK_TIMEOUT × random(1, 1.5) = 2–3 s, retransmit; double the timeout each time; up to MAX_RETRANSMIT = 4.
  3. Server replies ACK 2.04 (Changed) with the same Message ID (piggy-backed response).
  4. A retransmitted duplicate (same Message ID) is recognised by the server and answered with the same response, not processed twice.
Header bytes for CON POST, token length 1: 0x41 (version 01, type 00 CON, TKL 0001), 0x02 (code 0.02 POST), 0x7D 0x34 (Message ID), 0xA1 (token), option Uri-Path "t" 0xB1 0x74 (delta 11, length 1), payload marker 0xFF, 6 payload bytes → 14 bytes + UDP 8 + IPv4 20 = 42 bytes. The same over HTTP/1.1: request line + Host + Content-Type + Content-Length headers easily exceed 100 bytes, plus a TCP handshake.
Worst-case CoAP retry span: 2 + 4 + 8 + 16 (+ random factor up to 1.5×) ≈ 45 s (MAX_TRANSMIT_SPAN).

4. CODE: CHOOSING (WRONG vs RIGHT)

✖ WRONG — OTA image over MQTT QoS 1 at default sizes
for (off = 0; off < img_len; off += 128)
    mqtt_publish("fw/chunk", img + off, 128, 1);
// 4096 round trips for 512 kB, each with
// topic + header overhead; broker message
// limits and rate limits get hit
✔ RIGHT — HTTPS Range download, resumable
uint32_t off = flash_progress();       // resume point
http_set_header(h, "Range", fmt("bytes=%lu-", off));
while ((n = http_read(h, buf, 4096)) > 0) {
    flash_write(slot_b + off, buf, n);
    sha256_update(&ctx, buf, n);
    off += n; save_progress(off);      // survive reboot
}

5. WHAT GOES WRONG IF…

…CoAP runs over a carrier NAT. UDP NAT mappings often expire in 30–120 s; server-initiated messages (Observe notifications) cannot reach the device afterwards. LwM2M uses "queue mode": the device sends a registration update to reopen the path, then the server delivers queued requests.
CoAP is a REST protocol over UDP with a 4-byte header, confirmable messages retried with exponential backoff, message IDs for deduplication, Observe for subscriptions and block-wise transfer for large bodies, secured with DTLS; it suits NB-IoT because there is no TCP connection or keep-alive to maintain, but UDP NAT timeouts limit server-initiated traffic. HTTPS is heavy per request but universal, so I use it for large downloads like firmware with Range requests to resume. MQTT sits in between: a persistent connection that is best for frequent bidirectional messaging.

Payload formats: JSON vs CBOR vs Protocol Buffers

INTERMEDIATE▶

1. WHAT IS IT?

The payload format decides how many bytes each message costs, how much CPU/RAM the device spends encoding it, and how easily the backend team can read and evolve it. On a cellular plan billed per MB, and on NB-IoT where every byte is airtime, this is a real engineering trade-off.

2. TERMS

JSON
text, self-describing (field names in every message), human-readable, universally supported.
CBOR
Concise Binary Object Representation (RFC 8949): JSON's data model in binary; still self-describing (keys present), no schema needed.
Protobuf
Protocol Buffers (Google): schema in a .proto file; fields identified by numbers, not names; varint encoding. nanopb is the common embedded implementation.
Varint
variable-length integer: 7 bits per byte, MSB = "more bytes follow". 87 → 1 byte; 300 → 2 bytes.
Schema evolution
adding/removing fields without breaking old readers. Protobuf: never reuse field numbers.

3. ENCODING THE SAME READING, STEP BY STEP

Reading: time 1718000000, voltage 3.71 V, current 1.25 A, state of charge 87 %.

  1. JSON: {"t":1718000000,"v":3.71,"i":1.25,"soc":87} = 41 bytes.
  2. CBOR: map of 4 (A4); key "t" (61 74) + uint32 (1A + 4 B); "v" (61 76) + float32 (FA + 4 B); "i" + float32; "soc" (63 73 6F 63) + uint8 87 (18 57) → 1+2+5+2+5+2+5+4+2 = 28 bytes.
  3. Protobuf (uint32 t=1; float v=2; float i=3; uint32 soc=4;): tag 0x08 + varint(1718000000) 5 B = 6; tag 0x15 + 4 B float = 5; tag 0x1D + 4 = 5; tag 0x20 + varint 87 (1 B) = 2 → 18 bytes.
  4. Scaling instead of floats (voltage in mV as uint16 3710 → varint 2 B) shrinks protobuf further to ~15 B.
10 000 devices × one reading per minute × 30 days = 432 million messages/month. 41 B vs 18 B saves 23 B × 432 M ≈ 9.9 GB/month of payload alone (before MQTT/TLS/TCP overhead, which batching reduces further).

4. CODE: NANOPB ENCODE (WRONG vs RIGHT)

✖ WRONG — sprintf JSON into a fixed buffer
char buf[32];
sprintf(buf, "{\"t\":%lu,\"v\":%.2f,\"i\":%.2f,\"soc\":%u}",
        t, v, i, soc);   // 41+ B into 32 → stack overflow;
                         // %f pulls in float printf (+10–20 kB)
✔ RIGHT — schema'd binary, bounded
#include "pb_encode.h"
#include "reading.pb.h"           // generated from reading.proto
uint8_t buf[Reading_size];        // max size computed by nanopb
Reading r = Reading_init_zero;
r.t = t; r.v_mv = 3710; r.i_ma = 1250; r.soc = 87;
pb_ostream_t s = pb_ostream_from_buffer(buf, sizeof buf);
if (!pb_encode(&s, Reading_fields, &r))
    log_err("pb: %s", PB_GET_ERROR(&s));
mqtt_publish(topic, buf, s.bytes_written, 1);

5. WHAT GOES WRONG IF…

…someone renumbers a protobuf field (deletes field 3 and later reuses number 3 for a different meaning). Old devices in the field still send field 3 with the old meaning; the backend misreads every one of them silently. Mark removed numbers reserved.
JSON is self-describing and easy to debug but repeats field names and costs CPU and printf code; CBOR keeps the JSON model in binary and is usually 30 to 40 percent smaller without a schema; protobuf uses a schema with numbered fields and varints, so the same reading goes from about 41 bytes in JSON to 18 in protobuf. On metered cellular or NB-IoT links I prefer protobuf or CBOR with integer scaling, I size buffers from the generated maximum, and I manage schema evolution by never reusing field numbers.

TLS 1.2 / 1.3 handshakes on constrained devices (mbedTLS memory and time)

ADVANCED▶

1. WHAT IS IT?

TLS (Transport Layer Security) encrypts and authenticates the TCP connection to the cloud. The expensive part is the handshake: certificates are exchanged and verified with public-key cryptography, and a shared key is agreed. On an MCU with 128–256 kB of RAM this is often the single biggest RAM and time consumer in the product.

2. TERMS

Certificate (X.509)
a public key plus identity, signed by a CA (Certificate Authority).
Mutual TLS (mTLS)
both the server and the device present certificates. AWS IoT Core requires it on port 8883.
ECDHE
Elliptic-Curve Diffie-Hellman Ephemeral: key agreement with fresh keys each session (forward secrecy).
Cipher suite
e.g. TLS_ECDHE_ECDSA_WITH_AES_128_GCM_SHA256.
SNI
Server Name Indication: hostname sent in ClientHello; required by AWS IoT and most cloud endpoints.
Record
TLS unit of data, up to 16 384 bytes of plaintext.
Session resumption
reusing a previous session's secret (TLS 1.2 session ID/ticket, TLS 1.3 PSK) to skip certificate exchange.

3. THE HANDSHAKES, STEP BY STEP

TLS 1.2 mutual auth (2 round trips):

  1. Client → ClientHello (random, cipher suites, SNI, extensions).
  2. Server → ServerHello, Certificate (chain, often 3–5 kB), ServerKeyExchange (ECDHE public key, signed), CertificateRequest, ServerHelloDone.
  3. Client verifies the chain against its root CA (signature checks, validity dates!), then → Certificate (its own), ClientKeyExchange (its ECDHE key), CertificateVerify (signature with the device private key), ChangeCipherSpec, Finished.
  4. Server → ChangeCipherSpec, Finished. Application data may flow.

TLS 1.3 (1 round trip): ClientHello carries a key_share; the server answers ServerHello + encrypted {EncryptedExtensions, CertificateRequest, Certificate, CertificateVerify, Finished}; client sends {Certificate, CertificateVerify, Finished}. Certificates are encrypted (privacy) and one RTT is saved.

RAM: mbedTLS defaults MBEDTLS_SSL_IN_CONTENT_LEN = MBEDTLS_SSL_OUT_CONTENT_LEN = 16384 → two ~16.5 kB record buffers = ~33 kB per connection, plus handshake heap peak (certificate chain parsing, ECDHE/ECDSA contexts) of roughly 10–30 kB → ~45–60 kB peak. Reducing OUT to 4096 is safe (we decide what we send); reducing IN is only safe if the server is guaranteed to send small records (Max Fragment Length extension, RFC 6066, if the server supports it) — otherwise the first large record breaks the handshake.
Time over NB-IoT: RTT ~1.5 s. TLS 1.2 = TCP handshake (1 RTT) + 2 RTT = 4.5 s + crypto; TLS 1.3 = 3 s; TLS 1.3 resumption still 1 RTT but no certificate verification. Each second at ~70 mA costs 70 mC.
CPU: an ECDSA P-256 verify in software on a Cortex-M4 at ~64–168 MHz takes on the order of 100–500 ms; RSA-2048 verify is fast but RSA private-key operations are slow and keys are large. Hardware crypto (STM32 PKA, nRF CryptoCell, ESP32 ECC/RSA accelerators, a secure element such as Microchip ATECC608) cuts this to tens of ms.

4. CODE: mbedTLS SETUP (WRONG vs RIGHT)

✖ WRONG
mbedtls_ssl_conf_authmode(&conf, MBEDTLS_SSL_VERIFY_NONE);
// "fixes" handshake errors by not checking the server
// → anyone can impersonate the broker (MITM)
// no SNI set → AWS endpoint rejects the handshake

if (ret) printf("tls fail\n");   // error code thrown away
✔ RIGHT

mbedtls_ssl_conf_own_cert(&conf, &dev_cert, &dev_key); // mTLS
mbedtls_ssl_set_hostname(&ssl, endpoint);             // SNI + name check

while ((ret = mbedtls_ssl_handshake(&ssl)) != 0) {
    if (ret == MBEDTLS_ERR_SSL_WANT_READ || ret == MBEDTLS_ERR_SSL_WANT_WRITE)
        continue;
    uint32_t flags = mbedtls_ssl_get_verify_result(&ssl);
    log_err("tls -0x%04x verify 0x%08lx", -ret, flags); // e.g. 0x0200 = BADCERT_FUTURE
    return ret;    // -0x7F00 = SSL_ALLOC_FAILED (out of heap)
}

5. WHAT GOES WRONG IF…

…the device has no valid time. After a battery swap the RTC reads 2000-01-01. The server certificate's notBefore is 2024 → verify fails with MBEDTLS_X509_BADCERT_FUTURE (0x0200) and the handshake returns MBEDTLS_ERR_X509_CERT_VERIFY_FAILED (−0x2700). Get time first (cellular network time, SNTP over plain UDP, or a build-time floor) before TLS.
…heap is fragmented when MQTT reconnects. The first connect after boot succeeds; after hours of runtime the 16 kB buffer cannot be allocated → MBEDTLS_ERR_SSL_ALLOC_FAILED (−0x7F00). Allocate TLS buffers once at boot, or use a dedicated static heap for mbedTLS (mbedtls_memory_buffer_alloc_init).
TLS 1.2                         TLS 1.3
C ─ClientHello──────────►       C ─ClientHello+key_share──────────►
C ◄─SH,Cert,SKE,CReq,SHD─       C ◄─SH+key_share,{EE,CReq,Cert,CV,Fin}─
C ─Cert,CKE,CV,CCS,Fin──►       C ─{Cert,CV,Fin}, app data ─────────►
C ◄─CCS,Fin──────────────       (1 RTT)
(2 RTT)
A TLS 1.2 mutual-auth handshake takes two round trips: hello, the server's chain, ECDHE key exchange and certificate request, then my certificate, key exchange, CertificateVerify signed with the device key, and Finished; TLS 1.3 does it in one round trip with the key share in the ClientHello and encrypted certificates. On an MCU the cost is RAM — mbedTLS defaults to two 16 kB record buffers, so 45 to 60 kB peak — plus hundreds of milliseconds of ECC without hardware and several round trips on a slow cellular link. The two classic failures are heap exhaustion, error minus 0x7F00, and invalid time making the server certificate look not yet valid, so I sync time before TLS and allocate buffers up front.

Device identity: X.509 client certificates and AWS IoT provisioning

ADVANCED▶

1. WHAT IS IT?

Every device needs its own identity so the cloud knows which device is talking and can revoke just that one if it is stolen. The standard approach is a per-device X.509 certificate whose private key never leaves the device. Provisioning is how that key and certificate get created and registered — at the factory or on first boot — for thousands of devices.

2. TERMS

Private key / public key
the key pair. The private key signs (proves identity); the public key goes in the certificate.
CSR
Certificate Signing Request: a public key + subject signed by the private key, sent to a CA for signing. Lets the key be generated on the device and never exported.
CA
Certificate Authority: signs certificates. Can be AWS's or your own registered CA.
Thing / policy (AWS IoT)
registry entry for a device / JSON permissions attached to a certificate (which topics it may publish/subscribe).
JITP / JITR
Just-In-Time Provisioning/Registration: devices carry certs signed by your CA; on first connect AWS auto-registers the cert (connection fails once, then succeeds).
Fleet provisioning by claim
all devices ship with a shared, low-privilege claim certificate; on first boot each uses it to request its own unique certificate.
Secure element
a chip (e.g. Microchip ATECC608, NXP SE050) that generates and stores the private key and signs internally; the key cannot be read out.

3. FLEET PROVISIONING BY CLAIM, STEP BY STEP

  1. Factory flashes the same firmware and a claim certificate; its AWS policy allows only the provisioning topics.
  2. First boot: device generates its own key pair (ideally inside a secure element) and a CSR.
  3. Connects with the claim cert; publishes the CSR to $aws/certificates/create-from-csr/json.
  4. Receives on …/create-from-csr/json/accepted: certificatePem, certificateId and a certificateOwnershipToken.
  5. Publishes to $aws/provisioning-templates/<template>/provision/json with the token and parameters such as SerialNumber. A pre-provisioning hook (Lambda) can check the serial against your manufacturing database.
  6. Accepted → AWS creates the thing, activates the cert, attaches the device policy; returns thingName.
  7. Device stores the cert, disconnects, reconnects with its own certificate. The claim cert is never used again by this device.
Size budget on an MCU: device certificate (ECDSA P-256) ≈ 550–700 bytes DER (~900 B PEM); Amazon Root CA 1 ≈ 837 B DER (~1.2 kB PEM); EC private key 121 B DER. Total under 4 kB of flash — but a PEM chain loaded into RAM for parsing temporarily needs more.
Security impact: if one device's key leaks, you revoke 1 certificate. With a single shared certificate on 10 000 devices (an anti-pattern), the leak forces re-provisioning all 10 000.

4. CODE: GENERATE KEY + CSR ON DEVICE (mbedTLS)

mbedtls_pk_context key; mbedtls_x509write_csr csr;
mbedtls_pk_init(&key);
mbedtls_pk_setup(&key, mbedtls_pk_info_from_type(MBEDTLS_PK_ECKEY));
mbedtls_ecp_gen_key(MBEDTLS_ECP_DP_SECP256R1, mbedtls_pk_ec(key),
                    mbedtls_ctr_drbg_random, &drbg);       // needs a real TRNG seed
mbedtls_x509write_csr_init(&csr);
mbedtls_x509write_csr_set_key(&csr, &key);
mbedtls_x509write_csr_set_md_alg(&csr, MBEDTLS_MD_SHA256);
mbedtls_x509write_csr_set_subject_name(&csr, "CN=stn-0042");
unsigned char pem[1024];
mbedtls_x509write_csr_pem(&csr, pem, sizeof pem, mbedtls_ctr_drbg_random, &drbg);
store_private_key_protected(&key);   // never logged, never sent

5. WHAT GOES WRONG IF…

…the factory generates keys on a PC and flashes them. The keys exist outside the device (on the PC, in logs, in a spreadsheet) — a leak exposes the whole batch. Generate on-device (CSR flow) or inject into a secure element in a controlled HSM-backed process.
…the claim certificate's policy is too broad. Anyone extracting it from one device's flash can publish to fleet topics. Claim policies must allow only the provisioning topics, and the pre-provisioning hook should validate serial numbers.
Root CA ──signs──► (Intermediate) ──signs──► device cert (CN=stn-0042, pubkey)
                                                ▲
device: private key (secure element) ──CSR──────┘    AWS: thing + cert + policy
Each device should have its own X.509 certificate with a private key that never leaves it, ideally generated inside a secure element and turned into a certificate through a CSR, so a compromise means revoking one certificate. On AWS IoT the certificate is attached to a thing and a policy that uses the thing name to restrict topics. For volume manufacturing I use fleet provisioning by claim: a low-privilege claim certificate lets the device submit its CSR and a provisioning template, with a hook validating the serial, after which it reconnects with its own certificate; just-in-time provisioning with our own registered CA is the alternative.

OTA updates over wireless links

INTERMEDIATE▶

1. WHAT IS IT?

OTA (Over-The-Air) update replaces firmware on devices already in the field. Over wireless the link is slow, expensive and unreliable, power can fail half-way, and an attacker might push their own image. A good OTA design survives all of that and never bricks a device. (The bootloader side is covered in depth in topic 15; this card focuses on the wireless transport.)

2. TERMS

A/B slots
two firmware areas: run from A while writing B; switch only after B is complete and verified.
Signature
image hash signed by the vendor's private key (e.g. ECDSA P-256); bootloader verifies with the public key.
Anti-rollback
refuse images with a version (security counter) lower than the installed one.
Job
cloud-side record (AWS IoT Jobs) telling a device "update to version X from URL Y", with progress/status reporting.
Delta update
send only the binary difference between old and new image.
Confirm / test boot
new image boots in "test" mode and must confirm itself healthy, or the bootloader reverts (MCUboot swap/revert).

3. A ROBUST OTA, STEP BY STEP

  1. Device receives a job (MQTT) with version, size, SHA-256, signature and an HTTPS URL (pre-signed, time-limited).
  2. Checks preconditions: battery > threshold, not mid-operation, enough flash, version newer than current.
  3. Downloads in chunks with HTTP Range, writing to slot B and saving progress, so a dropped link resumes instead of restarting.
  4. Verifies hash and signature over the whole slot.
  5. Marks B pending, reboots; bootloader verifies again and boots B in test mode.
  6. App runs self-tests (connects to cloud, peripherals OK) and confirms; otherwise watchdog reset → bootloader reverts to A.
  7. Reports success/failure (with reason) to the job.
Image 900 kB over LTE-M at a realistic 200 kbps effective = 900 × 8 / 200 = 36 s of transfer, at ~100 mA → 3.6 C = 1 mAh. Over NB-IoT at ~20 kbps effective: 360 s, ~7 mAh, and at 10 000 devices × 0.9 MB = 9 GB of data on the plan — why delta updates (often 10–20 % of full size) matter. Over BLE (MCUmgr/SMP, MTU 247, 2M PHY) at ~100 kB/s: ~9 s.

4. CODE (WRONG vs RIGHT)

✖ WRONG — write over the running image
flash_erase(APP_START, img_len);    // erase current firmware
while (http_read(h, buf, 1024) > 0)
    flash_write(...);               // power cut or link drop → brick
NVIC_SystemReset();                 // no signature check
✔ RIGHT — A/B, resumable, verified, confirmed
if (!ota_preconditions_ok()) return job_report(JOB_REJECTED, "low batt");
ota_download_resumable(url, SLOT_B, &hash);        // Range + progress
if (memcmp(hash, job.sha256, 32) || !ecdsa_verify(pubkey, hash, job.sig))
    return job_report(JOB_FAILED, "bad signature");
boot_set_pending(SLOT_B);                          // test boot
NVIC_SystemReset();
/* new image, after cloud connect + self-test: */
boot_confirm();                                    // else revert on next reset

5. WHAT GOES WRONG IF…

…the new firmware cannot connect to the cloud (e.g. a changed TLS config) but confirms itself at boot before testing connectivity. The device is now permanently offline: no way to send it another update. Confirm only after a successful cloud round trip.
…all 10 000 devices download at once. Server and cellular cell congestion, many failures. Roll out in waves (1 %, 10 %, 100 %) with health gates, and add jitter to download start times.
Over wireless I treat OTA as a resumable, verified, reversible transaction: a job tells the device the version, hash, signature and URL, it checks battery and version, downloads into the inactive slot with HTTP Range so a dropped link resumes, verifies hash and signature, then test-boots the new image and only confirms it after it has reached the cloud, otherwise the bootloader reverts. Link cost drives delta updates on cellular, and fleet rollouts go in staged waves with jitter.

Reconnect with exponential backoff and jitter

INTERMEDIATE▶

1. WHAT IS IT?

When a connection fails, a device must try again — but how it retries decides whether a server outage ends gracefully or turns into a self-inflicted denial-of-service. Exponential backoff makes each retry wait longer; jitter randomises the wait so thousands of devices do not retry in lockstep.

2. TERMS

Base
first delay, e.g. 1 s.
Cap
maximum delay, e.g. 300 s, so a device never waits hours.
Full jitter
sleep = random(0, min(cap, base × 2^attempt)). Recommended by the AWS architecture blog analysis because it spreads load most evenly.
Equal jitter
sleep = half the exponential value + random(0, half). Guarantees some minimum wait.
Thundering herd / reconnect storm
many clients hitting a recovering server at the same instant, knocking it over again.

3. HOW IT BEHAVES, STEP BY STEP

  1. Connection lost; attempt = 0.
  2. Compute ceiling = min(cap, base × 2^attempt): 1, 2, 4, 8, 16, 32, 64, 128, 256, 300, 300… s.
  3. Sleep a random time in [0, ceiling] (full jitter) — use a properly seeded RNG (hardware TRNG, or seeded with a unique ID), otherwise all devices pick the same "random" values.
  4. Try again; on success reset attempt to 0 (ideally only after the connection has stayed up for a while, to avoid flapping).
  5. Distinguish errors: a TLS certificate rejection or "not authorised" will not fix itself with retries — go to a long backoff and report.
50 000 devices lose the broker at the same moment; it returns 60 s later.
Fixed 5 s retry: every 5 s, ~50 000 CONNECT + TLS handshakes arrive within a few hundred ms → ~100 000 handshakes/s bursts. The broker (or an account-level connect rate limit) rejects most; rejected devices retry 5 s later in sync → the storm never ends.
Full jitter, base 1 s, cap 300 s: by attempt 7 the window is 0–128 s; devices spread uniformly → 50 000 / 128 ≈ 390 connects/s, a load the broker can absorb. Recovery completes in ~2 minutes instead of never.

4. CODE (whiteboard solution)

✖ WRONG
while (!mqtt_connect()) {
    delay_ms(5000);           // every device in lockstep
}
// or: delay = 1000 << attempt;  → overflows at
// attempt 22 (uint32), no cap, no jitter
✔ RIGHT — capped exponential, full jitter
#include <stdint.h>
#define BASE_MS   1000u
#define CAP_MS  300000u

extern uint32_t trng_u32(void);          // hardware RNG

uint32_t backoff_ms(uint32_t attempt) {
    uint32_t ceil = CAP_MS;
    if (attempt < 31) {                   // avoid shift overflow
        uint64_t e = (uint64_t)BASE_MS << attempt;
        if (e < CAP_MS) ceil = (uint32_t)e;
    }
    return trng_u32() % (ceil + 1);       // full jitter: [0, ceil]
}

void connectivity_task(void) {
    uint32_t attempt = 0;
    for (;;) {
        int rc = mqtt_connect();
        if (rc == OK) { attempt = 0; run_until_disconnect(); continue; }
        if (rc == E_AUTH) { report_fatal(rc); attempt = 10; } // won't self-heal
        sleep_ms(backoff_ms(attempt));
        if (attempt < 31) attempt++;
    }
}

5. WHAT GOES WRONG IF…

…the RNG is seeded with a constant (e.g. srand(0) or rand() unseeded). All devices generate the identical "random" sequence → jitter does nothing and the storm returns. Seed from a TRNG or mix in the unique device ID.
ceiling  1 2 4 8 16 32 64 128 256 300 300 ...   (s)
fixed:   ▌▌▌▌▌ every 5 s, all devices together  → spikes forever
jitter:  ░░▒▒▒▓▓▓ spread uniformly inside the growing window → flat load
On failure I wait a random time between zero and min(cap, base times two to the attempt), which is exponential backoff with full jitter: the exponential part stops a failing device hammering the server and the jitter decorrelates thousands of devices so a recovering broker sees a flat load instead of synchronized storms. I cap the delay at a few minutes, guard the shift against overflow, seed the RNG from a TRNG or the device ID, reset the attempt counter after a stable connection, and treat authentication failures differently because retrying won't fix them.

Offline buffering and store-and-forward

ADVANCED▶

1. WHAT IS IT?

Wireless links go down — tunnels, basements, network outages, server maintenance. A device that only sends "live" data loses everything recorded while offline. Store-and-forward means: always write the record to local non-volatile storage first, send from storage when connected, and delete only after the server confirms it.

2. TERMS

Sequence number
monotonically increasing ID per record (persisted), letting the server detect gaps and duplicates.
Ack-based deletion
a record is removed only after the server acknowledges it (QoS 1 PUBACK is a broker ack; an application-level ack confirms it was stored in the database).
Ring buffer in flash
circular log over several flash sectors with head/tail pointers; oldest data is overwritten (or newest dropped) when full.
Wear levelling
spreading writes over many sectors because flash sectors endure ~10 000–100 000 erase cycles.
Backfill
sending buffered history after reconnect, usually at a lower priority than live data.

3. THE ALGORITHM, STEP BY STEP

  1. Sample → build record {seq, timestamp, data, CRC} → append to the flash ring (tail).
  2. Connectivity task: while connected and head ≠ tail, read a batch of records from head, publish (QoS 1).
  3. On ack for the batch, advance head (persist it). On timeout/disconnect, do not advance: the same records are re-sent next time.
  4. Server stores records keyed by (deviceId, seq) → re-sent duplicates are ignored (idempotent insert).
  5. Live data and alarms jump ahead of backfill so a dashboard is current within seconds.
  6. If storage fills, apply a policy: drop oldest (most common for telemetry), or downsample, and count dropped records in telemetry.
Record = 4 seq + 4 time + 24 data + 2 CRC + 2 header = 36 B. One record every 30 s = 2880/day = 103.7 kB/day.
Offline requirement: survive 7 days → 726 kB → use a 1 MB SPI-NOR region (256 sectors of 4 kB).
Wear: each sector erased once per lap of the ring; a lap = 1 MB / 103.7 kB ≈ 9.6 days → ~38 erases/year per sector — negligible against 100 000 cycles.
Backfill after a 3-day outage: 8640 records × 36 B = 311 kB; batched 50 per message → 173 messages.

4. CODE (WRONG vs RIGHT)

✖ WRONG — delete on send
rec_t r;
while (queue_pop(&r)) {        // removed now
    mqtt_publish(topic, &r, sizeof r, 0);  // QoS 0
}   // link drops mid-batch → records gone
✔ RIGHT — peek, send, ack, then advance
for (;;) {
    rec_t batch[50];
    size_t n = flog_peek(&log, batch, 50);          // head not moved
    if (!n || !link_up()) break;
    uint16_t pid = mqtt_publish(topic_backfill, batch, n * sizeof *batch, 1);
    if (wait_puback(pid, 30000) != OK) break;      // retry later, same batch
    flog_advance(&log, n);                         // persist new head
}

5. WHAT GOES WRONG IF…

…the head/tail pointers live only in RAM. After a reset the device either re-sends the whole log (huge duplicate burst) or skips unsent data. Persist pointers (or scan sectors for the latest valid header at boot) and make records self-describing with seq + CRC.
flash ring:  [acked/erasable][ head ► unsent unsent unsent ◄ tail ][ free ]
              send batch from head ──► PUBACK ──► advance head (persist)
I write every record to a flash ring buffer first, with a persisted sequence number, timestamp and CRC, and the connectivity task sends batches from the head and advances the head only after an acknowledgement, so a link drop just means the same batch is re-sent. The server inserts idempotently on device ID plus sequence, so re-sends are harmless and gaps are visible. Live data and alarms take priority over backfill, I size the ring for the longest outage I must survive and check wear, and I define and report the policy when it fills.

Time sync: NTP/SNTP and network time

INTERMEDIATE▶

1. WHAT IS IT?

Devices need wall-clock time for three reasons: TLS certificate validity checks, timestamps on stored data, and scheduling. A microcontroller's RTC drifts and resets to zero after power loss, so it must be set from the network. SNTP (Simple NTP) asks a time server; cellular networks can also provide time.

2. TERMS

t1, t2, t3, t4
client send time, server receive time, server transmit time, client receive time.
Offset θ
how far the client clock is behind the server: ((t2 − t1) + (t3 − t4)) / 2.
Delay δ
round-trip network delay: (t4 − t1) − (t3 − t2).
NTP epoch
NTP counts seconds from 1900-01-01; Unix from 1970-01-01. Difference: 2 208 988 800 s. 32-bit NTP seconds roll over in 2036.
NITZ / AT+CCLK
Network Identity and Time Zone: time the cellular network may send; read with AT+CCLK?. Not all operators provide it.
Drift (ppm)
a ±20 ppm 32 kHz crystal drifts up to 20 µs per second = 1.73 s per day.

3. HOW SNTP COMPUTES TIME, STEP BY STEP

  1. Client records t1 and sends a 48-byte UDP packet to port 123 (mode 3 = client).
  2. Server stamps t2 on receipt, t3 on transmit (both in the reply).
  3. Client records t4 when the reply arrives.
  4. Compute θ and δ; assume the path is symmetric (error ≤ δ/2). Reject replies with stratum 0 (kiss-of-death), a wrong mode, or an implausible δ.
  5. Apply θ to the RTC; repeat periodically (e.g. every few hours) and estimate drift.
t1 = 100.000 s (client clock), t2 = 150.020 (server), t3 = 150.021 (server), t4 = 100.080 (client).
θ = ((150.020 − 100.000) + (150.021 − 100.080)) / 2 = (50.020 + 49.941) / 2 = 49.9805 s → client is ~50 s behind.
δ = (100.080 − 100.000) − (150.021 − 150.020) = 0.080 − 0.001 = 0.079 s → max error ±39.5 ms.
Unix time from an NTP seconds value 3 927 000 000: 3 927 000 000 − 2 208 988 800 = 1 718 011 200 (June 2024).

4. CODE (WRONG vs RIGHT)

✖ WRONG — use t3 directly, ignore delay, no sanity
uint32_t secs = ntohl(pkt.tx_ts_sec);
rtc_set(secs);   // still NTP epoch (1900) → year 2094
                 // and ignores network delay
✔ RIGHT
#define NTP_UNIX_DELTA 2208988800ULL
static int64_t ntp_to_us(uint32_t s, uint32_t f) {      // 32.32 fixed point
    return (int64_t)(s - NTP_UNIX_DELTA) * 1000000 + ((uint64_t)f * 1000000 >> 32);
}
int sntp_apply(const ntp_pkt_t *p, int64_t t1, int64_t t4) {  // t1,t4 local µs
    if ((p->li_vn_mode & 7) != 4 || p->stratum == 0) return -1; // not server / KoD
    int64_t t2 = ntp_to_us(ntohl(p->rx_s), ntohl(p->rx_f));
    int64_t t3 = ntp_to_us(ntohl(p->tx_s), ntohl(p->tx_f));
    int64_t delay  = (t4 - t1) - (t3 - t2);
    if (delay < 0 || delay > 2000000) return -2;          // implausible
    int64_t offset = ((t2 - t1) + (t3 - t4)) / 2;
    clock_adjust_us(offset);
    return 0;
}

5. WHAT GOES WRONG IF…

…TLS is attempted before time is set. The RTC says 2000 → server certificate "not yet valid" → handshake fails → MQTT never connects → if your SNTP runs only after MQTT is up, the device is stuck forever. Order: network up → time (SNTP over UDP or AT+CCLK) → TLS. As a safety net, never let time go below the firmware build date.
client t1 ──── request ────► t2 server
client t4 ◄─── reply ──────── t3 server
offset = ((t2−t1)+(t3−t4))/2      delay = (t4−t1)−(t3−t2)
SNTP uses four timestamps: client send t1, server receive t2, server send t3 and client receive t4. The offset is the average of t2 minus t1 and t3 minus t4, the round-trip delay is t4 minus t1 minus the server's processing time, and the error is bounded by half the delay if the path is symmetric. I convert from the 1900 NTP epoch by subtracting 2,208,988,800 seconds, sanity-check stratum and delay, and get time before TLS — from SNTP or cellular network time — because certificate validity checks fail with an unset clock.

Connectivity state machine and modem watchdog

ADVANCED▶

1. WHAT IS IT?

Cellular modules occasionally wedge: they stop answering AT commands, stay registered but pass no data, or lose the SIM. A field device must detect each failure level and escalate the recovery — retry, re-attach, reset the modem, power-cycle it — without a human. This is organised as an explicit state machine with a watchdog for the modem.

2. TERMS

PWRKEY / RESET_N
module control pins: a timed pulse on PWRKEY turns the module on/off; RESET_N forces a reset.
Hard power cycle
cutting the module's supply (via a load switch/MOSFET controlled by the MCU) — the only recovery for a fully hung module.
Liveness check
periodic proof the whole path works, e.g. MQTT round-trip or a ping to the broker, not just "AT → OK".
Escalation ladder
ordered list of recovery actions from cheapest to most drastic.

3. THE STATE MACHINE, STEP BY STEP

  1. POWER_ON: PWRKEY pulse (module-specific timing, e.g. ≥ 500 ms on some Quectel parts), wait for RDY URC (timeout ~ 10–15 s).
  2. SIM: AT+CPIN? → READY; else SIM error state (report, retry less often).
  3. REGISTER: wait for +CEREG: 1/5 with timeout (e.g. 3 min); log RSRP/operator.
  4. DATA: activate PDP context / PPP; get IP.
  5. TIME → TLS → MQTT: sync time, connect broker.
  6. ONLINE: application traffic; liveness check every N minutes (e.g. publish + wait for PUBACK).
  7. Any failure → go back the minimum number of states, incrementing a failure counter per level. Escalation: (a) reconnect socket → (b) deactivate/reactivate PDP → (c) AT+CFUN=0/1 (radio off/on) → (d) PWRKEY reset → (e) hard power cycle → (f) MCU reset. Each with jittered backoff.
Liveness every 10 min; escalation thresholds: 2 failed liveness → CFUN cycle; 3 more → PWRKEY reset; 2 more → hard power cycle; a device with no successful cloud contact for 6 h → full system reset. Worst-case time to self-heal from a hung module: 10 + 10 + 30 + 20 min ≈ 70 min, without any human — vs a truck roll costing far more than the device.

4. CODE (WRONG vs RIGHT)

✖ WRONG — "AT responds, so all is fine"
void modem_check(void) {
    if (at_cmd("AT") == OK) return;  // module answers but
                                     // data path is dead
    NVIC_SystemReset();              // resets MCU, not modem;
                                     // module stays hung
}
✔ RIGHT — end-to-end check, escalating recovery
typedef enum { R_SOCKET, R_PDP, R_CFUN, R_PWRKEY, R_POWERCYCLE, R_MCU } rec_t;
static rec_t level;
void liveness_tick(void) {
    if (mqtt_ping_roundtrip(15000) == OK) { level = R_SOCKET; fails = 0; return; }
    if (++fails < 2) return;                     // tolerate one blip
    fails = 0;
    switch (level) {
    case R_SOCKET:     mqtt_reconnect();                    break;
    case R_PDP:        at_cmd("AT+CGACT=0,1"); at_cmd("AT+CGACT=1,1"); break;
    case R_CFUN:       at_cmd("AT+CFUN=0"); at_cmd("AT+CFUN=1"); break;
    case R_PWRKEY:     modem_pwrkey_reset();                break;
    case R_POWERCYCLE: gpio_clear(MODEM_EN); sleep_ms(2000); gpio_set(MODEM_EN); break;
    case R_MCU:        log_persist("modem unrecoverable"); NVIC_SystemReset();
    }
    if (level < R_MCU) level++;
    metrics.recoveries[level]++;                 // report in telemetry
}

5. WHAT GOES WRONG IF…

…the board has no MCU-controlled power switch on the modem. When the module firmware hangs hard (it happens with every vendor eventually), neither AT nor PWRKEY helps; the MCU watchdog resets only the MCU. The device stays offline until someone visits. Always include a load switch on the modem's VBAT.
POWER_ON → SIM → REGISTER → DATA → TIME → TLS/MQTT → ONLINE
    ▲         ▲        ▲        ▲                        │ liveness fail
    └─────────┴────────┴────────┴──── escalate: socket → PDP → CFUN → PWRKEY → power cycle → MCU reset
I model connectivity as an explicit state machine — power on and wait for RDY, SIM, registration, PDP or PPP, time, TLS and MQTT, online — with a timeout on every state. A liveness check proves the whole path works by a real round trip, not just AT OK, and on repeated failure I escalate from reconnecting the socket to re-activating the PDP context, toggling CFUN, a PWRKEY reset, a hard power cycle through a load switch the hardware must provide, and finally an MCU reset, with backoff and counters reported in telemetry.

Fleet telemetry design

ADVANCED▶

1. WHAT IS IT?

With thousands of devices in the field, telemetry is your only window into what is happening. Good telemetry answers "is the fleet healthy, and if not, which devices, since when, and why?" without costing a fortune in data or battery.

2. TERMS

Telemetry vs events
periodic measurements vs things that happened (alarm, reboot, OTA result). Events are sent immediately; telemetry can be batched.
Health metrics
uptime, reset reason, firmware version, free heap/stack high-water marks, RSRP/RSRQ/SINR or RSSI, reconnect count, recovery-level counters, buffered record count, battery.
Device shadow / twin
cloud document with reported state (from device) and desired state (from backend); the delta is what the device should change (AWS IoT Device Shadow).
Report-by-exception (deadband)
send only when a value changes by more than a threshold, plus a periodic heartbeat.
Schema version
field in every message (or in the topic) telling the backend how to decode it.

3. DESIGNING IT, STEP BY STEP

  1. Define the questions (fleet health, SLA, debugging) → derive metrics; avoid "send everything".
  2. Every message carries: device ID (topic), schema version, sequence number, device timestamp (and whether time was synced).
  3. Choose rates per class: alarms immediate (QoS 1), status on change (retained), metrics every N minutes, debug logs only on demand (enabled via shadow).
  4. Batch and compress: one message with 10 readings beats 10 messages (header/TLS/radio wake amortised).
  5. Budget the data plan: bytes/message × messages/day × devices.
  6. Server side: dedupe on (device, seq), alert on missing heartbeats, dashboards by firmware version, cohort comparisons after OTA.
Budget per device per month: telemetry batch every 15 min (96/day) × 300 B on wire = 28.8 kB/day; health message hourly 200 B → 4.8 kB/day; MQTT keep-alives (300 s) 288 × ~70 B (with TLS/TCP) ≈ 20 kB/day; TLS reconnects 2/day × 6 kB ≈ 12 kB/day. Total ≈ 66 kB/day ≈ 2 MB/month. Note keep-alive + reconnects are ~50 % of the bill — overhead, not data.

4. CODE: A HEALTH RECORD

typedef struct __attribute__((packed)) {
    uint8_t  schema;        // = 3

5. WHAT GOES WRONG IF…

…you log reset reason nowhere. After an OTA, 3 % of the fleet reboots every few hours. Without reset reason + firmware version + uptime in telemetry, you cannot tell watchdog resets from brown-outs from HardFaults, nor correlate with the new version. These three fields are the most valuable bytes you send.
I start from the questions the fleet team needs to answer and derive a small set of metrics: every message carries schema version, sequence number and device timestamp, alarms go immediately at QoS 1, status is retained, and metrics are batched. Health telemetry always includes firmware version, reset reason, uptime, signal quality, reconnect and recovery counters, heap low-water mark and backlog depth. I budget the data plan including keep-alive and TLS overhead, which is often half the bytes, and the backend dedupes by sequence and alerts on missing heartbeats and per-version anomalies.
