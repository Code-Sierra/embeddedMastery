1The problem a bootloader solves

Imagine you are the firmware engineer for a company that has installed 5 000 battery-swap stations across several cities. Each station has a main controller board with an STM32F407 microcontroller (an ARM Cortex-M4 chip with 1 MB of flash memory and 192 KB of RAM), a cellular modem for talking to the cloud, and a CAN bus connecting it to the battery slot controllers.

One morning you find a bug: under a rare timing condition the charger is not switched off after a full charge. You fix it in ten minutes. Now the real question: how do you get the fixed firmware onto 5 000 boards bolted inside metal cabinets in the street?

  1. Send a technician with a debug probe to every site. 5 000 sites × about 2 hours with travel = 10 000 technician-hours. Weeks of work, and every visit is a chance to break something.
  2. Let each station download the new firmware over its cellular link and install it itself. This is FOTA: Firmware Over The Air.

Option 2 sounds simple, but a microcontroller cannot just "overwrite its own program while it is running" safely. Think about what can go wrong:

  • The power fails while the new program is half written. Now the chip has half an old program and half a new one. It will crash, and it can no longer download anything because the download code was in the program you just destroyed.
  • The download is corrupted by a bad radio link. You install garbage.
  • Someone malicious sends your stations their firmware. Your stations now obey them.
  • The new firmware has a different bug that makes it crash at start-up. Every station is now stuck in a crash loop.

The bootloader is the piece of software designed to make all of those situations survivable. It is a small, separate program that always runs first after reset, never gets overwritten, checks the main program before letting it run, and keeps a way to recover if anything is wrong. The rest of this tab builds it up piece by piece.

The one rule to remember: at every instant, even if the power fails right now, the device must contain at least one complete, verified program that it knows how to start. Every design decision on this page exists to keep that rule true.

2The hardware picture: what is inside the chip

Before we talk about software, picture the physical parts. Inside the STM32F407 package there are several blocks connected by internal buses:

  • CPU core: executes instructions. It has a few special registers that matter here: the PC (Program Counter, address of the next instruction), the MSP (Main Stack Pointer, where the stack is in RAM) and VTOR (Vector Table Offset Register, where the table of interrupt handler addresses is).
  • Flash: 1 MB of non-volatile memory starting at address 0x0800_0000. "Non-volatile" means it keeps its contents with the power off. The program lives here and the CPU executes it directly from flash; it is not copied to RAM first. That is called XIP (execute in place).
  • SRAM: 128 KB of fast working memory at 0x2000_0000 for variables and the stack (plus 64 KB of CCM RAM we do not need here). It loses its contents when power is removed, but keeps them through a software reset.
  • Peripherals: UART, CAN, timers, the watchdog. Each has registers at fixed addresses (0x4000_0000 upwards) that the software reads and writes.

Notice that we have divided the flash into regions with different jobs. This division is called the partition layout. The bootloader lives at the very start, because that is where the CPU looks at reset. There are two application slots so that the new firmware can be written into one while the old firmware keeps running from the other. Card 03 explains exactly why the regions have these sizes.

3How flash memory behaves (the rules everything follows)

Almost every strange-looking design decision in a bootloader comes from four physical rules of flash memory. Learn these and the rest makes sense.

  1. Erase sets all bits to 1. An erased byte reads 0xFF. Erase is done for a whole sector at once (on the F407 a sector is 16, 64 or 128 KB). It is slow: about 1 second for a 128 KB sector.
  2. Programming can only change 1s into 0s. You program small aligned units (32-bit words on the F407, about 16 µs each). To turn a 0 back into a 1 you must erase the whole sector.
  3. Each sector wears out. It is guaranteed for about 10 000 erase cycles. Erasing the same small sector on every boot would kill it in years.
  4. While flash is being erased or programmed, the CPU cannot read from it (on single-bank parts like the F407). Since the program itself runs from flash, the CPU freezes until the operation finishes.

4What the CPU does at reset

When the chip comes out of reset, the Cortex-M4 does not "look for main()". It does exactly two memory reads, in hardware, before executing a single instruction:

  1. Read the 32-bit word at address 0x0000_0000 and put it in MSP. That is the initial stack pointer.
  2. Read the 32-bit word at address 0x0000_0004 and put it in PC. That is the address of the first code to run, the Reset_Handler.

On the STM32F407 with the BOOT0 pin tied low, address 0x0000_0000 is an alias (a second name) for the start of flash, 0x0800_0000. So the CPU reads the first two words of whatever program sits at the start of flash. In our design that is the bootloader. This list of addresses at the start of a program is called the vector table: word 0 is the stack, word 1 is the reset handler, and words 2 onwards are the addresses of the handlers for every exception and interrupt (NMI, HardFault, SysTick, USART1, CAN1 …).

Two details to notice in those numbers:

  • The handler addresses are odd (…99, …C5). The Cortex-M only runs Thumb instructions, and bit 0 = 1 in an address means "this is Thumb code". The real instruction is at the even address one below. An even value here would crash the CPU instantly.
  • Both programs have their own vector table. When the bootloader later starts the application, it must tell the CPU "from now on, use the application's table". That is what writing VTOR does. If it is forgotten, the first interrupt in the application jumps into the bootloader's handler. This is the most common bootloader bug in existence (Scenario 01, Jump Lab).

6One complete update, end to end, with real numbers

Let us follow one station from v1.0.0 to v1.1.0. The numbers are realistic for an STM32F407 at 168 MHz with an LTE-M cellular modem.

  1. Job arrives. The cloud sends a manifest: {"version":"1.1.0","size":307200,"sha256":"9f2c…","sig":"30 45 …","hw":["C","D"],"sec_cnt":2}. The app (still v1.0.0) checks that its hardware revision is in the list and that sec_cnt 2 ≥ its stored minimum 1. OK.
  2. Erase slot B. 3 sectors × ~1 s = ~3 s. During each erase the CPU stalls (rule 4), so the flash driver and the CAN interrupt handler have been placed in RAM, and the app sends the CAN nodes a "busy" message first. Slot A is not touched.
  3. Download chunk 1. HTTP request with header Range: bytes=0-4095. The server replies 206 Partial Content with 4 096 bytes. Air time: 4 096 / 12 500 = 0.33 s.
  4. Check and write chunk 1. Compute its CRC-32 and compare with the value sent alongside. Program 4 096 / 4 = 1 024 words × 16 µs = 16 ms into 0x0808_0000. Read them back and compare. Only now save "committed offset = 4096" in a small non-volatile record.
  5. Repeat for chunks 2 … 75. Total air time 75 × 0.33 = ~25 s; total programming 75 × 16 ms = 1.2 s. If the link drops at chunk 40, the app reconnects later and asks for Range: bytes=159744-… (39 × 4 096 = 159 744), because only 39 chunks were committed.
  6. Verify the whole image from flash. SHA-256 over 307 200 bytes at ~35 cycles/byte = 10.75 million cycles / 168 MHz = 64 ms. Compare with the hash in the header, then verify the ECDSA signature with the public key in the bootloader: ~50–100 ms. A tampered or corrupted image is rejected here and slot B is erased; the station never stopped working.
  7. Commit. Write one new metadata record into the older of the two metadata sectors: {seq: 8, active: A, pending: B, attempts: 0, crc: …}. Erasing the 16 KB metadata sector takes ~0.25 s, writing the record microseconds. This one write is the moment the decision changes. Before it is complete, the old record (seq 7, "boot A") is the newest valid one.
  8. Wait for an idle window (no battery mid-swap, no active charge), then reboot with NVIC_SystemReset().
  9. Bootloader runs. It reads both metadata records, takes seq 8 (valid CRC, highest), sees pending = B. It re-verifies slot B (~0.15 s), writes seq 9 with attempts = 1 before jumping, and starts the independent watchdog with a 32.8 s timeout (prescaler 256, reload 4095, 32 kHz clock: 256 × 4 096 / 32 000 = 32.8 s).
  10. Jump to slot B. Disable interrupts, stop SysTick, reset clocks and peripherals, clear the NVIC, set VTOR to slot B's vector table at 0x0808_0200 (this assumes the image was linked to run from slot B; MCUboot-style designs instead swap the new image into slot A so it always runs at one address, see card 07), load MSP from slot B's word 0, branch to word 1. Card 05 and the Jump Lab cover every step.
  11. Trial run and self-test. v1.1.0 starts, initialises CAN, sees all 12 slot controllers answer, the modem registers, MQTT connects to the cloud. It refreshes the watchdog all the time.
  12. Confirm. The app writes seq 10: {active: B, pending: none, attempts: 0}. Slot A (v1.0.0) is now the fallback. Only now, if the release is a security fix, the minimum security counter in OTP is raised from 1 to 2. The app reports "CONFIRMED" to the cloud.

Total time the station was out of service: the reboot plus the app's start-up, about 10–30 s, scheduled at night. Everything else happened while v1.0.0 kept running.

If v1.1.0 had a crash bug: step 11 fails, the chip resets (HardFault handler or watchdog), the bootloader sees attempts = 1, increments to 2, tries again, then 3. At attempts = 3 = maximum it marks slot B invalid and boots slot A. Total time ≈ 3 × (boot time up to the 32.8 s watchdog) ≈ 1–2 minutes. The app (v1.0.0 again) reports "ROLLED_BACK, reason BOOT_ATTEMPTS" and the rollout dashboard stops the wave. Try exactly this in the FOTA Simulator tab with the "New image crashes on boot" fault.

9Beginner confusions, cleared up

"The bootloader copies the app into RAM and runs it there."
Not on a flash microcontroller. A Cortex-M runs code directly from flash (XIP). The bootloader only checks the image and changes a few CPU registers so the CPU starts executing at the app's address. Copying to RAM is what U-Boot does on a Linux board with DDR memory.
"The CPU finds main() by itself."
No. It reads word 1 of the vector table (the reset handler address) and starts there. The reset handler (startup code) sets up RAM and then calls main().
"The app and the bootloader can share interrupt handlers."
Each has its own vector table and its own handlers compiled against its own RAM layout. VTOR selects which table the CPU uses. Using the wrong one runs code that touches the wrong variables.
"If the CRC matches, the image is safe."
It is undamaged, not genuine. An attacker recomputes a CRC in microseconds. Only a signature proves who built the image.
"Two slots means the device can never be bricked."
Two slots protect against power cuts during download. You still need an atomic metadata commit, a boot attempt counter, a watchdog and a confirm step, or a valid-but-broken image will loop forever.
"Disabling interrupts makes flash erase safe for my CAN traffic."
The CPU stalls on any flash read during the erase, interrupts or not. Hiding interrupts only hides the problem; the fix is running the needed code from RAM or using a dual-bank chip.

10Say it like this: the 60-second answer

A bootloader is the small immutable program at the reset vector. On every reset it reads boot metadata, verifies the chosen application image with a hash and a signature against a public key it holds, and hands over the CPU in a reset-like state: interrupts and SysTick off, NVIC cleared, VTOR pointed at the app's vector table, MSP and PC loaded from the app's first two words. For FOTA I use A/B slots: the running app downloads the new image into the inactive slot in chunks, persisting a committed offset so it can resume, verifies it, and commits with one CRC-protected, sequence-numbered metadata record. After reboot the bootloader trial-boots the new image, incrementing an attempt counter before the jump and starting the independent watchdog. The app confirms after a real self-test; if it crashes, hangs or never confirms, the bootloader rolls back. Anti-rollback counters in OTP block old signed images, and the fleet is updated in gated waves.

Why a bootloader exists at all

▶

1. What is it?

A bootloader is a small program that sits at the very start of flash and runs before your real application every time the chip resets. Think of it as a gatekeeper at the door of the building: it checks that the "application" waiting inside is complete and genuine, and only then opens the door. If the application is missing or damaged, the gatekeeper does not open the door; it waits for a new one to be delivered.

It exists because once a product leaves the factory you can no longer plug a debugger into it. SWD (Serial Wire Debug, the 2-wire ARM debug port) and JTAG (Joint Test Action Group, the older 4/5-wire test and debug port) need a technician on site with a probe. A bootloader lets the device rewrite its own flash from data it receives over UART, CAN, USB, BLE or cellular. That process is called FOTA (Firmware Over The Air) when the data arrives wirelessly.

It has four jobs, in this order:

  1. Choose which application image should run (there may be two copies).
  2. Prove that image is intact (a CRC or hash) and, with secure boot, that you signed it (a digital signature).
  3. Hand over the CPU to the application in a clean, reset-like state.
  4. Receive new firmware when asked, or when no valid application exists.
  • Field updates without SWD/JTAG access. A swap station bolted into a wall, or 5 000 of them, cannot be reflashed by a technician with a probe.
  • A recovery path. If the app is corrupt, the bootloader is still there and can fall back to a known-good image or wait for a new one.
  • Trust. In a secure boot design the bootloader (or the ROM before it) checks a signature, so only firmware you signed can ever run.
  • Policy. Version checks, anti-rollback, hardware-revision checks, update scheduling.

2. How does it work, step by step?

Here is what physically happens on an STM32F407 (an ARM Cortex-M4 microcontroller with 1 MB of flash starting at address 0x0800_0000) from the moment power is applied:

  1. Power on / reset. The CPU core comes out of reset. It knows nothing about your code yet.
  2. The core reads two words from address 0x0000_0000, which is aliased to the start of flash (0x0800_0000) when the BOOT0 pin is low. Word 0 is loaded into MSP (Main Stack Pointer, the register that tells the CPU where the stack is). Word 1 is loaded into PC (Program Counter, the address of the next instruction). Because the bootloader is the program stored at 0x0800_0000, these are the bootloader's stack and the bootloader's Reset_Handler.
  3. The bootloader's startup code runs: copies initialised variables (.data) to RAM, zeroes .bss, sets up a basic clock.
  4. It checks for an explicit request: did the app ask to enter update mode (a magic word in RAM, card 06)? Is a "force update" button held?
  5. It reads the boot metadata: which slot is active, is a new image pending, how many times has it been tried (cards 08–09).
  6. It verifies the chosen image: header magic, size in range, CRC/hash matches, signature valid, security counter not too old.
  7. Valid → it jumps to the application (card 05). Invalid → it tries the other slot, and if nothing is valid it stays in recovery mode, listening for a new image.

3. Worked example: does it fit, and is it worth it?

Flash budget. A practical bootloader with a CAN or UART receiver and signature checking on Cortex-M4 is roughly:

4. Code, line by line: the bootloader's main()

int main(void)
{
    clock_init_hsi();                          /* 16 MHz internal clock, nothing fancy */
    if (boot_req == REQ_ENTER_BL) {           /* app asked for update mode            */
        boot_req = 0;
        recovery_loop();                       /* never returns                        */
    }
    meta_t m;
    int idx = meta_load(&m);                  /* newest valid metadata record         */
    if (idx < 0) m = META_FACTORY_DEFAULT;    /* first boot: slot A active            */

    if (image_check(slot_base(m.active)) == 0)
        jump_to_app(slot_base(m.active));      /* card 05                              */
    if (image_check(slot_base(other(m.active))) == 0)
        jump_to_app(slot_base(other(m.active)));
    recovery_loop();                           /* nothing bootable                     */
}

5. What goes wrong if…

  • …the bootloader has a bug? Everything after it can be repaired by it, but nothing repairs it except a technician. Symptom: every unit with that bootloader version fails the same way, and no OTA can fix it. That is why it is kept small (8–64 KB), heavily tested, write-protected (WRP option bytes on STM32), and ideally never updated in the field. If you must update it, use an immutable stage 0 that picks one of two stage-1 bootloaders (the same A/B idea one level down).
  • …you skip the bootloader and only use the vendor ROM loader? You can still flash at the factory, but you have no signature check, no rollback, and you cannot pull an image over your modem (card 02).
  • …the bootloader jumps to an image without verifying it? A half-written image after a power cut gets executed. Symptom: random behaviour, outputs (relays, chargers) toggling, HardFaults. Never execute what you have not verified.
"The bootloader is what copies the app into RAM." Not on a flash MCU: Cortex-M runs the app in place from flash (XIP). The bootloader only validates and jumps. Copying to RAM happens on application processors (e.g. U-Boot loading Linux into DDR) or MCUboot's optional RAM-load mode.
A bootloader is the small, immutable program at the reset vector that decides which application image to run, verifies it with a CRC and ideally a signature, hands over the CPU cleanly, and can receive a new image when the application is missing or asks for an update. It is what lets a fielded device be updated and recovered without a debugger, so it must be small, well-tested and essentially never changed.

ROM (system) bootloader vs custom bootloader

▶

1. What is it?

There are two kinds of bootloader on most microcontrollers. The ROM bootloader (ST calls it the "system memory bootloader") is a program the chip vendor burned into the silicon at manufacturing. You cannot erase or change it. A custom bootloader is one you write and place at the start of the normal user flash.

The ROM loader exists so that a completely blank chip can be programmed without a debugger, for example on a production line over a UART cable. Your custom loader exists because the ROM one knows nothing about your product: your CAN IDs, your modem, your security keys, your A/B slots.

Most MCUs ship with a ROM bootloader that the vendor burned into system memory. On the STM32F4 it lives at 0x1FFF_0000 (30 KB) and is selected by BOOT0 = 1, BOOT1 = 0 at reset, which aliases system memory at 0x0000_0000. It speaks USART (the AN3155 protocol: 0x7F autobaud, commands like 0x31 Write Memory, 0x44 Extended Erase), USB DFU and, on some parts, CAN, I²C and SPI (ST AN2606 lists which per device). The ESP32 equivalent is the mask-ROM download mode entered with GPIO0 low.

2. How does the chip choose which one runs?

On the STM32F4 the choice is made by two pins sampled at reset. BOOT0 is a dedicated pin; BOOT1 is shared with PB2.

4. Why the ROM loader is not enough for a product

  1. No authentication. On most STM32s the ROM loader writes whatever it is sent. Anyone with access to the UART pins can load any firmware (unless readout protection blocks it, which also blocks you).
  2. No A/B or rollback. It writes where the host tells it. Power cut halfway → half an image.
  3. Fixed pins and protocols. USART1 on PA9/PA10, USB DFU on PA11/PA12, and so on. Your board may use those pins for something else.
  4. No network. It cannot drive a cellular modem, run TLS or talk MQTT.

5. What goes wrong if…

  • …BOOT0 floats? Noise can make it read 1 at reset; the product randomly boots into the ROM loader and looks dead. Symptom: "sometimes after a brown-out the unit does nothing until power-cycled". Fix: a 10 kΩ pull-down on BOOT0.
  • …you jump into the ROM without de-initialising? An application interrupt still enabled fires inside ROM code, which has no handler for it: HardFault. Or the PLL is still selected and the ROM's autobaud measures the wrong timing, so it never answers 0x79.
  • …you set RDP Level 2 on production units? The ROM loader can no longer read or write flash at all (and debug is permanently disabled). Your custom bootloader is then the only update path, so it must be solid.
Interview angle: "If you have a ROM bootloader, why write your own?" Because the ROM loader has no authentication, no A/B or rollback, uses fixed pins and protocols, and cannot pull an image over your cellular link. Keep the ROM path wired to a test pad as the factory and last-resort recovery route.
The ROM bootloader is vendor code in mask ROM, selected by BOOT0 on STM32, that speaks fixed protocols like the AN3155 UART protocol or USB DFU. It cannot be bricked, so it is ideal for factory programming and last-resort recovery, but it has no signature check, no A/B or rollback, and no network stack. A custom bootloader adds my transport, my security policy and my update strategy, and I keep the ROM path on a test pad as the safety net.

Flash partitioning and why sector sizes drive the layout

▶

1. What is it?

Flash partitioning means dividing the chip's flash into fixed regions, each with one job: the bootloader, the boot metadata, configuration data, and one or two application slots (a slot is a region big enough to hold one complete firmware image). The partition map is decided once, baked into the bootloader and the linker scripts, and practically never changes in the field.

The layout is driven by one physical fact about flash memory:

Flash can only be erased in whole sectors (or pages) and programmed in small aligned units. Erase sets bits to 1; programming can only clear bits to 0. Every partition boundary therefore has to sit on a sector boundary, so that erasing one partition never touches another.

A sector (ST's word; other vendors say page or block) is the smallest piece of flash that can be erased in one operation. If two partitions shared a sector, erasing one would destroy part of the other.

2. How do erase and program actually work?

  1. Each flash bit is a transistor with a floating gate that can hold charge. No charge reads as 1, charge reads as 0.
  2. Erase pulls the charge out of every cell in the sector at once. Result: every byte reads 0xFF. This is slow (hundreds of ms to seconds).
  3. Program pushes charge into selected cells, turning chosen 1-bits into 0-bits. It works on small aligned units (on the F407: 8, 16 or 32 bits at a time; about 16 µs per 32-bit word).
  4. Programming can never turn a 0 back into a 1. Only an erase of the whole sector can.
erased byte    1111 1111  (0xFF)
program 0xA5   1010 0101  (0xA5)   ok: only 1→0 changes
program 0x5A over it:
  old          1010 0101
  new          0101 1010
  result = AND 0000 0000  (0x00)   ← not 0x5A! you must erase first

3. Worked example: sizing the F407 layout

Suppose today's application image is 300 KB and you expect 25 % growth over the product's life.

  1. Future image: 300 KB × 1.25 = 375 KB.
  2. Add the image header (0x200 = 0.5 KB) and a trailer/TLV area for hash and signature (~0.5 KB): 375 + 1 = 376 KB.
  3. The slot must be whole sectors. Above sector 4 every sector is 128 KB, so 376 / 128 = 2.94 → round up to 3 sectors = 384 KB.
  4. Two slots: 2 × 384 = 768 KB = sectors 5–10. Sector 11 (128 KB) is left over for a scratch area or a log.
  5. Bootloader: 32 KB = sectors 0–1. Metadata needs two copies → sectors 2 and 3 (16 KB each). Sector 4 (64 KB) holds config/calibration/certificates.
  6. Check the total: 32 + 16 + 16 + 64 + 384 + 384 + 128 = 1 024 KB. ✓

Erase time check: one 128 KB sector is typically 1 s (max 2 s) on the F407, so erasing a whole slot is 3 × 1 = 3 s typical, 6 s worst case. Your watchdog and your communication timeouts must allow that.

Why this shape: the small 16 KB sectors at the bottom are the only cheap place for a small bootloader and small metadata records. Putting metadata in a 128 KB sector would cost 1 s of erase time and 128 KB of space for a 64-byte record. Uniform-page parts (STM32L4/G4: 2 KB pages; nRF52: 4 KB; ESP32 external SPI flash: 4 KB sectors) make layout easy; the F4's mixed sizes are a classic interview trap.

4. The partitions and what each holds

  • Bootloader — immutable, write-protected (WRP option bytes on STM32).
  • Slot A / slot B — two equal-size image slots. "Primary/secondary" in MCUboot, ota_0/ota_1 in ESP-IDF.
  • Scratch — temporary sector used by swap algorithms to exchange A and B without losing either on power loss.
  • Metadata / trailer — which slot is active, which is pending, boot attempt counter, confirmed flag, security counter. Usually two copies with sequence numbers.
  • Config — device identity, keys, calibration. Kept outside both slots so an update never erases it.

The same map has to appear in three places, and they must agree:

5. What goes wrong if…

  • …a partition boundary is not on a sector boundary? Say metadata started at 0x0800_6000 (inside sector 1). Erasing metadata would erase sector 1, which also contains the end of the bootloader. Symptom: the first metadata update bricks the device.
  • …you put the 64-byte metadata record in a 128 KB sector? Every state change costs about 1 s of erase and wastes 128 KB. With 4 state changes per update and 10 000 erase cycles of endurance, that sector lasts 2 500 updates (fine) but every boot that updates metadata stalls for a second.
  • …you write into a location that is not erased? You get the AND of old and new data (on F4) or a programming error flag (PROGERR on L4/G4). Symptom: CRC mismatch after "successful" writes.
"Slot B just needs to be big enough for today's image." Size both slots for the image you will have in three years, plus header and trailer. Shrinking a slot later needs a bootloader change, which is the one thing you cannot update safely.
Flash can only be erased in whole sectors and programmed by clearing bits, so every partition must start and end on sector boundaries. The bootloader, both linker scripts and the update code all share one header with these addresses.

The application image header

▶

1. What is it?

An image is the complete binary you flash: code, constant data and the vector table. An image header is a small structure placed in front of it (a "label on the box") that tells the bootloader what is inside without running it: is there an image at all, how many bytes, what version, which board it is for, and the numbers needed to check it (CRC, hash, signature).

The bootloader must be able to answer "is there an image here, how big, what version, is it intact, did we sign it?" without running it. So every image carries a header (in front) and often a trailer or TLV area (after).

2. How does the bootloader use it, step by step?

  1. Read the 32-bit magic at the slot base. Erased flash reads 0xFFFF_FFFF, so a wrong magic means "empty slot". Stop.
  2. Check hdr_size and img_size are sane: the image must fit inside the slot (hdr_size + img_size ≤ SLOT_SIZE), written so the addition cannot overflow.
  3. Check load_addr equals where this slot's code starts. An image linked for slot A will crash in slot B (card 07).
  4. Check hw_compat has this board's bit set.
  5. Compute CRC-32 over the payload and compare (cheap, catches accidents).
  6. Compute SHA-256 over header fields + payload, compare with sha256, then verify sig against the public key (card 11).
  7. Compare security_cnt with the minimum stored in OTP (card 13).
  8. Only if every check passes is the image allowed to run.

  • …the signature does not cover the header? An attacker takes a validly signed v1.0 image and edits security_cnt from 1 to 99, or edits hw_compat. The payload signature still verifies. Always sign header fields (everything except the signature itself) plus payload.
  • …you trust img_size blindly? A corrupted header with img_size = 0xFFFF_FFF0 makes the hash loop read past the end of flash into unmapped memory: BusFault inside the bootloader, before any decision. Range-check first.

  • The signature must cover the header fields too (version, security counter), otherwise an attacker edits the version of a validly signed old image.

The jump to application: every step and why

▶

1. What is it?

The jump is the moment the bootloader stops and the application starts. It looks like a single function call, but the application was written and tested assuming it starts straight after a hardware reset, with every register at its reset value. The bootloader has been running for a while: it changed clocks, enabled interrupts, used timers. The jump procedure exists to undo all of that so the application sees a "fake reset".

A function-pointer call changes exactly one thing: the PC. Everything else (VTOR, MSP, PRIMASK, enabled and pending interrupts, running peripherals, clock tree, CONTROL, FPU state) is inherited by the app. The app was written for a fresh reset, so the bootloader's job is to fake one as closely as possible.

Terms used below: VTOR = Vector Table Offset Register (address of the table the CPU uses to find interrupt handlers). PRIMASK = a 1-bit register that, when 1, blocks all interrupts with configurable priority. NVIC = Nested Vectored Interrupt Controller (enables, prioritises and latches pending interrupts). SysTick = the 24-bit timer built into every Cortex-M core. CONTROL = core register that selects privileged/unprivileged mode (nPRIV), which stack pointer is used (SPSEL: 0 = MSP, 1 = PSP) and whether floating-point context is active (FPCA). DSB/ISB = Data/Instruction Synchronization Barriers.

2. How does it work, step by step?

  1. Read the app's first two words at its vector table base: initial MSP and reset vector.
  2. Validate them: MSP inside SRAM, reset vector odd (Thumb) and inside the slot.
  3. Disable interrupts (PRIMASK = 1).
  4. Stop SysTick and clear its pending bit.
  5. Return clocks and peripherals to reset state.
  6. Disable and un-pend every NVIC interrupt.
  7. Point VTOR at the app's table, then DSB + ISB.
  8. CONTROL = 0 (privileged, MSP, no FP context).
  9. MSP = app word 0.
  10. Branch to app word 1.

  1. MSP check: F407 SRAM1+SRAM2 is 0x2000_0000–0x2001_FFFF (128 KB). The stack grows down and the first push writes at MSP − 4, so MSP = 0x2002_0000 (one past the end) is the correct "top of RAM". The check is 0x2000_0000 < msp ≤ 0x2002_0000.
  2. Reset vector: 0x0802_01C5 is odd → bit 0 = 1 → Thumb ✓. Real code is at 0x0802_01C4.
  3. Inside slot? 0x0802_0000 ≤ 0x0802_01C5 < 0x0802_0000 + 0x6_0000 (384 KB) = 0x0808_0000 ✓.
  4. Erased flash would give 0xFFFF_FFFF for both: MSP check fails → do not jump.
  5. VTOR alignment: the F407 has 16 system exceptions + 82 interrupts = 98 entries × 4 bytes = 392 bytes. Next power of two ≥ 392 is 512 = 0x200. 0x0802_0000 / 0x200 = 0x4010 exactly → aligned ✓. (If the header pushes the table to 0x0802_0200, that is also a multiple of 0x200 ✓.)

typedef void (*entry_t)(void);

__attribute__((noreturn)) void jump_to_app(void)
{
    uint32_t msp   = ((volatile uint32_t *)APP_BASE)[0];
    uint32_t reset = ((volatile uint32_t *)APP_BASE)[1];

    /* 0. sanity: SP inside SRAM, reset vector odd (Thumb) and inside the slot */
    if (msp < 0x20000000 || msp > 0x20020000 || !(reset & 1u) ||
        reset < APP_BASE || reset >= APP_BASE + SLOT_SIZE) { enter_recovery(); }

    __disable_irq();                                  /* 1. PRIMASK = 1                  */

    SysTick->CTRL = 0; SysTick->LOAD = 0; SysTick->VAL = 0; /* 2. stop SysTick        */
    SCB->ICSR = SCB_ICSR_PENDSTCLR_Msk;               /*    and clear its pending bit   */

    HAL_RCC_DeInit();                                 /* 3. back to HSI 16 MHz          */
    HAL_DeInit();                                     /*    reset APB/AHB peripherals   */

    for (uint32_t i = 0; i < 8; i++) {                /* 4. NVIC: 8 regs x 32 = 240 IRQ  */
        NVIC->ICER[i] = 0xFFFFFFFF;                   /*    disable every IRQ           */
        NVIC->ICPR[i] = 0xFFFFFFFF;                   /*    clear every pending IRQ     */
    }

    SCB->VTOR = APP_BASE;                             /* 5. app's vector table          */
    __DSB(); __ISB();

    __set_CONTROL(0);                                 /* 6. privileged, MSP, FPCA = 0   */
    __ISB();
    __set_MSP(msp);                                   /* 7. app's initial stack         */

    ((entry_t)reset)();                               /* 8. BLX: bit0=1 keeps Thumb     */
    for (;;) {}
}

  1. Validate first: jumping to erased flash loads MSP = 0xFFFF_FFFF and PC = 0xFFFF_FFFE, an instant HardFault/lockup.
  2. Disable IRQs: between "VTOR changed" and "MSP changed" an interrupt would run a handler with a half-switched context.
  3. SysTick is a core peripheral: HAL_DeInit() does not stop it. If it keeps ticking, the app's SysTick_Handler fires before HAL_Init() has set up its tick variable.
  4. RCC/peripheral de-init: the app's SystemClock_Config() assumes it starts on HSI with the PLL off. On STM32 you cannot reconfigure the PLL while it is the system clock source, so init fails with a timeout.
  5. NVIC clear: a UART IRQ left enabled and pending will fire the moment the app enables interrupts, before the app has initialised that UART. Clearing pending bits (ICPR) is as important as disabling (ICER).
  6. VTOR: on Cortex-M3/M4/M7 VTOR is writable; it must be aligned to the table size rounded up to a power of two (F407: 98 entries × 4 = 392 B → 512-byte alignment; bits [6:0] are always 0). Cortex-M0 has no VTOR; M0+ has it optionally. On M0 you copy the app's vector table into SRAM and remap SRAM to 0x0 (SYSCFG_CFGR1.MEM_MODE = 11 on STM32F0).
  7. CONTROL: if the bootloader ran an RTOS, CONTROL.SPSEL = 1 (PSP) and maybe nPRIV = 1. Zero it so the app starts privileged on MSP. FPCA = 1 left set causes extended stack frames the app did not expect.
  8. MSP: the app's startup reloads SP from _estack in most startup files, but not all, and any C code between __set_MSP and the jump must not use stack variables: read reset into a register first (as above).
  9. Branch: the reset vector already has bit 0 set; calling it through a function pointer emits BLX, which keeps Thumb state.

Last, the app must do its part: set VECT_TAB_OFFSET (or VTOR) to its own base in SystemInit(), because many vendor SystemInit() implementations write VTOR = FLASH_BASE and silently undo step 5, and call __enable_irq(), because PRIMASK = 1 survives the jump and HAL_Init does not clear it.

The alternative: reset with a magic word

▶

1. What is it?

Card 05 tears everything down by hand. This card is the lazy and more reliable alternative: let the hardware reset do the cleanup. You leave a short note in a piece of RAM that is not cleared by reset, trigger a reset, and the first lines of code that run read the note and act on it.

Two terms: a system reset is a reset triggered by software (on Cortex-M by writing AIRCR, the Application Interrupt and Reset Control Register at 0xE000_ED0C). It resets the core and the peripherals but does not remove power, so SRAM keeps its contents. A .noinit section is a linker section the startup code neither copies into nor zeroes, so whatever was there before the reset is still there.

Instead of tearing down every peripheral by hand, let the hardware do it: store a request somewhere that survives a system reset but not a power cycle, call NVIC_SystemReset(), and check the request first thing in the bootloader's (or the app's) Reset_Handler, before any peripheral is touched.

2. How does it work, step by step?

  1. App decides to start the new image (or enter update mode). It writes a 32-bit magic value, e.g. 0xB00710AD, into a variable in .noinit.
  2. __DSB() makes sure the store has actually reached SRAM.
  3. NVIC_SystemReset() writes 0x05FA_0004 to AIRCR. 0x05FA in the top half is the VECTKEY (writes without it are ignored); bit 2 is SYSRESETREQ.
  4. Reset happens: every peripheral, the NVIC, SysTick and the clock tree go back to reset values. SRAM is untouched.
  5. The bootloader's Reset_Handler runs. Before it zeroes .bss or touches peripherals, it reads the magic word.
  6. If it says "run app", it clears the word and jumps immediately: the app inherits a genuinely pristine state. If it says "enter bootloader", it clears the word and starts the update receiver.

3. Code, line by line

/* Linker: .noinit (NOLOAD) : { *(.noinit*) } > RAM   -- not zeroed, not copied */
__attribute__((section(".noinit"))) volatile uint32_t boot_req;
#define REQ_ENTER_BL   0xB00710ADu
#define REQ_RUN_APP    0xA5A5C3C3u

void request_bootloader(void) {           /* called from the app */
    boot_req = REQ_ENTER_BL;

    NVIC_SystemReset();                     /* AIRCR = 0x05FA0004: VECTKEY | SYSRESETREQ */

if (boot_req == REQ_ENTER_BL) { boot_req = 0; stay_in_bootloader(); }

4. Worked example: why a 32-bit magic and not a flag byte

On power-up SRAM bits settle randomly. A single-byte flag == 1 has a 1 in 256 chance of being accidentally true; with 5 000 stations each powering up once a day, that is about 5 000 / 256 ≈ 20 units per day randomly entering update mode. A 32-bit magic brings that to 5 000 / 4.29×10⁹ ≈ one false trigger every 2 350 years across the fleet.

You can also tell the reset reason apart using RCC_CSR (Control/Status Register) on the F4: bit 28 SFTRSTF = software reset, bit 27 PORRSTF = power-on reset, bit 29 IWDGRSTF = independent watchdog reset, bit 26 PINRSTF = reset pin. Write RMVF (bit 24) to clear them after reading. A request word found after a POR should be ignored.

5. Other places to store the request

  • Peripherals, NVIC, SysTick and clocks are all at reset values, so the app starts in exactly the state it was tested in. This is the most robust handoff.
  • SRAM survives a system reset on STM32, but contents are random on power-up: always use a full 32-bit magic, never a single flag byte, and clear it once consumed.
  • Alternatives to .noinit: RTC backup registers (RTC->BKP0R on F4, 20 × 32-bit; needs PWR->CR |= PWR_CR_DBP to unlock, survives resets and, with VBAT, power loss), a reserved word at the top of SRAM below the stack, or the reset-cause flags in RCC->CSR.
  • Pitfall: if the bootloader's startup code zeroes all of SRAM (some do, for ECC-SRAM initialisation on STM32H7/G4 parity SRAM), your magic word is erased before you read it. Put the check before the zero loop or use a backup register.

6. What goes wrong if…

  • …the bootloader's startup zeroes all RAM first? The magic is gone before you read it. Symptom: "the app requests the bootloader, the device resets, and boots straight back into the app". Read the word in the first few instructions of Reset_Handler, or use an RTC backup register.
  • …the bootloader and app put .noinit at different addresses? Same symptom: each reads a different word.
  • …you forget to clear the word? The device is stuck: every reset enters the bootloader again.
  • …you forget the DSB? Rare on Cortex-M4 (the store buffer usually drains), but on M7 with caches and write buffers the store may not have landed; the reset loses it intermittently.
Instead of de-initialising every peripheral by hand, I write a 32-bit magic word into a .noinit RAM section or an RTC backup register, call NVIC_SystemReset, and check that word at the very top of Reset_Handler before anything zeroes RAM. The hardware reset puts every peripheral, the NVIC and the clocks back to reset values, so the app starts in exactly the state it was tested in. I clear the word once consumed and ignore it after a power-on reset.

Update strategies: in-place, A/B, swap, bank swap

▶

1. What is it?

An update strategy is the answer to one question: where do the new bytes go while they arrive, and when does the old image stop being the one that boots? Every strategy is a trade between flash space, power-loss safety and the ability to go back (rollback = returning to the previous working image).

Words used below: slot A / slot B = two equal regions that can each hold an image. Primary / secondary = MCUboot's names (primary is where code runs, secondary is where new images are downloaded). Scratch = a spare sector used as temporary storage while exchanging A and B. Bank = an independent half of the flash array with its own read/program circuitry. XIP = execute in place (the CPU fetches instructions directly from flash).

2. How each one works, step by step

(a) Single-slot in-place

  1. App resets into the bootloader.
  2. Bootloader erases the app (from here on, no valid app exists).
  3. Chunks arrive and are written one by one.
  4. Last chunk verified → write "app valid" flag → boot it.

(b) A/B direct boot

  1. Running from A, the app downloads into B in the background.
  2. Verify B, write metadata "next boot = B (trial)".
  3. Reset; the bootloader boots B where it is. A is untouched and remains the fallback.

(c) Staged + swap (MCUboot swap-scratch)

  1. Download into secondary (B).
  2. Bootloader exchanges A and B one sector at a time through scratch, logging progress in the trailer.
  3. New image now runs from A (its link address); old image now sits in B.
  4. If the new one is not confirmed, the next boot swaps back (revert).
swap-scratch, one sector index i (3 erases + 3 copies per step):

3. Worked example: what a swap costs on the F407

Slot = 3 sectors × 128 KB. For each of the 3 sector indices, swap-scratch erases 3 sectors (scratch, B[i], A[i]) and copies 3 × 128 KB.

  1. Erases: 3 indices × 3 = 9 sector erases × ~1 s = ~9 s.
  2. Programming: 3 × 3 × 128 KB = 1 152 KB = 294 912 words × 16 µs ≈ 4.7 s.
  3. Total swap ≈ 14 s typical, nearly 28 s worst case (2 s erases). The station is offline that long on every update, and again on a revert.
  4. Wear: the single scratch sector is erased 3 times per swap. Endurance 10 000 cycles → 10 000 / 3 ≈ 3 300 swaps (revert counts as a swap). Fine for a station, a problem for a device updated daily.

Compare an STM32H7 with SWAP_BANK: write bank 2 while running from bank 1 (no stall), then one option-byte write and reset. Switch-over takes milliseconds and costs no extra erases.

An image is linked to an address. A binary linked for slot A (0x0802_0000) has absolute addresses in its vector table, literal pools and function pointers; run it from 0x0808_0000 and the first absolute branch goes back into slot A. Options: build two binaries per release (one per slot; ESP32 avoids this because the cache MMU maps either partition to the same virtual address), build position-independent code (-fPIC -msingle-pic-base, painful on Cortex-M), or swap/copy so the image always runs from slot A. That last point is why MCUboot's default modes copy or swap.

Same binary, run from the wrong slot (linked for 0x0802_0000, placed at 0x0808_0000):
vector[1] = 0x0802_01C5   → reset handler address still points into slot A!
literal pool: ldr r0,=0x08021234 (a const table)  → reads slot A's data
→ the "B" code calls into "A" code: mixing two versions = undefined behaviour

4. MCUboot modes

  • swap-scratch: for each sector: copy B → scratch, A → B, scratch → A, recording state in the trailer after each step. Works with unequal sectors, but the scratch sector is erased once per swapped sector, so it wears out fastest (10 k cycles on F4 / ~ 100 updates of 100 sectors).
  • swap-move: first shift slot A up by one sector, then swap sector by sector into the hole. No scratch, wear spread evenly; needs equal sector sizes and one extra sector in the primary slot.
  • swap-offset (newer MCUboot): the secondary image is written at a one-sector offset so the "move" pass is not needed; faster than swap-move.
  • overwrite-only: simplest, fastest, no revert. Good for very small flash, if your app is robust and you have another recovery path.
  • direct-xip: boot the slot with the highest valid version in place; images must be built per slot. ram-load: copy the chosen image to RAM and run there.

5. Hardware dual-bank (vendor-specific)

  • STM32F42x/43x (2 MB): two 1 MB banks; option bit BFB2 makes the system boot from bank 2, and the SYSCFG_MEMRMP.UFB_MODE bit swaps which bank appears at 0x0800_0000.
  • STM32L4/G4 dual-bank parts: option bit BFB2, read-back in SYSCFG_MEMRMP.FB_MODE. Both banks are aliased so the image can be linked once for 0x0800_0000.
  • STM32H7: option bit SWAP_BANK in FLASH_OPTCR; after option-byte launch, bank 2 appears at 0x0800_0000. One binary, linked once.
  • The big win besides layout: read-while-write. You can program bank 2 while executing from bank 1 without the CPU stalling.

6. What goes wrong if…

  • …you use in-place on a cellular product? A link drop after erase leaves only the bootloader. If the bootloader has no modem/TLS stack (most don't), the unit waits for a host that never comes: field visit.
  • …you use overwrite-only and the new image is broken? It is valid (signature OK) so the bootloader keeps booting it. Boot loop, no way back. Try this in the simulator.
  • …you boot B directly with an image linked for A? It runs a few instructions then jumps into slot A's code. Symptom: weird mixed-version behaviour, HardFaults that addr2line resolves to the old image.
"A/B means we never brick." A/B protects the image. You still brick if the metadata commit is not atomic, if the bootloader itself has a bug, or if the new image is valid but broken and nothing triggers a rollback (no boot counter, no watchdog, no confirm step).
In-place is cheapest but leaves a window with no valid image and no rollback. A/B keeps the old image untouched while downloading; it either boots the new slot directly, which needs per-slot builds or an address alias, or swaps it into the primary slot sector by sector with resumable progress, which gives revert. Dual-bank parts like the H7 do the swap with one option bit and read-while-write. My default for a connected product is A/B with trial boot and revert.

The update state machine and the atomic commit

▶

1. What is it?

The update state machine is the list of states a device goes through during an update (idle, downloading, verifying, pending, testing, confirmed, rolled back) and the rules for moving between them. The atomic commit is the single moment where "boot the old image" becomes "boot the new image". Atomic means it either happened completely or not at all; there is no half-state, even if power fails in the middle.

Every robust FOTA design reduces to the same sequence. The rule: at every instant, at least one bootable, known-good image exists, and the metadata says which one.

2. How does it work, step by step?

IDLE ──job──▶ DOWNLOAD ──all chunks──▶ VERIFY ──sig ok──▶ MARK_PENDING ──▶ REBOOT
  ▲             │ resume after reset       │ fail: erase B, report    │ (one atomic write)
  │             ▼                          ▼                          ▼
  │         (slot B only)               IDLE (still on A)       BOOTLOADER: pending?
  │                                                              attempts++ (persist)
  │                                                              verify again, boot B in TEST
  │                                                                     │
  │      CONFIRMED ◀── app self-test ok, cloud reachable ── TEST_BOOT ──┤
  │       (A becomes the fallback)                                      │ crash / WDT / no confirm
  └──────────── ROLLBACK: mark B invalid, boot A, report ◀── attempts ≥ N
  1. IDLE → DOWNLOAD: a job arrives. Erase slot B. Write chunks. Persist the committed offset after each one.
  2. DOWNLOAD → VERIFY: all bytes in. Hash and verify the signature by reading slot B back from flash.
  3. VERIFY → MARK_PENDING: write one metadata record: pending = B, attempts = 0. This write is the commit.
  4. REBOOT: the bootloader reads metadata, sees pending = B, increments attempts, persists it, starts the watchdog and boots B in TEST state.
  5. TEST → CONFIRMED: the app passes its self-test and writes active = B, pending = none.
  6. TEST → ROLLBACK: crash, hang or no confirm until attempts reach N: the bootloader marks B invalid and boots A.

3. Worked example: ping-pong records through one update

Two metadata sectors (F407 sectors 2 and 3). Each record = {seq, active, pending, attempts, crc}. At boot the bootloader takes the record with a valid CRC and the higher seq.

Notice the rule: each write goes to the sector that does not hold the current record. Erasing that sector destroys only the older copy, which nobody needs any more. At no instant is the newest valid record at risk.

CRC cost: a 16-byte record CRC takes about 16 × 8 = 128 cycles = 0.8 µs at 168 MHz. Erasing a 16 KB sector is ~250 ms typ. So every state change costs about a quarter of a second, dominated by the erase.

4. Making the commit atomic on flash

  • Ping-pong records with sequence numbers. Two metadata sectors. To change state, write a complete new record (state, active slot, attempts, seq = old + 1, CRC32) into the other sector, read it back, and only then is it valid. At boot, read both and take the one with a valid CRC and the higher sequence number. A power cut mid-write leaves a record with a bad CRC: it is ignored, the previous state stands.
  • Append-only log in one sector: each state change is a new record after the last; erase only when full (after copying the current state to the other sector). Fewer erases, which matters at 10 k cycles.
  • Write-once flags (MCUboot trailer): image_ok, copy_done, magic. Each flag sits in its own write-aligned unit so it can go from erased (0xFF) to set with a single program operation. "Erased" vs "written" is the state; no read-modify-write.
  • Order matters: write the image, verify it, then write the pointer to it. Never write a "valid" flag before the data it describes is on flash.

Code for the boot-time selection (sequence numbers compared with wrap-safe arithmetic):

static int seq_newer(uint32_t a, uint32_t b) { return (int32_t)(a - b) > 0; }

int meta_pick(const meta_t *r0, const meta_t *r1)
{
    int v0 = meta_valid(r0), v1 = meta_valid(r1);   /* magic + CRC each      */
    if (v0 && v1) return seq_newer(r1->seq, r0->seq) ? 1 : 0;
    if (v0) return 0;
    if (v1) return 1;
    return -1;                                       /* factory default      */
}
CODEMEANING

5. What goes wrong if…

  • …you use a single record that is erased and rewritten in place? Power cut between erase and program → no record at all. Symptom after an outage: device boots the factory default slot, which may be the old or even an erased slot.
  • …you write "valid" before the image is complete? A power cut leaves a flag that says "B is good" next to a half-written B. The bootloader trusts the flag and jumps into garbage.
  • …the record has no CRC? A torn write can leave plausible-looking bytes (e.g. pending = B written, attempts not yet written = 0xFF = 255): the bootloader immediately rolls back a perfectly good update.
ECC flash trap (STM32L4/G4/H7): an interrupted program operation can leave a double-word with an uncorrectable ECC error. Reading it raises an NMI (ECCD), not a nice CRC mismatch. Your metadata reader must survive that: handle the NMI, mark the record bad, continue. Do not discover this in the field.
The invariant is that at every instant at least one verified, bootable image exists and the metadata says which. I make the switch atomic with two metadata copies, each with a sequence number and CRC: a new state is written completely into the older copy, and at boot the valid copy with the highest sequence wins, so a torn write is just ignored. I always write data before the pointer to it, and on ECC flash I handle the NMI a torn double-word can cause.

Boot counter, test boot and watchdog-driven rollback

▶

1. What is it?

Card 08 makes sure a power cut cannot hurt you. This card handles the other danger: an image that is perfectly intact and correctly signed, but does not work. Rollback must be triggered without the new image's help, because the new image is the broken thing.

A signed, CRC-perfect image can still be broken: it hard-faults on this board revision, it deadlocks when the CAN bus is busy, it boots but can no longer reach the server. Rollback has to be triggered without the new image's cooperation, because the new image is the thing that is broken.

Terms: trial boot (also "test boot") = running a new image on probation. Boot attempt counter = how many times the bootloader has started this trial image. IWDG = Independent Watchdog on STM32: a down-counter clocked by the separate ~32 kHz LSI (Low Speed Internal) oscillator that resets the chip if software does not reload ("kick") it in time. Confirm = the app telling the bootloader "I am good, keep me".

2. How does it work, step by step?

  • Test boot: the bootloader boots the new image as "pending/trial", not yet trusted.
  • Boot attempt counter: incremented by the bootloader and persisted before jumping. If the app crashes, the counter has already been spent. After N attempts (typically 3) the bootloader stops trying and reverts.
  • Independent watchdog (STM32 IWDG, LSI-clocked ~32 kHz): started by the bootloader before the jump. Once started it cannot be stopped except by reset, so a hung app is guaranteed to come back to the bootloader. Set the window longer than the app's worst-case init (e.g. prescaler /256, reload 4095 → ~32 s).
  • Confirm: the app marks itself good only after a meaningful self-test: peripherals up, sensors plausible, comms to the cloud or the master ECU working. ESP-IDF: esp_ota_mark_app_valid_cancel_rollback(). Zephyr/MCUboot: boot_write_img_confirmed().
  • What counts as healthy is a product decision. Confirming in the first line of main() defeats the mechanism; never confirming causes a rollback loop.

3. Worked example: choosing the watchdog timeout

IWDG timeout formula: T = (4 × 2^PR) × (RLR + 1) / f_LSI, where PR is the prescaler setting (0–6 → divide by 4, 8, 16 … 256) and RLR is the 12-bit reload value (0–4095).

  1. Maximum: PR = 6 → divider 4 × 2⁶ = 256. RLR = 4095 → 4 096 counts.
  2. f_LSI nominal 32 kHz on the F4: T = 256 × 4096 / 32 000 = 1 048 576 / 32 000 = 32.8 s.
  3. LSI is not accurate: the F4 datasheet range is about 17–47 kHz. At 47 kHz, T = 1 048 576 / 47 000 = 22.3 s. Design with the shortest value.
  4. Your app's worst-case init before its main loop starts kicking: say clocks 5 ms, modem power-up 8 s, SIM registration up to 15 s. If that 15 s runs without kicking, you need T > 23 s → you are on the edge at 22.3 s. Better: kick the watchdog from the init sequence between stages.
  5. Time to rollback with MAX_ATTEMPTS = 3 and a hang: about 3 × 22–33 s ≈ 1–1.6 minutes.

5. What goes wrong if…

  • …the app confirms in the first line of main()? A broken CAN driver that crashes 2 s later is now "confirmed". Rollback never happens. Symptom: fleet stuck on a crashing image, each unit resetting every few seconds.
  • …the app never confirms? Works for a day, then the next reset reverts it, and the server re-sends it: a rollback loop (Scenario 03; try it in the simulator).
  • …MAX_ATTEMPTS = 1? One brown-out during the first trial boot reverts a good update. The counter cannot tell a power cut from a crash, so allow 2–3.
  • …the watchdog timeout is shorter than first-boot work (e.g. a 40 s config migration)? Every trial boot is killed before it can confirm. Scenario 10.
"The app increments the boot counter." If the app crashes before reaching that line, the counter never moves and you boot the broken image forever. The bootloader owns the counter; the app only clears it (confirm).
Rollback cannot depend on the new image working, so the bootloader owns it: it boots the new image as a trial, increments and persists an attempt counter before the jump, and starts the independent watchdog, which cannot be stopped. A crash or hang brings it back to the bootloader, and after N attempts it marks the image invalid and boots the old one. The app clears the trial state only by confirming after a meaningful self-test, such as peripherals up and the cloud reachable.

Flash programming constraints that bite FOTA code

▶

1. What is it?

Writing flash from your own code is not like writing RAM. Flash has rules about alignment (where a write may start), size (how many bits per write), order (erase before program), locking (it must be unlocked with keys) and timing (the CPU may freeze while it works). FOTA code writes flash constantly, so every one of these rules shows up as a bug sooner or later.

2. How a program operation works, step by step (STM32F4)

  1. Unlock: write KEY1 = 0x4567_0123 then KEY2 = 0xCDEF_89AB to FLASH_KEYR. A wrong sequence locks the flash controller until the next reset.
  2. Wait for BSY (bit 16 of FLASH_SR) = 0.
  3. Clear old error flags in FLASH_SR (write 1 to clear): leftovers block new operations.
  4. Set PSIZE (program size: 00 = x8, 01 = x16, 10 = x32, 11 = x64) and PG = 1 in FLASH_CR.
  5. Write the data to the flash address with a normal store of that size.
  6. Wait for BSY = 0 (~16 µs for a word).
  7. Check error flags, read back and compare.
  8. Clear PG, lock (LOCK bit 31 in FLASH_CR).

3. Worked example: L4 alignment arithmetic

The STM32L4 programs 64-bit double-words (8 data bytes plus 8 hidden ECC bits). Writes must start on an address divisible by 8 and must be exactly 8 bytes.

  1. Network chunk of 1 020 bytes. 1 020 / 8 = 127.5 → not a whole number of double-words.
  2. Chunk 1 at offset 0: 127 full double-words (1 016 bytes) + 4 leftover bytes.
  3. Chunk 2 starts at offset 1 020 = 0x3FC. 0x3FC mod 8 = 4 → misaligned → PGAERR.
  4. Fix: a staging buffer. Bytes are collected until 8 are available, then one double-word is programmed. At the end, the last partial buffer is padded with 0xFF.
  5. Image of 307 200 bytes: 307 200 / 8 = 38 400 double-word writes. At ~82 µs each (L4 typical double-word program time), that is about 3.1 s of programming.

5. The read-while-write stall, explained

  1. The CPU fetches instructions from flash at 0x0800_xxxx.
  2. You start erasing a 128 KB sector in the same bank.
  3. The flash array is busy. Any read from that bank (instruction fetch, constant read, vector table read on interrupt entry) is held by the bus until the erase finishes.
  4. The CPU simply stops for ~1 s. No interrupt can run because the handler code and the vector are both in flash.
  5. Fix: run the flash driver and the time-critical ISRs from RAM, copy the vector table to RAM and point VTOR there during the update, or use a dual-bank part.

6. What goes wrong if…

  • …you program a double-word twice on L4/G4? The ECC bits were already written; a second program sets PROGERR, or produces an ECC error on read. Only all-zeros overwrites are allowed on some parts. Write-once flags must each have their own double-word.
  • …you don't clear error flags? The first error poisons all later operations. Symptom: "after one failed write, nothing ever writes again until reset".
  • …you erase with code running from the same bank? CAN heartbeats stop for seconds; slave nodes declare the master lost (Scenario 06).
"Disable interrupts while erasing and it's fine." Disabling interrupts does not stop the bus stall; it just hides it. A 1 s erase still means 1 s with no CAN reception. The fix is executing from RAM (or the other bank), not masking IRQs.
Flash must be erased per sector and programmed in aligned units, which differ per family: 32-bit words on F4, 64-bit double-words with ECC on L4 and G4, 256-bit flash words on H7. So my writer buffers network chunks and only programs whole aligned units, pads the tail with 0xFF, clears stale error flags, and reads back every write. On a single-bank part an erase stalls every fetch from that bank, so the flash driver, critical ISRs and the vector table run from RAM, or I use a dual-bank part.

Integrity vs authenticity: CRC, SHA-256, signatures

▶

1. What is it?

Two different questions must be answered about an image:

  • Integrity: "Did these bytes get damaged by accident?" (a radio bit-flip, a torn flash write, a bad cell).
  • Authenticity: "Did we build these bytes, or did someone else?"

A CRC (Cyclic Redundancy Check) and a hash like SHA-256 (Secure Hash Algorithm, 256-bit output) answer the first question. Only a digital signature answers the second, because only a signature needs a secret (the private key) to produce. Terms: HMAC = Hash-based Message Authentication Code (a hash mixed with a shared secret key). ECDSA = Elliptic Curve Digital Signature Algorithm. P-256 = the NIST elliptic curve with 256-bit keys. Ed25519 = an Edwards-curve signature scheme with 32-byte keys.

2. How a signature check works, step by step

  1. At the factory / in CI: generate a key pair once. The private key goes into an HSM (Hardware Security Module) and never leaves it. The public key (64 bytes for P-256) is compiled into the bootloader.
  2. At release: CI computes SHA-256 over header fields + payload → a 32-byte digest. It asks the HSM to sign the digest → 64-byte signature (r, s). The signature is stored in the header or a TLV.
  3. On the device: the bootloader recomputes SHA-256 over the same bytes from flash.
  4. It runs ecdsa_verify(public_key, digest, signature). The maths only succeeds if the signature was made with the matching private key over exactly this digest.
  5. Any single changed bit in the image → completely different digest → verification fails.

How a signature check works: hash the signed region (header fields + payload) with SHA-256, then verify the 64-byte signature over that digest with the public key stored in the bootloader. The device needs only the public key: extracting it from a device lets an attacker verify images, not create them.

"We have a SHA-256 in the manifest, so it's secure." Only if the manifest itself is signed. An attacker who can send you an image can send you its hash.
A CRC or an unkeyed hash only detects accidents, because anyone can recompute them. On a 168 MHz M4 that check costs about 0.1 to 0.2 seconds for a 300 KB image, so I do it on every boot, and I still keep a CRC per chunk to catch transport errors early.

Secure boot: chain of trust, root of trust, key storage

▶

1. What is it?

Secure boot means the device will only run code that you signed. It works like a relay of trust: each stage checks the next stage's signature before running it. That relay is the chain of trust. The first runner in the relay must be trusted without being checked, so it has to be impossible to change after manufacturing: that is the root of trust.

Chain of trust: each stage verifies the next before running it. ROM → (verifies) first-stage bootloader → (verifies) application, or ROM → BL1 → BL2 (MCUboot) → app. A chain is only as strong as its first link, the root of trust: code and a key (or key hash) that cannot be modified after manufacturing.

  ┌──────────────┐ verifies ┌──────────────┐ verifies ┌──────────────┐
  │ ROM / WRP'd  │ ───────▶ │  bootloader  │ ───────▶ │ application  │
  │ first stage  │ sig+key  │ (MCUboot)    │ sig+key  │              │
  └──────┬───────┘          └──────────────┘          └──────────────┘
         │ trusts key hash in OTP / eFuse (cannot be rewritten)
         ▼
     ROOT OF TRUST = immutable code + immutable key (hash)

2. How it works, step by step (ESP32 Secure Boot v2 as the example)

  1. At manufacturing, the SHA-256 of your RSA-3072 public key is burned into eFuse BLOCK2 (an eFuse is a one-time-programmable bit: once blown it cannot be un-blown).
  2. Power on: the mask ROM reads the second-stage bootloader from flash, including the public key and signature appended to it.
  3. ROM hashes the appended public key and compares it with the eFuse digest. Different → stop.
  4. ROM verifies the bootloader's RSA-PSS signature with that key. Bad → stop.
  5. The verified bootloader then verifies the app the same way before running it.

On an STM32F4 there is no ROM secure boot. Your own bootloader becomes the root of trust, made immutable by option bytes:

  1. WRP (write protection) on sectors 0–1: nothing can erase or program the bootloader.
  2. RDP Level 2 (read-out protection, level 2): JTAG/SWD permanently disabled and option bytes (including WRP and RDP) frozen. This is irreversible.
  3. The bootloader holds the public key and verifies the app.
  • Mask ROM + OTP/eFuse key hash (strongest): ESP32 Secure Boot v2 (public key digest in eFuse BLOCK2), NXP i.MX RT HAB/HABv4 (SRK hash in fuses), STM32H5/U5 with ST's immutable root of trust.
  • Write-protected first stage (classic STM32F4/L4): your bootloader is the root of trust, made immutable with WRP on its sectors and RDP Level 2 (permanently disables debug and option-byte changes; irreversible). Level 1 alone is not enough: option bytes and WRP can still be changed by regressing to Level 0, which mass-erases flash but allows reprogramming a malicious bootloader.
  • Extra STM32 isolation features: PCROP (execute-only regions), secure user memory / HDP (G4, H7: bootloader area hidden after it hands over), TrustZone on L5/U5/H5.

4. Key storage

  • Signing private key: never on the device, never in git. In an HSM or a cloud KMS; CI asks it to sign. Have a revocation story: several public key slots or a key hash that can be retired (ESP32 supports up to 3 key digests with revocation).
  • Public key (or its SHA-256): in the immutable bootloader or OTP. Integrity matters, secrecy does not.
  • Image decryption key: secret, unique per device ideally (ECIES/X25519 wraps a random AES key per image; MCUboot ENC_X25519/ENC_EC256 TLVs). Stored in OTP, a secure element (ATECC608, SE050, OPTIGA Trust M) or a TrustZone secure partition.
  • Device identity (e.g. AWS IoT client cert + private key) is a different key with a different job; do not reuse the firmware signing key for TLS.

5. What goes wrong if…

  • …you leave RDP at Level 1 in production? An attacker regresses it, wipes the chip and loads their own bootloader without your public key. All your signature checking is bypassed because the checker itself was replaced.
  • …debug stays open? Secure boot checked the image at boot; with SWD the attacker halts the core afterwards and patches RAM or registers. Verification at boot is meaningless with an open debug port.
  • …the public key is stored in a normal (unprotected) flash sector? Anyone who can write flash replaces the key with their own and signs whatever they like.
Interview angle: "Can secure boot stop someone with a JTAG probe?" Only if debug is locked. Secure boot verifies what runs at boot; an open debug port lets an attacker halt the core and change memory after verification. Secure boot is a chain in which each stage verifies the signature of the next before running it, so everything rests on the first stage and its key being immutable: that is the root of trust. On an ESP32 it is the mask ROM plus a public-key digest in eFuse. On an STM32F4 it is my own bootloader made immutable with WRP and RDP Level 2, because Level 1 can be regressed. The private signing key lives only in an HSM, and production units have debug locked.

Anti-rollback counters and encrypted images

▶

1. What is it?

Anti-rollback stops the device from accepting an older image, even one that you genuinely signed. Image encryption hides the contents of the image from anyone who intercepts it. They solve different problems: anti-rollback is about freshness, encryption is about confidentiality. Neither replaces the signature, which is about authenticity.

A signature proves "we made this", not "this is current". v1.2 had a remote-exploitable parser bug, v1.3 fixed it. If the device accepts any signed image, an attacker simply replays the signed v1.2 and exploits it. Anti-rollback rejects images whose security version is below a monotonic minimum stored on the device.

Terms: security counter (MCUboot) or secure_version (ESP-IDF) = an integer in the signed header, separate from the version string. Monotonic counter = storage that can only go up, never down. OTP = One-Time Programmable memory (bits that can be written once). eFuse = a fuse bit blown electrically, also one-time. Secure element = a separate tamper-resistant chip (ATECC608, SE050, OPTIGA Trust M) with key storage and counters.

2. How anti-rollback works, step by step

  1. Each image header contains security_cnt inside the signed region.
  2. The device stores min_sec in OTP/eFuse, a value that can only increase.
  3. The bootloader (and the app's download code) rejects any image with security_cnt < min_sec.
  4. After a new image boots, passes its trial and confirms, the device raises min_sec to that image's counter.
  5. From then on, all images with a lower counter are permanently refused.
  • Security counter ≠ version string. Bump it only for security-relevant releases; every bump permanently prevents going back. Keep it in the signed header (MCUboot TLV 0x50 SEC_CNT, ESP-IDF secure_version).
  • Storage must be monotonic: OTP bits or eFuses (burn one bit per increment: ESP32 CONFIG_BOOTLOADER_APP_ANTI_ROLLBACK, eFuse field SECURE_VERSION), a secure element's monotonic counter, or a TrustZone-protected NV counter (TF-M). A counter in ordinary flash can be erased by anyone who can erase flash.
  • When to bump the device's stored minimum: after the new image is confirmed, never at download time. Bump at download and the update fails in test boot: you can no longer roll back to the old image you still have.
  • Limited fuse bits (e.g. 16–32 increments) means you budget security bumps over the product lifetime.

3. Worked example: fuse-bit counter

Suppose 32 OTP bits are reserved. The counter value is the number of bits that are programmed (a "thermometer code"). Programming can only add bits, so the value can only go up.

bits (LSB first)                         value
1111 1111 1111 1111 1111 1111 1111 1111   0   (erased OTP reads 1s on STM32; "programmed" = 0)
0111 1111 ...                             1   ← v1.0 shipped with security counter 1
0011 1111 ...                             2   ← v1.3 fixed a remote bug: counter 2
0001 1111 ...                             3   ← v2.0 counter 3
count = 32 − popcount(word)
  1. 32 bits → 32 security bumps over the product's life. Over a 10-year life that is ~3 per year: budget them.
  2. Releases v2.9.0 … v2.9.7 that only fix non-security bugs keep counter 3. You can still move freely between them.
  3. v2.6.0 (counter 2) has the BLE overflow. With min_sec = 3 the bootloader refuses it even though its signature is valid.

Timing rule with numbers: device on v2.9.3 (counter 3), slot A. v3.0.0 (counter 4) is downloaded into B. If you burned min_sec = 4 at download, and v3.0.0 then crashes in its trial boot, the bootloader wants to roll back to A … but A has counter 3 < 4 and is now refused. Nothing bootable: brick. Burn only after confirm.

5. Encrypted images

  • Why: protect IP and make reverse-engineering for exploits harder when images travel over the internet or sit in external flash. Encryption is for confidentiality; it does not replace signatures (unauthenticated encryption can be bit-flipped).
  • How (MCUboot): a random AES-128/256 key per image, wrapped with the device's public key (RSA-OAEP, ECIES-P256 or ECIES-X25519) and placed in a TLV. The secondary slot stays encrypted at rest; the bootloader decrypts (AES-CTR) while swapping into the primary slot, so internal flash holds plaintext and external flash ciphertext.
  • ESP32 flash encryption (AES-XTS with an eFuse key) is a different thing: it encrypts everything in external flash transparently, keyed per chip.
  • Sign-then-encrypt vs encrypt-then-sign: MCUboot signs the plaintext digest, so the bootloader verifies after decrypting. Either is fine if the signature is checked before execution and the decryption key is not shared across the fleet.
CI:     K = random AES-128 key (new per image)

        signature  = ECDSA(sign_key, SHA-256(plaintext + header))

6. What goes wrong if…

  • …the counter is in ordinary flash? Anyone who can erase that sector (bootloader bug, physical access) resets it to 0 and replays the old image.
  • …you bump on every release? 32 fuses are gone in a year or two; after that you can never raise the counter again, even for a critical fix.
  • …you encrypt with one fleet-wide AES key and no signature? One device leaks the key; the attacker decrypts every image and, because there is no signature, can encrypt and push their own.
A signature proves who built an image, not that it is current, so I add a security counter inside the signed header and keep a monotonic minimum in OTP, eFuse or a secure element. The bootloader rejects anything below the minimum, and the minimum is raised only after the new image has confirmed, otherwise a failed trial boot could not roll back. I bump it only for security fixes because fuse bits are limited. Encryption is separate: a random AES key per image wrapped for the device, for confidentiality, never as a substitute for the signature.

Delta updates and compression

▶

1. What is it?

A delta update (also "differential" or "patch" update) sends only the differences between the old and the new firmware instead of the whole new image. The device rebuilds the new image from the old image it already has plus the small patch. Compression shrinks the full image or the patch further. Both exist because cellular data costs money, battery, and time on weak links.

On cellular, every byte costs money and battery, and a 512 KB image on a weak 2G/LTE-M link can take minutes. A typical bug-fix release changes a few percent of the binary, but because code moves, a naive byte diff is still large. Delta tools find moved blocks.

2. How does it work, step by step?

  1. Build server has the exact old binary (v1.0.0) and the new one (v1.1.0).
  2. The delta tool (bsdiff, detools) finds long matching blocks, even when they moved because a function grew earlier in the image. It outputs instructions: "copy 4 096 bytes from old offset 0x1200 adding these small differences", "insert these 88 new bytes", and so on.
  3. The patch is compressed (heatshrink, LZMA) and signed metadata names the base image hash.
  4. Device checks: is my running image's SHA-256 equal to the base hash in the manifest? If not, refuse and ask for a full image.
  5. Device streams the patch: reads old bytes from slot A, applies instructions, writes the result into slot B.
  6. Device verifies the reconstructed slot B exactly like a full image: hash + signature of the result.
  7. Normal A/B trial boot and confirm follow.
slot A (old, read-only)     patch stream          slot B (new, being written)
┌──────────────┐        ┌──────────────────┐      ┌──────────────┐
│ ...code...   │──read──│ COPY 0x1200,4096 │─────▶│ ...code...   │
│              │        │ DIFF +01 00 ...  │      │              │
│              │        │ INSERT 88 bytes  │─────▶│ new function │
└──────────────┘        └──────────────────┘      └──────────────┘

3. Worked example: bytes and seconds saved

  1. Full image 300 KB. Compressed with LZ4/heatshrink (~35 % smaller): 300 × 0.65 = 195 KB.
  2. Bug-fix delta at 8 % of full size: 300 × 0.08 = 24 KB, compressed maybe 18 KB.
  3. On an LTE-M link with a real 50 kbit/s application throughput (6.25 KB/s): full = 300 / 6.25 = 48 s; compressed = 31 s; delta = 18 / 6.25 = 2.9 s.
  4. Across 5 000 stations: full = 5 000 × 300 KB = 1.5 GB per release; delta = 5 000 × 18 KB = 90 MB. A 16× reduction in data cost.
  5. Cost on the device: heatshrink decoder with a 1 KB window ≈ 1–2 KB RAM; LZMA ≈ 10–30 KB RAM; bspatch working buffers depend on the port (janpatch streams page by page).
  • bsdiff/bspatch: suffix-sort based, excellent ratios (often 5–20% of full size). bsdiff needs lots of RAM (PC side, fine); bspatch is streaming-friendly but the original uses bzip2, too heavy for small MCUs. Embedded ports (e.g. janpatch, "bsdiff for MCUs" with heatshrink) stream the patch and read the old image from flash.
  • detools (Python + C library): bsdiff-style or "match-blocks" algorithms, sequential or in-place patch types, compression with heatshrink, LZMA or CRLE. In-place patching saves a slot but must be power-loss safe (detools splits the operation into resumable segments).
  • Compression of full images: LZ4 (fast, tiny decoder), heatshrink (LZSS, configurable 256 B–2 KB window, a few hundred bytes of RAM), LZMA (best ratio, ~ 10–30 KB RAM for decode). Typical firmware compresses 30–50%.

4. The rules that make deltas safe

  1. A delta is only valid against one exact base. Send the base image hash in the manifest and refuse if the running image differs (field units drift: hotfix builds, factory images).
  2. Patch into slot B, never over the running image, then verify the reconstructed image's signature exactly as for a full update. The signature covers the result, not the patch.
  3. Keep a full-image fallback path on the server for devices whose base is unknown.
  4. Make builds reproducible and stable (fixed link order, no timestamps, -ffunction-sections with a stable layout) or deltas grow for no reason.

Base check in code:

int delta_allowed(const manifest_t *m)
{
    uint8_t running[32];
    slot_sha256(active_slot(), running);           /* hash what is actually on flash */
    if (memcmp(running, m->base_sha256, 32) != 0)
        return 0;                                  /* ask server for a full image    */
    return 1;
}
CODEMEANING
slot_sha256(active_slot())Hash the bytes really in flash, not the version string: two units may both say "1.0.0" but hold different builds.
m->base_sha256The manifest (itself signed) names exactly which base the patch was made against.
return 0Fall back to a full image. Never "try anyway".

5. What goes wrong if…

  • …you apply a delta to the wrong base? The result is garbage that still has the right length. If you verify the result's signature (you must), it is rejected and you wasted the download. If you don't, you boot garbage.
  • …you patch in place over the running image? A power cut halfway leaves neither old nor new. Only safe with a resumable in-place scheme (detools in-place splits into resumable segments).
  • …builds are not reproducible? Timestamps, absolute paths or random link order change thousands of bytes: the "8 % delta" becomes 60 %.
A delta tool such as bsdiff or detools encodes the new image as copy-with-differences instructions against the exact old image, often 5 to 20 percent of the full size, then compressed with heatshrink or LZMA. The device checks that its running image hash matches the base named in the signed manifest, streams the patch into the inactive slot reading old data from the active one, and verifies the reconstructed image's signature like any full image. It keeps a full-image fallback, and builds are made reproducible so deltas stay small.

Transports: UART, CAN/UDS, BLE, cellular with resume

▶

1. What is it?

The transport is how the bytes physically reach the device: a UART cable, the CAN bus, Bluetooth Low Energy, or a cellular modem. The bootloader and update logic do not care about the medium, but each medium has its own framing, size limits, error behaviour and recovery rules, and interviewers love to ask about them.

Terms: UDS = Unified Diagnostic Services (ISO 14229), the automotive request/response protocol used to reprogram ECUs. ECU = Electronic Control Unit. ISO-TP = ISO 15765-2, the transport layer that splits long UDS messages into 8-byte CAN frames. SID = Service Identifier (first byte of a UDS request). NRC = Negative Response Code. MTU = Maximum Transmission Unit. MQTT = a publish/subscribe messaging protocol common in IoT.

2. UDS over CAN, step by step

0x10 02            DiagnosticSessionControl → programmingSession (ECU may reset into FBL)

0x28 03 01         CommunicationControl: disable normal Tx/Rx    0x85 02  ControlDTCSetting off

0x31 01 0202/FF01  RoutineControl: checkMemory / checkProgrammingDependencies (CRC, signature)
0x11 01            ECUReset: hardReset
  1. The tester (a PC or a gateway) switches the ECU to a programming session (0x10 02). Many ECUs reset into their flash bootloader here.
  2. SecurityAccess (0x27): ECU sends a random seed, tester computes the key with a secret algorithm and sends it back.
  3. Normal traffic and fault logging are silenced (0x28, 0x85) so the bus is free.
  4. Erase via RoutineControl 0x31 01 FF00; while erasing, the ECU keeps answering 0x7F 31 78 (responsePending) so the tester does not time out.
  5. RequestDownload 0x34 with address and size; the ECU replies with the maximum block length it accepts.
  6. TransferData 0x36 repeatedly with a block sequence counter (BSC) 01, 02, … FF, 00, 01 …
  7. RequestTransferExit 0x37, then a check routine (0x31) for CRC/signature, then ECUReset 0x11 01.
  • Over classic CAN the UDS messages ride on ISO-TP (ISO 15765-2): Single Frame (PCI 0x0N), First Frame (0x1N NN), Consecutive Frames (0x2N, N = 0..F), Flow Control (0x30 BS STmin). Classic ISO-TP is limited to 4095 bytes per message, which is why maxNumberOfBlockLength is ≤ 0xFFF.
  • Retransmission rule: if the tester repeats a 0x36 with the previous sequence counter (its response got lost), the ECU must answer positively without writing again. A wrong counter gives NRC 0x73 wrongBlockSequenceCounter.
  • Useful NRCs: 0x22 conditionsNotCorrect, 0x24 requestSequenceError, 0x31 requestOutOfRange, 0x33 securityAccessDenied, 0x35 invalidKey, 0x70 uploadDownloadNotAccepted, 0x72 generalProgrammingFailure, 0x78 responsePending.

3. Worked example: how many CAN frames is one block?

maxNumberOfBlockLength = 0x0FFF = 4 095 bytes (includes SID 0x36 and the BSC byte, so 4 093 bytes of data).

  1. ISO-TP First Frame carries 6 data bytes (2 bytes of PCI + length). Consecutive Frames carry 7 each.
  2. Frames = 1 + ceil((4 095 − 6) / 7) = 1 + ceil(584.14) = 1 + 585 = 586 frames per block, plus one Flow Control frame from the ECU (more if Block Size BS ≠ 0).
  3. At 500 kbit/s a classic CAN frame with 8 data bytes is ~111–130 bits incl. stuffing → ~0.25 ms. With STmin = 0, 586 × 0.25 ms ≈ 147 ms per block ≈ 27 KB/s.
  4. A 300 KB image: 307 200 / 4 093 = 75.06 → 76 blocks. BSC goes 01 … 4C (76). No wrap needed; a 1 MB image would need 257 blocks and wrap FF → 00.
  5. Total ≈ 76 × 147 ms ≈ 11 s of transfer, plus ~3–6 s erase. CAN FD with 64-byte frames would be several times faster.

4. BLE and cellular

MCUmgr/SMP (Zephyr, nRF Connect SDK) or vendor DFU (Nordic Secure DFU). Throughput is limited by connection interval and MTU: with ATT MTU 247 + data length extension, 2M PHY and a short interval you get tens of kB/s; with default 23-byte MTU a few kB/s. Each write is acknowledged at the protocol level, and resume is by image offset.

BLE example: ATT MTU 247 → 244 bytes of payload per write. With a 15 ms connection interval and, say, 4 packets per event, that is 4 × 244 / 0.015 ≈ 65 KB/s theoretical; real-world 20–40 KB/s. With the default 23-byte MTU (20 bytes payload) and 1 packet per 30 ms event: 20 / 0.03 ≈ 0.7 KB/s, so a 300 KB image takes over 7 minutes.

  • HTTP Range requests: GET /fw/1.1.0.bin with Range: bytes=262144-266239 → 206 Partial Content. Download in fixed-size chunks (e.g. 4 KB), each written to flash and checked; persist the next offset only after the chunk is written and verified.
  • MQTT (e.g. AWS IoT Jobs + the OTA library over MQTT streams): the job document carries URL/stream, size, signature and version; data blocks arrive as numbered messages and the device tracks a bitmap of received blocks, so missing blocks can be re-requested in any order. Brokers cap payload size (AWS IoT Core: 128 KB), so blocks are a few KB.
  • TLS over a cellular module: certificate validation of the download server, and still a signature on the image (TLS protects the pipe, not the file; a compromised server or CDN still serves bad files).
  • Chunk and ack protocol essentials: fixed chunk size that is a multiple of the flash program unit, per-chunk CRC, explicit offset in every chunk (idempotent writes), ack/nack with the expected next offset, timeout and retry limits, overall job timeout.

5. Code: an HTTP Range resume loop

#define CHUNK 4096u                              /* multiple of every program unit  */
uint32_t off = nv_load_committed();               /* bytes verified ON FLASH          */
sha256_restore_or_rehash(&ctx, SLOT_B, off);      /* hash state matches [0, off)      */
while (off < total) {
    uint32_t n = MIN(CHUNK, total - off);
    int st = http_get(url, off, off + n - 1, buf);   /* Range: bytes=off-(off+n-1)     */
    if (st != 206 || !content_range_ok(off, n)) { backoff(); continue; }
    if (flash_write_verify(SLOT_B + off, buf, n)) return FAIL;
    sha256_update(&ctx, buf, n);
    off += n;
    nv_save_committed(off);                       /* ONLY after write + read-back     */
}
CODEMEANING
CHUNK 40964 096 is a multiple of 4 (F4), 8 (L4), 32 (H7) and the ESP32's 4 KB sector, so chunks never straddle a program unit.
nv_load_committed()Resume point = what is proven on flash, not what was received.
sha256_restore_or_rehashThe running hash must cover exactly [0, off). Restarting it at zero is a classic bug (Scenario 08).
st != 206A server or proxy that ignores Range returns 200 and the whole file from byte 0; writing that at off corrupts the slot.
nv_save_committed(off)Persisted last, after the data is on flash and read back.

6. What goes wrong if…

  • …a 0x36 response is lost and the tester repeats the block? If the ECU writes it again at the next address, the image shifts by one block. The rule: same BSC as the previous block → positive response, no write.
  • …the ECU forgets to send 0x78 during a 3 s erase? The tester's P2* timeout (typically 5 s) may expire on slow parts; the tester aborts mid-erase.
  • …the chunk size is not a multiple of the program unit? PGAERR on L4 (Scenario 07).
Resume correctly: on reboot, resume from the last persisted, verified offset, aligned down to the flash write unit (or sector, if you re-erase), and either re-hash the bytes already in slot B or persist the hash context with the offset. Resuming from "bytes received" instead of "bytes committed" is the classic corruption bug (Scenario 08).
Whatever the transport, I use fixed chunks that are a multiple of the flash program unit, each with an explicit offset and CRC, an ack with the next expected offset, and idempotent writes, and I persist only the committed, read-back offset. Over CAN that is UDS on ISO-TP: programming session, security access, erase with responsePending, RequestDownload, TransferData with a wrapping block counter where a repeated block is acked without rewriting, transfer exit, a check routine and a reset. Over cellular it is HTTP Range or numbered MQTT blocks, plus a signature on the file because TLS only protects the pipe.

3. MCUboot + Zephyr

4. Automotive FBL

  • Not standardised by AUTOSAR itself, but every vendor FBL (Vector, Elektrobit, KPIT) follows the same pattern: a standalone bootloader with its own CAN/ISO-TP/UDS stack, entered via 0x10 02 and a reset with a flag, programming via 0x34/0x36/0x37, verification via 0x31 routines, and per-OEM security (seed/key over 0x27, plus signature checks for newer OEM specs).
  • Typically single-slot per logical block (application, calibration) with a valid-application flag written last; the FBL stays resident if the flag is missing. Automotive dual-bank parts (Infineon AURIX, NXP S32K3, Renesas RH850) increasingly use A/B with bank swap for OTA through a central gateway.
  • The vehicle-level orchestration (gateway downloads, distributes to ECUs, campaign management) lives above, e.g. UNECE R156 SUMS compliance and Uptane-style metadata.

5. What goes wrong if…

  • …you enable ESP-IDF rollback but never call mark_app_valid? Every update reverts on the next reset.
  • …you sign with imgtool using a different --header-size than the Zephyr build reserved? The vector table ends up misaligned or the image overwrites the header: boot fails with "Image in the primary slot is not valid".
  • …the slot size given to imgtool doesn't match devicetree? MCUboot looks for the trailer at the wrong place: swaps never start or are misinterpreted.

MCUboot with Zephyr signs images with imgtool, keeps swap state in the slot trailer, does a test swap and reverts unless the app calls boot_write_img_confirmed. Testing FOTA: fault injection and power-cut rigs

▶

1. What is it?

A FOTA system is worth nothing if it only works when nothing goes wrong. Fault injection means deliberately causing the failures that will happen in the field (power cuts, corrupted data, broken images, network drops) and checking the device always recovers. The pass criterion is strict and simple: after every single test cycle the device boots, running either the old or the new version, never neither.

"We tested the update and it worked" is not a FOTA test. The value of the design is entirely in the failure paths, so the tests are about failing at every point.

2. How a power-cut rig works, step by step

  1. A MOSFET or relay switches the board's supply, driven by a PC or a small MCU.
  2. The device under test toggles a GPIO at interesting points ("erase start", "chunk 37 written", "metadata write start"). The rig can cut power a random 0–500 µs after a chosen edge, or at a random time in the whole update.
  3. After the cut, the rig waits (e.g. 2 s, so capacitors discharge below the BOR level), restores power and reads the device's version over UART.
  4. It logs: cycle number, cut point, version after boot, time to recover. Any cycle that ends with no answer is a failure and stops the run for analysis.
  5. Repeat thousands of times overnight.

3. Worked example: how many cycles is enough?

  1. Your update has about 75 chunk writes + 4 metadata writes + 3 erases ≈ 82 "dangerous" operations.
  2. To cut inside each operation at, say, 10 different positions: 82 × 10 = 820 cycles minimum for systematic coverage.
  3. Random cuts on top: if a bad window is 1 % of the update time, the chance of never hitting it in n random cuts is 0.99ⁿ. For 95 % confidence of hitting it at least once: 0.99ⁿ = 0.05 → n = ln 0.05 / ln 0.99 ≈ 298 cycles. For a 0.1 % window: ~3 000 cycles.
  4. One cycle (cut, reboot, check, start a new update) ≈ 30 s → 3 000 cycles ≈ 25 hours. Run it over a weekend.

4. The full checklist

  • Power-cut rig: a MOSFET or relay on the board supply, driven by a script, cuts power at a random delay during the update (or at instrumented points: GPIO toggles at "erase start", "chunk 37 written", "metadata write"). Thousands of cycles overnight. Pass criterion: every single cycle ends with a bootable device running either the old or the new version, never neither.
  • Brown-out, not just cut: slow VDD ramps and dips just above the BOR level corrupt flash writes in ways a clean cut does not. Test with a programmable supply.
  • Simulated flash faults: build the flash driver behind an interface and inject errors in a host build (unit tests on PC): failed program, torn record, ECC error on read, bit flips in slot B.
  • Bad images: wrong signature, wrong key, truncated image, valid image for another hardware revision, older security counter, image that crashes on boot, image that boots but never confirms, image that hangs (watchdog path).
  • Bad transport: dropped chunks, duplicates, out-of-order, corrupted payload with valid framing, connection drops mid-download, server returning 200 instead of 206 for a Range request.
  • Endurance: 1 000 back-to-back updates to see metadata/scratch wear and log rollover behaviour.
  • Fleet canary: the last test stage is real devices: a small cohort first (see next card).

static int      fail_after = -1;               /* inject: cut after N programs      */

{

5. What goes wrong if…

  • …you only test clean power cuts? Real outages are slow sags. VDD lingering just above BOR (brown-out reset threshold, ~2.7 V on F4 BOR level 3) while flash programming runs can write weak bits that read back correctly today and flip next month.
  • …you test only good images? The rollback path is never exercised until the day you need it.
  • …you don't test "server returns 200 instead of 206"? One misconfigured CDN corrupts every resumed download.
I test FOTA by failing it on purpose: a power-cut rig that cuts supply at random and instrumented points thousands of times, with the pass rule that the device always boots either the old or the new image; brown-out tests on a programmable supply; host unit tests with a fake flash that models AND-only programming and torn writes; bad images such as wrong key, truncated, wrong board, old security counter, crash, hang and never-confirm; bad transport like drops, duplicates and ignored Range; and endurance runs. Then a canary in the real fleet.
18ADVANCED

Fleet rollout: a battery-swap-station style network

▶

1. What is it?

A fleet rollout is how you deliver one release to thousands of devices without risking all of them at once. The device-side safety (A/B, signatures, rollback) protects one unit; the rollout plan protects the business. The core idea: release to a small group first, measure, and only widen when the numbers stay healthy.

Picture a generic IoT fleet: thousands of swap stations, each with a main controller on cellular, CAN-connected slot controllers / chargers behind it, and batteries swapping in and out all day. One bad release that bricks stations is a city-wide outage and a truck roll per site.

Terms: canary = a small early group whose failure warns you (like a canary in a coal mine). Cohort = a group of devices selected by a property (hardware revision, region, customer). Health gate = a measured condition that must hold before the next wave starts. Kill switch = a server setting that immediately stops offering a release.

2. How does it work, step by step?

  1. Lab and HIL: full fault-injection suite, against every hardware revision in the field.
  2. Internal canary: stations at the office/depot (≈ 1%). Watch for 24–72 h.
  3. Phased waves: 5% → 25% → 50% → 100%, each gated on health metrics, with an automatic stop if a gate fails.
  4. Health gates (telemetry the firmware must report): confirm rate after update, rollback count, reset reasons (WDT, HardFault, BOR) per hour, CAN error counters, swap transaction success rate, time to reconnect.

3. Worked example: gate numbers for 5 000 stations

  1. Canary 1 % = 50 stations (depot/office units first). Wave 5 % = 250, 25 % = 1 250, 50 % = 2 500.
  2. Gate "rollbacks ≤ 0.2 %": in the 250-station wave that allows 250 × 0.002 = 0.5 → effectively zero rollbacks. Small samples need absolute thresholds, not just percentages.
  3. Gate "WDT resets per station per day": baseline 0.05/day. In 250 stations over 24 h, expected 250 × 0.05 = 12.5. Alarm if > 2× baseline (25).
  4. Server load: 1 250 stations × 300 KB = 375 MB. Spread starts over a 2-hour window: 375 MB / 7 200 s ≈ 52 KB/s average, instead of 1 250 connections in the same second.
  5. Install window: stations are busiest 8:00–22:00. Download any time, but install (reboot, ~15 s) only between 01:00 and 05:00 and when no battery is mid-swap or charging session active.

4. Device-side rules

  • Never update during a transaction: defer install until the station is idle (no battery mid-swap, no charging session that would be interrupted), or schedule in a low-traffic window. Download can run in the background; only the reboot needs the window.
  • Targeting: the manifest names hardware revision and minimum base version; the device re-checks both (do not trust the server's targeting alone).
  • Sub-node updates (slot controllers over CAN): the main controller acts as the gateway, updating nodes one at a time so the station stays partly in service, with per-node rollback and version-compatibility checks between main and sub-node firmware.
  • Report everything: job state transitions (downloading, verified, pending, confirmed, rolled-back with reason code) so the backend can tell "1% rolled back with reason WDT" from "1% are offline".
  • Bandwidth: delta images and resume make the difference on weak sites; stagger the start times so 5 000 stations do not hit the server at the same second.

5. What goes wrong if…

  • …you push 100 % at once? A bug that bricks only hardware rev C hits every rev C unit before anyone notices.
  • …the backend re-offers a version that rolled back? Rollback loop: data costs and churn (Scenario 03).

Interview angle: "How would you roll out firmware to 10 000 devices?" A good answer covers device side (A/B, signed, confirm/rollback, deferral), server side (cohorts, staged %, health gates, kill switch, pinning per hardware rev), and observability (state reporting, reason codes). Most candidates only cover the first.
Device side I use A/B with signed images, trial boot, a bootloader-owned attempt counter and watchdog, confirm after a self-test, and install deferred to an idle window. Server side I target by hardware revision, go through an internal canary and then phased waves such as 1, 5, 25, 50 and 100 percent, each gated on confirm rate, rollback count, reset reasons and the product's own KPI like swap success, with a kill switch and staggered starts.
