STEP 1

What problem does "ARM architecture" solve?

When you compile C code for a microcontroller, the compiler turns it into a long list of numbers — machine instructions. Something has to define what each number means: "0xB510 means push R4 and LR onto the stack", "this register holds the return address", "when an interrupt happens, the CPU saves these eight registers". That written definition is the architecture. It is a contract between the software (your compiler, your RTOS, Linux) and the silicon (the actual CPU core).

Arm Ltd is a company that writes that contract and also designs CPU cores that obey it, then licenses them. Arm does not sell chips. ST, NXP, TI, Infineon, Qualcomm, NVIDIA and Apple buy a licence, put a core (or their own design) on their chip, add memory and peripherals, and sell the chip. That is why one compiler (arm-none-eabi-gcc) can build code for an STM32 from ST and an LPC from NXP: both chips contain a core that implements the same architecture.

WHY THE CONTRACT MATTERS TO YOU

  • Portability: code compiled for "ARMv7E-M" runs on every Cortex-M4 and Cortex-M7, from any vendor.
  • Debugging: when the board crashes, the architecture tells you exactly which registers hold the evidence (the stacked PC, the fault status registers) — the same on every Cortex-M part.
  • Interviews: almost every embedded interview at Qualcomm, NXP, TI, Bosch or Apple asks architecture questions: "what happens on an interrupt?", "what is the calling convention?", "what are exception levels?", "how does TrustZone isolate secrets?". They test whether you understand the contract, not one vendor's library.

One more idea before we start: Arm does not have one architecture but three families ("profiles"), because a phone, a brake controller and a battery sensor need very different things.

STEP 2

The physical picture: what is inside the chip?

Let's open up an STM32F407. It is one piece of silicon, but it contains several distinct blocks. Only one of them is "the ARM part": the Cortex-M4 core. Everything else — flash, RAM, GPIO, UART, timers — was designed or chosen by ST.

Walk through the picture from top to bottom:

  1. The core is the part that executes instructions. It has a small set of fast storage slots called registers (R0–R15 plus status registers). It fetches an instruction from flash, decodes it, executes it — a 3-stage pipeline on Cortex-M4 — at up to 168 MHz on this chip, so one simple instruction takes about 6 ns.
  2. Inside the core, Arm also put the NVIC (Nested Vectored Interrupt Controller — the block that decides which interrupt runs next), the MPU (Memory Protection Unit — a guard that can forbid certain code from touching certain addresses), the FPU (Floating-Point Unit) and debug hardware (breakpoints, watchpoints, a cycle counter).
  3. The bus matrix is the road network. Every load or store the core does travels over it to a memory or peripheral, chosen purely by the address.
  4. Flash (non-volatile, keeps its content without power) holds the program at 0x0800_0000. SRAM (fast, loses content at power-off) holds variables and stacks at 0x2000_0000. Peripherals live at 0x4000_0000 upward: writing to address 0x4002_0014 (GPIOA output register) literally changes a pin's voltage.

A phone or car SoC (System-on-Chip) is the same idea, just bigger: several Cortex-A cores, each with an MMU (Memory Management Unit — translates virtual addresses into physical addresses so each Linux process gets its own private view of memory), large caches, a GIC (Generic Interrupt Controller — the A-profile equivalent of the NVIC, but outside the core), and gigabytes of external DRAM. Part of that DRAM is fenced off for secure software by a TrustZone address-space controller.

On a microcontroller the Arm core sits next to vendor flash, SRAM and peripherals; everything is reached through a fixed memory map — flash at 0x0800_0000, SRAM at 0x2000_0000, peripherals at 0x4000_0000 on an STM32. The NVIC, MPU and debug blocks are part of the Arm core. On an application SoC, Cortex-A cores add an MMU, caches and exception levels, and an external GIC handles interrupts.
STEP 3

The key terms, defined one by one

Read these slowly. Every later card uses them, and interviewers expect you to use them precisely. They are ordered so that each one only depends on the ones above it.

Architecture / ISAThe specification: instruction set (ISA = Instruction Set Architecture), registers, exception model, memory model. Example: ARMv7E-M. Written in the "ARM ARM" (Architecture Reference Manual).
Core / micro-architectureOne concrete design that obeys an architecture. Cortex-M4 is a core that implements ARMv7E-M with a 3-stage pipeline. Its timing is in its TRM (Technical Reference Manual).
RegisterA 32-bit (or 64-bit on AArch64) storage slot inside the core. Cortex-M has R0–R12 for general data, plus three with special jobs below.
PC — Program Counter (R15)Holds the address of the instruction being executed. Changing PC = jumping somewhere.
SP — Stack Pointer (R13)Points at the top of the stack, the RAM area where functions save registers and keep local variables. On ARM the stack grows downward: pushing makes SP smaller.
LR — Link Register (R14)Holds the return address after a function call (BL = Branch with Link writes it). Inside an interrupt handler it holds a magic code called EXC_RETURN instead.
Thumb / T32The compact instruction encoding (16- and 32-bit instructions). Cortex-M runs only Thumb. Bit 0 of a code address = 1 means "Thumb", which is why function addresses look odd (0x0800_0199).
A64 / AArch64The 64-bit execution state of ARMv8-A and its instruction set: 31 registers X0–X30, each 64 bits wide.
AAPCS — calling convention"Procedure Call Standard for the Arm Architecture": the rules for which registers carry function arguments (R0–R3), return values (R0) and which ones a function must preserve (R4–R11).
Exception / InterruptAn exception is any event that makes the core stop normal code and run a handler. An interrupt (IRQ) is an exception caused by a peripheral; faults (bad memory access) and system calls (SVC) are exceptions too.
Vector tableA table that tells the core where each handler lives. On Cortex-M it is a list of addresses at 0x0800_0000; on Cortex-A it is a block of code at the address in VBAR_ELx.
NVIC / GICInterrupt controllers. NVIC (inside every Cortex-M) prioritises up to 240 IRQs. GIC (separate block on A/R systems) does the same for many cores at once.
Thread mode / Handler modeCortex-M's two modes: Thread = normal code (main, RTOS tasks); Handler = running an exception handler.
Privileged / UnprivilegedPrivileged code may touch everything (interrupt controller, MPU). Unprivileged code (an RTOS task) is restricted and must ask the kernel via SVC.
MSP / PSPMain and Process Stack Pointer: Cortex-M has two physical SP registers. Handlers always use MSP; RTOS tasks usually use PSP.
SVC / HVC / SMCInstructions that deliberately cause an exception to ask a more privileged layer for help: SVC → OS kernel, HVC → hypervisor, SMC → secure monitor.
Exception Level (EL0–EL3)A-profile privilege levels: EL0 apps, EL1 OS kernel, EL2 hypervisor, EL3 secure monitor firmware. Higher number = more privilege.
ERET"Exception Return" on A-profile: the only instruction that goes back down to a lower EL, restoring the saved PC (from ELR_ELx) and saved state (from SPSR_ELx).
TrustZoneHardware that splits the chip into a Secure world (keys, crypto, boot verification) and a Non-secure world (normal firmware/Linux). Secure memory is invisible to Non-secure code.
MPU vs MMUMPU: a few address ranges with permissions (no translation), used on M and R. MMU: page tables that translate virtual to physical addresses and set permissions per 4 KB page, used on A.
Memory type (Normal / Device)An attribute telling the core how it may access an address: Normal (RAM — may cache, merge, reorder) or Device (peripheral registers — exactly in order, never speculatively).
Barrier (DMB / DSB / ISB)Instructions that force ordering: DMB orders memory accesses, DSB waits for them to complete, ISB flushes the pipeline so new settings take effect.
STEP 4

One end-to-end worked example: a function call, then an interrupt

We will follow a real STM32F407 for a few hundred nanoseconds. The CPU runs at 168 MHz (1 cycle = 5.95 ns). Stack top is the end of the 128 KB SRAM: 0x2000_0000 + 0x2_0000 = 0x2002_0000. The code is:

int32_t scale(int32_t x, int32_t gain) {   // at 0x0800_0300 (Thumb)
    int32_t y = x * gain;
    return y >> 2;
}
int main(void) {
    ...
    int32_t r = scale(1000, 3);              // the BL is at 0x0800_0240
    ...
}

PART A — THE FUNCTION CALL (AAPCS IN ACTION)

  1. Arguments go into registers. The AAPCS says the first four arguments travel in R0–R3. So the compiler emits movw r0, #1000 and movs r1, #3: R0 = 0x0000_03E8, R1 = 0x0000_0003. Nothing is written to RAM — that is why ARM calls are fast.
  2. BL scale. The 32-bit BL instruction at 0x0800_0240 does two things at once: LR ← address of the next instruction with bit 0 set = 0x0800_0244 | 1 = 0x0800_0245 (the 1 means "come back in Thumb state"), and PC ← 0x0800_0300.
  3. Prologue. Suppose scale needs one callee-saved register for a temporary. It runs push {r4, lr}: two words = 8 bytes, so SP goes from 0x2002_0000 down to 0x2001_FFF8. Pushing an even number of registers keeps SP a multiple of 8 — the AAPCS requires 8-byte alignment at every call.
  4. Body. mul r4, r0, r1 → R4 = 3000 (0xBB8). asrs r0, r4, #2 → R0 = 750 (0x2EE). The result is in R0 because the AAPCS says results return in R0.
  5. Epilogue. pop {r4, pc} restores the caller's R4 and loads the saved LR value 0x0800_0245 straight into PC. Bit 0 = 1 keeps the core in Thumb state, and execution continues at 0x0800_0244 with R0 = 750. SP is back to 0x2002_0000.

PART B — AN INTERRUPT ARRIVES IN THE MIDDLE (EXCEPTION ENTRY)

Now replay it, but the SysTick timer fires just after the push, while PC = 0x0800_0302 is about to execute mul. SysTick is exception number 15.

  1. The NVIC decides. SysTick is pending and enabled, and nothing of higher priority is running, so the NVIC tells the core "take exception 15 now".
  2. Hardware stacking. Without any software, the core pushes 8 words (32 bytes) onto the current stack (MSP): xPSR, PC, LR, R12, R3, R2, R1, R0. SP: 0x2001_FFF8 − 32 = 0x2001_FFD8. That is 8-byte aligned (0xD8 = 216 = 27 × 8), so no padding word is needed.
  3. Vector fetch. In parallel, the core reads vector table word 15 at 0x0800_0000 + 15 × 4 = 0x0800_003C. Suppose it contains 0x0800_0411 (odd = Thumb). The handler starts at 0x0800_0410.
  4. LR gets a magic value. LR ← 0xFFFF_FFF9 = EXC_RETURN meaning "when this handler returns, go back to Thread mode, using MSP, no floating-point frame". IPSR (the exception-number field of xPSR) becomes 15.
  5. Handler runs. Total entry time on Cortex-M4 with zero-wait-state memory: 12 cycles = 12 × 5.95 ns ≈ 71 ns. The handler is an ordinary C function; it may freely use R0–R3 and R12 because the hardware already saved them.
  6. Exception return. The handler ends with bx lr. Because LR = 0xFFFF_FFF9 is not a real address, the core recognises it, pops the 8 words back (SP returns to 0x2001_FFF8), sets PC = 0x0800_0302 and resumes the mul as if nothing happened.

Why exactly those 8 registers? They are the registers the AAPCS lets any C function destroy (R0–R3, R12, LR) plus the PC and status needed to resume. Because the hardware saves them, the handler can be a normal C function; if the handler uses R4–R11, the compiler's normal prologue saves them, exactly like in Part A. The calling convention and the exception model were designed together.

PART C — PRIVILEGE: AN RTOS TASK ASKS THE KERNEL

Under an RTOS with memory protection, tasks run unprivileged in Thread mode on their own PSP stack. If a task tries to write the NVIC directly at 0xE000_E104, the core raises a BusFault — unprivileged code may not touch the System Control Space. Instead the task executes SVC #3. The SVC exception enters Handler mode (always privileged, on MSP), the kernel checks the request, writes the NVIC on the task's behalf, and returns with EXC_RETURN = 0xFFFF_FFFD ("back to Thread mode on PSP").

On a Cortex-M4, a call passes arguments in R0–R3 and BL puts an odd return address in LR. When an interrupt arrives, hardware pushes eight words — R0–R3, R12, LR, PC, xPSR — which are exactly the AAPCS caller-saved registers, loads the handler address from the vector table, and puts an EXC_RETURN value like 0xFFFF_FFF9 in LR. Entry takes 12 cycles, about 71 ns at 168 MHz, and BX LR with that magic value unstacks everything.
STEP 5

The same story on a Cortex-A running Linux

Now a Linux program on an ARMv8-A core calls write(fd, buf, 5). The C library puts the arguments in X0–X2 (AAPCS64 uses X0–X7), puts the system-call number 64 (__NR_write on arm64) in X8, and executes SVC #0.

  1. The program runs at EL0. SVC is a synchronous exception that always goes up, to EL1 (the kernel).
  2. Hardware saves only two things: the old PSTATE (flags, interrupt masks, which EL we came from) into SPSR_EL1, and the address of the instruction after SVC into ELR_EL1. It writes the reason into ESR_EL1: EC (Exception Class) = 0x15 means "SVC from AArch64".
  3. It masks interrupts (PSTATE.DAIF = 1111) and jumps to VBAR_EL1 + 0x400 — the slot for "synchronous exception from a lower EL running AArch64". If VBAR_EL1 = 0xFFFF_8000_0801_0800, PC becomes 0xFFFF_8000_0801_0C00.
  4. Unlike Cortex-M, no general registers were saved. The kernel's entry code stores X0–X30 into a pt_regs structure on the kernel stack itself, reads ESR to see it is a syscall, and calls sys_write.
  5. The result (5 bytes written) goes into the saved X0, the registers are restored and ERET copies ELR_EL1 → PC and SPSR_EL1 → PSTATE, which drops the core back to EL0 in one instruction.

STEP 7

Self-check — answer out loud, then open

1. Why does a function pointer on Cortex-M hold an odd value such as 0x0800_0301?

Bit 0 of a branch target selects the instruction set: 1 = Thumb. Instructions are 2-byte aligned, so bit 0 is free to carry the flag. Cortex-M only supports Thumb, so every code address used in BX/BLX or the vector table must have bit 0 = 1. The instruction itself starts at 0x0800_0300.

2. A handler starts with SP = 0x2001_FFD8 after an interrupt hit code whose SP was 0x2001_FFF8. Why 32 bytes?

The hardware pushed 8 words × 4 bytes = 32 bytes: R0, R1, R2, R3, R12, LR, PC, xPSR. 0x2001_FFF8 − 0x20 = 0x2001_FFD8. With an active floating-point context it would be 26 words = 104 bytes.

3. What is in LR when an interrupt handler starts on Cortex-M, and why?

An EXC_RETURN value such as 0xFFFF_FFF9 (return to Thread mode, MSP) or 0xFFFF_FFFD (Thread mode, PSP). It is not a real address: when the handler executes BX LR, the core sees the 0xFFFF_FFxx pattern and performs exception return — unstacking the frame — instead of a normal branch.

4. A Linux process executes SVC. Which EL handles it and at which vector offset?

EL1, at VBAR_EL1 + 0x400 (synchronous exception from a lower EL in AArch64). ESR_EL1.EC = 0x15, ELR_EL1 = address after the SVC, SPSR_EL1 = the process's PSTATE.

5. Name one thing an MPU cannot do that an MMU can.

Address translation. An MPU only checks permissions and attributes of a handful of physical address ranges; an MMU maps virtual pages to physical pages, so every Linux process can use the same virtual addresses with private physical memory.

A, R and M profiles: three architectures for three jobs

▶

1. WHAT IS IT?

A profile is a family of the Arm architecture tuned for one kind of product. Arm Ltd writes three of them because the needs of a phone, a car brake controller and a coin-cell sensor genuinely conflict: you cannot have "run Linux with virtual memory" and "always answer an interrupt within 50 ns" and "cost 30 cents" in the same design. ARM is a licensable architecture — Arm sells the specification and core designs, vendors make the chips.

  • A-profile (Application): runs rich operating systems (Linux, Android, iOS, Windows). Key hardware: an MMU (Memory Management Unit) that translates virtual addresses to physical ones using page tables, big caches, many cores kept coherent.
  • R-profile (Real-time): hard real-time and functional safety (ISO 26262 = the automotive safety standard; ASIL-D = its strictest level). Uses an MPU (Memory Protection Unit: a few address ranges with permissions, no translation), TCMs (Tightly-Coupled Memories: on-core SRAM with fixed one-cycle access), and lockstep cores.
  • M-profile (Microcontroller): low cost, low power, very low interrupt latency. Interrupt controller (NVIC) built into the core, fixed memory map, Thumb-only instructions, startup code can be written entirely in C.

2. HOW DO YOU PICK ONE, STEP BY STEP?

  1. Do you need a general-purpose OS with processes, virtual memory, a file system, a GPU driver? Then you need an MMU → A-profile.
  2. Do you need a guaranteed worst-case response time (e.g. "the brake-pressure loop must run every 100 µs, never late") plus safety features like lockstep and ECC, maybe several software partitions on one core? → R-profile.
  3. Is cost, power and simplicity dominant, with bare-metal code or an RTOS (FreeRTOS, Zephyr)? → M-profile.
  4. Many real products use all three on one board: a car domain controller may have Cortex-A cores for Linux, Cortex-R52 cores for AUTOSAR control, and a Cortex-M as a security or power-management controller.

3. WORKED EXAMPLE — WHY AN MMU HURTS DETERMINISM

A Cortex-A core translating an address first looks in its TLB (Translation Lookaside Buffer — a small cache of recent translations). On a hit, translation costs ~0 extra cycles. On a miss with 4 KB pages and 48-bit addresses it walks 4 levels of page table, each a memory read. If each read misses the caches and goes to DRAM at ~100 ns, the worst case is 4 × 100 ns = 400 ns added to one load — at 1.5 GHz that is 600 cycles.

A Cortex-R or Cortex-M MPU compares the address with all its regions in parallel in the same cycle as the access: 0 extra cycles, always. For a 10 µs control loop, an unpredictable 400 ns hiccup is 4 % of the budget — per access. That is why safety ECUs avoid the MMU.

4. WHAT GOES WRONG IF…

MISTAKE…you assume Cortex-M code runs on a Cortex-A (or the other way round). Symptom: it does not even boot. Cortex-M expects a vector table of addresses at 0x0000_0000 (word 0 = initial stack pointer); a Cortex-A expects executable code at its reset vector and has no NVIC at 0xE000_E000. The binaries are not compatible.
MISTAKE…you pick a Cortex-A for a 20 kHz motor-control loop because it is "faster". Symptom: average loop time is great, but jitter from cache misses, TLB walks and Linux scheduling occasionally makes a cycle late and the current controller trips. Fix: run the loop on an R or M core (or an M-class co-processor next to the A cores).

5. SAY IT LIKE THIS

Arm defines three profiles. A-profile has an MMU and runs rich OSes like Linux; R-profile uses an MPU, TCMs and lockstep for deterministic, safety-critical control; M-profile has the NVIC in the core, a fixed memory map and Thumb-only execution for low-cost microcontrollers. I choose by whether I need virtual memory, guaranteed worst-case latency with safety features, or lowest cost and power.

BEGINNER

Architecture vs micro-architecture vs SoC

▶

1. WHAT IS IT?

Three different documents describe "your ARM chip", and interviewers check that you know which is which. Think of them as three layers:

  1. Architecture (e.g. ARMv7E-M): what instructions mean and how exceptions behave. Same for every vendor. Document: the ARM ARM (Architecture Reference Manual).
  2. Core / micro-architecture (e.g. Cortex-M4): how one design implements that architecture — pipeline length, cycle counts, which optional features exist. Document: the core's TRM (Technical Reference Manual).
  3. SoC / MCU (e.g. STM32F407): what the chip vendor attached — flash size, RAM, peripherals, clock tree, and which core options were switched on. Document: the vendor reference manual (RM0090) and datasheet.

2. WORKED EXAMPLE — "HOW MANY INTERRUPT PRIORITY LEVELS DOES A CORTEX-M4 HAVE?"

The architecture (ARMv7-M) defines an 8-bit priority field per interrupt, so up to 28 = 256 levels. The Cortex-M4 core lets the vendor implement between 3 and 8 of those bits. ST chose 4 bits on the STM32F4, so there are 24 = 16 levels, and they live in the top four bits of each byte: priority 5 is written as 5 << 4 = 0x50. The unimplemented low bits read as zero.

So the correct answer is layered: "the architecture allows 256, the core allows the vendor to pick 8 to 256, and the STM32F407 implements 16." Same for MPU regions (Cortex-M4 option: 0 or 8 regions; ST chose 8) and the FPU (optional on M4; ST included it).

3. CODE — READ THE OPTIONS AT RUN TIME

4. WHAT GOES WRONG IF…

MISTAKE…you write NVIC_SetPriority(IRQn, 5) through a raw register write as NVIC->IP[n] = 5. Symptom: every interrupt seems to have priority 0 (highest), preemption is wrong. Why: 5 = 0b0000_0101 only sets unimplemented low bits, which read as 0. The CMSIS function shifts for you (5 << (8 − __NVIC_PRIO_BITS)); a raw write must do it yourself.

5. SAY IT LIKE THIS

The architecture is the contract — instructions, registers, exception model — documented in the ARM ARM. A core like Cortex-M4 is one implementation, with timing in its TRM. The SoC vendor then picks core options and adds memory and peripherals. So "how many priority levels" is: up to 256 architecturally, 16 on an STM32F4 because ST implemented 4 bits.

6. REFERENCE DETAIL

  • Architecture (ARMv7E-M, ARMv8-A…): the contract — instruction set, registers, exception model, memory model. Documented in the ARM ARM (Architecture Reference Manual).
  • Micro-architecture / core (Cortex-M4, Cortex-A78, Apple Firestorm): one implementation of an architecture — pipeline depth, caches, branch predictor, cycle counts. Documented in the core's TRM (Technical Reference Manual). Cortex-M4 = 3-stage pipeline, ARMv7E-M, optional FPv4-SP FPU and MPU.
  • SoC / MCU (STM32F407): the vendor adds flash, SRAM, peripherals, clock tree, bus matrix, and chooses core options (FPU present, 16 NVIC priority levels = 4 priority bits, MPU with 8 regions). Documented in the reference manual and datasheet.

Licensing models: a core licence (use Arm's Cortex design, e.g. ST, NXP) or an architecture licence (design your own core that implements the ISA, e.g. Apple, Qualcomm Oryon, NVIDIA Carmel/Denver, Ampere). This is why "Apple M-series runs ARMv8.x/v9" but is not a Cortex core.

Interview framing: "The ISA guarantees what my code means; the TRM tells me how fast it runs; the vendor manual tells me what is attached." If asked how many interrupt priority levels a Cortex-M4 has, the right answer is "the architecture allows up to 256; the vendor chooses — STM32F4 implements 16".

Architecture versions: ARMv6-M → ARMv9-A

▶

1. WHAT IS IT?

The architecture has versions, written ARMvN-profile: ARMv6-M, ARMv7-M, ARMv8-M, ARMv8-A, ARMv9-A. Each version adds instructions and features; a core implements exactly one version. Knowing the version tells you instantly what your core can do: "M0+ is ARMv6-M, so it has no hardware divide and no unaligned access" is a typical interview line.

2. HOW TO READ THE NAMES, STEP BY STEP

  1. The number is the generation (6, 7, 8, 9). Higher is newer, and usually a superset.
  2. The letter is the profile: -A, -R, -M.
  3. Suffixes: "E" in ARMv7E-M = DSP Extension (SIMD on 8/16-bit lanes, saturating maths). "Baseline/Mainline" in ARMv8-M = the small (M0-class, M23) versus full (M3-class, M33) variant. ".x" in ARMv8.3-A = minor version: each adds named features like FEAT_PAuth (pointer authentication) in v8.3.
  4. The core name does not tell you the version: Cortex-M7 (newer than M4) is still ARMv7E-M; Cortex-M23 (small) is ARMv8-M Baseline. Always look it up.

3. WORKED EXAMPLE — WHAT MOVING FROM M0+ TO M4 GIVES YOU

Code: uint32_t avg = sum / count;

  • On a Cortex-M0+ (ARMv6-M) there is no divide instruction, so the compiler calls the library routine __aeabi_uidiv: roughly 30–100 cycles depending on the operands.
  • On a Cortex-M4 (ARMv7E-M) the compiler emits UDIV r0, r0, r1: 2–12 cycles (it terminates early for small quotients).
  • On a Cortex-M4 with DSP, a 16-bit FIR filter tap pair can be done with one SMLAD (two 16×16 multiplies + accumulate) in 1 cycle, instead of two MUL + two ADD.

4. WHAT GOES WRONG IF…

MISTAKE…you compile with -mcpu=cortex-m4 and flash the binary onto a Cortex-M0+ board. Symptom: HardFault very early, often in a 32-bit Thumb-2 instruction like UDIV or an IT block. ARMv6-M only decodes a subset; anything else is UNDEFINED. Fix: compile with -mcpu=cortex-m0plus, or for portable libraries -march=armv6s-m.
MISTAKE…you say "Cortex-M7 is ARMv8". Symptom: lost interview points. M7 is ARMv7E-M; it is fast because of its 6-stage dual-issue pipeline and caches, not because of a newer architecture. TrustZone-M first appears in ARMv8-M (M23/M33).

5. SAY IT LIKE THIS

M0/M0+ are ARMv6-M — small Thumb subset, no divide, no unaligned access. M3 is ARMv7-M with full Thumb-2, divide and configurable faults; M4 and M7 are ARMv7E-M with DSP and optional FPU. M23 and M33 are ARMv8-M Baseline and Mainline with optional TrustZone-M; M55 and M85 are ARMv8.1-M with Helium. On the A side, v8.0 introduced AArch64, v8.3 added PAC, v8.5 BTI and MTE, and v9 makes SVE2 mandatory.

A32, T32 (Thumb-2) and A64 — and why Cortex-M is Thumb-only

▶

1. WHAT IS IT?

An instruction set is the list of binary encodings the core understands. Arm has three: A32 (the original "ARM" set, every instruction 32 bits), T32 ("Thumb-2", a mix of 16-bit and 32-bit instructions for smaller code), and A64 (the 64-bit set used in AArch64 state). Cortex-M runs only T32. The single most-asked detail is the Thumb bit: bit 0 of a branch target address says which instruction set to use.

2. HOW DOES THE THUMB BIT WORK, STEP BY STEP?

  1. Every instruction starts at an even address (Thumb instructions are 2 bytes or 4 bytes long, aligned to 2). So bit 0 of a real instruction address is always 0 — it is a "free" bit.
  2. Arm reuses that free bit as a flag in interworking branches: BX Rm, BLX Rm, POP {..., pc}, LDR pc, [...]. If bit 0 of the target is 1 → execute as Thumb; if 0 → execute as ARM (A32).
  3. The core strips bit 0 before fetching, so a target of 0x0800_0199 fetches from 0x0800_0198.
  4. The current state is held in EPSR.T — bit 24 of the xPSR register (EPSR = Execution Program Status Register).
  5. On Cortex-M there is no ARM state at all. A branch to an even address clears EPSR.T, and the very next instruction fetch raises a UsageFault INVSTATE ("invalid state", CFSR bit 17). If UsageFault is not enabled it escalates to HardFault.

3. WORKED EXAMPLE

The linker places Reset_Handler at 0x0800_0198. In the vector table and in any function pointer it is stored as 0x0800_0198 | 1 = 0x0800_0199. In binary the last hex digit 9 = 1001₂, so bit 0 = 1 → Thumb.

A map file lists the symbol address without the flag: 0x08004a10 cmd_reset. If you type 0x08004A10 into a function pointer, bit 0 = 0 (A = 1010₂) → INVSTATE on Cortex-M. The correct pointer value is 0x0800_4A11.

Code density: a typical Cortex-M application compiled as Thumb-2 is about 25–30 % smaller than the same code as A32. On a 1 MB flash MCU that is the difference between fitting and not fitting.

Note the stacked PC in an exception frame is a plain address (bit 0 is ignored/should be 0); the Thumb state is taken from the stacked xPSR.T instead.

6. SAY IT LIKE THIS

ARM has A32, T32 (Thumb-2, mixed 16/32-bit for density) and A64. Interworking branches use bit 0 of the target to choose Thumb (1) or ARM (0), which works because instructions are at least 2-byte aligned. Cortex-M implements only Thumb, so a branch to an even address clears EPSR.T and causes a UsageFault INVSTATE — that is why vector entries and function pointers on Cortex-M are always odd.

7. REFERENCE DETAIL

  • A32 ("ARM"): fixed 32-bit instructions, conditional execution on almost every instruction, 16 visible GPRs. AArch32 state only.
  • T32 ("Thumb-2"): mixed 16-bit and 32-bit encodings. Original Thumb (ARMv4T) was 16-bit only for code density; Thumb-2 (ARMv6T2/v7) added 32-bit encodings so one instruction set gives ~A32 performance at ~70% of the code size. Conditional execution via the IT (If-Then) block.
  • A64: fixed 32-bit instructions for AArch64, 31 × 64-bit GPRs, no general conditional execution (uses CSEL/CSINC/CBZ/TBZ instead), no LDM/STM (uses LDP/STP pairs), PC is not a general register.

THE THUMB BIT

Interworking branches (BX, BLX, POP {pc}, LDR pc) use bit 0 of the target address to choose the state: 1 → Thumb, 0 → ARM. Instructions are at least 2-byte aligned, so bit 0 is free to carry this flag. The current state is the EPSR.T bit (xPSR bit 24).

Cortex-M implements only T32. There is no ARM state to switch to, so an interworking branch to an even address does not "switch to ARM": it clears EPSR.T, and the next instruction fetch raises a UsageFault INVSTATE (CFSR bit 17), escalated to HardFault if UsageFault is disabled. That is why every vector table entry and function pointer on Cortex-M is odd (e.g. Reset_Handler at 0x0800_0198 is stored as 0x0800_0199).

Why Thumb-only on M? Code density is cost (flash is the largest area on an MCU die), and supporting one instruction decoder saves gates and power. Thumb-2 makes the performance penalty negligible. It also lets the core take an exception and start the handler without a state switch.
BEGINNER

Cortex-M register file: R0–R15, xPSR, CONTROL, mask registers

▶

1. WHAT IS IT?

The register file is the set of storage slots inside the Cortex-M core. There are 16 numbered registers R0–R15, each 32 bits, and a few special registers that are reached only with the MRS (move special → register) and MSR (move register → special) instructions: xPSR (status), CONTROL (privilege and stack selection), and the interrupt mask registers PRIMASK, FAULTMASK and BASEPRI.

2. WHAT DOES EACH ONE DO, STEP BY STEP?

  1. R0–R12: general data. R0–R7 are "low" registers that every 16-bit Thumb instruction can use; R8–R12 mostly need 32-bit encodings.
  2. R13 = SP: stack pointer. There are physically two: MSP (Main Stack Pointer, used by handlers and at reset) and PSP (Process Stack Pointer, used by RTOS tasks). Which one "R13" means depends on the mode and CONTROL.SPSEL. Bits [1:0] are always 0 (word aligned).
  3. R14 = LR: return address after BL, with bit 0 = 1. Inside an exception handler it holds EXC_RETURN (0xFFFF_FFxx).
  4. R15 = PC: reading it gives the current instruction address + 4 (because of the pipeline).
  5. xPSR: one 32-bit register with three non-overlapping parts: APSR (condition flags N Z C V Q and GE), IPSR (the number of the exception being handled, 0 in Thread mode) and EPSR (the Thumb bit and IT-block state).
  6. CONTROL: bit 0 nPRIV (Thread mode privilege), bit 1 SPSEL (Thread mode uses PSP), bit 2 FPCA (floating-point context active).
  7. PRIMASK / FAULTMASK / BASEPRI: switches that block interrupts — all of them, all but NMI, or only those at or below a priority level.

3. WORKED EXAMPLE — DECODE A REAL xPSR

Inside the USART2 interrupt on an STM32F407 the debugger shows xPSR = 0x6100_0036. Split it:

0x6100_0036 = 0110 0001 0000 0000 0000 0000 0011 0110
bits 31..28 = 0110 → N=0 Z=1 C=1 V=0   (last compare was equal, no borrow)
bit  24     = 1    → T=1 (Thumb, as it must be)
bits 8..0   = 0x036 = 54 → exception number 54 = 16 + 38 → IRQ 38 = USART2

So IPSR tells you which handler is running without looking at the code: exception number − 16 = IRQ number. HardFault would show 3, SysTick 15, PendSV 14.

5. WHAT GOES WRONG IF…

MISTAKEAn unprivileged RTOS task calls __disable_irq() (CPSID i) to protect a critical section. Symptom: no fault, no warning — and interrupts still fire, so the shared data is occasionally corrupted. Why: writes to PRIMASK/BASEPRI/FAULTMASK/CONTROL from unprivileged code are silently ignored by the architecture. Fix: use the RTOS critical-section API, which goes through an SVC or runs privileged.
MISTAKEReading MRS r0, EPSR to check the Thumb bit. Symptom: always reads 0. EPSR fields read as zero via MRS; you only see T in a stacked xPSR (e.g. in a fault handler's exception frame).

6. SAY IT LIKE THIS

Cortex-M has R0–R12, SP (banked MSP/PSP), LR and PC, plus special registers. xPSR combines APSR flags, IPSR — the active exception number, 0 in Thread mode — and EPSR with the Thumb bit. CONTROL holds nPRIV, SPSEL and FPCA. PRIMASK, FAULTMASK and BASEPRI mask interrupts, and they are privileged-only: unprivileged writes are silently ignored, not faulted.

AArch64 register file and PSTATE

▶

1. WHAT IS IT?

In AArch64 (the 64-bit state of ARMv8-A and later), the register file is wider and larger: 31 general-purpose 64-bit registers X0–X30, 32 SIMD/FP registers V0–V31 of 128 bits, and per-EL stack pointers. The status flags that AArch32 kept in one CPSR register are now spread into separate fields collectively called PSTATE.

2. HOW IT IS ORGANISED, STEP BY STEP

  1. Xn and Wn. X5 is the full 64-bit register; W5 is its low 32 bits. Writing W5 zeroes the upper 32 bits of X5 (no stale garbage, unlike AArch32 partial writes).
  2. X30 = LR (link register). There is no general "PC register": you cannot MOV into the PC; you use B, BR, RET.
  3. Register number 31 is not a normal register: in most data-processing instructions it means XZR (always reads 0, writes discarded); in address calculations and some ADD/SUB forms it means SP.
  4. One SP per EL: SP_EL0, SP_EL1, SP_EL2, SP_EL3. At EL1, PSTATE.SPSel chooses SP_EL0 (mode "EL1t") or SP_EL1 ("EL1h"). Kernels normally run on SP_EL1 = EL1h.
  5. PSTATE fields are accessed individually: NZCV (flags), DAIF (mask bits for Debug, SError = asynchronous abort, IRQ, FIQ), CurrentEL (bits [3:2] = the EL number), SPSel, plus security features (PAN, TCO for MTE, BTYPE for BTI). On exception entry the whole PSTATE is copied into SPSR_ELx.

3. WORKED EXAMPLE — READING CurrentEL

At EL1, mrs x0, CurrentEL returns 0x4 = 0b0100. The EL is in bits [3:2] → (0x4 >> 2) & 3 = 1. At EL2 it would return 0x8 → 2; at EL3, 0xC → 3. At EL0 the instruction is UNDEFINED, so user code cannot read it at all.

DAIF immediate: msr daifset, #2. The 4-bit immediate is D=8, A=4, I=2, F=1, so #2 sets only the I bit → IRQs masked; #0xF masks everything.

4. CODE, LINE BY LINE

    return (el >> 2) & 3;           // 0..3

5. WHAT GOES WRONG IF…

MISTAKEPorting AArch32 assembly that does mov pc, lr or uses LDM/STM. Symptom: it does not assemble — A64 has no writable PC and no load/store-multiple. Use ret and ldp/stp register pairs instead.
MISTAKEUsing a 32-bit int to hold a pointer in AArch64 code. Symptom: works in small tests, then crashes when an address above 4 GB (e.g. 0xFFFF_8000_…kernel address) is truncated. Use uintptr_t.

6. SAY IT LIKE THIS

AArch64 has 31 64-bit registers X0–X30 with W views, X30 is the link register, register 31 is XZR or SP depending on the instruction, and the PC is not directly writable. Each EL has its own stack pointer. PSTATE is a set of separate fields — NZCV, DAIF, CurrentEL, SPSel — and it is saved into SPSR_ELx on exception entry.

7. REFERENCE DETAIL

  • X0–X30: 31 general 64-bit registers; W0–W30 are the low 32 bits (writing Wn zero-extends into Xn). X30 = LR.
  • Register number 31 means XZR/WZR (zero) or SP depending on the instruction. There is one SP per EL: SP_EL0, SP_EL1, SP_EL2, SP_EL3. PSTATE.SPSel chooses SP_EL0 ("ELxt") or SP_ELx ("ELxh").
  • PC is not a GPR — you cannot MOV to it; use B/BR/RET. ADR/ADRP give PC-relative addresses.
  • V0–V31: 128-bit SIMD/FP (Qn/Dn/Sn/Hn/Bn views). With SVE they are the low 128 bits of Z0–Z31.
  • PSTATE is not one register: fields are accessed separately — NZCV, DAIF (Debug, SError, IRQ, FIQ masks), CurrentEL (bits[3:2]), SPSel, PAN, UAO, SSBS, TCO (MTE), BTYPE (BTI). On exception entry the whole PSTATE is saved into SPSR_ELx.
"CurrentEL can be read from EL0." No: reading CurrentEL at EL0 is UNDEFINED. User code cannot query its own EL (it is always 0).

AAPCS (32-bit): who owns which register

▶

1. WHAT IS IT?

The AAPCS (Procedure Call Standard for the Arm Architecture) is the agreement that lets code from different compilers, libraries and hand-written assembly call each other. It answers: where do the arguments go, where does the result come back, which registers may a called function destroy, and how must the stack look at the moment of a call. It is part of the ABI (Application Binary Interface). It is not enforced by hardware — but the Cortex-M exception model was designed around it.

2. HOW A CALL WORKS, STEP BY STEP

  1. Caller places arguments: first four 32-bit words of arguments in R0, R1, R2, R3 (in order). Further arguments go on the stack, the first one at [SP].
  2. 64-bit arguments (long long, or double in soft-float) need an even-numbered register pair: R0:R1 or R2:R3. If the next free register is odd, it is skipped.
  3. Caller checks SP alignment: SP must be a multiple of 8 at the call.
  4. BL puts the return address in LR and jumps.
  5. Callee prologue: if it needs R4–R11 (callee-saved, "variable" registers) it pushes them first, plus LR if it calls other functions.
  6. Callee may freely destroy R0–R3 and R12 (caller-saved, "scratch" registers).
  7. Result in R0 (32-bit) or R0:R1 (64-bit). The epilogue restores R4–R11 and returns with pop {..., pc} or bx lr.

3. WORKED EXAMPLE — f(int a, long long b, int c)

void f(int a, long long b, int c);   f(1, 0x0000000200000003, 7);

a (4 B)  → NCRN = 0 → R0 = 1                   NCRN = next core register number
b (8 B)  → NCRN = 1 is odd → skip R1 → R2:R3   R2 = 0x00000003 (low word) · R3 = 0x00000002 (high)
c (4 B)  → NCRN = 4, registers exhausted → stack [SP+0] = 7
Outgoing stack area: 4 bytes → caller reserves 8 so SP stays 8-aligned.

Notice R1 is wasted. If you reorder the declaration to f(int a, int c, long long b), a → R0, c → R1, b → R2:R3, and nothing goes on the stack: one store and one load fewer per call. Argument order is a real optimisation on ARM.

5. WHAT GOES WRONG IF…

MISTAKEAssembly routine uses R4 as a temporary without saving it. Symptom: the C caller's loop counter (kept in R4 by the compiler) changes "randomly" after the call, giving an infinite or short loop — only at -O2, because at -O0 the variable lived in RAM. Why: R4–R11 are callee-saved; the caller relies on them surviving.
MISTAKEA home-made scheduler starts a task with SP = 0x2000_1A54 (4 mod 8). Symptom: printf("%f") prints garbage only in that task. Why: va_arg(ap, double) rounds its pointer up to a multiple of 8, assuming the argument area was 8-aligned; with a 4-aligned SP it skips the wrong word.
✖ WRONG
static uint32_t stack2[257];
tcb.sp = &stack2[257];   /* may be 4 mod 8 */
✔ RIGHT

6. SAY IT LIKE THIS

Under AAPCS, R0–R3 carry the first arguments and R0 or R0:R1 the result; R0–R3 and R12 are caller-saved scratch, R4–R11 are callee-saved. 64-bit values use an even register pair, so f(int, long long) leaves R1 empty. Big structs come back through a hidden pointer in R0, and SP must be 8-byte aligned at every public call — otherwise va_arg on doubles and LDRD break.

RULES THAT GET ASKED

  • Arguments are assigned to R0–R3 in order; anything that does not fit goes on the stack (first stack argument at [SP] at the call).
  • 64-bit values (long long, double in soft-float) need an even/odd register pair: f(int a, long long b) puts a in R0, skips R1, b in R2:R3. A third int then goes to the stack.
  • Structs ≤ 4 bytes return in R0; larger structs are returned through memory: the caller passes a hidden pointer in R0 and the real arguments shift by one.
  • A composite argument can be split between the last core registers and the stack (AAPCS32 only, and only if nothing has gone to the stack yet).
  • With -mfloat-abi=hard (AAPCS-VFP) floats go in S0–S15 and doubles in D0–D7 with back-filling, but variadic functions always use the base (core-register) rules, so printf("%f", x) passes the double in R2:R3.
  • SP must be 8-byte aligned at every public function call boundary; 4-byte alignment is enough inside a function.
Why 8-byte stack alignment? So that 64-bit values (doubles, long long) stored on the stack can be accessed with LDRD/STRD and so that va_arg can find 8-byte-aligned doubles. va_arg rounds its pointer up to a multiple of 8 assuming the save area started 8-aligned; if SP was only 4-aligned, it skips the wrong word and printf("%f") prints garbage. On Cortex-M exception entry, CCR.STKALIGN = 1 makes hardware re-align the frame for exactly this reason.
Why split caller/callee-saved? Leaf functions use only R0–R3/R12 and save nothing (fast); non-leaf functions keep long-lived values in R4–R11 so they survive calls without being saved around every call. It is an optimisation of total push/pop traffic.
INTERMEDIATE

AAPCS64 and Apple's arm64 variations

▶

1. WHAT IS IT?

AAPCS64 is the calling convention for AArch64 code: Linux, Android, Windows and macOS/iOS on 64-bit Arm all use it, with small platform variations (Apple's is the best-known). Because AArch64 has 31 registers instead of 13, it passes up to eight integer arguments and eight floating-point arguments in registers.

2. HOW A CALL WORKS, STEP BY STEP

  1. Integer and pointer arguments → X0, X1 … X7 (NGRN = next general register number). FP/SIMD arguments → V0 … V7 (NSRN). The two counters are independent.
  2. A struct up to 16 bytes goes in up to two X registers. A struct of 1–4 identical float/double members (an HFA, Homogeneous Floating-point Aggregate) goes in consecutive V registers. A struct bigger than 16 bytes is copied by the caller and passed by pointer.
  3. If an argument does not fit in the remaining registers it goes entirely on the stack — AAPCS64 never splits a struct between registers and stack.
  4. A large struct result: the caller passes the address of the result buffer in X8, which is not one of the argument registers.
  5. The callee must preserve X19–X28, X29 (frame pointer), SP, and the low 64 bits of V8–V15. Everything else is scratch.
  6. SP must be 16-byte aligned whenever it is used to access memory.

3. WORKED EXAMPLE

struct big { long a, b, c; };          // 24 bytes
struct big g(int x, double y, struct big s, float z);

result (24 B > 16)  → caller passes &result in X8
x  int              → W0           (NGRN 0 → 1)
y  double           → D0           (NSRN 0 → 1)
s  24-byte struct   → caller copies it, passes pointer in X1   (NGRN 1 → 2)
z  float            → S1           (NSRN 1 → 2)

Compare AAPCS32 for the same call (soft-float): the hidden result pointer takes R0, x → R1, y (8 B) needs an even pair → R2:R3, then s and z go on the stack. AArch64 kept everything in registers.

Frame size example: a function saving X19, X20 and the frame record {X29, X30} with no locals needs 16 + 16 = 32 bytes → stp x29, x30, [sp, #-32]! keeps SP 16-aligned.

5. WHAT GOES WRONG IF…

MISTAKEDeclaring int printf(); (no prototype) or calling a variadic function through a non-variadic function pointer, on Apple silicon. Symptom: printed values are garbage on macOS/iOS but correct on Linux arm64. Why: Apple's ABI puts every variadic (anonymous) argument on the stack in 8-byte slots, while the generic AAPCS64 puts them in X/V registers. The caller and callee disagree about where the arguments are.
MISTAKEUsing X18 as a scratch register in hand-written assembly. Symptom: random crashes on Apple and Windows, where X18 is reserved by the platform (Windows uses it for the thread environment block). Never touch X18 in portable code.

6. SAY IT LIKE THIS

AAPCS64 passes up to eight integer arguments in X0–X7 and eight FP arguments in V0–V7, returns in X0 or V0, and uses X8 for the address of a large struct result. X19–X28, the frame pointer X29 and the low halves of V8–V15 are callee-saved, X30 is the link register, and SP is always 16-byte aligned. Structs over 16 bytes go by reference and nothing is split between registers and stack. Apple differs by reserving X18 and passing variadic arguments on the stack.

Thread/Handler mode, privilege, MSP/PSP

▶

1. WHAT IS IT?

A Cortex-M core is always in one of two modes: Thread mode (normal code: main(), RTOS tasks) or Handler mode (running an exception or interrupt handler). Independently, Thread mode can be privileged (may do anything) or unprivileged (restricted). And the core has two stack pointers, MSP and PSP. These three switches are how an RTOS protects itself from buggy tasks.

2. HOW THE SWITCHES CHANGE, STEP BY STEP

  1. Reset: Thread mode, privileged, using MSP (loaded from vector table word 0).
  2. RTOS starts the first task: it writes PSP = the task's stack top, then CONTROL = 0x3 (bit 1 SPSEL = 1 → Thread uses PSP; bit 0 nPRIV = 1 → unprivileged), then an ISB so the change takes effect before the next instruction.
  3. Interrupt or SVC: hardware switches to Handler mode — always privileged, always on MSP — and pushes the 8-word frame onto the stack that was in use (PSP for a task).
  4. Return: EXC_RETURN in LR tells the hardware which mode and stack to go back to (0xFFFF_FFFD = Thread mode, PSP).
  5. Unprivileged code can never raise its own privilege: writing CONTROL.nPRIV = 0 from Thread-unprivileged is ignored. The only path up is an exception (SVC), and a privileged handler decides.

3. WORKED EXAMPLE — WHY TWO STACKS SAVE RAM

Ten RTOS tasks, interrupts nested up to 4 deep, each handler needing ~120 bytes of locals plus the 32-byte hardware frame (104 bytes with FP).

  • One stack for everything: every task stack must have room for the worst-case interrupt nesting: 4 × (104 + 120) = 896 bytes extra per task → 10 × 896 ≈ 8.8 KB wasted.
  • MSP + PSP: interrupts run on the single MSP stack. Each task stack only needs room for one hardware frame (up to 104 bytes) plus what the context switch saves (R4–R11 = 32 bytes, + S16–S31 = 64 bytes with FP). The nesting headroom is paid once on MSP: ~0.9 KB total.

4. CODE, LINE BY LINE

/* Start the first task: unprivileged, on PSP */

    __set_PSP((uint32_t)psp_top);        // must be 8-byte aligned

5. WHAT GOES WRONG IF…

MISTAKEAn unprivileged task writes NVIC->ISER[1] to enable its interrupt. Symptom: precise BusFault (CFSR.PRECISERR, BFAR = 0xE000_E104), escalated to HardFault if BusFault is disabled. Why: the System Control Space (0xE000_E000–0xE000_EFFF: NVIC, SCB, SysTick, MPU) is privileged-only by architecture, independent of the MPU.
MISTAKEForgetting the __ISB() after writing CONTROL. Symptom: usually nothing on an M3/M4 — and an intermittent wrong-stack push on faster cores, because already-fetched instructions may still execute with the old SP selection.

6. SAY IT LIKE THIS

Cortex-M has Thread and Handler mode; Handler mode is always privileged and always uses MSP, while Thread mode's privilege and stack come from CONTROL.nPRIV and SPSEL. An RTOS runs tasks unprivileged on PSP and the kernel and ISRs on MSP, so task stacks don't need interrupt-nesting headroom. Unprivileged code can't raise its privilege; it executes SVC, and the privileged handler decides.

  • Unprivileged code cannot raise its own privilege — writing CONTROL.nPRIV = 0 is ignored. The only way back is an exception: SVC #n enters Handler mode (privileged), and the handler may clear nPRIV before returning.
  • What unprivileged code cannot do: access the System Control Space (NVIC, SCB, SysTick, MPU at 0xE000_E000–0xE000_EFFF) → BusFault (precise; MPU is not involved); change PRIMASK/BASEPRI/FAULTMASK/CONTROL (silently ignored); access regions marked privileged-only by the MPU → MemManage.
  • Why two stacks? Each RTOS task gets its own PSP stack, so the context switch is "save R4–R11 on PSP, swap PSP". Interrupts always land on the MSP, so no task stack needs headroom for worst-case interrupt nesting — only for one 8–26 word exception frame.
INTERMEDIATE

Cortex-M exception entry/return in one card (contrast with A-profile)

▶

1. WHAT IS IT?

This card is the Cortex-M exception entry and return sequence — what the hardware does between "interrupt request" and "first handler instruction", and back. It is the most-asked Cortex-M question, and the contrast with A-profile (which saves almost nothing) is a favourite follow-up.

2. ENTRY AND RETURN, STEP BY STEP (CORTEX-M4)

  1. Decision: the NVIC finds the highest-priority pending, enabled exception that may preempt the current one.
  2. Stacking: the core pushes xPSR, PC (return address), LR, R12, R3, R2, R1, R0 — 8 words = 32 bytes — onto the active stack (MSP or PSP). If CONTROL.FPCA = 1 (the code used the FPU) it reserves an extended frame of 26 words = 104 bytes for S0–S15 and FPSCR as well; with lazy stacking (FPCCR.LSPEN = 1) the FP registers are only written if the handler itself uses the FPU.
  3. Alignment: if SP is not a multiple of 8, the hardware inserts a 4-byte pad first and records it in stacked xPSR bit 9 (CCR.STKALIGN = 1, the default).
  4. Vector fetch (in parallel with stacking, on a separate bus): handler address ← word at VTOR + 4 × exception number.
  5. Register update: LR ← EXC_RETURN, IPSR ← exception number, mode ← Handler, SP ← MSP.
  6. First handler instruction: 12 cycles after the request on Cortex-M4 with zero-wait-state memory (15 on M0+).
  7. Return: the handler executes BX LR or POP {…, PC} with the EXC_RETURN value. The core unstacks the frame, removes the pad if bit 9 says so, and resumes.
  8. Optimisations: tail-chaining — if another exception is pending at return, skip the pop + push and go straight to it (6 cycles on M4); late arrival — if a higher-priority IRQ arrives during stacking, it uses the frame being built and runs first.

3. WORKED EXAMPLE — DECODING EXC_RETURN

EXC_RETURN bit:   4 (FType)   3 (Mode)    2 (SPSEL)
0xFFFF_FFF1  →    1 no FP     0 Handler   0 MSP     return to a nested handler
0xFFFF_FFF9  →    1 no FP     1 Thread    0 MSP     bare-metal main() was interrupted
0xFFFF_FFFD  →    1 no FP     1 Thread    1 PSP     an RTOS task was interrupted
0xFFFF_FFED  →    0 FP frame  1 Thread    1 PSP     task using the FPU was interrupted

Timing at 168 MHz: 12 cycles × 5.95 ns = 71 ns entry; a back-to-back second interrupt via tail-chaining costs 6 cycles = 36 ns instead of 12 + 12 (unstack + restack).

5. WHAT GOES WRONG IF…

MISTAKEA handler is compiled with an "interrupt" attribute that also saves R0–R3 again, or written in assembly that saves everything. Symptom: nothing breaks, but latency and stack use double. On Cortex-M the hardware frame already holds them.
MISTAKEA handler overwrites LR (e.g. calls a function without saving LR, in hand-written assembly) and then returns with bx lr. Symptom: instead of exception return, the core branches to a normal address in Handler mode; the stacked frame is never popped, the stack leaks, and later an INVPC UsageFault or HardFault occurs.

6. SAY IT LIKE THIS

On entry a Cortex-M pushes R0–R3, R12, LR, PC and xPSR — 8 words, or 26 with FP context — fetches the vector in parallel, puts EXC_RETURN in LR and switches to Handler mode on MSP, in 12 cycles on an M4. Those are exactly the AAPCS caller-saved registers, so handlers are plain C. Return is BX LR with the EXC_RETURN value; tail-chaining and late arrival cut back-to-back latency. AArch64, by contrast, saves only PSTATE into SPSR and the return address into ELR.

7. REFERENCE DETAIL

  • Entry (Cortex-M4: 12 cycles to the first handler instruction with zero-wait-state memory; M0+: 15): hardware pushes R0–R3, R12, LR, PC, xPSR (8 words = 32 B), or 26 words with FP context (S0–S15, FPSCR, reserved; lazily stacked on M4F when FPCCR.LSPEN = 1).
  • LR ← EXC_RETURN: 0xFFFF_FFF1 (return to Handler, MSP), 0xFFFF_FFF9 (Thread, MSP), 0xFFFF_FFFD (Thread, PSP); bit 4 = 0 (0x…E1/E9/ED) if an FP frame was stacked. On ARMv8-M extra bits: S (bit 6, frame on Secure stack), DCRS (bit 5), ES (bit 0, handler was Secure).
  • Return: BX lr / POP {pc} with an EXC_RETURN value triggers unstacking. Tail-chaining (6 cycles on M4) skips the pop/push between back-to-back exceptions; late arrival lets a higher-priority IRQ use the frame already being stacked.
The big contrast: AArch64 pushes nothing. It copies PSTATE to SPSR_ELx and the return address to ELR_ELx, then jumps to the vector — the software stub saves X0–X30. Cortex-M stacks the AAPCS caller-saved set in hardware so that an ISR can be an ordinary C function. Interviewers love asking "why exactly those 8 registers?" — because they are the ones a C function is allowed to clobber; R4–R11 are preserved by the handler itself if it uses them.

Exception levels EL0–EL3 and security states

▶

1. WHAT IS IT?

On ARMv8-A, privilege is organised in four Exception Levels, EL0 to EL3. The number is the privilege: EL0 is the least privileged (apps), EL3 the most (secure firmware). Separately, each level below EL3 can run in one of two security states — Secure or Non-secure — selected by the bit SCR_EL3.NS. This 2-D grid is what lets one phone chip run apps, Android, a hypervisor, a trusted OS for fingerprint keys, and boot firmware, all isolated in hardware.

              SECURE WORLD                 NON-SECURE (NORMAL) WORLD
 EL3   ┌───────────────── Secure Monitor (TF-A BL31) ─────────────────┐
 EL2   │ S-EL2: SPM (Hafnium)         │ Hypervisor (KVM, Xen)          │
 EL1   │ S-EL1: Trusted OS (OP-TEE)   │ Rich OS kernel (Linux)         │
 EL0   │ S-EL0: Trusted Apps          │ User apps                      │
       └──────────────────────────────┴────────────────────────────────┘
          ▲ exceptions go UP (or stay)            ERET goes DOWN ▼

2. THE RULES, STEP BY STEP

  1. Going up happens only through an exception: a system call (SVC → EL1), hypervisor call (HVC → EL2), secure monitor call (SMC → EL3), an interrupt, or a fault.
  2. An exception is taken to the same or a higher EL, never lower, and never to EL0. EL0 has no vector table.
  3. Going down happens only with ERET (exception return), which restores PC from ELR_ELx and PSTATE from SPSR_ELx.
  4. Each EL ≥ 1 has its own copy of the exception registers: VBAR_ELx (vector base), ELR_ELx (return address), SPSR_ELx (saved state), ESR_ELx (syndrome = cause), FAR_ELx (fault address), SP_ELx, SCTLR_ELx (system control).
  5. Switching worlds is EL3's job: it flips SCR_EL3.NS and ERETs. The NS bit travels with every bus transaction, so memory controllers (TZASC) can refuse Non-secure access to secure memory.
  6. Routing switches decide which EL gets interrupts: HCR_EL2.IMO sends IRQs to EL2, SCR_EL3.IRQ sends them to EL3; otherwise they go to EL1.

3. WORKED EXAMPLE — ONE FINGERPRINT CHECK

  1. App (NS-EL0) calls the Android API → SVC → Linux (NS-EL1).
  2. Linux TEE driver → SMC with function ID in W0 → TF-A (EL3).
  3. EL3 saves ~30 Non-secure EL1 system registers, restores OP-TEE's, sets SCR_EL3.NS = 0, ERET → OP-TEE (S-EL1).
  4. OP-TEE ERETs into the fingerprint TA at S-EL0, which reads the sensor data from secure memory and compares templates.
  5. Result returns: TA → SVC → OP-TEE → SMC → EL3 → swap context back, NS = 1 → ERET → Linux → ERET → app.

That is 4 exceptions up and 4 ERETs down, with two full world switches — typically a few microseconds total, mostly the EL1 context save/restore.

4. WHAT GOES WRONG IF…

MISTAKE"EL3 is the hypervisor." Why wrong: EL2 is the hypervisor level; EL3 is the secure monitor. The hypervisor is still Non-secure software and cannot see secure memory.
MISTAKEExpecting an IRQ to interrupt EL2 code when it is routed to EL1. Symptom: the interrupt seems "lost" while the hypervisor runs. Why: exceptions never go to a lower EL; it stays pending until an ERET drops the core to EL1 or below, then fires immediately. Try it in the Explorer tab.

5. SAY IT LIKE THIS

ARMv8-A has EL0 for applications, EL1 for the OS kernel, EL2 for the hypervisor and EL3 for the secure monitor, and SCR_EL3.NS selects the Secure or Non-secure world for EL0–EL2. Exceptions move to the same or a higher EL, never lower; only ERET goes down. Each EL has its own VBAR, ELR, SPSR and ESR, and because EL1 system registers aren't banked by world, EL3 saves and restores them on every world switch.

INTERMEDIATE

AArch64 exception entry: VBAR_ELx, 16 vectors × 0x80, ELR/SPSR/ESR, ERET

▶

1. WHAT IS IT?

On AArch64 each EL (1, 2, 3) has a vector table whose start address is in VBAR_ELx (Vector Base Address Register). Unlike Cortex-M, the table contains instructions, not addresses: the core jumps into the table and executes the code there (usually a branch to the real handler). There are 16 slots of 0x80 bytes, chosen by where the exception came from and what kind it is.

2. WHAT HAPPENS ON ENTRY, STEP BY STEP

  1. Pick the target EL from the exception type and routing bits (SVC → EL1, HVC → EL2, SMC → EL3, IRQ → wherever routed).
  2. SPSR_ELx ← PSTATE: flags, DAIF masks, and in M[3:0] the EL and stack the code was using.
  3. ELR_ELx ← return address: the next instruction for SVC/HVC/SMC; the faulting instruction itself for aborts (so it can be retried after fixing the page); the next instruction to run for interrupts.
  4. ESR_ELx ← syndrome (synchronous exceptions and SError): EC = Exception Class in bits [31:26], IL = instruction length in bit 25, ISS = class-specific details in [24:0]. For aborts, FAR_ELx ← faulting virtual address.
  5. PSTATE.DAIF ← 1111 (all interrupts masked), EL ← target, SPSel ← 1 (use SP_ELx).
  6. PC ← VBAR_ELx + offset. Offset = group (0x000 / 0x200 / 0x400 / 0x600) + type (0x00 sync / 0x80 IRQ / 0x100 FIQ / 0x180 SError).
  7. No general registers are saved. The first instructions in the slot must save whatever they will use.

3. WORKED EXAMPLE — COMPUTING THE VECTOR ADDRESS

VBAR_EL1 = 0xFFFF_8000_0801_0800      (bits[10:0] = 0 → 2 KB aligned ✔)

A user process (EL0, AArch64) executes SVC #0:
  group  = "lower EL, AArch64"   = 0x400
  type   = synchronous           = 0x000
  PC     = 0xFFFF_8000_0801_0800 + 0x400 = 0xFFFF_8000_0801_0C00
  ESR_EL1 = 0x5600_0000 → EC = 0x56 >> 2 = 0x15 (SVC from AArch64), IL = 1, ISS = imm16 = 0

The kernel itself touches a bad pointer (EL1, using SP_EL1):
  group  = "current EL, SP_ELx"  = 0x200,  type sync → PC = VBAR + 0x200
  ESR_EL1.EC = 0x25 (data abort, same EL), FAR_EL1 = the bad address

How to extract EC: 0x5600_0000 >> 26 = 0x15. (0x56 in the top byte = 0101 0110₂; the top six bits 010101₂ = 0x15, then IL = 1.)

MISTAKEA handler runs C code before saving X0–X18. Symptom: the interrupted program's registers are randomly corrupted after the interrupt. On AArch64 nothing is saved by hardware.

6. SAY IT LIKE THIS

On exception entry AArch64 copies PSTATE to SPSR_ELx, the return address to ELR_ELx, the cause to ESR_ELx and the faulting address to FAR_ELx, masks DAIF and jumps to VBAR_ELx plus an offset. The table is code, 2 KB aligned, with 16 slots of 0x80 bytes: four source groups — current EL with SP_EL0, current EL with SP_ELx, lower EL AArch64, lower EL AArch32 — times sync, IRQ, FIQ and SError. Software saves all general registers; ERET restores PC and PSTATE.

ADVANCED

Dropping from EL3 to EL1 at boot (and the Linux boot chain)

▶

1. WHAT IS IT?

An ARMv8-A core comes out of reset at the highest EL it implements — normally EL3, in Secure state. Linux, however, wants to run at EL2 or EL1 in the Non-secure world. Boot firmware therefore has to drop down through the levels. Since exceptions only go up, the drop uses ERET: firmware writes fake "saved" values into SPSR_EL3 and ELR_EL3 as if an exception had happened, then returns into the lower level.

2. THE DROP, STEP BY STEP

  1. Configure what the lower levels will be: SCR_EL3.RW = 1 (EL2/EL1 run AArch64), SCR_EL3.NS = 1 (they are Non-secure), SCR_EL3.HCE = 1 (HVC allowed).
  2. Configure EL2 if you skip it: HCR_EL2.RW = 1 so EL1 is AArch64.
  3. Put EL1 into a known state: SCTLR_EL1 with MMU and caches off and the RES1 bits set.
  4. Craft SPSR_EL3: which EL and stack to return to (M[3:0]) and which interrupts stay masked (DAIF).
  5. Write ELR_EL3 = the address where the lower level should start.
  6. ERET: PC ← ELR_EL3, PSTATE ← SPSR_EL3 — the core is now at EL1.

3. WORKED EXAMPLE — BUILDING SPSR = 0x3C5

bit:   9 8 7 6 │ 5 4 │ 3 2 1 0
       D A I F │ 0 0 │ M[3:0]
       1 1 1 1 │ 0 0 │ 0 1 0 1        M = 0b0101 = EL1h (EL1, using SP_EL1)
= 0b11_1100_0101 = 0x3C5

DAIF all set (0x3C0) means the new EL1 code starts with interrupts masked — safe, because it has not installed its vector table yet. M = 0b0101 → bits [3:2] = 01 = EL1, bit 0 = 1 = "h" (use SP_ELx). Other encodings: EL0t 0b0000, EL1t 0b0100, EL2h 0b1001, EL3h 0b1101.

The real chain on a phone or automotive SoC: BootROM (EL3) → BL2 → BL31 (EL3 runtime, stays resident) → BL32 = OP-TEE (S-EL1) → BL33 = U-Boot/UEFI (NS-EL2) → Linux (NS-EL2 with VHE, or NS-EL1). Every arrow downward is one ERET.

4. CODE, LINE BY LINE

6. SAY IT LIKE THIS

The core resets at EL3. To get to EL1 I set SCR_EL3.RW and NS so the lower levels are AArch64 and Non-secure, set HCR_EL2.RW, put SCTLR_EL1 in a known MMU-off state, write SPSR_EL3 = 0x3C5 for EL1h with DAIF masked and ELR_EL3 = the entry point, then ERET. ERET is the only way to lower the EL; the TF-A chain BL1, BL2, BL31, BL32 OP-TEE, BL33 U-Boot, Linux is a series of those drops.

7. REFERENCE DETAIL

An ARMv8-A core resets into the highest implemented EL (normally EL3, AArch64 if RVBAR/AA64nAA32 says so). Typical chain on a phone or automotive SoC: BootROM (EL3) → BL2 → BL31 (EL3 runtime monitor) → BL32 (OP-TEE, S-EL1) → BL33 (U-Boot/UEFI, NS-EL2) → Linux (NS-EL2 with VHE, or NS-EL1). Each step down is an ERET with a crafted SPSR.

"Just branch to the kernel." A BR never changes EL. The only instruction that lowers the EL is ERET, and only exceptions raise it.
ADVANCED

Key system registers: SCTLR, TTBR0/1, TCR, MAIR

▶

1. WHAT IS IT?

System registers are the configuration registers of an A-profile core, read and written with MRS/MSR (they are not memory-mapped). The suffix _EL1 says which level owns it. Four of them define virtual memory, and interviewers love "walk me through turning on the MMU": MAIR_EL1 (memory types), TCR_EL1 (translation control), TTBR0/1_EL1 (page-table base addresses) and SCTLR_EL1 (the on-switch).

2. TURNING ON THE MMU, STEP BY STEP

  1. MAIR_EL1 — define up to 8 memory types, one byte each. Page-table entries later refer to them by a 3-bit index (AttrIndx) instead of spelling out cacheability.
  2. TCR_EL1 — choose virtual address size (T0SZ/T1SZ: VA bits = 64 − TxSZ), page size (TG0/TG1 granule: 4 KB, 16 KB or 64 KB), and how the page-table walks themselves are cached.
  3. TTBR0_EL1 — physical address of the page tables for the lower VA range (0x0000_… user space), plus an ASID (Address Space ID) so TLB entries of different processes do not clash. TTBR1_EL1 — tables for the upper VA range (0xFFFF_… kernel).
  4. Invalidate the TLB (tlbi vmalle1), then dsb (wait for it) and isb.
  5. SCTLR_EL1 — set M (MMU on), C (data cache), I (instruction cache). Then isb: the next instruction fetch is translated.

3. WORKED EXAMPLE — T0SZ AND MAIR BYTES

T0SZ = 16  → VA size = 64 − 16 = 48 bits → user range 0x0000_0000_0000_0000 … 0x0000_FFFF_FFFF_FFFF
           (256 TB). With 4 KB pages: 48 − 12 = 36 index bits = 4 levels × 9 bits.
T1SZ = 16  → kernel range 0xFFFF_0000_0000_0000 … 0xFFFF_FFFF_FFFF_FFFF

MAIR_EL1 = ATTR(0,0x00) | ATTR(1,0x04) | ATTR(2,0x44) | ATTR(3,0xFF)
         = 0x0000_0000_FF44_0400
  Attr0 = 0x00 Device-nGnRnE   (strict MMIO)
  Attr1 = 0x04 Device-nGnRE    (normal MMIO)
  Attr2 = 0x44 Normal, non-cacheable
  Attr3 = 0xFF Normal, write-back, read+write allocate  (RAM)
A PTE for RAM sets AttrIndx = 3; a PTE for a UART sets AttrIndx = 1.

GIC: distributor, redistributor, CPU interface; SGI/PPI/SPI/LPI

▶

1. WHAT IS IT?

The GIC (Generic Interrupt Controller) is Arm's interrupt controller for A-profile and R-profile systems — the equivalent of the Cortex-M NVIC, but a separate block that serves many cores. It receives hundreds of interrupt lines from peripherals, decides priority and which core gets each one, and signals that core's IRQ or FIQ input. Current systems use GICv3 or GICv4.

2. HOW ONE INTERRUPT FLOWS, STEP BY STEP

  1. A UART raises its line, say SPI (Shared Peripheral Interrupt) INTID 33 + 32 = 65.
  2. The Distributor (GICD, one per system) checks it is enabled, looks up its priority, group (Secure/Non-secure) and route — GICD_IROUTER65 holds the target core's affinity (e.g. core 2).
  3. The Redistributor for core 2 (GICR, one per core) and its CPU interface compare the priority with the core's mask ICC_PMR_EL1 and its running priority. If higher, it asserts IRQ to the core.
  4. The core takes the IRQ exception (VBAR_EL1 + 0x280 or + 0x480). Software reads ICC_IAR1_EL1 = acknowledge: returns 65, and the interrupt moves pending → active.
  5. Driver handles the UART. Software writes 65 to ICC_EOIR1_EL1 = end of interrupt: priority drops, the interrupt becomes inactive.

3. WORKED EXAMPLE — INTID RANGES

  • Core 0 sends a "reschedule" IPI (inter-processor interrupt) to core 3: it writes ICC_SGI1R_EL1 with INTID 0 and target list {3}. That is an SGI (0–15).
  • Each core's own EL1 physical timer is PPI INTID 30; the virtual timer used by guests is 27. Same number on every core, but private to it.
  • A PCIe NVMe drive using MSI-X writes to the ITS (Interrupt Translation Service), which turns the write into an LPI numbered 8192+.
  • Reading 1023 from ICC_IAR1_EL1 means "spurious": the interrupt was withdrawn or taken by another core. Return without EOI.

TrustZone on A-profile: monitor, EL3, OP-TEE, SMC calls

▶

1. WHAT IS IT?

TrustZone splits one chip into two "worlds". The Secure world holds things that must stay secret even if Linux is completely hacked: device keys, DRM, fingerprint templates, secure boot verification. The Non-secure (normal) world runs everything else. On A-profile the switch between worlds is done by software at EL3 (the secure monitor), and hardware enforces the separation on the bus.

2. HOW THE ISOLATION IS ENFORCED, STEP BY STEP

  1. The core's current world is SCR_EL3.NS (for EL0–EL2; EL3 is always Secure).
  2. Every memory transaction leaving the core carries that NS bit on the bus (AxPROT[1] on AXI).
  3. The TZASC (TrustZone Address Space Controller, e.g. Arm TZC-400) in front of DRAM checks it: a Non-secure read of a secure carve-out returns an error or zeros.
  4. Peripheral firewalls (TZPC or vendor equivalents) mark peripherals such as the crypto engine or fuse controller secure-only.
  5. The GIC puts interrupts in groups: Group 0 and Secure Group 1 belong to the secure side; Non-secure Group 1 to Linux.
  6. Caches and TLBs tag entries with the security state, so secure data in a cache line is not visible to Non-secure accesses.

3. WORKED EXAMPLE — DECODING AN SMC FUNCTION ID

PSCI CPU_ON (64-bit)  W0 = 0xC400_0003
bit 31      = 1      → fast call (atomic: runs to completion, interrupts masked)
bit 30      = 1      → SMC64 calling convention (64-bit arguments)
bits 29:24  = 0x04   → owning entity 4 = Standard Secure Service (PSCI lives here)
bits 15:0   = 0x0003 → function 3 = CPU_ON
X1 = target core MPIDR, X2 = physical entry address, X3 = context id
Return: X0 = 0 (PSCI_SUCCESS) or a negative error code

A Trusted-OS (OP-TEE) call uses owning entity 50–63: OP-TEE's fast calls look like 0xB200_00nn (bit 31 = 1, owner 0x32 = 50), while its main "call with argument" is 0x3200_0004 — a yielding call (bit 31 = 0) that may be interrupted and resumed, because cryptographic work can take milliseconds.

5. WHAT GOES WRONG IF…

MISTAKEA user-space program executes smc #0 directly. Symptom: SIGILL "Illegal instruction". SMC is UNDEFINED at EL0 (ESR_EL1.EC = 0x00). User space must go through /dev/tee0 and the kernel's TEE driver.
MISTAKE"A hypervisor gives the same isolation as TrustZone." Why wrong: the hypervisor is itself Non-secure software and DMA masters bypass it; TrustZone memory is invisible to everything Non-secure, enforced by the TZASC on the bus.

6. SAY IT LIKE THIS

TrustZone-A gives two worlds on the same cores. SCR_EL3.NS sets the world, the NS bit travels on every bus transaction, and the TZASC, peripheral firewalls and GIC groups enforce it. Linux requests secure services with an SMC from EL1; the EL3 monitor decodes the SMCCC function ID in W0, saves the Non-secure EL1 context, restores OP-TEE's, clears NS and ERETs into S-EL1. EL0 cannot execute SMC.

7. REFERENCE DETAIL

  • Two worlds share the same cores. Hardware isolation comes from the NS bit on every bus transaction, checked by the TZASC/TZC-400 (DRAM carve-outs), TZPC/firewalls (peripherals: e.g. crypto engine, secure fuses), and secure-only GIC interrupts.
  • Normal world requests a service with SMC #0 from EL1 (or EL2). EL3 (TF-A BL31) decodes it per the SMC Calling Convention (SMCCC): function ID in W0 — bit 31 = fast (1) / yielding (0) call, bit 30 = SMC64, bits 29:24 = owning entity (0 = Arm architecture, 4 = Standard Secure Service such as PSCI, 50–63 = Trusted OS), bits 15:0 = function number. Arguments X1–X17, results X0–X3 (SMCCC v1.2).
  • For an OP-TEE call, BL31's dispatcher (OPTEED) saves the NS EL1 context, restores the secure EL1 context, clears SCR_EL3.NS and ERETs into OP-TEE at S-EL1. OP-TEE runs the TA at S-EL0 and returns with an SMC back to EL3.
  • Linux user space reaches OP-TEE via /dev/tee0 → TEE subsystem driver → SMC from EL1. EL0 cannot execute SMC: it is UNDEFINED there.
Why not just use a hypervisor for isolation? Because the hypervisor itself is normal-world software. TrustZone gives a root of trust whose memory is invisible to everything in the normal world, including EL2 and DMA masters, enforced on the bus.

TrustZone-M (ARMv8-M): SAU/IDAU, NSC, SG, BXNS/BLXNS, TF-M

▶

1. WHAT IS IT?

TrustZone-M is the microcontroller version of TrustZone, in ARMv8-M cores such as Cortex-M23 and Cortex-M33 (e.g. STM32L552, nRF5340, NXP LPC55S69). It has no EL3, no monitor and no SMC. Instead, the security state is decided by the address of the code being executed: run code from a Secure address and you are Secure; run code from a Non-secure address and you are Non-secure. A world switch is about as cheap as a function call.

2. HOW AN ADDRESS GETS ITS SECURITY ATTRIBUTE, STEP BY STEP

  1. The IDAU (Implementation-Defined Attribution Unit) is fixed by the chip vendor. On STM32L5, address bit 28 picks the alias: 0x0C00_0000 = Secure flash alias, 0x0800_0000 = Non-secure alias of the same flash.
  2. The SAU (Security Attribution Unit) is programmed by Secure boot code: up to 8 regions on Cortex-M33, each marked Non-secure or NSC (Non-secure-callable). Addresses not covered are Secure.
  3. The final attribute is the more secure of the two answers.
  4. Non-secure code may only enter Secure code by branching to an SG (Secure Gateway) instruction that sits in an NSC region. The linker generates those entry points ("veneers") in a section called .gnu.sgstubs.
  5. SG switches the core to Secure state and clears LR bit 0 — the marker for "return to Non-secure".
  6. The Secure function returns with BXNS LR: because LR[0] = 0, the core switches back to Non-secure.
  7. Any other branch from Non-secure into Secure memory → SecureFault with SFSR.INVEP (invalid entry point).
  NON-SECURE                      NSC (veneer)                SECURE
  0x0804_1F20  bl tz_sign ───►   0x0C03_E000  sg   ───►      0x0C00_2400  push {r4-r7,lr}
                                  0x0C03_E004  b.w __acle_se_tz_sign      …  work with key
  0x0804_1F24  str r0,[sp,#12] ◄──────────────────────────── 0x0C00_2504  bxns lr  (LR[0]=0)

Cost of a call: SG + B.W + BXNS + clearing ~5 registers ≈ 10–20 cycles, versus several microseconds for an A-profile SMC world switch.

MISTAKEThe Non-secure build gets the address of tz_sign from the Secure ELF (e.g. --just-symbols=secure.elf) instead of the CMSE import library. Symptom: first secure call → SecureFault, SFSR = 0x01 (INVEP), stacked PC = the real function (0x0C00_2400), not the veneer. 6. SAY IT LIKE THIS

In TrustZone-M the security state follows the address being executed. The SAU, programmed by Secure code, and the vendor's IDAU attribute each address as Secure, Non-secure-callable or Non-secure, and the more secure answer wins. Non-secure code enters only through an SG instruction in an NSC veneer; Secure code returns with BXNS and calls back with BLXNS, which hides the return address behind FNC_RETURN. Secure entry functions must clear registers and validate every Non-secure pointer with the TT instruction.

7. REFERENCE DETAIL

No monitor, no EL3, no SMC. The security state is a property of the address being executed. Each address is attributed Secure, Non-secure-callable (NSC) or Non-secure by the SAU (Security Attribution Unit, programmable, Cortex-M33: 0, 4 or 8 regions) combined with the IDAU (Implementation-Defined Attribution Unit, fixed by the SoC). The more secure of the two answers wins. Reference part: STM32L552 — secure flash alias 0x0C00_0000, non-secure 0x0800_0000; secure SRAM alias 0x3000_0000, non-secure 0x2000_0000 (address bit 28 selects the alias in ST's IDAU).

TRANSITIONS

  • NS → S: only by branching to an SG (Secure Gateway) instruction located in an NSC region. SG switches to Secure state and clears LR[0] so the return will go back to Non-secure. Any other branch from NS into Secure memory → SecureFault (SFSR.INVEP, invalid entry point). Data access from NS to Secure memory → SecureFault (SFSR.AUVIOL).
  • S → NS return: BXNS lr with LR[0] = 0. The compiler (cmse_nonsecure_entry) clears R0–R3 (except results), R12, APSR flags and FP registers first so no secret leaks in a register.
  • S → NS call (callback): BLXNS rX with bit 0 cleared. Hardware pushes the return address and partial PSR onto the Secure stack and sets LR = FNC_RETURN (0xFEFF_FFFF). When NS code returns with BX LR, the magic value makes hardware pop the real return address from the Secure stack — NS code never sees it.
  • Exceptions can cross states: an NS interrupt preempting Secure code pushes the normal frame plus R4–R11 and an integrity signature (0xFEFA_125B) onto the Secure stack, then clears the registers before the NS handler runs (EXC_RETURN.S = 1, DCRS = 0).

BANKED BETWEEN STATES

Pointer Authentication (PAC), BTI and MTE — the Apple-relevant trio

▶

1. WHAT IS IT?

Three ARMv8.x hardware features that make memory-corruption exploits much harder. They answer three different attacker moves:

  • PAC (Pointer Authentication Code, ARMv8.3): "the attacker overwrote a return address on the stack" → the pointer carries a cryptographic signature in its unused top bits; a forged pointer fails the check.
  • BTI (Branch Target Identification, ARMv8.5): "the attacker made an indirect branch jump into the middle of a function" → indirect branches may only land on special landing-pad instructions.
  • MTE (Memory Tagging Extension, ARMv8.5): "the attacker used a dangling pointer or a buffer overflow" → memory and pointers carry 4-bit colour tags that must match.

2. HOW PAC WORKS, STEP BY STEP

  1. With 48-bit virtual addresses, a 64-bit pointer has 16 unused high bits (bits 63:48; 8 of them if TBI — Top Byte Ignore — is on).
  2. At function entry, PACIASP computes a MAC (Message Authentication Code) = QARMA-style cipher(LR, modifier = SP, key = APIAKey) and writes the truncated result into those top bits of LR.
  3. LR is saved on the stack as usual — now signed.
  4. Before returning, AUTIASP recomputes the MAC with the current SP. If it matches, the top bits are restored to a normal canonical pointer. If not, the pointer is made non-canonical, so the RET faults (with FEAT_FPAC the AUT instruction itself faults, EC 0x1C).
  5. The keys live in system registers (APIAKeyLo/Hi_EL1 …) that EL0 cannot read, set per process by the kernel.

3. WORKED EXAMPLE

LR before signing  : 0x0000_AAAA_D000_1A40
LR after PACIASP   : 0x003B_AAAA_D000_1A40   ← bits 63:48 hold the PAC (example value 0x003B)
attacker overwrites saved LR on the stack with gadget 0x0000_AAAA_D000_2F00
AUTIASP computes PAC for 0x0000_AAAA_D000_2F00 with SP → ≠ 0x0000 → pointer poisoned
RET → translation fault on a non-canonical address → process killed instead of hijacked

Probability that a random guess passes: about 2−16 for a 16-bit PAC (≈ 1 in 65 536); fewer PAC bits with TBI or larger VAs (as low as ~7 bits). MTE: 4-bit tags give a 15/16 = 93.75 % chance of catching a random mismatch, and adjacent allocations are given different tags so linear overflows are always caught.

        bl    work

        ret                      // (retaa combines both)

5. WHAT GOES WRONG IF…

MISTAKEHand-written assembly or a longjmp/coroutine library switches stacks and returns through an LR signed with a different SP. Symptom: crashes only on PAC-enabled hardware (Apple arm64e, newer Android), never in the emulator. Fix: re-sign with the new modifier or use the generic-key/ABI helpers the platform provides.
MISTAKECode storing extra data in the top byte of pointers (tagged pointers). Symptom: breaks when MTE uses bits [59:56] for the logical tag, or when PAC uses the top bits. Use platform-sanctioned tagging only.

6. SAY IT LIKE THIS

PAC signs pointers — typically return addresses — by putting a MAC in the unused upper bits, computed from the pointer, a modifier like SP and a per-process key; PACIASP signs, AUTIASP verifies, and a forged pointer faults. BTI forces indirect branches to land on BTI landing pads in guarded pages. MTE tags every 16-byte granule and every pointer with 4 bits and checks they match. PAC and BTI stop control-flow hijacking; MTE catches the memory corruption itself. Apple's arm64e signs return addresses with the B key and also signs function and vtable pointers.

7. REFERENCE DETAIL

PAC (ARMv8.3 FEAT_PAuth)

  • Stores a cryptographic MAC of a pointer in its unused upper bits (about 7–16 bits depending on VA size and whether TBI is on). Inputs: the pointer, a 64-bit modifier (e.g. SP) and a 128-bit key held in system registers the user process cannot read: APIAKey, APIBKey (instructions), APDAKey, APDBKey (data), APGAKey (generic).
  • PACIASP signs LR with SP as modifier at function entry; AUTIASP verifies before return. On mismatch the pointer is made invalid (non-canonical) so the RET faults; with FEAT_FPAC (v8.6) AUT itself raises an exception (EC 0x1C).
  • Defeats ROP: an overwritten return address on the stack has no valid PAC. Apple's arm64e ABI (A12 and later, all M-series) signs return addresses with the B key (PACIBSP/RETAB) and also signs C++ vtable pointers and function pointers.
  • PAC instructions are in the HINT space, so binaries built with -mbranch-protection=pac-ret still run (unprotected) on older cores. Cortex-M85/M52 provide PACBTI for M-profile.

BTI (ARMv8.5 FEAT_BTI)

Defeats JOP: on pages marked guarded (GP bit in the PTE, enabled by SCTLR_EL1.BT0/BT1), an indirect branch (BR/BLR) must land on a BTI c / BTI j / BTI jc landing pad, else a Branch Target exception (EC 0x0D). PSTATE.BTYPE records what kind of branch just happened.

MTE (ARMv8.5 FEAT_MTE2)

  • Every 16-byte granule of memory has a 4-bit allocation tag stored in separate tag RAM (1/32 = ~3% of DRAM); every pointer carries a 4-bit logical tag in bits [59:56] (requires TBI). Loads/stores check that they match.
  • Instructions: IRG (insert random tag), STG/ST2G/STZG (set allocation tags), LDG, ADDG/SUBG. malloc tags each allocation; free retags, so use-after-free and linear overflow into a neighbour are caught (probabilistically 15/16 for random tags; adjacent allocations guaranteed different).
  • Modes (SCTLR_EL1.TCF0): sync (precise data abort, DFSC 0x11 tag-check fault), async (sets TFSR_EL1, reported at next kernel entry, low overhead), asymmetric (v8.7: sync reads, async writes).
  • Shipping: Android on Pixel 8+ (opt-in); Apple announced Memory Integrity Enforcement in 2025 built on Enhanced MTE (EMTE) in its A19-generation chips — always-on synchronous tag checking for the kernel and key user processes.
One-liner for interviews: PAC protects pointers you store, BTI restricts where indirect branches may go, MTE catches memory-safety bugs at the access. They are complementary: PAC + BTI address control-flow hijacking; MTE addresses the memory corruption that gives an attacker the write in the first place.

MPU on ARMv7-M (PMSAv7): power-of-two regions and subregions

▶

1. WHAT IS IT?

The MPU (Memory Protection Unit) is a small hardware guard inside the core. You give it a few address regions, each with permissions ("privileged read-write, unprivileged no access", "never execute") and a memory type. On every load, store and instruction fetch the MPU checks the address against all regions in parallel; a forbidden access becomes a MemManage fault instead of silently corrupting memory. It does not translate addresses. On ARMv7-M (Cortex-M3/M4/M7) the rules for region shapes are strict: power-of-two size, base aligned to the size — the "PMSAv7" model.

2. HOW YOU PROGRAM ONE REGION, STEP BY STEP

  1. Pick the size: 2N bytes, N from 5 (32 B) to 32 (4 GB). The SIZE field = N − 1.
  2. Check the base: base mod size must be 0. A 4 KB region can start at 0x2000_3000 but not at 0x2000_3800.
  3. Write MPU_RNR = region number (0–7 on Cortex-M4).
  4. Write MPU_RBAR = base address (bits [31:5]).
  5. Write MPU_RASR = XN, AP (access permissions), TEX/S/C/B (memory type), SRD (subregion disable), SIZE, ENABLE.
  6. After all regions: MPU_CTRL = ENABLE (+ PRIVDEFENA so privileged code still sees the default map for everything not covered), then DSB + ISB.

3. WORKED EXAMPLES WITH REAL NUMBERS

(a) A 2 KB no-access stack guard at 0x2000_1800. 2 KB = 211 → SIZE = 10. 0x1800 = 6144 = 3 × 2048 → aligned ✔.

RASR = XN(1<<28) | AP=000 | TEX=000 S=0 C=1 B=1 | SRD=0 | SIZE=10 (10<<1) | EN
     = 0x1000_0000 + 0x0003_0000 + 0x0000_0014 + 1  = 0x1003_0015
RBAR = 0x2000_1800

(b) The same guard at 0x2000_1400 (a real bug). 0x1400 = 5120 = 2.5 × 2048 → not aligned. Cortex-M3/M4 ignore the low base bits, so the region really covers 0x2000_1000–0x2000_17FF: it protects the wrong 1 KB at the bottom and leaves the top 1 KB of the intended guard open.

(c) 48 KB of SRAM (not a power of two) at 0x2000_0000. Use a 64 KB region (SIZE = 15) split into 8 subregions of 8 KB; disable the top two (SR6, SR7) → SRD = 0b1100_0000 = 0xC0.

RASR = AP=011 (full access, 0x0300_0000) | C B (0x0003_0000) | SRD 0xC0 (<<8 = 0xC000) | SIZE 15 (0x1E) | EN
     = 0x0303_C01F       covers 0x2000_0000 – 0x2000_BFFF = 48 KB exactly

5. WHAT GOES WRONG IF…

MISTAKEMisaligned base (example b). Symptom: MemManage fault in innocent code that touches the neighbouring buffer (CFSR = 0x82: DACCVIOL + MMARVALID, MMFAR inside the wrong range), while real overflows go undetected.
MISTAKEUsing SRD on a 128-byte region. Symptom: UNPREDICTABLE — subregions exist only for regions ≥ 256 B; SRD must be 0 for 32/64/128 B.
MISTAKEExpecting region 0 to override region 5. Why wrong: when regions overlap on ARMv7-M, the highest-numbered region wins. Put the broad "background" region at 0 and the holes at higher numbers.

6. SAY IT LIKE THIS

On ARMv7-M each MPU region is a power of two from 32 bytes to 4 GB, encoded as SIZE = log2(size) − 1, and the base must be aligned to the size. Regions of 256 bytes or more have eight subregions that SRD bits can disable, which is how you build shapes like 48 KB. Overlaps resolve to the highest region number, PRIVDEFENA gives privileged code a background map, and a violation raises MemManage with the address in MMFAR.

7. REFERENCE DETAIL

Cortex-M3/M4: 8 regions (M7: 8 or 16). Registers in the SCS: MPU_TYPE 0xE000_ED90 (DREGION = number of regions), MPU_CTRL 0xE000_ED94, MPU_RNR 0xE000_ED98, MPU_RBAR 0xE000_ED9C, MPU_RASR 0xE000_EDA0 (+ alias pairs A1–A3 for fast multi-region update).

  • Size = 2(SIZE+1) bytes, SIZE field 4…31 → 32 B … 4 GB. Must be a power of two.
  • Base must be aligned to the size. A 64 KB region can start at 0x2001_0000 but not at 0x2000_8000. Software must guarantee this; on M3/M4 the low base bits are effectively ignored, so a misaligned base silently protects the wrong range.
  • Subregions: regions ≥ 256 B are split into 8 equal subregions; each SRD bit (RASR[15:8]) set to 1 disables that eighth. Regions of 32/64/128 B must have SRD = 0. Used to carve non-power-of-two shapes: a 48 KB area = 64 KB region with the top two 8 KB subregions disabled.
  • Overlap: the highest-numbered region wins. Common pattern: region 0 = background "everything", higher regions punch holes.
  • MPU_CTRL: ENABLE[0], HFNMIENA[1] (keep MPU on in HardFault/NMI — usually 0), PRIVDEFENA[2] (privileged code gets the default memory map as a background region).
  • RASR fields: XN[28], AP[26:24], TEX[21:19], S[18], C[17], B[16], SRD[15:8], SIZE[5:1], ENABLE[0]. RBAR: ADDR[31:5], VALID[4] (when 1, REGION[3:0] selects the region instead of RNR).
  • Violation → MemManage fault: CFSR.MMFSR IACCVIOL[0], DACCVIOL[1], MUNSTKERR[3], MSTKERR[4], MLSPERR[5], MMARVALID[7]; faulting address in MMFAR 0xE000_ED34.

MPU on ARMv8-M (PMSAv8): base/limit and MAIR

▶

1. WHAT IS IT?

ARMv8-M (Cortex-M23/M33/M55/M85) replaced the power-of-two MPU with a simpler model, PMSAv8: every region is just a base and an inclusive limit, both on 32-byte boundaries. Any size that is a multiple of 32 bytes works at any 32-byte-aligned address. Memory types moved into separate MAIR registers (same idea as AArch64's MAIR_EL1).

2. HOW YOU PROGRAM ONE REGION, STEP BY STEP

  1. Write the memory types once: MPU_MAIR0 holds Attr0–Attr3 (one byte each), MPU_MAIR1 Attr4–Attr7.
  2. MPU_RNR = region number.
  3. MPU_RBAR = BASE[31:5] | SH (shareability) [4:3] | AP [2:1] | XN [0].
  4. MPU_RLAR = LIMIT[31:5] | AttrIndx [3:1] (which MAIR byte) | EN [0]. The hardware treats the low 5 bits of the limit as 0x1F, so the region includes the whole last 32-byte block.
  5. Enable with MPU_CTRL, then DSB + ISB.
  6. Design the map with no overlaps: an address hitting two enabled regions raises MemManage.

3. WORKED EXAMPLE — A 3 KB TASK STACK

Stack at 0x2000_4C00, 3 KB = 0xC00 bytes, RW for unprivileged code, never executable:

limit = 0x2000_4C00 + 0xC00 − 1 = 0x2000_57FF
RBAR  = 0x2000_4C00 | SH=00 | AP=01 (RW any) <<1 | XN=1     = 0x2000_4C03
RLAR  = (0x2000_57FF & ~0x1F) | AttrIndx=1 <<1 | EN=1   = 0x2000_57E3

On ARMv7-M a 4 KB region would need a 4 KB-aligned base, which 0x2000_4C00 is not (0x4C00 = 19 KB). You would have to use an 8 KB region at 0x2000_4000 (1 KB subregions) with SRD = 0b1100_0111 = 0xC7, so only SR3–SR5 (0x2000_4C00–0x2000_57FF) stay enabled. It works only because the stack happens to sit on 1 KB boundaries — that inflexibility is why Arm changed the model.

Stack overflow detection no longer needs an MPU guard at all on ARMv8-M: set PSPLIM = 0x2000_4C00; any push below it raises UsageFault STKOF.

4. CODE, LINE BY LINE

MPU->MAIR0 = (0x44u << 8) | 0x00u;            /* Attr1 = Normal NC, Attr0 = Device-nGnRnE */
MPU->RNR   = 0;
MPU->RBAR  = 0x20000000u | (0u<<3) | (1u<<1) | 1u;   /* non-shareable, RW any, XN   */
MPU->RLAR  = (0x20005FFFu & ~0x1Fu) | (1u<<1) | 1u; /* 24 KB, AttrIndx=1, enabled */
MPU->CTRL  = MPU_CTRL_PRIVDEFENA_Msk | MPU_CTRL_ENABLE_Msk; __DSB(); __ISB();
CodeMeaning
MAIR0 = 0x4400Byte 0 = 0x00 (Device-nGnRnE), byte 1 = 0x44 (Normal, inner/outer non-cacheable).
RBAR … (1<<1) | 1AP = 01 → read-write at any privilege; XN = 1 → instruction fetches fault. Result 0x2000_0003.
RLAR 0x2000_5FE0 | 2 | 1Limit block 0x2000_5FE0 (covers up to 0x2000_5FFF), AttrIndx = 1 → MAIR byte 1, enabled. Size = 0x6000 = 24 KB.
CTRL, DSB, ISBSame as v7-M: enable, wait, resynchronise.

5. WHAT GOES WRONG IF…

MISTAKEPorting a v7-M map that relies on "background region 0 + higher-numbered holes". Symptom: MemManage on the first access inside the hole — in PMSAv8 overlapping enabled regions are a fault, not a priority rule.
MISTAKEWriting the limit as "base + size" instead of "base + size − 1". Symptom: the region is 32 bytes too large and covers the start of the neighbouring object (often harmless, occasionally a fault in the neighbour, or a protection hole).

6. SAY IT LIKE THIS

The ARMv8-M MPU uses base and limit registers with 32-byte granularity, so any multiple of 32 bytes at any 32-byte-aligned address works and subregions are gone. RBAR holds base, shareability, access permissions and XN; RLAR holds limit, an attribute index into MAIR0/1 and enable. Overlapping enabled regions fault instead of "highest wins", and stack overflow is caught with MSPLIM/PSPLIM instead of guard regions.

7. REFERENCE DETAIL

  • MPU_RBAR: BASE[31:5] · SH[4:3] (shareability) · AP[2:1] · XN[0]. MPU_RLAR: LIMIT[31:5] (inclusive, low 5 bits treated as 0x1F) · PXN[4] (v8.1-M) · AttrIndx[3:1] · EN[0].
  • Granularity is 32 bytes; any size that is a multiple of 32 at any 32-byte aligned base. No subregions needed (and none exist).
  • AP[2:1]: 00 = RW privileged only, 01 = RW any, 10 = RO privileged only, 11 = RO any.
  • Memory type comes from MPU_MAIR0/1 (8 attribute bytes, same encoding idea as AArch64 MAIR): AttrIndx selects one.
  • Overlapping enabled regions → MemManage fault (unlike v7-M's "highest number wins"). Design your map without overlaps.
  • With TrustZone: two MPUs (MPU_S, MPU_NS), each with its own region count. Stack overflow detection no longer needs an MPU guard region: MSPLIM/PSPLIM trigger a UsageFault STKOF.
Why did Arm change it? Power-of-two alignment wastes memory and makes RTOS task stacks hard to place (a 3 KB stack needs a 4 KB aligned region). Base/limit costs two comparators per region instead of a mask, which was affordable by the v8-M era.

Memory types and attributes: Normal, Device, Strongly-ordered

▶

1. WHAT IS IT?

Every address has a memory type that tells the core what tricks it may play when accessing it. RAM is Normal memory: the core may cache it, merge writes, reorder accesses, read ahead speculatively — all to go faster, because RAM does not care. Peripheral registers are Device memory: every access must happen exactly as written, in order, at the exact size, never speculatively, because a read can have a side effect (e.g. reading a UART data register removes a byte from its FIFO).

2. WHAT EACH TYPE ALLOWS, STEP BY STEP

  1. Normal: caching (non-cacheable, write-through, write-back), merging several small writes into one, reordering, speculation, unaligned access. Also a shareability attribute: which other observers (cores, DMA) must be kept coherent.
  2. Device: no caching, no speculation. On AArch64 it is graded by three letters, each "n" meaning "not allowed": Gathering (merging), Reordering, Early write acknowledgement (the interconnect says "done" before the peripheral has the write).
  3. Device-nGnRnE: strictest — the old ARMv7 "Strongly-ordered". Device-nGnRE: the usual choice for MMIO (posted writes allowed). Device-GRE: rarely used.
  4. Where it comes from: on Cortex-M the default memory map fixes it per address range (or the MPU overrides it); on Cortex-A each page-table entry points at a MAIR byte.

3. WORKED EXAMPLE — THE CORTEX-M DEFAULT MAP

0x0000_0000–0x1FFF_FFFF  Code           Normal, write-through      flash (STM32: 0x0800_0000)
0x2000_0000–0x3FFF_FFFF  SRAM           Normal, WB write-allocate   variables, stacks
0x4000_0000–0x5FFF_FFFF  Peripheral     Device, eXecute-Never        GPIOA ODR = 0x4002_0014
0x6000_0000–0x9FFF_FFFF  External RAM   Normal                      FMC NOR/PSRAM banks
0xA000_0000–0xDFFF_FFFF  External dev.  Device, XN                  STM32F4 FMC SDRAM at 0xC000_0000 lands here!
0xE000_0000–0xE00F_FFFF  PPB            Strongly-ordered, XN        NVIC, SysTick, SCB, MPU, debug

So the same STR instruction behaves differently depending only on the address: str r1, [r0] with R0 = 0x2000_0100 may sit in a write buffer; with R0 = 0xE000_E100 (NVIC_ISER0) it is strongly ordered.

4. WHAT GOES WRONG IF…

✖ WRONG (Cortex-M7 / A-core)

   as Normal, cacheable */
UART->DR = 'A';
UART->DR = 'B';     /* may be merged with 'A'   */
while (!(UART->SR & TXE)) {}  /* stale cached SR */
✔ RIGHT

   (v7-M: TEX=000 C=0 B=1, A64: MAIR 0x04) */

UART->DR = 'B';

SYMPTOMCharacters lost or doubled, status flags that never change, a "read-to-clear" interrupt flag cleared by a speculative read the code never asked for. All caused by Normal attributes on peripheral space.
MISTAKEPlacing a DMA buffer in cacheable SRAM on a Cortex-M7 without cache maintenance. Symptom: the CPU reads old data after the DMA wrote new data (stale D-cache), or DMA transmits old data the CPU wrote but has not cleaned. Fix: non-cacheable MPU region (TEX=001 C=0 B=0) or SCB_CleanDCache_by_Addr / SCB_InvalidateDCache_by_Addr.

5. SAY IT LIKE THIS

Normal memory lets the core cache, merge, reorder and speculate, which is right for RAM and flash. Device memory forbids caching and speculation and keeps accesses in order and at the requested size, which peripherals with side effects need. AArch64 grades Device memory by Gathering, Reordering and Early write acknowledgement; nGnRnE is the strictest and nGnRE the usual MMIO type. Getting this wrong gives merged FIFO writes, stale status reads and DMA coherency bugs.

6. REFERENCE DETAIL

  • Normal: RAM/flash. The core may merge, reorder, speculate and cache accesses; unaligned accesses allowed (v7-M+). Cacheability: non-cacheable, write-through, write-back (± read/write allocate). Shareability: non-, inner-, outer-shareable (who must be kept coherent).
  • Device: peripherals. No speculation, no caching; accesses happen in program order relative to other Device accesses to the same peripheral, exactly the requested size. AArch64 splits it with three properties: Gathering (merge), Reordering, Early write acknowledgement → Device-nGnRnE (strictest, = ARMv7 Strongly-ordered), Device-nGnRE (typical MMIO), Device-nGRE, Device-GRE.
  • Strongly-ordered (ARMv7/ARMv7-M): like Device but the write completes at the peripheral before the next access (no early ack).
  • Cortex-M default memory map attributes: Code 0x0000_0000 Normal WT; SRAM 0x2000_0000 Normal WBWA; Peripheral 0x4000_0000 Device XN; External RAM 0x6000_0000/0x8000_0000 Normal; External device 0xA000_0000 Device; PPB 0xE000_0000 Strongly-ordered XN; 0xE010_0000+ vendor system (Device, XN).

Bit-banding (Cortex-M3/M4) and unaligned access

▶

1. WHAT IS IT?

Bit-banding is a Cortex-M3/M4 feature that gives every single bit in two 1 MB areas (the start of SRAM and the start of the peripheral space) its own 32-bit word address in a separate "alias" area. Writing 1 or 0 to that alias word sets or clears exactly that one bit, atomically — no read-modify-write sequence in software that an interrupt could split.

2. HOW IT WORKS, STEP BY STEP

  1. Take the target byte address and subtract the region base (0x2000_0000 for SRAM, 0x4000_0000 for peripherals) → byte_offset.
  2. Each byte has 8 bits, each bit gets a 4-byte alias word → each byte occupies 8 × 4 = 32 bytes of alias space. So multiply byte_offset by 32.
  3. Add bit_number × 4.
  4. Add the alias base (0x2200_0000 for SRAM, 0x4200_0000 for peripherals).
  5. A write to that alias word makes the bus matrix do a locked read-modify-write of the real word. A read returns 0 or 1.

3. WORKED EXAMPLES

(a) SRAM flag at 0x2000_0100, bit 3
    byte_offset = 0x2000_0100 − 0x2000_0000 = 0x100
    × 32        = 0x2000
    + 3 × 4     = 0xC
    alias       = 0x2200_0000 + 0x2000 + 0xC = 0x2200_200C

(b) GPIOA->ODR on STM32F4 = 0x4002_0014, bit 5 (PA5 LED)
    byte_offset = 0x0002_0014
    × 32        = 0x0040_0280
    + 5 × 4     = 0x14
    alias       = 0x4200_0000 + 0x0040_0280 + 0x14 = 0x4240_0294

(c) Wrong base: SRAM formula on the peripheral address
    (0x4002_0014 − 0x2000_0000) × 32 = 0x2002_0014 × 32 = 0x4_0040_0280 → truncated to 32 bits 0x0040_0280
    alias = 0x2200_0000 + 0x0040_0280 + 0x14 = 0x2240_0294 → bit 5 of SRAM byte 0x2002_0014 (!)

Bit-banding maps each bit of the first megabyte of SRAM and of peripherals to a word in a 32 MB alias region, so a single word write is an atomic read-modify-write of one bit. Barriers: DMB, DSB, ISB (and when each is mandatory)

▶

1. WHAT IS IT?

A modern core does not necessarily perform memory accesses in the order your code lists them, and a write may still be "in flight" in a buffer when the next instruction executes. Barriers are instructions that put fences in that stream. Arm has three: DMB (Data Memory Barrier — ordering), DSB (Data Synchronization Barrier — completion), and ISB (Instruction Synchronization Barrier — pipeline refresh).

2. WHAT EACH ONE GUARANTEES, STEP BY STEP

  1. DMB: every memory access before it is observed by others (other cores, DMA) before any memory access after it. It does not wait; it just forbids reordering across it.
  2. DSB: the core stops executing any later instruction until all memory accesses, cache maintenance and TLB maintenance before it have completed.
  3. ISB: throws away instructions already fetched and decoded, so everything after it is fetched again under the new context (new privilege, new MPU/MMU settings, new vector base, freshly written code).
  4. Rule of thumb: DMB between data and its flag; DSB before you rely on a side effect (sleep, peripheral state, maintenance done); ISB after changing how instructions themselves must execute.

3. WORKED EXAMPLE — DMA DESCRIPTOR HANDOFF

desc->buf = 0x2000_8000;   ①
desc->len = 256;           ②
__DMB();                   ③
desc->own = OWN_DMA;       ④   DMA engine polls this bit

Without ③, a core with a write buffer (Cortex-M7, any Cortex-A) may make ④ visible before ① and ②. The DMA engine sees "owned by DMA", reads a stale length of 0 or an old buffer pointer, and transmits garbage. With ③, ① and ② are guaranteed visible first. On a Cortex-M7 with D-cache you additionally need SCB_CleanDCache_by_Addr(desc, 32) so the data reaches SRAM at all.

M7 interrupt timing: an ISR at 480 MHz clears TIM6->SR as its last store and returns. The store takes ~40 ns to cross the AXI → AHB → APB bridges, but exception return takes a few ns, so the NVIC still sees the request and re-enters. __DSB() after the store waits for completion — problem gone.

4. CODE, LINE BY LINE

MPU->CTRL = MPU_CTRL_ENABLE_Msk | MPU_CTRL_PRIVDEFENA_Msk; __DSB(); __ISB();
__set_CONTROL(0x3);                       __ISB();
TIM2->SR = ~TIM_SR_UIF;                    __DSB();
__DSB(); __WFI();

✔ RIGHT (multi-core / DMA)

WHYvolatile only stops the compiler from removing or reordering volatile accesses. It emits no barrier instruction, so the CPU may still reorder the stores. On a Cortex-M3/M4 it happens to work (no reordering in that pipeline); the same code fails on an M7 or a multicore A-class SoC.

6. SAY IT LIKE THIS

DMB orders memory accesses, so data is observed before the flag that publishes it. DSB waits until earlier accesses and maintenance have completed — before WFI, after cache or TLB maintenance, after clearing an interrupt flag on an M7. ISB flushes the pipeline so new context takes effect — after writing CONTROL, enabling the MPU or MMU, or changing VBAR. volatile is not a barrier; it only constrains the compiler.

INTERMEDIATE

Debug architecture: CoreSight, DAP, SWD/JTAG, ITM, DWT, ETM, FPB

▶

1. WHAT IS IT?

When you click "Debug" in your IDE, a probe (ST-LINK, J-Link, CMSIS-DAP) talks to dedicated debug hardware inside the Arm core. Arm standardised that hardware as CoreSight. It lets the probe halt and single-step the core, read and write memory and registers while the program runs, set breakpoints in flash, watch data addresses, count cycles, and stream printf output or full instruction traces — without any code in your firmware.

2. THE PATH FROM PROBE TO CORE, STEP BY STEP

  1. Wires: SWD (Serial Wire Debug) uses 2 pins — SWDIO (data) and SWCLK (clock), on STM32 PA13/PA14 — plus optional SWO (trace output, PB3). JTAG uses 4–5 pins (TCK, TMS, TDI, TDO, nTRST) and can daisy-chain chips.
  2. DP (Debug Port) receives the serial protocol. It talks to one or more APs (Access Ports).
  3. The MEM-AP (AHB-AP on Cortex-M) is a bus master: the probe can read any address — RAM, flash, peripherals, debug registers — like the CPU does.
  4. Halting debug: writing DHCSR (Debug Halting Control and Status Register, 0xE000_EDF0) with the key 0xA05F in the top half stops or steps the core.
  5. Breakpoints: the FPB (Flash Patch and Breakpoint unit) compares the fetch address with up to 6 values (Cortex-M4) and halts on a match. Watchpoints and the cycle counter live in the DWT (Data Watchpoint and Trace unit). ITM (Instrumentation Trace Macrocell) sends printf-style bytes out over SWO. ETM (Embedded Trace Macrocell) records every branch for full instruction trace.

3. WORKED EXAMPLE — TIMING A FILTER WITH CYCCNT

t0 = 0x0012_3400   (DWT->CYCCNT before)
t1 = 0x0012_8F10   (after)
dt = t1 − t0 = 0x5B10 = 23 312 cycles
at 168 MHz: 23 312 / 168 = 138.8 µs

CYCCNT is 32 bits → wraps every 2^32 / 168 MHz = 25.6 s.
Unsigned subtraction still works across one wrap:
  t0 = 0xFFFF_FF00, t1 = 0x0000_0100  →  t1 − t0 = 0x0000_0200 = 512 cycles ✔

Why 6 hardware breakpoints matter: a software breakpoint replaces an instruction with BKPT (0xBExx), which requires writing the code memory. Flash cannot be rewritten one halfword at a time without erasing a sector, so in flash the debugger must use the FPB comparators. That is why the IDE refuses a 7th breakpoint on an STM32F4.

4. CODE, LINE BY LINE

5. WHAT GOES WRONG IF…

MISTAKEFirmware reconfigures PA13/PA14 as GPIO (e.g. a "use all pins" init). Symptom: after the first run the probe cannot connect ("no target"). Recovery: connect under reset (hold NRST, the pins are SWD again until your code runs) or boot from the system bootloader via BOOT0.
MISTAKECode waits in a busy-loop on ITM_SendChar with no debugger attached. Symptom: usually fine (CMSIS checks ITM enable bits) — but custom implementations that spin on the port's ready bit hang forever in the field.

6. SAY IT LIKE THIS

The probe connects over SWD or JTAG to a Debug Port, and a MEM-AP gives it bus access to memory and debug registers while the core runs. DHCSR halts and steps; DEMCR enables vector catch and trace. The FPB gives 6 hardware breakpoints on a Cortex-M4, needed because flash can't be patched with BKPT; the DWT gives 4 watchpoints and the CYCCNT cycle counter; ITM streams printf over SWO and ETM gives full instruction trace.

7. REFERENCE DETAIL

  • CoreSight is Arm's debug and trace framework: discoverable components (ROM table at 0xE00F_F000 on Cortex-M) connected over APB/ATB.
  • DAP = Debug Access Port: a DP (SW-DP, JTAG-DP, or SWJ-DP supporting both) plus one or more APs. A MEM-AP (AHB-AP on Cortex-M, APB-AP for A-profile debug registers, AXI-AP for system memory) lets the probe read/write memory while the core runs.
  • SWD: 2 wires (SWDIO, SWCLK) + optional SWO; JTAG: TCK, TMS, TDI, TDO, (nTRST) — supports daisy-chaining several devices and boundary scan. On STM32 the SWJ-DP shares pins: PA13 SWDIO/TMS, PA14 SWCLK/TCK, PB3 SWO/TDO.
  • Halting debug via DHCSR 0xE000_EDF0 (write key 0xA05F in [31:16]; C_HALT, C_STEP), core register access via DCRSR/DCRDR, vector catch via DEMCR 0xE000_EDFC (VC_HARDERR, VC_CORERESET; TRCENA bit 24 powers DWT/ITM).
  • FPB (Flash Patch and Breakpoint, 0xE000_2000): Cortex-M3/M4 have 6 instruction comparators + 2 literal comparators → 6 hardware breakpoints; M0+ up to 4; M7 up to 8. Needed because a software breakpoint (BKPT, 0xBExx) requires rewriting the instruction, which is impossible in flash.
  • DWT (0xE000_1000): 4 comparators on M4 for watchpoints (data address/value), PC sampling, and CYCCNT (0xE000_1004) — a 32-bit cycle counter (wraps after 25.6 s at 168 MHz).
  • ITM (0xE000_0000): 32 stimulus ports; ITM_SendChar() gives printf over SWO with almost no CPU cost; also carries DWT event packets and timestamps.
  • ETM: instruction trace (every branch) via the TPIU 4-bit parallel trace port, or into an ETB/ETF on-chip buffer. M0+ has the cheaper MTB (Micro Trace Buffer) into SRAM. ARMv9-A uses ETE + TRBE (trace into memory).
ADVANCED

NEON, SVE/SVE2, Helium (MVE) — briefly

▶

1. WHAT IS IT?

SIMD (Single Instruction, Multiple Data) means one instruction operates on several values packed in one wide register — for example four 32-bit floats in a 128-bit register added in one go. Arm has three SIMD families: NEON (Advanced SIMD, fixed 128-bit, A-profile), SVE/SVE2 (Scalable Vector Extension, vector length chosen by the hardware, servers and Armv9 phones), and Helium (MVE, M-profile Vector Extension, for Cortex-M55/M85 microcontrollers).

2. HOW THEY DIFFER, STEP BY STEP

  1. NEON: 32 registers V0–V31 × 128 bits. An instruction like fadd v0.4s, v1.4s, v2.4s adds 4 floats. Loops must handle the leftover "tail" elements separately.
  2. SVE: registers Z0–Z31 whose length is 128 to 2048 bits, decided by the chip. Code never hard-codes the width; predicate registers P0–P15 switch individual lanes on or off, so the loop tail is just a partially-enabled last iteration (whilelt). One binary runs on 128-bit phones and 512-bit servers.
  3. Helium: 8 registers Q0–Q7 × 128 bits, sharing the existing FP register file (S0–S31). The datapath is only 32 or 64 bits wide, so a 128-bit instruction executes in 4 (or 2) "beats", overlapped with the next instruction. Low-overhead loops (WLSTP/LETP) and tail predication remove loop bookkeeping.

3. WORKED EXAMPLE — A 1024-SAMPLE DOT PRODUCT

  • Scalar float: 1024 multiply-accumulates → ~1024 iterations (plus loop overhead).
  • NEON (4 floats per instruction): 1024 / 4 = 256 iterations of fmla.
  • SVE on 512-bit hardware (16 floats per instruction): 1024 / 16 = 64 iterations — same binary on 128-bit hardware just runs 256.
  • Helium on Cortex-M55, int8 ML kernel: 16 int8 lanes per 128-bit vector, and Arm quotes up to ~15× ML speed-up over earlier Cortex-M cores.

4. CODE — NEON INTRINSICS

#include <arm_neon.h>
float dot(const float *a, const float *b, int n) {   /* n multiple of 4 */
    float32x4_t acc = vdupq_n_f32(0.0f);
    for (int i = 0; i < n; i += 4)
        acc = vfmaq_f32(acc, vld1q_f32(a + i), vld1q_f32(b + i));
    return vaddvq_f32(acc);

5. WHAT GOES WRONG IF…

MISTAKECalling this with n = 1023. Symptom: reads 1 element past the end of the arrays (possible fault on a page boundary) and adds a garbage product. NEON needs a scalar tail loop; SVE/Helium handle it with predication.

6. SAY IT LIKE THIS

NEON is fixed 128-bit SIMD with 32 vector registers on AArch64. SVE and SVE2 are vector-length agnostic from 128 to 2048 bits with predicate registers, so one binary scales and loop tails disappear; SVE2 is mandatory in Armv9-A. Helium is the M-profile vector extension: eight 128-bit registers overlaid on the FP registers, executed in beats over a narrow datapath, which gives DSP and ML speed-ups at microcontroller power.

ADVANCED

big.LITTLE and DynamIQ

▶

1. WHAT IS IT?

Heterogeneous multi-processing: putting different core types on one chip — big out-of-order cores for performance and small in-order cores for efficiency — that all run the same instruction set, so the OS can move a thread between them. Arm's first version was big.LITTLE (2011, Cortex-A15 + A7 in separate clusters); the current version is DynamIQ (2017 onward, mixed cores in one cluster).

2. HOW IT WORKS, STEP BY STEP

  1. Same ISA everywhere: every core must support the same instructions (or the OS exposes only the common subset), because a thread can migrate between any two instructions.
  2. big.LITTLE: a "big" cluster and a "LITTLE" cluster, each with its own L2 cache, connected by a coherent interconnect (CCI-400). Migrating a thread means its working set crosses the interconnect.
  3. DynamIQ: all core types sit in one cluster behind the DSU (DynamIQ Shared Unit) with a shared L3 and per-core voltage/frequency. Migration is cheap (data is already in the shared L3), and mixes like 1 × X4 + 3 × A720 + 4 × A520 fit in one cluster.
  4. The OS decides: Linux's EAS (Energy Aware Scheduling) uses an energy model (power vs. performance per core type per frequency) to place each task on the core that meets its demand at the lowest energy.

3. WORKED EXAMPLE — WHY LITTLE CORES SAVE ENERGY

Illustrative numbers: a background sync task needs 50 M instructions.

big core    : IPC 3.0 at 2.8 GHz → 50e6/(3.0×2.8e9) = 6.0 ms at 1.5 W  → 9.0 mJ
LITTLE core : IPC 1.0 at 1.8 GHz → 50e6/(1.0×1.8e9) = 27.8 ms at 0.15 W → 4.2 mJ

The LITTLE core is 4.6× slower but uses about half the energy, which is the right trade for anything that is not user-visible. A UI frame that must finish in 8 ms goes to the big core.

4. WHAT GOES WRONG IF…

MISTAKEAn app probes CPU features once on a big core and uses an instruction the LITTLE cores lack. Symptom: rare SIGILL crashes only when the scheduler migrates the thread. This is why vendors keep feature sets identical across a DynamIQ cluster.

5. SAY IT LIKE THIS

big.LITTLE puts big and little cores with the same ISA in separate clusters joined by a coherent interconnect; DynamIQ puts them in one cluster behind the DSU with a shared L3 and per-core DVFS, so migration is cheaper and configurations like 1+3+4 are possible. Linux places tasks with Energy Aware Scheduling. Apple's P and E cores follow the same idea with its own design.

6. REFERENCE DETAIL

  • big.LITTLE (2011, Cortex-A15 + A7): two clusters of different cores with the same ISA, each cluster with its own L2, kept coherent through an interconnect (CCI-400). Software models evolved: cluster migration → CPU migration (in-kernel switcher pairs one big with one little) → Global Task Scheduling / HMP (all cores visible) → Linux Energy Aware Scheduling using an energy model.
  • DynamIQ (2017, ARMv8.2: A75/A55 onward): big and little cores in the same cluster behind a DynamIQ Shared Unit (DSU) with a shared L3, snoop filter and per-core power/clock domains. Faster task migration (shared L3 instead of crossing the interconnect), configurations like 1+3+4 (X4 + A720 + A520) in one cluster.
  • Requirement for both: identical ISA features across core types (or the OS masks to the common subset), because a thread may migrate between instructions.
  • Apple's P-cores and E-cores are custom heterogeneous clusters with their own fabric; the scheduling idea (QoS classes → core type) is the same, but it is not Arm's DynamIQ IP.

Cortex-R52 in automotive — why not an M7 or an A-core?

▶

1. WHAT IS IT?

The Cortex-R52 (ARMv8-R, 32-bit) is the workhorse of modern automotive safety controllers (NXP S32Z/S32E, ST Stellar). It answers a specific problem: carmakers want to consolidate several ECUs (Electronic Control Units) onto one chip, mixing software of different safety levels, without losing determinism or certification.

2. WHAT IT PROVIDES, STEP BY STEP

  1. Lockstep: two cores execute the same instructions one or two cycles apart; a comparator checks every output. A transient fault (e.g. a cosmic-ray bit flip) is detected within cycles — required for ASIL-D. Some parts can switch to "split" mode for twice the performance at lower ASIL.
  2. EL2 hypervisor with a two-stage MPU: the guest OS at EL1 programs its own MPU (stage 1); the hypervisor at EL2 programs a second MPU (stage 2) that confines each guest. No page tables, so no TLB-walk jitter. 64-byte region granularity (PMSAv8-32).
  3. TCMs with ECC: ATCM/BTCM/CTCM give single-cycle, cache-free access for the control loop code and data.
  4. Low, bounded interrupt latency and ECC on caches and buses.
  5. No EL3/TrustZone: security comes from a separate HSM (Hardware Security Module) core on the SoC.

3. WORKED EXAMPLE — CONSOLIDATING TWO ECUs

One R52 core runs a hypervisor with two partitions: an ASIL-D brake controller (AUTOSAR Classic, 1 ms task) and a QM (no safety rating) diagnostics stack. Stage-2 MPU regions give the brake partition exclusive access to its TCM, its CAN controller and its flash; the diagnostics partition gets the Ethernet controller. If a diagnostics bug writes into brake RAM, the stage-2 MPU blocks it and traps to EL2 — this is the "freedom from interference" ISO 26262 asks you to show. Worst-case timing analysis stays possible because there are no page tables.

4. WHAT GOES WRONG IF…

MISTAKEUsing a Cortex-A with Linux for the brake loop "because it is faster". Symptom: safety assessors cannot bound the WCET (worst-case execution time) with caches, TLB walks and a non-real-time OS; certification fails, even if bench tests pass.
MISTAKEUsing a Cortex-M7 and separating partitions only with an RTOS. Symptom: the RTOS itself is shared, privileged software; one partition's bug in privileged code can break the other. The M7 core also has no hardware virtualisation and no built-in lockstep.

5. SAY IT LIKE THIS

Cortex-R52 combines determinism with partitioning: an MPU instead of an MMU so there are no page-walk delays, ECC-protected TCMs, low interrupt latency, dual-core lockstep for ASIL-D, and an EL2 hypervisor with a two-stage MPU so software of different ASIL levels shares a core with freedom from interference. An M7 lacks virtualisation and lockstep in the core; an A-core's MMU and caches make worst-case timing hard to prove.

6. REFERENCE DETAIL

  • ARMv8-R AArch32, up to 4 cores, ~1.x GHz class in automotive MCUs (NXP S32Z/S32E, ST Stellar). Dual-core lockstep (two cores run the same instructions, a comparator flags any divergence) for ISO 26262 ASIL-D, or split mode for performance.
  • EL2 hypervisor with a two-stage MPU (no MMU, PMSAv8-32, 64-byte granularity): stage 1 controlled by the guest at EL1, stage 2 by the hypervisor at EL2. Lets ASIL-D and QM software, or several AUTOSAR Classic stacks, share one core with "freedom from interference" — without the unpredictability of page tables.
  • TCMs (ATCM/BTCM/CTCM) with ECC for deterministic single-cycle access, low-latency integrated GIC-based interrupt controller, ECC on caches and buses.
  • No EL3/TrustZone: security is typically provided by a separate HSM core on the SoC.
Interview framing for Bosch/NXP/Infineon: "M7 gives cheap determinism but no hardware virtualisation and limited safety features; A-cores give performance but page-table walks and complex caches make WCET analysis hard. R52 gives virtualisation with MPU determinism and lockstep — the combination mixed-criticality ECUs need."

NEVER DO THIS
    
        
  • Hand-type a function address from the map file into a Cortex-M function pointer (bit 0 = 0 → INVSTATE).
    • 
        
  • Initialise an RTOS task frame with xPSR = 0 (needs 0x0100_0000, the T bit).
    • 
        
  • Start a task/ISR stack on a 4-byte-but-not-8-byte aligned address.
    • 
        
  • Program an ARMv7-M MPU region whose base is not aligned to its size.
    • 
        
  • Use SRD bits on a region smaller than 256 B.
    • 
        
  • Overlap PMSAv8 regions expecting "higher number wins".
    • 
        
  • Call a TrustZone-M secure function by its real address instead of its NSC veneer.
    • 
        
  • Trust a pointer passed from Non-secure code without cmse_check_address_range.
    • 
        
  • Execute SMC or HVC at EL0 and expect anything but UNDEFINED.
    • 
        
  • Write CONTROL or enable the MPU without the ISB/DSB that follows.
    • 
        
  • Assume volatile orders memory for DMA or another core.
    • 
        
  • Use bit-band aliases on Cortex-M7/M33, or outside the first 1 MB of SRAM/peripherals.
    • 
        
  • Use X18 in arm64 code that must run on Apple or Windows.

60-SECOND REVISION
    
        
  • A = MMU + rich OS, R = MPU + deterministic + lockstep, M = MPU + NVIC + Thumb-only.
    • 
        
  • M0+ v6-M · M3 v7-M · M4/M7 v7E-M · M23 v8-M BL · M33 v8-M ML · M55/M85 v8.1-M (Helium).
    • 
        
  • Branch target bit 0 = Thumb. Cortex-M + even target = INVSTATE.
    • 
        
  • AAPCS: R0–R3 args, R0(:R1) return, R4–R11 callee-saved, 64-bit args in even pairs, SP 8-aligned at calls.
    • 
        
  • AAPCS64: X0–X7, X8 indirect result, X19–X28 callee-saved, X29 FP, X30 LR, SP 16-aligned.
    • 
        
  • Cortex-M: Handler = privileged + MSP; Thread = nPRIV + SPSEL; only an exception (SVC) restores privilege.
    • 
        
  • EL0 apps, EL1 kernel, EL2 hypervisor, EL3 monitor. Exceptions go up (or stay), ERET goes down.
    • 
        
  • VBAR_ELx 2 KB aligned, 16 × 0x80: current-SP0 / current-SPx / lower-64 / lower-32 × sync/IRQ/FIQ/SError.
    • 
        
  • Entry saves only PSTATE→SPSR and PC→ELR; software saves X0–X30.
    • 
        
  • SVC→EL1, HVC→EL2, SMC→EL3; HVC/SMC at EL0 are UNDEFINED (EC 0x00).
    • 
        
  • TrustZone-M: NS→S only via SG in NSC; return BXNS; S→NS call BLXNS + FNC_RETURN; bad entry = SecureFault INVEP.
    • 
        
  • v7-M MPU: 2(SIZE+1), aligned base, 8 subregions, highest wins. v8-M: base/limit 32 B, overlap = fault.
    • 
        
  • Bit-band alias = base + offset×32 + bit×4 (0x2200_0000 / 0x4200_0000). M3/M4 only.
    • 
        
  • DMB orders, DSB completes, ISB refetches.
    • 
        
  • SWD 2 wires, FPB 6 BPs on M4, DWT 4 WPs + CYCCNT, ITM over SWO, ETM instruction trace.
    • 
        
  • PAC signs pointers (anti-ROP), BTI landing pads (anti-JOP), MTE 4-bit tags per 16 B (memory safety).
    • 
        
  • big.LITTLE = separate clusters + CCI; DynamIQ = mixed cores in one cluster with DSU + shared L3.
