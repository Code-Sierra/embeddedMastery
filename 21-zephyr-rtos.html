1. What Zephyr is, and why so many vendors use it

▶

1. WHAT IS IT?

Zephyr is a free, open-source real-time operating system (RTOS) for microcontrollers. An RTOS is a small piece of software that lets one CPU run several independent jobs ("threads") and switch between them in a predictable amount of time. Zephyr gives you that scheduler, plus a large set of things a product needs: drivers for hundreds of chips, a Bluetooth stack, a TCP/IP network stack, a file system, logging, a command shell, a bootloader and firmware-update tools.

Linux Foundation
The non-profit that hosts the project. No single chip company owns Zephyr. Member companies (Nordic, NXP, Intel, ST, Google, Meta, Infineon, TI and others) fund it and sit on its technical steering committee.
Apache-2.0
The software licence. You can use Zephyr in a closed-source commercial product, change it, and you do not have to publish your own code. The licence also grants you a patent licence from the contributors. Compare with GPL (Linux kernel), which forces you to publish changes to the kernel.
Vendor-neutral
The same kernel, APIs and build system work on Nordic, NXP, ST, Espressif, Infineon, TI, Microchip, Renesas, RISC-V and x86 parts. Your application code that calls gpio_pin_toggle_dt() does not change when you change chip vendor. Only the board description changes.
LTS
Long Term Support release. Zephyr ships a release about every 4 months; an LTS (for example 2.7, 3.7) gets bug and security fixes for about 2+ years, so products can stay on it.
nRF Connect SDK (NCS)
Nordic Semiconductor's SDK. It is Zephyr plus Nordic's extra repositories (SoftDevice Controller for Bluetooth, modem libraries, Partition Manager). If your course uses Nordic DevAcademy, you are learning Zephyr through NCS.

2. WHO USES IT AND HOW

  1. Nordic builds its whole SDK (NCS) on Zephyr for nRF52, nRF53, nRF54 and nRF91 (cellular) chips.
  2. NXP supports i.MX RT, LPC, Kinetis and MCX parts in Zephyr alongside its MCUXpresso SDK.
  3. ST keeps a hal_stm32 module so almost every STM32 Nucleo/Discovery board builds out of the box.
  4. Intel started the project (it came from Wind River's "Rocket" kernel, open-sourced in 2016) and uses it on x86 and in audio DSP firmware (Sound Open Firmware).
  5. Google runs Chromebook embedded controllers (the EC firmware) on Zephyr. Meta, Bose, Oticon and many others ship it in products.

3. WHAT MAKES ZEPHYR DIFFERENT FROM A "KERNEL ONLY" RTOS

FreeRTOS is mainly a scheduler plus queues and semaphores. You bring your own drivers (usually the vendor HAL) and your own build system. Zephyr is closer to "Linux for microcontrollers": it borrows three ideas from Linux.

  1. Kconfig: a menu of compile-time options (CONFIG_I2C=y) that switch features on and off so only what you use is compiled in.
  2. Devicetree: a text file that describes the hardware (which pin the LED is on, at which address the sensor sits). Drivers read it at compile time, so the C code does not hard-code pins.
  3. A device driver model: every driver exposes the same API for its class (all I2C drivers look the same to the application).

4. WORKED EXAMPLE: HOW SMALL CAN IT BE?

A minimal Zephyr "hello world" on a Cortex-M4 with logging off is about 8–12 KB of flash and 4–6 KB of RAM (the kernel, one main thread with a 1 KB stack, the idle thread, the interrupt stack of 2 KB, and the UART console). Add Bluetooth LE peripheral support and you reach roughly 120–180 KB flash and 25–40 KB RAM. On the nRF52840 (1024 KB flash, 256 KB RAM) that leaves plenty of room. On a 32 KB-flash part Zephyr is possible but tight; FreeRTOS fits more easily there.

People pick Zephyr for a tiny 16 KB part, enable logging, shell and the sensor subsystem, and the image no longer fits. Symptom: the link step fails with region `FLASH' overflowed by 9344 bytes. Fix: turn features off in prj.conf and use west build -t rom_report to see which code is biggest.
Zephyr is an Apache-2.0, vendor-neutral RTOS hosted by the Linux Foundation. Besides a preemptive kernel it provides a full driver model, Bluetooth and networking stacks, and a Linux-style configuration system: Kconfig for software options and devicetree for hardware description. Nordic's nRF Connect SDK is built on it, and NXP, ST, Intel and others support their chips upstream, so the same application can move between vendors by changing the board, not the code.

2. Architecture overview: the layers of a Zephyr image

▶

1. WHAT IS IT?

A Zephyr firmware image is one single program (one zephyr.elf file). Your application, the kernel, the drivers and the libraries are all compiled and linked together. There is no separate "OS" loaded at runtime like on Linux. The layers below are a way to understand which code does what.

┌──────────────────────────────────────────────────────────────┐
│ APPLICATION      your main.c, threads, prj.conf, app.overlay │
├──────────────────────────────────────────────────────────────┤
│ SUBSYSTEMS       logging · shell · settings · Bluetooth host │
│                  networking (IP, sockets) · sensors · USB    │
│                  file systems · mcumgr · power management    │
├──────────────────────────────────────────────────────────────┤
│ DEVICE DRIVER    generic APIs: gpio_*, i2c_*, spi_*, uart_*  │
│ MODEL            struct device + per-class API table         │
├───────────────────────────────┬──────────────────────────────┤
│ KERNEL  threads, scheduler,   │ HAL MODULES (vendor code)    │
│ ISRs, timers, sem, mutex,     │ hal_nordic (nrfx), hal_stm32,│
│ msgq, work queues, heaps      │ hal_nxp, cmsis ...           │
├───────────────────────────────┴──────────────────────────────┤
│ ARCH layer   arch/arm: context switch (PendSV), MPU, faults  │
│ SoC/BOARD    soc/nordic/nrf52, boards/nordic/nrf52840dk      │
└──────────────────────────────────────────────────────────────┘
        all of this is built by west + CMake + Kconfig + devicetree
Kernel
The scheduler and the objects threads use to cooperate: threads, semaphores, mutexes, message queues, timers, work queues. Lives in zephyr/kernel/.
Arch layer
CPU-specific code: how to switch threads on Cortex-M (PendSV exception), how faults are reported, how the MPU (Memory Protection Unit) is programmed. Lives in zephyr/arch/arm/.
Driver
Code that talks to one kind of hardware block, e.g. the nRF TWIM (I2C master with DMA) driver drivers/i2c/i2c_nrfx_twim.c.
HAL module
HAL = Hardware Abstraction Layer. The vendor's own low-level library (Nordic's nrfx, ST's STM32Cube LL/HAL). Zephyr drivers often call it instead of touching registers directly. It is kept in a separate git repository called a module.
Subsystem
A bigger feature built on drivers and kernel: the logging system, the shell, the Bluetooth host, the network stack.
west manifest
A file (west.yml) listing every git repository (Zephyr itself + modules) and the exact commit of each, so everyone gets the same source tree.

2. WHAT HAPPENS WHEN YOUR CODE CALLS i2c_write_dt()

  1. Your code calls i2c_write_dt(&bme, buf, 2). This is a generic I2C API function in include/zephyr/drivers/i2c.h.
  2. The function looks inside bme.bus, which is a pointer to a struct device for the I2C controller, and finds its api pointer (a table of function pointers).
  3. It calls api->transfer(dev, msgs, 1, addr). For the nRF52840 that is the TWIM driver's function.
  4. The TWIM driver calls the nrfx HAL function nrfx_twim_xfer(), which writes the TWIM registers (TXD.PTR, TXD.MAXCNT, TASKS_STARTTX) and starts a DMA transfer.
  5. The driver blocks your thread on a kernel semaphore (k_sem_take). The scheduler runs another thread.
  6. When the transfer finishes, the TWIM interrupt fires; the ISR (Interrupt Service Routine) gives the semaphore, your thread becomes ready, and i2c_write_dt() returns 0.

Every layer in the diagram took part: application → driver API → driver → HAL → hardware → interrupt → kernel → back to application.

Because step 5 blocks on a semaphore, calling i2c_write_dt() from an ISR (for example a GPIO button callback) asserts or hangs: an ISR cannot block. See card 13 and scenario 6.
A Zephyr image is a single statically linked binary. At the bottom is the arch and SoC layer, then the kernel and the vendor HAL modules, then the device driver model that gives each peripheral class one generic API, then subsystems like logging, Bluetooth and networking, and finally the application. The source tree is assembled by west from a manifest, and the build is configured by Kconfig for software and devicetree for hardware.

3. west: the meta-tool (init, update, build, flash, debug, manifests, modules)

▶

1. WHAT IS IT?

west is Zephyr's command-line tool. It does two jobs. First, it fetches and updates the many git repositories a Zephyr workspace needs (like Google's repo tool). Second, it wraps CMake and the flashing/debugging tools in short commands, so you type west flash instead of a long J-Link or OpenOCD command line.

Workspace
The top folder that holds everything: .west/ (west's settings), zephyr/, modules/, bootloader/, and maybe your app.
Manifest repository
The one repository that contains west.yml. Usually zephyr/ itself, or your own app repository (a "T2 star" workspace, the recommended setup for products).
Module
An extra repository that Zephyr's build understands because it contains zephyr/module.yml. Examples: hal_nordic, hal_stm32, mbedtls, mcuboot, lvgl, littlefs.
Runner
A west plug-in that knows one flashing/debug tool: jlink, nrfjprog/nrfutil, openocd, pyocd, stm32cubeprogrammer, esp32. The board says which runners it supports in board.cmake.
Pristine build
Deleting the build folder and configuring from scratch. Needed when CMake's cached settings (board, overlay list) are stale.

  projects:
    - name: zephyr

This is a T2 "star" workspace: your application repository is the manifest repository, and it pins the Zephyr version. Upgrading Zephyr becomes a one-line pull request that changes revision:. Run west update afterwards.

4. WORKED EXAMPLE: WHY name-allowlist MATTERS

A full west update of upstream Zephyr clones about 60 modules, roughly 4–6 GB including history. With an allowlist of 3 modules (cmsis, hal_nordic, mcuboot) the workspace is under 1 GB and CI checkout time drops from several minutes to well under a minute.

Forgetting west update after git pull in the manifest repo: Zephyr moves to the new version, but the modules stay on old SHAs. Symptom: strange compile errors in HAL headers (nrfx_twim_xfer signature mismatch). Fix: always run west update after the manifest changes; west status and west diff show local changes in every project.
west is Zephyr's meta-tool. west init clones the manifest repository, and west update clones every project listed in west.yml at its pinned revision, which makes the workspace reproducible. Then west build -b board runs CMake and Ninja, west flash and west debug call the board's runner such as J-Link or OpenOCD. I use -p always when I add overlays or change boards, because CMake caches those decisions.

4. The build system: CMake + Kconfig + devicetree, and what lands in build/

▶

1. WHAT IS IT?

When you run west build, three tools work together. CMake decides which source files to compile. Devicetree tooling turns the hardware description into C macros. Kconfig turns your option choices into C macros. Then the compiler builds everything with those macros, and the linker produces zephyr.elf.

CMake
A build-system generator. Your app's CMakeLists.txt calls find_package(Zephyr), which pulls in all of Zephyr's build logic. CMake generates Ninja files; Ninja runs the compiler.
dtc / edtlib
dtc is the devicetree compiler (checks syntax and prints warnings). edtlib is Zephyr's Python library that combines the tree with the binding files and writes the C header.
Kconfiglib
Zephyr's Python implementation of the Linux Kconfig language. It reads all Kconfig files and your .conf files and writes .config and autoconf.h.
Ordinal
A number given to each devicetree node in dependency order. Device objects are named after it (__device_dts_ord_42).

2. STEP BY STEP: WHAT west build DOES

  1. Find the board. CMake looks up nrf52840dk/nrf52840 in boards/nordic/nrf52840dk/ and reads board.yml.
  2. Devicetree first. The C preprocessor runs on the board .dts (which #includes the SoC .dtsi files), then your overlay files are appended. dtc checks it. edtlib matches each node to its binding YAML, and writes zephyr.dts (the final merged tree) and devicetree_generated.h (thousands of macros).
  3. Kconfig second. Kconfig reads the board's _defconfig, then prj.conf, then extra fragments, in that order (later wins). It can see the devicetree through generated symbols like DT_HAS_BOSCH_BMI270_ENABLED, which is why devicetree must run first. It writes .config and autoconf.h.
  4. Compile. Every .c file is compiled with -include autoconf.h, so CONFIG_* macros are visible everywhere. Only drivers whose Kconfig option is y are added to the build (zephyr_library_sources_ifdef(CONFIG_BMI270 bmi270.c)).
  5. Link in stages. Zephyr links a temporary zephyr_pre0.elf, runs scripts over it to generate the interrupt vector table and other tables, then links the final zephyr.elf. Finally objcopy makes zephyr.hex and zephyr.bin.

5. Kconfig: prj.conf, menuconfig, dependencies, defconfigs, fragments

▶

1. WHAT IS IT?

Kconfig is a list of switches and numbers that decide which software is compiled in and how it is sized. Each switch is a symbol, such as I2C or MAIN_STACK_SIZE. In your files you write it with the prefix: CONFIG_I2C=y. Kconfig never describes hardware (pins, addresses); that is devicetree's job.

Symbol
One option. Types: bool (y/n), int, hex, string.
prompt
A symbol with a prompt is user-settable. A promptless symbol can only be set by defaults or select; writing it in prj.conf has no effect (and Zephyr warns).
depends on
A condition that must be true for the symbol to be enabled at all. If it is false, the symbol is forced to n, whatever you write.
select
A reverse dependency: "if I am y, force that other symbol to y". Powerful but dangerous because it ignores the other symbol's own dependencies.
default
The value used when nobody assigns one. Can be conditional: default y if DT_HAS_….
defconfig
The board's own fragment, e.g. nrf52840dk_nrf52840_defconfig, with CONFIG_GPIO=y, CONFIG_SERIAL=y. It is applied before your prj.conf.
Fragment / overlay config
Any extra .conf file merged on top: boards/<board>.conf in your app (picked automatically), or -DEXTRA_CONF_FILE=debug.conf.

2. STEP BY STEP: HOW THE FINAL VALUE IS DECIDED

  1. Load all Kconfig definition files (Zephyr's, modules', your app's optional Kconfig).
  2. Apply assignments in order: board _defconfig → boards/<board>.conf in the app (if any) → prj.conf → EXTRA_CONF_FILE files. A later assignment of the same symbol replaces the earlier one.
  3. For each symbol, evaluate depends on. If false → value is n (int symbols become unavailable).
  4. Apply selects from enabled symbols (forces y).
  5. If the user assigned a value and the symbol has a prompt and dependencies are met → use it. Otherwise use the first default whose condition is true.
  6. Check ranges for int symbols. Write .config and autoconf.h.
  7. Zephyr then compares what you asked for with what you got. Any mismatch → warning → build aborts.

6. Devicetree basics: nodes, properties, labels, aliases, chosen, status, compatible

▶

1. WHAT IS IT?

Devicetree (DT) is a text description of the hardware: which peripherals exist, at which address, which pins and interrupts they use, and what is connected to them. Zephyr reads it at build time (Linux reads it at boot) and turns it into C macros. The benefit: the LED pin is written once in the board file, and the same main.c works on any board.

/ {                                          // "/" = root node, the whole board
	aliases {
		led0 = &led0;                        // alias: a board-independent name → a node
	};
	chosen {
		zephyr,console = &uart0;             // chosen: "use THIS node for the console"
	};
	leds {
		compatible = "gpio-leds";            // which binding (schema) describes the children
		led0: led_0 {                        // "led0:" is a LABEL; "led_0" is the node NAME
			gpios = <&gpio0 13 GPIO_ACTIVE_LOW>; // phandle to controller, pin 13, flags
			label = "Green LED 0";
		};
	};
	soc {
		i2c0: i2c@40003000 {                 // name@unit-address (= first reg value, hex)
			compatible = "nordic,nrf-twim";  // "vendor,device" → selects driver + binding
			reg = <0x40003000 0x1000>;       // base address, size of register block
			status = "okay";                 // "okay" = in use; "disabled" = ignore
		};
	};
};
Node
A block name { … }; that represents one thing (a peripheral, an LED, a sensor). Nodes nest: a sensor node lives inside its I2C bus node.
Property
A name = value; line inside a node. Values: <cells> (32-bit numbers), "strings", phandles, or nothing (a boolean like gpio-controller;).
Path
The full location of a node: /soc/i2c@40003000.
Label
A short handle written before a node (i2c0:) so you can refer to it elsewhere as &i2c0. Labels exist only in the source; they are not part of the path.
Phandle
A reference from one node to another, written &gpio0. In gpios = <&gpio0 13 GPIO_ACTIVE_LOW> it means "the GPIO controller node, then 2 cells it defines: pin and flags".
compatible
A string "vendor,device" that says what the node is. Zephyr uses it to find the binding (card 7) and the driver.
status
"okay" means the hardware is present and should get a driver instance. "disabled" means "exists on the chip but not used on this board". The SoC .dtsi marks most peripherals disabled; boards and overlays enable what they use.
aliases
Generic names like led0, sw0, imu0 that samples use. Each board points them at its own nodes.
chosen
System-wide choices: zephyr,console, zephyr,shell-uart, zephyr,flash, zephyr,sram, zephyr,code-partition.
DTS / DTSI
.dts = the board file (one per board). .dtsi = an include file (the SoC description, shared by every board with that chip).

2. STEP BY STEP: HOW THE FINAL TREE IS BUILT

  1. The board file nrf52840dk_nrf52840.dts starts with #include <nordic/nrf52840_qiaa.dtsi>, which defines every peripheral of the chip, almost all with status = "disabled".
  2. The board file adds board-specific nodes (LEDs, buttons) and enables what is wired: &uart0 { status = "okay"; };.
  3. Your overlay (app.overlay or boards/nrf52840dk_nrf52840.overlay) is appended last. Writing &i2c0 { … } merges into the existing node; it does not create a new one.
  4. When the same property is set twice, the last one wins. So the overlay overrides the board, which overrides the SoC.
  5. The result is written to build/zephyr/zephyr.dts.

3. WORKED EXAMPLE: READING ONE PROPERTY

gpios = <&gpio0 13 GPIO_ACTIVE_LOW>; — the gpio0 controller says #gpio-cells = <2>, so two cells follow the phandle: pin = 13, flags = GPIO_ACTIVE_LOW = 1 (bit 0). On the nRF52840 DK, LED1 is wired from VDD through a resistor to P0.13, so driving the pin low turns it on. Because the flag says "active low", your code writes logical 1 ("on") and Zephyr drives the pin physically 0. If #gpio-cells were 3, the line would need 3 cells and dtc would complain.

Two nodes claiming the same pin. Devicetree does not check pin conflicts. If you put an LED on P0.26, which the board already uses as I2C SDA, the build succeeds and the bus stops working once your code configures the pin as an output. Always check the board's pin table and the pinctrl file.
Devicetree is a hierarchical description of the hardware. Nodes represent devices, properties give their addresses, interrupts and pins, and compatible strings select the binding and driver. Labels let other files refer to a node with &label, aliases give board-independent names like led0, chosen picks system devices like the console, and status says whether a node is used. Zephyr merges the SoC dtsi, board dts and overlays at build time, last write wins, and generates C macros instead of parsing it at runtime.

7. Bindings: the YAML schema that gives devicetree properties meaning

▶

1. WHAT IS IT?

A binding is a YAML file that says, for one compatible string, which properties a node may or must have and what type each one is. Without a matching binding, Zephyr generates almost no macros for that node, so your C code cannot read its properties. Bindings live in zephyr/dts/bindings/, in modules, or in your app's dts/bindings/ folder.

# dts/bindings/sensor/bosch,bme280-i2c.yaml (shape of a real binding)
description: BME280 temperature, pressure, humidity sensor on I2C
compatible: "bosch,bme280"          # must match the node's compatible exactly
include: [sensor-device.yaml, i2c-device.yaml]  # inherit common props (reg, …)
on-bus: i2c                          # only matches nodes whose parent is an I2C bus
properties:
  int-gpios:
    type: phandle-array              # <&gpio0 4 GPIO_ACTIVE_HIGH>
    description: Data-ready interrupt pin (optional)
  oversampling:
    type: int
    default: 1
    enum: [1, 2, 4, 8, 16]           # any other value → build error
type
int, array, boolean, string, string-array, phandle, phandles, phandle-array, uint8-array.
required
required: true → a node without the property fails the build with a clear message.
include
Reuses another binding's property list (e.g. i2c-device.yaml makes reg required).
on-bus
Lets the same compatible have different bindings for I2C and SPI (bosch,bme280 exists in both).
*-cells
Controllers declare names for the cells after their phandle, e.g. GPIO bindings: gpio-cells: [pin, flags]. That is how DT_GPIO_PIN() knows that cell 0 is the pin.

2. STEP BY STEP: WHAT edtlib DOES WITH A NODE

  1. Read the node's compatible list (it can have several, most specific first).
  2. Find a binding file with that compatible (and matching on-bus, if any). The first match wins.
  3. Check every property: required ones present, types correct, enum values allowed. Fill in defaults.
  4. Generate macros for every property the binding declares: DT_N_S_soc_S_i2c_40003000_S_bme280_76_P_oversampling 1.
  5. Generate the DT_HAS_BOSCH_BME280_ENABLED Kconfig symbol if any okay node uses that compatible.

3. WORKED EXAMPLE: A TYPO IN compatible

Overlay: compatible = "bosch,bme-280"; (extra dash). No binding matches → no property macros, and DT_HAS_BOSCH_BME280_ENABLED is n → the BME280 driver's Kconfig default stays n → DEVICE_DT_GET on this node is a link error. Nothing says "typo". This is the single most common devicetree mistake. Check build/zephyr/zephyr.dts and grep the bindings folder for the exact string.

A binding is the YAML schema for a compatible string. It lists properties with their types, which are required, defaults and allowed values, and it can be bus-specific with on-bus. edtlib validates each devicetree node against its binding and only generates macros for declared properties, so if the compatible has a typo, no binding matches and the driver silently is not instantiated.

8. Overlays: changing the board's devicetree from your application

▶

1. WHAT IS IT?

An overlay is a small devicetree file that the build appends after the board's .dts. You never edit the board file inside zephyr/; instead you write changes in your application folder. Typical uses: enable a bus, add a sensor under it, change a pin, add an alias.

2. WHICH OVERLAY FILES ARE USED? (THE RULE MOST PEOPLE GET WRONG)

  1. If you pass -DDTC_OVERLAY_FILE=a.overlay, only that list is used. Nothing is searched.

  3. If any file was found in step 2, the search stops. app.overlay is then ignored.
  4. Otherwise, <board>.overlay in the app root is used if present; otherwise app.overlay.
  5. -DEXTRA_DTC_OVERLAY_FILE=… files are always added on top.

The build log tells you what it found: -- Found devicetree overlay: /home/me/app/boards/nrf52840dk_nrf52840.overlay. If your file is not in that list, it was not used. 9. Devicetree from C: node identifiers and the DT_* / *_DT_SPEC macros

▶

1. WHAT IS IT?

Your C code never parses devicetree text. Instead, the build generated thousands of #defines, and a family of macros (DT_ALIAS, DT_PROP, GPIO_DT_SPEC_GET …) picks the right one at compile time. The result is a plain constant, so reading a pin number from devicetree costs zero bytes of RAM and zero cycles at runtime.

Node identifier
A token that names one node, e.g. DT_N_S_soc_S_i2c_40003000. It is not a variable or a pointer; it is just a name the preprocessor pastes onto other names. N = node, S = slash. Characters other than letters/digits become _ and everything is lowercase.
Property token
The property name with - turned into _: clock-frequency → clock_frequency.
Spec struct
A small const struct that bundles "which device + which pin/address + flags": struct gpio_dt_spec, struct i2c_dt_spec, struct spi_dt_spec. The *_dt API functions take these.

2. STEP BY STEP: HOW GPIO_DT_SPEC_GET(DT_ALIAS(led0), gpios) BECOMES CONSTANTS

  1. DT_ALIAS(led0) pastes tokens to DT_N_ALIAS_led0, which the generated header defines as DT_N_S_leds_S_led_0 (the path /leds/led_0).
  2. GPIO_DT_SPEC_GET(node, gpios) expands into three lookups on that node's gpios property, index 0:
    the controller → DT_N_S_leds_S_led_0_P_gpios_IDX_0_PH = DT_N_S_soc_S_gpio_50000000;
    the pin cell → …_IDX_0_VAL_pin = 13;
    the flags cell → …_IDX_0_VAL_flags = 1.
  3. The controller node becomes a device pointer with DEVICE_DT_GET(DT_N_S_soc_S_gpio_50000000) = &__device_dts_ord_9 (9 is that node's ordinal in this build).
  4. Final C, as the compiler sees it: { .port = &__device_dts_ord_9, .pin = 13, .dt_flags = 1 }.

5. DECODING DT COMPILE ERRORS

Because everything is token pasting, a missing node shows up as a strange undefined identifier. Learn to read it:

error: '__device_dts_ord_DT_N_ALIAS_led0_P_gpios_IDX_0_PH_ORD' undeclared here (not in a function)

Read it from the inside: DT_N_ALIAS_led0 was not replaced by a path, so the alias led0 does not exist on this board. If instead you see undefined reference to `__device_dts_ord_17' at link time, the node exists (it has ordinal 17) but no driver created a device for it: it is disabled or its driver's Kconfig option is off.

Devicetree is consumed through macros. DT_NODELABEL, DT_ALIAS, DT_CHOSEN and DT_PATH give a node identifier, which is just a token like DT_N_S_soc_S_i2c_40003000, and DT_PROP, DT_REG_ADDR and friends paste property names onto it to reach the generated defines. Spec macros like GPIO_DT_SPEC_GET bundle the controller device, pin and flags into a const struct, so there is no runtime lookup. An undeclared DT_N_ALIAS token means the alias is missing; an undefined __device_dts_ord_N at link means the node exists but has no enabled driver.

10. Threads: creating them, stacks, and Zephyr's priority numbers

▶

1. WHAT IS IT?

A thread is an independent function that runs "at the same time" as others: it has its own stack and its own saved CPU registers, and the kernel switches between threads. (General theory of states and context switching: page 15.) Zephyr's special twist is its priority numbering.

Priority
An integer. Lower number = more important.
Cooperative thread
Priority negative (−16 … −1 by default). Once it runs, no other thread can take the CPU from it, not even a more important one. Only interrupts can pause it, and it always gets the CPU back after the interrupt. It runs until it blocks, sleeps or yields.
Preemptible thread
Priority zero or positive (0 … 14 by default). A more important thread that becomes ready takes the CPU immediately.
Idle thread
Runs at the lowest priority (15) when nothing else can; it is where the CPU sleeps (WFI) and where power management happens.
Stack
RAM for the thread's local variables, function calls and saved registers. Declared with K_THREAD_STACK_DEFINE so the alignment and MPU guard area are correct.
priority:  -16 ... -2  -1 | 0   1   2 ... 13  14 | 15
           ◄── cooperative ─►|◄──── preemptible ──────►| idle
  examples:  sys workqueue = -1     main = 0     shell ≈ 14
  K_PRIO_COOP(x)    = -(CONFIG_NUM_COOP_PRIORITIES - x)
  K_PRIO_PREEMPT(x) = x

With the default CONFIG_NUM_COOP_PRIORITIES=16: K_PRIO_COOP(0) = −16 (most important), K_PRIO_COOP(15) = −1. K_PRIO_PREEMPT(7) = 7. Prefer these macros over raw numbers in shared code.

2. STEP BY STEP: TWO WAYS TO CREATE A THREAD

/* A) Static: defined at compile time, started automatically at boot */
void sensor_entry(void *p1, void *p2, void *p3)     // always 3 void* arguments
{
    while (1) {
        read_sensor();
        k_msleep(100);                              // block 100 ms → other threads run
    }
}
K_THREAD_DEFINE(sensor_tid,      // name of the k_tid_t variable created
                1024,            // stack size in bytes
                sensor_entry,    // entry function
                NULL, NULL, NULL,// p1, p2, p3
                5,               // priority 5 → preemptible
                0,               // options (K_FP_REGS, K_USER, K_ESSENTIAL)
                0);              // start delay in ms (0 = start at boot)

/* B) Dynamic: created at runtime, e.g. from main() */
K_THREAD_STACK_DEFINE(net_stack, 2048);             // aligned stack array (+ guard)
static struct k_thread net_thread;                  // the thread control block

k_tid_t tid = k_thread_create(&net_thread, net_stack,
                K_THREAD_STACK_SIZEOF(net_stack),   // NOT sizeof(): excludes reserved area
                net_entry, NULL, NULL, NULL,
                K_PRIO_PREEMPT(3), 0, K_NO_WAIT);
k_thread_name_set(tid, "net");                      // shows in shell and debugger

3. WHAT HAPPENS AT BOOT

  1. The reset handler sets up memory, then z_cstart() runs device init levels PRE_KERNEL_1 and PRE_KERNEL_2.
  2. The kernel creates the main thread (priority CONFIG_MAIN_THREAD_PRIORITY = 0, stack CONFIG_MAIN_STACK_SIZE = 1024) and the idle thread, and switches to main.
  3. The main thread runs POST_KERNEL and APPLICATION init levels, starts all K_THREAD_DEFINE threads whose delay is 0, then calls your main().
  4. If main() returns, the main thread simply ends. The system keeps running the other threads. (Unlike bare-metal, returning from main is fine.)

4. WORKED EXAMPLE: WHO RUNS?

Threads ready at the same moment: A (prio 5), B (prio −2), main (prio 0). B runs first (−2 is the lowest number). B is cooperative, so even if A's priority were raised to −5 while B runs, B keeps the CPU until B calls k_msleep(). Then −5 runs, then main (0), then A (5).

You copy an example that uses K_PRIO_COOP(7) (= −9) for a polling thread and the thread never sleeps. Every preemptible thread (main, shell, logging) stops forever. Symptom: the shell does not answer, and logs stop. See scenario 5 and the "cooperative hog" sim preset.
In Zephyr, lower numbers are higher priority. Negative priorities are cooperative: once running they are never preempted by another thread, only by interrupts, and they run until they block or yield. Zero and positive priorities are preemptible. I create threads statically with K_THREAD_DEFINE, or at runtime with k_thread_create and a stack from K_THREAD_STACK_DEFINE, using K_THREAD_STACK_SIZEOF for the size. Main runs at priority 0 with a 1 KB stack by default, and the idle thread at the lowest priority does the sleeping.

11. Scheduling in Zephyr: preemption, time slicing, k_sleep vs k_yield, sched lock

▶

1. WHAT IS IT?

The scheduler decides which ready thread uses the CPU. Zephyr's rule is short: run the highest-priority ready thread; among equal priorities, the one that has waited longest; never take the CPU away from a cooperative thread.

Ready
The thread could run now; it is not waiting for anything.
Preemption
The kernel stops the running thread in the middle of its code because a more important thread became ready.
Time slicing
Threads of the same priority take turns, each for a fixed time (the "slice"). Off by default (CONFIG_TIMESLICE_SIZE=0).
Reschedule point
A moment when the kernel re-checks who should run: a thread blocks, unblocks another, yields, or an ISR returns.

2. THE CALLS, AND EXACTLY WHO CAN RUN AFTER EACH

CallWhat it doesWho can run afterwards
k_msleep(10) / k_sleep(K_MSEC(10))Thread leaves the ready queue for at least 10 msAnyone, including lower priorities
k_yield()Moves the thread to the back of its priority's queueOnly threads of equal or higher priority. If none is ready, the caller continues immediately.
k_sleep(K_NO_WAIT)Zero-length sleep: the kernel implements it as k_yield()Same as k_yield: equal or higher priority only. A common wrong belief is that it lets lower priorities run.
k_busy_wait(50)Spins for 50 µs, does not give up the CPUNo one (except preemption by higher prio)
k_sched_lock() / k_sched_unlock()Temporarily makes the current thread behave cooperativelyNobody preempts it until unlock; ISRs still run
k_sem_take(&s, K_FOREVER)Blocks until givenAnyone

3. STEP BY STEP: TIME SLICING EXAMPLE

Config: CONFIG_TIMESLICING=y, CONFIG_TIMESLICE_SIZE=10 (ms), CONFIG_TIMESLICE_PRIORITY=0 (slicing applies to threads with priority ≥ 0). Two threads, both priority 5, both compute-bound.

  1. t = 0 ms: A runs (it became ready first).
  2. t = 10 ms: A's slice expires. The timer interrupt sees B ready at the same priority, moves A to the back. B runs.
  3. t = 20 ms: B's slice expires; A runs again. Each gets 50 % of the CPU in 10 ms turns.
  4. If C at priority 3 wakes at t = 14 ms, it preempts B immediately (preemption does not wait for the slice end).

With slicing off, A would run forever and B would starve, because equal priority never preempts.

4. WHY HAVE COOPERATIVE THREADS AT ALL?

A cooperative thread knows it will not be interrupted by another thread between two of its own instructions, so data it shares only with other cooperative threads needs no mutex. The system work queue is cooperative (−1) for this reason: work items run to completion one after another. Bluetooth host threads are cooperative too. The price: one long-running cooperative thread adds its whole run time to every other thread's latency.

✖ WRONG — coop thread "yielding" to lower priorities
void poll(void *a, void *b, void *c) {  // prio -3
    while (!data_ready()) {
        k_yield();  // main (0) never runs!
    }
}
✔ RIGHT — block until there is work
void poll(void *a, void *b, void *c) {
    k_sem_take(&data_sem, K_FOREVER);
    // the ISR does k_sem_give(&data_sem)
}
Zephyr always runs the highest-priority ready thread, FIFO within a priority. Preemptible threads are preempted as soon as something more important is ready; cooperative ones keep the CPU until they block, sleep or yield. k_yield only gives way to equal or higher priority, so to let lower priorities run you must block or sleep. Time slicing, when enabled, rotates equal-priority preemptible threads every CONFIG_TIMESLICE_SIZE ms, and k_sched_lock makes a section temporarily non-preemptible without disabling interrupts.

12. Time: ticks, tickless kernel, timeouts, k_uptime_get, cycles

▶

1. WHAT IS IT?

The kernel measures time in ticks. All timeouts (k_msleep, k_sem_take(..., K_MSEC(5)), timers) are rounded to whole ticks. A separate, much finer counter (cycles) is used for precise measurements.

Tick
The kernel's time unit. Rate set by CONFIG_SYS_CLOCK_TICKS_PER_SEC. On nRF52 the default is 32768 (one tick ≈ 30.5 µs, from the 32.768 kHz RTC1). On Cortex-M with SysTick the default is 10000 (100 µs).
Hardware cycles
The raw counter of the system timer: CONFIG_SYS_CLOCK_HW_CYCLES_PER_SEC (32768 on nRF RTC; CPU clock 64 000 000 for SysTick-based ports).
Tickless kernel
CONFIG_TICKLESS_KERNEL=y (default on most SoCs): there is no periodic interrupt. The kernel programs the timer for the next deadline only. If nothing is due for 3 seconds, the CPU sleeps 3 seconds with no wake-ups.
k_timeout_t
The type of every timeout argument. Build it with K_MSEC(x), K_USEC(x), K_SECONDS(x), K_TICKS(x), K_NO_WAIT, K_FOREVER. Passing a plain int is a compile error since 2.x (on purpose).

2. STEP BY STEP: WHAT k_msleep(10) DOES ON nRF52 (TICKLESS)

  1. Convert 10 ms to ticks: 10 × 32768 / 1000 = 327.68 → rounded up to 328 ticks. Zephyr adds one more tick because the current tick is already partly over, so the thread sleeps at least 10 ms (≈ 10.01–10.04 ms).
  2. Put the thread on the timeout list with an expiry of now + 329 ticks.
  3. If that is the earliest timeout, reprogram the RTC1 compare register (CC) to that tick count.
  4. Switch to another thread (or idle, which executes WFI and sleeps).
  5. The RTC compare interrupt fires; the timer driver calls sys_clock_announce(); the kernel moves the thread to ready; the scheduler runs it if it is the most important.

3. WORKED EXAMPLE: PERIODIC LOOP DRIFT

✖ WRONG — period = 100 ms + work time
while (1) {
    sample();        // takes 3 ms
    k_msleep(100);
}  // real period 103 ms → after 1 h
   // you have 34 951 samples, not 36 000
✔ RIGHT — absolute deadlines
int64_t next = k_uptime_get();
while (1) {
    sample();
    next += 100;
    k_sleep(K_TIMEOUT_ABS_MS(next));
}  // or use a periodic k_timer

3 600 000 ms / 103 ms = 34 951 iterations instead of 36 000: a 2.9 % error from 3 ms of work. K_TIMEOUT_ABS_MS needs CONFIG_TIMEOUT_64BIT=y (default).

4. READING TIME

int64_t  ms   = k_uptime_get();        // ms since boot, 64-bit, never wraps in practice
uint32_t ms32 = k_uptime_get_32();     // wraps after 49.7 days
int64_t  t0   = k_uptime_ticks();
uint32_t c0   = k_cycle_get_32();      // hardware cycles: fine timing
do_work();
uint32_t dc   = k_cycle_get_32() - c0; // unsigned subtraction handles wrap
uint64_t ns   = k_cyc_to_ns_floor64(dc);

On nRF52 a "cycle" is 1/32768 s = 30.5 µs, too coarse to time a 5 µs function. Enable the DWT cycle counter (Cortex-M CONFIG_TIMING_FUNCTIONS + timing_counter_get()) for CPU-clock resolution (15.6 ns at 64 MHz).

k_msleep(1) in a loop expecting 1000 Hz on a board with SYS_CLOCK_TICKS_PER_SEC=100: each sleep becomes 2 ticks = 20 ms, so the loop runs at 50 Hz. Check the tick rate before relying on short sleeps.
Zephyr timeouts are k_timeout_t values built with K_MSEC and friends, converted to ticks and rounded up, so a sleep lasts at least the requested time. Most SoCs run tickless: the timer is programmed only for the next deadline, so idle periods have no wake-ups. For periodic work I use absolute timeouts or a k_timer to avoid drift, k_uptime_get for milliseconds, and k_cycle_get_32 or the DWT counter for fine measurement.

13. Interrupts: IRQ_CONNECT, direct and zero-latency ISRs, irq_lock, what ISRs may call

▶

1. WHAT IS IT?

An ISR (Interrupt Service Routine) is the function the CPU runs when hardware signals an event. In Zephyr you usually never write ISRs for standard peripherals (drivers do), but you must know how they are connected and what they may and may not do.

IRQ_CONNECT
A macro that connects an interrupt line to a C function at build time. The two-stage link (card 4) places the entry in the generated vector/ISR table.
Software ISR table
On Cortex-M, by default every vector points to one common wrapper _isr_wrapper which looks up {function, argument} in _sw_isr_table and calls your function with its argument. Costs a few extra cycles but lets one ISR function serve many instances.
Direct ISR
IRQ_DIRECT_CONNECT puts your function directly in the vector table: fewer cycles, but you must call ISR_DIRECT_PM() and return whether to reschedule.
Zero-latency IRQ (ZLI)
With CONFIG_ZERO_LATENCY_IRQS=y and flag IRQ_ZERO_LATENCY, the interrupt gets a hardware priority above the level the kernel masks. The kernel never blocks it, not even inside irq_lock(), so its latency is just the hardware's (12 cycles on Cortex-M4). In exchange it may not call any kernel API, because it can interrupt the kernel in the middle of updating its lists.
irq_lock()
Masks interrupts (on ARMv7-M by raising BASEPRI, so ZLIs still run) and returns a key to pass to irq_unlock(key). Nestable.

3. WORKED EXAMPLE: PRIORITY NUMBERS ON nRF52840

The nRF52840 NVIC has 3 priority bits → hardware levels 0 (highest) to 7. 14. Work queues: k_work, the system work queue, k_work_delayable

▶

1. WHAT IS IT?

A work queue is a thread whose only job is to run small functions ("work items") that other code hands to it. It is Zephyr's standard answer to "my ISR needs to do something slow": the ISR submits a work item (fast, never blocks), and the work queue thread runs the function a moment later in normal thread context, where blocking is allowed.

struct k_work
A work item: a handler function pointer plus state flags. You do not allocate per submission; you reuse one static item.
System work queue
A work queue the kernel creates for everyone. Priority CONFIG_SYSTEM_WORKQUEUE_PRIORITY = −1 (cooperative), stack CONFIG_SYSTEM_WORKQUEUE_STACK_SIZE = 1024 bytes. Bluetooth, sensors triggers and many drivers use it too.
k_work_delayable
A work item with a built-in timer: "run this in 50 ms". Used for debouncing, retries, timeouts.
Pending / running
An item is pending while waiting in the queue, running while its handler executes. Submitting a pending item again does nothing (it is already queued).

2. STEP BY STEP: ISR → WORK ITEM

  1. At boot: K_WORK_DEFINE(rx_work, rx_handler); creates the item.
  2. The UART ISR calls k_work_submit(&rx_work). The kernel appends it to the system queue's list and readies the queue thread. Return value: 1 = queued now, 0 = was already queued, 2 = queued again while running.
  3. The ISR returns. The work queue thread (−1) is more important than main (0), so it runs next (unless a cooperative thread was running, which resumes first).
  4. The thread calls rx_handler(&rx_work). It may block (e.g. a flash write).
  5. When the handler returns, the next item in the queue runs. Items run one at a time, in order.

3. DELAYABLE WORK: BUTTON DEBOUNCE, WORKED

static void debounced(struct k_work *w)
{
    int pressed = gpio_pin_get_dt(&btn);      // read the settled level
    LOG_INF("button %s", pressed ? "down" : "up");
}
static K_WORK_DELAYABLE_DEFINE(db_work, debounced);

static void btn_isr(const struct device *d, struct gpio_callback *cb, uint32_t pins)
{
    k_work_reschedule(&db_work, K_MSEC(20)); // (re)start the 20 ms timer on every edge
}

Contacts bounce at t = 0, 1.2, 2.5 and 4 ms. Each edge calls k_work_reschedule, which moves the deadline: 20, 21.2, 22.5, 24 ms. The handler runs once at 24 ms. Had you used k_work_schedule, it keeps the first deadline (20 ms) and ignores the later calls, so you might sample while still bouncing at a long bounce. Choose: schedule = "at most once per window, first deadline", reschedule = "after things go quiet".

4. YOUR OWN QUEUE

K_THREAD_STACK_DEFINE(flash_wq_stack, 2048);

                   K_PRIO_PREEMPT(10), NULL);           // low prio, preemptible

Blocking for a long time on the system work queue. A handler that waits 500 ms for a modem reply delays every other user (Bluetooth connection events, sensor triggers, other drivers) by 500 ms, and since the queue is cooperative it also delays all preemptible threads while it computes. Symptom: BLE disconnects with reason 0x08 (supervision timeout). Fix: a dedicated work queue for slow jobs.
A work queue is a thread that runs work items in order. ISRs submit k_work items to defer anything slow or blocking into thread context. The system work queue is shared, cooperative at priority −1 with a 1 KB stack, so handlers must be short; long or blocking jobs get their own k_work_q. k_work_delayable adds a timer: k_work_schedule keeps the first deadline, k_work_reschedule moves it, which is the classic debounce pattern, and k_work_cancel_delayable_sync or k_work_flush let you shut it down safely.

15. Kernel timers (k_timer): periodic and one-shot callbacks

▶

1. WHAT IS IT?

A k_timer calls a function after a delay, optionally again every period. It uses the kernel's timeout list, so 100 timers cost no extra hardware. The expiry function runs in interrupt context (inside the system timer ISR), so it has the same rules as an ISR: no blocking.

static void blink_expiry(struct k_timer *t)      // ISR context!
{
    gpio_pin_toggle_dt(&led);                    // GPIO toggle is ISR-safe on nRF (register write)
}
K_TIMER_DEFINE(blink_timer, blink_expiry, NULL); // (name, expiry_fn, stop_fn)

k_timer_start(&blink_timer, K_MSEC(100),         // first expiry after 100 ms
                            K_MSEC(500));        // then every 500 ms (K_NO_WAIT = one-shot)
...
k_timer_stop(&blink_timer);                      // calls stop_fn if not NULL

/* A thread can also wait on it without an expiry function: */
k_timer_start(&tick_timer, K_MSEC(10), K_MSEC(10));
while (1) {
    k_timer_status_sync(&tick_timer);            // block until next expiry; returns count since last
    control_loop();                              // runs every 10 ms with no drift
}

STEP BY STEP

  1. k_timer_start inserts a timeout at now + 100 ms (rounded up to ticks).
  2. At expiry, the system timer ISR calls blink_expiry, increments the timer's status counter, and wakes threads in k_timer_status_sync.
  3. For periodic timers, the next expiry is computed from the previous expiry time, not from "now", so the period does not drift even if the ISR was late.

WORKED EXAMPLE: WHY IT DOES NOT DRIFT

Period 500 ms on nRF52 = 16 384 ticks exactly (500 × 32.768). Expiries are at ticks 3277 (first, 100 ms rounded up), 19 661, 36 045 … even if one ISR runs 2 ms late, the following one is still scheduled at its ideal tick.

Doing a sensor I2C read in the expiry function → assert (blocking in ISR). Put a k_work_submit() in the expiry function instead, or use a k_work_delayable that reschedules itself.
k_timer is a kernel software timer on the shared timeout list. k_timer_start takes an initial duration and a period, the period being drift-free because it is computed from the previous expiry. The expiry callback runs in the timer ISR, so it must not block; for heavier work I submit a work item, or have a thread block on k_timer_status_sync for a clean periodic loop.

16. Synchronisation: semaphores, mutexes (priority inheritance), condition variables, events

▶

1. WHAT ARE THEY?

These objects let threads wait for each other safely. Semaphores signal ("data arrived"); mutexes protect ("only one thread inside this code"); condition variables wait for a condition on shared data; events wait for combinations of flags. Theory of inversion and inheritance: page 15.

2. THE API, ANNOTATED

K_SEM_DEFINE(rx_sem, 0, 1);            // initial count 0, max 1 (binary)
k_sem_give(&rx_sem);                   // count++ (capped at limit) or wake a waiter; ISR-safe
int r = k_sem_take(&rx_sem, K_MSEC(50)); // 0 = got it, -EAGAIN = timed out, -EBUSY = K_NO_WAIT and 0

K_MUTEX_DEFINE(bus_lock);
k_mutex_lock(&bus_lock, K_FOREVER);    // owner = me; recursive: same thread may lock again
spi_transceive_dt(&flash, &tx, &rx);
k_mutex_unlock(&bus_lock);             // must be called by the owner, same number of times

K_CONDVAR_DEFINE(not_empty);
k_mutex_lock(&q_lock, K_FOREVER);
while (count == 0) {                   // ALWAYS a loop: wake-ups can be spurious / stolen
    k_condvar_wait(&not_empty, &q_lock, K_FOREVER); // atomically unlock + sleep, relock on wake
}
item = buf[--count];
k_mutex_unlock(&q_lock);
/* producer: lock; buf[count++]=x; k_condvar_signal(&not_empty); unlock; */

K_EVENT_DEFINE(sys_ev);
#define EV_WIFI BIT(0)
#define EV_TIME BIT(1)
k_event_post(&sys_ev, EV_WIFI);        // OR the bits in; ISR-safe
uint32_t got = k_event_wait_all(&sys_ev, EV_WIFI | EV_TIME, false, K_SECONDS(30));
                                       // wait until BOTH bits set; false = do not clear first

3. MUTEX PRIORITY INHERITANCE, STEP BY STEP (ZEPHYR'S RULES)

  1. L (priority 10) locks bus_lock.
  2. H (priority 2) wakes and calls k_mutex_lock(&bus_lock, …). It is owned, so H blocks.
  3. Zephyr raises L's priority to 2 (H's), limited by CONFIG_PRIORITY_CEILING. Now M (priority 5) cannot preempt L.
  4. L finishes and unlocks. Zephyr restores L to 10 and gives the mutex directly to H (H becomes owner and runs).
  5. H's worst wait = L's critical section length, not "L's section + all of M's work".

Try it in the Thread & Work Sim "priority inversion" preset, and its k_sem variant which has no inheritance.

Using k_sem initialised to 1 as a lock. Symptom: the high thread occasionally misses deadlines by tens of milliseconds under load.
Semaphores are counters for signalling and can be given from ISRs. Mutexes have an owner, are recursive, can only be used from threads, and implement priority inheritance: the owner is boosted to the highest waiter's priority until it unlocks, which bounds priority inversion. Condition variables pair with a mutex and are always waited in a loop, and k_event lets a thread wait for any or all of several bits, which semaphores cannot do cleanly.

struct sample { int16_t x, y, z; uint32_t ts; };    // 6 + 4 = 10 B, padded to 12 B (4-byte align)
K_MSGQ_DEFINE(imu_q, sizeof(struct sample), 16, 4); // 16 items × 12 B = 192 B buffer, 4-byte aligned

/* producer (ISR or thread) */
struct sample s = { .x = 12, .y = -3, .z = 1001, .ts = k_cycle_get_32() };
if (k_msgq_put(&imu_q, &s, K_NO_WAIT) != 0) {      // -ENOMSG if full: the queue copied nothing

struct sample r;

  2. If a consumer is waiting, the kernel copies straight into the waiting consumer's buffer instead and readies it.
  3. The producer can reuse s immediately because the data was copied.

3. k_poll: WAITING FOR TWO THINGS

struct k_poll_event ev[2] = {
    K_POLL_EVENT_INITIALIZER(K_POLL_TYPE_MSGQ_DATA_AVAILABLE, K_POLL_MODE_NOTIFY_ONLY, &imu_q),
    K_POLL_EVENT_INITIALIZER(K_POLL_TYPE_SEM_AVAILABLE,       K_POLL_MODE_NOTIFY_ONLY, &stop_sem),
};
while (1) {
    k_poll(ev, 2, K_FOREVER);                         // sleeps until at least one is ready
    if (ev[0].state == K_POLL_STATE_MSGQ_DATA_AVAILABLE) { k_msgq_get(&imu_q, &r, K_NO_WAIT); }
    if (ev[1].state == K_POLL_STATE_SEM_AVAILABLE)       { k_sem_take(&stop_sem, K_NO_WAIT); break; }
    ev[0].state = ev[1].state = K_POLL_STATE_NOT_READY; // must reset before the next k_poll
}

k_poll only tells you something is available; you still take it with K_NO_WAIT (another thread might have taken it first, so check the return). Needs CONFIG_POLL=y.

Putting a stack variable into a k_fifo: struct item it; k_fifo_put(&f, &it); then returning. Pipes are byte streams, mailboxes are addressed synchronous messages, and k_poll lets one thread wait on several objects. I size a msgq as production rate times the worst consumer stall.

18. ZBus: publish/subscribe channels between modules

▶

1. WHAT IS IT?

ZBus is a message bus. A channel holds the latest value of one message type (e.g. "accelerometer reading"). Code that produces data publishes to the channel; any number of observers are notified. Producers do not know who consumes the data, so modules stay decoupled: you can add a logger or a BLE notifier without touching the sensor code.

Channel
Static object with a message type, the current message (stored in RAM), an optional validator, and a list of observers. Defined with ZBUS_CHAN_DEFINE.
Listener
A callback run synchronously in the publisher's thread during zbus_chan_pub. Fast, but it delays the publisher and must not block.
Subscriber
A thread with a small queue of channel pointers. It is notified "channel X changed" and then reads the channel's current value (which may have changed again).
Message subscriber
(3.7+) Gets its own copy of every message, so none are lost to overwrite. Costs a net_buf pool.
VDED
Virtual Distributed Event Dispatcher: zbus's internal loop that, during publish, calls listeners and pushes notifications to subscribers in priority order.
struct acc_msg { int32_t x, y, z; };

ZBUS_CHAN_DEFINE(acc_chan,                   // channel name
    struct acc_msg,                          // message type
    NULL,                                    // validator (bool fn(const void*, size_t)), optional
    NULL,                                    // user data
    ZBUS_OBSERVERS(log_lis, ble_sub),        // observers known at build time
    ZBUS_MSG_INIT(.x = 0, .y = 0, .z = 0));  // initial value

static void log_cb(const struct zbus_channel *ch)       // listener: runs in publisher's context
{
    const struct acc_msg *m = zbus_chan_const_msg(ch);  // direct read, channel is locked here
    LOG_INF("acc %d %d %d", m->x, m->y, m->z);
}
ZBUS_LISTENER_DEFINE(log_lis, log_cb);
ZBUS_SUBSCRIBER_DEFINE(ble_sub, 4);                     // queue of 4 notifications

void ble_thread(void)
{
    const struct zbus_channel *ch;
    while (!zbus_sub_wait(&ble_sub, &ch, K_FOREVER)) {   // which channel changed?
        struct acc_msg m;
        zbus_chan_read(ch, &m, K_MSEC(10));              // copy out the CURRENT value
        notify_over_ble(&m);
    }
}
/* producer */
struct acc_msg m = { 12, -3, 1001 };
zbus_chan_pub(&acc_chan, &m, K_MSEC(10));               // lock, copy, notify observers, unlock

STEP BY STEP: WHAT zbus_chan_pub DOES

  1. Run the validator (if any); reject invalid messages with -ENOMSG.
  2. Lock the channel (a mutex-like lock, or spinlock in some configs), copy the 12-byte message into the channel's storage.
  3. Call every listener in order (log_cb runs now, in the publisher's thread).
  4. Push a notification into each subscriber's queue (ble_sub's queue gains &acc_chan).
  5. Unlock and return. ble_thread wakes later and reads the value.
A plain subscriber at 100 Hz that is slow: the channel holds only the latest value, so by the time it reads, several updates have been overwritten. If every sample matters, use a message subscriber or a k_msgq. Also: a slow listener (e.g. one that writes flash) blocks the sensor thread on every publish.
ZBus is Zephyr's publish/subscribe bus. Channels are statically defined with a message type and observers; publishers copy into the channel, listeners run synchronously in the publisher's context, subscribers are threads notified with the channel pointer that then read the latest value, and message subscribers get their own copies. It decouples modules, but plain subscribers can miss intermediate values, so for lossless streams I use message subscribers or a msgq.

19. Memory: heaps, k_malloc, memory slabs, stack sizing and the thread analyzer

▶

1. WHAT IS IT?

Zephyr prefers static allocation: thread stacks, queues and buffers are sized at build time, so the linker tells you if RAM runs out. Dynamic options exist for the cases that need them.

System heap
Used by k_malloc/k_free. Its size is CONFIG_HEAP_MEM_POOL_SIZE, default 0, so k_malloc returns NULL until you set it.
k_heap
Your own heap: K_HEAP_DEFINE(h, 4096), k_heap_alloc(&h, 100, K_MSEC(10)). Can block waiting for memory. Built on sys_heap (a fast segregated-fit allocator).
libc malloc
Separate arena (CONFIG_COMMON_LIBC_MALLOC_ARENA_SIZE with picolibc/newlib). Not the same pool as k_malloc.
Memory slab
A pool of equal-size blocks: O(1), no fragmentation, deterministic. K_MEM_SLAB_DEFINE(name, block_size, num_blocks, align).
Memory pools
The old k_mem_pool (buddy allocator) was removed in 2.x; k_heap replaced it. Interviewers may still ask.
Stack guard
On Cortex-M with an MPU, CONFIG_HW_STACK_PROTECTION puts a small no-access MPU region (32 B on ARMv7-M) below each stack, so an overflow causes an immediate MPU fault instead of silent corruption. ARMv8-M uses the PSPLIM register.

2. SLAB WORKED EXAMPLE

K_MEM_SLAB_DEFINE(pkt_slab, 64, 8, 4);  // 8 blocks × 64 B = 512 B, each 4-byte aligned

void *blk;
if (k_mem_slab_alloc(&pkt_slab, &blk, K_NO_WAIT) == 0) {  // -ENOMEM if all 8 in use
    memcpy(blk, frame, 64);
    k_fifo_put(&tx_fifo, blk);           // zero-copy hand-off (first word = fifo link!)
}
...
k_mem_slab_free(&pkt_slab, blk);        // 3.5+: pass the pointer (older: &blk)

Internally the free blocks form a linked list stored inside the blocks themselves; allocation pops the head (a few instructions), free pushes it back. That is why block size must be ≥ 4 bytes (pointer size) and a multiple of the alignment.

3. SIZING A THREAD STACK, STEP BY STEP

  1. Start generous (e.g. 2048 B), enable the analyzer: CONFIG_THREAD_ANALYZER=y, CONFIG_THREAD_ANALYZER_AUTO=y, CONFIG_THREAD_ANALYZER_AUTO_INTERVAL=5, CONFIG_THREAD_NAME=y.
  2. The kernel fills new stacks with 0xAA (CONFIG_INIT_STACKS, selected by the analyzer). The analyzer counts untouched 0xAA bytes from the bottom.
  3. Run the worst case (all log levels on, error paths, floats in printf). Read the report:
    sensor_th : STACK: unused 312 usage 1736 / 2048 (84 %); CPU: 3 %
  4. Pick size = peak × 1.25–1.5, rounded: 1736 × 1.3 ≈ 2256 → 2304 B. Or at least keep 20–30 % unused.
  5. Remember ISR stack is separate (CONFIG_ISR_STACK_SIZE = 2048), and with the FPU in use each context save can add 72 bytes of FP registers.

From the shell: kernel stacks prints the same numbers live.

Silent overflow without an MPU guard (e.g. a Cortex-M0 or guard disabled): the thread writes below its stack into the neighbouring thread's control block or stack. Symptoms appear later and elsewhere: another thread crashes, a queue gets corrupted. With the guard: ***** MPU FAULT *****, Stacking error, >>> ZEPHYR FATAL ERROR 2: Stack overflow on CPU 0, Current thread: 0x20001a40 (sensor_th). Reason 2 = K_ERR_STACK_CHK_FAIL.
Zephyr favours static allocation. For dynamic needs there is k_malloc on the system heap, which is zero bytes unless CONFIG_HEAP_MEM_POOL_SIZE is set, k_heap for private heaps, and memory slabs for deterministic fixed-size blocks without fragmentation. I size stacks by measuring with the thread analyzer, which counts untouched 0xAA fill bytes, under worst-case load and add 25–50 % margin, and I keep HW stack protection on so an overflow is an immediate MPU fault with reason 2 instead of silent corruption.

▶

1. WHAT IS IT?

Every hardware instance that has a driver (each enabled I2C controller, each sensor) is represented by one constant struct device in flash. #define DT_DRV_COMPAT acme_temp42                  // handles compatible = "acme,temp42"

#include <zephyr/drivers/i2c.h>
#include <zephyr/drivers/sensor.h>

struct temp42_config { struct i2c_dt_spec i2c; };  // from DT, const
struct temp42_data   { int16_t raw; };              // runtime, RAM

static int temp42_fetch(const struct device *dev, enum sensor_channel ch)
{
    const struct temp42_config *cfg = dev->config;
    struct temp42_data *data = dev->data;
    uint8_t buf[2];
    int ret = i2c_burst_read_dt(&cfg->i2c, 0x00, buf, 2);  // register 0x00, 2 bytes
    if (ret) { return ret; }
    data->raw = (int16_t)((buf[0] << 8) | buf[1]);       // big-endian, 1/128 °C per LSB
    return 0;
}

static int temp42_get(const struct device *dev, enum sensor_channel ch, struct sensor_value *val)
{
    struct temp42_data *data = dev->data;
    if (ch != SENSOR_CHAN_AMBIENT_TEMP) { return -ENOTSUP; }
    int32_t micro = (int32_t)data->raw * 1000000 / 128;   // to micro-degrees
    val->val1 = micro / 1000000;                          // integer part
    val->val2 = micro % 1000000;                          // fractional part, millionths
    return 0;
}

static DEVICE_API(sensor, temp42_api) = {                 // 4.1+; older: static const struct sensor_driver_api
    .sample_fetch = temp42_fetch,
    .channel_get  = temp42_get,
};

static int temp42_init(const struct device *dev)          // called once at boot
{
    const struct temp42_config *cfg = dev->config;
    if (!i2c_is_ready_dt(&cfg->i2c)) { return -ENODEV; }  // bus must already be initialised
    uint8_t id;
    if (i2c_reg_read_byte_dt(&cfg->i2c, 0x0F, &id) || id != 0x42) { return -EIO; }
    return 0;                                             // non-zero → device_is_ready() = false
}

3. WHAT device_is_ready() REALLY CHECKS

  1. The pointer is non-NULL.
  2. dev->state->initialized is true (the init level has run), and
  3. dev->state->init_res == 0 (init returned 0).

So it is false if init failed (chip ID wrong, bus not ready), or if the device uses zephyr,deferred-init and nobody called device_init() yet. A disabled node does not give "false": it gives a link error, because no struct device exists at all.

Skipping device_is_ready() and calling the API anyway: the driver's data was never set up (mutex not initialised, DMA not configured). Symptom: a fault inside the driver, far from the real cause, which was the sensor not ACKing at boot.
Each driver instance is a const struct device in flash with a config pointer from devicetree, a data pointer in RAM, an API table of function pointers and its init state. Drivers set DT_DRV_COMPAT and use DT_INST_FOREACH_STATUS_OKAY with DEVICE_DT_INST_DEFINE to create one device per okay node, choosing an init level and priority. Applications get the pointer with DEVICE_DT_GET at compile time and must check device_is_ready, which is false if init returned an error; a disabled node instead produces a link error.

21. Init levels and priorities: who initialises first at boot

▶

1. WHAT IS IT?

Drivers and SYS_INIT() functions run automatically before main(). Each declares a level (a boot phase) and a priority inside that level (0–99, lower runs first). A driver must run after everything it uses, e.g. a sensor after its I2C bus.

LevelWhenKernel services?Typical users (default priority)
EARLYVery first, before .bss cleanup is even finished on some archsNorare; SoC errata fixes
PRE_KERNEL_1No threads exist, no timer, interrupts not yet usableNo (no sleeping, no semaphores)clock control (30), GPIO (40), pinctrl, console UART (50)

2. STEP BY STEP: THE BOOT

  1. Reset handler → z_cstart(). Run EARLY, then PRE_KERNEL_1 in priority order (GPIO at 40 before UART at 50), then PRE_KERNEL_2.
  2. Prepare the main and idle threads, switch to main.
  3. Main thread runs POST_KERNEL (I2C 50 → regulator 75 → sensor 90), prints the boot banner, runs APPLICATION.
  4. Start static threads, call main().

Ties (same level and priority) run in link order, which you should treat as undefined. Since Zephyr 3.5, a build-time check (CONFIG_CHECK_INIT_PRIORITIES) compares devicetree dependencies with init order and fails the build if a device would init before one it depends on.

3. WORKED EXAMPLE

Your custom sensor driver uses POST_KERNEL, 40. The I2C bus is POST_KERNEL, 50. Sensor init runs first; i2c_is_ready_dt() is false (bus init has not run) → sensor init returns -ENODEV → device_is_ready(sensor) stays false forever. The build check catches it: it reports that the sensor node is initialised before its dependency, the I2C controller, with the two level+priority pairs. Fix: use CONFIG_SENSOR_INIT_PRIORITY (90). Try it in the Init Order tab.

static int board_power_init(void)          // SYS_INIT: not tied to a device
{
    return gpio_pin_configure_dt(&pwr_en, GPIO_OUTPUT_ACTIVE); // turn on sensor rail
}
SYS_INIT(board_power_init, POST_KERNEL, 60); // after GPIO (PRE_KERNEL_1), before sensors (90)
k_msleep(10) inside a PRE_KERNEL_1 init function (e.g. waiting for a PHY reset). The system timer is not running and there is no thread to put to sleep: depending on version you get an assert or a hang at boot before any log appears. Use k_busy_wait() in PRE_KERNEL, or move the device to POST_KERNEL.
Zephyr runs device and SYS_INIT functions in levels: PRE_KERNEL_1 and 2 without kernel services, POST_KERNEL once the kernel runs, then APPLICATION before main, and by priority 0 to 99 within a level. A device must initialise after its dependencies, so buses default to 50 and sensors to 90 in POST_KERNEL. If a dependency comes later, init fails and device_is_ready stays false; the CHECK_INIT_PRIORITIES build step now catches this from devicetree.

{
    switch (evt->type) {

        ring_buf_put(&rx_rb, evt->data.rx.buf + evt->data.rx.offset, evt->data.rx.len);

        break;

Worked number: at 115 200 baud with 8N1, one byte = 10 bits → 11 520 bytes/s → one byte every 86.8 µs. A 64-byte buffer fills in 5.6 ms, so the next buffer must be supplied within that time; the BUF_REQUEST event arrives early to give you that margin.

Async UART with only one buffer and no UART_RX_BUF_REQUEST handling: reception stops after the first 64 bytes (UART_RX_DISABLED), and the next bytes are lost. Always supply a second buffer.
All Zephyr peripheral APIs have _dt variants that take a spec struct built from devicetree. GPIO calls work in logical levels, so ACTIVE_LOW is handled for you, and GPIO callbacks run in ISR context. I2C and SPI calls are blocking transfers that use the controller's DMA and a semaphore underneath. UART has polling, interrupt-driven and async APIs; async uses DMA with double buffering via the RX_BUF_REQUEST event and is the right choice for high data rates.

23. The sensor API: fetch, channel_get, sensor_value, triggers

▶

1. WHAT IS IT?

One generic API for hundreds of sensors. You ask the driver to fetch a sample (talks to the chip) and then get channels (converts the stored raw data to SI units). The same code reads a BME280 or an SHT4x.

Channel
A quantity: SENSOR_CHAN_AMBIENT_TEMP (°C), SENSOR_CHAN_PRESS (kPa), SENSOR_CHAN_HUMIDITY (%), SENSOR_CHAN_ACCEL_XYZ (m/s², 3 values), SENSOR_CHAN_GYRO_XYZ (rad/s).
struct sensor_value
{ int32_t val1; int32_t val2; } = integer part + millionths. No floats needed in the driver.
Trigger
A callback when the sensor raises an interrupt (data ready, motion). Delivered in a thread (global or own thread mode, chosen per driver in Kconfig).
const struct device *const bme = DEVICE_DT_GET_ONE(bosch_bme280); // the one okay instance
struct sensor_value t, p;

if (!device_is_ready(bme)) { return; }
sensor_sample_fetch(bme);                              // I2C transfer(s): reads all channels once
sensor_channel_get(bme, SENSOR_CHAN_AMBIENT_TEMP, &t); // no bus access: converts cached data
sensor_channel_get(bme, SENSOR_CHAN_PRESS, &p);
printk("T=%d.%06d C  P=%d.%06d kPa\n", t.val1, t.val2, p.val1, p.val2);

WORKED EXAMPLE: DECODING sensor_value

23.45 °C → val1 = 23, val2 = 450000. −0.5 °C → val1 = 0, val2 = −500000 (both parts carry the sign). sensor_value_to_double(&t) = val1 + val2/1e6. 101.325 kPa → {101, 325000}. Printing with %d.%06d breaks for negatives between −1 and 0 (prints 0.-500000); handle the sign yourself or use the double helper with CONFIG_CBPRINTF_FP_SUPPORT.

Zephyr 3.6+ also has a newer read/decode API (sensor_read() with RTIO) for streaming and FIFO-capable sensors; fetch/get remains the common one in courses.

Calling sensor_channel_get without a fetch first: you get the previous sample (or zeros), with no error. And fetching from an ISR: fetch does bus transfers and blocks → assert.
The sensor API separates sensor_sample_fetch, which does the bus transfer and caches raw data, from sensor_channel_get, which converts it to SI units in a sensor_value of integer plus millionths. Drivers are selected by devicetree and Kconfig, triggers give data-ready or motion callbacks in thread context, and the newer read/decode API with RTIO exists for streaming.

24. Logging: LOG_MODULE_REGISTER, levels, deferred vs immediate, backends, dropped messages

▶

1. WHAT IS IT?

The logging subsystem prints timestamped, levelled messages per module, and can remove them entirely at compile time. By default it is deferred: the calling thread only stores the message in a buffer (fast), and a low-priority logging thread formats and sends it later.

#include <zephyr/logging/log.h>
LOG_MODULE_REGISTER(imu, CONFIG_IMU_LOG_LEVEL);  // once per module, in ONE .c file
/* other files of the same module: LOG_MODULE_DECLARE(imu, CONFIG_IMU_LOG_LEVEL); */

LOG_ERR("read failed: %d", ret);                 // level 1
LOG_WRN("retry %d", n);                          // level 2
LOG_INF("ready, id=0x%02x", id);                 // level 3
LOG_DBG("raw %d %d %d", x, y, z);                // level 4 — compiled out unless level ≥ 4
LOG_HEXDUMP_DBG(buf, 16, "frame");

Output: [00:00:01.234,567] <inf> imu: ready, id=0x24. Debug messages also show the function: <dbg> imu: imu_poll: raw 12 -3 1001.

Level
0 = none, 1 = error, 2 = warning, 3 = info, 4 = debug. CONFIG_LOG_DEFAULT_LEVEL (default 3) applies to modules registered without a level. A message is compiled in only if its level ≤ the module's level.
Deferred mode
CONFIG_LOG_MODE_DEFERRED (default). Arguments are packaged into a ring buffer of CONFIG_LOG_BUFFER_SIZE bytes (default 1024). Safe from ISRs, cheap for the caller.
Immediate mode
CONFIG_LOG_MODE_IMMEDIATE. Formats and sends in the caller's context. Messages never drop and appear before a crash, but every LOG call costs the full UART time and uses the caller's stack for formatting.
Minimal mode
CONFIG_LOG_MODE_MINIMAL: maps LOG to printk; smallest footprint.
Backend
Where messages go: UART (CONFIG_LOG_BACKEND_UART), SEGGER RTT (CONFIG_LOG_BACKEND_RTT, much faster over the debug probe), shell, network, file system.

2. WORKED EXAMPLE: WHY MESSAGES GET DROPPED

  1. A thread logs one INF line at 1 kHz. Each message is about 40 bytes in the buffer (header + timestamp + arguments).
  2. Formatted text is about 50 characters. At 115 200 baud the UART sends 11 520 chars/s → about 230 messages/s maximum.
  3. Incoming 1000/s, outgoing 230/s → the buffer gains 770 × 40 B = 30.8 KB per second. A 1 KB buffer is full after about 33 ms.
  4. With CONFIG_LOG_MODE_OVERFLOW=y (default) the oldest messages are overwritten; the log thread then prints --- 112 messages dropped ---.

Fixes in order of effect: log less (rate-limit, LOG_DBG off in production), switch to RTT (≈ 1 MB/s), increase CONFIG_LOG_BUFFER_SIZE for short bursts, and make sure the logging thread is not starved by higher-priority busy threads.

✖ WRONG — two registrations
/* a.c */ LOG_MODULE_REGISTER(imu);
/* b.c */ LOG_MODULE_REGISTER(imu);
// link error: multiple definition of
// log_const_imu
✔ RIGHT
/* a.c */ LOG_MODULE_REGISTER(imu, LOG_LEVEL_INF);
/* b.c */ LOG_MODULE_DECLARE(imu, LOG_LEVEL_INF);
Each source module registers once with LOG_MODULE_REGISTER and a level; messages above the level are compiled out. In the default deferred mode, LOG calls just package arguments into a ring buffer and a low-priority thread formats and outputs them to backends like UART or RTT, which keeps the caller fast and ISR-safe. If production rate exceeds backend throughput, the buffer overflows and you see "messages dropped"; immediate mode never drops but costs time and stack in the caller.

25. The shell: an interactive command line on the device

▶

1. WHAT IS IT?

The shell gives you a prompt on the UART (or RTT, USB, BLE) where you type commands with tab completion and history. Built-in commands inspect the running system; you can add your own in a few lines. It is the fastest way to test hardware without reflashing.

26. Settings and NVS: storing values across reboots

▶

1. WHAT IS IT?

NVS (Non-Volatile Storage) is a small key-value store in internal flash: numeric IDs map to byte blobs. Settings is a higher layer with string keys ("app/threshold") and handlers per subsystem; Bluetooth uses it to keep bonding keys. Settings can store into NVS, ZMS (Zephyr Memory Storage, 3.7+), FCB or a file.

Flash sector / page
The smallest erasable unit: 4096 bytes on nRF52840. Flash bits can only go 1 → 0 by writing; going back to 1 requires erasing a whole sector.
Partition
A named flash range in devicetree (storage_partition, e.g. 32 KB at 0xF8000).
ATE
Allocation Table Entry: NVS writes data from the start of a sector and small 8-byte entries (id, offset, length, CRC) from the end.
Garbage collection
When the current sector is full, NVS copies the latest valid entries into a fresh sector and erases the old one. This spreads wear (wear levelling).

2. STEP BY STEP: WRITING A VALUE WITH NVS

  1. nvs_mount() scans sectors to find the newest entries.
  2. nvs_write(&fs, 1, &thr, 4): if the latest value for ID 1 equals the new one, nothing is written (saves wear).
  3. Otherwise append 4 data bytes after the last data, and an 8-byte ATE before the previous ATE.
  4. Old copies of ID 1 stay in flash but are now stale; GC drops them later.

3. WORKED EXAMPLE: HOW LONG WILL FLASH LAST?

nRF52840 flash endurance: 10 000 erase cycles per sector. Partition = 8 sectors × 4096 B. Each write of a 4-byte value uses 4 (data, padded to 8) + 8 (ATE) = 16 bytes. One sector holds about 4096 / 16 ≈ 250 writes (a bit less after headers). Total writes before wear-out ≈ 8 × 250 × 10 000 = 20 million. Saving once a minute: 20 000 000 / (60 × 24 × 365) ≈ 38 years. Saving every 10 ms: about 2.3 days. That is why you never save on every sensor sample.

/* Settings: string keys, a handler loads values at boot */
static uint32_t threshold = 100;
static int app_set(const char *name, size_t len, settings_read_cb read_cb, void *cb_arg)
{
    if (!strcmp(name, "thr") && len == sizeof(threshold)) {   // key "app/thr"
        return read_cb(cb_arg, &threshold, sizeof(threshold)) < 0 ? -EIO : 0;
    }
    return -ENOENT;
}
SETTINGS_STATIC_HANDLER_DEFINE(app, "app", NULL, app_set, NULL, NULL);

settings_subsys_init();
settings_load();                                     // calls app_set for every stored "app/*"
settings_save_one("app/thr", &threshold, sizeof(threshold));
The storage partition overlaps the application or MCUboot's slot 1. A DFU then erases your settings, or worse, a settings write corrupts the new image. Check partitions in zephyr.dts (or NCS Partition Manager's partitions.yml).
NVS is a log-structured key-value store in internal flash with numeric IDs; it appends data and 8-byte entries, skips unchanged writes, and garbage-collects by copying live entries to a fresh sector, which levels wear. The settings subsystem adds string keys and per-subsystem handlers on top, with NVS or ZMS as backends. I estimate lifetime as sectors times entries per sector times endurance divided by write rate, and save on change, not periodically.

27. Power management: system PM states and device (runtime) PM

▶

1. WHAT IS IT?

Two separate mechanisms. System PM: when all threads are idle, the idle thread picks a low-power CPU/SoC state based on how long until the next timeout. Device PM: each peripheral can be suspended when not in use, either explicitly or automatically by reference counting (runtime PM).

PM state
PM_STATE_RUNTIME_IDLE, SUSPEND_TO_IDLE, STANDBY, SUSPEND_TO_RAM, SUSPEND_TO_DISK, SOFT_OFF. Which exist is SoC-specific and declared in devicetree with min-residency-us and exit-latency-us.
Residency
The minimum time you must stay in a state for it to save energy (entering and leaving costs energy and time).
Runtime PM
pm_device_runtime_get(dev) increments a usage count and resumes the device; pm_device_runtime_put(dev) decrements and suspends at zero.

2. STEP BY STEP: WHAT THE IDLE THREAD DOES

  1. No thread is ready → the idle thread runs.
  2. It asks the kernel: ticks until the next timeout? Say 800 ms.
  3. The PM policy chooses the deepest state whose min-residency-us ≤ 800 ms and that is not locked by pm_policy_state_lock_get().
  4. It suspends devices if needed, programs the wake-up timer, enters the state (on nRF52 "System ON idle" is just WFI with RTC running, ~1.5–3 µA).
  5. An interrupt wakes it; it restores, the kernel announces elapsed ticks, threads run.

On nRF52 most of the saving comes from tickless idle + WFI plus turning peripherals off; System OFF (≈ 0.4 µA) is a reset-on-wake state you enter explicitly with sys_poweroff().

3. WORKED EXAMPLE: AVERAGE CURRENT

Sensor node wakes every 1 s, active 5 ms at 4 mA (CPU + sensor), sleeps 995 ms at 3 µA. Average = (5 × 4000 µA + 995 × 3 µA) / 1000 = (20 000 + 2 985) / 1000 ≈ 23 µA. On a 220 mAh coin cell: 220 000 / 23 ≈ 9 565 h ≈ 1.1 years. Leaving the UART console enabled (≈ 0.5–1 mA on nRF52 because its clock stays requested) would cut that to under a month. Runtime PM on the UART fixes it.

static int my_pm_action(const struct device *dev, enum pm_device_action action)
{
    switch (action) {
    case PM_DEVICE_ACTION_SUSPEND: sensor_power_off(dev); return 0;
    case PM_DEVICE_ACTION_RESUME:  return sensor_power_on(dev);
    default: return -ENOTSUP;
    }
}
PM_DEVICE_DT_INST_DEFINE(0, my_pm_action);   // pass PM_DEVICE_DT_INST_GET(0) to DEVICE_DT_INST_DEFINE

pm_device_runtime_get(dev);   // count 0→1: RESUME
read_it(dev);
pm_device_runtime_put(dev);   // count 1→0: SUSPEND
A peripheral left active (UART RX enabled, a GPIO with a pull resistor fighting an external level, a clock request held) keeps the chip in a high-current state even though the CPU sleeps. Measure with a power profiler; disable unused console/logging in the production build.
Zephyr separates system PM, where the idle thread picks the deepest allowed state whose minimum residency fits the time to the next timeout, from device PM, where drivers implement suspend and resume actions, ideally driven by runtime PM reference counts. States and their residency and latency come from devicetree, and policy locks prevent deep states during critical activity. In practice most savings come from tickless idle plus turning off peripherals like the UART.

28. MCUboot and DFU: slots, signing, test/confirm, mcumgr/SMP

▶

1. WHAT IS IT?

MCUboot is a secure bootloader. It runs first at every reset, checks the application's signature, and can swap in a new image. DFU (Device Firmware Update) is how the new image gets onto the device; Zephyr's standard tool is mcumgr, which speaks the SMP protocol (Simple Management Protocol) over UART, BLE or UDP. Firmware-update theory in depth: page 17.

nRF52840 flash (1 MB), typical layout from devicetree fixed-partitions

0x0C000 ├──────────────────┤ slot0_partition 472 KB  running app (primary)
0x82000 ├──────────────────┤ slot1_partition 472 KB  new image lands here (secondary)
0xF8000 ├──────────────────┤ storage_partition 32 KB settings / NVS
0x100000└──────────────────┘

2. STEP BY STEP: AN UPDATE WITH "TEST THEN CONFIRM"

  1. Build with MCUboot: west build -b nrf52840dk/nrf52840 --sysbuild app -- -DSB_CONFIG_BOOTLOADER_MCUBOOT=y. Sysbuild builds MCUboot and the app, and signs the app → zephyr.signed.bin (512-byte header + image + TLV trailer with hash and signature).
  2. Upload to slot 1 over serial: mcumgr --conntype serial --connstring dev=/dev/ttyACM0,baud=115200 image upload zephyr.signed.bin (or smpmgr, or the nRF Device Manager phone app over BLE).
  3. image list shows both images and their hashes. image test <hash> marks slot 1 as "pending: try once".
  4. reset. MCUboot sees the pending flag, verifies the signature of slot 1, and swaps slot 0 ↔ slot 1 (using scratch or move algorithm). It boots the new image.
  5. The new app runs its self-test and calls boot_write_img_confirmed() (or you send image confirm).
  6. If it is not confirmed and the device resets (crash, watchdog, or just a reboot), MCUboot swaps back to the old image. This is the safety net.

3. WORKED NUMBERS

Uploading a 300 KB image over 115 200 baud serial: raw throughput 11.5 KB/s; SMP adds base64 and framing (~35 % overhead) → about 7.5 KB/s → ≈ 40 s. Over BLE with 2M PHY and data-length extension, 20–60 KB/s is realistic. The swap itself: 472 KB slot / 4 KB sector = 118 sectors, each erased and written twice (swap) → several seconds of bootloader time. Overwrite-only mode is faster but has no rollback.

Shipping with MCUboot's default development signing key (root-rsa-2048.pem / root-ec-p256.pem, published in the repo; the build warns about it). Anyone can sign an image your devices will accept. Generate your own key with imgtool keygen, keep it off the build server, and set SB_CONFIG_BOOT_SIGNATURE_KEY_FILE.
MCUboot verifies the signed application in the primary slot at every boot and installs updates from the secondary slot. With mcumgr over SMP I upload to slot 1, mark it test, and reset; MCUboot swaps it in, and if the new firmware does not confirm itself with boot_write_img_confirmed before the next reset, MCUboot reverts. 29. Networking and Bluetooth stacks: an overview

▶

1. NETWORKING

Zephyr has its own IPv4/IPv6 stack with TCP and UDP, a BSD sockets API (zsock_socket, or plain socket() with CONFIG_POSIX_API), and link layers for Ethernet, Wi-Fi, IEEE 802.15.4 (Thread via OpenThread, 6LoWPAN), PPP and cellular modems. On top: MQTT, CoAP, LwM2M, HTTP client/server, DNS, SNTP, TLS via mbedTLS (or PSA crypto with TF-M). Some modems (nRF91, ESP-AT) use offloaded sockets: the socket calls go to the modem's own stack.

  app ── sockets (zsock_*) ── TCP/UDP ── IPv4/IPv6 ── net_if ── L2: Ethernet | Wi-Fi | 802.15.4 | PPP
                                               net_buf pools carry packets with no copying
net_buf
Zephyr's packet buffer: fixed-size fragments from pools, reference counted, chained. Sizes set with CONFIG_NET_BUF_RX_COUNT / TX_COUNT. Running out = dropped packets.
net_mgmt
Event system: subscribe to "interface up", "IPv4 address added", "Wi-Fi connected".

2. BLUETOOTH

The stack is split into the host (GAP, GATT, L2CAP, SMP pairing, ATT) and the controller (link layer and radio). They talk over HCI (Host Controller Interface). Zephyr has its own open-source link layer; Nordic's NCS normally uses its SoftDevice Controller. On the dual-core nRF5340 the host runs on the application core and the controller on the network core (hci_ipc image, built automatically with sysbuild).

3. WORKED NUMBERS

Connection interval 30 ms, one 20-byte notification per event (default ATT MTU 23 → 20 B payload): 20 / 0.030 = 667 B/s. With data length extension (251-byte PDUs), MTU 247 and several packets per event at 2M PHY, 100+ KB/s is achievable. Bluetooth host threads (RX, TX) and the system work queue must have enough stack; BLE bugs often show up as stack overflows in BT RX.

Sending notifications from a loop without flow control: bt_gatt_notify returns -ENOMEM when TX buffers run out. Ignoring that return value loses data silently. Check it and back off, or use the callback variant to pace sends.
Zephyr's native IP stack offers BSD sockets over Ethernet, Wi-Fi, 802.15.4/Thread and PPP, with MQTT, CoAP, LwM2M and TLS on top, using net_buf pools for zero-copy packets; cellular modules may offload sockets. The Bluetooth stack has a host with GAP and GATT and a controller connected over HCI, which can be on another core; GATT services are defined statically with BT_GATT_SERVICE_DEFINE.

30. Userspace and memory domains: isolating threads with the MPU

▶

1. WHAT IS IT?

By default every Zephyr thread runs privileged and can touch all memory. With CONFIG_USERSPACE=y you can start threads in user mode: the CPU's MPU (Memory Protection Unit) then lets them access only their own stack and the memory partitions you grant, and they can call the kernel only through checked system calls. A bug in a user thread (or a hacked parser) cannot corrupt the kernel or other threads.

MPU
Hardware that checks each memory access against a small set of regions (8 on the nRF52840's Cortex-M4; 8 or 16 on ARMv8-M). A violation raises a MemManage fault.
Memory partition
A named range (start, size, attributes) defined with K_APPMEM_PARTITION_DEFINE; variables are placed in it with K_APP_DMEM(part) / K_APP_BMEM(part).
Memory domain
A set of partitions; threads in the domain may access them.
System call
A kernel API marked __syscall. From user mode it traps into the kernel (SVC), which verifies arguments (is this pointer in memory the caller may access? does the caller have permission on this kernel object?) before calling the real implementation z_impl_*.

STEP BY STEP

K_APPMEM_PARTITION_DEFINE(parser_part);
K_APP_BMEM(parser_part) static uint8_t parse_buf[512];   // only this partition is granted
static struct k_mem_domain parser_dom;

void start_parser(void)
{
    struct k_mem_partition *parts[] = { &parser_part };
    k_mem_domain_init(&parser_dom, ARRAY_SIZE(parts), parts);
    k_thread_create(&pth, pstack, K_THREAD_STACK_SIZEOF(pstack), parser_entry,
                    NULL, NULL, NULL, 7, K_USER, K_FOREVER);   // K_USER, not started yet
    k_mem_domain_add_thread(&parser_dom, &pth);
    k_object_access_grant(&rx_msgq, &pth);                   // may use this msgq via syscalls
    k_thread_start(&pth);
}

WORKED EXAMPLE: ARMv7-M ALIGNMENT COST

On ARMv7-M (Cortex-M3/M4) an MPU region's size must be a power of two ≥ 32 bytes, and its base aligned to its size. A 1000-byte partition must become a 1024-byte region aligned to 1024. A 1100-byte one becomes 2048 bytes: 948 bytes wasted. User thread stacks are padded the same way. ARMv8-M (Cortex-M33) only needs 32-byte granularity, so the waste disappears.

A user thread calls an API on a kernel object it was not granted → >>> ZEPHYR FATAL ERROR 3: Kernel oops with a log like "thread … does not have permission on k_msgq …". It is a deliberate kill of the offending thread, not a kernel bug: grant the object.
With CONFIG_USERSPACE, threads created with K_USER run unprivileged and the MPU restricts them to their stack plus partitions in their memory domain. They reach the kernel only through system calls, where the kernel validates pointers and object permissions before calling the implementation, so a faulty thread is killed with a kernel oops instead of corrupting others. On ARMv7-M the power-of-two MPU regions cost RAM to alignment; ARMv8-M avoids that.

31. Testing: ztest, twister, native_sim and QEMU

▶

1. WHAT IS IT?

ztest is Zephyr's unit-test framework (assert macros, suites). twister is the test runner that builds and runs many tests on many boards and collects results. native_sim is a "board" that compiles your Zephyr application into a normal Linux program, so tests run on your PC or CI server in seconds, no hardware needed.

#include <zephyr/ztest.h>
#include "ringbuf.h"

static struct rb rb;
static void before(void *f) { rb_init(&rb); }          // runs before EACH test

ZTEST(ringbuf, test_empty_on_init)
{
    zassert_true(rb_empty(&rb), "new buffer must be empty");
}
ZTEST(ringbuf, test_wraps)
{
    for (int i = 0; i < 20; i++) { rb_put(&rb, i); (void)rb_get(&rb); }
    rb_put(&rb, 42);
    zassert_equal(rb_get(&rb), 42, "value lost after wrap");
}
ZTEST_SUITE(ringbuf, NULL, NULL, before, NULL, NULL);   // (name, predicate, setup, before, after, teardown)

tests:
  lib.ringbuf:
    tags: ringbuf
    platform_allow: [native_sim, nrf52840dk/nrf52840]

west twister -T tests/ringbuf -p native_sim          # build + run on the PC

                                                     # flash real boards, parse UART output

STEP BY STEP: WHAT TWISTER DOES

  1. Finds every testcase.yaml/sample.yaml under the given path.
  2. Filters by platform, tags and Kconfig/DT requirements (depends_on: i2c).
  3. Builds each combination in parallel into twister-out/.
  4. Runs them (native executable, QEMU, or real hardware), parses ztest's output (PROJECT EXECUTION SUCCESSFUL), and writes JSON/JUnit reports.

For drivers, Zephyr has emulators (emul): fake I2C/SPI devices on native_sim that respond like a real chip, and the FFF (Fake Function Framework) for mocking functions.

Tests that pass on native_sim but fail on hardware: native_sim is 64-bit by default (pointer size 8, long 8 bytes), has no real interrupts latency and runs "infinitely fast" between kernel calls. Keep some tests on real boards or QEMU Cortex-M (qemu_cortex_m3) in CI.
I write unit tests with ztest suites and zassert macros, describe them in testcase.yaml, and run them with twister, which builds every test for every allowed platform and parses results into reports. native_sim builds Zephyr as a Linux executable so CI runs fast without hardware, emulators fake I2C and SPI devices for driver tests, and twister's device-testing mode runs the same tests on real boards.

32. Debugging: west debug, thread-aware GDB, asserts, fatal errors, coredumps

▶

1. THE TOOLS, ONE BY ONE

west debug
Flashes, starts the runner's GDB server (J-Link GDB server, OpenOCD, pyOCD) and opens GDB on zephyr.elf. west debugserver starts only the server (for an IDE); west attach connects without flashing.
Thread awareness
CONFIG_DEBUG_THREAD_INFO=y exports kernel data so OpenOCD (rtos auto) or the J-Link Zephyr RTOS plug-in can list all threads and show each thread's call stack, not only the current one.
CONFIG_DEBUG_OPTIMIZATIONS
Builds with -Og so variables are not "optimized out".
__ASSERT
__ASSERT(cond, "msg %d", x) checks only when CONFIG_ASSERT=y. The kernel is full of them (e.g. "mutexes cannot be used inside ISRs"); enable it in every debug build.
Fatal error handler
On a fault, Zephyr prints registers and the reason, then calls k_sys_fatal_error_handler(reason, esf). The default halts (or reboots with CONFIG_RESET_ON_FATAL_ERROR); you can override it to log and reset.
Coredump
CONFIG_DEBUG_COREDUMP=y saves registers and selected memory on a crash (to the log or a flash partition). Later you load it into GDB with Zephyr's coredump GDB server script and inspect the crash as if live.

33. Board porting basics: the board directory (Hardware Model v2)

▶

1. WHAT IS IT?

A board in Zephyr is a folder that tells the build which SoC you use and how your PCB is wired. To support your own PCB you create one (in your app repo, not in zephyr/) and build with -b myboard plus -DBOARD_ROOT=. (or a module).

boards/acme/sensornode/            (Zephyr 3.7+ "HWMv2" layout)
├── board.yml                       name, vendor, which SoC(s), revisions
├── Kconfig.sensornode              selects the SoC: select SOC_NRF52840_QIAA
├── Kconfig.defconfig               board-specific DEFAULTS (default y if ...)
├── sensornode_defconfig            options always on: CONFIG_GPIO=y, CONFIG_ARM_MPU=y ...
├── sensornode.dts                  the devicetree: #include SoC dtsi, LEDs, buses, partitions
├── sensornode-pinctrl.dtsi         pin mux: which pins each peripheral uses
├── board.cmake                     flash/debug runners: include(${ZEPHYR_BASE}/boards/common/jlink.board.cmake)
└── sensornode.yaml                 metadata for twister (ram, flash, supported features)

In the older model (Zephyr ≤ 3.6), the folder was boards/arm/<board>/ and the SoC was selected in Kconfig.board; the rest (_defconfig, .dts, board.cmake) is the same idea. Interviewers may say "Kconfig.board".

STEP BY STEP: PORTING FROM A DEV KIT

  1. Copy the closest existing board (here nrf52840dk) into your board root and rename files and the board name.
  2. Edit the .dts: delete what your PCB lacks (Arduino header, extra LEDs), set your LED/button pins, enable the buses you wired and add your sensors under them.
  3. Edit the pinctrl file: e.g. I2C0 on P0.04 (SDA) / P0.05 (SCL) instead of P0.26/27.
  4. Edit the flash partitions if you use MCUboot or need a different storage size.
  5. Check clocks: does your PCB have the 32.768 kHz crystal? If not, select the RC oscillator in Kconfig (CONFIG_CLOCK_CONTROL_NRF_K32SRC_RC=y), or the kernel timer will never start.
  6. Build blinky and hello_world, then samples/drivers/… for each peripheral.
Board has no LFXO crystal but the copied config still requests it: the board hangs at boot inside clock start-up, before any printk. Symptom: no output at all, debugger shows a loop waiting for LFCLKSTARTED.
A Zephyr board is a directory with board.yml naming the SoC, Kconfig files that select the SoC and set board defaults, a defconfig, the board DTS with pinctrl and flash partitions, and board.cmake for runners. I port by copying the nearest dev-kit board into my own board root, changing pins, buses, partitions and clock sources to match the schematic, and bringing peripherals up one sample at a time.

34. Sysbuild: building several images (bootloader, app, network core) together

▶

1. WHAT IS IT?

Sysbuild is a higher-level CMake build that builds multiple Zephyr images in one command and wires them together: MCUboot + the application, or the nRF5340's application-core firmware + network-core Bluetooth controller. Before sysbuild, you had to build MCUboot separately and keep keys and partitions consistent by hand.

STEP BY STEP

  1. west build -b nrf52840dk/nrf52840 --sysbuild my-app (default in NCS 2.7+; in upstream you add --sysbuild or set it as default with west config build.sysbuild True).
  2. Sysbuild reads sysbuild.conf in your app (Kconfig with SB_CONFIG_ prefix), e.g. SB_CONFIG_BOOTLOADER_MCUBOOT=y.
  3. It adds the images, here mcuboot and your app, as separate CMake sub-builds, each with its own prj.conf/overlays. Per-image files go in sysbuild/mcuboot.conf and sysbuild/mcuboot.overlay.
  4. It passes shared settings: the signing key to MCUboot and to the app's signing step, the same flash partition layout.
  5. Output: build/mcuboot/zephyr/zephyr.hex, build/my-app/zephyr/zephyr.signed.bin, and (NCS) a merged.hex. west flash programs all images.
# my-app/sysbuild.conf
SB_CONFIG_BOOTLOADER_MCUBOOT=y
SB_CONFIG_BOOT_SIGNATURE_TYPE_ECDSA_P256=y
SB_CONFIG_BOOT_SIGNATURE_KEY_FILE="${APP_DIR}/keys/prod-p256.pem"
Putting CONFIG_BOOTLOADER_MCUBOOT=y in the app's prj.conf but building without sysbuild: the app is linked for slot 0 at 0xC000, but nothing is at 0x0000, so the chip boots into erased flash and does nothing. Enable MCUboot through sysbuild so both images agree.
Sysbuild is Zephyr's multi-image build. One west build configures the bootloader, the application and other cores' images as separate Zephyr builds, with SB_CONFIG options in sysbuild.conf and per-image config under the sysbuild folder, and keeps shared things like signing keys and partitions consistent; west flash then programs all of them.

NEVER DO THIS
  • Call k_mutex_lock, k_msleep, I2C/SPI or sensor_sample_fetch from an ISR, GPIO callback or k_timer expiry function.
  • Busy-loop in a cooperative (negative priority) thread, or "yield" to let lower priorities run.
  • Block for long in a system work-queue handler.
  • Skip device_is_ready() / gpio_is_ready_dt().
  • Edit files inside zephyr/boards; use overlays and your own board root.
  • Add app.overlay when boards/<board>.overlay exists and expect both to apply.
  • Use k_sem as a lock between priorities (no inheritance).
  • Put stack or freed memory into a k_fifo.
  • Call k_msleep in a PRE_KERNEL init function.
  • Ship with MCUboot's default signing key, or forget boot_write_img_confirmed().
  • Change settings in menuconfig and forget to copy them into prj.conf.
60-SECOND REVISION
  1. Zephyr: Apache-2.0, Linux Foundation, vendor-neutral RTOS + drivers + stacks; NCS is built on it.
  2. west fetches repos from west.yml and wraps build/flash/debug.
  3. Build = devicetree → Kconfig → compile → 2-stage link. Check zephyr.dts and .config.
  4. Kconfig: defconfig → prj.conf → fragments; depends/select/default; unmet deps abort the build.
  5. Devicetree: SoC dtsi → board dts → overlays, last wins; labels, aliases, chosen, status, compatible.
  6. Bindings (YAML) give properties types; no binding = no macros.
  7. boards/<board>.overlay hides app.overlay; new overlay → pristine build.
  8. DT macros are compile-time token pasting; spec structs bundle device + pin/addr + flags.
  9. Missing alias = compile error; disabled/no driver = link error; init failed = device_is_ready false.
  10. struct device = config (flash) + data (RAM) + API table; DEVICE_DT_INST_DEFINE per okay node.
  11. Init: PRE_KERNEL_1/2 (no kernel), POST_KERNEL, APPLICATION; priority 0–99; buses 50, sensors 90.
  12. Priorities: negative cooperative, ≥0 preemptible, lower = higher.
  13. k_yield = equal/higher only; k_sleep lets anyone run.
  14. ISRs: IRQ_CONNECT at build time; never block; defer with k_work.
  15. System work queue: coop −1, 1 KB stack, shared — keep handlers short.
  16. k_work_reschedule = debounce; k_timer expiry runs in ISR.
  17. Mutex has owner + priority inheritance; semaphore doesn't.
  18. msgq copies; fifo passes pointers; k_poll waits on many.
  19. Thread analyzer + MPU stack guard; reason 2 = stack overflow.
  20. Logging deferred by default: buffer can drop; LOG_PANIC on crash.
  21. MCUboot: slot0/slot1, test then confirm, else revert; mcumgr over SMP.
  22. Test with ztest + twister on native_sim; debug with west debug + thread awareness.
