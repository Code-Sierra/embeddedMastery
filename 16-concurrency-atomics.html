1 What problem does this topic solve?

Your firmware is not one program running from top to bottom. Even on a tiny single-core microcontroller there are several independent flows of execution that run "at the same time" and look at the same memory:

  • The main loop (or several RTOS tasks), running your normal code.
  • Interrupt service routines (ISRs): functions the hardware calls by itself when an event happens (a UART byte arrived, a timer expired). An ISR can start between any two instructions of the main loop, without the main loop knowing.
  • DMA (Direct Memory Access) engines: small hardware units that copy data into RAM while the CPU does something else.
  • On bigger chips, other CPU cores running their own code at the same instant.

We call each of these a context. When two contexts touch the same variable, the result can depend on exactly when one of them interrupts the other. Most of the time the timing is "lucky" and everything works. Once in a while (one time in ten thousand, or once a week in the field) the timing is "unlucky" and a value is lost, torn in half or read too early. That is a race condition.

This topic is the toolbox for making shared data safe: knowing which operations the hardware does in one indivisible step (atomic), how to make bigger operations indivisible (critical sections, LDREX/STREX), and how to make sure one context sees another's writes in the right order (memory ordering, barriers).

Why interviewers love this topic: the bugs are real, rare and expensive, and the most common answer ("just make it volatile") is wrong. If you can explain why it is wrong, with instructions and numbers, you stand out immediately.

2 The physical picture: what is actually in the chip

To understand races you have to picture where a variable lives and how the CPU changes it. On a Cortex-M4 the CPU cannot do arithmetic directly on RAM. It must:

  1. Load the value from SRAM (Static RAM, the chip's main data memory at address 0x2000_0000) into a register (one of 16 tiny 32-bit storage slots inside the core: r0…r12, SP, LR, PC).
  2. Modify the register with an ALU (Arithmetic Logic Unit) instruction such as ADDS.
  3. Store the register back to SRAM.

This three-step pattern is called read-modify-write (RMW). The danger is the gap between step 1 and step 3: the "real" value in SRAM can change while the CPU is holding its own private copy in a register.

What an interrupt physically does. When USART1 receives a byte it raises its request line to the NVIC (Nested Vectored Interrupt Controller). If the interrupt is enabled and no mask blocks it, then at the next instruction boundary the core:

  1. Finishes (or abandons) the current instruction. Interrupts are taken between instructions.
  2. Pushes 8 registers (R0–R3, R12, LR, PC, xPSR = 8 words × 4 bytes = 32 bytes) onto the stack. This is the "exception frame". It takes 12 clock cycles on an M4 with zero-wait-state memory: 12 × 5.95 ns = 71 ns at 168 MHz.
  3. Reads the handler address from the vector table and jumps to USART1_IRQHandler.
  4. When the handler returns, pops the 8 registers back, so the main loop continues exactly where it stopped, with its old register values.

That last point is the root of every lost update: the main loop gets its old register copy back. If it was in the middle of a read-modify-write, it will now write back a value it computed from stale data.

A single-core Cortex-M4 has no data cache, and the core always sees its own memory accesses in program order. So for main ↔ ISR on one core the only problems are (1) atomicity (an ISR landing inside a multi-instruction operation) and (2) the compiler reordering or caching accesses. Hardware reordering only becomes a problem with a second observer: another core or a DMA engine (section 6).

4 One end-to-end worked example: the UART byte counter

The setup. An STM32F407 at 168 MHz receives a serial stream at 115 200 baud. The USART1 ISR puts each byte into a buffer and increments rx_count. The main loop, every 1 ms, takes one byte out and decrements rx_count.


        
STEP A — What the compiler really produces

        
The single C line rx_count--; becomes three machine instructions (arm-none-eabi-gcc -O2):

STEP C — How often does this happen? (the arithmetic)

        
    
          
  1. 115 200 baud with 8N1 framing = 10 bits per byte (1 start + 8 data + 1 stop). Bytes per second = 115 200 / 10 = 11 520. Time between bytes = 1 / 11 520 = 86.8 µs.
    2. 
          
  2. One CPU cycle at 168 MHz = 1 / 168 000 000 = 5.95 ns.
    3. 
          
  3. The danger window is from after the LDR until the STR: about 3 cycles = 3 × 5.95 ≈ 18 ns.
    4. 
          
  4. Chance that a given byte's interrupt lands inside one particular window = 18 ns / 86.8 µs ≈ 2.1 × 10⁻⁴, roughly 1 in 4 800.
    5. 
          
  5. main decrements 1 000 times per second, so expected lost updates = 1 000 × 2.1 × 10⁻⁴ ≈ 0.2 per second ≈ 750 per hour.
    6. 
        

        
So a 5-second bench test usually passes (expect about 1 hit, often 0), and the device drifts in the field. Add a printf to debug it and the timing changes, so the bug "disappears". That is why concurrency bugs are called heisenbugs.

        
STEP D — Why volatile does not help

        
rx_count in the code above is already volatile. volatile makes the compiler emit the LDR and the STR (instead of keeping the value in a register forever). It does not glue the three instructions together. The ISR can still land between them. The table in step B is exactly what happens with volatile.

        
Say it like this: "rx_count-- is a load, a subtract and a store. If the UART interrupt fires after the load, the ISR's increment is overwritten when main stores its stale value. volatile only forces the load and store to exist; it does not make them one operation. I would fix it with an atomic fetch-sub, a tiny interrupt-masked section, or better, by redesigning so each variable has only one writer."

      


      
      

        
5 The three ways to fix it (and what each costs)

        
FIX 1 — Make the RMW atomic with LDREX/STREX

        
LDREX loads the value and arms the exclusive monitor. STREX stores only if the monitor is still armed, and reports success (0) or failure (1). On Cortex-M, every exception entry and return disarms the monitor, so if the ISR ran in the middle, STREX fails and the loop simply tries again with the fresh value.

        

          
#WHOWHAT HAPPENSMAIN r2MONITORrx_count

          
            
1mainldrex r2,[r3]5Exclusive5

            
2HWIRQ entry → monitor cleared(5 saved)Open5

            
3ISRLDR / ADDS / STR: 5 → 6(5 saved)Open6

            
4mainsubs r2,r2,#14Open6

            
5mainstrex r1,r2,[r3] → monitor is Open → nothing stored, r1 = 14Open6

            
6maincbnz r1, retry → go back4Open6

            
7mainldrex → 6, subs → 5, strex succeeds, r1 = 05Open5 ✓

          
        

        
Cost: about 6–8 cycles when nobody interferes (≈ 40 ns). No interrupt latency added. Not available on Cortex-M0/M0+.

        
FIX 2 — Mask interrupts for 3 instructions (critical section)

        

        
While PRIMASK = 1, the UART interrupt stays pending in the NVIC; it is not lost, just delayed. Cost: the masked window is ~7 cycles = 42 ns. That 42 ns is added to the worst-case latency of every interrupt in the system, so it must stay tiny. Works on every Cortex-M, including M0.

        
FIX 3 — Redesign so nothing is shared for writing (the best fix)

        
Replace the shared counter with two indices: the ISR is the only writer of head, main is the only writer of tail. The number of bytes waiting is computed, never stored: count = head − tail. Each variable has one writer and is updated with a single aligned 32-bit store, which is atomic, so there is no read-modify-write race at all. This is the SPSC ring buffer (see the Ring tab).

        
Worked numbers: head = 1 000 007, tail = 1 000 002 → count = 5. Wrap-around: head = 0x0000_0002, tail = 0xFFFF_FFFE → unsigned subtraction 0x0000_0002 − 0xFFFF_FFFE = 0x0000_0004 = 4. Still correct, because unsigned arithmetic in C wraps modulo 2³².

Say it like this: "I first try to give every shared variable a single writer, like an SPSC ring with separate head and tail. If two contexts really must modify the same word, I use an LDREX/STREX loop, which retries automatically because exception entry clears the monitor. If several variables must change together, I use a short PRIMASK or BASEPRI section with save and restore, and I measure how long it is because it adds to every interrupt's latency."

      


      
      

        
6 When there are two cores: ordering, not just atomicity

        
On a phone SoC (Cortex-A53/A72, Apple M-series) or a dual-core MCU, a new problem appears. Each core has a store buffer: writes wait there for a while before reaching memory, so the core does not stall. On ARM the store buffer may release writes to memory in any order, and loads may also run early. So another core can see your second write before your first.

        


        

        
    
          
  1. Core 0 executes data = 42; the write goes into its store buffer.
    2. 
          
  2. Core 0 executes flag = 1; also into the store buffer.
    3. 
          
  3. On ARM the buffer may drain flag first (different address, no rule against it).
    4. 
          
  4. Core 1 reads flag = 1, then reads data, which is still 0 in memory.
    5. 
          
  5. Core 1 processes garbage. On x86 this specific outcome is impossible (its store buffer is FIFO), which is why such code passes CI on a PC and fails on the phone.
    6. 
        

        
The fix is a pair: a release on the writer (all earlier writes are visible before the flag) and an acquire on the reader (no later read happens before the flag is read). In C11: atomic_store_explicit(&flag, 1, memory_order_release) and atomic_load_explicit(&flag, memory_order_acquire). On ARMv8 they become STLR and LDAR; on ARMv7 a DMB before the store and after the load. A barrier on only one side is not enough: try Lab preset 11.

        
Say it like this: "Atomicity means a single operation is indivisible; ordering means another core sees my operations in the order I did them. On a weakly ordered ARM core, stores can become visible out of order and loads can run early, so publishing data with a flag needs a release store paired with an acquire load. x86 hides this bug because its store buffer is FIFO."

      


      
      

        
7 How all the pieces connect

        
Every concurrency question can be answered with the same four questions, in this order:

        
1. WHAT is shared?            one aligned word?  a counter?  a struct?  a stream of bytes?
2. WHO writes it?             one writer?  two writers?  hardware (status register)?
3. WHICH contexts?            main + ISR on ONE core?   two cores?   CPU + DMA?
4. WHAT must be guaranteed?   atomicity (no lost/torn value)?   ordering (data before flag)?

                    +-- one writer, one aligned word ----------> plain access + volatile/_Atomic
                    |
  shared data ------+-- RMW by several writers, one word -----> LDREX/STREX  (atomic_fetch_*)
                    |
                    +-- several words must change together ---> critical section (PRIMASK/BASEPRI)
                    |                                            or seqlock (ISR writes, main reads)
                    +-- stream of items --------------------------> SPSC ring buffer (no lock)
                    |
                    +-- long operation between tasks -----------> RTOS mutex (priority inheritance)

  plus, if a SECOND OBSERVER (other core / DMA) exists:
      ordering ---> release/acquire (DMB, STLR/LDAR);   caches ---> non-cacheable region or clean/invalidate

Lock-Free Ring Buffer & Memory-Order Drill

        
Push and pop through the two-phase protocol (write slot → publish head; read slot → release tail). Indices are free-running uint32_t counters; the slot is index & (N-1). Jump to the 232 wrap to see why that works only for power-of-two sizes, and flip the bug toggle to publish before writing.

      

      
HOW TO USE THIS LAB — 4 GUIDED EXPERIMENTS
    

  1. Fill it up. N = 4. Press Push five times. Notice count goes 1, 2, 3, 4 = FULL and the fifth push is dropped with overruns = 1. This shows the full test head − tail == N and that the producer never touches tail.
    2. 

  2. Half a push is invisible. Reset, press ① Write slot[head] only, then press Pop. Notice the consumer says empty: head has not moved, so the written slot is not yet published. This is why the slot is written before head.
    3. 

  3. Break the order. Turn Bug order: ON, press ① Publish head++, then ① Read slot on the consumer side. Notice the red STALE READ: the consumer trusted head before the data existed. This is what missing release ordering looks like.
    4. 

  4. Why power of two. Choose N = 5, press Jump near 2³² wrap, then Push three times without popping. Notice OVERWRITE: 0xFFFF_FFFF % 5 = 0 and 0 % 5 = 0. Repeat with N = 4: no error, the slots stay continuous.

NEVER DO THIS

          
    
            
  • __enable_irq() at the end of a critical section you did not open with interrupts enabled — save/restore PRIMASK.
    • 
            
  • Use volatile as a lock, a fence, or an atomic increment.
    • 
            
  • Spin on a lock in an ISR, or between tasks of different priority on a single core.
    • 
            
  • Call printf, malloc, strtok or an RTOS blocking call from an ISR.
    • 
            
  • Read a 64-bit counter updated by an ISR with a plain uint64_t load.
    • 
            
  • Let two producers share an SPSC queue.
    • 
            
  • TIMx->SR &= ~FLAG on rc_w0 flags: it can clear a flag that just arrived. Write TIMx->SR = ~FLAG.
    • 
            
  • Put memory accesses, a function call, or a breakpoint-stepped debugger between LDREX and STREX.
    • 
            
  • Take two locks in different orders in different places.
    • 
            
  • Test lock-free code only on x86 and ship it on ARM.

60-SECOND REVISION

          
    
            
  1. A race is a correctness bug from unlucky timing; a data race (two unordered conflicting non-atomic accesses) is undefined behaviour in C11.
    2. 
            
  2. Only aligned 8/16/32-bit loads and stores are atomic on Cortex-M. x++ is three instructions; 64-bit is two accesses.
    3. 
            
  3. Fix RMW with LDREX/STREX (v7-M+), a PRIMASK/BASEPRI critical section, or by redesigning so each variable has one writer.
    4. 
            
  4. Exception entry/exit clears the M-profile local monitor, so an ISR between LDREX and STREX makes the STREX fail and retry. Cortex-A kernels must CLREX on context switch.
    5. 
            
  5. volatile = "emit every access". _Atomic = indivisible + ordering you choose. Barrier = ordering only.
    6. 
            
  6. Release on the publishing store, acquire on the observing load. seq_cst only when you need store→load ordering (Dekker).
    7. 
            
  7. x86 only reorders store→load. ARM reorders everything: code that works on x86 can fail on ARM and Apple silicon.
    8. 
            
  8. DMB orders, DSB waits for completion, ISB refetches instructions.
    9. 
            
  9. SPSC: one writer per index, power-of-two size, free-running counters, write slot before publishing index.
    10. 
            
  10. No spinlocks on single core; mutex has an owner (and priority inheritance), a semaphore is a signal/counter.
    11. 
            
  11. ABA → tags, hazard pointers or LL/SC. Seqlock → writer never waits, reader retries; the writer must not be preemptible by the reader.
    12. 
            
  12. Test with stress + random ISR timing on target, ThreadSanitizer and model checkers on host.
    13.
