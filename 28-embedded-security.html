01

Security goals: the CIA triad (and friends)

BEGINNER▶
1. What is it?

Before you can protect a device you must say what "secure" means for it. The CIA triad is the standard checklist of three properties you might want to protect: Confidentiality, Integrity and Availability. Every security mechanism on the page (encryption, signatures, watchdogs, secure boot) exists to protect one or more of these.

2. Every term, defined
  • Confidentiality = only the right people can read the data. Example: the Wi-Fi password stored in flash must not be readable by someone who steals the device. Tool: encryption (scrambling data with a secret key so it looks like random noise without the key).
  • Integrity = data or code cannot be changed without the change being noticed. Example: the firmware image must not be modified by an attacker. Tools: hashes, MACs and digital signatures (explained in cards 04–05).
  • Availability = the device keeps doing its job. Example: a battery-swap station must keep accepting batteries even if someone floods its network port. Tools: watchdogs, rate limits, input validation, redundant paths.
  • Authenticity = you know who produced the data (the firmware really came from your company). Usually provided together with integrity by a signature.
  • Freshness / anti-replay = an old, genuine message cannot be re-sent later to trick you (e.g. replaying yesterday's "unlock" command). Tools: counters, nonces, timestamps.
  • Non-repudiation = the sender cannot later deny sending it. Only asymmetric signatures give this, because only one party holds the private key.
3. How to apply it, step by step
  1. List each asset (anything worth protecting): firmware, keys, user data, the physical actuator.
  2. For each asset ask the three questions: must it stay secret (C)? must it stay unmodified (I)? must it keep working (A)?
  3. Pick a mechanism per "yes". Do not encrypt things that only need integrity — it adds key-management cost with no benefit.
  4. Write down which mechanism protects which property; this table becomes part of your threat model (card 02).
4. Worked example — a smart door lock
AssetCIAMechanism
Firmware imagenice-to-havemustmustSigned image + secure boot; optional encryption to protect IP
Device private keymustmust—Stored in a secure element; never leaves it

Notice the third row: the classic wrong answer is "encrypt the unlock command". Encryption alone gives confidentiality; an attacker who records the encrypted "unlock" packet can simply replay it. You need integrity + freshness.

5. What goes wrong if you confuse them
/* WRONG: AES-CTR encrypt the command, no MAC, no counter */
ct = aes_ctr(key, nonce, "UNLOCK");   // attacker cannot read it…
// …but can (1) replay ct tomorrow, or (2) flip bits: CTR is malleable,
//   ct ^ ("UNLOCK" ^ "LOCK!!") decrypts to "LOCK!!" without knowing the key.

/* RIGHT: authenticated + fresh */
msg = counter(4 bytes, strictly increasing) || "UNLOCK";
tag = HMAC_SHA256(key, msg)[0..15];   // integrity + authenticity
// receiver: verify tag in constant time, then require counter > last_counter
Say it like this: "I start every design by listing assets and asking which of confidentiality, integrity and availability each one needs. For firmware, integrity and authenticity matter most, so I sign it; for keys, confidentiality, so they live in protected storage; for commands, integrity plus freshness, so I use a MAC with a counter. Encryption alone never gives integrity."

Threat modelling: assets, attack surfaces, attackers, STRIDE

BEGINNER▶
1. What is it?

A threat model is a written answer to four questions: What are we building? What can go wrong? What are we going to do about it? Did we do a good job? It stops you from spending effort on the wrong defences (for example, buying an expensive secure element while leaving a debug shell open on the UART).

2. Terms
  • Asset = something of value: firmware IP, cryptographic keys, user data, the ability to control an actuator, the vendor's reputation.
  • Attack surface = every place where outside input reaches the device: radio (BLE, Wi-Fi, LTE), wired buses (CAN, UART, USB, RS-485), debug ports (SWD/JTAG), external flash chips, the update channel, the cloud backend, and the physical enclosure.
  • Trust boundary = a line on your diagram where data goes from less-trusted to more-trusted (e.g. bytes arriving over BLE crossing into your parser). Every boundary needs validation.
  • Threat = a possible bad event; vulnerability = a weakness that lets it happen; risk = likelihood × impact.
  • STRIDE = Microsoft's checklist of six threat types (table below). Each one breaks one security property.
  • TARA = Threat Analysis and Risk Assessment, the name ISO/SAE 21434 (automotive) uses for this same activity.

4. Attacker capabilities — the four classes

The same device needs very different defences depending on where the attacker stands. Always say which class you are defending against:

  1. Remote: only reaches the device over a network (internet, cellular). Cheap to attack thousands of devices at once — the most dangerous for fleet-wide damage. Defences: TLS, input validation, secure update.
  2. Local / proximate: within radio range (BLE, Wi-Fi, NFC) or on the same bus (CAN in a vehicle). Defences: pairing, authenticated messages, bus message authentication (AUTOSAR SecOC).
  3. Physical, non-invasive: holds the device, can open the case, connect to SWD/UART, read an external flash chip, measure power consumption or inject voltage disturbances. Defences: debug lock, encrypted external storage, side-channel and fault countermeasures.
  4. Invasive: decapsulates the chip, uses microprobes or a focused-ion-beam workstation. Costly (lab equipment, expertise, time). Only certified secure elements / smart-card chips are designed to resist this.

Key principle — scalability of attack: an attack that needs physical access to each device is far less damaging than one that, once done on one device, works on all devices (a "class break"). Your goal is often: "physical access to one unit must not compromise the fleet". That is why per-device keys matter (Scenario 04).

5. Worked example — data-flow diagram of a battery-swap station controller

  1. Assets: firmware, AWS-IoT-style device certificate private key, relay control.

Say it like this: "I draw a data-flow diagram, mark the trust boundaries, and walk STRIDE over every arrow that crosses one. I classify attackers as remote, local, physical or invasive, and I make sure no single-device physical attack can scale to the whole fleet — which drives per-device keys and signed updates."

Symmetric encryption: AES and its modes (ECB, CBC, CTR, GCM)

BEGINNER▶
1. What is it?

Symmetric encryption uses the same secret key to encrypt and decrypt. AES (Advanced Encryption Standard, FIPS-197) is the block cipher almost every MCU uses. A block cipher on its own only scrambles exactly one 16-byte block. To encrypt a 100 KB firmware image you need a mode of operation — a recipe for chaining many block operations. The mode matters as much as the cipher: AES used in the wrong mode leaks your data.

2. Terms
  • Key: 128, 192 or 256 bits (16/24/32 bytes). AES-128 does 10 rounds, AES-256 does 14.
  • Block: always 128 bits = 16 bytes for AES, regardless of key size.
  • Plaintext (P) / ciphertext (C): data before / after encryption.
  • IV (Initialisation Vector) / nonce ("number used once"): a non-secret value that makes encrypting the same message twice give different ciphertexts. Rule: CBC needs an unpredictable IV; CTR/GCM need a never-repeated nonce under the same key.
  • Keystream: in CTR mode, the pseudo-random bytes produced by encrypting a counter; they are XORed (⊕, bitwise exclusive-OR) with the plaintext.
  • AEAD (Authenticated Encryption with Associated Data): a mode that encrypts and produces an authentication tag, e.g. AES-GCM, AES-CCM, ChaCha20-Poly1305.
3. The four modes, step by step
  1. ECB (Electronic Codebook): Ci = AESK(Pi). Each block encrypted independently. Identical plaintext blocks give identical ciphertext blocks, so patterns survive (open the AES Mode Lab tab — the padlock outline is still visible). Never use ECB for data longer than one block.
  2. CBC (Cipher Block Chaining): Ci = AESK(Pi ⊕ Ci−1), with C0 = IV. Each block depends on all previous ones, so patterns vanish. Needs padding (e.g. PKCS#7) to a multiple of 16 bytes. Encryption is sequential (cannot be parallelised). Without a MAC it is vulnerable to padding-oracle attacks (an attacker who can learn "padding was valid / invalid" can decrypt data).
  3. CTR (Counter): keystream block i = AESK(nonce ‖ counter i); C = P ⊕ keystream. Turns AES into a stream cipher: no padding, random access (decrypt block 500 directly — great for execute-in-place from encrypted external flash), parallelisable. Weakness: if a nonce is ever reused with the same key, the keystream repeats.
  4. GCM (Galois/Counter Mode): CTR encryption + a GHASH authentication tag (usually 16 bytes) over ciphertext and "associated data" (e.g. a packet header that is sent in clear but must not be modified). Standard nonce = 96 bits. This is what TLS 1.3 uses. Nonce reuse in GCM is worse than in CTR: it also leaks the authentication key H, letting the attacker forge tags.
4. Worked example — why CTR nonce reuse is a catastrophe

Suppose a device encrypts two log records with the same key and the same nonce (because the nonce counter lived in RAM and reset to 0 after a power cycle — see Scenario 03).

keystream K = 3A 91 C4 07 ...          (same both times, because nonce repeated)
P1 = "TEMP=21C"  = 54 45 4D 50 3D 32 31 43
P2 = "PIN=4711"  = 50 49 4E 3D 34 37 31 31
C1 = P1 ⊕ K ,  C2 = P2 ⊕ K
C1 ⊕ C2 = (P1 ⊕ K) ⊕ (P2 ⊕ K) = P1 ⊕ P2        // K cancels out!
P1 ⊕ P2 = 04 0C 03 6D 09 05 00 72
If the attacker knows/guesses P1 ("TEMP=21C" is a predictable format):
P2 = (C1 ⊕ C2) ⊕ P1 = "PIN=4711"               // secret recovered, key never touched

This is the "two-time pad" problem. The key was perfectly safe and the cipher was perfectly strong; the mode was misused.

5. Annotated code (mbedTLS-style GCM) — wrong vs right nonce handling

Hashes and MACs: SHA-256, HMAC, CMAC

BEGINNER▶
1. What is it?

A hash function turns any amount of data into a short fixed-size "fingerprint". SHA-256 always outputs 32 bytes, whether you hash 1 byte or a 1 MB firmware image. A hash has no key, so anyone can compute it — it detects accidental or malicious change only if the expected hash itself is protected. A MAC (Message Authentication Code) is a "keyed hash": only someone with the secret key can compute the correct tag, so it proves integrity and authenticity.

2. Terms and the three security properties of a hash
  • Digest = the output of the hash (32 bytes for SHA-256).
  • Preimage resistance: given a digest, you cannot find any input that produces it (cost ≈ 2256 tries).
  • Second-preimage resistance: given a specific image, you cannot find a different image with the same digest. This is what secure boot relies on.
  • Collision resistance: you cannot find any two inputs with the same digest (cost ≈ 2128 because of the birthday paradox: among N random values, collisions appear after about √N). SHA-1 and MD5 have practical collisions — never use them for signatures.
  • Avalanche effect: flipping 1 input bit changes about half of the 256 output bits. Try it in the Secure Boot simulator: click one byte and the whole hash changes.
  • CRC vs hash: a CRC-32 detects random transmission errors but is linear — an attacker can modify data and fix up the CRC trivially. A CRC is not a security check.
3. How SHA-256 processes a firmware image, step by step
  1. Pad: append byte 0x80, then zeros, then the original length in bits as a 64-bit big-endian number, so the total is a multiple of 64 bytes. Example: a 3-byte message "abc" → 3 + 1 + 52 zero bytes + 8 length bytes = 64 bytes = one block.
  2. Initialise eight 32-bit state words H0…H7 with fixed constants (fractional parts of square roots of the first 8 primes; H0 = 0x6a09e667).
  3. For each 64-byte block: expand the 16 input words into 64 words, run 64 rounds of additions, rotations and boolean functions that mix the block into the state.
  4. Output: the final eight words concatenated = 32 bytes. SHA-256("abc") = ba7816bf…f20015ad.

The simulator on this page runs this exact algorithm in JavaScript over the image bytes you can edit.

4. HMAC and CMAC — how a key is mixed in
HMAC(K, m) = H( (K ⊕ opad) || H( (K ⊕ ipad) || m ) )
  ipad = 0x36 repeated 64 times, opad = 0x5C repeated 64 times (block size of SHA-256 = 64 bytes)
  If K is longer than 64 bytes it is first hashed.

CMAC(K, m)  = AES-CBC-MAC with a final-block tweak using subkeys K1/K2 derived from AES_K(0)
              (NIST SP 800-38B). Used where you already have an AES engine and no SHA engine,
              e.g. AUTOSAR SecOC on CAN, many automotive HSMs.

Why not just H(K ‖ m)? SHA-256 is a Merkle–Damgård construction: from H(K‖m) and len(K‖m) an attacker can compute H(K‖m‖pad‖extra) without knowing K. That is the length-extension attack. HMAC's double hashing blocks it.

5. Worked example — sizes and costs on a Cortex-M4 at 168 MHz
  • Software SHA-256 (mbedTLS, -O2): roughly 30–40 cycles/byte → a 256 KB image ≈ 256×1024×35 ≈ 9.2 M cycles ≈ 55 ms. Numbers vary with compiler and library; measure on your target.
  • Hardware HASH peripheral (STM32F415/F437 have HASH and CRYP; the F407 does not): a few cycles/byte plus DMA, often bus-limited.
  • HMAC tag on CAN: CAN classic frame carries only 8 data bytes, so SecOC typically sends a truncated MAC (e.g. 24–64 bits) plus a truncated freshness counter. Truncation trades forgery probability (2−24 per try) for bandwidth.
6. Annotated code — verifying a MAC
/* WRONG */
if (memcmp(rx_tag, calc_tag, 16) == 0) accept();   // early-exit compare leaks timing (card 07)
if (strcmp(rx_tag, calc_tag) == 0) accept();       // stops at first 0x00 byte: may compare 0 bytes!

/* RIGHT */
uint8_t calc_tag[32];
mbedtls_md_hmac(mbedtls_md_info_from_type(MBEDTLS_MD_SHA256),
                key, 32, msg, msg_len, calc_tag);  // HMAC-SHA256 over the whole message
if (ct_equal(rx_tag, calc_tag, 16)) accept();       // constant-time compare, 16-byte truncated tag
mbedtls_platform_zeroize(calc_tag, sizeof calc_tag);// wipe secrets from the stack
Say it like this: "A hash like SHA-256 gives a fixed 32-byte fingerprint with preimage and collision resistance, but it has no key, so it only proves integrity if the reference hash is trusted. A MAC — HMAC or CMAC — adds a shared key and proves integrity and authenticity. I never use H(key‖msg) because of length extension, never use a CRC as a security check, and I compare tags in constant time."
05

Asymmetric crypto: RSA vs ECC, ECDSA/Ed25519 signatures, ECDH

INTERMEDIATE▶
1. What is it?

Asymmetric (public-key) cryptography uses a key pair: a private key that never leaves its owner and a public key that can be published. Whatever the private key signs, anyone with the public key can verify — but nobody can forge it. This is exactly what firmware needs: the vendor signs in a secure build server, and millions of devices verify using a public key they can store openly. If a device is dumped, the attacker gets only the public key, which is useless for signing.

2. Terms
  • RSA: security rests on the difficulty of factoring a large number n = p·q. Key sizes 2048–4096 bits.
  • ECC (Elliptic Curve Cryptography): security rests on the elliptic-curve discrete-log problem. Much smaller keys for the same strength. Common curves: P-256 (NIST, also called secp256r1/prime256v1) and Curve25519.
  • ECDSA (Elliptic Curve Digital Signature Algorithm): signs a hash with an EC private key. Needs a fresh secret random number k per signature.
  • Ed25519: an EdDSA signature on Curve25519. Deterministic (k is derived from key and message), faster, harder to misuse.
  • ECDH (Elliptic Curve Diffie–Hellman): two parties each combine their private key with the other's public key and get the same shared secret — key agreement over an open channel. X25519 = ECDH on Curve25519.
  • Security level ("bits of security"): log2 of the work to break it.
3. Size comparison — the numbers interviewers expect

Verification speed: RSA verify with e = 65537 is very fast (only 17 modular multiplications), RSA signing is slow; ECDSA verify is slower than RSA verify but keys and signatures are far smaller — this is why constrained devices prefer ECC.

4. How a firmware signature works, step by step
  1. Build server computes d = SHA-256(image).
  2. HSM (Hardware Security Module, a tamper-resistant key vault in the build pipeline) computes sig = ECDSA_Sign(priv_key, d) → 64 bytes (r, s).
  3. The image, its header (version, size) and sig are shipped.
  4. Device computes d' = SHA-256(header ‖ image) over what it actually has in memory.
  5. Device runs ECDSA_Verify(pub_key, d', sig). Only if it returns success does it jump to the image.
5. What goes wrong: ECDSA nonce reuse

Every ECDSA signature mixes the message digest, the private key and a one-time secret number k. The maths is designed so that k "hides" the private key inside each signature. If the same k is ever used for two different messages, that hiding cancels out and simple algebra on the two public signatures reveals the private key. Even a k that is only slightly predictable or biased leaks the key over many signatures. This is a well-documented real-world failure: a games-console vendor's code-signing key was publicly exposed around 2010 because its signing tool used a fixed k.

How engineers prevent it: 1. Use RFC 6979 deterministic k (k is derived from the private key and the message with HMAC-DRBG, so it is unique per message and needs no RNG). 2. Or use Ed25519, which is deterministic by design. 3. Sign only inside an HSM / secure element whose implementation is certified. 4. In code review, treat "where does k come from?" as a mandatory question for any ECDSA code.

6. ECDH key agreement — worked flow
Device:  priv a, pub A = a·G          Server: priv b, pub B = b·G     (G = curve base point)
Device sends A, server sends B (in clear, authenticated by certificates/signatures!)
Device computes  a·B = a·b·G           Server computes b·A = b·a·G      → same point S
session_key = HKDF(salt, S.x, info="fw-update v1")   // never use S.x directly as a key

Pitfall: unauthenticated ECDH is open to a man-in-the-middle (attacker does ECDH separately with both sides). The public values must be signed or come from certificates. Also validate received public keys are on the curve (invalid-curve attacks).

7. Annotated code — verifying a signature with PSA Crypto (Mbed TLS 3.x / TF-M)
psa_key_attributes_t at = PSA_KEY_ATTRIBUTES_INIT;
psa_set_key_type(&at, PSA_KEY_TYPE_ECC_PUBLIC_KEY(PSA_ECC_FAMILY_SECP_R1));
psa_set_key_bits(&at, 256);                               // P-256

                                  d, 32, sig, 64);         // raw r||s, 64 bytes

Say it like this: "For firmware I use asymmetric signatures because the device only needs the public key, so dumping a device never lets anyone sign. ECC wins on MCUs: P-256 or Ed25519 give 128-bit security with 32–64-byte keys and 64-byte signatures, versus 384-byte RSA-3072 keys. The classic ECDSA trap is nonce reuse, which leaks the private key, so I use RFC 6979 or Ed25519. ECDH gives a shared secret, but it must be authenticated and fed through a KDF."

Key derivation and randomness: HKDF, PBKDF2, TRNG vs DRBG

INTERMEDIATE▶
1. What is it?

Cryptography needs two kinds of "good" numbers: keys derived correctly from some starting secret, and truly unpredictable random numbers for nonces, keys and ECDSA k values. A KDF (Key Derivation Function) turns one secret into many independent keys. A random number generator produces values an attacker cannot predict. Weak randomness silently destroys every other defence (Scenario 08).

2. Terms
  • HKDF (HMAC-based KDF, RFC 5869): two steps, Extract and Expand. Used when the input secret already has high entropy (an ECDH shared secret, a device master key).
  • PBKDF2 (Password-Based KDF 2, RFC 8018) / scrypt / Argon2: deliberately slow KDFs for low-entropy inputs like a user PIN, so brute force costs time. On an MCU, a PIN is better protected by a retry counter inside a secure element than by iteration count.
  • Entropy: unpredictability measured in bits. A 4-digit PIN has log2(10 000) ≈ 13.3 bits — trivially brute-forced offline.
  • TRNG (True RNG): hardware that samples a physical noise source (e.g. jitter between free-running ring oscillators — what STM32 RNG peripherals use). Slow, may be biased; must be health-tested.
  • PRNG: deterministic algorithm. rand() is a PRNG for simulations — never for security.
  • DRBG / CSPRNG (Deterministic Random Bit Generator, NIST SP 800-90A: CTR_DRBG, HMAC_DRBG): a cryptographically secure PRNG seeded from a TRNG, reseeded periodically. Output is unpredictable as long as the seed is.
3. HKDF step by step
  1. Extract: PRK = HMAC-SHA256(salt, IKM). IKM = input keying material (e.g. ECDH secret). Salt = optional non-secret random value. Output: a uniformly random 32-byte pseudo-random key.
  2. Expand: T(1) = HMAC(PRK, info ‖ 0x01), T(2) = HMAC(PRK, T(1) ‖ info ‖ 0x02), … concatenate until you have L bytes. info = a context label like "fw-enc v1" — different labels give independent keys.
  3. Use each output for exactly one purpose: one key for encryption, a different one for MAC. Never reuse one key for two algorithms.
4. Worked example — per-device keys from a factory master key
UID (STM32F4, 96-bit unique ID at 0x1FFF7A10) = 0x0039002E 0x3436510B 0x32353530
k_dev    = HKDF(salt = "acme-2026", IKM = K_master, info = "dev" || UID, L = 32)
k_logenc = HKDF(salt = none,        IKM = k_dev,    info = "log-enc v1", L = 16)  // AES-128
k_logmac = HKDF(salt = none,        IKM = k_dev,    info = "log-mac v1", L = 32)  // HMAC key

Factory computes k_dev in its HSM and injects only k_dev into the device. Dumping one device reveals that device's key, not K_master and not other devices' keys. (Better still: each device generates its own key pair inside a secure element — see card 12.)

Constant-time code, crypto libraries and hardware accelerators

INTERMEDIATE▶
1. What is it?

Code is constant-time when the time it takes (and the memory addresses it touches) does not depend on secret data. If a check finishes faster when the first byte is wrong than when the first byte is right, then the response time itself carries information about the secret — the check is "talking" through a channel the designer never intended. The Constant-Time Lab tab visualises this difference and shows how a constant-time compare removes it.

2. Terms
  • Timing side channel: information leaking through execution time.
  • Early exit: a loop that returns as soon as it sees a difference — standard memcmp does this.
  • Secret-dependent branch: if (secret_bit) …. Even with the same instruction count, branches can change pipeline/flash-prefetch timing.
  • Secret-dependent memory index: table[secret]. On cores with a data cache (Cortex-M7, A-class) the cache line touched leaks the index (classic T-table AES attacks).
3. Why early exit leaks — step by step with numbers
  1. The device checks a 16-byte MAC tag with memcmp. Suppose each compared byte costs about 7 cycles, plus 12 cycles of fixed overhead. At 168 MHz, 1 cycle ≈ 5.95 ns.
  2. A tag that is wrong in byte 0 makes memcmp stop after 1 byte: 12 + 7 = 19 cycles.
  3. A tag whose byte 0 happens to be right but byte 1 wrong makes it compare 2 bytes: 12 + 14 = 26 cycles — 7 cycles (≈ 42 ns) longer.
  4. So the response time is a function of "how many leading bytes are correct". That is information about the secret tag that the protocol never meant to reveal. Noise (interrupts, jitter) blurs a single measurement, but averaging many measurements reduces noise by √N, so small differences become visible with enough repetitions.
  5. The security consequence: the strength of the check is no longer "guess all 16 bytes at once" (2128) but degrades towards "learn the tag piece by piece", which is dramatically weaker. That is why secure-coding standards (CERT C, MISRA-adjacent security guidelines, every crypto library) require constant-time comparison for secrets.

How engineers detect it: code review rule "no memcmp/strcmp on secrets"; static checkers and tools such as dudect or ctgrind (Valgrind-based) that flag secret-dependent branches; measuring cycle counts with the DWT cycle counter (DWT->CYCCNT on Cortex-M4) for matching vs non-matching inputs in a unit test — the counts must be identical.

4. Annotated code — wrong vs right
/* WRONG: returns at the first mismatch, so time ∝ length of matching prefix */
int naive_eq(const uint8_t *a, const uint8_t *b, size_t n) {
    for (size_t i = 0; i < n; i++)
        if (a[i] != b[i]) return 0;      // ← secret-dependent exit
    return 1;
}

/* RIGHT: always touches all n bytes, no branch on the data */
int ct_equal(const volatile uint8_t *a, const volatile uint8_t *b, size_t n) {
    uint8_t diff = 0;
    for (size_t i = 0; i < n; i++)
        diff |= a[i] ^ b[i];             // accumulate differences; never branch
    /* map diff==0 → 1, diff!=0 → 0 without a branch:
       (uint32_t)diff - 1 has bit 31 set only when diff == 0 (0 - 1 = 0xFFFFFFFF);
       for diff = 1..255 the result is 0..254, so bit 31 is clear */
    return (int)((((uint32_t)diff) - 1u) >> 31);
}

Secure boot: the chain of trust from ROM to application

INTERMEDIATE▶
1. What is it?

Secure boot means: the device only runs code that was signed by the vendor. It works like a relay of trust. The first code that runs is in ROM (cannot be changed), and it checks the signature of the next stage before running it. That stage checks the next, and so on. If any check fails, the device stops instead of running unknown code. Apple's iPhone does exactly this: Boot ROM → iBoot → kernel, each verified before execution.

2. Terms
  • Root of Trust (RoT): the component you trust without checking, because it cannot be modified: mask ROM code + a key hash burned in OTP fuses.
  • OTP / eFuse: One-Time-Programmable memory. Bits can be changed from 0→1 once (blowing a fuse) and never back. Ideal for storing a root key hash and anti-rollback counters.
  • Root public key hash: storing a full public key in fuses is expensive, so you store SHA-256(public key) = 32 bytes. The key itself travels in the image header and is checked against the hash.
  • Chain of trust: ROM verifies first-stage bootloader → bootloader verifies application (and maybe a second-stage loader or a TrustZone secure image first).
  • Fail closed / fail secure: on any error (bad signature, unknown header field, parse error), refuse to boot. The opposite — "fail open" — is a vulnerability.
3. What happens at power-on, step by step
  1. ROM runs. Mask ROM code executes first (immutable; on many MCUs the vendor bootloader ROM, or a user "secure boot" flash area locked by option bytes, e.g. STM32 "secure user memory" / HDP; on NXP and ESP32 a real ROM secure-boot feature).
  2. ROM reads the bootloader header: magic, version, image size, the public key, signature.
  3. Key check: computes SHA-256(public key in header) and compares with the 32-byte hash in OTP. Mismatch → halt. This stops an attacker who re-signs a bootloader with their own key and puts their own public key in the header.
  4. Signature check: d = SHA-256(header ‖ bootloader code); verify(pubkey, d, sig). Fail → halt (or fall back to a recovery image).
  5. Jump to the bootloader. Now the bootloader is trusted.
  6. Bootloader verifies the application the same way, using an app-signing public key built into the bootloader (and therefore covered by the bootloader's signature). It also checks version ≥ anti-rollback counter (card 09).
  7. Lock down before jumping: disable the bootloader's own flash region (e.g. STM32 HDP "hide protection"), lock the key storage, set MPU, then jump to the app.

6. Annotated code — the bootloader decision (naive vs hardened)

    jump_to_app();

volatile uint32_t r1 = SB_FAIL, r2 = SB_FAIL;   // default to failure (fail closed)

random_delay();                       // de-synchronise the attacker's timing

        jump_to_app();
    }

7. What goes wrong if…
  • …the key hash is not checked: attacker builds their own bootloader, signs it with their own key, puts their public key in the header — the signature verifies perfectly. Symptom: secure boot "passes" with foreign code.
  • …you verify one copy and execute another (external flash, TOCTOU): Scenario 02.
  • …the parser trusts header lengths before verifying: a crafted hdr_size causes an out-of-bounds read inside the trusted ROM/bootloader itself. Parse with strict bounds checks, then verify.
  • …debug is left open: the attacker simply halts the core after verification and writes new code into RAM. Secure boot without debug lock is incomplete.
Say it like this: "Secure boot is a chain of trust anchored in immutable ROM and a public-key hash in OTP fuses. Each stage checks the next stage's public key against the trusted hash, verifies its signature over header plus code, checks the version against an anti-rollback counter, and only then jumps — failing closed on any error. I also harden the final decision against fault injection with non-trivial OK constants and redundant checks, verify the exact bytes I execute, and lock debug, otherwise the chain can be bypassed around it."

Anti-rollback counters, measured boot and attestation

INTERMEDIATE▶
1. What is it?

A signature proves an image came from you — but your old images were also signed by you. If version 2 had a known vulnerability, an attacker can install the genuine signed v2 and exploit it. Anti-rollback stops the device from accepting versions older than a stored minimum. Measured boot records what actually booted, and attestation lets the device prove that record to a server.

2. Terms
  • Security counter / ARC (anti-rollback counter): a monotonic (only-increasing) number stored where software cannot decrease it — OTP fuses, a secure element's monotonic counter, or RPMB (Replay Protected Memory Block in eMMC).
  • Security version vs marketing version: the counter only bumps when a release fixes a security issue; feature releases keep the same security version so you can still roll back between them.
  • Measurement: a hash of a boot stage. Extend operation: PCRnew = H(PCRold ‖ measurement). A PCR (Platform Configuration Register, from TPMs) can only be extended, never set, so the final value encodes the whole ordered boot sequence.
  • Attestation: the device signs (nonce from server ‖ measurements) with a device key, and the server checks it against known-good values.
  • DICE (Device Identifier Composition Engine, TCG standard for MCUs): hardware holds a Unique Device Secret (UDS); ROM computes CDI = HMAC(UDS, H(first mutable code)) and then hides UDS until next reset. Changing the firmware changes the CDI and therefore every key derived from it.
3. Anti-rollback, step by step
  1. OTP counter ARC = 3 (three fuses blown in a 32-fuse field: 0b111 → thermometer coding, value = number of 1s).
  2. Update arrives with signed header field sec_ver = 4. Bootloader: signature OK, 4 ≥ 3 → accept, boot it in trial mode.
  3. New image runs self-tests and calls "confirm". Only now the bootloader blows fuse #4 → ARC = 4. (If you bump first and the new image is broken, you can never go back to v3 — bricked.)
  4. Attacker later supplies genuine signed v3: 3 < 4 → reject. Rollback blocked.

Worked numbers: a 64-bit OTP field in thermometer code allows 64 security bumps. At 2 security releases per year that is 32 years — plenty. Storing the counter as a binary number in fuses would not work because you cannot turn 1 bits back to 0 to count up (0b011 → 0b100 needs clearing bits).

4. Annotated code
/* WRONG: counter in normal flash, attacker with SWD or a flash bug just erases it */
if (hdr->sec_ver < *(uint32_t*)CFG_FLASH_MIN_VER) reject();

/* WRONG: version field outside the signed region — attacker edits it freely */

boot_trial(hdr);
/* later, after the app confirms health: */
if (hdr->sec_ver > arc) otp_blow_up_to(OTP_ARC_FIELD, hdr->sec_ver);

Secure boot vs measured boot: secure boot prevents bad code from running (local enforcement). Measured boot records what ran so a remote party can decide (e.g. refuse to give the device cloud credentials). They are complementary.

Say it like this: "Signatures alone don't stop a downgrade to an old, signed, vulnerable image, so I put a security version in the signed header and compare it to a monotonic counter in OTP or a secure element, bumping the counter only after the new image confirms it is healthy. Measured boot extends a hash of each stage into a register, and attestation signs those measurements with a server nonce so the backend can verify exactly what firmware is running."

Secure firmware update: sign + encrypt, A/B slots, key rotation

INTERMEDIATE▶
1. What is it?

A firmware update (FOTA = Firmware Over The Air) is the most powerful feature you ship: it can replace all the code on every device. If an attacker can push their own update, they own the fleet. A secure update guarantees authenticity (only vendor images install), optionally confidentiality (competitors cannot read the code in transit), freshness (no rollback) and availability (a failed update cannot brick the device).

2. Terms
  • A/B (dual-slot): two image slots; the new image is written to the inactive slot, so the running one is untouched until the switch.
  • Swap / revert: MCUboot swaps primary and secondary; if the new image does not confirm itself, the next reset reverts.
  • Sign-then-encrypt: sign the plaintext image, then encrypt it. The device decrypts, then verifies the signature over the plaintext it will actually run.
  • Key wrapping: encrypt a random per-image AES key (the content key) with each device's key (e.g. ECIES = ECDH + KDF + AES), so one firmware file can be decrypted by any authorised device.
  • Key rotation / revocation: replacing a signing key (because it is old or compromised). Needs a plan from day one: multiple key-hash slots in OTP with revoke fuses.
3. The update pipeline, step by step
  1. Build: reproducible build produces app.bin; CI computes SHA-256 and generates an SBOM.
  2. Sign in an HSM (private key never on a developer laptop): sig = ECDSA(PK_priv, SHA-256(header ‖ app)).
  3. Encrypt (optional): random content key CK; ct = AES-CTR(CK, nonce, app); CK wrapped for the device class or per device.
  4. Transport over TLS — protects the channel, but do not rely on it: the image itself must be signed (end-to-end), because servers and CDNs get compromised.
  5. Device downloads into the inactive slot, then verifies (decrypt → hash → signature → version ≥ ARC).
  6. Bootloader re-verifies at next boot (the slot could have been altered after download), swaps, boots in trial mode.
  7. App self-test passes → confirm → bump anti-rollback counter. Fails or watchdog resets → bootloader reverts to the old slot.
4. Why sign the plaintext and not the ciphertext?

Because the property you want is "the code I am about to execute is genuine". If you only sign the ciphertext, a bug in decryption or a wrong key produces garbage that was never verified. Sign plaintext, encrypt for confidentiality, and if you also want early rejection of junk downloads, use an AEAD so the ciphertext is authenticated too.

5. Worked example — flash budget
STM32F407VG: 1 MB flash = sectors 0–3 (4×16 KB), sector 4 (64 KB), sectors 5–11 (7×128 KB)

  0x0801_0000  config/keys     64 KB  sector 4

Slots must start and end on sector boundaries, because flash erases whole sectors.
6. Key rotation design
  • OTP holds 3 root key hashes + 3 revoke bits. Boot ROM accepts an image signed by any non-revoked key.
  • If key #0 leaks: ship an update signed by key #1 that blows revoke bit #0. From then on, images signed with key #0 are rejected.
  • Prefer a two-level hierarchy: root key (offline, in a safe) signs a short-lived image-signing key certificate; rotating the image key needs no fuse change.
Say it like this: "I sign the plaintext image in an HSM, optionally encrypt it with a per-image content key wrapped for devices, and ship it over TLS — but trust only the signature. The device writes to the inactive slot, the bootloader re-verifies signature and security version, boots in trial mode, and only after a self-test confirms does it bump the anti-rollback counter; otherwise it reverts. From day one I reserve multiple key-hash slots with revoke fuses so a leaked key can be rotated."

Key storage: OTP, secure elements, TrustZone-M, PUF (the Secure Enclave mindset)

ADVANCED▶
1. What is it?

Strong algorithms are useless if the key sits in plain flash where a debugger or a memory-disclosure bug can read it. Key storage is about where the key lives and who can touch it. The best design — Apple's Secure Enclave principle — is that the key never leaves the protected hardware at all: software sends data in and gets results out, but can never read the key itself.

2. Terms
  • OTP / eFuse: one-time-programmable bits. Good for root key hashes and counters; secret keys in plain OTP can still be read by any code (or by an invasive attacker), unless the OTP has read-lock and is wired to a crypto engine (e.g. ESP32 eFuse key blocks readable only by the AES/HMAC peripheral).
  • Secure element (SE): a separate small chip designed to resist physical attacks, connected by I²C/SPI. Examples: Microchip ATECC608 (ECC P-256 sign/verify/ECDH, SHA-256/HMAC, 16 key slots, monotonic counters, keys generated internally and never exported), NXP EdgeLock SE050 (RSA up to 4096 and ECC, AES, Common Criteria EAL 6+ certified), Infineon OPTIGA Trust M.
  • TrustZone-M (Armv8-M, e.g. Cortex-M33/M55/M85): splits the MCU into a Secure world and a Non-secure world in hardware. The SAU (Security Attribution Unit) and the vendor's IDAU mark each address range S, NS or NSC (Non-Secure Callable). Non-secure code can only enter secure code through SG (Secure Gateway) instructions in NSC regions. TF-M (Trusted Firmware-M) runs crypto and secure storage in the Secure world.
  • PUF (Physically Unclonable Function): derives a key from tiny manufacturing differences in the silicon (e.g. SRAM start-up values). The key is regenerated at each boot and never stored, so there is nothing to read out of non-volatile memory. Needs helper data and error correction because the raw response is noisy. Example: NXP LPC55S6x "PUF key store".
  • Key wrapping: storing a key encrypted under a hardware key (e.g. STM32U5 SAES with DHUK = Derived Hardware Unique Key). The wrapped blob can sit in normal flash.

4. How an ATECC608 signs, step by step
  1. Factory: the SE runs GenKey on slot 0 — the private key is created inside the chip; only the public key comes out.
  2. The public key is put in a certificate signed by your CA (or Microchip's pre-provisioned "Trust&GO" certificate).
  3. Configuration and data zones are locked (irreversible): slot 0 is marked "private key, never readable".
  4. At run time the MCU sends a 32-byte digest over I²C: atcab_sign(0, digest, sig) → 64-byte signature back.
  5. The MCU never sees the key. If the MCU firmware is fully compromised, the attacker can use the key while they control the device (sign things), but cannot copy it to clone the device elsewhere.

Pitfall — bus binding: the I²C bus between MCU and SE is exposed on the PCB. If the SE returns "PIN OK → here is the secret" in clear, an attacker can sniff or spoof the bus. Use the SE's encrypted/authenticated I/O protection (e.g. ATECC608 "IO protection key", SE050 SCP03 secure channel).

Say it like this: "My rule is that a long-term key should never exist in readable memory. Ideally it is generated inside a secure element or a hardware key slot or regenerated from a PUF, and software only asks for operations like 'sign this digest'. On Armv8-M I put crypto in the TrustZone secure world behind a narrow API and validate every pointer that comes from the non-secure side. And I never ship one shared key across the fleet."

Device identity and factory provisioning

INTERMEDIATE▶
1. What is it?

Each device needs its own identity — a unique key pair and a certificate that says "this public key belongs to device #000123 made by ACME" — so the cloud can tell genuine devices from clones and so one compromised device can be revoked alone. Provisioning is the factory step that creates and installs this identity, plus locking the chip (debug, option bytes) before it ships.

2. Terms
  • X.509 certificate: a signed document binding a public key to a name (the device ID), signed by a CA (Certificate Authority).
  • CSR (Certificate Signing Request): the device sends its public key (signed with its private key to prove possession) and asks the CA to issue a certificate.
  • Manufacturing CA / intermediate CA: a CA used only in the factory, kept in an HSM, chained to an offline root CA.
  • Lifecycle state: open (development) → provisioned → locked/production → (RMA/decommissioned). Many MCUs have a hardware lifecycle register (e.g. STM32H5/U5 "product state", NXP LPC55 lifecycle fuses).
3. A secure provisioning line, step by step
  1. Flash the signed bootloader and a minimal provisioning firmware.
  2. Generate the key on the device: the provisioning firmware asks the SE (or the TRNG + secure storage) to generate a P-256 key pair. The private key never travels over the test fixture.
  3. CSR: the device outputs its public key + unique ID (e.g. STM32 96-bit UID) as a CSR.
  4. Sign: the station's HSM signs the CSR with the manufacturing CA → device certificate.
  5. Write back the certificate (public data, can sit in flash) and register serial + certificate fingerprint in the cloud database.
  6. Burn fuses: root key hash, anti-rollback counter start, secure-boot enable.
  7. Lock: set RDP level 2 / product state "closed", disable debug, erase provisioning firmware, flash production firmware.
  8. Verify: a test connects to the cloud with the new identity (mutual TLS) to prove the whole chain works; log the result.
4. Worked example — what an untrusted factory can and cannot do

Contract manufacturer (CM) is partly trusted. If the CM injects keys it generated, the CM can keep a copy and clone devices. With on-device key generation (step 2) the CM never sees private keys. With a quota-limited HSM (the HSM signs at most 10 000 CSRs per production order), the CM cannot mint extra "genuine" devices for the grey market: unit #10 001 gets no certificate. ST calls their version "Secure Firmware Install" (SFI): firmware is encrypted for the target chip family and an HSM counts installs.

5. What goes wrong if…
  • …all devices share one AWS IoT certificate/key: one dump lets an attacker impersonate every device, and you can only revoke all of them at once.
  • …locking is skipped on one batch (operator unchecks "set RDP2" to save time): those units ship with open SWD. Make the line software refuse to log a unit as "passed" until a read-back confirms option bytes and lifecycle state.
  • …the private key is generated on the test PC and pushed over UART: it now exists in PC memory, logs and swap files.
Say it like this: "Each device gets a unique key pair generated on-chip or in a secure element, so the private key never leaves it. The factory station collects a CSR, an HSM-backed manufacturing CA issues the certificate, and the line then burns the root key hash, enables secure boot and locks debug, verifying the lock by read-back. Per-device identity means one stolen device can be revoked without touching the rest of the fleet."

Debug port protection: STM32 RDP levels, JTAG lock, authenticated debug

INTERMEDIATE▶
1. What is it?

The debug port (SWD = Serial Wire Debug, 2 pins; or JTAG, 4–5 pins) gives total control: halt the CPU, read and write all memory, change registers. In development you need it; in a shipped product it is the easiest way to steal firmware and keys or to bypass secure boot (halt after verification, patch RAM, resume). Readout protection limits what the debug port and the built-in ROM bootloader can do.

2. STM32F4 RDP (Read-out Protection) levels — reference manual RM0090

The level is chosen by the RDP byte in the option bytes (FLASH_OPTCR bits 15:8):

LevelRDP byteDebugger connects?Flash readable by debugger / RAM boot / system bootloader?Can go back?
00xAAyesyes — no protection—
1any value except 0xAA and 0xCC (commonly 0x55)yes (RAM and peripherals still accessible)no: any flash access while debug is connected or when booted from SRAM/system memory gives a bus erroryes → level 0, but this mass-erases user flash first
20xCCno — debug permanently disabledno; boot from SRAM/system memory disabled; option bytes frozennever (irreversible on F4)

Your own firmware can always read its own flash at every level (it has to, to run). Newer families differ: STM32L5/U5 add a level 0.5 for TrustZone; STM32U5/H5 support password-based regression from level 2 or a "product state" lifecycle — always read the specific reference manual.

3. Setting level 1 then 2 — annotated register sequence (F4)
HAL_FLASH_OB_Unlock();                         // writes 0x08192A3B, 0x4C5D6E7F to FLASH_OPTKEYR
FLASH_OBProgramInitTypeDef ob = {0};
ob.OptionType = OPTIONBYTE_RDP;
ob.RDPLevel   = OB_RDP_LEVEL_1;                // 0x55: reversible (with mass erase)
HAL_FLASHEx_OBProgram(&ob);                    // writes RDP byte into FLASH_OPTCR[15:8]
HAL_FLASH_OB_Launch();                         // sets OPTSTRT; new level active after reset
/* Production: OB_RDP_LEVEL_2 (0xCC). Irreversible — test the full field-update path BEFORE. */
4. Why level 1 is not enough for high-value secrets

Level 1 is enforced by a check in the flash interface logic: "is a debugger attached or did we boot from RAM? then block flash reads". Over the years, published academic and hobbyist research has shown that on several MCU families from different vendors, such checks can be defeated by fault injection (disturbing the chip so the check is evaluated wrongly — see card 18) or by weaknesses in the debug-interface logic itself. Notable public examples: a 2017 USENIX WOOT paper on STM32F0 readout protection; hardware-wallet research presented at 35C3 (2018) on STM32F2-based wallets; and 2020 work on Nordic nRF52 APPROTECT, after which Nordic changed APPROTECT behaviour in new silicon revisions. The lesson interviewers want is not the recipe — it is the design conclusion:

  1. Treat readout protection as raising the cost, not as a guarantee. Use the strongest level (RDP2 / closed lifecycle) for production.
  2. Design so that a dumped device is not a disaster: no shared fleet secrets in flash; per-device keys; ideally keys in a secure element or hardware key slot.
  3. Track vendor errata and security advisories for your exact part and revision.
5. Other debug-lock mechanisms
  • JTAG lock fuses (many SoCs, ESP32 JTAG_DISABLE eFuse, i.MX JTAG modes): disable or restrict JTAG permanently.
  • Authenticated debug: debug stays physically present but opens only after a challenge–response. The debugger reads a random challenge, an authorised server signs it with a debug key, the chip verifies the signature with a public key hash in OTP and then opens debug — optionally only the non-secure world. Examples: Arm PSA ADAC (Authenticated Debug Access Control), NXP LPC55 "debug authentication", STM32H5 debug authentication. Great for RMA (returned-unit analysis) without leaving debug open.
  • Don't forget the other doors: UART bootloader shells, factory test commands, USB DFU, the ROM bootloader (BOOT0 pin) — Scenario 07.
6. What goes wrong if…
  • …you ship RDP level 0 "temporarily": anyone with a $10 ST-Link clone reads the whole flash in seconds.
  • …you set level 2 but your field update path depended on the ROM bootloader: it is now disabled, and devices with a bricked app can never be recovered. Always have an in-application/bootloader update path before locking.
  • …you rely on level 1 to protect a fleet-wide AES key: one successful bypass on one unit compromises all units (Scenario 01 + 04).
Say it like this: "On STM32F4, RDP level 0 is open, level 1 blocks flash access from the debugger or RAM boot and can be reverted only with a mass erase, and level 2 permanently disables debug and option-byte changes. Level 1 has been bypassed on several families by fault injection or debug-logic weaknesses, so for production I use the strongest lock or authenticated debug, close every other door like UART shells, and design so that a dumped device exposes only that device's key."

Memory protection on MCUs: MPU, W^X, stack canaries, no ASLR, CFI, PAC/BTI

ADVANCED▶
1. What is it?

Bugs will exist. Exploit mitigations make a bug harder to turn into "attacker runs their own code". On a PC you get an MMU, ASLR and non-executable stacks for free; on a microcontroller you get almost none by default — every address is fixed, and SRAM is executable. You must switch the protections on yourself.

2. Terms
  • MPU (Memory Protection Unit): hardware that checks every memory access against up to 8 (Cortex-M4) or 16 (Armv8-M) regions with permissions: read/write, privileged/unprivileged, and XN (eXecute Never). A violation raises a MemManage fault. No address translation (that is an MMU).
  • W^X ("write XOR execute"): no memory region may be both writable and executable. Then injected data (shellcode) can never run.
  • Stack canary: a secret value placed between local buffers and the saved return address. GCC -fstack-protector-strong checks it before returning; if it changed, it calls __stack_chk_fail().
  • ASLR (Address Space Layout Randomisation): randomising where code/stack live. Absent on MCUs — no MMU, code is linked to fixed flash addresses — so an attacker knows every function address from one firmware dump.
  • ROP (Return-Oriented Programming): instead of injecting code, the attacker chains existing instruction snippets ("gadgets") ending in a return, by overwriting a sequence of return addresses. W^X does not stop ROP; CFI/PAC does.
  • CFI (Control-Flow Integrity): checks that indirect jumps/returns go only to legitimate targets.
  • PAC (Pointer Authentication Code) and BTI (Branch Target Identification): Arm hardware CFI. Armv8.3-A / Armv8.5-A on application cores (Apple A12 and later use PAC heavily); on microcontrollers the PACBTI extension of Armv8.1-M (e.g. Cortex-M85). PAC signs the return address in LR with a secret key and the SP as context, storing a tag; AUT checks it before return. BTI makes indirect branches fault unless they land on a BTI instruction.
  • Stack limit registers MSPLIM/PSPLIM (Armv8-M Mainline, e.g. Cortex-M33): a hardware stack overflow check, no MPU region needed.
3. Configuring a W^X MPU layout on Cortex-M4, step by step
  1. Flash (code): read-only, executable.
  2. SRAM (data, stack, heap): read-write, XN = 1.
  3. Peripherals: read-write, XN, device memory type.
  4. A 32-byte "guard" region with no access at the bottom of the main stack — overflow hits it → MemManage fault instead of silent corruption.
  5. Enable with PRIVDEFENA (privileged code gets the default map for anything not covered), then DSB/ISB.

Worked numbers — ARMv7-M region size encoding: RASR.SIZE = log2(bytes) − 1, region base must be aligned to its size. 128 KB SRAM: log2(131 072) = 17 → SIZE = 16. 32-byte guard: log2(32) = 5 → SIZE = 4 (minimum allowed). A 96 KB region is impossible (not a power of two) — use a 128 KB region with subregions disabled (8 subregions of 16 KB; disable the top 2 → 96 KB).

MPU->RNR  = 0;                                  // region 0: flash, RO + executable
MPU->RBAR = 0x08000000;
MPU->RASR = (0b110u << 24)                      // AP = 110: read-only, priv + unpriv
          | (1u << 17)                          // C = 1 (normal, cacheable)
          | (19u << 1)                          // SIZE = 19 → 2^20 = 1 MB
          | 1u;                                 // ENABLE
MPU->RNR  = 1;                                  // region 1: SRAM, RW + XN
MPU->RBAR = 0x20000000;
MPU->RASR = (1u << 28)                          // XN = 1: never execute from RAM  ← W^X
          | (0b011u << 24)                      // AP = 011: full access
          | (1u << 18) | (1u << 17)             // S = 1, C = 1
          | (16u << 1) | 1u;                    // SIZE = 16 → 128 KB, ENABLE
MPU->RNR  = 2;                                  // region 2: stack guard, no access
MPU->RBAR = 0x2001E000;                         // lowest address of an 8 KB stack (32-B aligned)
MPU->RASR = (1u << 28) | (0b000u << 24)         // AP = 000: no access at all
          | (4u << 1) | 1u;                     // SIZE = 4 → 32 bytes; higher region number wins overlap
MPU->CTRL = MPU_CTRL_PRIVDEFENA_Msk | MPU_CTRL_ENABLE_Msk;
__DSB(); __ISB();                               // make the new map take effect before next access
SCB->SHCSR |= SCB_SHCSR_MEMFAULTENA_Msk;        // get MemManage instead of HardFault

Exception: code that must run from RAM (flash-programming routines) needs one small executable RAM region that is not writable after it is copied — keep W^X by changing permissions after the copy.

4. Stack canary — what the compiler generates
void parse(const uint8_t *in, size_t n) {       // compiled with -fstack-protector-strong
    // prologue: push {r4, lr}; ldr r3,=__stack_chk_guard; ldr r3,[r3]; str r3,[sp,#20]
    uint8_t buf[16];
    memcpy(buf, in, n);                         // bug: n unchecked
    // epilogue: reload canary from stack, compare with __stack_chk_guard, bne __stack_chk_fail
}
/* You must provide on bare metal: */
uintptr_t __stack_chk_guard;                    // set at boot from the TRNG, NOT a constant!
void __stack_chk_fail(void) { secure_log_and_reset(); }

Stack layout with canary:

high addr   [ saved LR (return address) ]  ← attacker's target
            [ saved r4                  ]
            [ CANARY  0x9e3f…           ]  ← overwritten first by a linear overflow → detected
low addr    [ buf[0..15]                ]  ← overflow starts here and writes upward

Limits: a canary detects linear overflows on return; it does not stop an arbitrary-write bug that skips over it, a leak that reveals the canary, or overflows of function pointers stored before the canary.

5. What goes wrong without these

Picture a parser bug that lets an oversized CAN payload write past a 16-byte stack buffer on a Cortex-M4 with no MPU configured. Conceptually, three default properties make such a bug far more dangerous on an MCU than on a PC: (1) SRAM is executable by default, (2) the saved return address sits just above local buffers, and (3) every address is fixed and identical on every unit (no ASLR). The impact can escalate from "crash" to "the device's control flow is no longer under the vendor's control".

How each defence breaks the chain: the length check (card 15) stops the overflow in the first place; a TRNG-seeded canary detects the corrupted frame before the function returns and resets safely; XN on SRAM means that even corrupted control flow cannot execute data as code — the core raises a MemManage fault; unprivileged tasks plus MPU regions limit what any surviving bug can touch; PAC/BTI (Armv8.1-M) make forged return addresses fault. Defence in depth means no single layer has to be perfect.

Say it like this: "MCUs have no ASLR and SRAM is executable by default, so a single overflow is very exploitable. I configure the MPU for W^X — flash read-only executable, RAM and peripherals execute-never — add a no-access guard below each stack or use PSPLIM on Armv8-M, compile with stack protectors seeded from the TRNG, and run tasks unprivileged. On Armv8.1-M cores with PACBTI I enable pointer authentication and BTI to stop ROP and jump-oriented attacks."

Common C vulnerabilities in firmware (and how to write it safely)

INTERMEDIATE▶
1. What is it?

C lets you write past the end of an array, use memory after freeing it, and silently wrap integers around. In firmware, the code that touches untrusted input — protocol parsers for BLE, CAN, USB, Modbus, MQTT, update headers — is where these bugs become remote exploits. Most real embedded CVEs are one of the six patterns below.

2. The six patterns, each with wrong and right code

(a) Buffer overflow from a length field. The packet says how long it is; the code believes it.

/* frame: [type:1][len:1][payload:len] */
/* WRONG */
uint8_t payload[32];
memcpy(payload, &rx[2], rx[1]);                 // len = 200 → writes 168 bytes past payload
/* RIGHT */
if (rx_len < 2) return ERR_SHORT;                // header present?
uint8_t len = rx[1];
if (len > sizeof payload) return ERR_TOO_LONG;   // fits the destination?
if ((size_t)len > rx_len - 2) return ERR_TRUNC;  // actually received that many? (no over-read)
memcpy(payload, &rx[2], len);

(b) Integer overflow → heap overflow. The size calculation wraps, so a tiny buffer is allocated and then filled with a huge amount.

/* WRONG: count from the network, 16-bit arithmetic on a 32-bit size */
uint16_t count = rd_u16(pkt);                     // attacker sends 0x2000 = 8192
uint16_t bytes = count * 8;                       // 8192*8 = 65536 → wraps to 0 in 16 bits!
rec_t *r = malloc(bytes);                         // malloc(0) → tiny or NULL
for (i = 0; i < count; i++) r[i] = read_rec();   // writes 64 KB into it → heap overflow
/* RIGHT */
if (count == 0 || count > MAX_RECS) return ERR;  // semantic limit first
size_t bytes = (size_t)count * sizeof(rec_t);     // widen BEFORE multiplying
// or: if (__builtin_mul_overflow(count, sizeof(rec_t), &bytes)) return ERR;

(c) Format string. Passing received data as the format argument means any % conversion characters inside it are interpreted by printf, which then reads (and with some conversions writes) memory the caller never supplied. It is a pure coding mistake with a one-line fix.

printf(rx_name);            // WRONG: received text is treated as a format string
printf("%s", rx_name);      // RIGHT; also compile with -Wformat -Wformat-security

(d) Use-after-free. A pointer is kept after free(); the memory is reused by something else and the stale pointer now writes into it.

free(sess); /* … */ sess->state = CLOSED;   // WRONG: dangling pointer write
free(sess); sess = NULL;                     // RIGHT (plus: avoid heap in firmware; static pools)

(e) TOCTOU (Time-Of-Check to Time-Of-Use). Data is checked, then re-read from a place the attacker can change, and the second read is used.

/* WRONG: the length lives in a buffer the DMA / other core / host can still modify */
if (shared->len <= MAX) memcpy(dst, shared->data, shared->len);   // read twice!
/* RIGHT: copy once into private memory, check the copy, use the copy */
uint32_t len = READ_ONCE(shared->len);
if (len > MAX) return ERR;
memcpy(dst, shared->data, len);

Same bug at system level: verifying a firmware image in external flash and then executing it from external flash (Scenario 02).

(f) Unchecked return values and fail-open defaults. int ok = 1; if (verify(...) == ERR_SIG) ok = 0; — any other error code (out of memory, parse error) leaves ok = 1. Always start from "deny" and set "allow" only on the explicit success value.

3. Secure coding practices — a checklist you can recite
  1. Validate every length against both the destination size and the received size.
  2. Do size arithmetic in size_t, check for overflow (__builtin_add_overflow).
  3. Prefer fixed-size static buffers and pools over malloc (MISRA C:2012 Rule 21.3).
  4. Fail closed; check every return value.
  5. Compile with -Wall -Wextra -Wconversion -Wformat-security -fstack-protector-strong; run static analysis (cppcheck, clang-tidy, Coverity, Polyspace) and MISRA/CERT C rules.
  6. Run parsers under AddressSanitizer + UBSan on the host, and fuzz them (card 16).
  7. Wipe secrets after use with a call the compiler cannot remove (mbedtls_platform_zeroize, C23 memset_explicit).
Say it like this: "Most firmware exploits come from parsers trusting a length field, integer wrap in size calculations, format strings, use-after-free and TOCTOU double reads. I check each length against the destination and the bytes actually received, widen before multiplying, copy shared data once and check the copy, fail closed on every error, and back it up with static analysis, sanitizers and fuzzing."

Fuzzing protocol parsers

ADVANCED▶
1. What is it?

Fuzzing means feeding a program millions of automatically mutated inputs and watching for crashes or sanitizer reports. A coverage-guided fuzzer (libFuzzer, AFL++) keeps any input that reaches new code, so it "learns" the format and digs deep into the parser. It finds exactly the length-field and integer bugs from card 15 — usually within minutes — before an attacker does.

2. Terms
  • Harness: a tiny function that takes a byte array from the fuzzer and calls your parser with it.
  • Corpus: a set of valid sample inputs to start from (captured CAN frames, BLE packets).
  • Sanitizers: compiler instrumentation that turns silent memory bugs into immediate crashes: ASan (AddressSanitizer: out-of-bounds, use-after-free), UBSan (undefined behaviour: signed overflow, bad shifts), MSan (uninitialised reads).
  • Rehosting: running firmware code on a PC (host build) or in an emulator (QEMU, Renode, Unicorn) so you can fuzz fast — real MCUs are thousands of times slower and have no sanitizers.
3. Step by step: fuzzing a CAN/ISO-TP parser on the host
  1. Separate the parser from hardware: int parse_frame(const uint8_t *buf, size_t len, msg_t *out) with no register access.
  2. Write the harness (below) and build with clang: clang -g -O1 -fsanitize=fuzzer,address,undefined parse.c harness.c -o fz.
  3. Seed the corpus with a few real frames: ./fz corpus/ -max_len=4096.
  4. The fuzzer reports a crash with the exact input file; replay it in a debugger, fix, add the input to a regression test.
  5. Run it in CI for every merge (e.g. 10 minutes per parser) and continuously on a server (OSS-Fuzz style).
#include <stdint.h>
#include <stddef.h>
#include "parser.h"
int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {   // called millions of times
    msg_t m;
    (void)parse_frame(data, size, &m);   // any OOB access → ASan aborts with a stack trace
    return 0;                            // never keep state between calls
}

5. Beyond the host
  • Protocol-aware / grammar fuzzers (boofuzz, structure-aware libFuzzer with protobuf) for stateful protocols like BLE pairing or MQTT.
  • On-target fuzzing over a real bus with a watchdog/reset monitor to detect hangs — slow but tests the real stack and timing.
  • Emulator fuzzing of binary-only firmware (Fuzzware, HALucinator approaches) when you have no source.
Say it like this: "I keep parsers hardware-independent so I can compile them on a PC with libFuzzer, AddressSanitizer and UBSan, seed a corpus with real frames, and let coverage guidance find the length and integer bugs. Every crash becomes a regression test, and the fuzzers run in CI. On target the same bug would silently corrupt memory, so host fuzzing with sanitizers is where it gets caught."

Side-channel attacks: timing, power (SPA/DPA), electromagnetic

ADVANCED▶
1. What is it?

A side channel is any physical by-product of computation — time, power consumption, electromagnetic emission, even sound — that depends on secret data. The algorithm can be mathematically perfect while its implementation leaks the key through these channels. Apple, smart-card and automotive HSM teams design specifically against them.

2. Terms
  • Timing attack: the secret changes how long an operation takes (card 07, Constant-Time Lab tab). Can be measurable remotely, which is why it matters even for network-only threat models.
  • SPA (Simple Power Analysis): looking at one or a few power traces and reading the secret directly from their shape. Classic: a square-and-multiply RSA/ECC routine does an extra "multiply" only for 1-bits of the key, so the trace pattern spells out the key bits.
  • DPA / CPA (Differential / Correlation Power Analysis): statistical analysis over many power measurements. Because power use correlates slightly with the data being processed, and the cipher processes the key in small pieces (e.g. one byte per S-box), the statistics can be applied to small pieces of the key independently — which is why an unprotected implementation is far weaker than its 2128 key space suggests. You need to know that it works and why (data-dependent power + divide-and-conquer), and above all how masking and hiding break it.
  • Hamming weight: number of 1 bits in a value. CMOS power draw at a register update roughly tracks the Hamming weight (or Hamming distance between old and new value) — that is the physical reason DPA works.
  • EM analysis: the same idea with a small magnetic probe near the chip, which can localise one block (e.g. the AES engine) and sometimes works through the package.
3. Why SPA reads a key — worked example
Key bits (MSB first): 1 0 1 1 0
Naive double-and-add (ECC) / square-and-multiply (RSA):
for each bit: DOUBLE ; if (bit) ADD
Power trace:  [D][A]  [D]  [D][A]  [D][A]  [D]
                1      0     1       1      0      ← readable from the trace shape

Fix: a Montgomery ladder or "always double-and-add" so every bit performs the same operations, with constant-time conditional swaps instead of branches.

4. Countermeasures, from software to hardware
  1. Constant-time code: no secret-dependent branches, memory indexes or early exits (stops timing and SPA patterns).
  2. Masking: split every secret intermediate into random shares (x = x1 ⊕ x2), compute on shares, so a single power sample is statistically independent of the secret. First-order masking defeats first-order DPA; higher orders cost more.
  3. Hiding: random delays, dummy operations, shuffling the order of S-box computations, noise generators, dual-rail logic — reduce the signal-to-noise ratio so more traces are needed.
  4. Blinding for RSA/ECC: randomise the input or scalar each time (e.g. use k + r·n instead of k).
  5. Protocol-level: limit how many operations an attacker can trigger with the same key (key rolling, rate limits, per-session keys from HKDF) — DPA needs thousands to millions of traces.
  6. Hardware: use side-channel-hardened engines (STM32 SAES, certified secure elements) for long-term keys.
5. What goes wrong if…

…you use a fast table-based software AES with a fixed long-term key on an unprotected MCU and let anyone trigger unlimited encryptions: published academic work repeatedly shows such implementations are within reach of a well-equipped lab. Since every unit shares the same design, the method transfers between units even if each key is per-device. Design response: hardened engine or SE for long-term keys, per-session keys derived with HKDF, rate limits, and PSA Level 3 / CC evaluation if physical attackers are in your threat model.

Say it like this: "Side channels leak secrets through time, power or EM rather than through the math. Timing attacks I stop with constant-time code; SPA with regular algorithms like a Montgomery ladder; DPA, which correlates thousands of traces with a guessed key byte via Hamming weight, with masking, hiding and blinding — or by keeping long-term keys in a side-channel-hardened engine or secure element and limiting how many operations an attacker can trigger."

Fault injection and tamper detection — concepts and countermeasures

ADVANCED▶
1. What is it?

Fault injection (FI) means deliberately disturbing a chip for a very short moment so that it computes something wrong — most usefully, so that a security decision such as if (signature_ok) goes the wrong way, or an instruction is effectively skipped. Side channels observe; fault injection interferes. You will be asked how to make firmware robust against it, so this card focuses on the defender's view.

2. Terms — fault types and the abstract fault model
  • Voltage glitch: a brief disturbance of the supply voltage.
  • Clock glitch: a disturbance of the clock signal (only if the chip runs from an external clock that can be manipulated).
  • EMFI (Electromagnetic Fault Injection): a strong, short magnetic pulse from a probe near the die.
  • Laser / optical FI: light on a decapsulated die; very precise, expensive.
  • Body-bias / temperature faults: less common.
  • Fault model: what the defender assumes a fault can do. The most common software-level models are instruction skip (one instruction behaves like a NOP), register/flag corruption (a value becomes 0 or all-ones), and data corruption during a load. Countermeasures are designed so that one such fault cannot cause a security failure.
3. Why the naive check is fragile — step by step
  1. Code: if (verify(img) == 0) boot(); else halt();
  2. Compiled: bl verify → cmp r0, #0 → bne halt → bl boot.
  3. If a fault turns the single bne into a no-op, execution falls through to boot with a bad image.
  4. If a fault zeroes r0 (a common corruption), the result looks like "0 = OK".
  5. So the security of the entire chain of trust can rest on one instruction. The Secure Boot lab's "single-fault model" toggle shows how the hardened decision code removes this single point of failure.

Communication security: TLS 1.3, mutual authentication, certificate pinning

INTERMEDIATE▶
1. What is it?

When a device talks to a cloud server, three things must be true: nobody can read the traffic (confidentiality), nobody can modify it (integrity), and each side is sure who the other is (authentication). TLS (Transport Layer Security) provides all three over TCP; DTLS does the same over UDP (e.g. CoAP/LwM2M).

2. Terms
  • Server authentication: the device checks the server's certificate chains to a trusted root CA it stores, and that the name matches.
  • Mutual TLS (mTLS): the device also presents its own certificate and proves it holds the private key. AWS IoT Core requires this.
  • Certificate pinning: the device accepts only a specific certificate or public key (or a specific CA), not any certificate from any public CA. Protects against a mis-issued certificate.
  • Cipher suite: the algorithm set, e.g. TLS_AES_128_GCM_SHA256 (TLS 1.3). Key exchange in TLS 1.3 is always ephemeral (EC)DHE → forward secrecy: stealing the long-term key later does not decrypt recorded sessions.
  • PSK (Pre-Shared Key) mode: both sides share a symmetric key; small and fast but key management is harder.
3. TLS 1.3 mutual-auth handshake, step by step
  1. ClientHello: device sends supported suites + an ephemeral ECDHE public key (X25519 or P-256) + random.
  2. ServerHello: server picks a suite, sends its ephemeral public key. Both now compute the ECDHE shared secret → handshake keys via HKDF (TLS 1.3's key schedule is built on HKDF).
  3. Server sends (encrypted) Certificate + CertificateVerify (signature over the handshake transcript) + CertificateRequest.
  4. Device verifies chain → pinned root, hostname, validity time (needs a trusted clock!), then the signature.
  5. Device sends its Certificate + CertificateVerify (signed by its private key — ideally inside the secure element) + Finished.
  6. Both derive application keys; data flows with AES-GCM.
4. Worked numbers — cost on an MCU
  • RAM: Mbed TLS with 16 KB input + 16 KB output record buffers ≈ 40–60 KB peak. Using the max_fragment_length extension (e.g. 4 KB) or TLS 1.3 record size limit cuts this a lot.
  • CPU: one ECDHE + one ECDSA sign + 2–3 ECDSA verifies (chain) on a Cortex-M4 at 80 MHz in software takes on the order of a second; hardware PKA or an SE brings it to tens of milliseconds. Use session resumption to avoid a full handshake every connection.
5. Annotated code — the mistakes that disable TLS security
/* WRONG: "it didn't connect in testing, so…" */
mbedtls_ssl_conf_authmode(&conf, MBEDTLS_SSL_VERIFY_NONE);    // accepts ANY server → MITM
/* WRONG: no hostname set → a valid cert for attacker.com is accepted */

/* RIGHT */
mbedtls_ssl_conf_authmode(&conf, MBEDTLS_SSL_VERIFY_REQUIRED); // fail the handshake on bad cert
mbedtls_ssl_conf_ca_chain(&conf, &pinned_root_ca, NULL);       // only our (pinned) root
mbedtls_ssl_set_hostname(&ssl, "a1b2c3-ats.iot.eu-west-1.amazonaws.com"); // SNI + name check
mbedtls_ssl_conf_own_cert(&conf, &dev_cert, &dev_key_in_SE);   // mutual TLS, key via PSA/SE
mbedtls_ssl_conf_min_tls_version(&conf, MBEDTLS_SSL_VERSION_TLS1_2);

Pinning trade-off: pin to your own CA or to a set of 2–3 roots, not to one leaf certificate — leaf certificates expire and rotate (often yearly or faster), and a device that pinned the old leaf can never reconnect. Always have an update path for the trust store.

Say it like this: "I use TLS 1.3 or 1.2 with ECDHE for forward secrecy and AES-GCM, verify the server chain against a pinned CA set plus the hostname and a trusted time source, and use mutual TLS with a per-device certificate whose private key lives in a secure element. The common failures are VERIFY_NONE left in from debugging, missing hostname checks, and pinning a leaf certificate that later expires."

SBOM, vulnerability management and secure manufacturing

INTERMEDIATE▶
1. What is it?

Security does not end at shipping. Firmware contains third-party code (RTOS, TCP/IP stack, TLS library, BLE stack, vendor HAL). When a vulnerability is published in one of them, you must answer within hours: which of our products and versions contain it, and is it exploitable? An SBOM makes that answer possible. Secure manufacturing makes sure the factory does not become the weak link.

2. Terms
  • SBOM (Software Bill of Materials): a machine-readable list of every component and version in a build. Formats: SPDX and CycloneDX. Required by the EU CRA and US federal procurement.
  • CVE (Common Vulnerabilities and Exposures): the public ID of a vulnerability, e.g. CVE-2021-31571 (FreeRTOS). CVSS: severity score 0–10.
  • VEX (Vulnerability Exploitability eXchange): a statement "product X is not affected by CVE-Y because the vulnerable function is not compiled in" — saves customers from false alarms.
  • PSIRT (Product Security Incident Response Team): the team that receives reports and coordinates fixes; coordinated disclosure: reporter and vendor agree on a publication date after a fix.
3. The vulnerability-management loop, step by step
  1. CI generates an SBOM for every release (from the build system / package manifests, e.g. Zephyr west spdx).
  2. A scanner matches SBOM entries against CVE feeds daily.
  3. Triage: is the vulnerable code compiled in and reachable? (e.g. a bug in the lwIP PPP module does not matter if PPP is disabled) → publish VEX.
  4. If affected: fix, bump security version, sign, roll out via staged FOTA (1% → 10% → 100%), monitor.
  5. Publish an advisory; keep your support period promise (CRA requires a defined support period).
4. Worked example — real embedded CVE class

The 2020 "Ripple20" (Treck TCP/IP) and "AMNESIA:33" (several open-source TCP/IP stacks incl. uIP, FNET, picoTCP) disclosures were mostly length/bounds bugs in packet parsers — exactly card 15. Vendors with SBOMs could answer "are we affected?" in a day; others spent weeks finding which products even contained the stack.

5. Secure manufacturing checklist
  • Signing keys and CA keys in HSMs, never on factory PCs; HSM quotas per production order.
  • Keys generated on-device or injected encrypted (ST SFI, NXP secure provisioning); factory sees no plaintext secrets.
  • Line software verifies lock state by read-back before marking a unit as passed; logs serial ↔ certificate ↔ test result.
  • Separate development/test keys from production keys; development-signed images must not boot on production units (different key hash).
  • Controlled handling of rejects/RMA units (they may be unlocked for analysis — wipe secrets first).
Say it like this: "Every release produces an SPDX or CycloneDX SBOM that we scan daily against CVE feeds; we triage reachability, publish VEX statements for non-affected products and ship fixes through signed, staged updates with a security-version bump. In the factory, keys stay in HSMs or are generated on-device, production and development keys are separated, and the line verifies each unit is locked before it can pass."

THE TWO IMPLEMENTATIONS
/* naive: time = 12 + 7 × (bytes compared) cycles */
int naive_eq(const uint8_t *a, const uint8_t *b, size_t n) {
    for (size_t i = 0; i < n; i++)
        if (a[i] != b[i]) return 0;   // exits early ← time depends on data
    return 1;
}
/* constant-time: time = 12 + 7 × n, always */
int ct_eq(const volatile uint8_t *a, const volatile uint8_t *b, size_t n) {
    uint8_t d = 0;
    for (size_t i = 0; i < n; i++) d |= a[i] ^ b[i];  // no branch on data
    return (int)(((uint32_t)d - 1u) >> 31);          // 1 iff d == 0
}

THE ARITHMETIC

  1. Received tag wrong in byte 0: naive compares 1 byte → 12 + 7 = 19 cycles (113 ns at 168 MHz).
  2. Byte 0 right, byte 1 wrong: it compares 2 bytes → 12 + 14 = 26 cycles. The 7-cycle (42 ns) difference is information about the secret.
  3. Measurement noise σ shrinks to σ/√N when you average N runs. σ = 16, N = 64 → 2 cycles of noise against a 7-cycle signal: clearly visible. That is why "it's only 42 ns" is not an argument.
  4. Constant-time: every input costs 12 + 7 × 8 = 68 cycles. The difference is 0, so averaging finds nothing.
  5. Trade-off: the constant-time version is never faster than the worst case of the naive one. For an 8–32-byte tag that is a few hundred nanoseconds — irrelevant.

HOW ENGINEERS PREVENT AND DETECT IT

  • Prevent: use the library's compare (mbedtls_ct_memcmp, CRYPTO_memcmp, psa_mac_verify which compares internally), or the AEAD's own tag check; never memcmp/strcmp on secrets.
  • Verify the compiler: inspect the disassembly — no conditional branch inside the loop that depends on the data.
  • Detect in CI: a unit test with DWT->CYCCNT (Cortex-M cycle counter) for matching vs non-matching inputs; tools like dudect apply the same statistical idea on a host build.
  • Limit exposure: rate-limit / lock out after N failed tags, and return one uniform error for "wrong length", "wrong tag", "bad padding" so the error code itself is not an oracle.
Say it like this: "An early-exit compare takes longer the more leading bytes are right, so its timing leaks how close a guess is and the check becomes much weaker than its length suggests. I compare secrets with a constant-time routine that touches every byte and never branches on the data — OR together the XORs — check the disassembly, test it with a cycle-counter unit test, and add rate limiting."

AES Mode Lab: why the mode matters

The 32×32 "image" below is 1 024 bytes, one byte per pixel. It is encrypted with real AES-128 (implemented in this page, FIPS-197) in three modes. Each row of 32 pixels = two 16-byte AES blocks. Each 16-byte ciphertext block is drawn as one colour derived from its value (equal blocks → equal colour), so you see exactly the structure an eavesdropper can see: which blocks repeat.

What to look at, step by step: 1. ECB: the padlock is still visible — every all-background 16-pixel block encrypts to the same ciphertext block, so equal blocks show the same colour stripe. 2. CBC and CTR: noise, because each block is mixed with the previous ciphertext (CBC) or a different counter (CTR). 3. Below: a design mistake to recognise in code review — two different images encrypted with CTR under the same key and the same nonce (for example because the nonce counter lived in RAM and restarted at 0 after reboot). Combining the two ciphertexts shows both images on top of each other: the confidentiality is gone even though the key is still secret. Switch to "fresh nonce per message" — the correct design — and the combination is pure noise.

⊕

WHY ECB LEAKS — THE NUMBERS

  1. Image = 32 rows × 32 bytes = 1 024 bytes = 64 blocks of 16 bytes.
  2. Background rows are 16 identical bytes (0x10) per block. AES is a deterministic function: AESK(0x10…10) is the same 16 bytes every time.
  3. So every all-background block encrypts to the same ciphertext block. The counter under the ECB image shows how many of the 64 ciphertext blocks are duplicates.
  4. CBC XORs each block with the previous ciphertext first, CTR XORs with a keystream from a different counter: no duplicates (count = 0).

WHY NONCE REUSE IS A DESIGN BUG — THE ALGEBRA

C1 = A ⊕ KS        C2 = B ⊕ KS        (same key + nonce → same KS)
C1 ⊕ C2 = A ⊕ KS ⊕ B ⊕ KS = A ⊕ B   ← keystream cancels
Structured data (headers, zeros, fixed formats) makes A⊕B
readable, so confidentiality is lost without touching the key.
In GCM the same mistake also undermines the authentication tag.

PREVENTION (design rules):
 • nonce = persistent boot counter (incremented BEFORE use) ‖ msg counter
 • or 96-bit random nonce from a health-checked TRNG/DRBG
 • or a fresh session key per boot via HKDF
 • or a misuse-resistant AEAD (AES-GCM-SIV) where reuse only leaks equality
 • unit test: encrypt twice across a simulated reboot → nonces must differ
Say it like this: "ECB is deterministic per block, so identical plaintext blocks give identical ciphertext and images or structured records leak their pattern. CBC and CTR hide that, but CTR and GCM are stream modes: reuse a nonce under the same key and C1 XOR C2 equals P1 XOR P2, and in GCM authentication breaks too. So I use an AEAD with a guaranteed-unique nonce across reboots."
