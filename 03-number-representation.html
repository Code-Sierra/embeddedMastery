How numbers really live in bits: integers, fixed-point and floating-point

Reference part: STM32F407 (Arm Cortex-M4F, 168 MHz, single-precision FPU, DSP extension), with Cortex-M0/M0+ (no divider, no FPU, no DSP) used as the contrast case. Every card starts in plain words, defines each term, walks through the mechanism step by step with real numbers, shows wrong vs right code, and ends with a "Say it like this" answer for the interview. Read them in order — later cards build on earlier ones.

01BEGINNER

Bits, unsigned binary and hexadecimal

▶

A computer stores every number as a row of switches that are either off (0) or on (1). Unsigned binary is the simplest way to turn such a row into a number: each position is worth a power of two, and you add up the positions that are on. Every other representation on this page (signed integers, fixed-point, floating-point) is a different rule for reading the same row of bits.

1. TERMS YOU NEED
bit
One binary digit, 0 or 1 ("binary digit").
N-bit word
A group of N bits treated as one value. On a Cortex-M4 a "word" is 32 bits (4 bytes), a "halfword" is 16 bits, a "byte" is 8 bits.
LSB / MSB
Least Significant Bit (bit 0, worth 20 = 1) and Most Significant Bit (bit N−1, worth 2N−1).
hexadecimal (hex)
Base-16 notation, digits 0–9 and A–F. One hex digit is exactly 4 bits (a nibble), which is why engineers use it: 0x7F is easier to read than 0111 1111.
wrap-around (modulo 2N)
When a result is too big for N bits, the extra high bits are simply dropped. What remains is the true result minus a multiple of 2N.
2. HOW TO READ AN UNSIGNED NUMBER — STEP BY STEP
  1. Write the bits with bit 0 on the right. Example 8-bit value: 1011 0110.
  2. Write the weight of each position above it: 128 64 32 16 | 8 4 2 1.
  3. Add the weights where the bit is 1: 128 + 32 + 16 + 4 + 2 = 182.
  4. To get hex, split into nibbles: 1011 = 11 = B, 0110 = 6 → 0xB6. Check: 11×16 + 6 = 182. ✔
  bit:     7    6    5    4  |  3    2    1    0

 value:    1    0    1    1  |  0    1    1    0
           └──── 0xB ──────┘    └──── 0x6 ─────┘

4. WHAT HAPPENS WHEN IT DOESN'T FIT — WORKED EXAMPLE
  1. uint8_t a = 200, b = 100;
  2. True sum = 300 = binary 1 0010 1100 (9 bits).
  3. Only 8 bits fit, so bit 8 (worth 256) is dropped: 300 − 256 = 44 (0010 1100 = 0x2C).
  4. In C, unsigned arithmetic is defined to wrap like this (C11 §6.2.5p9: "reduced modulo the number that is one greater than the largest value"). It is never undefined behaviour for unsigned types.

The same rule makes unsigned subtraction work for timers. A 32-bit tick counter that wraps from 0xFFFF_FFF0 to 0x0000_0010 still gives the right elapsed time: 0x10 − 0xFFFFFFF0 = 0x20 (32 ticks), because the wrap of the counter and the wrap of the subtraction cancel out.

✖ WRONG — breaks at counter wrap 
if (now >= start + TIMEOUT)   /* start+TIMEOUT can wrap  */
    timeout();                /* to a small number, so   */
                              /* this fires immediately  */
✔ RIGHT — wrap-safe elapsed time 
if ((uint32_t)(now - start) >= TIMEOUT)
    timeout();   /* unsigned subtraction wraps exactly
                    the same way the counter did */
5. WHAT GOES WRONG IF…
  • …you count down with an unsigned loop variable: for (uint8_t i = 9; i >= 0; i--) never ends. When i is 0, i-- wraps to 255, and i >= 0 is always true for an unsigned value. Symptom: the firmware hangs in the loop or writes past an array. GCC warns with -Wtype-limits ("comparison is always true").
  • …you use a uint8_t index for a 300-element buffer: the index wraps at 255 and silently overwrites the start of the buffer.
"Unsigned binary gives each bit a weight of 2i, so N bits hold 0 to 2N−1. In C, unsigned overflow is well defined: the result is reduced modulo 2N, which is exactly why now − start on a uint32_t tick counter stays correct across the wrap. I use hex because one hex digit is exactly four bits, so I can read bit fields straight from a register dump."
02BEGINNER

Negative numbers: sign-magnitude, one's complement, two's complement (and why two's complement won)

▶

Bits have no minus sign, so we need a rule that says which patterns mean negative numbers. Three rules were used historically. Every modern CPU (Arm, x86, RISC-V) uses two's complement, and since C23 the C standard requires it. To understand why, you need to see all three side by side.

1. TERMS
sign bit
The MSB. In all three schemes, 1 in the MSB means "negative".
sign-magnitude
MSB = sign, the other bits = the size (magnitude) of the number, like writing "−5" on paper.
one's complement
To negate, invert (flip) every bit. "Complement" = the bit-wise NOT.
two's complement
To negate, invert every bit and then add 1. Equivalently: the MSB has a negative weight, −2N−1, and all other bits have their usual positive weights.
2. THE SAME VALUE IN THE THREE SCHEMES — WORKED EXAMPLE (−5 IN 8 BITS)
  1. Start with +5 = 0000 0101.
  2. Sign-magnitude: set the sign bit: 1000 0101 (0x85).
  3. One's complement: flip every bit of +5: 1111 1010 (0xFA).
  4. Two's complement: flip every bit and add 1: 1111 1010 + 1 = 1111 1011 (0xFB).
  5. Check two's complement using the weight rule: −128 + 64 + 32 + 16 + 8 + 2 + 1 = −128 + 123 = −5. ✔

3. WHY TWO'S COMPLEMENT WON — THE HARDWARE ARGUMENT
  1. One adder for everything. In two's complement, adding signed numbers uses exactly the same binary adder as unsigned numbers. Example 4-bit: −3 + 5 → 1101 + 0101 = 1 0010; drop the carry → 0010 = 2. ✔ The CPU does not even need to know whether the values are signed. In sign-magnitude, the adder must compare signs and magnitudes and sometimes subtract instead.
  2. Subtraction is free. a − b = a + (~b) + 1. The ALU feeds the inverted b and sets carry-in = 1. Arm's SUBS does exactly this.
  3. Only one zero. Sign-magnitude and one's complement both have +0 and −0, so "is it zero?" needs two comparisons, and equality tests get messy.
  4. Multiplying the low half is identical. The lower N bits of an N×N product are the same for signed and unsigned operands, so Cortex-M has one MUL instruction for both (only the 64-bit SMULL/UMULL need separate versions).
  5. Sign extension is trivial: copy the MSB into the new upper bits (card 03).

The price is asymmetry: there is one more negative value than positive values (−8…+7 in 4 bits; −2 147 483 648 … +2 147 483 647 in 32 bits). That one extra value, INT_MIN, causes a whole family of bugs (card 04).

5. WHAT GOES WRONG IF…
  • …you assume -x is always positive when x is negative: −(−128) in 8 bits is +128, which does not exist, so the pattern 1000 0000 stays −128. Same for INT32_MIN.
  • …you decode a sensor's sign-magnitude field as two's complement: some sensors (e.g. certain temperature and magnetometer ICs, and the IEEE-754 float sign itself) use sign-magnitude. 0x85 read as int8 gives −123 instead of −5. Always check the datasheet's data-format section.
"Two's complement gives the MSB a weight of −2N−1. It won because the same adder handles signed and unsigned numbers, subtraction is just add-the-inverse-plus-one, there is only one zero, and sign extension is copying the top bit. The cost is an asymmetric range: an 8-bit value goes from −128 to +127, so negating the minimum overflows."
03BEGINNER

Sign extension, truncation and C's integer promotion rules

▶

Values constantly move between widths: an 8-bit register is read into a 32-bit variable, a 32-bit result is stored into a 16-bit field. Widening must keep the value the same; narrowing throws away high bits. C also silently widens small types before doing arithmetic. Most "impossible" integer bugs come from these three hidden conversions.

1. TERMS
zero extension
Widening an unsigned value by filling the new upper bits with 0. 0xF0 → 0x0000_00F0 (240 stays 240).
sign extension
Widening a signed value by copying its sign bit into the new upper bits. 0xF0 (−16) → 0xFFFF_FFF0 (still −16).
truncation
Narrowing by keeping only the low bits. 0x0001_2345 → uint16 0x2345.
integer promotion
C rule: any operand of type char, short, int8_t, int16_t, uint8_t, uint16_t is converted to int (32-bit on Arm) before arithmetic.
usual arithmetic conversions
When the two operands of a binary operator have different types after promotion, both are converted to a common type. If one is unsigned int and the other is int, the int is converted to unsigned.
2. WHAT THE CPU DOES (CORTEX-M4 INSTRUCTIONS)
  1. LDRSB/LDRSH load a byte/halfword and sign-extend to 32 bits; LDRB/LDRH zero-extend.
  2. SXTB/SXTH sign-extend a register; UXTB/UXTH zero-extend (1 cycle each).
  3. SBFX r0, r1, #4, #12 extracts a 12-bit signed field starting at bit 4 and sign-extends it — perfect for packed sensor data. (UBFX for unsigned.)
  4. Narrowing needs no instruction: STRB/STRH just store the low bits.
3. WORKED EXAMPLE: A 12-BIT TWO'S-COMPLEMENT SENSOR VALUE

Many accelerometers return a 12-bit signed value in a 16-bit register. Raw read: 0x0FF6.

  1. Bit 11 (the 12-bit sign bit) of 0x0FF6 = 1, so the value is negative.
  2. As a 12-bit number: 0xFF6 = 4086. Subtract 212 = 4096 → −10.
  3. Sign extending to 16 bits means copying bit 11 into bits 15..12: 0x0FF6 → 0xFFF6, which as int16 is −10. ✔
✖ WRONG — reads +4086 
uint16_t raw = read_reg();      /* 0x0FF6           */
int16_t  v   = (int16_t)raw;    /* 0x0FF6 = +4086,
                                   bit 15 is 0, so the
                                   cast does nothing   */
✔ RIGHT — portable sign extension 
static inline int32_t sext(uint32_t x, unsigned bits)
{
    uint32_t m = 1u << (bits - 1);  /* sign-bit mask: 0x800 */
    x &= (1u << bits) - 1;          /* keep low 12 bits    */
    return (int32_t)((x ^ m) - m);  /* flip sign bit, then
                                       subtract its weight */
}
/* sext(0x0FF6,12): x^m = 0x07F6 = 2038; 2038-2048 = -10 */

Why the (x ^ m) − m trick works: XOR with the sign-bit mask turns a negative 12-bit value (sign bit 1) into its value + 2048 with the sign bit cleared, and a positive value into value + 2048 too (sign bit set to 1 contributes +2048). Subtracting 2048 removes the offset in both cases. It uses no shifts of negative numbers, so it has no implementation-defined behaviour.

5. WHAT GOES WRONG IF…
  • …you check a signed length against a signed limit and then pass it to memcpy: int len = rx_len(); if (len > MAX_LEN) return; memcpy(buf, src, len);. A corrupted frame with len = -1 passes the check (−1 is not greater than MAX_LEN), then memcpy's size_t parameter converts −1 to 4 294 967 295 and the copy runs through the whole RAM → HardFault. Use unsigned lengths, or check len < 0 too, and build with -Wsign-compare -Wconversion.
  • …you port code to a 16-bit-int MCU (MSP430, AVR): int is 16 bits there, so uint8_t*uint8_t or raw*3300 overflows in the promoted int. Code that worked on Cortex-M breaks.
"Widening a signed value copies the sign bit (sign extension), widening unsigned fills zeros, and narrowing keeps the low bits. In C, anything smaller than int is promoted to int before arithmetic, and mixing int with unsigned int converts the int to unsigned — so −1 < 1u is false. For packed sensor fields I sign-extend with (x ^ m) − m or SBFX, and I build with -Wconversion -Wsign-compare to catch silent conversions."
04INTERMEDIATE

Range asymmetry and the INT_MIN traps: −INT_MIN, abs(INT_MIN), INT_MIN / −1

▶

In two's complement the most negative value has no positive partner. For 32 bits, INT_MIN = −2 147 483 648 exists but +2 147 483 648 does not (the maximum is +2 147 483 647). Any operation whose result would be +2 147 483 648 overflows. Interviewers love this because it hides in "obviously safe" code like abs().

1. TERMS
INT_MIN / INT_MAX
Limits from <limits.h>: −2 147 483 648 (0x8000_0000) and +2 147 483 647 (0x7FFF_FFFF) for 32-bit int. INT32_MIN/INT32_MAX in <stdint.h> are the same on Arm.
undefined behaviour (UB)
The C standard places no requirements on what happens. The compiler may assume UB never occurs and optimise on that assumption, so the result is not just "a wrong number".
2. WALKTHROUGH: WHY −INT_MIN == INT_MIN IN HARDWARE
  1. INT_MIN = 1000 0000 … 0000 (0x8000_0000).
  2. Negate = invert + 1: invert → 0111 1111 … 1111 (0x7FFF_FFFF); add 1 → 1000 0000 … 0000 = 0x8000_0000.
  3. We are back at INT_MIN. The Arm RSBS r0, r0, #0 (negate) instruction sets the V (overflow) flag to tell you it happened, but C code never looks at V.
  4. In C, -x with x == INT_MIN is signed overflow → UB. In practice on Cortex-M you get INT_MIN back.

4. WORKED EXAMPLE: THE abs() BUG IN A FAULT CHECK
int32_t err = setpoint - measured;  /* a broken sensor reports INT32_MIN    */

The protection fails exactly in the most broken situation. Even worse, because abs(x) > LIMIT is UB for INT_MIN, GCC may rewrite abs(x) < 0 to false, so a "defensive" check for a negative result can be deleted by the optimiser.

✖ WRONG 
if (abs(err) > ERR_LIMIT) fault();
✔ RIGHT — compare without negating 
if (err > ERR_LIMIT || err < -ERR_LIMIT) fault();
/* -ERR_LIMIT is safe: ERR_LIMIT is a small positive
   constant, so its negation always exists.          */

/* or: magnitude in unsigned, which is always defined */
uint32_t mag = (err < 0) ? 0u - (uint32_t)err : (uint32_t)err;
/* INT32_MIN → 0x80000000u = 2147483648u  ✔          */

Why the unsigned version works: (uint32_t)err is defined (the value modulo 232, here 0x8000_0000), and unsigned negation 0u − x is also defined modulo 232: 0 − 0x8000_0000 = 0x8000_0000 = 2 147 483 648 as unsigned, the correct magnitude.

5. THE LITERAL TRAP: WHY limits.h WRITES (−2147483647 − 1)
  1. In C, -2147483648 is not one token. It is unary minus applied to the literal 2147483648.
  2. 2147483648 does not fit in int, so the literal gets type long or long long (64-bit) — or, in C89, unsigned long!
  3. So -2147483648 has a 64-bit type, and sizeof(-2147483648) is 8. In C89 it was even a positive unsigned number.
  4. That is why <limits.h> defines INT_MIN as (-2147483647 - 1): both pieces fit in int.
6. WHAT GOES WRONG IF…
  • …you print INT_MIN with a home-made itoa that does if (n < 0) { putc('-'); n = -n; }: n stays negative, and the digit loop (n % 10 gives negative remainders) prints garbage like "-./,)(-*,(" or nothing. Fix in the Q&A bank (itoa question).
  • …you saturate a Q31 negation: −(−1.0) in Q31 = +1.0 is not representable; CMSIS arm_negate_q31 saturates to 0x7FFF_FFFF for exactly this reason.
"Two's complement has one more negative value than positive, so INT_MIN has no positive counterpart. −INT_MIN, abs(INT_MIN) and INT_MIN/−1 all overflow, which is undefined behaviour in C. On a Cortex-M the hardware just returns INT_MIN — SDIV doesn't trap — while x86 raises a divide error. So I never negate untrusted values: I compare against both +LIMIT and −LIMIT, or compute the magnitude in unsigned arithmetic."
05INTERMEDIATE

Overflow detection for add, subtract and multiply (C rules, compiler builtins, CPU flags C and V)

▶

Overflow means the true mathematical result does not fit in the destination type. The hardware always produces some bit pattern; the question is whether you can tell that it is wrong. The CPU tells you through status flags, but plain C hides those flags, and for signed types C even declares the overflow itself to be undefined behaviour. So you need to know both levels: what the silicon does, and how to write C that detects overflow legally.

1. TERMS
APSR
Application Program Status Register on Cortex-M. Bits 31..28 are the condition flags N, Z, C, V; bit 27 is Q (sticky saturation flag, card 06).
N (Negative)
Copy of bit 31 of the result.
Z (Zero)
1 if the result is exactly zero.
C (Carry)
For addition: 1 if there was a carry out of bit 31 → the unsigned result overflowed. For subtraction on Arm: C = 1 means no borrow (a ≥ b unsigned). x86 is the opposite (CF = 1 means borrow) — a classic trick question.
V (oVerflow)
1 if the signed (two's complement) result overflowed.
-fwrapv / -ftrapv
GCC options: -fwrapv makes signed overflow wrap (defined); -ftrapv calls abort() on overflow. -fsanitize=signed-integer-overflow (UBSan) reports it at runtime on a host build.
2. HOW THE ALU SETS C AND V — STEP BY STEP (8-BIT EXAMPLES)
  1. Add the two patterns as unsigned binary, producing 9 bits.
  2. C = bit 8 (the carry out). The low 8 bits are the result.
  3. V = 1 if both operands have the same sign and the result has the opposite sign. (Adding two positives can't give a negative, and vice versa. Adding numbers of different signs can never overflow.)

Key insight: the bits of the result are identical for signed and unsigned. Only the interpretation differs, which is why the CPU computes both flags every time and lets software pick the right one (BCS/BHS for unsigned, BVS for signed).

3. WHY SIGNED OVERFLOW IS UB — AND WHY THAT MATTERS

Because the standard says signed overflow cannot happen in a correct program, the optimiser is allowed to reason as if it never does:

✖ WRONG — check is deleted at -O2 
int add_checked(int a, int b) {
    int s = a + b;            /* overflow here is UB      */
    if (b > 0 && s < a)       /* compiler: "a+b<a with b>0 */
        return ERROR;         /* is impossible" → removed */
    return s;
}
✔ RIGHT — test BEFORE the operation 
#include <limits.h>
int add_checked(int a, int b, int *out) {
    if ((b > 0 && a > INT_MAX - b) ||   /* would exceed max */
        (b < 0 && a < INT_MIN - b))     /* would go below   */
        return -1;
    *out = a + b;                        /* now provably safe */
    return 0;
}

Even simpler and fastest: GCC/Clang builtins, which compile to the actual flag check (ADDS + BVS/VS-conditional on Arm):

int32_t s;
if (__builtin_add_overflow(a, b, &s)) { /* overflowed; s holds the wrapped value */ }
if (__builtin_sub_overflow(a, b, &s)) { ... }
if (__builtin_mul_overflow(a, b, &s)) { ... }   /* uses SMULL and checks the high word */
/* C23 standardises these as ckd_add / ckd_sub / ckd_mul in <stdckdint.h> */

Unsigned overflow is defined, so the simple post-check is legal: uint32_t s = a + b; if (s < a) /* carry */.

4. MULTIPLY OVERFLOW — WORKED EXAMPLE
  1. A 32×32 multiply needs up to 64 bits. Cortex-M4 SMULL rlo, rhi, ra, rb produces the full signed 64-bit product in 1 cycle (UMULL for unsigned). Cortex-M0/M0+ have no long multiply; the compiler calls __aeabi_lmul.
  2. The product fits in int32 if and only if the high word equals the sign-extension of the low word, i.e. hi == (lo >> 31) (all 0s or all 1s).
  3. Example: 70 000 × 40 000 = 2 800 000 000 = 0x0000_0000_A6E4_9C00. hi = 0, but lo's bit 31 is 1, so as int32 it would read −1 494 967 296 → overflow.
int mul_ok(int32_t a, int32_t b, int32_t *out) {
    int64_t p = (int64_t)a * b;          /* cast FIRST: one SMULL, full 64-bit product */
    if (p > INT32_MAX || p < INT32_MIN)  /* doesn't fit in 32 bits                     */
        return 0;
    *out = (int32_t)p;
    return 1;
}
/* WRONG: (int64_t)(a * b) — the multiply is done in 32 bits (UB on overflow),
   and only the already-broken result is widened. */
5. WHAT GOES WRONG IF…
  • …you write for (int i = 0; i <= n; i++) with n == INT_MAX: the loop never ends, and the compiler may assume it terminates and vectorise around that assumption.
  • …you rely on x + 1 > x to detect the maximum: GCC folds it to true for signed x.
  • …you port flag logic from x86 assembly: "carry set after SUB" means borrow on x86 but no borrow on Arm. BCC after CMP on Arm means "unsigned lower".
"The ALU sets C for unsigned overflow and V for signed overflow; V is set when two same-sign operands give an opposite-sign result. In C, signed overflow is undefined, so I must check before the operation — compare against INT_MAX − b — or use __builtin_add_overflow, which compiles to ADDS plus a branch on V. For multiplication I widen one operand first so the CPU does a 32×32→64 SMULL, then check the product against the int32 range."
06INTERMEDIATE

Saturation arithmetic: clamp instead of wrap (C, SSAT/USAT, QADD and the DSP extension)

▶

Saturation means: if the result is too big, return the biggest value instead; if it is too small, return the smallest. Wrap-around turns "slightly too loud" into "maximum negative" — a full-scale click in audio, or a motor command flipping from full forward to full reverse. Saturation turns it into "as loud as possible", which is almost always the safer error.

1. TERMS
saturate / clamp
Limit a value to [min, max] of the destination type.
DSP extension
Optional set of Armv7E-M instructions present on Cortex-M4, M7 and (optionally) M33/M35P/M55: saturating add/sub, SIMD on packed 8/16-bit values, dual 16-bit multiply-accumulate. Not on M0/M0+/M3.
SSAT / USAT
"Signed/Unsigned SATurate": clamp a 32-bit register to an n-bit signed (or unsigned) range. Present on all Armv7-M (M3, M4, M7). 1 cycle.
QADD / QSUB
Saturating 32-bit add/subtract (DSP extension). QDADD/QDSUB double one operand with saturation first. 1 cycle.
Q flag
APSR bit 27. Set to 1 by any saturating instruction that actually clipped. It is sticky: it stays 1 until software clears it, so you can run a whole filter and then check once "did anything clip?".
2. WORKED EXAMPLE: int16 AUDIO MIX
  1. Sample a = 30 000, sample b = 10 000. True sum = 40 000. int16 max = 32 767.
  2. Wrapping: 40 000 − 65 536 = −25 536. The speaker jumps from almost full positive to strongly negative → loud click.

Integer division and modulo with negative numbers (truncation toward zero, % sign, shifts)

▶

Integer division throws away the fractional part — but which way does it round when the answer is negative? Since C99 the answer is fixed: toward zero. That choice makes % return negative numbers for negative dividends, which breaks the "wrap an index into a ring buffer" idiom, and it means x >> 1 is not the same as x / 2.

1. TERMS
dividend, divisor, quotient, remainder
In a / b = q remainder r: a is the dividend, b the divisor, q the quotient, r the remainder.
truncation toward zero
Drop the fraction: 3.5 → 3, −3.5 → −3. What C99 and later require for /.
floor division
Round toward −∞: −3.5 → −4. What Python's // does, and what an arithmetic right shift does.
arithmetic shift right (ASR)
Shift right while copying the sign bit into the top. Arm ASR. Right-shifting a negative signed value in C is implementation-defined (GCC and Arm compilers use ASR).
2. THE RULE C GUARANTEES

For any b ≠ 0 (and no overflow): (a / b) * b + (a % b) == a. Since / truncates toward zero, % must take the sign of the dividend a.

The cost of division, dividing by constants with multiply-and-shift, and surviving on a Cortex-M0

▶

Division is the slowest basic integer operation. A Cortex-M4 has a hardware divider that takes 2–12 cycles; a Cortex-M0/M0+ has no divide instruction at all, so every / and % becomes a library call costing tens to over a hundred cycles. Compilers replace division by a constant with a multiply and a shift; you should know how, and how to do the same thing yourself for divisors known only at run time.

1. TERMS
SDIV / UDIV
Signed/unsigned 32-bit divide instructions on Armv7-M (M3, M4, M7). 2–12 cycles on M4 depending on operand sizes ("early termination").
__aeabi_idiv / __aeabi_uidiv
Run-time library functions defined by the Arm EABI that the compiler calls when there is no divide instruction (M0, M0+, M23 without divider). Typically 30–100+ cycles in libgcc; optimised assembly versions reach ~20–40.
magic number / reciprocal multiplication
Replace x / d with (x × m) >> s where m ≈ 2s/d, rounded up, chosen so the result is exact for every 32-bit x.
UMULL
Unsigned 32×32→64 multiply, 1 cycle on M4. The magic-number method needs the high half of this product.
2. HOW x / 10 BECOMES A MULTIPLY — STEP BY STEP
  1. We want x/10 = x × (1/10). 1/10 is not an integer, so scale it: 1/10 = (235/10) / 235.
  2. 235/10 = 3 435 973 836.8. Round up to m = 3 435 973 837 = 0xCCCC_CCCD.
  3. Then x/10 = (x × 0xCCCCCCCD) >> 35. The error from rounding m up is (0.2/235) × x ≤ 0.2 × 232/235 = 0.025, too small to change the integer part for any 32-bit x (proved by the standard Granlund–Montgomery bound; you can also check it exhaustively).
  4. On Cortex-M4 this is: UMULL lo, hi, x, m (1 cycle) then LSRS r0, hi, #3 (35 − 32 = 3). Two cycles instead of up to 12 — and on M0 it replaces a ~40-cycle call, although M0 also lacks UMULL so the compiler uses a few 16×16 MULs instead.
  5. Check with x = 12345: 12345 × 3435973837 = 42 417 097 017 765; >> 35 = 42 417 097 017 765 / 34 359 738 368 = 1234.5 → 1234 ✔.

   Precompute a Q32 reciprocal so the hot path has no division.          */
static uint32_t recip_q32;                   /* ≈ 2^32 / n                     */
void set_len(uint32_t n) {                   /* runs once; requires n >= 2     */
    recip_q32 = (uint32_t)((0xFFFFFFFFull + n) / n);  /* ceil(2^32 / n)        */
}

4. OTHER WAYS TO AVOID DIVISION
  • Choose power-of-two sizes: average 16 samples, not 10, and shift by 4.
  • Compare instead of divide: if (a / b > c) → if (a > c * b) for positive values (check that c*b can't overflow — widen to 64 bits if needed).
  • Fold constants: mv = raw * 3300 / 4096 uses a shift; raw * 3300 / 4095 forces a real division (or magic multiply). The 0.02 % difference is far below the ADC's own error.
  • Hardware helpers: Raspberry Pi RP2040 (dual Cortex-M0+) has a memory-mapped divider (8 cycles) in its SIO block; some STM32 parts have a CORDIC/FMAC co-processor (STM32G4) — vendor-specific.
5. WHAT GOES WRONG IF…
  • …you put % BUFFER_SIZE in a 1 MHz ISR on an M0 with BUFFER_SIZE = 100: each __aeabi_uidivmod call can cost ~50 cycles at 48 MHz ≈ 1 µs — the entire ISR budget. Making the size 128 turns it into one AND.
  • …you hand-write a magic number with too small a shift: it is right for small test values and wrong for large ones. Always verify across the full input range (exhaustively for 32-bit is only 4 × 109 cases — minutes on a PC).
"Division is slow: 2 to 12 cycles with SDIV on a Cortex-M4, and a library call of tens of cycles on an M0, which has no divider. Compilers turn division by a constant into a multiply by a scaled reciprocal and a shift — x/10 is the high word of x times 0xCCCCCCCD, shifted right by 3. In hot code I pick power-of-two sizes, precompute reciprocals for run-time-constant divisors, and rewrite comparisons to avoid dividing at all."

Scaling and units in firmware: millivolts, 0.1 °C and order of operations

▶

Most firmware never needs fractional numbers if you pick a smaller unit. Instead of storing 3.271 V as a float, store 3271 mV as an integer. Instead of 23.4 °C, store 234 in units of 0.1 °C. This is called scaled integer (or "decimal fixed-point") arithmetic. It is exact for the values you care about, fast on any CPU, and safe in interrupts. The only skills required are choosing the unit and ordering the operations so intermediates neither overflow nor lose precision.

1. TERMS
scale factor
The value of one count. "Temperature in 0.1 °C" means 1 count = 0.1 °C; a stored 234 means 23.4 °C.
ADC
Analog-to-Digital Converter. The STM32F407 ADC is 12-bit: it returns 0…4095 for 0…VREF (typically 3.3 V).
intermediate
A temporary value inside an expression, e.g. raw * 3300 before the division. Its type, not the final variable's type, decides whether it overflows.
LSB (as a unit)
The physical value of one ADC count: 3300 mV / 4096 = 0.806 mV.
2. RECIPE: CONVERTING AN ADC READING TO MILLIVOLTS — STEP BY STEP
  1. Formula: mV = raw × 3300 / 4096.
  2. Multiply first, then divide. If you divide first, 3300 / 4096 = 0 in integer arithmetic and every reading becomes 0.
  3. Check the intermediate range: max raw × 3300 = 4095 × 3300 = 13 513 500. That needs 24 bits → fits in int32/uint32 easily (max ≈ 2.1 × 109), but would overflow a 16-bit intermediate (max 32 767 / 65 535).
  4. Round instead of truncate: add half the divisor before dividing: (raw × 3300 + 2048) / 4096. Truncation always errs low by up to 1 mV; rounding halves the worst-case error.
  5. Prefer a power-of-two divisor so the division is a shift: (raw * 3300u + 2048u) >> 12.

Worked: raw = 2482 → 2482 × 3300 = 8 190 600; + 2048 = 8 192 648; >> 12 = 8 192 648 / 4096 = 2000.16 → 2000 mV. ✔ (2482/4096 × 3.3 V = 1.99966 V.)

3. WORKED EXAMPLE: TEMPERATURE IN 0.1 °C FROM A LINEAR SENSOR

A TMP36-style sensor outputs 500 mV at 0 °C and 10 mV/°C. So T(°C) = (mV − 500) / 10, and T in 0.1 °C = (mV − 500) × 10 / 10 = mV − 500. Choosing the unit to match the sensor slope makes the conversion a single subtraction.

  2. Range check: −40 °C … +125 °C → t_x10 = −400 … 1250 → fits int16 (±32 767) with lots of headroom.
  3. Display without floats: printf("%d.%d", t / 10, abs(t % 10)) — but watch out for −0.5 °C (see below).

Rule of thumb: summing K values of B bits needs B + ⌈log2K⌉ bits. 12-bit samples × 16 = 12 + 4 = 16 bits unsigned — which already overflows a signed int16 (15 value bits).

5. WHY AVOID FLOATS IN ISRs
  • No FPU (M0/M0+/M3): every float operation is a soft-float library call (__aeabi_fadd ≈ 50–100 cycles, __aeabi_fdiv more). A scaled integer add is 1 cycle.
  • With FPU (M4F): the first FP instruction in the ISR causes the lazily-reserved FPU registers (S0–S15, FPSCR) to be stacked, adding ~17 extra memory writes to the interrupt, and an RTOS must then save S16–S31 on context switch (card 19).
  • Determinism: integer timing does not depend on the values; soft-float timing does (normalisation loops, subnormals).
"I pick the unit so values are integers — millivolts, 0.1 °C, milliamps — and store them in int16 or int32. I multiply before dividing, check the worst-case intermediate (4095 × 3300 needs 24 bits, so int32), round by adding half the divisor, and prefer power-of-two divisors so the divide is a shift. That keeps ISRs fast, deterministic and float-free."

Fixed-point and Q-format: Qm.n notation, Q15, Q31, range, resolution and conversion

▶

Fixed-point stores a fractional number as an ordinary integer that is understood to be divided by a fixed power of two. Card 09 used powers of ten (0.1 °C); fixed-point uses powers of two (1/32768) so that rescaling is a shift instead of a division. The CPU only ever sees integers — the "binary point" exists only in the programmer's head and in the comments. This is how DSP filters, motor control loops and audio run fast on MCUs without an FPU.

1. TERMS
binary point
The binary equivalent of the decimal point. Bits to its right are worth 1/2, 1/4, 1/8, …
Qm.n (Arm/academic notation)
A signed number with m integer bits and n fractional bits, plus one sign bit: total width = 1 + m + n. Q15 = Q0.15 (16 bits), Q31 = Q0.31 (32 bits), Q4.11 = 16 bits.
Qn (TI notation)
Texas Instruments' IQmath and many DSP books give only the fractional bits: "Q15" means 15 fraction bits in whatever word size is in use. Some authors count the sign bit inside m. Always state the total width: "Q4.11 in int16_t".
UQm.n
Unsigned version: m + n bits, no sign bit.
resolution (LSB)
The value of one count: 2−n. Q15: 2−15 = 0.000030518.
range
Signed Qm.n covers −2m … 2m − 2−n. Q15: −1.0 … +0.999969.

  • …two modules disagree on the format (one writes Q4.11, the other reads Q15): values are off by exactly 24 = 16×. If a value is wrong by a power of two, suspect a Q-format mismatch first.
  • …you want exactly +1.0 in Q15: it does not exist. Use 0x7FFF (0.99997) or move to Q1.14.

static inline int16_t q15_mul(int16_t a, int16_t b)
{
    int32_t p = (int32_t)a * b;   /* Q30, exact, can't overflow */
    p += 1 << 14;                 /* round to nearest           */
    p >>= 15;                     /* back to Q15 (ASR = floor)  */
    if (p > 32767) p = 32767;     /* only -1*-1 gets here       */
    return (int16_t)p;            /* or: __SSAT(p, 16)          */
}

Note on y2: some code deliberately uses >> 16 on Q31 data because the Arm SMULWB/SMMUL instructions return the top 32 bits of a product (an implied >> 16 or >> 32). Then it must compensate with a left shift by 1 — mixing the two conventions is a common bug.

3. Q31 × Q31 — WHY YOU NEED 64 BITS
  1. Q31 × Q31 = Q62 in a 64-bit product. A 32-bit intermediate keeps only the bottom 32 bits — the least important ones.
  2. Correct: int64_t p = (int64_t)a * b; → one SMULL (1 cycle on M4).
  3. Round and shift: (p + (1LL << 30)) >> 31, then saturate to int32 (again only −1 × −1 overflows).
  4. Fast Arm alternative: SMMULR r0, a, b returns (a×b + 0x8000_0000) >> 32 = a rounded Q30 result in 1 instruction; shift left 1 (with saturation, QADD r0,r0,r0) to get Q31 — losing the last bit of precision.
  5. On a Cortex-M0 (no SMULL) the 64-bit multiply is a call to __aeabi_lmul; Q31 maths is expensive there, so prefer Q15.
static inline int32_t q31_mul(int32_t a, int32_t b) {
    int64_t p = (int64_t)a * b;          /* Q62, SMULL                   */
    p += (int64_t)1 << 30;               /* round                        */
    p >>= 31;                            /* Q31                          */
    if (p > INT32_MAX) p = INT32_MAX;    /* -1 * -1                      */
    return (int32_t)p;
}

/* add: same format, may overflow → saturate */
int16_t q15_add(int16_t a, int16_t b) { return (int16_t)__SSAT((int32_t)a + b, 16); }

/* divide Q15 / Q15 → Q15 : pre-shift dividend so the fraction bits survive.
   Valid only when |a| < |b| (result magnitude < 1). */
int16_t q15_div(int16_t a, int16_t b) {
    int32_t num = (int32_t)a << 15;            /* Q30                      */
    int32_t q   = num / b;                     /* Q30 / Q15 = Q15          */
    return (int16_t)__SSAT(q, 16);             /* |a|>=|b| saturates       */
}   /* 0.25 / 0.5: (8192<<15)/16384 = 16384 = 0.5  ✔                      */

5. WHAT GOES WRONG IF…
  • …the filter output has a slowly growing negative offset: truncating shifts (>> without a rounding constant) in a recursive (IIR) filter. Each step loses on average 0.5 LSB, always downwards.
  • …the output is exactly half or double what it should be: shifted by 16 instead of 15 (or vice versa).
  • …a Q31 gain stage is wildly wrong on large inputs: the product was computed as a * b in 32 bits.
"In fixed-point, adding needs equal formats and can overflow by one bit, so I saturate. Multiplying adds the fraction bits: Q15 × Q15 gives Q30 in 32 bits, so I add 1<<14 to round, shift right by 15 and saturate — the only overflow is −1 × −1. For Q31 the product needs a 64-bit intermediate, which is a single-cycle SMULL on the M4. Division pre-shifts the dividend left so the fraction bits survive."

Choosing a Q format from the physical range, guard bits for accumulators, and CMSIS-DSP q15/q31

▶

Designing a fixed-point system means answering two questions for every signal: how big can it get (decides m, the integer bits) and how finely must it be resolved (decides n, the fraction bits). The sum 1 + m + n must fit in the word. Accumulators that add many products need extra integer bits, called guard bits, so they don't overflow halfway through a sum.

1. TERMS
headroom
Spare integer bits above the expected maximum, to absorb overshoot, noise or calibration error.
guard bits
Extra integer bits in an accumulator. Summing K values needs ⌈log2K⌉ guard bits to be overflow-proof.
MAC
Multiply-ACcumulate: acc += a × b, the core of every filter. M4: SMLAL (32×32+64, 1 cycle), SMLALD (two 16×16 products + 64-bit acc, 1 cycle).
CMSIS-DSP
Arm's free DSP library for Cortex-M: filters, FFT, matrix, statistics, in f32, q31, q15 and q7 versions, using the DSP instructions where available.
2. CHOOSING THE FORMAT — STEP BY STEP (MOTOR CURRENT EXAMPLE)

Requirement: phase current −40 A … +40 A, resolution 2 mA or better, 16-bit storage if possible.

  1. Integer bits m: need 2m > 40 → 25 = 32 is too small, 26 = 64 works → m = 6 (range ±64 A, which also gives 24 A of headroom for overshoot).
  2. Fraction bits n: need 2−n ≤ 0.002 → 2−8 = 0.0039 is too coarse, 2−9 = 0.00195 works → n = 9.
  3. Total: 1 + 6 + 9 = 16 bits → Q6.9 in int16_t fits exactly.
  4. Check: 40 A → 40 × 512 = 20 480 (0x5000) < 32 767 ✔. Resolution 1.95 mA ✔.
  5. If it hadn't fitted (e.g. 0.5 mA resolution needs n = 11 → 18 bits) → use Q6.25 in int32, or reconsider the requirement — a 12-bit ADC over ±40 A only resolves 80/4096 = 19.5 mA anyway, so asking for 0.5 mA is meaningless.

Try this in the Q-Format Designer tab: it does these steps for any range and prints the conversion code.

3. GUARD BITS — WORKED FIR EXAMPLE
  1. A 64-tap FIR filter: y = Σ h[k] × x[n−k], with h and x in Q15.
  2. Each product is Q30 in 32 bits, up to magnitude 1.0 (230).
  3. Worst case: 64 products of +1.0 → sum = 64 = 26 → needs 6 guard bits → 1 + 6 + 30 = 37 bits. A 32-bit accumulator can overflow.
  4. CMSIS arm_fir_q15 therefore accumulates in a 64-bit accumulator (format Q33.30 — 34 integer bits including sign — with SMLALD), and only at the end shifts right by 15 and saturates to Q15.
  5. arm_fir_q31 accumulates Q31×Q31 products in a 64-bit accumulator in Q2.62 — only 1 guard bit — so the documentation tells you to scale the input down by log2(numTaps) bits to avoid overflow. Always read the "Scaling and Overflow Behavior" section of each CMSIS function.

5. WHAT GOES WRONG IF…
  • …you pick the format from typical values instead of worst case: a current loop sized for ±40 A wraps during a short-circuit transient at 70 A — exactly when you need correct numbers to trip the protection.
  • …you use more fraction bits "for free": spare bits are free only if you keep headroom elsewhere. Every fraction bit you add halves the range.
  • …on a Cortex-M4F you insist on q31: the FPU does a float MAC in 3 cycles with no scaling worries; CMSIS f32 functions are often as fast as q31. Fixed-point wins on M0/M3, on M4 for 16-bit SIMD (2 MACs/cycle), and where bit-exact results are required.
"I size the integer bits from the worst-case magnitude plus headroom, and the fraction bits from the required resolution, then check 1 + m + n fits the word — for ±40 A at 2 mA that's Q6.9 in an int16. Accumulators need log2(number of terms) guard bits, which is why CMSIS's q15 FIR accumulates in 64 bits. On an M4F I'd consider float32 first; fixed-point pays off on cores without an FPU or when I can use the 16-bit SIMD MACs."

IEEE-754 floating point: sign, exponent, mantissa and the bias — encoding a float by hand

▶

Floating point is scientific notation in binary: a number is stored as sign × 1.fraction × 2exponent. Unlike fixed-point, the binary point "floats", so one 32-bit format can hold both 0.000001 and 1 000 000 000 with about 7 significant decimal digits each. The rules are fixed by the IEEE-754 standard, so a float means the same bits on a Cortex-M4, a PC and a GPU.

1. TERMS
sign (S)
1 bit: 0 positive, 1 negative. Floats use sign-magnitude, not two's complement.
exponent (E)
8 bits in float, 11 in double, stored with a bias added so it is always non-negative.
bias
127 for float, 1023 for double, 15 for half. True exponent = stored E − bias. Biasing makes floats sort like integers (bigger bit pattern = bigger magnitude).
mantissa / significand / fraction (M)
23 bits in float, 52 in double: the bits after the binary point of 1.xxxx. The leading "1." is not stored (the hidden bit), giving 24 bits of precision for 23 stored.
normalised
A number written so the leading digit is 1: 1.1001 × 22, not 0.011001 × 24.

2. ENCODING −6.25 AS A FLOAT — STEP BY STEP
  1. Sign: negative → S = 1.
  2. Convert the magnitude to binary: 6 = 110, 0.25 = .01 → 6.25 = 110.01.
  3. Normalise: move the point left 2 places: 1.1001 × 22.
  4. Exponent: true exponent 2, stored E = 2 + 127 = 129 = 1000 0001.
  5. Mantissa: the bits after "1." → 1001, padded with zeros to 23 bits: 100 1000 0000 0000 0000 0000.
  6. Assemble: 1 | 1000 0001 | 100 1000 0000 0000 0000 0000 → group in nibbles: 1100 0000 1100 1000 0000 … = 0xC0C8_0000.
  7. Check by decoding: (−1)1 × (1 + 0.5 + 0.0625) × 2129−127 = −1.5625 × 4 = −6.25 ✔.
3. WHY 0.1 CANNOT BE STORED EXACTLY
  1. 0.1 in binary is 0.0001100110011001100… — the pattern 0011 repeats forever (just like 1/3 = 0.333… in decimal), because 10 = 2 × 5 and 5 is not a power of two.
  2. Normalised: 1.10011001100…× 2−4 → E = −4 + 127 = 123 = 0111 1011.
  3. The 23 mantissa bits are 1001 1001 1001 1001 1001 100 | 1100… The next bits (1100…) are more than half an LSB, so we round up: …1001 101.
  4. Result 0x3DCC_CCCD = exactly 0.100000001490116119384765625. The double version is 0x3FB9_9999_9999_999A = 0.1000000000000000055511151231257827…

subnormal (denormal)
Numbers smaller than FLT_MIN that fill the gap down to 0 with evenly spaced values (spacing 2−149). They give gradual underflow: x − y == 0 only if x == y. Cost: fewer significant bits (precision drops as they get smaller).
infinity
Result of overflow (FLT_MAX × 2) or of x/0 for x ≠ 0. inf + 1 = inf, 1/inf = 0.
NaN

quiet vs signalling NaN
A qNaN silently propagates. An sNaN raises the Invalid Operation exception (FPSCR.IOC on Arm) when used, then becomes a qNaN. sNaNs are used to mark uninitialised memory: fill RAM with 0x7F80_0001 and any read-before-write raises a flag.
FPSCR

3. WORKED EXAMPLE: HOW A NaN SNEAKS INTO A CONTROL LOOP
  1. A sensor disconnects; the driver divides by a zero range: gain = span / (max − min) with max == min == 0 → 0/0 = NaN, FPSCR.IOC = 1. No exception, no fault — Cortex-M floating-point exceptions only set flags (the FPU interrupt line, IRQ 81 on STM32F4, fires only if you enable it in the NVIC).
  2. The PID controller computes out = kp*err + ki*integ → NaN.
  3. The limiter runs: if (out > MAX) out = MAX; if (out < MIN) out = MIN; → both comparisons are false with NaN, so NaN passes through the limiter.
  4. Conversion to PWM: (uint16_t)out → converting NaN to an integer is UB in C; Arm's VCVT returns 0. On another compiler or core, something else.
  5. The integrator is now NaN forever: NaN + anything = NaN. The loop never recovers without a reset.

4. SUBNORMAL PERFORMANCE AND FLUSH-TO-ZERO
  • The Cortex-M4 FPU handles subnormals in hardware at full speed (Arm states the FPv4-SP is fully IEEE-754 compliant without support code), so on STM32F4 they are not a speed problem.
  • On many desktop x86 CPUs, an operation producing or consuming a subnormal can take ~100× longer (microcode assist). IIR filters decaying towards zero ("denormal stalls" in audio plugins) are the classic case.
  • FZ (flush-to-zero), FPSCR bit 24: treat subnormal inputs and results as zero — faster on some cores, slightly less accurate. Default is off.
5. WHAT GOES WRONG IF…
  • …you compile with -ffast-math: it implies -ffinite-math-only, so the compiler assumes NaN and inf never occur and may delete your isnan() checks.
  • …you sort or use floats as keys with NaN present: a < b is no longer a strict ordering, and qsort can misbehave.

Precision: ULP, machine epsilon, rounding modes, and why 0.1 + 0.2 != 0.3

▶

Floats are not evenly spaced. Between 1 and 2 there are 223 floats; between 1024 and 2048 there are also 223, so the gaps are 1024× bigger. The size of the gap at a given value is called the ULP. Every arithmetic result is rounded to a neighbouring float, so it can be off by up to half an ULP. Understanding this explains every "my float maths is slightly wrong" bug.

1. TERMS
ULP
Unit in the Last Place: the distance between a float and the next larger float. For x in [2e, 2e+1), ULP = 2e−23 (float). At 1.0: 1.19 × 10−7; at 1000: 6.1 × 10−5; at 16 777 216: 2.0.
machine epsilon (FLT_EPSILON)
The ULP of 1.0: 2−23 ≈ 1.19 × 10−7. It is not the smallest float (that is 1.4 × 10−45) and not a universal tolerance.
relative error
|stored − exact| / |exact|. For correctly rounded results it is at most ε/2 = 2−24 ≈ 6 × 10−8 (the unit roundoff).
rounding mode
How a result between two floats is chosen. IEEE defines: round to nearest, ties to even (default); toward +∞; toward −∞; toward zero. Cortex-M4: FPSCR.RMode bits 23:22 = 00/01/10/11. In C: fesetround(FE_TONEAREST / FE_UPWARD / FE_DOWNWARD / FE_TOWARDZERO).
ties to even
When exactly halfway, pick the neighbour whose last bit is 0. Unlike "round half up", this has no systematic bias over many operations ("banker's rounding").
2. HOW ONE ADDITION IS ROUNDED — STEP BY STEP
  1. The FPU computes the exact result internally (with guard, round and sticky bits).
  2. It finds the two floats that bracket the exact result.
  3. It picks the nearer one (ties → even mantissa) and sets FPSCR.IXC (inexact) if the result wasn't exact.
  4. So each single operation is "correctly rounded": error ≤ 0.5 ULP. Errors come from chains of such operations and from the inputs already being rounded.
3. WORKED EXAMPLE: 0.1 + 0.2 IN DOUBLE
  1. 0.1 is stored as 0.1000000000000000055511151231257827 (rounded up by 5.6 × 10−18).
  2. 0.2 is stored as 0.2000000000000000111022302462515654 (also up, 1.1 × 10−17).
  3. Exact sum of the stored values: 0.3000000000000000166533453693773481.
  4. The doubles nearest to that: 0.2999999999999999888977697537484346 (this is what the literal 0.3 becomes) and 0.3000000000000000444089209850062616. The sum is closer to the second → result 0.30000000000000004.
  5. The two values differ by one ULP (5.55 × 10−17), so 0.1 + 0.2 == 0.3 is false.
  6. Twist: in single precision, 0.1f + 0.2f == 0.3f is true! The rounding errors happen to land on the same float. (0.1f+0.2f exact = 0.30000000447, nearest float is 0.30000001192 = 0.3f.) Equality is a matter of luck either way. Try both in the Number Explorer (operations panel).

5. WHAT GOES WRONG IF…
  • …you use FLT_EPSILON as a tolerance for big numbers: at 1000.0 the ULP is 6.1 × 10−5, 500× larger than FLT_EPSILON, so fabsf(a − b) < FLT_EPSILON is the same as a == b. Tolerances must scale with magnitude (card 16).
  • …you change FPSCR.RMode for an interval calculation and forget to restore it: every later float operation in the whole program (and in other RTOS tasks, since FPSCR is per-context only if the RTOS saves it) rounds differently.
  • …you print a float with %f (6 decimals) and assume that's its value: 0.1f prints as 0.100000, hiding the real 0.100000001490.
"An ULP is the gap between adjacent floats and it grows with magnitude: 1.2e-7 at 1.0 but 2.0 at 16 million. Machine epsilon is just the ULP at 1.0. Each IEEE operation is correctly rounded to within half an ULP using round-to-nearest-even by default. 0.1 + 0.2 isn't 0.3 in double because both inputs are already rounded up and the sum lands one ULP above the double nearest 0.3 — in float it happens to compare equal, which shows equality is luck."

Comparing floats properly: absolute, relative and ULP tolerances

▶

Because results are rounded, two calculations that "should" give the same number usually differ in the last bit or two. Testing them with == therefore fails randomly. The fix is to ask "are they close enough?" — but what "close" means depends on the size of the numbers, so you need the right kind of tolerance.

1. THE THREE TOLERANCES
absolute
|a − b| ≤ abs_tol. Right when the values are near zero or have a known physical scale ("within 1 mV").
relative
|a − b| ≤ rel_tol × max(|a|, |b|). Right for values of any size; useless near zero (0 × rel_tol = 0).
ULP distance
How many representable floats lie between a and b. Computed by reinterpreting the bits as integers, because adjacent floats have adjacent bit patterns. "Within 4 ULPs" is the standard for testing maths libraries.
2. WALKTHROUGH: WHY ULP DISTANCE IS JUST INTEGER SUBTRACTION
  1. For positive floats, a bigger value always has a bigger bit pattern (that is why the exponent is biased and sits above the mantissa).
  2. So 1.0f = 0x3F80_0000 and the next float up is 0x3F80_0001. Their integer difference = 1 = one ULP.
  3. Negative floats use sign-magnitude, so their patterns run the "wrong way". Map them onto one continuous integer line: if the sign bit is set, use 0x8000_0000 − bits (as signed). Then −0 and +0 both map to 0.
  4. ULP distance = |mapped(a) − mapped(b)|.
3. CODE — WRONG VS RIGHT
✖ WRONG

    if (isnan(a) || isnan(b)) return false;
    float diff = fabsf(a - b);
    if (diff <= abs_tol) return true;          /* near 0 */
    float big = fmaxf(fabsf(a), fabsf(b));
    return diff <= big * rel_tol;              /* scaled */
}
/* nearly_equal(v, 3.3f, 1e-3f, 1e-5f): within 1 mV
   or within 10 ppm, whichever is looser           */
/* ULP-based comparison (for tests of numeric code) */
#include <stdint.h>
#include <string.h>
static int32_t ordered(float f) {
    int32_t i; memcpy(&i, &f, 4);              /* raw bits                      */
    return (i < 0) ? (int32_t)(0x80000000u - (uint32_t)i) : i;
}   /* negative floats: map so ordering is monotonic and -0 == +0 == 0         */
uint32_t ulp_diff(float a, float b) {
    int64_t d = (int64_t)ordered(a) - ordered(b);  /* 64-bit: can't overflow   */
    return (uint32_t)(d < 0 ? -d : d);
}
/* ulp_diff(1.0f, 1.0000001f) == 1 ; ulp_diff(-0.0f, 0.0f) == 0                */

Worked numbers: a = 1000.0f, b = 1000.00006f. b actually stores 1000.00006103515625 (the next float above 1000, 1 ULP = 6.1 × 10−5). |a − b| = 6.1 × 10−5 > FLT_EPSILON → the epsilon test says "different", the ULP test says "1 ULP apart", the relative test with 1e-6 says "equal" (6.1e-5 ≤ 1000 × 1e-6 = 1e-3).

4. WHEN == IS FINE
  • Comparing with values that are exactly representable and were assigned, not computed: if (x == 0.0f) after x = 0.0f, sentinel values, small integers below 224.
  • Checking for "unchanged" (same bits copied).
5. WHAT GOES WRONG IF…
  • …a loop waits for pos == target: with fractional steps it never matches exactly, overshoots, and runs forever (see Scenario 04). Use pos >= target or count integer steps.
  • …the tolerance is relative but the value crosses zero: a reading that should be 0.0 comes out 1e-9; relative tolerance × 1e-9 rejects it. Always include an absolute floor.
"I never use == on computed floats. I use a combined test: equal if the difference is under an absolute tolerance — needed near zero — or under a relative tolerance times the larger magnitude. FLT_EPSILON alone is wrong because it's the spacing at 1.0 only. For testing numeric code I compare ULP distance by mapping the bit patterns to ordered integers, so 'within 4 ULPs' works at any magnitude."

How errors grow: catastrophic cancellation, absorption, accumulation error and Kahan summation

▶

One rounding error of half an ULP is harmless. Problems come when (a) subtracting nearly equal numbers exposes earlier rounding errors, (b) adding a tiny number to a huge one throws the tiny one away, or (c) millions of small errors pile up. All three are common in firmware: offset subtraction, long-running integrators, timers kept in float.

1. TERMS
catastrophic cancellation
Subtracting two close numbers: the leading digits cancel, leaving only the noisy trailing digits. The subtraction itself is exact — it just reveals the error already present in the inputs.
absorption (swamping)
a + b where |b| < half an ULP of a: the result is exactly a, b vanishes.
accumulation error
Summing N terms naively gives an error bound that grows like N × ε (and typically like √N × ε for random rounding).
Kahan (compensated) summation
An algorithm that keeps a second variable holding the low-order bits lost at each step and feeds them back in. Error becomes about 2ε, independent of N.
2. CATASTROPHIC CANCELLATION — WORKED EXAMPLE
  1. A load cell reads x = 10 000.37 kg-units; the tare (empty) value is t = 10 000.12. True net = 0.25.
  2. As floats: x = 10000.3701171875, t = 10000.1201171875 (ULP at 10 000 is 2−10 ≈ 0.00098).
  3. x − t = 0.25 exactly here, but each input carries up to ±0.00049 error, so the difference is uncertain by ±0.001 — a 0.4 % relative error on 0.25, although each input was accurate to 5 × 10−8 relative.
  4. Fix: subtract in integers before converting (raw ADC counts − raw tare counts), then scale. Integer subtraction is exact.

Other classic cases: variance as E[x²] − E[x]² (use Welford's algorithm), the quadratic formula with b² ≫ 4ac (use the conjugate form), 1 − cos(x) for small x (use 2·sin²(x/2)).

3. ABSORPTION — THE STOPPED CLOCK
float t = 16777216.0f;   /* 2^24: ULP here is 2.0          */
t += 1.0f;               /* exact 16777217 is a tie between
                            16777216 and 16777218 → ties-to-even
                            → 16777216. t did not change!     */

A float counter incremented by 1 stops forever at 16 777 216. A float seconds counter incremented by 0.001 every millisecond loses accuracy from the start and freezes at 32 768 s (9.1 h) — see the Float Accumulation tab and Scenario 06.

4. KAHAN SUMMATION — STEP BY STEP
float kahan_sum(const float *x, int n)
{
    float sum = 0.0f;
    float c   = 0.0f;               /* running compensation: the "lost" low bits  */
    for (int i = 0; i < n; i++) {
        float y = x[i] - c;         /* 1. correct the new term by what was lost   */
        float t = sum + y;          /* 2. big + small: low bits of y are lost     */
        c = (t - sum) - y;          /* 3. (t - sum) = the part of y that got in;  */
                                    /*    minus y   = -(the part that was lost)   */
        sum = t;                    /* 4. next iteration subtracts c → adds it back */
    }
    return sum;
}
  1. Suppose sum = 10 000.0 (ULP ≈ 0.00098) and y = 0.1. t = 10 000.0 + 0.1 → rounds to 10 000.099609375.
  2. t − sum = 0.099609375 (exact, because t and sum are close — the cancellation is our friend here).
  3. c = 0.099609375 − 0.1 = −0.000390625 (approx.): we lost +0.00039.
  4. Next step: y = 0.1 − (−0.00039) = 0.10039 — the lost amount is re-added.
Compiler trap: with -ffast-math (or -fassociative-math) the compiler may simplify (t − sum) − y algebraically to 0, deleting the compensation. Compile Kahan code without fast-math, or mark it volatile/use #pragma GCC optimize("no-fast-math").
5. WHAT GOES WRONG IF…
  • …an energy meter accumulates watt-hours in a float: after the total reaches ~105 Wh, each 0.001 Wh increment is below half an ULP (0.004) and is lost — the meter stops counting. Accumulate in a uint64 of mWh (or a Kahan pair), convert for display.
  • …you average 10 000 samples by summing floats first: the error is visible in the 4th–5th digit. Sum integers, or use pairwise/Kahan summation.
"Subtraction of nearly equal values cancels the good digits and exposes earlier rounding, so I subtract raw integers before scaling. Adding something smaller than half an ULP to a big float does nothing at all — a float counter stops at 224. Long sums grow error proportional to N; Kahan summation keeps a compensation term with the lost low bits and makes the error independent of N, as long as fast-math doesn't optimise the compensation away. For counters and time I just use integers."

float vs double on a Cortex-M4F: single-precision FPU, soft-float doubles, -fsingle-precision-constant, printf %f

▶

The STM32F407's FPU (Arm calls it FPv4-SP, "SP" = Single Precision) executes float operations in hardware in 1–14 cycles. It has no double-precision hardware. Every double operation becomes a call into a software library that emulates it with integer instructions, typically 10–50× slower. Because C quietly turns float into double in several places, a single missing f suffix can make an ISR an order of magnitude slower.

1. TERMS
FPU
Floating-Point Unit. Cortex-M4F: optional single-precision FPU with 32 registers S0–S31. Cortex-M7 may have FPv5 with single and double precision (e.g. STM32F76x/H7 — check the part).
soft-float
Floating-point implemented in software by library routines (in libgcc these are named per the Arm EABI: __aeabi_dadd, __aeabi_dmul, __aeabi_ddiv, __aeabi_f2d, __aeabi_d2f…).
float ABI
-mfloat-abi=soft (no FPU instructions), softfp (FPU instructions, but floats passed in integer registers), hard (floats passed in S registers). All objects and libraries must agree or the link fails.
default argument promotion
When a float is passed to a variadic function like printf, C converts it to double. There is no way to pass a float to printf.

4. TOOLCHAIN SWITCHES THAT CATCH IT
  • -Wdouble-promotion — warns whenever a float is implicitly promoted to double. Turn it on for every M4F project.

  • -mfpu=fpv4-sp-d16 -mfloat-abi=hard — tells GCC the FPU exists. Without it, even float maths is soft-float.

  3. Typical bug: stack overflow when a task with a 256-byte stack calls printf("%f").
  4. Alternative: print scaled integers (card 09) or a small dedicated formatter.

I avoid %f in firmware because newlib-nano needs _printf_float, which costs flash and stack."

Turning the FPU on (CPACR), lazy stacking (FPCCR/FPCAR), and floats in ISRs and RTOS tasks

▶

The Cortex-M4 FPU is off after reset. Software must grant access to it before the first floating-point instruction, or the core faults. Once it is on, every interrupt and every RTOS context switch has to decide whether to save 17 or more FPU registers — which is where "lazy stacking" comes in. Interviewers for automotive and RTOS roles ask about this often.

1. TERMS
CPACR
Coprocessor Access Control Register, address 0xE000_ED88. The FPU is coprocessors 10 and 11; their access fields are bits 21:20 (CP10) and 23:22 (CP11). 0b00 = no access, 0b01 = privileged only, 0b11 = full access.
NOCP
"No coprocessor" UsageFault: UFSR bit 3 (CFSR bit 19). Raised when an FP instruction executes while CPACR denies access.
extended stack frame
On exception entry the core normally pushes 8 words (R0–R3, R12, LR, PC, xPSR). If the interrupted code was using the FPU, it pushes 26 words: those 8 plus S0–S15, FPSCR and one reserved word (18 extra words).
lazy stacking
The core reserves stack space for S0–S15/FPSCR but does not write them unless the handler itself executes an FP instruction. Controlled by FPCCR.
FPCCR / FPCAR
FP Context Control Register (0xE000_EF34): ASPEN bit 31 (automatic state preservation), LSPEN bit 30 (lazy), LSPACT bit 0 (lazy save pending). FP Context Address Register (0xE000_EF38): address of the reserved space where S0–S15 will be written if needed.
EXC_RETURN bit 4
In the LR value at exception entry, bit 4 = 0 means "an extended (FP) frame was stacked" (e.g. 0xFFFF_FFE9 instead of 0xFFFF_FFF9 / 0xFFFF_FFFD).
2. ENABLING THE FPU — STEP BY STEP
/* CMSIS SystemInit() does this when __FPU_PRESENT and __FPU_USED are 1 */
SCB->CPACR |= (3UL << 20) | (3UL << 22);   /* CP10 and CP11 = full access   */
__DSB();                                      /* make sure the write completes */
__ISB();                                      /* flush the pipeline so the next
                                                 instruction sees the new state */
/* Raw address version: *(volatile uint32_t *)0xE000ED88 |= 0x00F00000; */
  1. Reset: CPACR = 0 → FPU disabled.
  2. Startup code (Reset_Handler → SystemInit) sets bits 20–23 = 1111 → CPACR = 0x00F0_0000.
  3. DSB + ISB guarantee no FP instruction was already fetched under the old setting.
  4. Only now may any code — including C library start-up and C++ constructors — use float.

What goes wrong: if the compiler was told the FPU exists (-mfpu=fpv4-sp-d16 -mfloat-abi=hard) but SystemInit didn't enable it (e.g. __FPU_USED not defined, or a custom startup), the first VMOV/VADD raises UsageFault NOCP — escalated to HardFault if UsageFault isn't enabled. The fault may happen in printf or a constructor before main(), which is confusing. Also note GCC may use FP registers as scratch for integer code at high optimisation, so "I don't use float yet" is no guarantee.

3. LAZY STACKING — WHAT HAPPENS ON AN INTERRUPT
  1. Thread code has used the FPU (CONTROL.FPCA = 1). An IRQ arrives.
  2. Core pushes the 8 basic words and reserves 18 more words. FPCAR = address of the reserved area, FPCCR.LSPACT = 1. LR = EXC_RETURN with bit 4 = 0. Entry latency stays 12 cycles.
  3. Case A — the ISR uses only integers: on exit the reserved space is simply discarded. Cost ≈ nothing.
  4. Case B — the ISR executes its first FP instruction: the core stalls that instruction, writes S0–S15 and FPSCR into the reserved area (≈ 17+ cycles of memory writes), clears LSPACT, then continues. On exit, they are restored.
  5. So an ISR that touches floats pays the FP save/restore; one that doesn't, doesn't.

4. RTOS CONTEXT SWITCH
  • Hardware saves only S0–S15. An RTOS PendSV handler must save S16–S31 itself when the outgoing task's EXC_RETURN bit 4 is 0 (tst lr, #0x10; it eq; vstmdbeq r0!, {s16-s31} in the FreeRTOS ARM_CM4F port).
  • Each task's stack must be large enough for the extended frame (+72 bytes for S16–S31 plus 72 for S0–S15/FPSCR).
  • Using the wrong FreeRTOS port (ARM_CM3 instead of ARM_CM4F) on an M4F → FPU registers are not saved → tasks corrupt each other's float variables at random.

  1. π as float32 = 0x4049_0FDB.

3. INT8 AFFINE QUANTISATION — WORKED EXAMPLE

TensorFlow Lite Micro and CMSIS-NN represent a real value r as r = scale × (q − zero_point), with q an int8.

  1. A layer's activations range from −2.0 to +6.0. 256 levels over 8.0 → scale = 8.0 / 255 = 0.031373.
  2. zero_point is chosen so r = 0 maps to an integer: zp = −128 − round(−2.0 / 0.031373) = −128 + 64 = −64.
  3. Quantise r = 1.5: q = round(1.5 / 0.031373) + zp = 48 − 64 = −16.
  4. Dequantise: 0.031373 × (−16 − (−64)) = 0.031373 × 48 = 1.506 (error 0.006, within half a step).
  5. Inside the layer, int8 × int8 products are summed in int32 accumulators, then rescaled with a fixed-point multiplier (a Q31 value plus a shift) — the same Q-format arithmetic as cards 10–11.
4. WHAT GOES WRONG IF…
  • …you store a sensor value up to 100 000 in fp16: it overflows to infinity (max 65 504). bfloat16 would not overflow but would only resolve steps of 512 at that magnitude.
  • …you set FPSCR.AHP on a Cortex-M4: "alternative half precision" has no inf/NaN and reaches 131 008 — files produced that way aren't IEEE fp16.

BCD (Binary-Coded Decimal): RTC registers, displays and conversion

▶

BCD stores each decimal digit in its own 4-bit nibble. The number 59 is stored as 0101 1001 = 0x59 instead of binary 0011 1011 = 0x3B. It wastes some bit patterns (A–F are never used), but makes decimal display trivial and is exactly what real-time-clock chips use. If you've ever seen a clock reading "minute 89", someone forgot the conversion.

1. TERMS
packed BCD
Two digits per byte: 0x59 = "59".
unpacked BCD
One digit per byte: 0x05, 0x09.
RTC
Real-Time Clock. STM32 RTC_TR (time register) and RTC_DR (date) store fields in BCD; so do external chips like the DS3231 and PCF8563.
2. STM32 RTC_TR LAYOUT
  RTC_TR (STM32F4)
  bit: 22 | 21:20 | 19:16 | 14:12 | 11:8 | 6:4 | 3:0

          | hour  | hour  | min   | min  | sec | sec
          | tens  | units | tens  | units| tens| units

Notice how the hex dump reads like the time itself — that's the main charm of BCD for debugging.

3. CONVERSION — STEP BY STEP
  1. Binary → BCD (one byte, 0–99): tens = v / 10, units = v % 10, bcd = (tens << 4) | units. 37 → 3, 7 → 0x37.
  2. BCD → binary: (bcd >> 4) × 10 + (bcd & 0x0F). 0x37 → 3 × 10 + 7 = 37.
  3. Validate: each nibble must be ≤ 9. 0x3A is not valid BCD.
✖ WRONG — uses the BCD byte as binary 
uint8_t min = (RTC->TR >> 8) & 0x7F; /* 14:37 → 0x37 */
if (min >= 45) alarm();   /* 0x37 = 55 ≥ 45: the
                             alarm fires at :37!  */
printf("%d", min);        /* prints "55", not 37  */
✔ RIGHT — decode first 
static inline uint8_t bcd2bin(uint8_t b) {
    return (uint8_t)((b >> 4) * 10u + (b & 0x0Fu));
}
static inline uint8_t bin2bcd(uint8_t v) {   /* v ≤ 99 */
    return (uint8_t)(((v / 10u) << 4) | (v % 10u));
}
uint8_t min = bcd2bin((RTC->TR >> 8) & 0x7F); /* 37 */

For multi-digit binary → BCD without division (useful on M0 or in hardware), the double-dabble algorithm shifts the binary number left into BCD nibbles one bit at a time and adds 3 to any nibble ≥ 5 before each shift.

HAL note: ST's HAL takes a Format argument (RTC_FORMAT_BIN or RTC_FORMAT_BCD) in HAL_RTC_GetTime; passing the wrong one gives exactly this bug. Also read RTC_DR after RTC_TR — on STM32F4 reading TR locks the shadow registers until DR is read.

"BCD stores one decimal digit per nibble, so 59 is 0x59. RTCs like the STM32's RTC_TR and the DS3231 use it, so I convert with (b >> 4) × 10 + (b & 0xF) and back with ((v/10) << 4) | (v%10). The classic bug is using the raw BCD byte as a binary number, which gives minutes like 0x59 = 89."

  1. Cortex-M is little-endian: 0xC0C8_0000 (−6.25f) sits in memory as bytes 00 00 C8 C0.
  2. A big-endian protocol (Modbus, many CAN DBC signals marked "Motorola") expects C0 C8 00 00.
  3. Pack explicitly with shifts — never memcpy a struct with a float onto the wire: padding, endianness and alignment all differ between sender and receiver.
void put_f32_be(uint8_t *p, float f) {
    uint32_t u; memcpy(&u, &f, 4);       /* legal type pun                       */
    p[0] = u >> 24; p[1] = u >> 16;       /* most significant byte first          */
    p[2] = u >> 8;  p[3] = u;
}   /* Often better: send a scaled integer (e.g. int16 in 0.01 units) — smaller, exact */
"Float to int truncates toward zero, and if the value is out of range or NaN it's undefined behaviour — Arm happens to saturate, x86 returns 0x80000000 — so I clamp in float first and then convert with lrintf for proper rounding. Int to float loses integers above 224. For type punning I use memcpy, and for the wire I pack bytes explicitly with shifts, or better, send scaled integers."
23ADVANCED

Integer square root and fast reciprocal (bit-by-bit, Newton–Raphson, the 0x5F3759DF trick)

▶

Without an FPU (or inside an integer-only ISR) you still sometimes need √x — vector magnitude, RMS current, distance — or 1/x for normalisation. Two families of algorithms cover almost every case: digit-by-digit methods (exact, one result bit per iteration) and Newton–Raphson iteration (starts from a guess and doubles the number of correct bits each step).

1. TERMS
isqrt(n)
⌊√n⌋, the largest integer r with r² ≤ n.
Newton–Raphson
To solve f(x) = 0, repeat x ← x − f(x)/f′(x). Converges quadratically: the number of correct bits roughly doubles each iteration.
CLZ
Count Leading Zeros instruction (M3/M4/M7, 1 cycle; not on M0). Gives ⌊log2⌋ instantly, which is the best way to get a good initial guess.
2. BIT-BY-BIT INTEGER SQUARE ROOT
uint32_t isqrt32(uint32_t n)          /* returns floor(sqrt(n)), max 65535    */
{
    uint32_t res = 0;
    uint32_t bit = 1u << 30;          /* highest power of 4 that fits in 32 bits */
    while (bit > n) bit >>= 2;        /* start at the highest power of 4 <= n  */
    while (bit != 0) {
        if (n >= res + bit) {         /* can this result bit be 1?              */
            n  -= res + bit;          /* yes: remove its contribution           */
            res = (res >> 1) + bit;   /*      and set the bit                   */
        } else {
            res >>= 1;                /* no: bit stays 0                        */
        }
        bit >>= 2;                    /* next lower result bit                  */
    }
    return res;                       /* 16 iterations max, no multiply/divide  */
}

3. NEWTON–RAPHSON RECIPROCAL (NO DIVIDE INSTRUCTION)
  1. We want y = 1/d. Use f(y) = 1/y − d. Newton's step simplifies to y ← y × (2 − d × y) — only multiplies and a subtraction.
  2. Start: d = 3, guess y₀ = 0.3 (error 0.0333).
  3. y₁ = 0.3 × (2 − 0.9) = 0.33 (error 0.0033).
  4. y₂ = 0.33 × (2 − 0.99) = 0.3333 (error 0.000033).
  5. y₃ = 0.3333 × (2 − 0.9999) = 0.33333333 — error squared each time: 1 → 2 → 4 → 8 correct digits.
  6. In fixed point: normalise d with CLZ so it lies in [0.5, 1), take y₀ from a small lookup table (e.g. 8 bits correct), and two iterations give ~30 bits. This is how many DSPs and the Cortex-M55's Helium code do division.
4. FAST INVERSE SQUARE ROOT (THE "QUAKE" TRICK)
float fast_rsqrt(float x) {
    uint32_t i; float y;
    memcpy(&i, &x, 4);
    i = 0x5F3759DF - (i >> 1);        /* integer ops on the float's bits:
                                          halving the exponent ≈ sqrt,
                                          negating it ≈ reciprocal       */
    memcpy(&y, &i, 4);                /* first guess: within ~3.4 %       */
    y = y * (1.5f - 0.5f * x * y * y);  /* one Newton step: within ~0.18 % */
    return y;
}   /* x = 4: guess 0.4831, after one step 0.49915 (exact 0.5)           */

Why it works: a float's bit pattern read as an integer is approximately a scaled and shifted log2 of its value. Shifting right by 1 halves the log (square root), subtracting from a constant negates it (reciprocal), and the magic constant fixes the bias and minimises error. On a Cortex-M4F this is not worth it: VSQRT + VDIV = 28 cycles and are exact. It is still a favourite interview question for explaining float layout.

"For integer sqrt I use the bit-by-bit method: it decides one result bit per iteration with only shifts, adds and compares — 16 iterations for a 32-bit input, exact floor result. For reciprocals without a divider I use Newton–Raphson, y ← y(2 − dy), which doubles the correct bits each iteration from a CLZ-normalised table guess. The 0x5F3759DF trick works because a float's bits approximate its log2, but on an M4F I'd just use VSQRT."

    60-SECOND REVISION
    
          
    
            
    Two's complement: MSB weight −2N−1; one adder for signed and unsigned; single zero; asymmetric range, so −INT_MIN, abs(INT_MIN), INT_MIN/−1 overflow (UB in C; M4 SDIV returns INT_MIN, x86 traps).
    
            
    Flags: C = unsigned overflow (Arm SUB: C=1 means no borrow), V = signed overflow (same-sign inputs, opposite-sign result). C hides flags; use __builtin_add_overflow or pre-checks.
    
            
    Promotion: small types → int; int + unsigned → unsigned. Widen one operand before multiplying.
    
            
    Division: truncates toward zero, % takes dividend's sign, >> floors. Constants → multiply-shift. M0 has no divider.
    
            
    Saturation: clamp instead of wrap; SSAT/USAT (M3+), QADD (DSP), sticky Q flag.
    
            
    Q-format: int / 2n. Multiply: widen, + half LSB, >> n, saturate (Q15: 32-bit; Q31: 64-bit). −1×−1 is the only overflow. Choose m from worst-case range, n from resolution, add guard bits for sums.
    
            
    IEEE-754: S, biased E, hidden-1 mantissa. float: 1-8-23, bias 127, ~7 digits, exact ints to 224. Specials: ±0, subnormals (gradual underflow), ±inf, qNaN/sNaN; NaN ≠ NaN.
    
            
    Precision: ULP grows with magnitude; ε = ULP(1). Round-to-nearest-even. 0.1+0.2 ≠ 0.3 in double (equal in float, by luck). Compare with abs + rel tolerance or ULP distance.
    
            
    Error growth: cancellation exposes old errors; absorption drops tiny addends; accumulation ∝ N — use integers or Kahan (not with fast-math).
    
            
    M4F: SP-only FPU, 1-cycle add/mul, 14-cycle div; double = soft-float. f suffixes, sinf, -Wdouble-promotion. Enable via CPACR 0xE000ED88 |= 0xF<<20 + DSB/ISB, else NOCP. Lazy stacking reserves S0–S15/FPSCR; RTOS saves S16–S31.
    
            
    Other: fp16 1-5-10 (max 65504), bf16 1-8-7 (float range), int8 r = s(q − z). BCD nibble per digit (RTC). Float→int out of range = UB. isqrt bit-by-bit; Newton doubles bits.
