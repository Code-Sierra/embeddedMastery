Bits, Masks, Shifts & Byte Order — taught step by step

Every idea here is explained from zero: plain-language intro, every term defined, a numbered walkthrough, real numbers, code with the wrong and right versions side by side, what breaks and why, and a "Say it like this" answer for the interview. Reference core: ARM Cortex-M4 (STM32F407) — a 32-bit, little-endian CPU where int and long are both 32 bits. Read the cards in order the first time; each builds on the previous one.

BEGINNER

1. Binary & hex fluency — reading a register value like a sentence

▶

A microcontroller stores everything — numbers, characters, the settings of a peripheral — as rows of on/off switches called bits. Hexadecimal ("hex") is simply a short way to write those rows down, four switches per symbol, so that humans can read them quickly.

1. The words you need
bit
one binary digit, 0 or 1. Physically: one flip-flop or one memory cell.
nibble
4 bits. One hex digit describes exactly one nibble (24 = 16 possibilities, 0–F).
byte
8 bits = 2 hex digits. The smallest unit that has its own memory address.
halfword / word
on ARM: halfword = 16 bits, word = 32 bits = 4 bytes = 8 hex digits. (On x86 "word" means 16 bits — another reason to say the bit count.)
bit n
bits are numbered from 0 at the right. Bit n has weight 2n. Bit 0 is the LSB (Least Significant Bit), bit 31 of a word is the MSB (Most Significant Bit).
radix / base
how many symbols a number system uses: binary = base 2, decimal = base 10, hex = base 16. In C: 0x prefix = hex, 0b = binary (GCC extension, standard in C23), a leading 0 = octal (base 8).
2. How to picture a 32-bit register

The rightmost hex digit always describes bits 3..0, the next one bits 7..4, and so on. That is why hex is the language of registers: you can find any bit by counting nibbles from the right.

4. Walkthrough: converting in your head

Decimal 200 → binary → hex

  1. Find the largest power of two ≤ 200: 128 (27). Remainder 200 − 128 = 72.
  2. Largest power ≤ 72: 64 (26). Remainder 8.
  3. 8 = 23. Remainder 0. So bits 7, 6 and 3 are 1: 1100 1000.
  4. Split into nibbles: 1100 = C, 1000 = 8 → 0xC8.

Hex 0x3E8 → decimal: each hex digit is worth 16× the one to its right: 3·256 + 14·16 + 8·1 = 768 + 224 + 8 = 1000.

Reading a real register: the debugger shows GPIOA->MODER = 0x0000_0C00. Nibble 2 (bits 11..8) is C = 1100, so bits 11 and 10 are set. On STM32F4 the MODER register uses 2 bits per pin: pin n lives in bits 2n+1..2n, so bits 11..10 belong to pin 5 and value 0b11 = "analog mode". You just decoded a register by reading hex.

2. Two's complement, signed vs unsigned, and integer promotion

▶

The CPU stores negative numbers using a trick called two's complement, which lets the same adder circuit handle both positive and negative values. C then adds its own rules about how small types are widened before any arithmetic — and those rules are where most bit-manipulation bugs hide.

1. The words you need
unsigned
all bits are value bits; an N-bit unsigned holds 0 … 2N−1.
two's complement
signed representation where the top bit has a negative weight of −2N−1. Range −2N−1 … 2N−1−1.
sign bit
the MSB of a signed value: 1 means negative.
integer promotion
C rule: any type narrower than int (char, short, uint8_t, uint16_t, bit-fields) is converted to int before it is used in arithmetic or bitwise operations.
usual arithmetic conversions
C rule for binary operators: when the two operands have different types they are converted to a common type; if one is unsigned int and the other int, the int becomes unsigned.
UB
Undefined Behaviour: the C standard places no requirement on what happens. The optimiser is allowed to assume it never occurs, so the result may be "anything", including code being deleted.
2. How two's complement works — 8-bit walkthrough
bit weight:   -128   64   32   16    8    4    2    1
0x05 =          0     0    0    0    0    1    0    1   =  4 + 1                 =   5
0xFB =          1     1    1    1    1    0    1    1   = -128+64+32+16+8+2+1    =  -5
0x80 =          1     0    0    0    0    0    0    0   = -128                   = -128  (no +128 exists)
0x7F =          0     1    1    1    1    1    1    1   =  127

To negate a number: invert all bits, then add 1.

  1. Start with 5 = 0000 0101.
  2. Invert every bit (the ~ operator): 1111 1010 = 0xFA.
  3. Add 1: 1111 1011 = 0xFB. Check with the weights above: −128 + 123 = −5. ✓
  4. Add 5 + (−5) with the ordinary binary adder: 0x05 + 0xFB = 0x100; the carry out of bit 7 is dropped → 0x00. The same circuit did signed arithmetic — that is the whole point of two's complement.
x + ~x = 111…1 (each position adds 1 + 0, no carries) = −1. So ~x = −1 − x, therefore ~x + 1 = −x. Special case: the most negative value 0x80 (−128) negates to itself, because +128 does not fit. In 32 bits, −INT32_MIN overflows back to INT32_MIN.
3. Integer promotion — the silent widening
  1. You write uint8_t a = 0x0F; if (~a == 0xF0) …
  2. Before ~ runs, C promotes a to int: 0x0000_000F.
  3. ~ inverts all 32 bits: 0xFFFF_FFF0 (the int −16).
  4. Compare with 0xF0 (= 240): −16 ≠ 240 → the condition is false, even though "in 8 bits" it looked true.

That's why I do all bit work on uint32_t with U-suffixed literals.

3. The six bitwise operators — what each one is for

▶

C has six operators that work on individual bits instead of whole numbers. Each one has a job: AND clears or tests bits, OR sets them, XOR flips them, NOT builds "everything except" masks, and the shifts move bits left or right.

1. Truth tables (one bit position at a time)

 1 0 |  0    1    1

The operator applies the table to every one of the 32 bit positions independently and in parallel — bit 5 of the result depends only on bit 5 of the inputs.

5. What the Cortex-M4 actually executes

Every one of these is a single-cycle instruction: AND, ORR, EOR (XOR), MVN (NOT), BIC (bit clear = a & ~b in one instruction), LSL, LSR, ASR, ROR. The ARM "barrel shifter" lets most instructions shift their second operand for free: ORR r0, r0, r1, LSL #4 computes r0 | (r1 << 4) in one cycle. So bit manipulation is as cheap as it gets.

AND clears or tests — it keeps only the bits the mask allows; OR sets bits; XOR toggles them and is its own inverse; NOT builds the "everything but" mask I use with AND to clear. Shifts position a value into a field or bring a field down to bit zero. On a Cortex-M4 each is one cycle, and BIC does AND-NOT in a single instruction. And I never confuse && with &: && is a logical test that returns 0 or 1.

4. Set / clear / toggle / test macros — and the 1<<31 trap

▶

Almost every line of driver code does one of four things to one bit: set it to 1, clear it to 0, flip it, or check it. These four idioms are so common that every codebase wraps them in macros — and writing those macros correctly needs more care than it looks.

1. The four idioms, step by step

Let r = 0x0000_00A4 (binary 1010 0100) and n = 3.

  1. Build the mask: 1U << 3 = 0000 1000 = 0x08. A mask is a value with 1s exactly where you want to act.
  2. Set: r | 0x08 → 1010 1100 = 0xAC. OR forces bit 3 to 1, leaves the rest.
  3. Clear: r & ~0x08. ~0x08 = 0xFFFF_FFF7 (all ones except bit 3). AND with it forces bit 3 to 0: from 0xAC back to 0xA4.
  4. Toggle: r ^ 0x08 flips bit 3 each time it runs: 0xA4 → 0xAC → 0xA4.
  5. Test: (r >> 3) & 1U → shift bit 3 down to position 0, keep only it → 0 or 1. For 0xA4 it is 0; for 0xAC it is 1.

3. Why 1U and not 1 — the 1<<31 trap
  1. The literal 1 has type int (signed, 32 bits on ARM).
  2. 1 << 31 asks for 231 = 2 147 483 648. The largest int is 2 147 483 647. The result is not representable.
  3. The C standard (C99, C11, C17 and C23) says: left-shifting a signed value whose result does not fit is undefined behaviour. (C++20 made it defined; C did not.)
  4. In practice GCC produces the bit pattern 0x8000_0000 — which, as an int, means −2 147 483 648.
  5. The damage appears when that negative int is widened to 64 bits: it is sign-extended (the sign bit copied into the new upper bits).
A 64-bit bitmap of free CAN mailboxes uses map &= ~(1 << idx). For idx = 31 the mask becomes 0xFFFF_FFFF_8000_0000 inverted = 0x0000_0000_7FFF_FFFF, which clears bits 31..63 — 33 mailboxes vanish at once. For idx ≥ 32 the shift is UB and on ARM gives 0 (nothing cleared) while on x86 it wraps (the wrong bit is cleared). Unit tests on a PC pass; the target misbehaves.
4. Two more subtleties
  • Truncation of a test result: uint8_t ready = USART1->SR & (1U << 7); stores 0x80 → fine; but & (1U << 9) gives 0x200, and storing 0x200 in a uint8_t keeps only the low 8 bits → always 0. Normalise: != 0U or shift down first.
  • Double evaluation: a macro that uses its argument twice evaluates it twice. SET_BIT(*p++, 3) only uses r once here, but a FIELD macro might use it twice. For anything non-trivial prefer static inline functions: they type-check, evaluate once, and compile to identical code at -O1 and above.
To set I OR with a mask, to clear I AND with the inverted mask, to toggle I XOR, and to test I shift down and AND with 1. In the macros every parameter and the whole body are parenthesised, and the mask is built from 1U or 1UL — because 1 is a signed int and 1 << 31 overflows it, which is undefined behaviour and sign-extends to 0xFFFFFFFF80000000 if it is ever widened to 64 bits.

5. Multi-bit fields: masks from (width, position), extract, insert, CMSIS _Pos/_Msk

▶

Many register settings are not a single bit but a small number stored in a group of adjacent bits — a "field". A clock divider might be 4 bits wide starting at bit 4. To read or change it you need a mask covering exactly those bits, built from the field's width and position.

1. The words you need
field
a group of w adjacent bits starting at bit p (its LSB). It holds a value 0 … 2w−1.
mask
a value with 1s exactly on the field's bits: ((1U << w) − 1U) << p.
extract
read the field as a plain number: shift it down to bit 0 and mask.
insert
write a new value into the field without disturbing other bits: clear the field, then OR in the shifted value.
CMSIS
Cortex Microcontroller Software Interface Standard — ARM's naming convention used by ST, NXP, Nordic, Microchip device headers.
2. Building the mask — walkthrough for w = 4, p = 4
  1. 1U << 4 = 0001 0000 (= 16).
  2. Subtract 1: 16 − 1 = 15 = 0000 1111. Subtracting 1 from a power of two turns the single 1 into a run of w ones below it — this is the core trick.
  3. Shift that run up to the field position: 0000 1111 << 4 = 1111 0000 = 0xF0. That is the mask for bits 7..4.
register r = 0x0000_0A5C     bits:  ...  1010 | 0101 | 1100
field (w=4, p=4)                                  ^^^^  bits 7..4 = 0101 = 5
mask = 0x0000_00F0                         0000 | 1111 | 0000
3. Extract — walkthrough
  1. r >> 4 = 0x0000_00A5 — the field (5) is now in bits 3..0, but higher bits (A) came along.
  2. & 0xF → 0x5. The field value is 5.
4. Insert value 0xC — walkthrough (this is a read-modify-write)
  1. Read: r = 0x0A5C.
  2. Clear the field: r & ~0xF0 = 0x0A5C & 0xFFFF_FF0F = 0x0A0C.
  3. Position the new value: (0xC << 4) & 0xF0 = 0xC0. The final & mask guards against a value that is too big.
  4. Merge: 0x0A0C | 0xC0 = 0x0ACC. Bits outside 7..4 are unchanged.
  5. Write the result back.

RIGHT

On x86 the SHL instruction masks the count to 5 bits, so 1 << 32 = 1 << 0 = 1, and the mask becomes 0. Same source code, opposite answers — that is what "undefined" means in practice.

A field of width w at position p has mask ((1U << w) − 1) << p — subtracting one from a power of two gives a run of w ones. To extract I shift right by p and AND with the low mask; to insert I clear the field with AND-NOT mask and OR in the value shifted by p and masked, so an out-of-range value can't spill into neighbours. CMSIS headers give me _Pos and _Msk for every field so there are no magic numbers, and I special-case width 32 because 1U << 32 is undefined.

6. Read-modify-write on hardware registers — W1C flags, BSRR, bit-banding

▶

"Changing one bit" of a hardware register is usually three separate CPU steps — read the whole register, change the bit in a CPU register, write the whole thing back. Anything that happens between the read and the write can be lost, and some registers react to being written in ways that make this pattern outright wrong.

1. The words you need
RMW
Read-Modify-Write: load a value, change it, store it back. reg |= x, reg &= ~x, reg ^= x are all RMW.
atomic
happens as one indivisible step — nothing (interrupt, DMA, other core) can observe or change state in the middle.
W1C (rc_w1 in ST manuals)
"write 1 to clear" status bit: reading gives the flag; writing 1 clears it; writing 0 does nothing. Example: STM32F4 EXTI->PR.
rc_w0
ST's "read, clear by writing 0": writing 0 clears, writing 1 has no effect. Example: STM32 TIMx->SR.
rc_r
cleared by reading (e.g. some error flags; USART RXNE clears when DR is read).
BSRR
STM32 GPIO "Bit Set/Reset Register": a write-only register whose bits set or clear output pins with a single store.
bit-banding
a Cortex-M3/M4 feature that gives every bit of SRAM and peripheral space its own 32-bit alias address.
2. What GPIOA->ODR |= (1U << 5); really executes

6. Bit-banding (Cortex-M3/M4 only; implemented on STM32F1/F2/F4)

Each bit in two 1 MB regions gets its own word address in a 32 MB alias region. Writing 0 or 1 to that word clears or sets the one bit.

Worked example — GPIOA->ODR bit 5: ODR address = 0x4002_0000 + 0x14 = 0x4002_0014. byte_offset = 0x4002_0014 − 0x4000_0000 = 0x2_0014. × 32 = 0x40_0280. bit 5 × 4 = 0x14. alias = 0x4200_0000 + 0x40_0280 + 0x14 = 0x4240_0294.

Bit-banding a W1C register still breaks it. The bus performs a locked read-modify-write of the whole word in hardware: it is atomic against interrupts, but the write-back still writes 1s to every other pending flag. Bit-banding also does not exist on Cortex-M0/M0+/M7/M23/M33 — code using it will not port. Prefer set/clear registers, or LDREX/STREX (exclusive load/store) for RAM flags.
reg |= bit is three instructions — load, OR, store — so an interrupt between them can have its change overwritten, and on write-1-to-clear status registers the write-back clears every other pending flag, even with interrupts off. So for W1C I write only the bit I want, for GPIO I use BSRR which sets or resets with a single store, and when I truly need RMW on shared registers I protect it with a critical section. Bit-banding on M3/M4 makes a single-bit write atomic, but it's still a hardware RMW so it doesn't fix W1C.

7. Shifts: logical vs arithmetic, undefined and implementation-defined cases

▶

Shifting moves all bits of a value left or right by some number of places. It looks trivial, but C leaves several shift cases undefined or up to the compiler, and different CPUs genuinely produce different answers for them.

1. The words you need
logical shift right (LSR)
bits move toward bit 0; zeros enter at the top. Used for unsigned values.
arithmetic shift right (ASR)
bits move toward bit 0; copies of the sign bit enter at the top, so a negative number stays negative.
shift left (LSL)
bits move toward the MSB; zeros enter at bit 0; bits pushed past the top are lost.
implementation-defined
the compiler must pick a behaviour and document it (GCC: arithmetic shift for signed >>).
undefined (UB)
no requirement at all; the optimiser may assume it never happens.
2. Walkthrough — the same 8-bit pattern 0xB4 (1011 0100) shifted right by 2
            1 0 1 1 0 1 0 0        0xB4 = 180 (unsigned)  or  -76 (signed)
LSR by 2:   0 0 1 0 1 1 0 1        0x2D = 45   (180 / 4)          zeros came in
ASR by 2:   1 1 1 0 1 1 0 1        0xED = -19  (-76 / 4 = -19)    sign bit (1) copied in
LSL by 2:   1 1 0 1 0 0 0 0        0xD0 (top two bits "10" fell off the end)
  1. C decides LSR vs ASR from the type of the left operand: unsigned → logical, signed → (on GCC) arithmetic.
  2. The result type is the promoted left operand; the right operand only gives the count.
  3. If the count is negative or ≥ the width of the promoted left operand (32 for int) → UB, whatever the type.

8. Operator precedence pitfalls — reg & MASK == MASK

▶

Precedence is the rule that decides which operator in an expression is applied first. In C, the bitwise operators &, ^ and | have lower precedence than comparisons like ==, which is the opposite of what almost everyone expects, and it produces code that compiles cleanly but tests the wrong thing.

9. Endianness — definition, detection, network order, byte swapping, safe serialisation

▶

Memory is a long row of bytes, each with its own address. A 32-bit number needs four of them, and endianness is simply the agreement about which of the four bytes goes first. It matters the moment bytes leave the CPU — over a network, a CAN bus, a sensor's I²C registers, or a file.

1. The words you need
little-endian (LE)
the least significant byte is stored at the lowest address. Cortex-M (all STM32), x86, RISC-V, most ARM Linux systems.
big-endian (BE)
the most significant byte is stored at the lowest address. Network protocols, PowerPC (NXP MPC5xxx automotive), Motorola 68k, many sensors.
network byte order
big-endian, as fixed by the Internet RFCs (IP, TCP, UDP headers).
htons / htonl
"host to network short/long": convert a 16/32-bit value from the CPU's order to big-endian. ntohs/ntohl convert back. On a LE CPU they swap bytes; on a BE CPU they do nothing.
serialise / deserialise
turn a value into a byte sequence in a defined order (and back).
2. Picture it — 0x12345678 stored at address 0x2000_0000
                    address:   0x2000_0000   0x2000_0001   0x2000_0002   0x2000_0003

big-endian (network):             0x12          0x34          0x56          0x78      ← "big end first", reads like the hex

10. Bit-level protocols: packing signals into a CAN payload

▶

A CAN frame carries at most 8 data bytes, so vehicle networks squeeze many small values ("signals") into those 64 bits — a 12-bit speed here, a 2-bit gear state there. Packing and unpacking them is pure bit manipulation, plus one twist: two different byte-order conventions.

1. The words you need
CAN
Controller Area Network, the automotive/industrial bus. Classic CAN payload: 0–8 bytes; CAN FD: up to 64.
signal
one value inside the payload, described by start bit, length, byte order, signedness, factor and offset.
DBC
Vector's text file format that describes messages and signals; the de-facto standard.
raw / physical

little-endian signal: the start bit is the LSB; higher bits go to higher bit numbers and then into the next byte. J1939 (trucks) uses this.
Motorola byte order (DBC @0)
big-endian signal: in DBC the start bit is the MSB; lower bits go down within the byte and then continue at bit 7 of the next byte.

13. Rounding to powers of two and alignment (next power of 2, ALIGN_UP)

▶

Buffers, DMA transfers, MPU regions and memory allocators often need sizes or addresses rounded up to a power of two or to an alignment boundary. Both are done with a few bit operations instead of loops or division.

1. The words you need
next power of two
the smallest 2k ≥ x. Examples: 5 → 8, 8 → 8, 1000 → 1024.
alignment
an address is a-aligned if it is a multiple of a (a = power of two), i.e. its low log₂(a) bits are zero.
smear
copy the highest set bit into every lower position: 0010 0100 → 0011 1111.
2. Next power of two — walkthrough with x = 37
  1. x-- → 36 = 0010 0100. (Decrement first so an exact power, e.g. 32, maps to itself and not to 64.)
  2. x |= x >> 1 → 0010 0100 | 0001 0010 = 0011 0110. Now the top 1 has a 1 next to it (2 ones at the top).
  3. x |= x >> 2 → 0011 0110 | 0000 1101 = 0011 1111. 4 ones (already full here).
  4. x |= x >> 4, >> 8, >> 16 → still 0011 1111 = 63. In general each step doubles the run: 1→2→4→8→16→32, covering any 32-bit value in 5 steps.
  5. x + 1 → 64. ✓ (37 rounded up to a power of two is 64.)

3. Align up / align down — walkthrough with x = 0x2000_0013, a = 8
  1. a − 1 = 7 = 0b111: the bits that must be zero in an aligned address.
  2. Align down: x & ~7 = 0x2000_0013 & 0xFFFF_FFF8 = 0x2000_0010 (drop the low 3 bits).

16. Bit reversal, parity, Gray code, rotate

▶

Four classic transforms that all use the same divide-and-conquer idea — do the job on pairs, then on groups of four, then eight, and so on — so a 32-bit word needs only 5 steps instead of 32.

1. Bit reversal — what and why

Reverse the order of bits: bit 0 ↔ bit 31, bit 1 ↔ bit 30. 0x0000_0001 → 0x8000_0000; 0x0000_00F0 → 0x0F00_0000. Used by reflected CRCs, FFT bit-reversed addressing, LSB-first serial protocols, and ctz via CLZ(RBIT).

Walkthrough of the swap network on 8 bits, x = abcdefgh:

  1. Swap adjacent bits (mask 0x55 = 01010101): badcfehg.
  2. Swap adjacent pairs (mask 0x33 = 00110011): dcbahgfe.
  3. Swap nibbles (mask 0x0F): hgfedcba — reversed after log₂ 8 = 3 steps. 32 bits need 5 steps (add bytes 0x00FF00FF and halfwords).
2. Parity — is the number of 1s odd?
  1. Parity is popcount mod 2. XOR is addition mod 2, so XOR-ing halves together preserves parity.
  2. x ^= x >> 16: low 16 bits now have the same parity as all 32. Then >> 8, >> 4: low 4 bits carry the parity.
  3. Look up the parity of a 4-bit number in the constant 0x6996 = 0110 1001 1001 0110: bit n of it is the parity of n. (0x6996 >> (x & 0xF)) & 1.
  4. Example: x = 0x0000_0007 (three ones): folding leaves 7, 0x6996 >> 7 = 0xD3, & 1 = 1 → odd. ✓
3. Gray code — only one bit changes between neighbours
dec  binary  gray        dec  binary  gray
 0    000    000          4    100    110
 1    001    001          5    101    111
 2    010    011          6    110    101
 3    011    010          7    111    100     each step: exactly ONE gray bit flips (3→4: 010→110)

Why it matters: a rotary encoder or an asynchronous FIFO pointer crossing clock domains may be sampled while changing. In binary, 3 → 4 flips three bits (011 → 100) and a mid-transition sample can read any of 8 values; in Gray only one bit changes, so the sample is either the old or the new value.

4. Rotate — and the UB-safe idiom

A rotate is a shift where bits falling off one end come back in at the other: rotl(0x8000_0001, 1) = 0x0000_0003. C has no rotate operator; you build it from two shifts.

WRONG
RIGHT

ARM has ROR but no ROL — the compiler implements rotl(x, n) as ROR by (32 − n). C++20 std::rotl/rotr, C23 stdc_rotate_left/right. Rotates appear in hash functions (MurmurHash, FNV variants), xorshift PRNGs and ciphers.

Bit reversal can be a 32-step loop, a 5-stage swap network — swap adjacent bits with 0x5555, pairs with 0x3333, nibbles, bytes, halfwords — or one RBIT on Cortex-M3/M4. Parity folds the word with XOR shifts down to 4 bits and looks it up in 0x6996. Gray code is b ^ (b >> 1) so neighbours differ by one bit, which is why async FIFO pointers use it. For rotate I mask the count so neither shift is by 32 — (x << n) | (x >> (−n & 31)) — and the compiler turns it into a single ROR.

17. Sign extension of an N-bit field, branchless abs/min/max, XOR swap

▶

Many sensors and ADCs send signed numbers that are narrower than any C type — a 12-bit two's-complement value inside a 16-bit register, for example. To use it as a normal int32_t you must copy its sign bit into all the upper bits. Getting this wrong produces readings like +4095 where −1 was meant.

1. The words you need
sign extension
widening a signed value by copying its sign bit into the new upper bits. 12-bit 0xFFF (−1) → 32-bit 0xFFFF_FFFF (−1).
zero extension
widening by filling with zeros (correct for unsigned). 0xFFF → 0x0000_0FFF (+4095).
branchless
computed with arithmetic/bitwise operations instead of if/else, so execution time does not depend on the data.
2. Walkthrough — a 12-bit accelerometer value

Range of a 12-bit two's-complement field: −2048 (0x800) … +2047 (0x7FF). The sign bit is bit 11.

  1. The register reads raw = 0x0FFF. The field meaning is −1.
  2. Naive: int16_t v = raw; → 0x0FFF = +4095. Wrong: bit 11 was set, but bits 15..12 are zero, so int16_t sees a positive number.
  3. XOR trick: m = 1 << 11 = 0x800. raw ^ m = 0x7FF (2047). Subtract m: 2047 − 2048 = −1. ✓
  4. Positive check: raw = 0x7FF → 0x7FF ^ 0x800 = 0xFFF = 4095 → 4095 − 2048 = 2047. ✓
  5. Most negative: raw = 0x800 → 0x000 − 2048 = −2048. ✓
raw (16-bit reg):   0000 1111 1111 1111      upper nibble is junk/zero, field = bits 11..0
sign-extended:      1111 1111 1111 1111 1111 1111 1111 1111    = -1   (bit 11 copied into bits 31..12)
zero-extended:      0000 0000 0000 0000 0000 1111 1111 1111    = 4095 (WRONG for a signed field)
WRONG
RIGHT
For field value u ∈ [0, 2ᴺ) with sign bit b, the two's-complement meaning is s = u − b·2ᴺ. XOR with m = 2ᴺ⁻¹ flips the sign bit: if b = 0 it adds m; if b = 1 it subtracts m. Then subtracting m gives u (b = 0) or u − 2m = u − 2ᴺ (b = 1). ∎
3. Branchless abs, min, max, absolute difference
  1. m = x >> 31 (arithmetic): 0 if x ≥ 0, −1 (all ones) if x < 0.
  2. (x ^ m) − m: if m = 0 → x. If m = −1 → (~x) + 1 = −x. Example x = −5: ~(−5) = 4, 4 − (−1) = 5. ✓
  3. min: -(x < y) is 0 or all ones; it selects (x ^ y) or nothing; XOR with y then gives x or y.

Honest engineering note: on Cortex-M4 the compiler already emits branch-free code for x < 0 ? -x : x (an IT block: CMP; IT LT; RSBLT), so hand-written tricks rarely help. They matter for SIMD/DSP code and for constant-time cryptography, where a data-dependent branch leaks timing information.

4. XOR swap — and why not to
XOR swap fails when both pointers alias the same object (it zeroes it), it is a chain of 3 dependent operations (slower than 2 independent moves on any pipelined core), and with a temporary the compiler often emits zero instructions (it just renames registers). The add/subtract variant also risks signed overflow UB. Mention it in interviews as a curiosity and say you would not use it.
To sign-extend an N-bit field I mask it, XOR with the sign bit 1 << (N−1) and subtract the same value — portable, no UB, branchless; on Cortex-M4 SBFX does it in one instruction. Casting to int16_t only works when N is 16, which is the classic bug with 12-bit ADC data. Branchless abs uses m = x >> 31 and (x ^ m) − m, with the INT_MIN caveat, and XOR swap breaks when both operands are the same object, so I just use a temporary.

18. Bitmaps & bitsets: block allocators, RTOS ready lists, event flags

▶

A bitmap uses one bit per item to record a yes/no state — free or used, ready or blocked, set or clear. It is the most compact data structure there is, and combined with CLZ/CTZ it finds "the first free one" or "the highest ready one" in a single instruction.

1. Indexing — walkthrough for item i = 77 in an array of uint32_t words
  1. Word index = i / 32 = i >> 5 = 77 >> 5 = 2.
  2. Bit within word = i % 32 = i & 31 = 77 & 31 = 13.
  3. Mask = 1U << 13 = 0x0000_2000. Set: b[2] |= 0x2000; clear: b[2] &= ~0x2000; test: (b[2] >> 13) & 1.
  4. Shifts and ANDs replace division and modulo because 32 is a power of two (Cortex-M4 UDIV takes 2–12 cycles; LSR/AND take 1).

Note: alloc/free from both thread and ISR context would need a critical section — bm[k] = … is a RMW on shared memory.

2. RTOS ready list — O(1) scheduling (FreeRTOS on Cortex-M3/M4)
uxTopReadyPriority (32-bit):   bit p = 1  ⇔  "the ready list for priority p is non-empty"
   priority:  31 ... 7  6  5  4  3  2  1  0
   bitmap:     0 ... 0  0  1  0  1  0  0  1       = 0x0000_0029  (tasks ready at 5, 3, 0=idle)
   highest = 31 - CLZ(0x29) = 31 - 26 = 5     → run the head of pxReadyTasksLists[5]
  1. With configUSE_PORT_OPTIMISED_TASK_SELECTION = 1, adding a task to ready list p sets bit p (portRECORD_READY_PRIORITY).
  2. When list p becomes empty, bit p is cleared.
  3. The scheduler computes the top priority with one CLZ: uxTopPriority = 31 - __clz(uxTopReadyPriority) — constant time regardless of task count.
  4. Limitation: at most 32 priorities (configMAX_PRIORITIES ≤ 32). On Cortex-M0 (no CLZ) the generic port scans the lists linearly instead.

µC/OS-III and ThreadX use the same trick; for 256 priorities they use two levels — a summary word says which group of 32 has something ready, a second CLZ picks within the group.

3. Event flags and edge detection
FreeRTOS event groups reserve the top 8 bits of the 32-bit event word for internal control flags, so only 24 user bits are available — using bit 24+ silently interferes with the kernel. And setting event bits from an ISR goes through xEventGroupSetBitsFromISR, which defers the RMW to the timer task precisely because a read-modify-write of a shared word is not atomic.
A bitmap stores one state per bit; item i lives in word i >> 5 at bit i & 31. To find the first free block I skip zero words and take ctz of the first non-zero one, then clear it with w & (w−1). FreeRTOS on Cortex-M3/M4 keeps a 32-bit ready-priority bitmap and finds the highest ready priority as 31 − CLZ, which makes task selection O(1) and is why that port is limited to 32 priorities.

19. Checksums and CRC — the bitwise basics

▶

When data travels over a noisy wire or sits in flash, you attach a small check value so the receiver can tell whether anything changed. Simple sums are cheap but weak; a CRC (Cyclic Redundancy Check) is just shifts and XORs too, yet it catches far more error patterns.

1. The words you need
checksum
a value computed from the data (sum, XOR, …) and sent with it.
CRC
remainder of dividing the message, viewed as a polynomial with 0/1 coefficients, by a fixed generator polynomial. Arithmetic is "carry-less": addition and subtraction are both XOR.
polynomial (poly)
written as the bit pattern of its coefficients without the top term: CRC-8 x⁸+x²+x+1 → 0x07; CRC-32 → 0x04C11DB7.
reflected (refin/refout)
bits processed LSB-first; implemented by shifting right with the bit-reversed poly (CRC-32: 0xEDB88320).
init / xorout
starting register value and a final XOR (CRC-32: both 0xFFFF_FFFF).
2. Simple checksums compared
checkhowmisses
8-bit sumadd all bytes mod 256 (Intel HEX stores the two's complement so the total is 0)swapped bytes, +1/−1 pairs
XOR (LRC)XOR all bytes (NMEA 0183 "*hh")two flips in the same bit column, any reordering
Fletcher-16 / Adler-32two running sums; the second weights by positionfar less, but weaker than CRC on bursts
CRC-npolynomial divisiondetects all bursts ≤ n bits, all single-bit errors, and (with a good poly) all 2-bit and odd-count errors up to a length
3. CRC-8 by hand — walkthrough of one byte 0xC1, poly 0x07, init 0
  1. crc = 0x00 ^ 0xC1 = 0xC1 = 1100 0001.
  2. Bit 7 is 1 → shift left and XOR poly: (0x82) ^ 0x07 = 0x85.
  3. 0x85: bit 7 = 1 → 0x0A ^ 0x07 = 0x0D.
  4. 0x0D: bit 7 = 0 → shift only: 0x1A. Then 0x34, 0x68, 0xD0 (bit 7 was 0 each time; that is shifts 3–6).
  5. 0xD0: bit 7 = 1 → 0xA0 ^ 0x07 = 0xA7 (7th shift).
  6. 0xA7: bit 7 = 1 → 0x4E ^ 0x07 = 0x49 (8th shift). Eight shifts done: CRC-8(0xC1) = 0x49.

Each step is "if the bit about to fall off the top is 1, subtract (XOR) the polynomial" — exactly long division in GF(2).

A CRC is fully specified by six parameters (the "Rocksoft model"): width, poly, init, refin, refout, xorout — plus the published "check" value for the ASCII string "123456789" to verify an implementation. Faster versions: a 256-entry table (one lookup per byte; 1 KB for CRC-32) or a 16-entry nibble table (64 B, two lookups per byte) for small MCUs.

STM32F4 CRC peripheral vs zlib: the F4's CRC unit uses poly 0x04C11DB7 and init 0xFFFF_FFFF but processes 32-bit words, MSB-first, without reflection and without the final XOR. Feeding it the same bytes as zlib's crc32() gives a different result, and the bootloader's image check fails against the PC tool's value. Newer STM32 (F0/F3/F7/L4/G0/H7) add REV_IN/REV_OUT and programmable poly/init: set REV_IN = byte, REV_OUT = 1 and XOR the result with 0xFFFF_FFFF to match zlib.
A CRC treats the data as a polynomial over GF(2) and computes the remainder after dividing by a generator; since subtraction is XOR, the bitwise version is "shift left, and if the bit falling out is 1, XOR in the polynomial". It's defined by width, poly, init, reflection and final XOR, and you verify against the check value of "123456789". It detects every burst up to its width, unlike a sum or XOR. On the STM32F4 the hardware CRC is non-reflected, word-based and has no final XOR, so it doesn't match zlib without adjustment.
