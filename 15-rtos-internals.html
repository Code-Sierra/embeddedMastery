1The problem: one CPU, many jobs, different deadlines

Imagine a small motor-drive board built around an STM32F407 microcontroller. The microcontroller (MCU) contains one ARM Cortex-M4F processor core running at 168 MHz, which means it executes up to 168 million clock cycles every second. The board has four jobs:

JOBHOW OFTENHOW LONG IT TAKESWHAT HAPPENS IF IT IS LATE
Control: read motor current, compute a new PWM duty cycleevery 1 ms0.2 msThe motor current overshoots; in the worst case a transistor overheats. Very serious.
Sensor: read temperature and voltage over SPI, filter themevery 10 ms2 msThe protection logic sees old data. Serious.
Display: redraw the LCD with the current valuesevery 50 ms15 msThe screen updates a little late. Nobody notices.
Commands: a byte arrives on the UART (serial port) from a PCat any momenta few µsIf the byte is not read before the next one arrives, it is lost.

A CPU core can only execute one instruction at a time. So the real question of this whole topic is: in what order, and when, does the single CPU work on these four jobs, so that each one finishes before its deadline?

1.1 The first attempt: a "superloop"

The simplest firmware is one endless loop that calls each job in turn. It is called a superloop:

int main(void) {
    hw_init();
    for (;;) {                 // forever
        run_control();        // 0.2 ms
        read_sensors();       // 2 ms
        update_display();     // 15 ms
        check_uart();         // a few µs
    }
}

Let us add up one trip around the loop: 0.2 + 2 + 15 + 0.005 ≈ 17.2 ms. The control job runs once per trip, so it runs every 17.2 ms. But it was supposed to run every 1 ms. It is 17 times too slow, and the reason has nothing to do with the control code itself: it is waiting for the display, the least important job.

time (ms) 0    0.2       2.2                                  17.2  17.4
          |ctrl|--sensor--|----------------display----------------|ctrl|...
          ^ control runs here ...         ... and next runs here: 17.2 ms later (needed: 1 ms)

This is the core weakness: in a superloop, the worst-case delay of every job equals the total time of all the other jobs. Adding one slow feature (say a 30 ms SD-card write) silently breaks every timing in the product.

1.2 The second attempt: interrupts for the urgent part

An interrupt is a hardware signal (for example "the UART has received a byte" or "the timer counter reached its limit") that makes the CPU stop what it is doing, run a special function called an ISR (Interrupt Service Routine), and then go back. On a Cortex-M4 the CPU starts executing the ISR only 12 clock cycles after the signal: 12 ÷ 168 MHz = 71 nanoseconds. So we could run the control code inside a 1 kHz timer ISR and the UART read inside the UART ISR.

This works for the first one or two jobs, and many products are built this way ("foreground/background": ISRs in the foreground, the loop in the background). But it does not scale: the sensor job (2 ms) cannot go into an ISR, because while one ISR runs, other interrupts of the same or lower priority wait, so a 2 ms ISR would delay the UART by 2 ms and lose bytes. The sensor and display jobs stay in the loop, so the sensor still waits up to 15 ms for the display. And code inside ISRs cannot wait for anything (it cannot say "sleep until the SPI transfer is done"), so the ISRs become complicated state machines.

1.3 What we actually want

We want each job to be written as if it had the CPU to itself, as a simple sequence of steps that can wait ("wait 1 ms", "wait until a byte arrives"), and we want a referee that decides, at every moment, which job uses the CPU, always preferring the most urgent one. That referee is the RTOS: a Real-Time Operating System. With an RTOS:

  • The control job gets the CPU within about 1–2 µs of its timer going off, no matter what the display job is doing. The display is simply paused in the middle of its work and continued later.
  • Jobs that are waiting use zero CPU. When nobody needs the CPU, the RTOS can put the MCU to sleep.
  • The cost: some RAM (each job needs its own stack, around 0.5–4 KB each), some flash (the FreeRTOS kernel is about 6–12 KB), about 1 µs of overhead per switch, and a new family of bugs (shared-data races, deadlock, priority inversion, stack overflow) that the rest of this page teaches you to avoid.
"Real-time" does not mean "fast". It means predictable: you can prove that the worst-case response time of an important job is below its deadline. A system that answers in 1 ms on average but occasionally in 50 ms is not real-time if the deadline is 10 ms. An RTOS actually adds a little overhead; what it buys you is the guarantee.

2The physical picture: what the Cortex-M4 actually has

An RTOS is not magic; it is a few kilobytes of C and assembly that use a handful of hardware features. Here is everything physical that matters, with what each part is for.

Walk through the picture from left to right:

  1. Registers. The CPU core has 16 general registers R0–R15, each 32 bits (4 bytes). Three have special jobs: R13 = SP (Stack Pointer, the address of the top of the current stack), R14 = LR (Link Register, where to return when the current function finishes) and R15 = PC (Program Counter, the address of the next instruction). xPSR (Program Status Register) holds the result flags (zero, negative, carry, overflow) and some state bits. Everything a running piece of code is "in the middle of" lives in these registers.
  2. Two stack pointers. The Cortex-M actually has two physical SP registers. MSP (Main Stack Pointer) is used at reset and by every interrupt handler. PSP (Process Stack Pointer) is used by ordinary code when a bit called CONTROL.SPSEL is 1. An RTOS gives each task its own stack and points the PSP into the stack of whichever task is running, while all ISRs share the single MSP stack.
  3. SysTick. A small 24-bit timer built into every Cortex-M core. The RTOS programs it to interrupt every 1 ms. This interrupt is the tick: the kernel's clock, used for "wait 10 ms" style delays.
  4. NVIC. The Nested Vectored Interrupt Controller decides which interrupt runs when several are requested, using a priority number per interrupt (on STM32 a 4-bit number 0–15, where 0 is the most urgent). It also contains a special software-triggered interrupt called PendSV ("pendable service call") that the RTOS uses to perform task switches.
  5. SRAM. The STM32F407 has 192 KB of RAM (128 KB main SRAM plus 64 KB of "core-coupled" CCM RAM). The RTOS carves it into one stack per task, one small record per task called a TCB (Task Control Block), its own lists, and the main stack used by ISRs.
The single most important idea on this page: if you copy all the CPU register values of a running program into RAM, and later copy them back, the program continues exactly where it was, as if nothing had happened. It cannot tell that it was paused. That copy-out / copy-in is the context switch, and an RTOS is essentially a policy for deciding when to do it and to whom.

3The key words, defined one by one

Every later section uses these words. Each definition says what it is in plain language, then gives a concrete example.

Task (also called thread)
A function that runs forever in its own loop, with its own private stack, and that the RTOS can pause and resume. Example: void vControlTask(void *p) { for(;;) { control(); wait_1ms(); } }. On a microcontroller "task" and "thread" mean the same thing; FreeRTOS says task, Zephyr and POSIX say thread.
Stack
A region of RAM used by a function for its local variables, saved registers and return addresses. It grows downwards on ARM (towards lower addresses). Each task needs its own stack because each task is in the middle of its own chain of function calls. Example: a 1 KB stack from address 0x2000_0800 down to 0x2000_0400.
TCB (Task Control Block)
A small C struct (around 100 bytes in FreeRTOS) that the kernel keeps for every task: where the task's saved stack pointer is, its priority, its state, its name. The first field is the saved stack pointer, and that fact is used by the assembly code that switches tasks.
Context
The complete set of CPU register values of a task at one instant: R0–R12, SP, LR, PC, xPSR, and, if the task used floating point, the FPU registers S0–S31 and FPSCR. Saving the context = writing these values to RAM.
Context switch
Saving the context of the task that is running, choosing another task, and loading that task's saved context into the CPU. On a 168 MHz Cortex-M4 running FreeRTOS this takes roughly 100–200 cycles, about 1 µs.
Scheduler
The part of the kernel that decides which task should run now. In every common MCU RTOS the rule is: run the highest-priority task that is ready.
Priority
A number you give each task to say how important it is. In FreeRTOS a larger number is more important (0 is the idle task). Careful: in Zephyr and in the NVIC a smaller number is more important. Example: control = 3, sensor = 2, display = 1.
Ready, Running, Blocked
Running: this task owns the CPU right now (only one per core). Ready: it could run, but a more important task is using the CPU. Blocked: it is waiting for something (a time delay, data in a queue, a semaphore) and uses no CPU at all. Example: the display task is Ready while control is Running; control is Blocked for the 0.8 ms between its runs.
Preemption
Taking the CPU away from a running task, without its cooperation, because a more important task just became Ready. Example: the display is in the middle of drawing a character when control's 1 ms timer fires; the display is paused (preempted) and continues 0.2 ms later.
Tick
The periodic SysTick interrupt, usually every 1 ms (configTICK_RATE_HZ = 1000). The kernel counts ticks; "delay 10 ticks" means "wake me after 10 more tick interrupts".
ISR (Interrupt Service Routine)
The function the hardware calls when an interrupt happens. ISRs are not tasks: they cannot wait for anything, they run on the MSP stack, and they must use special ...FromISR() versions of the RTOS functions.
PendSV
A Cortex-M exception (an interrupt triggered by software) that FreeRTOS sets to the lowest priority and uses to perform the context switch. "Pending PendSV" means "please switch tasks as soon as no other interrupt is running".
Semaphore
A counter used to signal "something happened". Giving it adds 1 and wakes a waiting task; taking it subtracts 1, or blocks the caller if it is 0. Example: the UART ISR gives a semaphore, the command task was blocked taking it and wakes up.
Mutex (mutual exclusion lock)
A lock that protects something shared, such as an SPI bus, so only one task uses it at a time. Unlike a semaphore it has an owner (the task that took it), only the owner may release it, and the kernel uses the owner to fix "priority inversion" (section 7).
Queue
A fixed-size buffer of messages between tasks (or from an ISR to a task). Sending copies the message in; receiving copies it out, blocking if the queue is empty. Example: a queue of 8 sensor_reading_t structs.
Deadline
The latest time by which a job must finish, measured from when it was released. Example: control is released every 1 ms and must finish before the next release, so its deadline D = 1 ms.
WCET (Worst-Case Execution Time), written C
The longest time a job can take to run if it has the CPU to itself. Example: control C = 0.2 ms, measured with the cycle counter over millions of runs with a safety margin added.
Period, written T
How often a periodic job is released. Example: sensor T = 10 ms.
Utilisation, written U
The fraction of the CPU a task needs on average: U = C ÷ T. Example: sensor 2 ms ÷ 10 ms = 0.2 = 20 %. The sum over all tasks must be below 1 (100 %), or the CPU simply cannot keep up.
Response time, written R
The time from a job's release until it finishes, including the time it spent waiting for higher-priority tasks. It is always at least C. The job meets its deadline if R ≤ D.
Jitter
Variation in timing from one cycle to the next. Example: a control task that should start at exactly 1.000, 2.000, 3.000 ms but actually starts at 1.000, 2.004, 3.001 ms has 4 µs of start jitter.

4The trick: how one CPU runs many tasks

Now put the words together. Suppose Task A (display, priority 1) is running and Task B (control, priority 3) is Blocked, waiting for the next tick. Here is what happens, in order, when the tick arrives. You can watch every single register move in the Context Switch lab.

  1. The SysTick timer reaches zero and raises its interrupt. Task A is in the middle of some function; the CPU registers hold A's values.
  2. The hardware automatically saves 8 registers (R0, R1, R2, R3, R12, LR, PC, xPSR = 8 × 4 = 32 bytes) onto A's stack, using the PSP. It does this by itself, before running a single instruction of the ISR, in 12 cycles. Then it switches to the MSP stack and starts the SysTick ISR.
  3. The SysTick ISR (part of FreeRTOS) counts the tick and checks its list of delayed tasks. Task B's wake-up time has arrived, so B moves from Blocked to Ready. B's priority (3) is higher than A's (1), so a switch is needed. The ISR does not switch itself; it just sets the PendSV pending bit (writes 1 to bit 28 of the register ICSR at address 0xE000ED04).
  4. The SysTick ISR returns, and PendSV runs immediately (it was pending, and nothing more urgent is running). The core goes straight from one handler to the next without restoring A's registers in between; ARM calls this tail-chaining, and it costs 6 cycles.
  5. PendSV saves the rest of A's registers (R4–R11 plus the special return code in LR, 9 × 4 = 36 bytes) onto A's stack, and writes A's final stack pointer into A's TCB. Task A is now completely frozen in RAM.
  6. PendSV calls the scheduler (vTaskSwitchContext()), which looks up the highest-priority Ready task (B) and makes the global pointer pxCurrentTCB point at B's TCB.
  7. PendSV loads B's saved stack pointer from B's TCB, pops B's R4–R11 into the CPU, and sets PSP to B's stack.
  8. PendSV returns. The hardware sees the special return code, pops the 8 registers B had saved the last time it was interrupted (including B's PC), and B continues exactly where it stopped. Total time from the tick to B running: about 1–2 µs.
  9. Later, B finishes its 0.2 ms of work and calls a delay (xTaskDelayUntil). B becomes Blocked, the scheduler picks the highest Ready task (A again), and the same save/restore happens in the other direction. A continues drawing the screen as if it had never stopped.

That is the entire illusion of multitasking: tasks take turns on one CPU, and their registers are parked in their own stacks while they are not running.

5One complete worked example with real numbers

Back to the motor-drive board. We turn the four jobs into three FreeRTOS tasks plus one ISR and work through every number an engineer would check before shipping.

Step 1 — Write the tasks

void vControlTask(void *pv) {                // priority 3
    TickType_t last = xTaskGetTickCount();
    for (;;) {
        run_control();                             // 0.2 ms of CPU
        xTaskDelayUntil(&last, pdMS_TO_TICKS(1));  // wake exactly every 1 ms
    }
}
void vSensorTask(void *pv)  { /* same shape, period 10 ms, 2 ms of work  - priority 2 */ }
void vDisplayTask(void *pv) { /* same shape, period 50 ms, 15 ms of work - priority 1 */ }

int main(void) {
    hw_init();
    xTaskCreate(vControlTask, "ctrl", 256,  NULL, 3, NULL);   // 256 words = 1 KB stack
    xTaskCreate(vSensorTask,  "sens", 512,  NULL, 2, NULL);   // 2 KB
    xTaskCreate(vDisplayTask, "disp", 1024, NULL, 1, NULL);   // 4 KB (it uses snprintf)
    vTaskStartScheduler();                                     // never returns
}
CODEMEANING
TickType_t last = xTaskGetTickCount();Remember the tick number at which the loop starts. Every later wake-up is computed from this value, so the period does not drift.
xTaskDelayUntil(&last, pdMS_TO_TICKS(1))Block until tick last + 1, then set last = last + 1. pdMS_TO_TICKS(1) converts 1 ms to ticks: 1 × 1000 / 1000 = 1 tick.
xTaskCreate(fn, "ctrl", 256, NULL, 3, NULL)Create a task running fn, named "ctrl" (for the debugger), with a stack of 256 words (256 × 4 = 1024 bytes), no parameter, priority 3, and we do not need its handle.
vTaskStartScheduler()Create the idle task (priority 0) and the timer task, start SysTick, and start the highest-priority task. Code after this line never runs.

Step 2 — Program the tick

SysTick counts down from a reload value to 0, then interrupts and reloads. To get 1000 interrupts per second from a 168 MHz clock:

Step 3 — Can the CPU keep up at all? (utilisation)

U = Σ C/T = 0.2/1 + 2/10 + 15/50
          = 0.20  + 0.20 + 0.30  = 0.70   → the tasks need 70 % of the CPU

70 % is below 100 %, so on average there is enough CPU. But average is not enough: we need every deadline met. A classic result (Liu & Layland, 1973) says that if priorities are assigned "shorter period = higher priority" (called Rate Monotonic, which is exactly what we did: 1 ms → 3, 10 ms → 2, 50 ms → 1), then any set of n tasks with U ≤ n(21/n − 1) always meets its deadlines. For n = 3: 3 × (21/3 − 1) = 3 × (1.2599 − 1) = 0.780. Our 0.70 ≤ 0.780, so the set is guaranteed schedulable. (Card 22 and the RMS/RTA lab explain why.)

Step 4 — Watch the first 13 ms, tick by tick

All three tasks are released together at t = 0 (the worst case, called the critical instant). The diagram is computed by simulation in 0.1 ms steps; the axis is in milliseconds and each dashed line is one tick.

  1. t = 0.0: all three are Ready. Control has the highest priority, so it runs first, for its 0.2 ms, then blocks until t = 1.0.
  2. t = 0.2: sensor (priority 2) is now the highest Ready task and starts its 2 ms of work.
  3. t = 1.0: the tick wakes control. Control preempts the sensor in the middle of its work (the sensor has done 0.8 ms). Control runs 1.0–1.2, then blocks again; the sensor resumes at 1.2.
  4. t = 2.0: the same again. Control runs 2.0–2.2; the sensor has now done 1.6 ms.
  5. t = 2.6: the sensor finishes its last 0.4 ms. Its response time is R = 2.6 ms (2 ms of its own work + 0.6 ms of control preempting it). 2.6 ≤ 10 ✔.
  6. t = 2.6 → 26.4: the display finally gets the CPU and runs in slices of 0.8 ms between control's runs, plus a 2 ms gap at t = 10 and t = 20 when the sensor runs again. It finishes at t = 26.4 ms: 15 ms of its own work, 27 control runs × 0.2 = 5.4 ms, and 3 sensor runs × 2 = 6 ms. 15 + 5.4 + 6 = 26.4 ≤ 50 ✔.
  7. Control's response time is always 0.2 ms (plus about 1–2 µs of switch overhead), whatever the display is doing. Compare the superloop in section 1: there, control waited up to 17.2 ms.

The display result can be computed without drawing anything, using the response-time formula you will meet in card 22: R = C + Σ ⌈R/Tj⌉ · Cj over the higher-priority tasks, iterated until it stops changing. Starting from R = 15:

R0 = 15
R1 = 15 + ⌈15/1⌉·0.2  + ⌈15/10⌉·2   = 15 + 3.0 + 4 = 22.0

7The three things that go wrong most often

7.1 Priority inversion

The display task (priority 1) locks the SPI-bus mutex to read a font from flash. Control (priority 3) wakes up and also needs SPI, so it blocks, waiting for the display to release the lock. That is expected and short. But now the sensor task (priority 2, does not use SPI) becomes Ready. It is more important than the display, so it preempts the display, which is still holding the lock. Control is now waiting for the sensor, a less important task that has nothing to do with SPI. Its priority has effectively been "inverted". The fix is priority inheritance: while control waits for the lock, the display temporarily runs at priority 3, so the sensor cannot preempt it. This exact bug reset the Mars Pathfinder lander in 1997 (card 12, and the "Mars Pathfinder" preset in the Scheduler Sim).

7.2 Deadlock

Task X takes lock 1 then lock 2. Task Y takes lock 2 then lock 1. If X is preempted right after taking lock 1, and Y then takes lock 2, each waits forever for the lock the other holds. The CPU looks idle and nothing happens. The fix: everyone takes locks in the same global order (card 20).

7.3 Stack overflow

A task's stack is a fixed region. If the task calls something that needs more stack than you gave it (newlib printf("%f") can need over 1 KB), it writes below the bottom of its region, usually into the next task's TCB or stack. The crash then appears in a different task, minutes later. The fix: measure stacks with uxTaskGetStackHighWaterMark(), enable overflow checking, and use the MPU (card 18).

How an RTOS Actually Works

From the superloop to response-time analysis. The reference kernel is FreeRTOS (the ARM_CM4F port) on an STM32F407 / Cortex-M4F at 168 MHz. Zephyr, ThreadX, QNX and PREEMPT_RT are covered where they differ. Each card opens; a green dot means you have read it.

BEGINNER

1. Superloop → foreground/background → RTOS: why an RTOS exists

▶

1. What is it?

This card answers the question every RTOS interview starts with: why use an RTOS at all? There are three ways to organise the code of a microcontroller, and each one was invented to fix a weakness of the previous one. A superloop calls every job in turn forever. Foreground/background adds interrupts (ISRs, Interrupt Service Routines) for the urgent part. An RTOS (Real-Time Operating System) splits the firmware into independent tasks and lets a scheduler decide, at every instant, which task uses the CPU, always choosing the most important one that has work to do.

2. How does it work, step by step?

  1. Superloop. main() contains for(;;){ a(); b(); c(); }. Each function runs to completion before the next one starts. The time to get back to any function is the sum of all the others. Nothing can interrupt c() to run a() early.
  2. Foreground/background. The hardware interrupts the loop when something urgent happens. The ISR does the minimum (copy a byte, set a flag) in a few microseconds and returns. The loop checks the flags. The urgent reaction is fast (interrupt latency, about 71 ns to start on a 168 MHz Cortex-M4), but the processing of the data still waits for its turn in the loop.
  3. RTOS. Each job becomes a task with its own stack and a priority. A task that has nothing to do calls a blocking function such as "wait for a message" and stops using the CPU. When an ISR or the tick makes a more important task Ready, the kernel immediately pauses the current task (saving its registers) and runs the important one. The response time of a task now depends only on more important tasks.

3. Worked example

Four jobs: control 0.2 ms (needed every 1 ms), sensors 2 ms, display 15 ms, UART check 0.005 ms.

DESIGNWORST-CASE DELAY BEFORE CONTROL RUNS AGAINVERDICT

  • …you put the slow job inside an ISR to "make it real-time"? Every interrupt of equal or lower NVIC priority waits for it. Symptom: UART overrun errors (the ORE flag set in USART_SR) and lost bytes at high baud rates.
  • …a superloop function grows? Every other job's latency grows by the same amount. Symptom: a feature added by another team breaks motor control timing, with no change to the control code.

Say it like this: "In a superloop the worst-case latency of any job is the whole loop time, so a slow display delays the control loop. Interrupts fix the urgent reaction but not the processing. It does not make code faster; it makes the worst case bounded, at the cost of RAM for stacks, a few KB of flash and about a microsecond per switch."

7. The compact reference version (for revision)

There are three ways to structure firmware, and interviewers often open by asking you to justify an RTOS at all.

SUPERLOOP (CYCLIC EXECUTIVE)

int main(void) {
    hw_init();
    for (;;) {
        read_sensors();     // 2 ms
        run_control();      // 1 ms
        update_display();   // 15 ms  ← everything waits for this
        service_uart();     // 0.2 ms
    }
}
  • Worst-case latency to any event = the whole loop time (here ≈18 ms), plus the time to get back to that function. Adding a slow function slows everyone down.
  • Pros: no stacks per task, no kernel, fully deterministic order, trivial to debug, zero RAM overhead. Fine for small products and for safety code that must be simple.
  • Long jobs have to be broken by hand into state machines. That is cooperative multitasking done manually.

FOREGROUND / BACKGROUND (INTERRUPT-DRIVEN SUPERLOOP)

ISRs (the foreground) do urgent work and set flags or fill ring buffers. The superloop (the background) polls the flags. Latency for the urgent part becomes the interrupt latency (12 cycles on Cortex-M4 ≈ 71 ns at 168 MHz, plus any time interrupts are masked). But anything handled in the background still waits for the whole loop, and ISRs tend to grow because that is the only place with good latency.

volatile uint8_t rx_ready;
void USART2_IRQHandler(void){ rb_put(&rx, USART2->DR); rx_ready = 1; }
for (;;) { if (rx_ready) { rx_ready = 0; parse(); } run_control(); ... }

RTOS (PREEMPTIVE MULTITASKING)

  • Each activity is a task with its own stack and a priority. The kernel always runs the highest-priority task that is ready.
  • Latency for a high-priority task = interrupt latency + kernel critical-section time + context-switch time. It does not depend on how long the low-priority tasks run. This decoupling is the real reason to use an RTOS.
  • Blocking APIs (xQueueReceive(q, &m, portMAX_DELAY)) replace polling, so the CPU can sleep in the idle task.
  • Costs: RAM (one stack + TCB per task, ~100 B TCB in FreeRTOS), flash (FreeRTOS kernel ≈ 6–12 KB), context-switch overhead, and a new class of bugs: races, deadlock, priority inversion, stack overflow.
"An RTOS makes code faster." No: it adds overhead. It makes the response time of important work bounded and independent of unimportant work. "Real-time" means predictable, not fast.
When NOT to use one: tiny MCUs (≤ 8 KB RAM), a single control loop, or certified code where a kernel adds certification cost. A time-triggered cyclic executive (fixed schedule table driven by a timer) is still common in avionics (ARINC 653 partitions use it at the top level).

2. Tasks, threads and the Task Control Block (TCB)

▶

1. What is it?

A task is one independent activity of your firmware: a C function with an endless loop, plus a private stack (RAM for its local variables and saved registers), plus a TCB (Task Control Block), a small struct where the kernel keeps everything it needs to know about the task when it is not running. The TCB is the task's "passport": its saved stack pointer, priority, state and name.

2. How does it work, step by step?

What xTaskCreate(vSensorTask, "sens", 256, NULL, 3, &hSens) actually does:

  1. Allocate the stack. 256 words × 4 bytes = 1024 bytes from the FreeRTOS heap (pvPortMalloc). With stack overflow checking on, it fills the whole area with the byte 0xA5 so that later it can tell how much was ever used.
  2. Allocate the TCB (about 92–120 bytes depending on configuration options).
  3. Fill in the TCB: name "sens", priority 3, pxStack = lowest address of the stack.
  4. Build a fake saved context at the top of the stack (pxPortInitialiseStack), as if the task had already run and been interrupted: PC = vSensorTask, R0 = the parameter, xPSR = 0x01000000. pxTopOfStack is set to point at it (card 9).
  5. Insert the task into the Ready list for priority 3. If the scheduler is already running and 3 is higher than the current task's priority, a switch happens immediately.
  6. Return the handle (hSens), which is simply a pointer to the TCB.

3. Worked example

RAM cost of 5 tasks with stacks of 256, 256, 512, 512 and 1024 words, plus FreeRTOS's idle (128 words) and timer (256 words) tasks, on heap_4:

stacks: (256+256+512+512+1024+128+256) words × 4 B = 2944 × 4 = 11 776 B
TCBs:   7 × ~100 B                                            =    700 B
heap_4 block headers: 14 allocations × 8 B                    =    112 B
total ≈ 12.6 KB  → on an STM32F407 (192 KB SRAM) about 6.5 %

Notice that the TCBs are tiny compared with the stacks. Stack size is almost always the dominant RAM cost of an RTOS design.

  • …you pass the stack size in bytes (xTaskCreate(f, "x", 1024, …) meaning 1 KB)? Say it like this: "A task is a function with an infinite loop, its own stack and a TCB. 3. Task states: Ready, Running, Blocked, Suspended, Deleted

▶

1. What is it?

At every instant, each task is in exactly one state. The state tells the scheduler whether the task can be given the CPU. There are five: Running (has the CPU), Ready (wants the CPU), Blocked (waiting for an event or a time), Suspended (switched off until someone resumes it) and Deleted. In the kernel, a state is simply "which list the task's TCB is linked into".

2. How does it work, step by step?

Follow one task, vButtonTask, through a button press:

  1. It calls xSemaphoreTake(sem, portMAX_DELAY). The semaphore is 0, so the kernel removes the task from the Ready list and puts it on the semaphore's waiting list (and, because the timeout is infinite, on the Suspended list). State: Blocked. A switch to another task happens immediately.
  2. For the next 3 seconds it uses no CPU at all. The scheduler never even looks at it.
  3. The user presses the button. The EXTI ISR calls xSemaphoreGiveFromISR. The kernel unlinks the task from the waiting list and links it into the Ready list for its priority. State: Ready.
  4. If its priority is higher than the running task's, the ISR's portYIELD_FROM_ISR pends PendSV and, right after the ISR, it becomes Running. If not, it stays Ready until every more important task blocks.
  5. It handles the button and loops back to step 1.

3. Worked example

Three tasks, 1 ms tick. At t = 4.3 ms: control (prio 3) is running its 0.2 ms job; sensor (prio 2) was preempted halfway through its work; display (prio 1) has finished its frame and called vTaskDelay(50) at t = 3.0.

5. What goes wrong if…

  • …you use vTaskSuspend/vTaskResume to synchronise with an ISR? If the ISR's resume happens before the task reaches its suspend, the resume does nothing (the task was not suspended yet) and the task then suspends forever. Symptom: a rare permanent hang. Notifications and semaphores remember a give that arrives early; suspend/resume does not.
  • …the idle task never runs? Self-deleted tasks are never freed. Symptom: xPortGetFreeHeapSize() shrinks every time a worker task deletes itself, until creation fails.
  • …you confuse Blocked with "busy"? A polling loop while(!flag){} keeps the task Ready/Running; it is not Blocked and it eats the CPU.
Say it like this: "A task is Running, Ready, Blocked, Suspended or Deleted, and in FreeRTOS the state is just which list its TCB is linked into. Blocked tasks wait for an event or a timeout and cost zero CPU; Suspended tasks wait only for an explicit resume. A self-deleting task is freed by the idle task, which is one reason idle must get CPU time, and I never use suspend/resume for synchronisation because an early resume is lost."

7. The compact reference version (for revision)

  • Running: owns the CPU. Exactly one per core.
  • Ready: able to run, waiting for the CPU because a task of equal or higher priority is running. Lives in pxReadyTasksLists[prio].
  • Blocked: waiting for an event (queue data, semaphore, notification) and/or time. Always has an optional timeout. Lives in the delayed list (by wake time) and/or an object's event list (by priority). Uses zero CPU.
  • Suspended: out of scheduling until someone calls vTaskResume(). No timeout. A task blocked with portMAX_DELAY (and INCLUDE_vTaskSuspend = 1) is actually put on the suspended list, so it waits forever.
  • Deleted: vTaskDelete() removes it from all lists. If a task deletes itself, its TCB and stack cannot be freed while it is still using that stack, so it is moved to xTasksWaitingTermination and the idle task frees it. That is one reason the idle task must get CPU time.

Zephyr names: running, ready (queued), pending (= blocked on an object), sleeping (= delayed), suspended, dead. Linux: TASK_RUNNING covers both running and runnable, TASK_INTERRUPTIBLE / UNINTERRUPTIBLE are the blocked states.

"A suspended task is the same as a blocked one." Blocked tasks wake on an event or timeout by themselves; suspended tasks only wake when explicitly resumed. Using vTaskSuspend/vTaskResume for synchronisation is a race: a resume sent before the suspend is lost. Use a notification or semaphore.

4. Scheduling policies: preemptive priority, time slicing, cooperative

▶

1. What is it?

A scheduling policy is the rule the kernel uses to choose the next task. Three rules matter on microcontrollers. Fixed-priority preemptive: the most important Ready task always runs, and it takes the CPU the moment it becomes Ready. Time slicing: tasks that share the same priority take turns, one tick (or a configured "quantum") each. Cooperative: a task keeps the CPU until it voluntarily blocks or yields.

2. How does it work, step by step?

What happens at each kind of scheduling point under the default FreeRTOS policy (preemptive + time slicing):

  1. A task blocks (delay, empty queue): it leaves the Ready list; the kernel picks the highest-priority Ready task.
  2. An ISR or another task makes a task Ready: if the new task's priority is higher than the running one, switch now (at the end of the ISR). If equal or lower, no switch; it waits in its Ready list.
  3. A tick occurs: if another task of the same priority as the running one is Ready, the kernel rotates: the running task goes to the back of its list and the next one runs. Lower priorities are never considered.
  4. A task calls taskYIELD(): it goes to the back of its priority's list; if no other task of that priority is Ready, it simply continues.

3. Worked example

Tasks A and B at priority 2, each needing 3 ticks of CPU, and L at priority 1 needing 2 ticks. All Ready at tick 0.

tick:         0   1   2   3   4   5   6   7
preemptive +  A   B   A   B   A   B   L   L     ← A,B alternate every tick; L waits until both finish
time slicing
no slicing    A   A   A   B   B   B   L   L     ← A runs to completion first, then B
cooperative   A   A   A   B   B   B   L   L     ← same here; but if H (prio 3) became ready at tick 1,
              it would wait until A blocks (tick 3) instead of running at tick 1

Response times with slicing: A finishes at 5, B at 6. Without slicing: A at 3, B at 6. Slicing makes equal tasks share fairly but delays each of them; it never helps L.

5. What goes wrong if…

  • …you give every task the same priority "to be fair"? You lose the main benefit of the RTOS: an urgent task now waits up to (number of equal tasks − 1) ticks for its turn. Symptom: control loop jitter of several milliseconds.
  • …you port FreeRTOS priorities to Zephyr without inverting them? In Zephyr 0 is more important than 5. Your idle-like logger becomes the most important thread. Symptom: everything else is starved.
  • …you choose cooperative mode and one task has a long loop without a yield? Every other task waits for it, exactly like a superloop. Symptom: watchdog resets during heavy processing.
Say it like this: "The default MCU policy is fixed-priority preemptive: the highest-priority Ready task always runs, and a newly ready higher task preempts immediately at the end of the ISR, not at the next tick. Time slicing only rotates tasks of equal priority on the tick and never gives time to lower priorities. Cooperative scheduling switches only when a task blocks or yields, which removes many races but makes latency equal to the longest gap between yields."

7. The compact reference version (for revision)

FIXED-PRIORITY PREEMPTIVE (THE DEFAULT IN EVERY MCU RTOS)

Rule: the highest-priority Ready task always runs. When a higher-priority task becomes ready (an ISR gives a semaphore, a delay expires), it preempts the running one immediately: at the end of that ISR, not at the next tick.

  • FreeRTOS: configUSE_PREEMPTION 1. Priorities 0 … configMAX_PRIORITIES−1; larger number = more important; 0 is the idle task.
  • Zephyr: smaller number = more important; negative priorities are cooperative threads, ≥ 0 are preemptible.
  • NVIC: smaller number = more urgent. Mixing these up is a common bug.

TIME SLICING (ROUND-ROBIN AMONG EQUAL PRIORITIES)

With configUSE_TIME_SLICING 1 (the default), if several Ready tasks share the top priority, the tick interrupt rotates between them each tick (FreeRTOS quantum = 1 tick; ThreadX and Zephyr allow a configurable slice, e.g. CONFIG_TIMESLICE_SIZE). Lower-priority tasks still never run while any of them is ready. Without time slicing, a task at the same priority only runs when the current one blocks or yields.

COOPERATIVE

configUSE_PREEMPTION 0: a context switch only happens when the running task blocks, delays or calls taskYIELD(). Pros: almost no data races between tasks (a task cannot be interrupted by another task between yields), smaller stacks. Cons: worst-case latency = the longest stretch between yields of any task, just like a superloop. ISRs still preempt.

OTHER POLICIES YOU SHOULD NAME

  • Rate Monotonic: a rule for assigning fixed priorities (shorter period → higher priority). Optimal among fixed-priority schemes for implicit deadlines.
  • Deadline Monotonic: shorter relative deadline → higher priority; optimal when D ≤ T.
  • EDF: dynamic priority, earliest absolute deadline runs first. Optimal on one core (100 % utilisation). Linux SCHED_DEADLINE, Zephyr CONFIG_SCHED_DEADLINE (as a tie-breaker among equal priorities).
  • Preemption threshold (ThreadX): a thread can only be preempted by threads above its threshold, which reduces context switches and stack usage.
"A higher-priority task becomes active at the next tick." No: in a preemptive kernel the switch happens as soon as the event occurs (the ISR pends PendSV, which runs right after the ISR returns). The tick only matters for time-based events and time slicing.

5. The tick interrupt and tickless idle

▶

1. What is it?

The tick is a periodic hardware interrupt, normally from the Cortex-M SysTick timer, that gives the kernel its sense of time. Every "wait 10 ms" in an RTOS is really "wait 10 ticks". Tickless idle is a power-saving mode where, when nothing has work to do, the kernel stops the periodic tick, sleeps for exactly as long as it can, and then corrects its tick count when it wakes.

2. How does it work, step by step?

  1. Configuration. At scheduler start, the port writes SysTick's reload register: LOAD = fCPU ÷ ftick − 1, and enables it with its interrupt.
  2. Each tick (every 1 ms at 1 kHz), xPortSysTickHandler runs and calls xTaskIncrementTick(), which: (a) adds 1 to xTickCount; (b) looks at the head of the delayed list, which is sorted by wake-up tick, and moves every task whose wake tick ≤ now to its Ready list; (c) decides whether a switch is needed (a woken task outranks the current one, or time slicing).
  3. If a switch is needed it sets PENDSVSET; PendSV runs right after SysTick returns (card 8).
  4. Tickless idle. When only the idle task is Ready, the idle task computes "ticks until the next delayed task wakes" (the head of the delayed list). If that is at least configEXPECTED_IDLE_TIME_BEFORE_SLEEP (2 by default), it stops SysTick, programs a timer to fire after that many ticks, executes WFI (Wait For Interrupt: the core stops until an interrupt), and on wake-up measures how much time really passed and calls vTaskStepTick(n) to add those n ticks in one go.

3. Worked example

STM32F407 at 168 MHz, configTICK_RATE_HZ = 1000
LOAD = 168 000 000 / 1000 − 1 = 167 999 (fits in 24 bits: max 16 777 215)
Longest possible SysTick sleep = 2^24 / 168 MHz = 16 777 216 / 168 000 000 = 0.0999 s ≈ 99 ticks

Battery example: tick ISR wakes the core 1000×/s for ~2 µs each.
Sensor node that only needs to run every 500 ms:
  ticking:  1000 wake-ups/s, core never reaches deep sleep (STOP mode)
  tickless: 2 wake-ups/s; with an LPTIM clocked at 32.768 kHz the core can stay in STOP
            (≈ µA instead of mA) for ~500 ms at a time

Notice the SysTick limit: a single SysTick-based tickless sleep at 168 MHz lasts at most about 99 ms, after which the port must wake up and go back to sleep. Low-power ports therefore use an LPTIM or RTC with a slow clock.

  • …you use STOP mode with the default SysTick tickless port on STM32? SysTick is clocked from the CPU clock, which stops in STOP mode, so the timer that should wake you never fires. Symptom: the system sleeps until some unrelated interrupt and the tick count falls behind real time.
  • …you set configTICK_RATE_HZ to 10 kHz for "precision"? Each tick costs ~2 µs, so 2 % of the CPU goes to ticks, and most RTOS delays still do not need that. Use a hardware timer for precise sampling instead.
Say it like this: "The tick is the SysTick interrupt, usually 1 kHz. 7. The compact reference version (for revision)

The tick is a periodic interrupt (SysTick on Cortex-M) that is the kernel's sense of time. Each tick, xTaskIncrementTick():

  1. increments xTickCount (and handles overflow by swapping the two delayed lists),
  2. moves every task whose wake time has arrived from the delayed list to its ready list (the delayed list is sorted, so it only looks at the head),
  3. decides whether a switch is needed: a woken task has higher priority, or time slicing and another equal-priority task is ready,
  4. if so, sets PendSV pending (SCB->ICSR = 1<<28).

TICKLESS IDLE (configUSE_TICKLESS_IDLE = 1)

A 1 kHz tick wakes the MCU 1000 times per second even when nothing is due, which ruins battery life. In tickless mode the idle task:

  1. computes the expected idle time = ticks until the next delayed task wakes (head of the delayed list),
  2. if it is ≥ configEXPECTED_IDLE_TIME_BEFORE_SLEEP (default 2), calls portSUPPRESS_TICKS_AND_SLEEP(xExpectedIdleTime),
  3. the port stops SysTick, programs a timer (SysTick itself for sleep, or an LPTIM/RTC clocked from LSE so it keeps running in STOP mode) to fire after that time, and executes WFI,
  4. on wake-up, by the timer or by any other interrupt, it reads how much time actually passed and calls vTaskStepTick(n) to advance the tick count in one go, then restarts the periodic tick.
Gotchas: SysTick stops in STOP mode on STM32, so deep sleep needs an LPTIM-based port. Tick compensation errors accumulate as clock drift. A wake-up from an unrelated interrupt must correctly compute the partial tick. configPRE_SLEEP_PROCESSING() is where you gate clocks or abort the sleep.

Zephyr is tickless by default (CONFIG_TICKLESS_KERNEL=y): it programs the system timer for the next timeout and never has a periodic tick at all.

6. Semaphores: binary vs counting

▶

1. What is it?

A semaphore is a counter with a waiting room. Give (also called V, post or signal) adds one to the counter and, if some task is waiting, wakes the most important waiter. Take (P, wait or pend) subtracts one if the counter is above zero, otherwise the caller waits (blocks). A binary semaphore's counter can only be 0 or 1. A counting semaphore's counter goes up to a maximum you choose.

2. How does it work, step by step?

An ISR signals a task with a binary semaphore:

  1. At start, xSemaphoreCreateBinary() creates it empty (count = 0).
  2. The task calls xSemaphoreTake(sem, portMAX_DELAY). Count is 0, so the task is put on the semaphore's waiting list and becomes Blocked.
  3. The button interrupt fires. The ISR clears the interrupt flag and calls xSemaphoreGiveFromISR(sem, &woken). The kernel sees a waiter, moves it to Ready, and sets woken = pdTRUE because the task outranks the interrupted one. (Inside FreeRTOS the count briefly becomes 1; the woken task takes it back to 0 as soon as it runs.)
  4. portYIELD_FROM_ISR(woken) pends PendSV; right after the ISR the task runs and handles the event.
  5. If instead the give comes while the task is busy (not yet waiting), the count becomes 1. The next take returns immediately and sets it back to 0. A second give before that take finds the count already 1 and is refused: the event is lost.

3. Worked example

Pulses arrive at 5 per 380 µs while the counting task is preempted for 400 µs by a more important task:

pulse 2 (give)1 → 1 (refused, lost)1 → 2

The binary semaphore answered "did at least one pulse happen?" (yes), but not "how many?" (5). That is the difference.

  • …you count events with a binary semaphore? Bursts are lost. Symptom: counts are correct at low rates and 30–60 % low under load (scenario "Five Pulses, Two Counted").
  • …you use a semaphore as a lock around shared data used by several priorities? No owner means no priority inheritance. Symptom: rare long delays of a high-priority task (unbounded priority inversion, card 12).
  • …you call xSemaphoreGive (not FromISR) in an ISR? With configASSERT defined you hit an assert; without it, rare list corruption.
Say it like this: "A semaphore is a counter plus a list of waiters: give increments and wakes the highest-priority waiter, take decrements or blocks. Semaphores have no owner, which makes them right for ISR-to-task signalling and wrong for protecting shared data, where I use a mutex with priority inheritance."

7. Timing: vTaskDelay vs vTaskDelayUntil (drift)

▶

1. What is it?

Both functions make a task wait, but they measure from different points. vTaskDelay(n) means "wait n ticks from now". xTaskDelayUntil(&last, n) means "wait until n ticks after my previous wake-up". For a task that must run periodically (every 10 ms), only the second one gives a correct average period; the first adds the task's own run time to every period, so the timing drifts.

2. How does it work, step by step?

  1. vTaskDelay(10): the kernel computes wake = xTickCount + 10 at the moment of the call, puts the task in the delayed list with that value, and blocks it.
  2. xTaskDelayUntil(&last, 10): the kernel computes wake = last + 10 (not "now" + 10), sets last = wake for next time, and blocks the task until that tick. If that tick is already in the past (the work overran), it does not block at all and returns pdFALSE.
  3. In both cases, when the wake tick arrives, the tick handler moves the task to Ready. It runs when it is the highest Ready task.

3. Worked example

A 10 ms loop whose work takes 3 ms; tick = 1 ms; task released at tick 0.

vTaskDelay(10):         start 0, work ends 3, wake 3+10 = 13
                         start 13, work ends 16, wake 26 → period 13 ms → 76.9 Hz (not 100)
                         after 1000 loops: 13 000 ms instead of 10 000 ms → 3 s behind

xTaskDelayUntil(&last,10): last=0 → wake 10; last=10 → wake 20; last=20 → wake 30 ...
                         period exactly 10 ms → 100.0 Hz, after 1000 loops still on time

If one iteration takes 12 ms (an overrun), DelayUntil at tick 12 computes wake = 10 (already past): it returns at once with pdFALSE, the next wake is 20, and the task is back on schedule after one late cycle.

5. What goes wrong if…

  • …you use vTaskDelay in a control loop? The loop period is longer than designed and varies with the work. Symptom: a PI controller tuned for 1 kHz behaves differently in the field; logged sample rates of 77 Hz instead of 100 Hz.
  • …you put last = xTaskGetTickCount() inside the loop? Same drift as vTaskDelay, hidden behind the "right" API.
  • …you need sub-tick precision (10 kHz ADC sampling)? No delay API can do it. Trigger the ADC from a hardware timer and let DMA collect the samples; the task only processes blocks.
Say it like this: "vTaskDelay is relative to the call, so the loop period is work time plus the delay and it drifts. xTaskDelayUntil computes each wake time from the previous wake time, so the average period is exact and only jitter remains; it returns pdFALSE on an overrun so I can count it. For anything that needs better than tick resolution I use a hardware timer trigger."

7. The compact reference version (for revision)

  • vTaskDelay(n) blocks until n ticks after the call. If do_work() takes 3 ms and a higher-priority task preempts for 2 ms, the period is 15 ms that iteration. The error accumulates: after 1000 iterations a "100 Hz" loop has lost seconds.
  • xTaskDelayUntil(&last, n) computes the wake time as last + n and updates last, so each release is anchored to the previous release, not to when the work finished. Jitter remains (the task may start late), but there is no cumulative drift.
  • If the work overruns the period, last + n is already in the past: the call returns immediately (in FreeRTOS ≥ 10.4 xTaskDelayUntil returns pdFALSE to tell you). The task then runs back-to-back to catch up, so detect and log overruns.
  • Both handle tick-counter wraparound because the arithmetic is unsigned.
  • For the precise cases (ADC sampling, control loops at 10 kHz) use a hardware timer to trigger the sample or the task, not the tick.
"vTaskDelay(10) gives exactly 10 ms." It gives 9–10 ticks of block time (from mid-tick to the 10th tick edge), only if the tick is 1 ms, plus however long the task waits in the Ready state before it gets the CPU.

8. Context switch on Cortex-M, step by step (PendSV, PSP, EXC_RETURN)

▶

1. What is it?

A context switch is the moment the CPU stops executing one task and starts executing another. Physically it means: copy every CPU register of the old task into that task's stack, remember where (in its TCB), then load the new task's registers from its stack. On Cortex-M, the hardware does half of the copying automatically on every interrupt, and FreeRTOS does the other half in a special low-priority interrupt handler called PendSV. Definitions used below: MSP = Main Stack Pointer (used by ISRs), PSP = Process Stack Pointer (used by tasks), EXC_RETURN = a magic value placed in LR on interrupt entry that tells the CPU how to return.

2. How does it work, step by step?

  1. Interrupt entry (hardware, 12 cycles). SysTick fires while Task A runs on PSP. The core pushes 8 registers (R0, R1, R2, R3, R12, LR, PC, xPSR) onto A's stack via PSP, sets LR = 0xFFFFFFFD ("return to Thread mode using PSP"), switches to MSP and jumps to the SysTick handler.
  2. Decision. The handler increments the tick, finds Task B is due and more important, and writes 1 to ICSR bit 28 (PENDSVSET).
  3. Tail-chain (6 cycles). When SysTick returns, PendSV is pending, so the core jumps straight into PendSV without popping A's registers first.
  4. Save the rest (software). PendSV reads PSP into R0, pushes R4–R11 and the EXC_RETURN value (and S16–S31 if A used the FPU) below the hardware frame, and stores the final R0 into TCB_A->pxTopOfStack.
  5. Choose. With kernel interrupts masked (BASEPRI = 0x50), PendSV calls vTaskSwitchContext(), which sets pxCurrentTCB = TCB_B.
  6. Load B. R0 = TCB_B->pxTopOfStack; pop R4–R11 and B's EXC_RETURN (and S16–S31 if needed); write R0 to PSP.
  7. Exception return. bx r14 with 0xFFFFFFFD: the hardware pops B's 8 registers from PSP. PC is now B's saved PC, and B continues.

3. Worked example

Task A's PSP before the tick: 0x2000_0800

PendSV pushes 9 words (R4–R11, LR) = 36 B → R0 = 0x2000_07E0 − 0x24 = 0x2000_07BC
TCB_A->pxTopOfStack = 0x2000_07BC

Each task's stack must reserve 32 + 36 = 68 B (integer) or 104 + 100 = 204 B (FPU) for a switch.

Time: ~12 (entry) + ~40 (tick handler) + 6 (tail-chain) + ~100 (PendSV + vTaskSwitchContext)

Say it like this: "On Cortex-M the hardware pushes R0–R3, R12, LR, PC and xPSR onto the task's PSP when any interrupt arrives. 7. The compact reference version (for revision)

The Cortex-M was designed to make RTOS context switches cheap. Four hardware features do most of the work. Step through it on the Context Switch tab.

THE HARDWARE PIECES

  • Two stack pointers. MSP (main) is used by handlers and at reset; PSP (process) is used by tasks in Thread mode when CONTROL.SPSEL = 1. The kernel and all ISRs share one MSP stack, so task stacks do not need room for ISR nesting, only for one exception frame.
  • Automatic stacking. On exception entry the core pushes R0–R3, R12, LR, PC, xPSR (8 words = 32 B) onto whichever stack was in use, i.e. the task's PSP. If the FPU context is active (CONTROL.FPCA = 1) it pushes an extended frame of 26 words (104 B): S0–S15, FPSCR and a reserved word as well.
  • EXC_RETURN. On entry LR is loaded with a magic value, and bx lr with that value performs an exception return that unstacks the frame. Its bits tell the core which stack and mode to return to.
  • PendSV: a software-pendable exception set to the lowest priority (0xFF, i.e. 0xF0 with 4 priority bits). It runs only when no other ISR is active, so the switch never happens in the middle of a nested ISR, and many "please switch" requests within one burst of interrupts collapse into one switch.

WHY ONLY R4–R11 IN SOFTWARE?

AAPCS splits registers into caller-saved (R0–R3, R12, LR, S0–S15) and callee-saved (R4–R11, S16–S31). The hardware saves the caller-saved set so that a handler can be a normal C function. PendSV must save the callee-saved set itself because it is about to run a different task's code that will overwrite them.

LAZY FP STACKING

With FPCCR.ASPEN and LSPEN = 1 (FreeRTOS sets both in xPortStartScheduler), on entry the core only reserves the 18 FP words and records the address in FPCAR. The registers are actually written only if the handler executes an FP instruction. The vstmdb in PendSV is such an instruction, so for an FP-using task the lazy save happens there. ISRs that do not touch the FPU never pay the ~17-cycle FP save.

COST

Exception entry 12 cycles, tail-chaining 6 cycles, exit ≈ 10 cycles (zero-wait-state memory). A full FreeRTOS switch on an M4 is roughly 100–200 cycles including vTaskSwitchContext, i.e. ~1 µs at 168 MHz, plus 32 more register transfers when FP context is involved. Measure it with the DWT cycle counter (DWT->CYCCNT) or a GPIO toggle in traceTASK_SWITCHED_IN.

"The context switch happens inside SysTick." SysTick only decides a switch is needed and pends PendSV. When SysTick returns, the core tail-chains straight into PendSV without unstacking, which costs 6 cycles instead of 12+10.

9. Starting the first task: fake stack frame + SVC

▶

1. What is it?

The context switch in card 8 restores a task from a saved context. But a brand-new task has never run, so it has nothing saved. FreeRTOS solves this by fabricating a saved context at creation time, exactly as if the task had been interrupted at the first instruction of its function. The very first task is then started with an SVC (Supervisor Call) instruction, a software interrupt whose handler performs only the "restore" half of a switch.

2. How does it work, step by step?

  1. xTaskCreate calls pxPortInitialiseStack(top, vTaskFn, pvParam), which writes 17 words (no FP) at the top of the new stack: xPSR = 0x01000000, PC = the task function, LR = prvTaskExitError, R12/R3/R2/R1 = don't care, R0 = the parameter, then EXC_RETURN = 0xFFFFFFFD and R11…R4 = don't care.
  2. vTaskStartScheduler creates the idle task (priority 0) and the timer task, then calls xPortStartScheduler.
  3. xPortStartScheduler sets PendSV and SysTick to the lowest priority, programs and starts SysTick, enables FPU lazy stacking, and calls prvPortStartFirstTask.
  4. prvPortStartFirstTask reads the initial MSP value from the vector table (word 0) and writes it back into MSP, throwing away everything main() had on its stack. It enables interrupts and executes svc 0.
  5. vPortSVCHandler loads pxCurrentTCB->pxTopOfStack, pops R4–R11 and EXC_RETURN, sets PSP, clears BASEPRI and executes bx r14.
  6. The hardware pops the fabricated 8-word frame from PSP: PC = the task function, R0 = its parameter. The first task is running, in Thread mode, on its own stack.

10. Scheduler data structures: ready lists, bitmap + CLZ, O(1) selection

▶

1. What is it?

The scheduler has to answer one question very often and very fast: which Ready task has the highest priority? FreeRTOS keeps one list of Ready tasks per priority level plus a 32-bit bitmap in which bit n is 1 when the list for priority n is non-empty. The Cortex-M3/M4 instruction CLZ (Count Leading Zeros) finds the highest set bit in one cycle, so choosing the next task takes the same time whether you have 3 tasks or 300. That is what "O(1) scheduling" means: constant time.

2. How does it work, step by step?

  1. A task becomes Ready at priority p: append it to pxReadyTasksLists[p] and set bit p: uxTopReadyPriority |= (1 << p).
  2. A list becomes empty (its last task blocks): clear bit p.
  3. To choose: top = 31 − CLZ(uxTopReadyPriority). That is the highest non-empty priority.
  4. Within that list, take the next task after the list's index pointer (listGET_OWNER_OF_NEXT_ENTRY). Advancing the index each time is what gives round-robin among equal priorities for free.
  5. Delayed tasks live in a separate list sorted by wake-up tick. Each tick only the head is compared with the tick count: O(1) when nothing wakes.

3. Worked example

Ready tasks at priorities 0 (idle), 5 and 7:
bitmap = 1<<0 | 1<<5 | 1<<7 = 0b0000_0000_0000_0000_0000_0000_1010_0001 = 0x000000A1
CLZ(0x000000A1): leading zeros before bit 7 = 31 − 7 = 24
top = 31 − 24 = 7 → run the next task in pxReadyTasksLists[7]

Task at 7 blocks, its list is now empty: bitmap &= ~(1<<7) → 0x00000021
CLZ(0x21) = 26 → top = 5

Compare the generic C version: it starts at the highest priority that was ever ready and decrements until it finds a non-empty list. With 32 priorities that can be up to 31 checks per switch; with the bitmap it is always one instruction.

  • …you set configMAX_PRIORITIES to 40 with configUSE_PORT_OPTIMISED_TASK_SELECTION = 1? A 32-bit bitmap cannot hold 40 bits; FreeRTOS refuses to compile (an #error in portmacro.h). Use ≤ 32 or the generic method.
  • …you use the optimised method on Cortex-M0/M0+? ARMv6-M has no CLZ instruction, so the port does not offer it; the generic scan is used.
  • …you create 200 delayed tasks? Inserting into the sorted delayed list is O(n), so vTaskDelay itself gets slower with many delayed tasks, even though the tick check stays O(1).
Say it like this: "FreeRTOS keeps an array of ready lists, one per priority, and on Cortex-M3 and up a 32-bit bitmap of which lists are non-empty. The highest ready priority is 31 minus CLZ of the bitmap, one instruction, so selection is O(1) and limited to 32 priorities. Round-robin within a priority comes free from the list's index pointer. Delayed tasks sit in a list sorted by wake time, so the tick only looks at the head, and there are two delayed lists to handle tick-counter overflow."

  • CLZ (count leading zeros) is a single-cycle Cortex-M3/M4 instruction (not on M0/M0+). So the optimised mode limits you to 32 priorities. Example: map = 0b0000_1010_0001 → CLZ = 24 → top = 31 − 24 = 7.
  • Round-robin is free: each list keeps an index pointer, and listGET_OWNER_OF_NEXT_ENTRY advances it, so equal-priority tasks take turns.
  • Insert into a ready list is O(1) (append at end). Insert into the delayed list is O(n) because it is sorted by wake time, but the tick only checks the head: O(1) per tick when nothing wakes.
  • Event lists (waiting on a queue) are sorted by priority, so xQueueSend wakes the highest-priority waiter in O(1).
  • Larger RTOSes with up to 256 priorities (ThreadX has 32–1024 configurable, μC/OS-III, Zephyr multiq) use a two-level bitmap: one word saying which group of 32 is non-empty, then CLZ inside the group. Still O(1).
  • Zephyr lets you pick the ready queue: CONFIG_SCHED_SIMPLE (formerly DUMB, a sorted list, smallest code), CONFIG_SCHED_SCALABLE (red-black tree, many threads), CONFIG_SCHED_MULTIQ (array of lists + bitmap, O(1), the classic RTOS design).
Why two delayed lists? Wake time = now + delay can overflow the 32-bit tick counter. Tasks whose wake time wrapped go into the overflow list. When xTickCount wraps to 0, the kernel swaps the two list pointers. This keeps the sorted insert correct without comparing wrapped values.

11. Mutexes: ownership, recursion, priority inheritance

▶

1. What is it?

A mutex (short for MUTual EXclusion) is a lock that guarantees only one task at a time uses a shared resource, such as an I2C bus, a global struct or a file. It looks like a binary semaphore that starts at 1, but it has an owner: the task that took it. Because the kernel knows the owner, it can do three things a semaphore cannot: refuse a release by anybody else, let the owner take it again (recursive mutex), and temporarily raise the owner's priority when a more important task is waiting (priority inheritance).

2. How does it work, step by step?

  1. Low task L (prio 1) takes the mutex. It is free, so the kernel records L as the holder and L continues.
  2. High task H (prio 3) wakes and tries to take it. The mutex is held. Before blocking H, the kernel calls xTaskPriorityInherit(L): L's priority 1 < 3, so L's priority is raised to 3 and L is moved to the priority-3 Ready list. H blocks.
  3. Medium task M (prio 2) wakes. It is less important than L's current priority (3), so it cannot preempt L.
  4. L gives the mutex. xTaskPriorityDisinherit drops L back to 1 (because L holds no other mutexes) and hands the mutex to H, which becomes Ready and, at priority 3, runs immediately.
  5. H finishes with the resource, gives the mutex, and later M and L run.

3. Worked example

L takes the I2C mutex at t = 0 for a 0.6 ms transfer. H wakes at t = 0.2 ms and needs I2C.
M (no I2C) wakes at t = 0.3 ms and wants to run for 20 ms.

Without inheritance:  H waits 0.4 ms (rest of L's transfer) + 20 ms (all of M) = 20.4 ms
With inheritance:     H waits 0.4 ms (rest of L's transfer), then runs; M runs after H
                      blocking of H = 0.4 ms, bounded by one critical section

5. What goes wrong if…

  • …you take a mutex in an ISR? An ISR has no TCB, cannot be an owner and cannot block. FreeRTOS asserts (with configASSERT). Symptom without the assert: corrupted inheritance state.
  • …the holder takes the same (non-recursive) mutex twice? It blocks on itself: a one-task deadlock. Symptom: that task hangs in xSemaphoreTake with itself as holder.
  • …you hold two mutexes? FreeRTOS only restores the base priority when all mutexes are released, so the boost may last longer than needed. Not a bug, but it lengthens other tasks' blocking.
Say it like this: "A mutex is a lock with an owner. Only the owner may release it, it can be recursive, and because the kernel knows the owner it applies priority inheritance: when a higher-priority task blocks on it, the holder runs at that higher priority until it releases, so medium tasks cannot stretch the wait. It must never be used from an ISR. I always take it with a finite timeout and release it on a single exit path."

7. The compact reference version (for revision)

A mutex (mutual exclusion lock) protects a shared resource. Unlike a binary semaphore it has an owner:

  • Only the owner may release it. FreeRTOS records xMutexHolder; POSIX PTHREAD_MUTEX_ERRORCHECK returns EPERM otherwise.
  • Priority inheritance (PI): if a higher-priority task blocks on a mutex, the owner's priority is raised to that task's priority until it releases the mutex. This is impossible with a semaphore, because there is no owner to boost.
  • Recursive mutex: the owner can take it again without deadlocking itself; a counter tracks depth and it must be given as many times as it was taken (xSemaphoreCreateRecursiveMutex, xSemaphoreTakeRecursive). Useful when a locked API calls another locked API; often a sign of poor layering.
  • Not usable from ISRs: an ISR is not a task. It cannot block, it has no priority to inherit to, and it cannot "own" anything.
SemaphoreHandle_t i2cLock = xSemaphoreCreateMutex();      // created "available"

bool i2c_write(uint8_t addr, const uint8_t *d, size_t n) {
    if (xSemaphoreTake(i2cLock, pdMS_TO_TICKS(50)) != pdTRUE)
        return false;                                    // bounded wait, report error
    bool ok = hal_i2c_tx(addr, d, n);
    xSemaphoreGive(i2cLock);                               // same task gives it back
    return ok;
}

HOW FREERTOS INHERITANCE WORKS

  • In xQueueSemaphoreTake, before blocking: xTaskPriorityInherit(holder). If holder's priority < caller's, the holder is moved from its ready list to the caller's priority list.
  • On give: xTaskPriorityDisinherit(). FreeRTOS restores the base priority only when the task holds no more mutexes (uxMutexesHeld == 0). With nested mutexes the boost lasts until the last one is released: simple, slightly pessimistic.
  • If a waiter times out, vTaskPriorityDisinheritAfterTimeout() lowers the holder back to the highest priority among the remaining waiters.
  • Inheritance is transitive in full PI (H waits on M1 held by M, M waits on M2 held by L → L gets H's priority). FreeRTOS handles one level per take; Zephyr and Linux rt_mutex walk the chain.
"Priority inheritance prevents priority inversion." It bounds it. The high task still waits for the low task's critical section (that is unavoidable), but it no longer waits for unrelated medium-priority tasks. And PI alone does not prevent deadlock.

12. Priority inversion and the Mars Pathfinder story

▶

1. What is it?

Priority inversion is the situation where a high-priority task is waiting while a lower-priority task runs. A short wait for a low task that holds a lock is normal and unavoidable (bounded inversion). The dangerous version, unbounded inversion, happens when a medium-priority task that has nothing to do with the lock preempts the low task while it holds the lock: now the high task waits for the medium task's entire work, which can be arbitrarily long. The most famous example happened on Mars in 1997.

2. How does it work, step by step?

  1. L (low) takes mutex M and starts using the shared resource.
  2. H (high) becomes Ready, preempts L, tries to take M, and blocks. So far this is bounded: H only needs L to finish its short critical section.
  3. Med (medium, never uses M) becomes Ready. The scheduler compares Med (2) with L (1): Med wins and preempts L.
  4. L cannot run, so it cannot release M, so H cannot run. H is effectively running at a priority below Med.
  5. H's wait now equals Med's whole execution time plus any other medium tasks that arrive: unbounded.

3. Worked example (the Scheduler Sim "Mars Pathfinder" preset)

bc_dist  prio 3, released t=2,  C=3, D=10, takes M1 at its first tick for 2 ticks
comms    prio 2, released t=3,  C=12, no mutex

t=0 ASI/MET runs; t=1 takes M1
t=2 bc_dist preempts, tries M1 → blocked
t=3 comms preempts ASI/MET (2 > 1) and runs 12 ticks → until t=15
t=15 ASI/MET resumes; it has held M1 for 2 ticks and needs 2 more → releases at t=17
t=17 bc_dist finally gets M1 and finishes at t=20; its deadline was t = 2 + 10 = 12 → MISSED by 8 ticks
With inheritance: ASI/MET runs at prio 3 from t=2, releases M1 at t=5, bc_dist done at t=8 ✔

  • …you only test at low load? Inversion needs the medium task to be Ready at exactly the wrong moment. Pathfinder's bug appeared only when the meteorological data rate was high. Symptom: passes every bench test, fails in the field.
  • …you "fix" it by raising H's priority? H is blocked; a blocked task cannot run at any priority. Nothing changes.
  • …there is no timeout or watchdog? The failure is silent: H is just late. Pathfinder's bc_sched check converted it into a visible reset, which is what let engineers find it.
Say it like this: "Unbounded priority inversion needs three tasks: low holds a lock, high blocks on it, and a medium task that does not use the lock preempts low, so high waits for all of medium's work. JPL reproduced it on the ground and uploaded a patch turning on priority inheritance for that mutex."

7. The compact reference version (for revision)

Priority inversion = a high-priority task waits while a lower-priority task runs. Bounded inversion (H waits for L's short critical section) is normal. Unbounded inversion is the bug:

  1. L takes mutex M.
  2. H becomes ready, preempts L, tries to take M, blocks.
  3. M-priority task (does not use M at all) becomes ready and preempts L, because M > L.
  4. H now waits for all of M's work, which can be arbitrarily long. H's priority is effectively below M's.

MARS PATHFINDER, JULY 1997

  • Pathfinder landed on 4 July 1997 running VxWorks (Wind River) on a RAD6000 CPU. A few days into the mission the lander began doing total system resets, losing data each time.
  • Tasks involved: bc_dist, a high-priority task that distributed data on the "information bus" (a shared memory area protected by a mutex); the ASI/MET meteorological data task, low priority, which published to the bus occasionally; and a communications task of medium priority that ran for a long time.
  • The low-priority ASI/MET task held the bus mutex (through VxWorks's select()/pipe mechanism). bc_dist blocked on it. The medium communications task preempted ASI/MET. When the next bus cycle began, the scheduler task bc_sched found that bc_dist had not completed and treated it as a critical fault: it reset the system. A watchdog-style check did its job.
  • JPL engineers (Glenn Reeves's team) reproduced it on a ground replica with full tracing enabled, which took about 18 hours. The mutex had been created without the priority inheritance option. VxWorks supports it (SEM_INVERSION_SAFE).
  • Fix: they uploaded a small patch that changed the global initialisation parameter so the select mutex was created with priority inheritance on. The C interpreter they had left in the flight software made the patch possible. The resets stopped.
Lessons interviewers want: (1) use mutexes with PI or ceiling for any lock shared across priorities; (2) keep critical sections short; (3) keep tracing and patching capability in deployed systems; (4) the watchdog/timeout check turned a silent timing failure into a visible, recoverable one; (5) test under worst-case load: the bug only appeared when the data rate was high.

13. Priority ceiling protocols (OCPP, ICPP / highest locker)

▶

1. What is it?

A priority ceiling protocol is an alternative to priority inheritance. Every mutex is given, at design time, a ceiling: the highest priority of any task that will ever lock it. In the Immediate Ceiling Priority Protocol (ICPP, also called "highest locker" or POSIX "priority protect"), a task that locks the mutex is raised to the ceiling immediately, before anyone else has even asked for it. That means no task that could compete for the mutex can run while it is held.

2. How does it work, step by step?

  1. Design time: list who uses each mutex. M1 is used by tasks of priorities 1 and 3 → ceiling(M1) = 3.
  2. L (prio 1) locks M1: its priority immediately becomes 3.
  3. H (prio 3) becomes Ready: it is not higher than L's current 3, so it does not preempt. It simply waits in the Ready list. It never blocks on the mutex.
  4. Med (prio 2) becomes Ready: 2 < 3, so it cannot preempt L either.
  5. L unlocks M1: its priority drops back to 1. H (3) is now the highest Ready task and runs; it takes M1, which is guaranteed free.

3. Worked example: why ICPP prevents deadlock

Task A (prio 2) locks spi then flash. Task B (prio 3) locks flash then spi.
ceiling(spi) = ceiling(flash) = 3

Plain mutexes:   A locks spi → B preempts, locks flash → B wants spi (held by A) → blocks
                 → A runs, wants flash (held by B) → blocks → DEADLOCK
ICPP:            A locks spi → A runs at prio 3 → B (3) cannot preempt (not higher)
                 → A locks flash, finishes, unlocks both → B runs and gets both → no deadlock

Blocking bound: with ICPP a task is blocked at most once, for at most the single longest critical section of a lower-priority task on a mutex whose ceiling ≥ its priority. If low tasks hold critical sections of 0.3 ms, 0.5 ms and 0.2 ms, then B = 0.5 ms (with inheritance it could be 0.3 + 0.5 + 0.2 = 1.0 ms in the worst chain).

  • …a new task starts using the mutex but nobody updates the ceiling? The new, higher task can now preempt a holder and block on the mutex: the guarantee is gone silently.
  • …a holder keeps the mutex for a long time? Every task between its own priority and the ceiling is delayed, even tasks that never use the mutex. That cost is the price of ICPP.
  • …you need this in FreeRTOS? There is no ceiling mutex. Emulate it by raising priority with vTaskPrioritySet around the section, or use a short critical section / scheduler lock.
Say it like this: "The ceiling of a mutex is the highest priority of any task that uses it. With the immediate ceiling protocol a task jumps to that ceiling as soon as it locks, so no competing task can even start. A task is then blocked at most once, by one critical section, and deadlock is impossible on a single core. It needs static design-time knowledge, which is why OSEK and AUTOSAR use it, while general RTOSes like FreeRTOS use inheritance."

pthread_mutexattr_setprioceiling(&a, 40);     // ceiling = highest user priority
/* or PTHREAD_PRIO_INHERIT for PIP */
  • Why ICPP prevents deadlock (one core): while a task holds a mutex it runs at that mutex's ceiling, so no other task that uses the same mutex can even start running and take a second lock in the opposite order.
  • Cost: a task holding the mutex delays tasks between its own priority and the ceiling even if they never wanted the mutex (they are "blocked" by priority, not by the lock). Ceilings must be maintained when tasks change.
  • FreeRTOS has no ceiling mutex; the equivalent is to raise priority with vTaskPrioritySet or to use a critical section/scheduler lock for very short sections.
Blocking term in response-time analysis: with PCP/ICPP, Bi = the longest single critical section of any lower-priority task on a mutex whose ceiling ≥ prio(i). With PIP, Bi can be a sum of several critical sections.

14. Event groups, queues, task notifications, stream/message buffers

▶

1. What is it?

Besides semaphores and mutexes, an RTOS offers several ways for tasks (and ISRs) to pass data or events. A queue is a fixed-size FIFO of fixed-size messages. An event group is a word of flag bits that tasks can wait on. A task notification is a 32-bit value built into every TCB that another task or ISR can set. A stream buffer is a byte FIFO for one writer and one reader; a message buffer is the same but keeps message boundaries. Picking the right one is a common interview question.

2. How does it work, step by step? (queue by copy)

  1. xQueueCreate(8, sizeof(msg_t)) allocates storage for 8 messages plus a control block.
  2. xQueueSend(q, &m, timeout): if there is space, the kernel copies sizeof(msg_t) bytes from &m into the next slot (inside a critical section), and if a task is waiting to receive, it wakes the highest-priority one. If the queue is full, the sender blocks up to timeout.
  3. xQueueReceive(q, &out, timeout): if there is a message, copy it out to &out, free the slot, wake a waiting sender if any. If empty, block.
  4. Because the data is copied, the sender may reuse or destroy its own m immediately after the call.

3. Worked example

msg_t = { uint32_t id; int16_t x, y, z; uint16_t flags; } = 4 + 6 + 2 = 12 bytes
queue of 8 → storage 8 × 12 = 96 B + ~80 B control block

Cost per message by copy: 2 memcpy of 12 B ≈ a few dozen cycles + kernel overhead ≈ 1–2 µs
A 1 KB image frame by copy: 2 × 1024 B copied, the critical section grows with it → use a pointer:
queue of 8 pointers = 8 × 4 B = 32 B; the frames live in a static pool

Notification as an event counter from an ISR:  vTaskNotifyGiveFromISR(h, &w)
  FreeRTOS states ~45 % faster than a binary semaphore and uses 0 extra RAM (already in the TCB)

  • …you queue a pointer to a local (stack) buffer? The sender returns or loops, the buffer is overwritten, and the receiver reads garbage. Symptom: corrupted messages that look "almost right".
  • …you pass f instead of &f to xQueueSend? The kernel copies 4 bytes from the frame's first field instead of the pointer. Symptom: the receiver gets a nonsense address and HardFaults.
  • …two ISRs write the same stream buffer? Stream buffers assume a single writer; concurrent writers corrupt the indices. Use a queue or serialise the writers.
  • …a library also uses task notification index 0 on the same task? The two uses overwrite each other's value. Use a different index (configTASK_NOTIFICATION_ARRAY_ENTRIES > 1).
Say it like this: "FreeRTOS queues copy data in and out, which is simple and safe for small items and gives many-to-many communication. For large buffers I queue pointers with a free-buffer pool and an explicit ownership rule. For one ISR signalling one task, a direct task notification is the fastest and uses no extra RAM. Stream and message buffers are lock-free byte FIFOs for one writer and one reader, ideal for UART data, and event groups let a task wait for any or all of several flags."

MESSAGE QUEUES: COPY vs REFERENCE

FreeRTOS queues copy the item into the queue storage on send and copy out on receive (memcpy of itemSize bytes inside a critical section).

  • By copy (small items ≤ ~16–32 B): simple, no ownership problems, sender can reuse its buffer immediately. Cost: two memcpys, and the critical section length grows with item size.
  • By reference (large buffers): queue a pointer (itemSize = sizeof(buf_t*)). Fast, but you now need an ownership rule: the sender must not touch the buffer after sending, and the buffer must not be on the sender's stack. Pair it with a pool of free buffers (a second queue of free pointers).
QueueHandle_t q = xQueueCreate(8, sizeof(msg_t));   // 8 items, copied

xQueueReceive(q, &m, portMAX_DELAY);                 // block until data

EVENT GROUPS

A word of flag bits (24 usable bits with a 32-bit tick type). A task can wait for any or all of a set of bits, optionally clearing them on exit. xEventGroupSync() implements a rendezvous/barrier. Setting bits can wake many tasks, so it is not deterministic: xEventGroupSetBitsFromISR() therefore defers the work to the timer service task.

DIRECT-TO-TASK NOTIFICATIONS

Each TCB has a 32-bit notification value and state (an array since v10.4, configTASK_NOTIFICATION_ARRAY_ENTRIES). xTaskNotifyGive / ulTaskNotifyTake act as a lightweight counting or binary semaphore; xTaskNotify(eSetBits) acts like an event group; eSetValueWithOverwrite as a mailbox. FreeRTOS documents them as up to 45 % faster than a binary semaphore with no extra RAM. Limits: one receiving task only (the target), the sender cannot block waiting for the value to be consumed, no broadcast.

STREAM AND MESSAGE BUFFERS (v10+)

Byte-stream ring buffers optimised for one writer and one reader (e.g. UART ISR → protocol task). Because there is a single writer and single reader, no lock is needed around the data copy. A message buffer stores a length prefix (a size_t, 4 B) before each message so messages are read whole. A trigger level wakes the reader only when enough bytes have arrived. Multiple writers need external serialisation.

15. ISRs and the kernel: FromISR APIs, configMAX_SYSCALL_INTERRUPT_PRIORITY, deferred processing

▶

1. What is it?

Interrupt handlers and the RTOS have to cooperate carefully, because an ISR can fire in the middle of the kernel changing its own lists. Three rules make it safe. (1) An ISR may only call the special ...FromISR() versions of kernel functions. (2) Only ISRs whose NVIC priority is numerically equal to or greater than configMAX_SYSCALL_INTERRUPT_PRIORITY may call them at all. (3) The ISR should do the minimum and hand the real work to a task (deferred interrupt processing).

2. How does it work, step by step?

  1. The priority split. STM32 implements 4 priority bits: values 0 (most urgent) to 15 (least). FreeRTOS stores configMAX_SYSCALL_INTERRUPT_PRIORITY = 5 << 4 = 0x50. During its critical sections the kernel writes 0x50 to the BASEPRI register, which blocks every interrupt whose priority value is ≥ 5. Interrupts 0–4 are never blocked.
  2. A UART ISR at priority 6 fires while a task runs. It reads the byte and calls xQueueSendFromISR(q, &c, &woken).
  3. Inside the FromISR call: it saves the current BASEPRI and raises it to 0x50 (so another kernel-aware ISR cannot interleave), copies the byte, and if a task was waiting for data, moves it to Ready. If that task's priority is higher than the interrupted task's, it sets woken = pdTRUE. It never blocks and never switches.
  4. At the very end of the ISR, portYIELD_FROM_ISR(woken) pends PendSV if woken is true. The switch happens right after the ISR, not at the next tick.
  5. A motor-control ISR at priority 2 is never masked by the kernel, so its latency is not increased by the RTOS at all. In exchange it must never call any FreeRTOS function, because it could interrupt the kernel mid-update.

3. Worked example

configPRIO_BITS = 4  (STM32: __NVIC_PRIO_BITS = 4)
configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5
configMAX_SYSCALL_INTERRUPT_PRIORITY = 5 << (8 − 4) = 5 × 16 = 80 = 0x50
configKERNEL_INTERRUPT_PRIORITY      = 15 << 4 = 240 = 0xF0  (SysTick, PendSV)

Why the shift by 4? The NVIC priority registers are 8 bits wide but STM32 only implements the top 4. Priority 5 is stored as 0101_0000 = 0x50. BASEPRI uses the same 8-bit format.

5. What goes wrong if…

  • …an ISR at priority 0–4 calls a FromISR function? It can run while the kernel is half-way through linking a list node. Symptom: a crash hours later in vListInsert or an endless loop in the tick handler. With configASSERT defined, vPortValidateInterruptPriority() catches it immediately.
  • …you call xQueueSend (no FromISR) in an ISR? It uses the task-level critical section and may try to block. Symptom: an assert in vPortEnterCritical or random lock-ups (scenario "xQueueSend in the UART ISR").
  • …you forget portYIELD_FROM_ISR? The woken task waits until the next tick or until the current task blocks. Symptom: up to 1 ms of extra latency, everything else works.
Say it like this: "ISRs can't block and must not switch context mid-handler, so FreeRTOS has FromISR APIs with no timeout and a woken flag; at the end of the ISR portYIELD_FROM_ISR pends PendSV so the woken task runs immediately. Kernel critical sections write BASEPRI with configMAX_SYSCALL_INTERRUPT_PRIORITY, 0x50 on STM32, so interrupts with priority values 5 to 15 may use the kernel, and 0 to 4 run with zero added latency but may never call it. I keep ISRs short and defer the processing to a task with a notification."

7. The compact reference version (for revision)

WHY SEPARATE FromISR APIs

  • An ISR cannot block, so xQueueSendFromISR has no timeout parameter.
  • An ISR must not context-switch in the middle of itself. Instead the API reports through pxHigherPriorityTaskWoken, and the ISR calls portYIELD_FROM_ISR(woken) at the end, which just pends PendSV.
  • They use portSET_INTERRUPT_MASK_FROM_ISR() (saves and restores the old BASEPRI) instead of the nesting-counter critical section.

THE PRIORITY SPLIT ON CORTEX-M

  • Kernel critical sections write BASEPRI = 0x50: interrupts with priority value 5…15 are masked; 0…4 still run with zero added latency. That is how FreeRTOS gives you "zero-latency" interrupts for motor control or safety.
  • The cost: an ISR at priority 0–4 must never call any FreeRTOS API, because it could run in the middle of a list update. With configASSERT defined, vPortValidateInterruptPriority() catches violations.
  • Reset default NVIC priority is 0 (the highest) for every IRQ. So an ISR you forgot to configure is automatically in the forbidden range. This is among the most common FreeRTOS support-forum bugs.

16. Critical sections vs scheduler suspension

▶

1. What is it?

There are three ways to protect shared data, and they differ in who is kept out. A critical section (taskENTER_CRITICAL) keeps out other tasks and kernel-aware interrupts by raising BASEPRI. Scheduler suspension (vTaskSuspendAll) keeps out other tasks but lets every interrupt run. A mutex keeps out only the tasks that want the same mutex. The longer the protected operation, the narrower the protection you should choose.

2. How does it work, step by step?

  1. taskENTER_CRITICAL(): write 0x50 to BASEPRI (masking ISR priorities 5–15), dsb; isb, increment uxCriticalNesting. No task switch can happen because SysTick and PendSV (priority 15) are masked. taskEXIT_CRITICAL(): decrement; if it reaches 0, write 0 to BASEPRI.
  2. vTaskSuspendAll(): increment uxSchedulerSuspended. Ticks still happen, ISRs still run and may still make tasks Ready, but those tasks go onto xPendingReadyList and no switch happens. xTaskResumeAll(): decrement; at 0, move the pending tasks to their ready lists, process missed ticks, and switch if needed.
  3. Mutex take/give: only a task calling take on the same mutex is blocked; everything else runs normally, the holder may itself block, and priority inheritance applies.

3. Worked example

Shared 32-bit counter, updated by an ISR and read-modify-written by a task:
  task code: counter++;   compiles to   LDR r1,[r0]  ;  ADDS r1,#1  ;  STR r1,[r0]
  if the ISR does counter++ between the LDR and the STR, the ISR's increment is lost.
  → critical section: 3 instructions protected, ≈ 10–15 cycles of masking ≈ 0.1 µs

Copying a 2 KB configuration table shared only between tasks:
  memcpy 2048 B at ~1 byte/cycle effective ≈ 2000 cycles ≈ 12 µs
  critical section: adds 12 µs to the latency of every kernel-aware ISR
  scheduler suspension: ISR latency unchanged; other tasks wait 12 µs  → better choice

I2C transfer of 32 bytes at 400 kHz: 32 × 9 bits / 400 000 ≈ 0.72 ms
  critical section: blocks all kernel ISRs and the tick for 0.72 ms → never
  mutex: only other I2C users wait → right choice

  • …you use __disable_irq() (PRIMASK) instead? It also masks your priority 0–4 "zero-latency" interrupts. Symptom: motor-control jitter whenever the kernel is busy.
  • …you call vTaskDelay inside a critical section? The task asks to block but switching is impossible. Symptom: an assert, or the system freezes.
  • …you think vTaskSuspendAll protects data shared with an ISR? ISRs still run. Symptom: the same lost-update race as with no protection.
Say it like this: "A critical section raises BASEPRI, so it keeps out tasks and kernel-aware ISRs; it is for a few instructions of data shared with an ISR. Scheduler suspension stops task switches but leaves ISRs running, for longer task-only work without hurting interrupt latency. A mutex only affects tasks that want the same resource and supports blocking and inheritance, so it is for long ownership like a bus transfer. Single aligned 32-bit loads and stores are atomic on Cortex-M, but read-modify-write is not."

17. Memory management: heap_1 … heap_5 and static allocation

▶

1. What is it?

Every task, queue, semaphore and timer needs RAM. FreeRTOS can take that RAM from its own heap (a big static array ucHeap[configTOTAL_HEAP_SIZE] managed by one of five allocators, heap_1.c to heap_5.c), or you can hand it the memory yourself as static variables (static allocation). The choice decides whether memory can be freed, whether it can fragment, and whether an allocation can fail while the product is running.

2. How does it work, step by step? (heap_4, the usual default)

  1. At the first allocation, the whole ucHeap array becomes one big free block. Every block starts with an 8-byte header: a pointer to the next free block and the block size.
  2. pvPortMalloc(n): round n up to a multiple of 8 and add the 8-byte header. Walk the free list (sorted by address) and take the first block that is big enough. If the block is much bigger, split it and leave the remainder in the free list.
  3. vPortFree(p): step back 8 bytes to the header, insert the block in the free list at its address position, and if the block right before or right after it is also free, merge them into one (coalescing).
  4. The allocator runs with the scheduler suspended, so it is thread-safe but not usable from ISRs.

3. Worked example: fragmentation

Heap 10 KB. Allocate A=2 KB, B=2 KB, C=2 KB, D=2 KB (2 KB left at the end).
Free B and D.
  heap_2 (no coalescing): free blocks = 2 KB (B), 2 KB (D), 2 KB (end) → 6 KB free
                          D and the end block are adjacent, but heap_2 never merges them,
                          so malloc(3 KB) FAILS although 6 KB are free.
  heap_4 (coalescing):    D + end merge into 4 KB → free = 2 KB (B) + 4 KB → malloc(3 KB) OK
Now free A as well: heap_4 merges A + B → 4 KB, plus 4 KB at the end.

  • …tasks are created and deleted at runtime with heap_2? Fragmentation grows until creation fails. Symptom: works for days, then xTaskCreate returns an error.
  • …the malloc-failed hook is disabled? A failed allocation returns NULL silently. Symptom: a NULL queue handle passed to xQueueSend, then a HardFault far from the cause.
  • …printf and FreeRTOS use different heaps? newlib's malloc is not protected against two tasks calling it at once. Symptom: rare heap corruption when two tasks print.
Say it like this: "heap_1 only allocates and never frees, heap_2 frees without coalescing so it fragments, heap_3 wraps the C library malloc, heap_4 is first-fit with coalescing and is the usual default, and heap_5 is heap_4 over several RAM regions. 18. Stack sizing and overflow detection (method 1/2, canary, MPU)

▶

1. What is it?

Each task has a fixed-size stack. If the task ever needs more (a deep call chain, a big local array, printf), it writes past the end of its stack into whatever memory lies below it: usually another task's TCB or stack. That is a stack overflow, and it is the most common RTOS crash. Sizing means choosing a size that is always enough; detection means noticing as early as possible when it was not.

2. How does it work, step by step? (sizing)

  1. Measure the code's own need. Compile with -fstack-usage: GCC writes a .su file per source file with each function's frame size. Add up the frames along the deepest call path.
  2. Add one exception frame: 32 B (or 104 B if the task uses the FPU), because when an interrupt arrives the hardware pushes it onto the task's stack. Nested ISRs go on the MSP, not here.
  3. Add the saved context: 36 B for R4–R11 + EXC_RETURN, plus 64 B for S16–S31 if FP.
  4. Add library calls: newlib printf with %f can need 1–2 KB.
  5. Run and measure: uxTaskGetStackHighWaterMark(h) returns the minimum free space ever seen, in words, by scanning for the 0xA5 fill pattern. Add a 20–50 % margin.

19. Software timers and the timer service (daemon) task

▶

1. What is it?

A software timer calls a function of yours (a callback) after a delay, once (one-shot) or repeatedly (auto-reload), without you writing a task for it. In FreeRTOS all callbacks run inside one hidden task, the timer service task (also called the daemon task, prvTimerTask), and all timer commands (start, stop, reset) are sent to it through a queue. Knowing this explains every rule about timers.

2. How does it work, step by step?

  1. vTaskStartScheduler() creates the timer task with priority configTIMER_TASK_PRIORITY and a command queue of length configTIMER_QUEUE_LENGTH.
  2. xTimerStart(t, 0) does not touch any timer list. It sends a "start t" command to the queue and returns.
  3. The timer task, which was blocked on that queue, wakes, computes expiry = now + period, and inserts the timer into its active list sorted by expiry.
  4. The timer task then blocks until either the earliest expiry time arrives or a new command arrives, whichever is first. Idle timers cost no CPU.
  5. At expiry it calls your callback in its own task context, then (for auto-reload) re-inserts the timer with the next expiry.

3. Worked example

Timer task priority 2. LED timer period 500 ms. A priority-3 task runs a 30 ms computation at t = 999 ms.
Expected callback: t = 1000 ms.
Actual: the timer task is Ready at 1000 but priority 3 is running → callback at t = 1029 ms (29 ms late)

Two callbacks due at the same tick, the first takes 5 ms (it formats a log line):
  second callback runs 5 ms late, because callbacks run one after another in ONE task.

20. Deadlock (Coffman conditions), livelock and starvation

▶

1. What is it?

Deadlock: two or more tasks wait for each other forever, so none of them can continue. Livelock: tasks keep running and retrying but never make progress. Starvation: a task is Ready but never gets the CPU because more important tasks always have work. All three make a feature "just stop", and the debugging technique is to look at what each task is waiting for.

2. How does it work, step by step? (the classic deadlock)

  1. Task A (priority 2) takes spiLock.
  2. A tick or an ISR makes Task B (priority 3) Ready; B preempts A.
  3. B takes flashLock (free) and then tries to take spiLock: held by A, so B blocks.
  4. A resumes and tries to take flashLock: held by B, so A blocks.
  5. A waits for B, B waits for A. With portMAX_DELAY neither ever wakes. The CPU runs only the idle task. This is the "wait-for cycle": A → B → A.

All four Coffman conditions are true here: mutual exclusion (a lock has one holder), hold-and-wait (each holds one while waiting for another), no preemption (the kernel cannot take a lock away), circular wait (the cycle). Remove any one and deadlock is impossible.

3. Worked example: how rare is it?

A's window between its two takes: 50 µs, executed 100 times per second → 5 ms per second "at risk"
B must start its double-take inside that window. B runs 10 times per second at random phase.
probability per B run ≈ 5 ms / 1000 ms = 0.5 %   → expected time to deadlock ≈ 1 / (10 × 0.005) = 20 s
If A's window is 2 µs: 0.02 % → ≈ 8 minutes.  If B runs once per minute: ≈ 3.5 days.

That is why deadlocks typically appear "after 2–30 hours of soak testing" and never on the bench.

  • …both tasks back off and retry immediately, in lock-step? They may collide forever: livelock. Symptom: CPU load is high, nothing gets done. Fix: random back-off or a fixed order.
  • …a high-priority task polls a flag? Lower tasks, including idle, starve. Symptom: low-priority features never run, the MCU never sleeps, deleted tasks never free memory.
  • …you use portMAX_DELAY everywhere? A deadlock shows up only as a watchdog reset with no clue. Symptom: "random resets after hours".
Say it like this: "Deadlock needs all four Coffman conditions: mutual exclusion, hold-and-wait, no preemption and circular wait. I break circular wait with a documented global lock order, and hold-and-wait with bounded timeouts that release and report. Better still is designing locks away with a gatekeeper task that owns the resource. Livelock is tasks running without progress, and starvation in an RTOS is caused by a high-priority task that never blocks, because fixed-priority schedulers deliberately have no aging."

DEADLOCK REQUIRES ALL FOUR COFFMAN CONDITIONS (1971)

  1. Mutual exclusion: the resource can be held by only one task.
  2. Hold and wait: a task holds one resource while waiting for another.
  3. No preemption: a resource cannot be taken away from its holder.
  4. Circular wait: T1 waits for T2's resource, T2 waits for T1's.

Break any one and deadlock is impossible. In practice you break circular wait with a global lock order, or hold-and-wait by taking all locks at once or using a timeout and backing off.

  • Detection: watchdog with per-task check-ins (card 25); all tasks Blocked except idle while work is pending; trace tools (Tracealyzer, SystemView) show both tasks waiting on each other's mutex.

LIVELOCK

Tasks are not blocked; they keep running but make no progress. Classic: two tasks that both take lock 1, fail to get lock 2, release, retry, in lock-step forever. Fix: randomised back-off, or a fixed order.

STARVATION

A ready task never gets the CPU because higher-priority tasks always have work. In a fixed-priority RTOS this is by design: priority is absolute. The causes are always busy-waiting or polling in a high-priority task, or total utilisation above 100 %. Fixes: block instead of poll; lower the polling task's priority; rate-limit; general-purpose OSes use aging (Linux CFS/EEVDF fair share), but RTOSes deliberately do not. Starving the idle task also stops freeing deleted tasks, idle-hook watchdog kicks and tickless sleep.

21. Real-time theory: hard/soft/firm, WCET, jitter

▶

1. What is it?

Real-time theory gives precise words for "how bad is it to be late?" and "how long can this take?". A hard deadline must never be missed (a miss is a failure). A firm deadline makes a late result useless, but an occasional miss is survivable. A soft deadline only makes things worse the later you are. WCET (Worst-Case Execution Time) is the longest a piece of code can take running alone. Jitter is how much the timing varies from one cycle to the next.

2. How does it work, step by step? (describing a task)

  1. Give every periodic task three numbers: C = WCET, T = period (or minimum time between arrivals for an event-driven, "sporadic" task), D = relative deadline (how long after release it must finish). This is the Liu & Layland task model.
  2. Compute its utilisation U = C ÷ T.
  3. Find C: measure the maximum over many runs with worst-case inputs, or use a static analysis tool, then add a margin.
  4. Note the jitter sources: release jitter J (the task is released late, for example because it waits for the next tick) and start/finish jitter (interference from higher-priority tasks).
  5. Feed C, T, D, J and blocking B into the schedulability tests of card 22.

3. Worked example: measuring WCET with the cycle counter

DWT->CYCCNT counts CPU cycles at 168 MHz (one count = 5.95 ns).
1 000 000 runs of control_step():  min 28 412 cycles, mean 29 050, max 33 960 cycles
max = 33 960 / 168 000 000 = 202 µs
margin 20 % (measurement cannot prove the worst path was hit) → C = 243 µs ≈ 0.25 ms
period T = 1 ms → U = 0.25

Where the spread comes from: flash wait states (5 WS at 168 MHz) partly hidden by the ART accelerator
(a cache: hit = fast, miss = up to 5 extra cycles per fetch), branches, and DMA using the bus.

I measure WCET with the DWT cycle counter over worst-case inputs and add margin, or use static analysis for the highest safety levels, and I remove jitter from control loops by having hardware trigger sampling and actuation."

  • Measurement-based: run worst-case inputs, record max with DWT->CYCCNT or a GPIO + scope, add a margin. Cheap but cannot prove you hit the worst path.
  • Static analysis (AbsInt aiT, Rapita RVS hybrid): models the pipeline, caches and flash wait states to compute a safe upper bound. Required for the highest safety levels (DO-178C DAL A, ISO 26262 ASIL D).
  • What makes WCET hard: caches (STM32F4 ART accelerator, F7 L1 cache), branch prediction, flash wait states (5 WS at 168 MHz), DMA bus contention, interrupts (accounted separately as higher-priority "tasks").

  • Release jitter Ji: variation between when the event happens and when the task becomes ready (e.g. a tick-driven task has up to one tick of release jitter).
  • Start/response jitter: variation of start or finish time between jobs, caused by interference from higher-priority tasks. A control loop's phase margin suffers from it; that is why the ADC trigger and the PWM update should be done by hardware and only the computation by the task.

22. Rate Monotonic, Liu & Layland bound, EDF, response-time analysis

▶

1. What is it?

Schedulability analysis answers, with arithmetic and before running anything: will every task always meet its deadline? Rate Monotonic Scheduling (RMS) is a rule for choosing fixed priorities: shorter period → higher priority. The Liu & Layland bound is a quick utilisation test for RMS. Response-Time Analysis (RTA) is the exact test: it computes each task's worst-case response time R and compares it with D. EDF (Earliest Deadline First) is a different scheduler that always runs the job whose deadline is nearest.

2. How does it work, step by step?

  1. Assign priorities by period (RMS) or by deadline when D < T (Deadline Monotonic).
  2. Quick test: compute U = Σ Ci/Ti and compare with n(21/n − 1). If U is below, done: schedulable. If above, the test says nothing (it is only sufficient), so continue.
  3. Exact test (RTA) for each task i, highest priority first: start with R = Ci + Bi. Repeatedly compute Rnew = Ci + Bi + Σ over higher-priority j of ⌈(R + Jj)/Tj⌉ × Cj. The ceiling term counts how many times task j can be released inside a window of length R, each costing Cj.
  4. Stop when Rnew = R (the window is big enough to contain all the interference it causes): that is the worst-case response time. Compare with D. Or stop early if R exceeds D.
  5. The worst case for task i is the critical instant: all higher-priority tasks released at the same moment as i. RTA assumes exactly that.

  • Tighter sufficient test, the hyperbolic bound (Bini 2001): Π (Ui + 1) ≤ 2.

RESPONSE-TIME ANALYSIS (Joseph & Pandya 1986, Audsley et al.)

Exact test for fixed priorities. The worst case for task i occurs at the critical instant, when all higher-priority tasks are released together with it:

Ri = Ci + Bi + Σj ∈ hp(i) ⌈ (Ri + Jj) / Tj ⌉ · Cj

Iterate: R⁽⁰⁾ = Ci + Bi;  R⁽ⁿ⁺¹⁾ = Ci + Bi + Σ ⌈(R⁽ⁿ⁾+Jj)/Tj⌉·Cj
Stop when R⁽ⁿ⁺¹⁾ = R⁽ⁿ⁾ (schedulable if R + Ji ≤ Di) or R⁽ⁿ⁺¹⁾ > Di (not schedulable).

Worked example: τ1 (C=1, T=4), τ2 (C=2, T=6), τ3 (C=3, T=12). U = 0.25 + 0.333 + 0.25 = 0.833 > 0.780, so the L&L test fails. RTA for τ3:

R⁰ = 3
R¹ = 3 + ⌈3/4⌉·1 + ⌈3/6⌉·2 = 3 + 1 + 2 = 6
R² = 3 + ⌈6/4⌉·1 + ⌈6/6⌉·2 = 3 + 2 + 2 = 7
R³ = 3 + ⌈7/4⌉·1 + ⌈7/6⌉·2 = 3 + 2 + 4 = 9

Bi is the blocking from lower-priority tasks (critical sections, non-preemptible regions). Jj is the release jitter of higher-priority tasks. Real analyses also add kernel overhead: the tick ISR as the highest-priority task, and 2 context switches per job added to each C.

EARLIEST DEADLINE FIRST (EDF)

  • Dynamic priority: at every scheduling point run the job with the earliest absolute deadline.
  • Optimal on a single core: with D = T, schedulable iff U ≤ 1. With D < T, use processor-demand analysis.
  • Why not everywhere? (1) Overload behaviour: when U > 1, EDF can make every task miss in a cascade (domino effect), while fixed priority sacrifices only the lowest priorities, which is predictable. (2) It needs deadlines per job and a sorted queue, more overhead. (3) Certification and tooling are built around fixed priority. Linux has it as SCHED_DEADLINE with CBS bandwidth reservation.

Try it: Scheduler Sim → preset "RMS fails, EDF passes", and the RMS/RTA Calc tab.

23. RTOS landscape: FreeRTOS, Zephyr, ThreadX, QNX, VxWorks, Linux PREEMPT_RT

▶

1. What is it?

There is no single "RTOS". The landscape ranges from tiny kernels that are linked into your firmware as a library (FreeRTOS, ThreadX), through full platforms with drivers and networking (Zephyr), to process-based operating systems with memory protection (QNX, VxWorks) and Linux made preemptible (PREEMPT_RT). Interviewers want to see that you know the main differences (priority numbering, latency class, licence, certification) and can justify a choice.

2. How does it work, step by step? (choosing)

  1. What CPU? Cortex-M or R with no MMU (Memory Management Unit) → an MCU RTOS. Cortex-A with an MMU and lots of RAM → Linux or QNX are possible.
  2. What latency? Single-digit microseconds or a 10–20 kHz loop → MCU RTOS or bare-metal ISR. Tens of microseconds acceptable → PREEMPT_RT can do it.
  3. What certification? ISO 26262 ASIL D or IEC 61508 SIL 3/4 → a pre-certified kernel (SafeRTOS, ThreadX, QNX, an AUTOSAR OS) saves months of work.
  4. What ecosystem? BLE, Wi-Fi, USB, filesystems, many sensors → Zephyr's drivers and devicetree. A small team and one MCU family → FreeRTOS.
  5. Licence: MIT (FreeRTOS, ThreadX), Apache 2.0 (Zephyr), commercial (QNX, VxWorks), GPL (Linux).

24. SMP RTOS issues: spinlocks, affinity, migration, cross-core inversion

▶

1. What is it?

SMP (Symmetric Multi-Processing) means several CPU cores run one RTOS image and share the same ready lists, so any task can run on any core (ESP32, RP2040, FreeRTOS SMP since V11). Almost every single-core assumption breaks: disabling interrupts no longer excludes the other core, two tasks of different priorities run at the same time, and memory writes from one core may appear in a different order on the other. AMP (Asymmetric) instead runs a separate OS on each core and avoids most of this.

2. How does it work, step by step? (a kernel critical section on SMP)

  1. Core 0 wants to change the ready list. It disables interrupts on core 0 only (BASEPRI or PRIMASK).
  2. That does nothing to core 1, which could be modifying the same list. So core 0 also takes a spinlock: a shared word it sets atomically from 0 to 1, retrying while it is 1.
  3. Core 0 modifies the list.
  4. Core 0 releases the spinlock (with a memory barrier first, so its writes are visible before the lock appears free), then re-enables its interrupts.
  5. If core 1 was spinning, it now succeeds. It must have its own interrupts disabled while holding the lock, otherwise an ISR on core 1 that wants the same lock would spin forever against its own core.

3. Worked example: the broken assumption

Single core, priorities: H = 5 updates (a, b) together; L = 1 reads (a, b).
  On one core L can never run while H is running, so some code skipped the lock:
  "H is higher priority, L can't interrupt it."

Dual core: H runs on core 0, L runs on core 1 AT THE SAME TIME.
  core 0: a = 10; ............. b = 20;
  core 1:         read a (10) ...       read b (old value 0)  → inconsistent pair (10, 0)
Fix: a real lock (spinlock or mutex) or a sequence counter, plus barriers.

4. Code, line by line

/* ESP-IDF (FreeRTOS SMP fork) */
static portMUX_TYPE mux = portMUX_INITIALIZER_UNLOCKED;
portENTER_CRITICAL(&mux);          // disable local interrupts + take the spinlock
shared.a = 10; shared.b = 20;
portEXIT_CRITICAL(&mux);           // release the spinlock + restore interrupts

xTaskCreatePinnedToCore(ctrl, "ctrl", 4096, NULL, 10, NULL, 1);   // always on core 1
CODEMEANING
portMUX_TYPEThe spinlock word (plus debug owner info in ESP-IDF).
portENTER_CRITICAL(&mux)On SMP the critical-section macro needs a lock argument; there is no global "disable everything".
xTaskCreatePinnedToCore(..., 1)Affinity: the task never migrates, so its timing can be analysed per core and its cache stays warm. Stack size here is in bytes (ESP-IDF convention).

5. What goes wrong if…

  • …a spinlock holder is preempted? The other core spins uselessly for the whole time. Symptom: one core at 100 % doing nothing. Rule: hold spinlocks only with local interrupts and preemption disabled, for a few microseconds.
  • …you share a buffer between an M7 with D-cache and an M4 (STM32H7)? The M4 reads stale RAM while the data is still in the M7's cache. Symptom: the other core sees old values. Fix: clean/invalidate the cache lines, or make the region non-cacheable with the MPU.
  • …tasks migrate freely? Global scheduling anomalies (Dhall's effect) mean a set with low total utilisation can still miss deadlines. Partition critical tasks to cores.
Say it like this: "On SMP, masking interrupts only protects the local core, so kernel and shared data need spinlocks with local interrupts disabled. The N highest-priority tasks run in parallel, so code that relied on 'a low task can't run while a high task runs' becomes a race. I pin critical tasks to cores so the analysis is per core, use acquire/release barriers for shared data, and handle cache coherence explicitly on parts like the STM32H7; or I use AMP with mailboxes to avoid most of the problem."

7. The compact reference version (for revision)

With several cores (ESP32 dual Xtensa/RISC-V, RP2040 dual M0+, STM32H7 dual M7+M4 in AMP, Cortex-R52 clusters), the uniprocessor assumptions break:

  • Disabling interrupts is no longer a lock. It stops your core only. Kernel critical sections need a spinlock plus local interrupt masking. ESP-IDF: portENTER_CRITICAL(&mux) takes a portMUX_TYPE spinlock. FreeRTOS SMP (configNUMBER_OF_CORES > 1, mainline since V11) uses a task lock and an ISR lock.
  • Scheduler suspension only stops scheduling on one core in some ports; code that relied on "nobody else runs while I suspend the scheduler" breaks.
  • "Highest priority task runs" becomes "the N highest run", so a low-priority task can run at the same time as a high one. Code that assumed a high-priority task cannot be interrupted by a low one, used as implicit mutual exclusion, becomes a race.
  • Affinity: pinning tasks to cores (xTaskCreatePinnedToCore, vTaskCoreAffinitySet, Zephyr k_thread_cpu_mask_*) makes analysis per-core (partitioned scheduling) and keeps caches warm. Global scheduling (tasks migrate) gives better average utilisation but analysis is harder: Dhall's effect shows global RMS/EDF can fail at a total utilisation just above 1 on m cores.
  • Priority inversion across cores: H on core 0 spins or blocks on a lock held by L on core 1; inheritance must boost L on its core. Spin-waiting on a lock held by a preempted task wastes a whole core: hold spinlocks only with interrupts and preemption disabled.
  • Memory ordering and caches: the other core may see writes in a different order. Use atomics with acquire/release semantics and DMB barriers; with non-coherent caches (STM32H7 M7 D-cache) shared buffers need cache clean/invalidate or a non-cacheable MPU region.
  • AMP (separate OS image per core, e.g. Linux on A-cores + FreeRTOS on an M4 via OpenAMP/RPMsg, or two independent FreeRTOS images) avoids most of this by sharing only mailboxes (hardware semaphores HSEM, IPCC).

25. Watchdogs with tasks: the check-in pattern

▶

1. What is it?

A hardware watchdog is a counter that resets the MCU unless software "kicks" (refreshes) it in time. With an RTOS, the question is who kicks it. If an interrupt or the tick kicks it, the watchdog only proves that interrupts still run; every task could be deadlocked and the watchdog would be happy. The check-in pattern makes each important task report "I'm alive" once per cycle, and a watchdog manager kicks the hardware only when every task has reported.

2. How does it work, step by step?

  1. At boot, start the IWDG (Independent Watchdog, clocked from the ~32 kHz LSI oscillator, cannot be stopped by software once started) with a timeout of, say, 1 second.
  2. Each monitored task sets its own bit in an event group at the end of every loop iteration.
  3. The watchdog task waits up to 500 ms for all bits (wait-for-all, clear-on-exit).
  4. If all bits arrived: write 0xAAAA to IWDG->KR (refresh). If not: do not refresh; write the missing bits to .noinit RAM for diagnosis. Within the remaining ~500 ms the IWDG resets the MCU.
  5. After reset, read RCC->CSR: the IWDGRSTF bit says the last reset was the watchdog. Report it with the saved bits, then clear the flags (RMVF).

3. Worked example: the IWDG timeout

LSI ≈ 32 kHz (STM32F4: 17–47 kHz over temperature and parts!)
prescaler /32 → counter clock = 32 000 / 32 = 1000 Hz → 1 count = 1 ms
reload RLR = 999 → timeout ≈ 1000 counts = 1.0 s nominal
worst case with LSI = 47 kHz: 1000 × 32 / 47 000 = 0.68 s
→ the manager must refresh well inside 0.68 s, so its 500 ms wait is safe;
  a 900 ms period would fail on a fast-LSI part

4. Code, line by line

IWDG->KR  = 0x5555;   IWDG->PR = 3;   IWDG->RLR = 999;   // unlock, /32, reload
IWDG->KR  = 0xCCCC;                                      // start: cannot be stopped now

void vWatchdogTask(void *pv) {
    for (;;) {
        EventBits_t b = xEventGroupWaitBits(wdEv, WD_ALL,
                         pdTRUE,                  // clear the bits on exit
                         pdTRUE,                  // wait for ALL bits
                         pdMS_TO_TICKS(500));     // at most 500 ms
        if ((b & WD_ALL) == WD_ALL) IWDG->KR = 0xAAAA;   // everyone alive: refresh
        else noinit.wd_missing = WD_ALL & ~b;              // remember who was missing
    }
}
CODEMEANING
KR = 0x5555Unlock write access to PR and RLR.
PR = 3Prescaler code 3 = divide by 32 (codes 0..6 → /4 … /256).
KR = 0xCCCCStart the watchdog. From now on only a reset stops it.
xEventGroupWaitBits(..., pdTRUE, pdTRUE, 500 ms)Return when all bits are set or after 500 ms, and clear them so the next round starts fresh.
KR = 0xAAAARefresh: reload the counter from RLR.
WD_ALL & ~bThe bits that did not arrive: the stuck tasks.

5. What goes wrong if…

  • …you kick the watchdog in the SysTick hook? A deadlock leaves the tick running. Symptom: the product hangs forever instead of recovering.
  • …a task legitimately blocks for 10 s waiting for a command? It cannot check in, so the system resets. Fix: check in from the timeout path (block with a 200 ms timeout and loop) or exclude it while idle.
  • …you debug with a breakpoint? The IWDG keeps counting while the core is halted and resets the board. Set DBGMCU->APB1FZ |= DBGMCU_APB1_FZ_DBG_IWDG_STOP in debug builds.
Say it like this: "I never kick the watchdog from an ISR or the tick, because interrupts keep running when tasks are deadlocked. Each monitored task sets a check-in bit once per cycle, and a watchdog manager refreshes the IWDG only when all bits arrived inside the window, recording the missing ones in no-init RAM before the reset. I size the window against the LSI tolerance, freeze the watchdog in the debugger, and read the reset cause at boot."

7. The compact reference version (for revision)

A hardware watchdog (STM32 IWDG: clocked from the ~32 kHz LSI, independent of the main clock, cannot be stopped once started; WWDG: windowed, clocked from APB1, must be refreshed inside a window, catching code that runs too fast as well) resets the MCU if not refreshed in time.

Kicking the watchdog from the SysTick hook, an ISR or a high-priority timer. Interrupts keep running when every task is deadlocked, so the watchdog never fires. It only proves that the tick still runs.
/* Each monitored task sets its bit once per loop iteration */
#define WD_SENSOR  (1u << 0)
#define WD_CONTROL (1u << 1)
#define WD_COMMS   (1u << 2)
#define WD_ALL     (WD_SENSOR | WD_CONTROL | WD_COMMS)
EventGroupHandle_t wdEv;

void vControlTask(void *pv) {
    for (;;) { run_control(); xEventGroupSetBits(wdEv, WD_CONTROL); xTaskDelayUntil(&last, 10); }
}

/* Watchdog manager: low-to-medium priority, period well inside the IWDG timeout */
void vWatchdogTask(void *pv) {
    for (;;) {
        EventBits_t b = xEventGroupWaitBits(wdEv, WD_ALL, pdTRUE, pdTRUE, pdMS_TO_TICKS(500));
        if ((b & WD_ALL) == WD_ALL) IWDG->KR = 0xAAAA;   // refresh only if EVERYONE checked in
        else log_missing(b ^ WD_ALL);                     // to .noinit before the reset hits
    }
}
  • Per-task deadlines: a counter per task plus an expected rate catches a task that runs but too slowly. Tasks that legitimately block for long (waiting for a command) should check in from their timeout path or be excluded while idle.
  • Place the watchdog manager at a low priority if you also want to catch CPU starvation (it will not run if a high task spins), or high if you only want deadlock detection. Many systems do both: a low-priority idle-check plus task check-ins.
  • Freeze the watchdog while halted in the debugger (DBGMCU->APB1FZ |= DBG_IWDG_STOP) or every breakpoint resets the board.
  • After a watchdog reset, read RCC->CSR (IWDGRSTF/WWDGRSTF), report it and clear it with RMVF. Store the missing task bits in .noinit RAM before the reset for post-mortem.
  • Pathfinder's bc_sched check was exactly this kind of software watchdog.

  • RTOS = bounded response time for important work, independent of unimportant work. Real-time means predictable, not fast.
  • The highest-priority Ready task always runs. Blocked tasks use zero CPU.
  • TCB's first field is the saved SP. Registers live on the task's stack.
  • Cortex-M switch: SysTick/ISR pends PendSV (lowest prio) → saves R4–R11 (+S16–S31) onto PSP → vTaskSwitchContext → restore → bx lr with 0xFFFFFFFD.
  • Hardware frame = R0–R3, R12, LR, PC, xPSR (32 B); 104 B with FP. Lazy stacking defers S0–S15.
  • First task starts through SVC and a fabricated frame; MSP is reset.
  • O(1) selection: one ready list per priority + bitmap + CLZ.
  • Semaphore = signalling, no owner. Mutex = ownership + priority inheritance, never in an ISR.
  • Unbounded priority inversion needs a medium task. PI bounds it; ceiling bounds it to one critical section and prevents deadlock.
  • Mars Pathfinder 1997: VxWorks mutex without PI → bc_dist starved → bc_sched reset. Fixed by a patch enabling PI.
  • Deadlock needs all 4 Coffman conditions. Global lock order + timeouts.
  • ISRs: FromISR APIs only, NVIC prio numerically ≥ MAX_SYSCALL, yield at the end, defer the work to a task.
  • Critical section masks ISRs (BASEPRI); scheduler suspension does not.
  • heap_1 no free · heap_2 no coalesce · heap_3 libc · heap_4 coalesce · heap_5 regions. Static is best for safety.
  • Stack check 1 = SP at switch, 2 = + 0xA5 canary; MPU/PSPLIM catch it in hardware.
  • vTaskDelay drifts; xTaskDelayUntil doesn't.
  • RMS bound n(21/n−1) → 0.693; sufficient only. RTA is exact. EDF: U ≤ 1.
  • Watchdog: refresh only after every task checks in, never from an ISR.

NEVER DO THIS
  • Call a non-FromISR API (or anything that can block) from an ISR.
  • Call any FreeRTOS API from an ISR whose NVIC priority is numerically below configMAX_SYSCALL_INTERRUPT_PRIORITY (default priority 0 is such an ISR).
  • Take or give a mutex from an ISR; give a mutex from a task that does not own it.
  • Busy-wait/poll in a high-priority task: it starves everything below it, including idle.
  • Block inside a software-timer callback, idle hook, or critical section; call a blocking API with the scheduler suspended.
  • Kick the watchdog from an ISR or the tick hook.
  • Use a binary semaphore when events can arrive faster than they are processed.
  • Take two locks in different orders in different tasks.
  • Use vTaskDelay for a periodic control loop.
  • Size stacks in bytes in FreeRTOS (they are words), or call printf from a 128-word task.
  • Pass a pointer to a stack variable of main() or of a task that may exit into a queue or a new task.
  • Disable interrupts for long operations instead of using a mutex.
  • Rely on "a high-priority task can't be interrupted by a low one" on an SMP system.
  • Leave configASSERT undefined and stack checking off during development.
