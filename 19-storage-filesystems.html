01

The memory family: SRAM, DRAM, NOR, NAND, EEPROM, FRAM, MRAM, eMMC, SD

BEGINNER▶

1. WHAT IS THIS ABOUT?

A microcontroller needs two kinds of memory: memory that is fast and easy to change while the program runs, and memory that remembers data when the power is switched off. No single technology is best at both, so a real product mixes several. This card is the map; later cards zoom into each one.

Volatile
Loses its contents when power is removed. Example: SRAM, DRAM.
Non-volatile (NV)
Keeps its contents with no power, for years. Example: flash, EEPROM, FRAM, MRAM.
SRAM
Static RAM. Each bit is a tiny latch made of 6 transistors ("6T cell"). Holds its value as long as power is on, no refresh needed. Very fast (single CPU cycle on-chip), but large per bit, so expensive. Your MCU's 128 KB of RAM is SRAM.
DRAM
Dynamic RAM. Each bit is 1 transistor + 1 capacitor ("1T1C"). The capacitor leaks, so every row must be refreshed (read and re-written) about every 64 ms. Very dense and cheap per bit, used as external RAM in Linux-class SoCs (DDR3/DDR4/LPDDR4).
Flash
Non-volatile memory that stores bits as electric charge trapped in a transistor. Can be read fast, but changing it is slow and has rules (erase in big blocks first). Two layouts: NOR and NAND.
NOR flash
Flash whose cells are wired in parallel, so any single byte can be read directly at random, fast. The CPU can execute code straight out of it (XIP = eXecute In Place). Your STM32's internal flash and an external SPI flash like W25Q128 are NOR.
NAND flash
Flash whose cells are wired in series strings. Much denser and cheaper per bit than NOR, but read only in whole pages (e.g. 2 KB), has bad blocks from the factory, and needs ECC (error correction). Used in SD cards, eMMC, SSDs, USB sticks.
SLC / MLC / TLC / QLC
How many bits each NAND cell stores: Single (1 bit, 2 charge levels), Multi (2 bits, 4 levels), Triple (3 bits, 8 levels), Quad (4 bits, 16 levels). More levels = cheaper per bit, but levels are closer together, so the cell wears out faster and needs stronger ECC.
EEPROM
Electrically Erasable Programmable ROM. Non-volatile like flash, but each byte can be rewritten individually (the chip erases and programs that byte internally). Small (bytes to a few hundred KB), slow writes (~5 ms per page), high endurance (~1 million writes). Example: Microchip 24LC256 (I²C, 32 KB).
FRAM
Ferroelectric RAM. Stores a bit as the polarisation of a ferroelectric crystal. Writes at full bus speed with no erase and no wait, endurance about 1014 writes. Expensive per bit, small sizes. Example: Infineon (Cypress) FM25V10, 128 KB SPI.
MRAM
Magnetoresistive RAM. Stores a bit as a magnetic orientation. Like FRAM: byte-writable, fast, practically unlimited endurance. Example: Everspin MR25H40 (512 KB SPI).
eMMC
embedded MultiMediaCard: a NAND flash chip plus its own controller in one BGA package, soldered to the board. The controller hides bad blocks, ECC and wear levelling, so the host just sees an array of 512-byte sectors.
SD card
Secure Digital card: same idea as eMMC (NAND + controller) but removable. Talks SD protocol (4-bit bus) or a simpler SPI mode.

2. HOW TO CHOOSE — THE QUESTIONS YOU ASK, IN ORDER

  1. Must it survive power-off? No → SRAM (on-chip) or DRAM (external, Linux-class). Yes → continue.
  2. How big? Bytes to KB → EEPROM / FRAM / MRAM / spare internal flash. MB → SPI NOR. GB → NAND, eMMC, SD.
  3. How often is it rewritten? Counters updated every second need 108+ writes over life → FRAM/MRAM, or flash with careful wear levelling (card 13). Firmware updated a few times a year → any flash.
  4. Must code execute directly from it? Yes → NOR (internal, or Quad-SPI NOR in memory-mapped mode). NAND cannot do XIP because it is read in pages through a command interface and has bit errors that need ECC first.
  5. Who handles bad blocks and wear? Raw NAND → you (or Linux UBI). eMMC/SD → the card's controller.

• Internal STM32F4 flash, rewriting one sector each time: endurance 10,000 erases → dies after 10,000 / 2,000 = 5 days.
• EEPROM 24LC256, rewriting the same 4 bytes: 1,000,000 cycles → dies after 1,000,000 / 2,000 = 500 days ≈ 1.4 years.
• FRAM: 1014 cycles → effectively infinite.

You pick EEPROM because "EEPROM is for config" and then write a counter to the same address every second. 1,000,000 cycles ÷ 86,400 writes/day = 11.6 days. The symptom in the field is a counter that suddenly reads back wrong or the I²C write never finishes (the device keeps NACKing because its internal write never verifies).
Volatile SRAM holds working data; non-volatile memory holds code and settings. NOR flash is randomly readable so code can run from it, NAND is denser and cheaper but page-based, has bad blocks and needs ECC, which is why eMMC and SD cards wrap it with a controller. For small, very frequently updated data I'd pick FRAM or MRAM, or flash with a log-structured, wear-levelled scheme — and I'd always do the endurance arithmetic first.

1. WHAT DO THE COLUMNS MEAN?

Read granularity
The smallest piece you can read. NOR: one byte. NAND: one page (2–16 KB), you then pick bytes out of the page buffer.
Write (program) granularity
The smallest piece you can write. On flash "program" means changing selected bits from 1 to 0. STM32F4: 1 byte. STM32L4: 8 bytes (a "double-word"). STM32H7: 32 bytes (a "flash word"). SPI NOR: 1 byte up to a 256-byte page per command. NAND: one page.
Erase granularity
The smallest piece you can return to all-1s. Flash can only erase big blocks: STM32F4 sectors are 16–128 KB, SPI NOR 4 KB, NAND blocks 128 KB–several MB.
Endurance
How many program/erase cycles ("P/E cycles") each block survives before bits stop working reliably.
Retention
How long data stays readable without power. It shrinks with temperature and with how worn the cell is.

2. HOW TO READ THE TABLE — STEP BY STEP

  1. Look at the erase unit vs the size of the data you change. If you change 4 bytes but must erase 128 KB, every naive update costs a 1-second erase and rewrites 128 KB: that ratio is called write amplification (card 10).
  2. Look at endurance × number of erase units you rotate over: that is your total erase budget.
  3. Look at write time: it is how long a power cut can hit you in the middle (card 12), and how long the CPU may stall if it executes from the same flash (card 5).
  4. Look at retention at your maximum temperature, not at 25 °C (card 20).

Read 131,072 bytes into RAM (needs 128 KB of RAM — the whole SRAM of an F407!) → erase sector: typ 1 s, max 2 s at x32 → program 131,072 / 4 = 32,768 words × 16 µs = 0.52 s. Total ≈ 1.5 s for 4 bytes, write amplification = 131,072 / 4 = 32,768×. That is why we never do read-modify-erase-write on big sectors.
The key numbers are the three granularities and endurance. Flash reads in bytes (NOR) or pages (NAND), programs bits from 1 to 0 in bytes, double-words or pages, and can only erase whole sectors or blocks. Internal MCU flash is ~10k cycles, SPI NOR ~100k, SLC NAND ~100k, TLC a few thousand, EEPROM a million, FRAM and MRAM effectively unlimited. I design by comparing the size I update against the erase unit, and endurance times rotated sectors against the lifetime write count.
03

How a flash cell stores a bit — and why erase = 1, program = 0

BEGINNER▶

1. WHAT IS A FLASH CELL?

A flash cell is a normal MOS transistor with an extra, completely insulated piece of conductor buried inside it, called the floating gate. Electrons pushed onto the floating gate stay there for years because they are surrounded by insulating oxide. Those trapped electrons change how easily the transistor switches on, and that is how one bit is remembered.

Floating gate
An isolated polysilicon layer between the control gate and the channel. Charge on it is the stored data. (Modern NAND uses a "charge trap" layer of silicon nitride instead; same idea.)
Threshold voltage (VT)
The gate voltage at which the transistor starts conducting. Electrons on the floating gate raise VT.
Tunnel oxide
The ~10 nm insulating layer electrons must cross to get on or off the floating gate. Every crossing slightly damages it — this is the root of limited endurance.
Fowler–Nordheim tunnelling
Electrons crossing the oxide under a strong electric field (~10–20 V across it). Used for erase (and for programming in NAND).
Hot-carrier injection
Electrons accelerated along the channel gain enough energy to jump onto the floating gate. Used for programming in NOR.
Sense amplifier
The circuit that applies a read voltage to the cell and decides "conducts → 1" or "does not conduct → 0".

2. WHAT HAPPENS, STEP BY STEP

  1. Erase: a large voltage pulls electrons off the floating gates of a whole sector at once (they all share one well, so you cannot erase just one cell). Low VT → the transistor conducts at the read voltage → the sense amp reads 1. That is why erased flash reads 0xFF.
  2. Program: for each bit that must become 0, the chip pushes electrons onto that cell's floating gate. High VT → no conduction at the read voltage → reads 0. Bits that should stay 1 simply get no pulse.
  3. Program-verify: the chip internally re-reads, and gives more pulses until the cell is safely past the threshold. This is why program time varies.
  4. Read: apply a read voltage between the "erased" and "programmed" VT levels; conduction or not gives the bit.
  5. No "un-program": there is no operation to remove electrons from a single cell. The only way back to 1 is a sector erase. So a program operation can only clear bits (1→0), never set them.

3. WHY DOES IT WEAR OUT AND FORGET?

  1. Each P/E cycle drives electrons through the tunnel oxide; some get stuck in the oxide (trapped charge) and the oxide develops leakage paths.
  2. Trapped charge shifts VT: erased cells no longer erase fully (erase gets slower, then fails), programmed cells leak charge away faster.
  3. At the rated endurance (e.g. 10k cycles) the manufacturer still guarantees the rated retention; beyond it, bits start to flip earlier.
  4. Retention loss is a thermally activated leak: hotter = faster (card 20). A worn cell at 105 °C may only hold data for a few years.
You rely on "writing 0xFF erases a byte". It does not: programming 0xFF means "clear no bits", so the byte keeps its old value. Symptom: a "cleared" config flag is still set after reboot, and your code that checked if (flag == 0xFF) takes the wrong branch.
A flash cell is a transistor with a floating gate; trapped electrons raise its threshold voltage. Erase removes the electrons from a whole sector at once, so erased cells read 1 and erased flash reads 0xFF. Programming adds electrons to selected cells to make them 0. There is no single-cell un-program, so a write can only clear bits — the result is old AND new — and only a sector erase sets bits back to 1. Every cycle damages the tunnel oxide, which is why endurance and retention are limited.
04

NOR flash operations: sectors, blocks, pages and the program/erase rules

INTERMEDIATE▶

1. WHAT ARE THE UNITS?

Page
The largest chunk one program command can write. SPI NOR: 256 bytes. (Internal STM32F4 flash has no page concept for programming; you program 8/16/32/64 bits per operation.)
Sector
The smallest erasable unit. W25Q128: 4 KB. STM32F4 calls its 16–128 KB erase units "sectors". STM32L4/G0 call their 2 KB erase units "pages" — vendors are not consistent, so always say the size.
Block
A larger erasable unit offered for speed: W25Q128 has 32 KB and 64 KB blocks. Erasing one 64 KB block (150 ms typ) is faster than 16 × 4 KB sectors (16 × 45 ms = 720 ms).
Chip erase
Erase the whole device (W25Q128: 40 s typ, up to 200 s).

2. THE THREE RULES, STEP BY STEP

  1. Erase sets every bit in the sector to 1 (bytes read 0xFF). It takes milliseconds to seconds, and counts as one P/E cycle against that sector's endurance.
  2. Program can only change 1 → 0. Physically the result is old & new. To be correct you must program only into erased locations (or deliberately clear extra bits, which is a useful trick for status flags).
  3. To change any 0 back to 1 you must erase the whole sector, which destroys every other byte in it. So you either keep a RAM copy and rewrite it, or (much better) never update in place and append new versions elsewhere (cards 11–13).

3. CHECKING WHETHER A WRITE IS POSSIBLE WITHOUT ERASE

A new value can be programmed over an old one only if it does not need any 0 → 1 change, i.e. every 1 in new is also 1 in old: (old & new) == new.

WRONG — assumes flash behaves like RAM
void cfg_save(uint32_t addr, uint32_t v) {
    flash_unlock();
    flash_program_word(addr, v);  // old value still there!
    flash_lock();                 // reads back old & v
}
RIGHT — check, erase if needed, verify
bool cfg_save(uint32_t addr, uint32_t v) {
    uint32_t old = *(volatile uint32_t *)addr;
    if ((old & v) != v) {         // needs a 0→1 change
        return false;             // caller must use a fresh slot
    }                             // (or erase, losing neighbours)
    flash_unlock();
    int rc = flash_program_word(addr, v);
    flash_lock();
    return rc == 0 &&             // no PGSERR/PGAERR...
        *(volatile uint32_t *)addr == v; // read-back verify
}

4. THE "CLEAR MORE BITS LATER" TRICK (ONLY ON NON-ECC FLASH)

Because programming can clear additional bits without erase, you can encode a state machine whose every step only clears bits: 0xFFFF (erased) → 0xEEEE (receiving) → 0x0000 (valid). 0xFFFF→0xEEEE clears bits 0,4,8,12; 0xEEEE→0x0000 clears the rest. ST's EEPROM-emulation application note AN3969 for the F4 uses exactly these values. On ECC flash (card 6) re-programming a word is forbidden, so each state needs its own fresh word.

  status word evolution without any erase:
  1111 1111 1111 1111  0xFFFF  ERASED
  1110 1110 1110 1110  0xEEEE  RECEIVE_DATA   (only 1→0 changes)
  0000 0000 0000 0000  0x0000  VALID_PAGE     (only 1→0 changes)
Can 0x0000_00FF be overwritten with 0x0000_000F without erase? old & new = 0x0F = new → yes (only clears bits 4–7).
Can 0x0F be overwritten with 0xF0? 0x0F & 0xF0 = 0x00 ≠ 0xF0 → no; you would read back 0x00.
You write a 32-bit counter in place: 1 → 2 → 3. 1 = ...0001, 2 = ...0010: (1 & 2) = 0, so after "writing 2" the flash holds 0. Then "writing 3" gives 0 & 3 = 0. Your counter is stuck at 0 forever, and no error flag is raised on STM32F4 (it only flags PGSERR/PGPERR for sequence/parallelism errors, not for "can't set bits").
NOR flash reads at byte granularity, programs by clearing bits from 1 to 0, and erases whole sectors back to all ones. So a program operation physically ANDs the new data into the old. A value can be written in place only if (old AND new) == new; otherwise you need an erase, which wipes the whole sector, so robust designs append new versions to erased space instead of updating in place.

1. WHAT IS IT?

The STM32F407 (ST) has up to 1 MB of NOR flash on the die, mapped at 0x0800_0000. The CPU executes code from it directly. Your firmware can also erase and program it at run time through the FLASH interface peripheral — for configuration, logs, or an update. Its sectors are not all the same size, which matters for where you put data.

3. REGISTERS YOU TOUCH

FLASH_ACR 0x4002_3C00
Access control: LATENCY (wait states — 5 WS at 168 MHz/3.3 V), PRFTEN (prefetch), ICEN/DCEN (caches), ICRST/DCRST (cache reset).
FLASH_KEYR 0x4002_3C04
Unlock register. Write 0x45670123 then 0xCDEF89AB. Any other sequence locks FLASH_CR until the next reset.
FLASH_SR 0x4002_3C0C
Status: EOP (bit 0, end of operation), OPERR (1), WRPERR (4, write-protected), PGAERR (5, alignment), PGPERR (6, parallelism), PGSERR (7, sequence), BSY (16). Error bits are cleared by writing 1.
FLASH_CR 0x4002_3C10
Control: PG (bit 0, program), SER (1, sector erase), MER (2, mass erase), SNB (bits 6:3, sector number), PSIZE (bits 9:8: 00=x8, 01=x16, 10=x32, 11=x64), STRT (16, start erase), EOPIE (24), ERRIE (25), LOCK (31).
PSIZE / parallelism
How many bits are programmed per operation. x32 needs VDD 2.7–3.6 V; x64 needs an external 8–9 V on VPP. Lower VDD forces x8/x16, which makes erase slower.

4. THE PROGRAM SEQUENCE STEP BY STEP

  1. Wait until FLASH_SR.BSY == 0.
  2. If FLASH_CR.LOCK == 1, write the two keys to FLASH_KEYR.
  3. Clear stale error flags in FLASH_SR (write 1s to bits 4–7, 1, 0).
  4. Set PSIZE = 10 (x32) and PG = 1.
  5. Write the data with an ordinary store to the flash address: *(volatile uint32_t*)addr = data;. The store itself starts the program operation.
  6. Wait for BSY = 0, check error flags, clear PG.
  7. Set LOCK again and read back to verify.

5. THE ERASE SEQUENCE STEP BY STEP

  1. Wait BSY = 0, unlock.
  2. Set SER = 1, SNB = sector number, PSIZE.
  3. Set STRT = 1. Erase runs in hardware.
  4. Wait BSY = 0, check errors, clear SER. If the D-cache/I-cache held old contents of that sector, reset the caches (DCRST/ICRST while disabled) before reading it.
/* STM32F4 — register level. Must not execute from the bank being written
   if you care about latency: the CPU stalls on any flash fetch while BSY=1. */
#define FLASH_KEY1 0x45670123u
#define FLASH_KEY2 0xCDEF89ABu

static void flash_unlock(void) {
    if (FLASH->CR & FLASH_CR_LOCK) {
        FLASH->KEYR = FLASH_KEY1;           // order matters
        FLASH->KEYR = FLASH_KEY2;           // wrong key = locked until reset
    }
}
static int flash_wait(void) {
    while (FLASH->SR & FLASH_SR_BSY) { }   // busy-wait (stalls if code is in flash)
    uint32_t err = FLASH->SR & (FLASH_SR_WRPERR | FLASH_SR_PGAERR |
                                FLASH_SR_PGPERR | FLASH_SR_PGSERR | FLASH_SR_OPERR);
    FLASH->SR = err | FLASH_SR_EOP;         // write-1-to-clear
    return err ? -1 : 0;
}
int flash_erase_sector(uint32_t snb) {      // snb 0..11
    flash_unlock();
    flash_wait();
    FLASH->CR = (2u << FLASH_CR_PSIZE_Pos)  // x32 (VDD 2.7–3.6 V)
              | (snb << FLASH_CR_SNB_Pos)   // which sector
              | FLASH_CR_SER;               // sector-erase mode
    FLASH->CR |= FLASH_CR_STRT;             // go: 16 KB ≈ 250 ms typ
    int rc = flash_wait();
    FLASH->CR &= ~(FLASH_CR_SER | FLASH_CR_SNB);
    FLASH->CR |= FLASH_CR_LOCK;
    return rc;
}
int flash_program_word(uint32_t addr, uint32_t data) {
    if (addr & 3u) return -1;               // x32 needs 4-byte alignment
    flash_unlock();
    flash_wait();
    FLASH->CR = (2u << FLASH_CR_PSIZE_Pos) | FLASH_CR_PG;
    *(volatile uint32_t *)addr = data;      // this store starts programming
    int rc = flash_wait();                  // ≈16 µs typ, 100 µs max
    FLASH->CR &= ~FLASH_CR_PG;
    FLASH->CR |= FLASH_CR_LOCK;
    if (rc == 0 && *(volatile uint32_t *)addr != data) rc = -2; // verify (AND effect!)
    return rc;
}

How long does the CPU freeze if a 128 KB sector is erased while code runs from flash? Up to the erase time: ~1 s typical, 2+ s worst case. During that time every instruction fetch from flash stalls the bus. At 1 kHz SysTick you miss ~1,000 ticks; a UART at 115,200 baud receives 11,520 bytes/s into a 1-byte data register, so it overruns (ORE) after about 87 µs. On the STM32F407 the 1 MB flash has four 16 KB sectors, one 64 KB and seven 128 KB sectors. To write, I unlock with the two key words, set PSIZE and PG, do a normal store, wait for BSY to clear, check the error flags and verify. Erase is SER plus sector number plus STRT, and a 128 KB sector takes about a second. It's single-bank, so any instruction fetch from flash stalls during erase — the driver and critical ISRs must run from RAM, and frequently-written data goes in the small 16 KB sectors.
06

ECC flash on newer MCUs: STM32L4 double-word and STM32H7 flash-word programming

ADVANCED▶

1. WHAT IS IT AND WHY DOES IT EXIST?

Smaller flash cells (newer process nodes) occasionally lose a bit. To hide that, newer MCUs store extra ECC bits next to every chunk of data. When you read, the hardware silently fixes a single flipped bit. The price: the chunk is now the smallest thing you can program, and you can program it only once between erases.

ECC
Error-Correcting Code. Extra check bits computed from the data (a Hamming-type code here). Lets hardware correct 1 wrong bit and detect 2 wrong bits per chunk ("SECDED" = Single Error Correct, Double Error Detect).
Double-word
64 bits = 8 bytes. On STM32L4/L4+/G0/G4/WB (ST) each double-word has 8 ECC bits. It is the programming unit.
Flash word (H7)
On STM32H7 (ST) the unit is 256 bits = 32 bytes with 10 ECC bits.
PROGERR
STM32L4 FLASH_SR error flag: you tried to program a double-word that is not erased.
ECCC / ECCD
FLASH_ECCR flags: ECC Corrected (1-bit error fixed, optional interrupt) / ECC Detected (2-bit error, uncorrectable → NMI). The failing address is latched in FLASH_ECCR.ADDR_ECC.

2. WHAT THE HARDWARE DOES, STEP BY STEP

  1. You write the first 32-bit half of a double-word to the flash address (with PG set). The controller only latches it.
  2. You write the second 32-bit half to address+4. Now the controller has 64 bits, computes 8 ECC bits, and programs all 72 bits together.
  3. On every read, the controller recomputes ECC from the 64 data bits and compares with the stored 8. Mismatch in 1 bit → corrects on the fly, sets ECCC. Mismatch in 2 bits → sets ECCD and raises NMI.
  4. If you try to program a double-word that is not all-ones, the controller refuses (PROGERR), because the new ECC bits would need 0→1 changes. (Exception on L4: programming all-zeros 0x0000_0000_0000_0000 is allowed — handy for "invalidate this record".)

  ┌───────────── 64 data bits ─────────────┬ 8 ECC ┐
  │ word @ addr          │ word @ addr+4    │ hidden│
  └──────────────────────┴──────────────────┴───────┘
   one shot only: erased → programmed. No second "clear more bits" pass.

Instead reserve three separate double-words in the page header: one per state, each written once: [RECEIVING dword][VALID dword][OBSOLETE dword]. Page header = 3 × 8 = 24 bytes. A 2 KB page then holds (2048 − 24) / 8 = 253 eight-byte records.

A power cut in the middle of programming a double-word can leave the ECC bits inconsistent with the data. On the next read you get an ECCD → NMI instead of a wrong value. If your NMI handler is the default infinite loop, the device bricks itself on every boot while scanning the config page. Robust code: in the NMI handler check FLASH_ECCR.ECCD, record ADDR_ECC, mark that record bad, clear the flag and return (or erase the page on next compaction).
Newer STM32s such as L4 and H7 store ECC with each 64-bit double-word or 256-bit flash word. That makes the double-word the minimum program size and you can program it only once per erase — the F4 trick of clearing more bits later causes PROGERR, though L4 lets you overwrite with all zeros. Single-bit errors are corrected silently, double-bit errors raise an NMI, which also happens after a torn write, so the NMI handler and the record format have to tolerate that.

SPI NOR flash: commands, status register, WEL/WIP and the page-wrap trap

INTERMEDIATE▶

1. WHAT IS IT?

An SPI NOR flash (e.g. Winbond W25Q128JV, 16 MB) is an external chip you talk to with SPI. Every operation is one transaction: pull CS (chip select) low, send a 1-byte opcode, maybe a 3-byte address and data, then pull CS high. Pulling CS high is what makes the chip start a program or erase.

CS# / nCS
Chip select, active low. A command is framed by CS low…high.
Opcode
First byte after CS goes low; tells the chip what to do.
SR1
Status Register 1, read with opcode 0x05. Bit 0 = WIP/BUSY (Write In Progress: 1 while a program/erase runs). Bit 1 = WEL (Write Enable Latch). Bits 2–4 BP0–2 (block protect), bit 5 TB, bit 6 SEC, bit 7 SRP.
WEL
A safety latch. Program, erase and write-status commands are silently ignored unless WEL = 1. Set by WREN (0x06). Cleared automatically when a program/erase finishes, and by WRDI (0x04) or power-up.
Dummy cycles
Clocks the host sends while the chip fetches data internally before it can output it, needed at high clock rates (Fast Read).

3. PAGE PROGRAM, STEP BY STEP

  1. Make sure the target bytes are erased (0xFF) — page program only clears bits.
  2. CS↓ 06 CS↑ — WREN. WEL becomes 1.
  3. CS↓ 02 A2 A1 A0 D0 … Dn CS↑ — opcode, 24-bit address MSB first, data. The internal program starts on CS rising edge. CS must rise after a whole number of bytes, or the command is ignored.
  4. CS↓ 05 [SR] [SR] … CS↑ — poll until WIP = 0. Expect SR = 0x03 (WIP=1, WEL=1) while busy, then 0x00 (WIP=0, WEL auto-cleared).
  5. Optionally read back and compare.

4. THE PAGE-WRAP RULE

A page is the 256-byte aligned region [addr & ~0xFF, +255]. Inside one 0x02 command, the chip increments only the low 8 address bits. If you send more bytes than remain in the page, the address wraps to the start of the same page and overwrites (ANDs into) what is there. The chip raises no error.

Writing 100 bytes at 0x00_00F0 in one command.
Bytes left in page = 0x100 − 0xF0 = 16. Bytes 0–15 go to 0xF0…0xFF. Bytes 16–99 (84 bytes) wrap to 0x00…0x53 of the same page instead of 0x100…0x153. Correct: split into chunk 1 = 16 bytes at 0xF0, chunk 2 = 84 bytes at 0x100, each with its own WREN and WIP poll.

Quad SPI, XIP memory-mapped mode, 4-byte addressing and deep power-down

ADVANCED▶

1. WHAT ARE THESE?

Dual / Quad SPI
Using 2 or 4 data lines instead of 1 MOSI + 1 MISO. In Quad mode the WP# and HOLD# pins become IO2 and IO3. Notation "1-1-4" = opcode on 1 line, address on 1 line, data on 4 lines; "1-4-4" = address and data on 4 lines.
QE bit
Quad Enable, bit 1 of Status Register 2 on Winbond (read 0x35, write 0x31). Must be 1 before quad commands work, because it turns the WP#/HOLD# pins into data pins. Non-volatile on many parts.
XIP / memory-mapped mode
eXecute In Place. The MCU's QSPI/OCTOSPI peripheral (e.g. STM32H7 QUADSPI at 0x9000_0000) automatically issues Read commands when the CPU accesses that address range, so code and constants can run straight from the external flash.
Continuous read mode
Mode bits (e.g. 0xA0 after the address in 0xEB) tell the flash "next transaction skips the opcode", saving 8 clocks per random access in XIP.
4-byte addressing
3 address bytes reach 224 = 16 MB. Larger chips (W25Q256 = 32 MB) need 4 bytes: either enter 4-byte mode (0xB7, exit 0xE9) or use dedicated 4-byte opcodes (0x13 read, 0x0C fast read, 0x12 program, 0x21 4 KB erase, 0xDC 64 KB erase).
SFDP
Serial Flash Discoverable Parameters (opcode 0x5A, JEDEC JESD216): a table inside the chip describing its sizes, erase types and quad commands, so one driver can support many chips.
Deep power-down
Opcode 0xB9 puts the chip into ~1 µA; it ignores everything except 0xAB (release), and needs tRES1 ≈ 3 µs after release.

2. A QUAD I/O FAST READ (0xEB), STEP BY STEP

  1. CS↓, opcode 0xEB on IO0 only (8 clocks).
  2. 24-bit address on IO0–IO3: 6 clocks (4 bits per clock).
  3. Mode byte (2 clocks) + 4 dummy clocks (default for W25Q128JV) while the flash fetches.
  4. Data on IO0–IO3: 2 clocks per byte. CS↑ ends the burst.

NAND flash: pages, spare (OOB) area, bad blocks, ECC, read/program disturb

INTERMEDIATE▶

1. WHAT IS NAND, AND WHY IS IT DIFFERENT?

NAND puts 32–128 cells in series in a "string", so there are fewer contacts and it packs far more bits into the same silicon. The cost: you cannot read a single byte directly; you load a whole page into the chip's internal buffer and then stream it out. NAND also ships with some broken blocks and has bit errors as a normal part of operation, so software must cope.

Page
The read/program unit. Micron MT29F1G08 (1 Gbit SLC): 2048 data bytes + 64 spare bytes = 2112 bytes.
Spare / OOB area
Out-Of-Band bytes next to each page, not part of the user data. Holds the ECC parity, the bad-block marker, and FTL metadata (logical address, sequence number).
Block
The erase unit: 64 pages × 2 KB = 128 KB on MT29F1G08 (1024 blocks total).
Bad block
A block that cannot be reliably erased/programmed. Factory bad blocks are marked by a non-0xFF byte in the spare area (byte 0 of the first page's spare on this part — check the datasheet). Spec allows up to ~2% (e.g. ≤ 20 of 1024) and guarantees block 0 good. More go bad during life ("grown bad blocks").
ECC (BCH / LDPC)
BCH = Bose–Chaudhuri–Hocquenghem code, corrects t bits per chunk (e.g. 8 bits per 512 B). LDPC = Low-Density Parity Check, stronger, used for MLC/TLC/QLC in SSDs. Old SLC needed 1-bit Hamming per 512 B; modern SLC asks for 4–8 bits per 512 B; MLC 24–40 bits per 1 KB.
Read disturb
Reading a page applies a pass voltage to all other word lines in the block. After many reads (order of 100k for SLC, much fewer for MLC/TLC), unread pages in the same block gain charge and flip bits. Fix: count reads per block and rewrite ("scrub") the block.
Program disturb
Programming one page slightly stresses cells in neighbouring pages/strings. That is why pages inside a block must be programmed in order (0,1,2,…) and each page may be partially programmed only NOP times (e.g. NOP = 4 for SLC, 1 for MLC).
FTL
Flash Translation Layer: software (or controller firmware) that maps logical sectors to physical pages, handles bad blocks, ECC, wear levelling and garbage collection (card 10).

2. READING A PAGE, STEP BY STEP (ONFI-STYLE COMMANDS)

  1. Send command 0x00, then 5 address cycles (2 column + 3 row), then command 0x30.
  2. The chip moves the page from the array into its page register: busy for tR ≈ 25 µs (R/B# pin low).
  3. Stream 2112 bytes out over the 8-bit bus.
  4. Controller computes the ECC syndrome over each 512-byte chunk, corrects up to t bit errors.
  5. If errors corrected are close to t (say ≥ 6 of 8), schedule the block for scrubbing — it is degrading.
  6. If uncorrectable → report a read error, mark block suspect.

3. PROGRAM AND ERASE

  1. Program: 0x80, address, data (page + spare including ECC), 0x10 → busy tPROG ≈ 200 µs. Read status 0x70: bit 0 = FAIL.
  2. Erase: 0x60, 3 row-address cycles, 0xD0 → busy tBERS ≈ 0.7 ms. Status FAIL → mark the block bad and move its data.

Is 8-bit BCH enough? Datasheet asks "8 bits per 512 B" → each 512-byte chunk (4096 bits) needs 8 × 13 = 104 parity bits = 13 bytes (BCH over GF(213)). 4 chunks × 13 = 52 bytes → fits in the 64-byte spare, leaving 12 bytes for bad-block marker and FTL metadata. Capacity budget: 1024 blocks − 20 worst-case bad = 1004 usable × 128 KB ≈ 125.5 MB of a nominal 128 MB, before over-provisioning.
You write a "simple driver" that assumes all blocks are good. One factory-bad block sits at block 37. You erase it (status FAIL ignored), program it (FAIL ignored), and later read garbage — or worse, you erase the whole chip at the factory and destroy the factory bad-block markers, so you can never find the bad blocks again. Always scan and build a bad-block table before the first erase.
NAND is read and programmed in pages with a spare area that holds ECC and metadata, and erased in blocks. It ships with factory bad blocks marked in the spare area and grows more, and bit errors are normal, so every page needs BCH or LDPC ECC. Reads disturb neighbouring pages and programming must go in page order, so you need a flash translation layer — or a managed device like eMMC — to handle mapping, bad blocks, scrubbing and wear levelling.

FTL ideas: wear levelling (dynamic vs static), garbage collection, write amplification

ADVANCED▶

1. THE PROBLEM IN PLAIN WORDS

The host wants to overwrite "logical sector 5" again and again. Flash cannot overwrite, and erase blocks wear out. So the FTL never overwrites: it writes the new version to a fresh page somewhere else, updates a map "logical 5 → physical page X", and marks the old page as garbage. Later it cleans up the garbage. Every design choice is about doing this while wearing all blocks evenly and copying as little as possible.

Logical vs physical
Logical = address the host uses. Physical = real page in flash. The map between them lives in RAM and is persisted in flash (spare area or map pages).
Valid / invalid (stale) page
Valid = holds the newest copy of some logical address. Invalid = an older copy that has been superseded.
Garbage collection (GC)
Pick a block with many invalid pages ("victim"), copy its few valid pages to a free block, then erase the victim so it becomes free.
Dynamic wear levelling
When choosing where to write new data, pick the free block with the lowest erase count. Only spreads wear across blocks that are being rewritten.
Static wear levelling
Also periodically moves cold data (written once, never changed — e.g. a firmware image) out of low-wear blocks, so those blocks join the rotation.
Write amplification (WA)
WA = bytes physically written to flash ÷ bytes the host asked to write. 1.0 is ideal; GC copies and metadata push it up.
Over-provisioning (OP)
Spare physical capacity hidden from the host (e.g. 7–28% on SSDs). More free space → victims have fewer valid pages → lower WA.
TRIM / discard
Host tells the FTL a logical range is deleted, so its pages become invalid and need not be copied by GC.

2. WHAT HAPPENS ON EACH WRITE, STEP BY STEP

  1. Host writes logical page L.
  2. FTL appends the data to the next free page of the current "open" block, writing L and a sequence number into the spare area.
  3. FTL updates the RAM map L → new physical page, and marks the old physical page invalid.
  4. If free blocks fall below a threshold, GC runs: choose victim (greedy = fewest valid pages; cost-benefit also considers age), copy valid pages, erase victim, increment its erase count.
  5. Periodically (static WL): if max_erase − min_erase > threshold (e.g. 1000), move the data from the least-worn block to a worn one.
  6. After power loss: rebuild the map by scanning spare areas — for each L keep the copy with the highest sequence number.
Write amplification for a victim that is 75% valid. To free one 64-page block the FTL copies 48 valid pages and gains 16 free pages for new host data. Physical writes per 16 host pages = 16 + 48 = 64 → WA = 64 / 16 = 4.0. If the victim were only 25% valid: copy 16, gain 48 → WA = 64/48 = 1.33. Rule of thumb: WA ≈ 1 / (1 − u), where u = fraction of valid pages in the victim. That is why keeping free space (OP) matters so much.
Lifetime effect: 1 GB SLC NAND, 100k cycles, WA 4 → total host data = 1 GB × 100,000 / 4 = 25 TB written ("TBW"). At 10 GB/day → 2,500 days ≈ 6.8 years.

Your FTL picks GC victims purely by "most invalid pages" and never moves static data. 90% of the device holds a never-changing map database; all logging traffic rotates through the other 10%. Those blocks hit 3,000 cycles (MLC) after one-tenth of the expected life; grown bad blocks explode, and the device goes read-only years early. Symptom in the field: eMMC "life time estimation" (EXT_CSD DEVICE_LIFE_TIME_EST) jumps to 0x0A/0x0B.
An FTL never overwrites: it appends new data to a free page, remaps the logical address and marks the old page stale. Garbage collection copies the remaining valid pages out of a victim block and erases it, and those copies are write amplification — roughly one over one minus the victim's valid fraction, so free space or over-provisioning keeps it low. Dynamic wear levelling picks the least-worn free block for new writes; static wear levelling also relocates cold data so every block shares the wear.

EEPROM emulation on flash: two sectors, records with ID+data+CRC, status markers, compaction

INTERMEDIATE▶

1. WHAT IS IT?

Many MCUs have no EEPROM, but you still want to store a few settings (baud rate, calibration, a boot counter) and change them sometimes. EEPROM emulation is a small driver that makes two flash sectors behave like byte-rewritable memory. It does this by never overwriting: every change is appended as a new record, and the newest record for a variable wins. When a sector fills up, the newest values are copied to the other sector and the full one is erased.

Variable ID (virtual address)
A small number naming each setting (1 = baud, 2 = gain …). The driver stores it in each record so it knows which variable a record belongs to.
Record
One saved version of one variable: [ID][sequence][value][CRC]. In this page: 1 B ID + 2 B seq + 4 B value + 1 B CRC-8 = 8 bytes = exactly one STM32L4 double-word.
CRC
Cyclic Redundancy Check: a checksum computed over the record. If power dies while the record is being programmed, the stored CRC will not match, so the reader ignores that torn record.
Sequence number
A counter incremented on every write. Tells you which record is newer regardless of where it sits.
Sector status marker
A header word saying what state the sector is in: ERASED (0xFFFF), RECEIVING (0xEEEE, compaction in progress), ACTIVE/VALID (0x0000). Lets boot code know which sector is authoritative after a power cut.
Compaction (a.k.a. page transfer)
Copying only the newest record of each variable into the other sector, then erasing the old one.

3. WRITE, STEP BY STEP

  1. Compare with the current value in the RAM cache. If equal, do nothing (saves wear).
  2. Find the first free slot in the ACTIVE sector (kept in RAM after boot — no need to rescan).
  3. If there is a free slot: build the record {id, ++seq, value}, compute CRC over the first 7 bytes, program 8 bytes, read back and verify. Done.
  4. If the sector is full → compaction:
    1. Program the other sector's header to RECEIVING (0xEEEE).
    2. Write the new record into it first.
    3. For every other variable, copy its newest valid record.
    4. Erase the old sector (its header becomes 0xFFFF).
    5. Program the new sector's header to ACTIVE (0x0000 — only clears bits of 0xEEEE, so no erase needed).

(a) No CRC → a record torn by power loss is read as valid: the baud rate becomes 0x0001C2FF and the device is unreachable. (b) No status markers → after a cut mid-compaction, boot picks the half-copied sector and half the variables revert to defaults. (c) Erase the old sector before the copy is complete → a cut loses everything. (d) Retry a failed program into the same slot → AND-corrupted record. Try all of these in the Flash Lab's EEPROM mode.
EEPROM emulation uses two flash sectors as an append-only log. Each write appends a record with the variable ID, a sequence number, the value and a CRC, and the newest valid record per ID wins. When the active sector fills, I mark the other one RECEIVING, write the new value and copy the latest value of every variable, erase the old sector, then mark the new one ACTIVE. On boot the status markers tell me how far a compaction got, and the CRC lets me discard a record torn by power loss.

Power-loss-safe writes: atomicity, two-phase commit, journaling, copy-on-write, sequence numbers

ADVANCED▶

1. THE PROBLEM IN PLAIN WORDS

Power can disappear at any instant — in the middle of a 16 µs word program, or in the middle of a 1-second erase. After the next boot your data must be either the complete old version or the complete new version, never a mix. That property is called atomicity. Flash does not give it to you for free: an interrupted program leaves some bits programmed and some not (a "torn write"), and an interrupted erase leaves a sector of random-looking bits.

Atomic update
An update that is observed either fully done or not at all.
Torn write
A write cut part-way: some bytes/bits new, some old/erased.
Weak (marginal) bits
Cells whose program or erase was cut, sitting near the read threshold: they may read correctly today and flip next week or at another temperature. So "it read back OK" after a cut is not proof.
Commit marker
A small value written last; its presence means everything before it is complete.
Two-phase commit
Phase 1 write the data (not yet valid). Phase 2 write the commit marker. Reader trusts data only if the marker is present.
Journaling (write-ahead log)
Write the intended change to a log first, commit it, then apply it to the main structure. After a crash, replay committed log entries, discard uncommitted ones.
Copy-on-write (COW)
Never modify live data. Write a full new copy elsewhere, then switch one pointer/root to it in one atomic step.
Brown-out / PVD
Brown-out reset holds the MCU in reset when VDD is too low. PVD (Programmable Voltage Detector on STM32) gives an early interrupt as VDD falls, so firmware can stop starting new flash operations.

2. FIVE TECHNIQUES, EACH STEP BY STEP

A. CRC per record (detects torn records)

  1. Compute CRC over the payload. 2. Store it inside the same record. 3. Reader recomputes; mismatch → ignore record. CRC-16 gives a 1-in-65,536 chance that random garbage passes; CRC-32 1 in 4 billion; an all-0xFF blank must not pass (choose an init value so CRC(0xFF…) ≠ 0xFF…).

B. Two-phase commit with a valid flag (non-ECC flash)

  1. Write payload with flag byte left at 0xFF.
  2. Verify.
  3. Program flag byte to 0x00 (only clears bits). Reader: flag == 0x00 → committed.

C. Sequence numbers + A/B copies (simple config block)

  1. Two slots A and B, each [seq][data][CRC].
  2. To save: erase the slot with the older (or invalid) copy, write new data with seq = newest + 1.
  3. Boot: take the valid-CRC slot with the higher seq (wrap-safe compare). A cut during the erase or write only ever damages the older copy.

D. Journaling: log record "set X=5" + commit → apply → mark log entry done. Used by ext4 (jbd2) and many KV stores.

E. Copy-on-write: LittleFS writes new metadata to the other block of a pair and the new revision count makes it current atomically (card 16).

A/B config with sequence numbers, a power cut at every step. State: A = {seq 41, CRC ok}, B = {seq 40, CRC ok}. Save new config:
1. Erase B — cut here → B garbage (CRC fails), A seq 41 valid → boot uses A (old). ✔
2. Program B = {seq 42 …} — cut here → B torn, CRC fails → A (old). ✔
3. Done → B seq 42 > A seq 41 → boot uses B (new). ✔
Never at any point is the only valid copy being modified. That is the whole trick.
Hold-up time for finishing an operation. 470 µF on a 3.3 V rail, MCU + flash draw 40 mA, brown-out at 2.7 V. t = C·ΔV/I = 470e-6 × 0.6 / 0.04 = 7 ms. Enough to finish a 16 µs word program or a 0.4 ms SPI page program, not enough for a 250 ms sector erase. So: on PVD interrupt, don't start an erase; finish only short programs.
WRONG — the only copy is destroyed first
void cfg_save(const cfg_t *c) {
    flash_erase_sector(CFG_SECTOR); // ~250 ms window:
    flash_write(CFG_ADDR, c, sizeof *c); // cut = config gone
}
RIGHT — A/B with seq + CRC
void cfg_save(cfg_t *c) {
    int tgt = (newest == SLOT_A) ? SLOT_B : SLOT_A;
    c->seq = g_seq + 1;
    c->crc = crc32(c, offsetof(cfg_t, crc));
    flash_erase_sector(slot_sector[tgt]);  // old copy only
    flash_write(slot_addr[tgt], c, sizeof *c);
    if (verify(tgt, c)) { newest = tgt; g_seq = c->seq; }
}
You protect records with CRC but compute "newest" as "last valid record found" in a ring buffer that wraps: after wrap the newest record is in the middle, not at the end, and boot restores a week-old value. Sequence numbers fix ordering; CRC fixes torn data. You need both.
To survive power loss I never modify the only good copy. Data goes into erased space with a CRC and a sequence number, and becomes valid only when it's complete — via the CRC or a commit marker written last. On boot I take the newest copy whose CRC checks. For bigger structures that's journaling or copy-on-write, as ext4 and LittleFS do. I also use the PVD interrupt to avoid starting a long erase when power is failing, because hold-up capacitors usually cover milliseconds, not a sector erase.

Key-value stores on flash (Zephyr NVS, ESP-IDF NVS, KVS designs)

INTERMEDIATE▶

1. WHAT IS IT?

A key-value (KV) store is EEPROM emulation grown up: instead of 10 fixed numeric IDs with 4-byte values, you can save named entries ("wifi_ssid" → "Station-42", 18 bytes) of any length. It is still a log over flash sectors, with garbage collection, CRCs and wear levelling.

Key
The name (string or 16-bit ID). Zephyr NVS uses 16-bit IDs; ESP-IDF NVS uses namespace + string key (≤ 15 chars).
Allocation table entry (ATE)
Zephyr NVS term: a small 8-byte metadata record {id, offset, length, part, crc8} written from the end of a sector downwards, while data grows from the start upwards.
Tombstone
A record that says "key X deleted" (length 0). Needed because you cannot erase one record.
RAM index
Optional hash table key → flash address built at mount, to avoid scanning the whole log on every read.

2. ZEPHYR NVS SECTOR LAYOUT AND FLOW

  sector N
  ┌─ data → → →───────────────────────── free ──────────── ← ← ← ATEs ─┐
  │ "Station-42"│ 0x2580 │                       │ATE id2│ATE id1│close│
  └─────────────────────────────────────────────────────────────────────┘
  ATE = {id, offset, len, crc8}; "close" ATE written when sector is full
  1. Write: data bytes are programmed at the data pointer, then the ATE pointing to them is programmed (ATE last = commit).
  2. Read: walk ATEs from newest to oldest; first ATE with matching id and valid CRC wins; data CRC is also checked (optional).
  3. Sector full: write a "close" ATE, move to the next sector (sectors form a ring).
  4. GC: before the sector after next is reused, copy any still-current entries out of the oldest sector, then erase it. One sector is always kept empty for this.
  5. Mount: find the open sector (the one not closed), recover pointers, finish an interrupted GC.
#include <zephyr/fs/nvs.h>
static struct nvs_fs fs;
fs.flash_device = FIXED_PARTITION_DEVICE(storage_partition);
fs.offset       = FIXED_PARTITION_OFFSET(storage_partition);
fs.sector_size  = 4096;         // must be a multiple of the flash erase unit
fs.sector_count = 3;            // ≥ 2; one is always kept free for GC
nvs_mount(&fs);
uint32_t boots = 0;
nvs_read(&fs, 1, &boots, sizeof boots);     // returns bytes read or -ENOENT
boots++;
nvs_write(&fs, 1, &boots, sizeof boots);    // no write if value unchanged
Usable space. 3 sectors × 4 KB with one kept free → 8 KB of log. Each 4-byte entry costs 4 B data (rounded to write block) + 8 B ATE = 12 B → about (2 × 4096 − 2 × 16 overhead) / 12 ≈ 680 writes before a GC. Boot counter written once per boot: 680 boots per GC cycle.
You store a 2 KB blob (a certificate) in a KV store with 4 KB sectors and 3 sectors. Each update of the blob fills half a sector; GC has to copy the current blob every time — WA ≈ 2 and frequent erases. Worse, if the live data exceeds (sector_count − 1) × sector_size, GC can never free space and writes fail with -ENOSPC. Size KV partitions to ≥ 2–3× live data.
A flash key-value store is an append-only log of records with key, length, data and CRC, where the newest valid record wins and deletes are tombstones. Zephyr NVS, for example, writes data upward and 8-byte allocation entries downward in each sector, rotates through sectors as a ring, and garbage-collects the oldest sector into an always-free one. I keep live data well under the partition size, or garbage collection thrashes or fails.

FAT12/16/32: boot sector, FAT table, clusters, directory entries — and why it is not power-fail safe

INTERMEDIATE▶

1. WHAT IS FAT?

FAT (File Allocation Table) is the 1977-era filesystem every PC, phone and camera can read. Embedded devices use it on SD cards and USB sticks exactly for that reason: a technician pulls the card and opens the logs on a laptop. It is simple: the disk is cut into equal clusters, and a big table says which cluster follows which in each file.

Sector
The disk's addressable unit, 512 bytes on SD cards.
Cluster
Allocation unit = N sectors (power of 2), e.g. 64 sectors = 32 KB. A 1-byte file still uses one whole cluster.
Boot sector / BPB
Sector 0 of the volume. The BIOS Parameter Block inside it says: bytes per sector (offset 11, 2 B), sectors per cluster (13), reserved sectors (14, 2 B), number of FATs (16, usually 2), root entry count (17, 0 on FAT32), FAT size (22 for FAT12/16, 36 for FAT32), root directory cluster (44, FAT32). Signature 0x55 0xAA at offset 510.
FAT (the table)
One entry per cluster. Entry value = the next cluster of the file, 0 = free, 0x0FFFFFF8+ = end of chain (FAT32), 0x0FFFFFF7 = bad. FAT12 entries are 12 bits, FAT16 16 bits, FAT32 32 bits (28 used).
Directory entry
32 bytes per file: name 8.3 (11 B), attribute (offset 11), first cluster high (20), modified time/date (22/24), first cluster low (26), file size (28, 4 B). First byte 0xE5 = deleted. Long file names use extra entries with attribute 0x0F.
FSInfo
FAT32 sector with a cached "free cluster count" and "next free" hint — only a hint, may be stale.

2. WHICH FAT TYPE? (DECIDED ONLY BY CLUSTER COUNT)

< 4,085 clusters → FAT12; < 65,525 → FAT16; otherwise FAT32. (Microsoft spec; the label in the boot sector is ignored.)

3. READING A FILE, STEP BY STEP

  1. Read MBR (partition table) → find the volume start LBA.
  2. Read the boot sector, compute: FAT start = volume + reserved; data start = FAT start + NumFATs × FATsize (+ root dir sectors on FAT12/16).
  3. Read the directory cluster(s), find the 32-byte entry by name, get first cluster and size.
  4. Cluster c lives at LBA = data start + (c − 2) × sectors_per_cluster (clusters are numbered from 2).
  5. Next cluster = FAT[c]; repeat until end-of-chain or size reached.
8 GB SDHC formatted FAT32, 32 KB clusters. Clusters ≈ 8 × 230 / 32,768 = 262,144 → FAT32. FAT size = 262,144 × 4 B = 1 MB per copy, 2 copies = 2 MB. Reserved = 32 sectors. Suppose volume at LBA 8,192: FAT1 at 8,224, FAT2 at 8,224 + 2,048 = 10,272, data at 12,320. Cluster 2 = LBA 12,320; cluster 100 = 12,320 + 98 × 64 = 18,592.

4. WHY A POWER CUT CORRUPTS FAT

Appending 1 KB to a log file touches at least three different places, each a separate sector write:

  1. The data sector(s) in the cluster.
  2. FAT entries (both copies) if a new cluster was allocated: FAT[last] = new, FAT[new] = EOC.
  3. The directory entry: new file size (and timestamp).

There is no journal. A cut between 2 and 3 → lost cluster (allocated, but size says it is not part of the file). Between 1 and 2 → data written into a cluster still marked free; next allocation overwrites it. Cut during a FAT sector write → cross-linked or broken chains for other files sharing that FAT sector. On top of that the SD card's own controller may be mid-way through an internal erase/garbage collection, and on MLC NAND a cut can damage previously written "paired pages" — data you wrote yesterday.

  append 1 KB:   [data write] → [FAT1 + FAT2 write] → [dir entry size write]
  power cut  ↑ here: data lost, FS ok   ↑ here: lost cluster   ↑ ok if after
  FAT16/32 "dirty" flag (FAT[1] bit) tells PC chkdsk to scan, nothing more.

5. FRAGMENTATION

Files grow in clusters wherever free space is found. Many files growing in parallel interleave clusters → reading one file needs many FAT look-ups and non-sequential SD reads, which are slower (SD cards are much faster at sequential access in their allocation unit, often 4 MB). Mitigations: pre-allocate (FatFs f_expand), one file per day, larger cluster size.

You keep a log file open for days and call f_write but never f_sync. Directory size is updated only on sync/close, so after a brown-out the PC shows the file as 0 bytes even though megabytes of data sit in clusters (now "lost clusters" for chkdsk).
FAT divides the volume into clusters. A table with one entry per cluster links each file's clusters into a chain, and 32-byte directory entries hold the name, first cluster and size. The type — FAT12, 16 or 32 — is decided purely by the cluster count. It isn't power-fail safe because one append updates the data, both FAT copies and the directory entry in separate, unjournaled sector writes, and the SD controller underneath can also lose data on a cut. So I sync at commit points, keep files short-lived, and use hold-up or a journaling or copy-on-write filesystem when integrity matters.

FatFs (ChaN) API and porting layer

INTERMEDIATE▶

1. WHAT IS FATFS?

FatFs by ChaN is the de-facto FAT library for microcontrollers (used inside STM32Cube, ESP-IDF, many RTOSes). You give it four low-level functions to read/write 512-byte sectors on your medium; it gives you f_open, f_write, f_read like a PC.

FATFS object
Per-volume work area (~560 B incl. a 512-byte sector window) passed to f_mount.
FIL object
Per-open-file state; in non-tiny mode includes a 512-byte sector buffer.
diskio layer
Your port: disk_initialize, disk_status, disk_read, disk_write, disk_ioctl (CTRL_SYNC, GET_SECTOR_COUNT, GET_BLOCK_SIZE, CTRL_TRIM), plus get_fattime() for timestamps.
ffconf.h
Options: FF_FS_TINY (share one buffer), FF_USE_LFN (long names, needs a buffer), FF_FS_REENTRANT (RTOS mutex), FF_MAX_SS, FF_USE_EXPAND (f_expand).

2. LOGGING A LINE SAFELY, STEP BY STEP

  1. f_mount(&fs, "", 1) — 1 = mount now (reads boot sector, validates).
  2. f_open(&fil, "log.csv", FA_OPEN_APPEND | FA_WRITE).
  3. f_write the line; check bw == len (bw < len means disk full).
  4. f_sync at your commit points: flushes the cached data sector, FAT and directory entry. This is the moment the data becomes recoverable after a cut.
  5. f_close when done (does a sync).
FATFS fs; FIL fil; UINT bw; FRESULT fr;
fr = f_mount(&fs, "", 1);                   // FR_NO_FILESYSTEM → card not formatted
if (fr != FR_OK) return fr;
fr = f_open(&fil, "0:/log/20261018.csv",
            FA_OPEN_APPEND | FA_WRITE);     // creates if missing, seeks to end
if (fr != FR_OK) return fr;
int n = snprintf(line, sizeof line, "%lu,%d\r\n", ts, mv);
fr = f_write(&fil, line, n, &bw);           // buffered in fil's 512 B window
if (fr != FR_OK || bw != (UINT)n) goto err; // bw<n = volume full
if (++lines % 32 == 0) f_sync(&fil);        // commit every 32 lines (trade-off)

    return sd_read_blocks(buf, sector, count) ? RES_ERROR : RES_OK; // SDHC: block address
}
DRESULT disk_ioctl(BYTE pdrv, BYTE cmd, void *buf) {
    switch (cmd) {
    case CTRL_SYNC:        sd_wait_not_busy(); return RES_OK; // card finished writing
    case GET_SECTOR_COUNT: *(LBA_t *)buf = sd_sectors(); return RES_OK;

How much data can a brown-out lose? Logging 40-byte lines at 10 Hz = 400 B/s. Without f_sync until close, a cut loses everything since open as far as the directory knows. With f_sync every 32 lines (3.2 s), at most ~1.3 KB lost. Each f_sync costs ~3 sector writes (data, FAT, dir) ≈ a few ms on SD and extra wear on the dir/FAT sectors (the card's FTL wear-levels them).
Two RTOS tasks call FatFs on the same volume with FF_FS_REENTRANT = 0 → they share the volume's sector window and corrupt the FAT. Or the FIL object is a local variable in a function that returns while the file is still open → dangling state, later write scribbles the stack.
FatFs needs only a diskio port — sector read and write, ioctl for sync and sector count, and get_fattime — and gives you f_mount, f_open, f_write, f_sync and f_close. f_write is buffered, so data and the directory size only reach the card on f_sync or f_close, and I choose the sync interval as a trade-off between how much a brown-out loses and extra writes. Under an RTOS I enable FF_FS_REENTRANT, and I always check bytes-written against the length requested.

LittleFS: metadata pairs, copy-on-write, wear levelling, small RAM (and why SPIFFS is deprecated)

ADVANCED▶

1. WHAT IS LITTLEFS?

LittleFS (from Arm Mbed, now used in Zephyr, ESP-IDF, nRF Connect, PX4…) is a filesystem designed for raw NOR/NAND flash on microcontrollers. Its two promises: every operation is power-loss safe (after a cut you see the old or the new state, never corruption), and it uses a small, bounded amount of RAM (a few cache buffers, no big tables).

Block
LittleFS's unit = the flash erase unit (e.g. 4 KB sector on W25Q128).
Metadata pair
Every directory is stored in two blocks. Updates are appended as small "commits" to one of them; when it fills, the directory is compacted into the other. Each block has a revision count; the higher valid one is current.
Commit
A batch of tags (file created, name, size, inline data…) ending with a CRC. A commit without a valid CRC is ignored on mount — that is what makes updates atomic.
CTZ skip-list
How file data is stored: a backward-linked list of blocks with extra "skip" pointers so seeking is O(log n). Written copy-on-write: modifying a block writes a new block and new pointers.
Inline file
Small files (≤ cache size, typ. tens to hundreds of bytes) stored directly inside the directory's metadata commit.
block_cycles
Config value: after this many erases a metadata block is relocated to another block (wear levelling of the hot metadata). −1 disables.
lookahead buffer
A bitmap (lookahead_size × 8 blocks) of free blocks found by scanning; allocation is round-robin from a moving point, giving dynamic wear levelling.

2. WHAT HAPPENS WHEN YOU UPDATE A FILE, STEP BY STEP

  1. lfs_file_write buffers data in the file cache.
  2. When a block's worth is ready (or on sync/close), the data goes to a newly allocated block (copy-on-write); old data blocks are untouched.
  3. On lfs_file_sync/lfs_file_close, a commit is appended to the directory's metadata block: "file X: head = new block, size = N", followed by a CRC.
  4. Only when that CRC lands is the new version visible. Cut before → mount sees the previous commit → old file contents. The orphaned new data blocks are simply free.
  5. If the metadata block is full → compact the directory into the other block of the pair with revision+1, then that becomes current. A cut during compaction leaves the old block (lower revision, valid CRC) current.
  dir metadata pair             data (copy-on-write)
  blk 0 rev 7 ┐                  old: [B12]←[B13]       (still intact)
   commit…crc  │ current         new: [B12]←[B13]←[B40] (appended block)
   commit "head=B40,size=9000" crc ✓   ← the atomic switch
  blk 1 rev 6 ┘ older

3. CONFIGURING AND USING IT

const struct lfs_config cfg = {
    .read  = nor_read,   .prog = nor_prog,      // your SPI NOR driver
    .erase = nor_erase,  .sync = nor_sync,
    .read_size      = 16,       // min read unit
    .prog_size      = 16,       // min program unit (≥ flash write unit)
    .block_size     = 4096,     // = 0x20 sector erase size
    .block_count    = 4096,     // 16 MB / 4 KB
    .cache_size     = 256,      // ≥ prog_size; = page size is natural
    .lookahead_size = 32,       // 32 B → 256 blocks tracked per scan
    .block_cycles   = 500,      // relocate metadata every 500 erases
};

    lfs_format(&lfs, &cfg);           // (do NOT auto-format on any error
    lfs_mount(&lfs, &cfg);            //  in production — you may wipe data)
}

RAM cost. One read cache + one prog cache (256 B each) + lookahead 32 B + per open file one cache (256 B) ≈ 256×3 + 32 + struct overhead ≈ ~1 KB for one open file. FAT with FatFs needs ~1.1 KB as well, but FAT is not power-safe and does no wear levelling on raw flash.

4. SPIFFS — WHY IT IS DEPRECATED

SPIFFS (SPI Flash File System) was an earlier flat (no directories) FS for SPI NOR with static wear levelling. Problems: not fully power-loss safe (needs a check/repair pass), RAM and mount time grow with flash size, slows down badly when nearly full, and it is unmaintained. Espressif's ESP-IDF documents SPIFFS as no longer under active development and recommends LittleFS for new designs.

(a) prog_size smaller than the flash's real program unit (e.g. 1 on an STM32L4 where the unit is 8) → the driver tries to program a double-word twice → PROGERR, corrupted commit. (b) Calling lfs_format automatically on any mount error → one marginal read during a brown-out formats the customer's data away. (c) Directories with thousands of files → each metadata compaction rewrites the whole directory: slow; spread files across directories.
LittleFS is power-loss safe because nothing is updated in place. Directories live in metadata pairs that take appended commits, each ending in a CRC, and file data is copy-on-write, so a file change becomes visible only when the commit's CRC is written. It wear-levels by allocating blocks round-robin and relocating metadata blocks after block_cycles erases, and it needs only a few cache buffers of RAM. SPIFFS is deprecated because it isn't fully power-safe, scales badly and isn't maintained.

Linux on flash: MTD, JFFS2, UBI/UBIFS, and ext4 journaling on eMMC

ADVANCED▶

1. TWO WORLDS: RAW FLASH vs BLOCK DEVICES

Linux treats raw flash (NAND/NOR chips without a controller) and managed flash (eMMC, SD, SSD — they have an FTL inside) completely differently. Raw flash shows up as an MTD device; managed flash shows up as a normal block device (/dev/mmcblk0). Putting the wrong filesystem on the wrong kind is a classic mistake.

MTD
Memory Technology Device subsystem: exposes raw flash with erase/read/write and knows about erase blocks, OOB and bad blocks. Devices /dev/mtd0, partitions from device tree.
JFFS2
Journalling Flash File System v2: a log-structured FS directly on MTD with compression and wear levelling. Must scan the whole flash at mount to build its index in RAM → mount time and RAM grow with size; fine for small NOR (≤ 64 MB), poor for big NAND.
UBI
Unsorted Block Images: a volume manager on top of MTD. Maps logical erase blocks (LEBs) to physical ones (PEBs) across the whole chip, handling bad blocks, wear levelling (keeps erase counters in each PEB's EC header) and scrubbing on bit-flips. Each PEB starts with an EC header and a VID header.
UBIFS
Filesystem on a UBI volume: journaled, with an on-flash B+tree index (wandering tree, copy-on-write), write-back caching and fast mount. The standard choice for raw NAND on embedded Linux.
ext4
The default Linux block-device FS; uses the jbd2 journal. Correct choice on eMMC/SD because their controller already does the FTL work.

2. ext4 JOURNALING, STEP BY STEP (DEFAULT data=ordered)

  1. Write the file's data blocks to their final location.
  2. Write the metadata changes (inode, bitmaps, directory) into the journal, then a commit block (with checksum).
  3. Later, checkpoint: copy the metadata from the journal to its home location; free the journal space.
  4. After a crash, mount replays every journal transaction that has a valid commit block and discards incomplete ones → metadata is always consistent. Modes: data=journal (data also journaled, safest, 2× writes), ordered (default), writeback (fastest, data may be stale after crash).
  Raw NAND:   NAND ─ MTD ─ UBI ─ UBIFS          (Linux does FTL work)
  Small NOR:  NOR  ─ MTD ─ JFFS2  (or UBI/UBIFS)
  eMMC/SD:    NAND+controller(FTL) ─ mmcblk ─ ext4 / F2FS / FAT
  Never:      ext4 on /dev/mtdblock (no wear levelling, no bad blocks)
UBI overhead on a 256 MB SLC NAND, 128 KB PEBs. 2,048 PEBs. UBI reserves ~20 PEBs per 1,024 for bad-block handling by default (≈ 40), plus 4 internal (2 layout volume, 1 WL, 1 atomic LEB change). Each LEB loses 2 NAND pages (EC + VID header) = 4 KB → LEB = 124 KB. Usable ≈ (2048 − 44) × 124 KB ≈ 242 MB.
Mounting ext4 on raw NAND through mtdblock: every 4 KB write becomes read-erase-rewrite of a 128 KB block (WA 32×), no wear levelling, no bad-block handling → device dies in weeks, corrupts after a power cut. Equally wrong: UBIFS on eMMC — eMMC is not an MTD device.
On Linux, raw flash is an MTD device and needs a flash-aware stack: JFFS2 for small NOR, or UBI plus UBIFS for NAND. UBI does bad-block handling, wear levelling and scrubbing across the whole chip, and UBIFS gives a journaled, fast-mounting filesystem. eMMC and SD are block devices with their own FTL, so ext4 is right there; its jbd2 journal writes metadata transactions with a commit block and replays committed ones after a crash.

SD cards: SPI-mode init (CMD0, CMD8, ACMD41, CMD58), block size, SDIO

INTERMEDIATE▶

1. WHAT IS IT?

An SD card is NAND flash plus a controller. Hosts talk to it either in SD mode (CLK, CMD line, 1 or 4 data lines — "SDIO" peripheral on STM32) or in the simpler SPI mode (CS, SCK, MOSI, MISO), which any MCU can do. Every command is 6 bytes: 0x40|index, a 32-bit argument, and a CRC7 byte.

R1 response
1-byte reply in SPI mode. Bit 0 = in idle state, bit 1 = erase reset, bit 2 = illegal command, bit 3 = CRC error, bit 4 = erase sequence error, bit 5 = address error, bit 6 = parameter error, bit 7 always 0. 0x00 = ready, 0x01 = idle (initialising).
SDSC / SDHC / SDXC
Standard capacity (≤ 2 GB, byte addressing), High capacity (≤ 32 GB) and eXtended (≤ 2 TB): both block (512-byte) addressing.
OCR
Operation Conditions Register; bit 30 = CCS (Card Capacity Status): 1 = SDHC/SDXC.
ACMD
"Application command": must be preceded by CMD55 (APP_CMD).

2. THE SPI INIT SEQUENCE, STEP BY STEP

  1. Power up, set SCK to 100–400 kHz. With CS high and MOSI high, send ≥ 74 clocks (10 bytes of 0xFF).
  2. CMD0 (GO_IDLE_STATE), arg 0, CRC 0x95, with CS low → expect R1 = 0x01. The card enters SPI mode because CS was low during CMD0. (CRC is checked here because the card is still in SD mode.)
  3. CMD8 (SEND_IF_COND), arg 0x000001AA (VHS = 2.7–3.6 V, check pattern 0xAA), CRC 0x87 → R7 = R1 + 4 bytes. If R1 has "illegal command" (0x05) → SD v1 or MMC. Otherwise the last byte must echo 0xAA and the voltage nibble must be 1.
  4. Loop: CMD55 then ACMD41 with arg 0x40000000 (HCS = host supports high capacity) until R1 = 0x00. Takes up to ~1 s; time out after 1 s.
  5. CMD58 (READ_OCR) → if OCR bit 30 (CCS) = 1 → SDHC/SDXC, block addressing. Else SDSC → send CMD16 (SET_BLOCKLEN 512).
  6. Raise SCK to up to 25 MHz (default speed).

3. READ AND WRITE A BLOCK

  1. Read: CMD17 (READ_SINGLE_BLOCK) arg = block number (SDHC) or byte address (SDSC). Wait R1 = 0, then wait for data token 0xFE, read 512 bytes + 2 CRC16 bytes.
  2. Write: CMD24, R1 = 0, send one 0xFF gap, token 0xFE, 512 bytes, 2 CRC bytes. Data response xxx0sss1: sss = 010 → accepted (byte & 0x1F == 0x05); 101 = CRC error; 110 = write error. Then the card holds MISO low (busy) until programming finishes — poll for 0xFF.
  3. Multi-block: CMD18 + CMD12 stop; CMD25 with token 0xFC per block and stop token 0xFD. ACMD23 (pre-erase count) speeds multi-block writes.
static uint8_t sd_cmd(uint8_t idx, uint32_t arg, uint8_t crc) {
    spi_xfer(0xFF);                          // make sure card is ready
    spi_xfer(0x40 | idx);                    // start bit 0, tx bit 1
    spi_xfer(arg >> 24); spi_xfer(arg >> 16); spi_xfer(arg >> 8); spi_xfer(arg);
    spi_xfer(crc);                           // CRC7<<1 | end bit
    for (int i = 0; i < 10; i++) {           // R1 within 8 bytes (NCR)
        uint8_t r = spi_xfer(0xFF);
        if (!(r & 0x80)) return r;
    }
    return 0xFF;                             // no response
}
int sd_init(void) {
    spi_set_hz(400000);
    cs_high(); for (int i = 0; i < 10; i++) spi_xfer(0xFF); // 80 clocks, CS HIGH
    cs_low();
    if (sd_cmd(0, 0, 0x95) != 0x01) return -1;     // idle
    uint8_t r = sd_cmd(8, 0x1AA, 0x87);
    bool v2 = false;
    if (r == 0x01) {                               // SD v2
        uint8_t r7[4]; for (int i = 0; i < 4; i++) r7[i] = spi_xfer(0xFF);
        if ((r7[2] & 0x0F) != 0x01 || r7[3] != 0xAA) return -2; // voltage/pattern
        v2 = true;
    }
    uint32_t t0 = millis();
    do {
        sd_cmd(55, 0, 0x01);
        r = sd_cmd(41, v2 ? 0x40000000 : 0, 0x01); // HCS only for v2
    } while (r != 0x00 && millis() - t0 < 1000);
    if (r) return -3;
    g_block_addr = false;
    if (v2 && sd_cmd(58, 0, 0x01) == 0) {
        uint8_t ocr[4]; for (int i = 0; i < 4; i++) ocr[i] = spi_xfer(0xFF);
        g_block_addr = ocr[0] & 0x40;              // CCS = OCR bit 30
    }
    if (!g_block_addr) sd_cmd(16, 512, 0x01);      // SDSC: fix 512 B blocks
    cs_high(); spi_xfer(0xFF);
    spi_set_hz(25000000);
    return 0;
}
Address for sector 1,000,000. SDHC: CMD17 argument = 1,000,000 (0x000F4240). An SDSC card would need the byte address 1,000,000 × 512 = 512,000,000 (0x1E848000). Sending a block number to an SDSC card reads the wrong place; sending a byte address to SDHC gives "address error" (R1 bit 5) or reads far beyond.
(a) Init clock 8 MHz instead of ≤ 400 kHz → some cards never leave idle. (b) Forgot the 74 dummy clocks with CS high → CMD0 returns 0xFF. (c) CS shared on a bus with another device whose CS is left floating → corrupted responses. (d) No 10–50 kΩ pull-ups on CMD/DAT lines in SD mode → intermittent init. (e) Not waiting for the busy (MISO low) after write → next command fails.

SDIO / SD mode: same command set but on a dedicated CMD line with CRC always on, 1- or 4-bit data, 25 MHz (default speed, 12.5 MB/s) or 50 MHz high speed (25 MB/s), UHS-I up to 104 MB/s at 1.8 V. STM32F4's SDIO peripheral + DMA does this in hardware.

In SPI mode I clock 74 or more cycles at under 400 kHz with CS high, send CMD0 with CRC 0x95 to get R1 = 0x01 idle, then CMD8 with 0x1AA and CRC 0x87 to detect a v2 card. I loop CMD55 plus ACMD41 with the HCS bit until R1 is zero, read the OCR with CMD58 — the CCS bit means SDHC with 512-byte block addressing, otherwise I set CMD16 to 512. Then I raise the clock and use CMD17/CMD24 with the 0xFE data token, checking the 0x05 data-accepted response and waiting out busy.

Data logging designs: ring buffer in flash, sequence numbers, timestamps, rotation

INTERMEDIATE▶

1. WHAT IS IT?

A flash ring buffer stores the most recent N log records, overwriting the oldest when full — like a car's black box. Because flash erases in sectors, "overwriting the oldest" means erasing the oldest sector when the write pointer reaches it. The hard part is finding where you were after a reboot.

Head / tail
Head = where the next record is written. Tail = oldest record still present.
Sequence number (seq)
Monotonic counter stored in every record. After reboot, newest = highest seq. Needed because after wrap-around position no longer tells you age.
Wrap-safe compare
With a 16-bit seq, "a is newer than b" is (int16_t)(a - b) > 0. Works as long as live records span less than 32,768 numbers.
Monotonic vs wall-clock time
Wall clock (RTC, UTC) can jump (NTP sync, dead coin cell). Store both: seq/uptime for order, UTC for humans.

2. WRITE, STEP BY STEP

  1. If head is at the start of a sector, that sector holds the oldest data: erase it first (tail moves forward one sector).
  2. Program record {seq++, utc, uptime_ms, type, payload, CRC} at head.
  3. head += record size; if head == end, head = start (wrap).

3. FIND THE HEAD AFTER REBOOT, STEP BY STEP

  1. Read the first record of every sector (cheap: one read per sector).
  2. Pick the sector whose first record has the highest seq (wrap-safe). That is the newest sector.
  3. Inside it, scan (or binary-search, since blank slots are all at the end) for the first blank slot → head. Skip a final CRC-failing torn record.
  4. g_seq = seq of last valid record + 1.
16 sectors × 4 KB, 32-byte records = 128 records/sector, 2,048 total. Logging 1 record per minute: 1,440/day → the ring holds 2,048/1,440 = 1.4 days of history (minus one sector being erased: 15 × 128 = 1,920 records guaranteed = 1.33 days). Erases: 1,440 / 128 = 11.25 sector erases/day spread over 16 sectors = 0.7/day/sector → 100,000 cycles (W25Q) / 0.7 = 142,000 days. Wear is no concern; capacity is the design driver.

A flash ring log erases the oldest sector just before the write pointer enters it, and every record carries a sequence number, timestamps and a CRC. After reboot I read the first record of each sector, take the one with the highest sequence number using a wrap-safe signed difference, then find the first blank slot inside it. Position alone can't tell age after a wrap, and the wall clock can jump, so I order by sequence and keep UTC only for humans.

Flash wear budget calculation and data retention vs temperature

ADVANCED▶

1. WHY CALCULATE?

Wear-out is invisible during development (weeks of testing) and lethal in the field (years of operation). A one-line calculation at design time tells you whether a storage scheme lasts 3 days or 30 years. Interviewers love it because it shows you think in numbers.

2. THE FORMULA, STEP BY STEP

  1. Writes per day: W.
  2. Record size including header/CRC/padding to the program unit: r bytes.
  3. Slots per erase unit: R = floor((sector_size − header) / r).
  4. Live records copied per compaction: L (e.g. number of variables). New slots gained per erase: R − L.
  5. Erases per day (all sectors): E = W / (R − L) × (1 + safety margin for metadata).
  6. Sectors in rotation N, endurance C → life_days = C × N / E.
  7. Compare with the no-levelling case (in-place: one erase per write → life = C / W days).
Write one 16-byte record every second, STM32F4 16 KB sectors, 10k endurance.
W = 86,400/day.
• In place (erase sector every write): 10,000 / 86,400 = 0.116 days = 2.8 hours.
• Append in one sector: R = 16,384/16 = 1,024; E = 86,400/1,024 = 84.4/day → 10,000/84.4 = 118 days ≈ 4 months.
• Two sectors (EEPROM emulation, L = 8): R − L = 1,016 → E = 85/day, per sector 42.5 → 235 days.
• External W25Q128, 14 MB log ring (3,584 × 4 KB sectors, 100k cycles): R = 256 → E = 337.5/day over 3,584 sectors = 0.094/sector/day → 100,000/0.094 ≈ 1.06M days ≈ 2,900 years.
• Or keep it in RAM and write only on change / every 10 min / on PVD: W = 144 → in-place erase on F4 still only 69 days, log in two sectors → ~390 years.

3. RETENTION vs TEMPERATURE

Charge leaks from the floating gate by a thermally activated process, modelled with the Arrhenius equation: acceleration factor AF = exp[(Ea/k) × (1/Tuse − 1/Tstress)], with activation energy Ea ≈ 1.1 eV for intrinsic charge loss (JEDEC JESD47/JESD22-A117 use 1.1 eV; some mechanisms ~0.6 eV), k = 8.617×10⁻⁵ eV/K. Retention also drops with cycling: a block at its full endurance retains for much less time than a fresh one.

STM32F4 datasheet values: 30 years at 85 °C after 1k cycles; 10 years at 105 °C after 1k cycles; 20 years at 55 °C after 10k cycles.
Arrhenius check 85 °C → 105 °C with Ea = 1.1 eV: 1/358.15 − 1/378.15 = 1.477×10⁻⁴ K⁻¹; × (1.1 / 8.617×10⁻⁵) = 12,765 × 1.477×10⁻⁴ = 1.886 → AF = e1.886 ≈ 6.6. 30 y / 6.6 ≈ 4.5 y; the datasheet's 10 y means ST uses a lower effective Ea (≈ 0.6–0.7 eV) for this spec — another reason to always use the datasheet's table, not your own extrapolation.
An outdoor swap-station controller in Rajasthan runs at 70–85 °C internal temperature for years, uses a cheap TLC SD card and rewrites the same config file every minute. Retention and endurance are both consumed far faster than the 25 °C marketing number; the symptom is CRC errors on old data and the card going read-only after 2–3 years. Mitigation: industrial-temp SLC/pSLC cards, rate-limit writes, scrub (re-write) old data periodically.
I start the wear budget from writes per day and the record size, work out how many records fit per erase unit minus what compaction copies, and that gives erases per day. Endurance times sectors in rotation, divided by that, is the lifetime. Writing a record every second to one 10k-cycle sector lasts hours if done in place and months as a log, so I spread wear across many sectors, coalesce writes in RAM, and confirm retention at the real maximum temperature and worn state from the datasheet's derating table.
