PART 1 / 7

What problem does embedded Linux solve?

Embedded Linux means running the same Linux kernel that runs servers and Android phones on a product: a charger, a router, a camera, an industrial gateway, a car's infotainment unit. You choose it when the product needs things that are very expensive to write yourself on a microcontroller: a full TCP/IP stack with TLS, Wi-Fi, USB host, filesystems, a display with a GUI, containers, and thousands of ready-made open-source programs.

1. Why can't a normal microcontroller run Linux?

Take the microcontroller you know, an STM32F407: a Cortex-M4 at 168 MHz with 1 MB of Flash and 192 KB of SRAM. Now look at the size of a small Linux system:

Linux kernel image (uImage) on our reference board = 7,712,264 bytes ≈ 7.4 MiB STM32F407 Flash = 1,048,576 bytes = 1.0 MiB kernel alone is 7,712,264 / 1,048,576 ≈ 7.4 × larger than all of the MCU's Flash Kernel RAM use after boot ("Memory: 434616K/491520K available") 491,520 K − 434,616 K = 56,904 K ≈ 55.6 MiB used by the kernel itself STM32F407 SRAM = 192 KB → about 300 × too small

Size is only the first problem. The bigger one is that Linux needs an MMU (Memory Management Unit). An MMU is hardware inside the CPU that translates every address the program uses (a virtual address) into a real memory location (a physical address) through tables the kernel writes. Linux builds its whole design on this: every process gets its own private address space, so a crashing app cannot overwrite another app or the kernel. A Cortex-M4 has only an MPU (Memory Protection Unit): it can forbid access to 8 regions but cannot translate addresses. So we need a bigger class of chip.

2. The application processor (the "SoC")

An application processor, usually called an SoC (System-on-Chip), has Cortex-A cores (A = "application") with an MMU and caches, but almost no memory inside. Our reference part for this whole page is the ST STM32MP157 (used on the STM32MP157C-DK2 board):

Notice three things in the picture, because they explain everything that follows:

  1. The big memory is outside the chip. The 512 MB DDR3L RAM is a separate chip on the circuit board. It is useless until software configures the DDR controller for that exact memory chip (more in Part 3).
  2. There is no Flash for code inside. All software (bootloader, kernel, apps) lives on an SD card or an eMMC chip (eMMC = "embedded MultiMediaCard", basically an SD card soldered onto the board). The CPU cannot execute directly from it; code must be copied into RAM first.
  3. At reset only two tiny memories work: the 128 KB BootROM (code written by ST at the factory, cannot be changed) and the 256 KB SYSRAM. Starting from just these, the chip must "pull itself up by its bootstraps" — that is where the word boot comes from.

The design idea: Linux on the A7 cores handles networking, UI and updates; the hard real-time control loop (motor, power stage) runs on the M4, which has the predictable 71 ns interrupt response Linux cannot promise. They talk through shared memory (a mechanism called RPMsg).

Embedded Linux runs on an application processor, not a microcontroller, because Linux needs an MMU for per-process virtual memory and tens of megabytes of RAM. An SoC like the STM32MP157 has Cortex-A cores with an MMU but keeps its RAM and storage outside the chip, so at reset only a small ROM and SRAM work, and the board has to boot itself through several stages. I pick Linux when I need networking, filesystems, displays and a big software ecosystem, and I keep hard real-time work on an MCU core.

PART 2 / 7

The vocabulary, one term at a time

Embedded Linux has many names for things. Read this list once; every later section uses these words, and the Concepts tab defines them again in context.

1. The pieces of software, in boot order

BootROM
Code burned into the SoC at the factory (128 KB on STM32MP1). It runs first, reads the boot pins (resistors on the board that say "boot from SD" or "boot from eMMC"), and loads the next stage into SYSRAM. You cannot change it.
FSBL / SPL / BL2
"First Stage Boot Loader" / "Secondary Program Loader" / "Boot Loader stage 2": three names for the small program the ROM loads. Its main job is to turn on the external DDR RAM. On STM32MP1 it is TF-A (Trusted Firmware-A, ARM's open-source firmware); on TI AM335x it is U-Boot SPL.
OP-TEE
"Open Portable Trusted Execution Environment": a tiny secure operating system that runs in a protected part of the CPU (ARM TrustZone, the "secure world"). It holds keys and does crypto that even a hacked Linux cannot read. Optional.
U-Boot
"Universal Boot Loader": the main bootloader. It has drivers for SD, USB and Ethernet, a command prompt, and settings called the environment. Its job: load the kernel and the device tree from storage into RAM and start the kernel.
Kernel
The Linux kernel itself: the program that manages memory, schedules processes and contains the drivers (code that controls hardware). It runs in privileged mode.
DTB / device tree
"Device Tree Blob": a small binary file (≈ 90 KB) that describes the board's hardware: "there is an I²C controller at address 0x5C00_2000 using interrupt 95, with a TMP117 sensor at address 0x48". It is data, not code. Source files are .dts/.dtsi.
initramfs
"Initial RAM filesystem": an optional small archive of files the kernel unpacks into RAM and runs before the real filesystem is ready. Used when the root filesystem needs work before it can be mounted (decryption, verification).
rootfs
"Root filesystem": the partition that becomes /. It contains /bin, /etc, the C library and all programs.
init / PID 1
The first user-space program, process ID 1 (usually systemd or BusyBox init). It starts every other service. If it ever exits, the kernel panics.

2. Words for how the kernel is organised

User space
Where normal programs run: unprivileged CPU mode (called EL0 on 64-bit ARM, USR mode on 32-bit ARM). A program here can only touch its own memory.
Kernel space
Where the kernel runs: privileged mode (EL1 on ARMv8, SVC mode on ARMv7). It can touch all memory and all hardware registers.
System call
The only door from user space into the kernel. A special instruction (svc #0 on ARM) makes the CPU switch to kernel mode and jump to a fixed kernel entry point. open(), read(), ioctl() are system calls.
Virtual address
The address a program uses. The MMU translates it to a physical address (the real location in DDR or a register). Two processes can both use virtual address 0x0001_0000 and get different physical memory.
Driver
Kernel code that knows one kind of hardware (a UART, a sensor). It is bound to a device (one instance of that hardware) by the driver model.
probe()
The function the kernel calls when it pairs a driver with a device. Probe maps registers, requests the interrupt and creates the user interface.
Module (.ko)
A driver compiled as a separate file ("kernel object") that can be loaded at runtime with modprobe, instead of being built into the kernel image.
/dev node
A special file like /dev/ttySTM0 or /dev/i2c-1. Opening and reading it calls the driver's functions. A character device is one you read/write as a stream of bytes.
sysfs (/sys)
A virtual filesystem the kernel generates: every device, driver and bus appears as a directory, with small text files for settings.
MMIO
"Memory-Mapped I/O": peripheral registers appear at physical addresses (GPIOA at 0x5000_2000). The kernel maps them with ioremap() and accesses them with readl()/writel().
IRQ
"Interrupt Request": a hardware signal that makes the CPU stop and run an interrupt handler. On ARM SoCs they are routed by the GIC (Generic Interrupt Controller).
Context
"Where am I running?": in process context (on behalf of a program, may sleep) or in interrupt/atomic context (must never sleep). Most kernel bugs in interviews are about this.

3. Words for building and shipping

Cross toolchain
A compiler that runs on your x86 PC but produces ARM code, e.g. arm-linux-gnueabihf-gcc. The prefix (called a triplet) says CPU, OS and ABI.
BSP
"Board Support Package": the vendor's bootloader, kernel, device trees and patches for a chip or board.
Yocto / Buildroot
Build systems that compile the toolchain, bootloader, kernel and every program from source and produce a ready-to-flash image.
OTA
"Over-The-Air" update: replacing the software on a deployed device through the network, safely even if power fails.
Secure boot
Each boot stage checks a cryptographic signature on the next one before running it, so only your signed software can run.

The boot chain is BootROM, then a first-stage loader such as TF-A or U-Boot SPL that brings up DDR, optionally OP-TEE in the secure world, then U-Boot, which loads the kernel and the device tree blob. The kernel uses the device tree to find the hardware, binds drivers by calling their probe functions, mounts the root filesystem and starts PID 1. User programs reach drivers only through system calls on device nodes or sysfs files.

PART 3 / 7

The boot journey, with real numbers

Let's follow the STM32MP157C-DK2 board from the moment you plug in power until the login: prompt, about 9 seconds later. The numbers below are taken from a real serial-console log (the Boot-Flow Simulator tab replays it). Keep one question in mind: at each moment, which memory works, and who is running?

1. Why there must be several stages

The DDR RAM chip needs to be configured and trained before it can store a single byte. "Configured" means telling the DDR controller the chip's size (512 MB), bus width (16 bits), speed (533 MHz) and timing parameters from its datasheet. "Training" means the controller measures, for each data line, the exact delay at which to sample data, because the copper traces on every board have slightly different lengths. These values differ for every board design, so ST cannot put them in the factory ROM. Therefore:

  1. The ROM can only use SYSRAM (256 KB), so it loads a small program (TF-A BL2, about 120 KB) that fits in SYSRAM.
  2. That small program, written for your board, configures and trains DDR.
  3. Only now is there room (512 MB) for the big programs: U-Boot (~1 MB), the kernel (~7.4 MB), the root filesystem's programs.

Rule to remember: every stage is as big as the memory it is allowed to run in.

4. The hand-over contract between U-Boot and the kernel

U-Boot does not "call" the kernel like a C function. It prepares the CPU in an exact state the kernel documents, then jumps:

  1. Writes the kernel command line (the bootargs setting, e.g. root=PARTUUID=e91c… rootwait console=ttySTM0,115200) into the DTB, in a node called /chosen.
  2. Writes the real RAM size into the DTB's /memory node and marks OP-TEE's region as reserved.
  3. Turns off the MMU and the data cache, and masks interrupts.
  4. Puts the physical address of the DTB in register r2 (r0 = 0, r1 = machine type, unused with DT). On 64-bit ARM: DTB address in x0.
  5. Jumps to the kernel's entry point. U-Boot's memory is now considered free; U-Boot is gone.

PART 4 / 7

Kernel space, user space, and one read() traced end to end

On a microcontroller your code and the UART driver are one program; any function can write any register. On Linux there is a wall between programs (user space) and the kernel. The wall is enforced by the CPU itself, and the only door is the system call.

1. Why the wall exists

If any app could write any register, one buggy app could reprogram the DDR controller and crash everything, and a malicious app could read another app's passwords. So the CPU has two privilege levels. User programs run at EL0 (Exception Level 0, unprivileged) and the MMU only maps their own memory. The kernel runs at EL1 and can access everything. An app that touches a register address directly gets a "Segmentation fault" because that address is simply not in its page tables.

2. The worked example: our app reads 64 bytes from an ADC

The page uses a made-up but realistic "Acme" ADC (analog-to-digital converter) throughout. Its driver creates /dev/acme_adc0; each sample is 16 bits (2 bytes). The app does:

int fd = open("/dev/acme_adc0", O_RDONLY);
uint16_t buf[32];                         /* 32 samples × 2 bytes = 64 bytes */
ssize_t n = read(fd, buf, sizeof(buf));   /* asks for 64 bytes            */

Here is exactly what happens, on 64-bit ARM (arm64):

  1. libc prepares registers. The C library's read() is a tiny wrapper. It puts the arguments in registers: x0 = fd (say 3), x1 = address of buf (a user virtual address such as 0x0000_ffff_d2a3_c5e0), x2 = 64, and the system call number 63 (__NR_read on arm64) in register x8.
  2. The door: svc #0. This instruction causes an exception. The CPU switches from EL0 to EL1 and jumps to the kernel's exception vector. Nothing in user space can stop or skip this.
  3. The kernel saves the app's state. All user registers are stored on the task's kernel stack (a structure called pt_regs) so the app can resume later exactly where it was.
  4. Dispatch. The kernel looks up entry 63 in its system call table → ksys_read() → vfs_read(). The VFS (Virtual File System) layer finds the open file for fd 3. Because it is a device node, the file's operation table points at our driver's acme_read().
  5. The driver may sleep. If no samples are ready, the driver puts the task to sleep on a wait queue. The CPU runs other programs meanwhile. This is legal because we are in process context: running on behalf of the app.
  6. An interrupt wakes it. The ADC's FIFO fills, it raises interrupt SPI 61, the interrupt handler copies samples into a software buffer and wakes the sleeping task.
  7. Copy to the app. The driver calls copy_to_user(buf, kernel_samples, 64). It must use this special function, never memcpy, because buf is an untrusted user address: it could be invalid or point into the kernel. copy_to_user checks it and turns a bad address into an error (-EFAULT) instead of a crash.
  8. Return. The driver returns 64. The kernel puts 64 in x0, restores the user registers and executes eret back to EL0. In the app, n is 64.
One system call round trip on a Cortex-A53 at 1.2 GHz ≈ 0.3–1 µs (a few hundred to ~1,000 cycles) Errors come back negative: the driver returns −14 (−EFAULT); libc turns it into return value −1 and sets errno = 14 ("Bad address")

3. Virtual addresses: the same number, different memory

On 32-bit ARM Linux, the 4 GB of virtual addresses are split 3G/1G: 0x0000_0000–0xBFFF_FFFF belongs to the current app, 0xC000_0000–0xFFFF_FFFF to the kernel (this boundary is called PAGE_OFFSET). On the STM32MP1 DDR also starts at physical 0xC000_0000, which is a coincidence that confuses many people: on TI AM335x, DDR is at physical 0x8000_0000, and the kernel sitting at physical 0x8000_8000 runs at virtual 0xC000_8000.

AM335x: virtual = physical − PHYS_OFFSET + PAGE_OFFSET 0x8000_8000 − 0x8000_0000 + 0xC000_0000 = 0xC000_8000

User programs run at EL0 and can only see their own virtual memory; the kernel runs at EL1. A read() on a device node goes libc → svc #0 with the syscall number in x8 → the kernel saves registers → vfs_read → the driver's read function, which may sleep in process context, and copies data out with copy_to_user because user pointers are untrusted. The return value goes back in x0 and errors come back as negative errno values.

PART 5 / 7

How the kernel finds hardware: device tree → driver → /dev node

A PC discovers its hardware: a PCI or USB device reports "I am vendor 0x8086, device 0x1533". On-chip peripherals of an ARM SoC cannot do that; they just sit at fixed addresses. So someone has to tell the kernel what exists. That is the device tree.

1. The description

The board's device tree contains a node for our ADC:

adc@4c004000 {
	compatible = "acme,adc-v2", "acme,adc";      /* "what am I?"  most specific first */
	reg = <0x4c004000 0x400>;                     /* registers: start, length          */
	interrupts = <GIC_SPI 61 IRQ_TYPE_LEVEL_HIGH>; /* which interrupt line              */
	clocks = <&rcc ADC12_K>;                      /* which clock feeds it              */
	status = "okay";                               /* create a device for this node     */
};
CodeMeaning
adc@4c004000Node name: a generic name plus "@" plus the first register address (the "unit address").
compatibleThe identity strings. A driver will be chosen by comparing these strings, letter by letter, with the strings the driver lists.
reg = <0x4c004000 0x400>The register block starts at physical 0x4C00_4000 and is 0x400 = 1,024 bytes long, so it ends at 0x4C00_43FF.
interruptsThree numbers for the GIC: type SPI ("Shared Peripheral Interrupt"), number 61, level-triggered active high.
clocksA reference (a phandle) to the clock controller node rcc, clock number ADC12_K.

2. From node to running driver, step by step

  1. Device creation. At boot, the kernel walks the tree and creates a platform device named 4c004000.adc for this enabled node, turning reg and interrupts into "resources".
  2. Driver registration. Our driver (built in or loaded as a module) registers a table of strings it supports: "acme,adc-v2" and "acme,adc".
  3. Matching. The platform bus compares the node's compatible strings with the driver's table, exactly and case-sensitively. "acme,adc-v2" = "acme,adc-v2" → match.
  4. probe() is called. The driver maps the registers, gets the clock, asks for its interrupt number and registers its interrupt handler.
  5. User interface. Probe creates a character device; the kernel and the helper daemon udev create the file /dev/acme_adc0.

3. Worked example: the interrupt number changes twice

A classic interview trap: "the DT says 61, so request_irq(61)?" No. The number is translated twice:

DT says: GIC_SPI 61 GIC numbers: IDs 0–15 are SGIs (software), 16–31 PPIs (per-CPU), SPIs start at 32 GIC hardware ID = 61 + 32 = 93 ← shown as "GIC-0 93 Level" in /proc/interrupts Linux maps hardware IDs to its own small numbers ("virq") through an irq domain platform_get_irq() returns e.g. 47 ← the number you pass to request_irq() Char device number: dynamic major 241 (picked by the kernel), minor 0 (first instance) dev_t = (241 << 20) | 0 = 0x0F10_0000 ; ls -l shows "241, 0"

You can check every one of these from a shell on the board: grep acme /proc/interrupts shows 47: … GIC-0 93 Level 4c004000.adc; grep 4c004000 /proc/iomem shows 4c004000-4c0043ff : 4c004000.adc.

4. What goes wrong if…

THE COMPATIBLE STRING HAS A TYPO

Node says "acme,adc-v2", driver says "acme,adc_v2". Symptom: the module loads without error, but probe never runs, no /dev node appears, and nothing is printed. The device exists in /sys/bus/platform/devices/ but has no driver link. Matching is a plain string compare, so one character is enough to break it.

ARM SoC peripherals cannot be discovered, so the device tree describes them as data: compatible, reg, interrupts, clocks, status. The kernel creates a device per enabled node, the bus matches the compatible strings exactly against each driver's of_match_table, and on a match calls probe, which maps the registers, gets the IRQ as a Linux virq rather than the DT number, and creates the user interface such as a /dev node.

PART 6 / 7

Interrupts and "context": why some code must never sleep

"Sleeping" in the kernel means "give the CPU away and come back later", for example while waiting for an I²C transfer or a lock. Some kernel code is allowed to sleep, some must never. Knowing which is which is the single most tested driver skill.

1. Two kinds of "where am I"

Process context
The kernel is running on behalf of a task: inside a system call (our acme_read()), in probe(), in a kernel thread. There is a task to put to sleep and wake later, so sleeping is allowed.
Interrupt (atomic) context
The kernel is running because hardware interrupted whatever was running. The interrupted task has nothing to do with this work, interrupts are disabled on this CPU, and there is no "self" to put to sleep. If the handler sleeps, the kernel prints BUG: scheduling while atomic or deadlocks.

2. Worked example: why an I²C sensor cannot be read in the interrupt handler

A TMP117 temperature sensor pulls a GPIO line low when a new reading is ready. We want to read its 16-bit temperature register over I²C at 400 kHz. How long does that take?

One I²C register read = START + address byte + register byte + repeated START + address byte + 2 data bytes + STOP Each byte = 8 data bits + 1 ACK bit = 9 bit-times write part: 2 bytes × 9 = 18 ; read part: 3 bytes × 9 = 27 ; START/Sr/STOP ≈ 2 total ≈ 47 bit-times At 400 kHz one bit-time = 1 / 400,000 s = 2.5 µs 47 × 2.5 µs ≈ 118 µs (plus driver overhead → typically 150–300 µs)

Two problems: 118 µs with interrupts off is far too long (a hard interrupt handler should take a few µs), and the I²C driver waits for its own "transfer complete" interrupt by sleeping. So the read must happen in a context that may sleep. The kernel's answer is a threaded interrupt:

  1. The GPIO edge arrives. A tiny "hard" handler runs with interrupts off: it records a timestamp and returns IRQ_WAKE_THREAD. Time: ~1 µs.
  2. The kernel keeps that interrupt line masked (flag IRQF_ONESHOT) so it does not fire again.
  3. A dedicated kernel thread named irq/47-tmp117 wakes up. It is process context, so it can do the 150 µs I²C read, take mutexes, even allocate memory.
  4. The thread returns IRQ_HANDLED; the kernel unmasks the line, ready for the next reading.

3. Locks follow the same rule

LockHow it waitsWhere you can use it
mutexSleeps until freeProcess context only (syscalls, probe, threads)
spinlockSpins in a loop until free; holder must not sleepAnywhere, including interrupt handlers. Use spin_lock_irqsave() in process context when an interrupt handler takes the same lock.
WHAT GOES WRONG IF YOU TAKE A MUTEX IN THE INTERRUPT HANDLER

Symptom on the console: BUG: sleeping function called from invalid context … in_atomic(): 1 with mutex_lock and your handler in the stack trace. If the mutex happens to be held by the very task the interrupt preempted, that task can never run again to release it: the CPU is stuck forever. This is Scenario 01 in the Scenario Simulator.

Kernel code runs either in process context, on behalf of a task, where it may sleep, or in atomic context such as a hard interrupt handler or while holding a spinlock, where it must not. Anything that can block, like an I²C transfer, a mutex or GFP_KERNEL allocation, belongs in process context, so for a slow bus device I use a threaded IRQ with IRQF_ONESHOT and keep the hard handler to a few microseconds.

PART 7 / 7

Building, shipping and updating — and how all the pieces connect

Nobody types gcc for 300 programs by hand. A build system produces the whole SD-card image; an update system replaces it safely in the field; secure boot makes sure only your images run.

1. Building the image

  1. Toolchain. A cross compiler such as arm-ostl-linux-gnueabi-gcc (32-bit ARM, Linux, hard-float) runs on your PC and produces ARM binaries. Using arm-none-eabi-gcc (the MCU compiler) for a Linux program is wrong: it has no Linux C library.
  2. Build system. Yocto (used by ST's "OpenSTLinux" BSP) or Buildroot fetches source code for TF-A, U-Boot, the kernel, BusyBox/systemd and your apps, compiles everything with that toolchain, and assembles partitions.
  3. Output. An image with a partition table: fsbl1, fsbl2 (two copies of TF-A), fip (OP-TEE + U-Boot), u-boot-env, bootfs (kernel, DTB), rootfs, userfs.

2. Updating in the field without bricking

If power fails while you overwrite the only kernel, the device is dead. The standard design is A/B: two copies of the root filesystem (slot A and slot B). The device runs from A while the updater writes B. Then it tells U-Boot "try B next boot" and sets a boot counter. If B fails to boot three times before Linux confirms "B is healthy", U-Boot automatically goes back to A.

Storage cost: rootfs 300 MB → A + B = 600 MB, plus a shared data partition eMMC 4 GB: 2 × 300 MB = 600 MB = 15 % of the device → acceptable for most products

3. Trust: secure boot in one paragraph

The hash of your public key is burned into one-time-programmable fuses in the SoC. The BootROM checks the signature on TF-A; TF-A checks OP-TEE and U-Boot; U-Boot checks a signed kernel+DTB package (a FIT image); the kernel checks the root filesystem block by block (dm-verity). One broken link and the chain is worthless, so you also lock the U-Boot console and its settings.

01BEGINNER

MCU vs MPU / application SoC

▶

A microcontroller (MCU) runs one program straight out of its own Flash; an application processor (an "SoC" with Cortex-A cores) runs a full operating system with many isolated programs, and to do that it needs an MMU and lots of external memory. This card explains exactly what differs and why Linux cares.

1. What is it?

MCU
Microcontroller Unit. CPU + Flash + SRAM + peripherals on one chip. Example: STM32F407, Cortex-M4 at 168 MHz, 1 MB Flash, 192 KB SRAM. Code executes in place (XIP = "eXecute In Place") from internal Flash.
MPU (1)
Memory Protection Unit: hardware in a Cortex-M that can mark up to 8 address regions as read-only, no-execute or privileged-only. It checks addresses, it does not translate them.
MPU (2)
"Microprocessor Unit", the marketing name for application processors. Same three letters as above: say "application processor" or "Cortex-A SoC" in an interview to avoid confusion.
MMU
Memory Management Unit: translates every virtual address the program uses into a physical address using page tables in RAM, and enforces permissions per 4 KB page. A small cache of recent translations is the TLB (Translation Lookaside Buffer).
SoC
System-on-Chip. Example: STM32MP157: 2 × Cortex-A7 at 650–800 MHz with MMU, L1 32 KB I + 32 KB D per core, 256 KB L2, a Cortex-M4 at 209 MHz, 256 KB SYSRAM, no user Flash, external DDR3/DDR3L up to 1 GB.
GIC
Generic Interrupt Controller: the Cortex-A equivalent of the NVIC.

2. How does the MMU work, step by step?

Every load or store the CPU issues goes through these steps (32-bit ARMv7 short-descriptor format, 4 KB pages, which the Cortex-A7 uses):

  1. The CPU produces a virtual address (VA), e.g. 0x0001_2345.
  2. The MMU first looks in the TLB. If the translation for page 0x00012 is cached (a "TLB hit"), it takes 0 extra cycles.
  3. On a miss, the hardware table walk starts: bits VA[31:20] index the first-level table (base address in register TTBR0), giving the address of a second-level table.
  4. Bits VA[19:12] index the second-level table, giving the physical page base and permission bits (user/kernel, read-only, execute-never).
  5. If the entry is invalid or the permissions forbid the access, the CPU raises an exception (a page fault); the kernel decides whether to map a page (normal) or kill the program ("Segmentation fault").
  6. Otherwise physical address = page base + VA[11:0], and the TLB caches the result.

3. Worked example

VA = 0x0001_2345 VA[31:20] = 0x000 → first-level entry #0 VA[19:12] = 0x12 → second-level entry #18 VA[11:0] = 0x345 → offset inside the 4 KB page (0x345 = 837 bytes) If entry #18 says "physical page 0xC3A5_7000, user read/write": PA = 0xC3A5_7000 + 0x345 = 0xC3A5_7345 Process A and process B can both use VA 0x0001_2345: each has its own tables (TTBR0 is reloaded on every context switch), so they reach different physical pages.

This is what Linux builds on: separate address spaces per process, fork() with copy-on-write (both processes share pages read-only until one writes), demand paging (memory is mapped only when first touched) and mmap(). A Cortex-M has none of it. A "nommu" Linux (formerly uClinux) exists for Cortex-M7 and some RISC-V parts, but without isolation and without fork(), so it is rare in products.

5. What goes wrong if…

…YOU PUT THE 1 KHZ CONTROL LOOP IN A LINUX THREAD WITHOUT RT

Symptom: the loop runs at 1000 ± 20 µs for hours, then occasionally a cycle takes 3 ms during network or storage traffic and the motor drive trips. Why: a stock kernel has non-preemptible sections (softirqs, spinlock-held regions) that can last milliseconds. The fix is PREEMPT_RT plus core isolation (card 19), or running the loop on the M4 where interrupt latency is a fixed 71 ns.

"An MPU is a microprocessor and an MPU is a memory protection unit, they are the same thing." The acronym collides. Say "application processor" or "Cortex-A SoC" to avoid ambiguity, and know that a Cortex-M MPU gives protection without translation.
Linux needs an MMU because its whole process model relies on it: isolated address spaces, fork() with copy-on-write, demand paging, mmap(). A "nommu" Linux (formerly uClinux) exists for Cortex-M7/RISC-V, but without process isolation and with no fork(), so it is rare in products.

An MCU executes in place from internal Flash, has only a protection unit and reaches main() in under a millisecond; an application processor like the STM32MP157 has Cortex-A cores with an MMU, caches and a GIC, but its RAM and storage are external, so it boots through a chain of loaders. Linux needs the MMU for per-process virtual memory, fork and demand paging. In real products I often split the work: Linux on the A-cores for networking, UI and OTA, and the hard real-time loop on the companion Cortex-M4, loaded by remoteproc and reached through RPMsg.

02BEGINNER

The boot chain: why there are so many stages

▶

When an application processor comes out of reset it can use only a tiny ROM and a small on-chip RAM. Loading Linux therefore happens in a relay of programs, each one setting up enough hardware for the next, bigger one. That relay is the boot chain.

1. What is it?

The one fact that explains the whole chain: external DDR is not usable until its controller and PHY are configured and trained for this specific board's memory chips and trace lengths. The ROM is fixed at the factory and cannot know those values, so it loads a small customer-built program that does. Every stage is as large as the memory it is allowed to run in.

PHY
The analog "physical layer" circuit that drives and samples the DDR signals.
Training
An automatic calibration where the controller sweeps delays on each data line and picks the middle of the window where data is read correctly.
TF-A
Trusted Firmware-A, ARM's reference boot firmware. Its stages are called BL1, BL2, BL31, BL32, BL33 ("Boot Loader" stage numbers).
SPL
Secondary Program Loader: a cut-down U-Boot built from the same source tree, used as second stage on many 32-bit SoCs (called MLO on TI).
EL3
Exception Level 3, the most privileged ARMv8 level, where the "secure monitor" lives.

A hang right after the SPL banner points me at DDR first.

Boot media and boot pins

▶

The BootROM has to decide which storage chip to read the second stage from. It decides by reading a few pins, wired high or low with resistors on the board, the moment reset is released.

1. What is it?

Boot pins
BOOT[2:0] on STM32MP1, SYSBOOT[15:0] on TI AM335x, BOOT_MODE + eFuses on NXP i.MX. Sampled once at reset.
OTP / eFuse
One-Time-Programmable bits in the SoC. Once a product is "locked", fuses can override the pins so nobody can boot from an SD card.
eMMC
Embedded MultiMediaCard: NAND flash plus a controller in one BGA package. It has two small hardware boot partitions (boot0/boot1, often 4 MB each), a big user area and an RPMB (Replay Protected Memory Block) for secrets.
Serial download
A fallback in the ROM: if no medium works it waits for an image over USB or UART (STM32CubeProgrammer USB DFU, NXP uuu over SDP, TI UART/USB RNDIS). Used for factory flashing and unbricking.

2. How does it work, step by step?

  1. PMIC releases reset; the ROM starts.
  2. ROM reads BOOT[2:0] (or fuses, if programmed). STM32MP15 table (from ST's boot-mode documentation): 000 UART/USB, 001 QSPI NOR, 010 eMMC, 011 FMC NAND, 100 no boot (development), 101 SD card, 110 UART/USB, 111 QSPI NAND.
  3. ROM initialises that controller in a slow, safe mode (e.g. SD at 400 kHz identification, then a modest speed).
  4. ROM finds the image: on STM32MP1 a GPT partition named fsbl1; on AM335x a file called MLO in the first FAT partition or raw copies at fixed offsets.
  5. ROM checks the image header (and signature on secure parts). If it fails, it tries the backup copy (fsbl2), then the next device in its list, and finally serial download.

Kernel space vs user space, and system calls

▶

Your program and the kernel run at different CPU privilege levels. A program cannot call kernel functions directly; it executes a special trap instruction, the system call, and the CPU switches into the kernel at a fixed entry point.

1. What is it?

EL0 / USR
Unprivileged level for user processes (ARMv8 "Exception Level 0"; ARMv7 "User mode"). Only its own virtual memory is mapped.
EL1 / SVC
Privileged level for the kernel: all memory, MMIO, system registers.
System call
A numbered kernel service (read = 63 on arm64) entered with a trap instruction. The only legal door between EL0 and EL1.
errno
The thread-local error code libc sets when a syscall fails. The kernel returns -errno (e.g. −14 = −EFAULT); libc returns −1 and stores 14 in errno.
vDSO
"virtual Dynamic Shared Object": a small library the kernel maps into every process so calls like clock_gettime() run without a trap.

2. How does it work, step by step?

  1. libc loads the arguments into registers and the syscall number into the "number" register (table below).
  2. The trap instruction (svc #0) raises a synchronous exception. Hardware switches to EL1, saves the return address (ELR_EL1) and status (SPSR_EL1), and jumps to the vector table (VBAR_EL1).
  3. Kernel entry code (el0_svc) saves all user registers into pt_regs on the task's kernel stack.
  4. invoke_syscall() checks the number, indexes sys_call_table and calls e.g. __arm64_sys_read.
  5. On the way out the kernel checks for pending signals and whether to reschedule, puts the result in x0, restores registers and executes eret back to EL0.

…AN APP TRIES TO WRITE A REGISTER DIRECTLY

Why can't a driver just be a normal program? It can, for some devices (spidev, UIO, libgpiod), but user space cannot take interrupts directly, cannot run in atomic context, cannot program a DMA controller safely (it does not know physical addresses and could DMA over the kernel), and can be preempted or killed at any time. Anything that must be shared, timed or secured belongs in the kernel.

User processes run at EL0 in their own virtual address space and the kernel at EL1. On arm64 libc puts the syscall number in x8 and arguments in x0 to x5 and executes svc #0; the exception enters el0_svc, registers are saved in pt_regs, invoke_syscall dispatches through sys_call_table, and the return value comes back in x0, negative errno on failure, which libc turns into -1 and errno. Hot calls like clock_gettime avoid the trap through the vDSO.

Kernel modules: build, load, license

▶

A kernel module is a piece of kernel code (usually a driver) compiled into a separate .ko file that can be inserted into the running kernel and removed again, without rebooting or rebuilding the kernel image.

1. What is it?

.ko
"Kernel object": an ELF relocatable file with extra sections: .modinfo (license, author, aliases, vermagic), __versions (symbol CRCs), init and exit code.
Kbuild
The kernel's build system. An out-of-tree module is built by calling the kernel's own Makefile with M=$(PWD).
Symbol export
A kernel function is callable from modules only if exported with EXPORT_SYMBOL() (any module) or EXPORT_SYMBOL_GPL() (GPL-compatible modules only).
vermagic
A string such as 6.6.48 SMP preempt mod_unload aarch64; the module must match the running kernel's.
Taint
Flags the kernel records when something unusual was loaded: P proprietary, O out-of-tree, E unsigned. They appear in every oops.

2. How does loading work, step by step?

  1. insmod hello.ko reads the file and calls the finit_module() system call.
  2. The kernel checks the signature if module signing is enforced, then vermagic and symbol CRCs (with CONFIG_MODVERSIONS).
  3. It reads MODULE_LICENSE. Non-GPL → taint, and GPL-only symbols become invisible to this module.
  4. It allocates memory, copies sections, resolves every undefined symbol against the kernel and loaded modules, applies relocations.
  5. It creates /sys/module/hello/ (with parameters/), then calls the function registered with module_init(). If it returns non-zero the load fails and everything is undone.

U-Boot: environment, bootcmd, FIT and kernel image formats
▶


U-Boot is the bootloader that runs after DDR works. It is a small operating system of its own, with drivers, a shell and stored settings; its single job in a product is to load the kernel and its device tree into RAM, prepare them, and jump.


1. What is it?




Environment
U-Boot's settings: a list of name=value strings protected by a CRC32, stored in a raw area of eMMC/SD, a file (uboot.env), SPI NOR or UBI.


bootcmd
The environment variable U-Boot executes as a script when the bootdelay countdown ends.


bootargs
The kernel command line (console=, root=, rootwait…); U-Boot writes it into the DTB's /chosen node.


distro boot / bootstd
A standard script that scans boot targets for extlinux.conf or boot.scr, so one U-Boot works with many OS images.


FIT
Flattened Image Tree: one file (.itb) in device-tree format that contains kernel, DTBs, initramfs, with hashes and signatures.




2. How does it work, step by step?


    

  1. U-Boot proper starts in DDR (0xC010_0000 on STM32MP1) and relocates itself to the top of RAM (0xDDB4_8000, just below OP-TEE) so the low area is free for the kernel.
    2. 

  2. Starts its driver model from its own control device tree: MMC, Ethernet, USB, console.
    3. 

  3. Loads the environment and checks its CRC; on failure prints *** Warning - bad CRC, using default environment and uses the compiled-in default.
    4. 

  4. Counts down bootdelay; any key stops at the prompt.
    5. 

  5. Runs bootcmd: loads kernel, DTB, initramfs from storage into DDR.
    6. 

  6. Verifies the image (CRC for uImage, hashes/signatures for FIT), patches the DTB, cleans/disables caches and MMU, and jumps.
    7.

Device tree: DTS, DTSI, DTB, bindings, overlays
▶


The device tree is a text description of the board's hardware that is compiled into a small binary and handed to the kernel at boot. It lets one kernel binary run on many different boards: only the description changes.


1. What is it?


ARM SoCs have no enumerable bus for on-chip peripherals (unlike PCI/USB), so something must tell the kernel what exists, where, and how it is wired. The device tree is that description, data, not code.


  • .dtsi: shared include, typically the SoC (stm32mp151.dtsi): every peripheral with status = "disabled".
    • 

  • .dts: the board (stm32mp157c-dk2.dts): includes the dtsi, enables what is populated (&i2c4 { status = "okay"; ... }), adds external chips, pinmux.
    • 

  • dtc compiles to .dtb (Flattened Device Tree, big-endian, magic 0xD00DFEED). The C preprocessor runs first so #include <dt-bindings/interrupt-controller/arm-gic.h> and macros work.
    • 

  • Bindings (Documentation/devicetree/bindings/**.yaml) are the schema: required properties and their meaning. make dtbs_check validates your DTS against them.


2. How does it work, step by step?


    

  1. Write: SoC vendor's .dtsi + your board .dts.
    2. 

  2. Preprocess and compile: cpp expands macros like GIC_SPI = 0 and IRQ_TYPE_LEVEL_HIGH = 4; dtc produces the binary .dtb (~90 KB on MP1).
    3. 

  3. Load: U-Boot loads the DTB to RAM, fixes it up (/chosen, /memory) and passes its address.
    4. 

  4. Unflatten: early in boot the kernel converts the blob into a tree of struct device_node.
    5. 

  5. Populate: of_platform_populate() creates a device for each enabled node under a simple bus; bus controllers create their own children when they probe.
    6. 

  6. Match and probe: drivers are bound by compatible string (card 9).
    7.

The device tree describes non-discoverable hardware as data: a SoC .dtsi with everything disabled, a board .dts that enables and wires things, compiled by dtc into a DTB the bootloader passes to the kernel. Drivers bind by an exact compatible string match, and a disabled node or a disabled parent bus means no device at all.

Virtual memory: per-process address spaces
▶


Every Linux process believes it has a huge private memory starting near address zero. The MMU and the kernel's page tables create that illusion, mapping each process's virtual pages onto scattered physical pages, and only when they are actually used.


1. What is it?




Page
The unit of mapping, 4 KB (4,096 bytes) by default on ARM.


Page table
Tree of tables in RAM that maps virtual pages to physical pages; one per process (mm_struct->pgd).


TTBR0 / TTBR1
Translation Table Base Registers. On arm64 TTBR0_EL1 translates the lower half (user, switched at each context switch, tagged with an ASID = Address Space ID so the TLB need not be flushed) and TTBR1_EL1 the upper half (kernel, shared by all).


Page fault
Exception when a virtual page has no valid mapping or wrong permissions; the kernel handles it (allocate, read from file, copy-on-write) or sends SIGSEGV.


RSS
Resident Set Size: physical memory actually used by a process.




2. How does it work, step by step? (arm64, 4 KB pages, 48-bit VA)


With 4 KB pages and 48-bit VA: user 0x0000_0000_0000_0000–0x0000_FFFF_FFFF_FFFF (248 = 256 TB), kernel 0xFFFF_0000_0000_0000 upwards. The walk uses four levels, 9 bits each:


    

  1. VA bits [47:39] index the level-0 table (512 entries) found through TTBR0_EL1.
    2. 

  2. Bits [38:30] index level 1, bits [29:21] level 2, bits [20:12] level 3.
    3. 

  3. The level-3 entry gives the physical page address and permissions (user/kernel, read-only, execute-never).
    4. 

  4. Bits [11:0] are the offset in the page.
    5. 



VA = 0x0000_FFFF_D2A3_C5E0   (a user stack address from the oops in card 20)
  L0 index = VA[47:39] = 0x1FF (511)
  L1 index = VA[38:30] = 0x1FF (511)
  L2 index = VA[29:21] = 0x095 (149)
  L3 index = VA[20:12] = 0x03C (60)
  offset   = VA[11:0]  = 0x5E0 (1,504)
4 levels × 512 entries × 8 bytes = each table is exactly one 4 KB page


3. Worked example: demand paging and lowmem


malloc(100 MB) on a 512 MB board:
  100 MB / 4 KB = 25,600 pages reserved as VIRTUAL space only → RSS barely changes
  memset(p, 0, 100 MB) → 25,600 page faults → RSS +100 MB
  mlockall(MCL_CURRENT|MCL_FUTURE) → faults everything in now and pins it (RT tasks)

32-bit ARM, 3G/1G split: kernel virtual space = 0xC000_0000–0xFFFF_FFFF = 1 GB
  minus vmalloc area + fixmaps (≈ 240 MB default)  → direct-mapped "lowmem" ≈ 760 MB
  a board with 1 GB DDR: 1024 − 760 = 264 MB is "highmem", mapped temporarily with kmap()


On 32-bit ARM the default split is 3G/1G: user below PAGE_OFFSET = 0xC000_0000, kernel above it. On STM32MP1 DDR physically starts at 0xC000_0000 too, a coincidence that confuses people: physical 0xC000_0000 ≠ kernel virtual 0xC000_0000 in general, they just happen to be equal there.


  • Demand paging: malloc(100 MB) only reserves virtual space. Physical pages arrive on first touch (page fault). mlockall(MCL_CURRENT|MCL_FUTURE) pre-faults and pins: essential for real-time tasks.
    • 

  • Copy-on-write: fork() shares pages read-only; the first write faults and copies.
    • 

  • Overcommit and the OOM killer: embedded systems usually have no swap; when RAM is exhausted the OOM killer picks a victim by oom_score. Protect critical daemons with oom_score_adj=-1000.
    • 

  • Kernel ↔ user isolation: the kernel must never dereference a user pointer directly. ARMv8.1 PAN (Privileged Access Never) makes such a dereference fault; copy_to_user() temporarily lifts PAN and has an exception-table fixup so a bad user address returns -EFAULT instead of an oops.
    • 

  • Useful views: /proc/<pid>/maps, /proc/<pid>/smaps (RSS, PSS per mapping), /proc/meminfo, /proc/vmallocinfo, /proc/iomem (physical map with claimed regions).

The Linux driver model: bus, device, driver, probe, devm
▶


Linux separates "a piece of hardware exists" (a device) from "code that knows how to drive it" (a driver), and lets a bus introduce them to each other. When they match, the kernel calls the driver's probe() function with that device.


1. What is it?


Three objects: a bus (struct bus_type: platform, i2c, spi, usb, pci) owns a match() function; a device (struct device, embedded in platform_device, i2c_client, ...) describes one instance of hardware; a driver (struct device_driver, embedded in platform_driver, i2c_driver) knows how to run it. Whenever either side is registered the core tries to pair them; on a match it calls probe(). remove() is called on unbind, module unload or device removal.




Platform device
A device at a fixed address on the SoC's internal interconnect (UART, timer, the I²C controller itself). Comes from DT nodes under a simple-bus.


devm_*
"Device-managed" resource functions: the resource is recorded on the device and released automatically.


-EPROBE_DEFER
Error code (−517) meaning "a resource I need is not ready yet, try me again later".


fw_devlink
Kernel feature (5.x+) that reads phandles in the DT to learn supplier→consumer links and orders probing accordingly.




2. How does binding work, step by step?


    

  1. A device is registered (e.g. by of_platform_populate()) or a driver is registered (platform_driver_register()).
    2. 

  2. The driver core iterates over the other side on the same bus and calls bus->match(dev, drv); for DT devices this compares compatible strings.
    3. 

  3. On a match, really_probe() links the device to the driver, applies the pinctrl "default" state, then calls drv->probe(dev).
    4. 

  4. Probe returns 0 → bound (sysfs gets a driver symlink). Returns -EPROBE_DEFER → put on the deferred list and retried after any other driver binds. Any other error → not bound; devm resources acquired so far are freed.
    5. 

  5. Unbind (rmmod, echo dev > …/unbind, hot-unplug) → remove(), then devm releases everything in reverse order.
    6.

4. Worked example: devm release order


probe acquires, in order:     1 kzalloc   2 ioremap   3 clk enable   4 request_irq
probe fails at step 4  →  devm releases:  3 clk disable/put → 2 iounmap → 1 kfree
normal unbind: remove() runs FIRST, then devm releases 4 free_irq → 3 → 2 → 1
  ⇒ between remove() returning and free_irq, the IRQ handler can still run!


  • Platform devices are for things that live at a fixed address on the SoC's internal interconnect (UART, timers, the I²C controller itself). They come from DT nodes under a simple-bus.
    • 

  • Deferred probe: if a resource is not ready yet (clock/regulator/GPIO provider not probed), the getter returns -EPROBE_DEFER. Return it unchanged; the core retries after other drivers bind. Use dev_err_probe(): it logs real errors but stays quiet for deferral and records the reason in /sys/kernel/debug/devices_deferred.
    • 

  • devm_* managed resources are attached to the device and freed automatically, in reverse order of acquisition, when probe fails or after remove() returns. They remove the classic error-path goto ladder and its leaks.
    • 

  • devm pitfalls: (1) a devm_request_irq handler stays live until after remove(), so if remove() frees something the handler uses, the IRQ can fire into freed state: disable the device's interrupt in remove() or order resources carefully. (2) Memory from devm_kzalloc is freed on unbind even if user space still has the char device open: refcount the state and tie it to file lifetime.
    • 

  • Sysfs map of the model: /sys/bus/platform/devices/, /sys/bus/platform/drivers/<drv>/ (with bind/unbind files), /sys/devices/platform/soc/..., each device's driver symlink and of_node.


5. What goes wrong if…


WRONG
clk = devm_clk_get(dev, NULL);
if (IS_ERR(clk)) {
	dev_err(dev, "no clock\n");
	return -ENODEV;     /* swallows -EPROBE_DEFER */
}
If the clock driver probes after this one, the device fails permanently, with a scary error in the log on every boot.
RIGHT

	return dev_err_probe(dev, PTR_ERR(clk),
			     "no clock\n");
Deferral propagates; the core retries; the log stays clean; the reason appears in devices_deferred.


Why split device and driver? One driver serves N instances (four UARTs, one driver); a device can exist without its driver (module not loaded yet); and the same driver code works whether the device came from DT, ACPI or a board file.


The driver model has buses, devices and drivers; registering either side makes the bus's match function compare them, for DT by compatible string, and a match calls probe after pinctrl's default state is applied. Probe acquires resources with devm helpers, which are released in reverse order when probe fails or after remove, and it must propagate -EPROBE_DEFER, ideally through dev_err_probe. The two devm traps are an IRQ that outlives remove and devm memory freed while user space still holds the device open.

A character device is the simplest way for a driver to offer an interface to programs: a file in /dev that you open(), read(), write() and ioctl(), where each of those calls lands in a function of your driver.


1. What is it?


A character device is a byte stream reached through a node such as /dev/acme0. The node carries a dev_t: 12-bit major (which driver) and 20-bit minor (which instance). MAJOR(), MINOR(), MKDEV() convert. The kernel looks up the cdev registered for that dev_t and installs its file_operations in the struct file at open().




cdev
Kernel object linking a dev_t range to a file_operations table.


file_operations
Table of function pointers: .open .read .write .unlocked_ioctl .poll .release.


ioctl
"I/O control": a syscall carrying a command number and one argument (usually a pointer to a struct) for operations that are not plain reads/writes.


misc device
Shortcut for drivers with one node: major 10, dynamic minor, one registration call.




2. How does registration work, step by step?


  1. alloc_chrdev_region(&devt, 0, n, "acme") — dynamic major (do not hard-code one).
    2. 

  2. cdev_init(&cdev, &fops); cdev_add(&cdev, devt, n) — the device is live from this moment: be fully initialised first.
    3. 

  3. class_create("acme") (one argument since 6.4; older kernels take THIS_MODULE first) + device_create(cls, parent, devt, NULL, "acme%d", i) — emits a uevent, devtmpfs creates /dev/acme0, udev applies permissions/symlinks.

4. Code, line by line: a correct read()


static ssize_t acme_read(struct file *f, char __user *buf, size_t len, loff_t *ppos)
{
	struct acme *a = f->private_data;          /* set in open()                 */
	u16 tmp[32];
	unsigned int n;

	if (wait_event_interruptible(a->wq, a->count))   /* sleep until data         */
		return -ERESTARTSYS;                     /* a signal arrived             */
	n = take_samples(a, tmp, min(len / 2, ARRAY_SIZE(tmp)));
	if (copy_to_user(buf, tmp, n * 2))          /* returns bytes NOT copied      */
		return -EFAULT;
	return n * 2;                                /* bytes delivered (may be short) */
}


CodeMeaning


char __user *buf__user marks a user-space address; the static checker sparse flags any direct dereference.


loff_t *pposFile position; update it for seekable devices, ignore for streams.


wait_event_interruptible(wq, cond)Sleeps until cond is true; non-zero return = interrupted by a signal → return -ERESTARTSYS.


copy_to_userCopies to user memory safely; can sleep (page fault), so never under a spinlock.


return n * 2Return bytes transferred; 0 means end-of-file, so a blocking device must not return 0.




READ / WRITE RULES


  • Signature: ssize_t read(struct file *f, char __user *buf, size_t len, loff_t *ppos). Return bytes transferred, 0 for EOF, or -errno. Update *ppos if the device is seekable.
    • 

  • copy_to_user(dst, src, n) / copy_from_user() return the number of bytes not copied. Non-zero → return -EFAULT. They can sleep (page fault on the user page), so never call them with a spinlock held.
    • 

  • get_user(x, ptr) / put_user(x, ptr) for single scalars. simple_read_from_buffer() handles offset and length clamping for you.
    • 

  • Blocking read: wait_event_interruptible(wq, cond), return -ERESTARTSYS if interrupted; honour O_NONBLOCK with -EAGAIN; implement .poll so select/poll/epoll work.


IOCTL


Command numbers are 32 bits built by _IO(type,nr), _IOR, _IOW, _IOWR(type,nr,datatype): direction (2 bits) | size of the argument (14 bits) | magic type (8 bits) | number (8 bits). Encoding the size means a struct change produces a new number instead of silently mis-parsing. Unknown commands must return -ENOTTY ("inappropriate ioctl for device"), not -EINVAL. .unlocked_ioctl runs without the old Big Kernel Lock, so you lock yourself; .compat_ioctl handles 32-bit user space on a 64-bit kernel (use fixed-width types and no pointers-in-structs to make compat_ptr_ioctl enough).


5. What goes wrong if…


WRONG

	struct stats *u = (void *)arg;
	u->overruns = a->overruns;   /* direct store */
	return 0;
default:
	return -EINVAL;
On arm64 with PAN this oopses ("access to user memory outside uaccess routines"); on older CPUs it is a security hole (a malicious pointer makes the kernel write anywhere). -EINVAL for unknown commands confuses tools that probe ioctls.
RIGHT
case GET_STATS: {
	struct stats st = { };      /* zero padding */
	st.overruns = a->overruns;
	return copy_to_user((void __user *)arg,
		&st, sizeof(st)) ? -EFAULT : 0;
}
default:
	return -ENOTTY;
Kernel copy, zeroed so padding never leaks kernel stack bytes, one copy_to_user, correct errno.


When ioctl vs sysfs? sysfs: one human-readable value per file, configuration and status. ioctl: binary commands, atomic multi-field transactions, performance paths. A third option, a netlink or a dedicated subsystem (IIO, input, hwmon), is usually better than inventing a private ABI.


A char device is a dev_t, 12-bit major and 20-bit minor, reserved with alloc_chrdev_region, connected to a file_operations table by cdev_add, and published in /dev by device_create through devtmpfs and udev. read and write move data with copy_to_user and copy_from_user, which return the bytes not copied and may sleep, return 0 only for EOF, and support O_NONBLOCK and poll. ioctl numbers encode direction, size, type and number, so changing a struct changes the number, and unknown commands return -ENOTTY.

5. What goes wrong if…


…YOU USE gpiod_set_value() ON AN I²C EXPANDER LINE
Symptom: a WARN splat from gpiolib (gpiod_set_value on a chip that can sleep) and, if called in atomic context, "scheduling while atomic". The expander needs an I²C transfer to change the pin. Use _cansleep in process context, or pick a SoC GPIO for anything driven from an interrupt handler.


…YOU PASS A STACK BUFFER TO spi_sync()
Works with PIO, corrupts data (or warns with DMA debug) once the controller uses DMA: stack memory may be vmalloc'd (VMAP_STACK) and shares cache lines with other variables. Use a kmalloc'd buffer or spi_write_then_read().

WHY /dev/mem IS DANGEROUS


  • Races with kernel drivers on the same registers: a read-modify-write of GPIOx_MODER from user space can undo a concurrent change by the pinctrl driver, with no lock in common.
    • 

  • CONFIG_STRICT_DEVMEM blocks RAM; CONFIG_IO_STRICT_DEVMEM also blocks any MMIO range a driver has claimed with request_mem_region(). A kernel update that adds or enables a driver for "your" block turns mmap() into EPERM overnight.
    • 

  • No interrupts, no clock or power management: the block may be clock-gated (reads return 0 or bus-fault) after runtime PM suspends it.
    • 

  • Security: root with /dev/mem can patch the kernel. Locked-down / secure-boot kernels disable it.

Interrupts in Linux: top half, threaded IRQs, bottom halves
▶


When a peripheral raises an interrupt, Linux runs your handler immediately with interrupts disabled on that CPU. Because that blocks everything else, the handler must be tiny; any slow work is handed to a "bottom half" that runs later, in a context where it is allowed to take its time or even sleep.


1. What is it?




Top half
The hard IRQ handler you pass to request_irq(). Hardirq context: atomic, local IRQs off.


Bottom half
Deferred work: threaded IRQ handler, workqueue, softirq, tasklet, timer.


virq
Linux's interrupt number, mapped from the controller's hardware number (hwirq) by an irq domain.


preempt_count
Per-task counter whose bit fields record "in hard IRQ", "in softirq", "preemption disabled". Non-zero = atomic.




2. How does interrupt entry work, step by step?


    

  1. The ADC asserts its line; the GIC signals the CPU (IRQ exception).
    2. 

  2. Arch entry code saves registers and calls the GIC driver's handler, which reads the IAR (Interrupt Acknowledge Register) to get hwirq 93.
    3. 

  3. generic_handle_domain_irq() maps hwirq 93 → virq 47 and runs the flow handler (level/edge logic).
    4. 

  4. preempt_count += HARDIRQ_OFFSET (0x10000); your handler runs with local interrupts off.
    5. 

  5. Your handler returns IRQ_HANDLED, IRQ_NONE or IRQ_WAKE_THREAD.
    6. 

  6. GIC end-of-interrupt is written; on exit pending softirqs may run; if a higher-priority task was woken, the scheduler switches to it.
    7. 



The GIC raises an exception; the arch code calls generic_handle_domain_irq() which maps the hardware ID to a Linux virq through the irq domain and runs the registered handler with local interrupts disabled and preempt_count incremented by HARDIRQ_OFFSET (0x10000). That is atomic context: no sleeping, keep it short (microseconds).

preempt_count bit fields: [7:0] preempt-disable depth  [15:8] softirq  [19:16] hardirq  [23:20] NMI

    •

5. What goes wrong if…


…A LEVEL-TRIGGERED HANDLER DOES NOT CLEAR THE SOURCE
The handler schedules work to read the sensor (which clears the line) and returns IRQ_HANDLED. The line is still asserted, so the GIC re-delivers immediately, forever: an interrupt storm. Symptom: /proc/interrupts count rising by hundreds of thousands per second, one CPU at 100 % in hardirq (top shows hi), RCU stall warnings, the work never runs on that CPU. Fix: threaded IRQ with IRQF_ONESHOT (Scenario 10).


"A tasklet runs in process context so it can sleep." Tasklets and timers are softirq context. Only threaded handlers and workqueues (and normal process context) may sleep.


A hard IRQ handler runs with local interrupts off and HARDIRQ_OFFSET in preempt_count, so it must not sleep and should only acknowledge the device, timestamp and defer. Work that sleeps, such as an I2C read, goes in a threaded handler with IRQF_ONESHOT so a level line stays masked until the thread finishes, or in a workqueue; softirqs, tasklets and timers are atomic too. Shared handlers must return IRQ_NONE when it is not their device, or the kernel eventually disables the line with nobody cared.

2. How does the IRQ deadlock happen, step by step?


    

  1. CPU0, in acme_read() (process context), calls spin_lock(&fifo_lock): acquired.
    2. 

  2. While it holds the lock, the ADC interrupt arrives on CPU0; the CPU jumps into acme_isr().
    3.

    4. 

  4. The holder is the code the ISR interrupted on the same CPU. It can only continue after the ISR returns. The ISR only returns after the holder unlocks. Deadlock: CPU0 spins forever with interrupts off; the watchdog or a "hard LOCKUP" detector fires.

  5. With spin_lock_irqsave() in step 1, local interrupts are off while the lock is held, so step 2 is postponed until the unlock: no deadlock. An interrupt on CPU1 just spins briefly until CPU0 unlocks.

ioremap
Creates a kernel virtual mapping of a physical MMIO range with Device memory attributes (uncached, no merging or reordering of accesses).

arm64 memory type: non-Gathering, non-Reordering, Early write acknowledgement allowed.

An instruction (dmb, dsb on ARM) that forces earlier memory accesses to be visible before later ones.

A write the interconnect acknowledges before it actually reaches the peripheral.




2. How does it work, step by step?


With the MMU on, the kernel cannot use a physical address such as 0x5C00_2000 directly. ioremap(phys, size) creates a kernel virtual mapping with Device memory attributes (arm64 Device-nGnRE: no gathering, no reordering, early write acknowledgement allowed; uncached). Drivers normally use devm_platform_ioremap_resource(pdev, 0), which also calls request_mem_region() so two drivers cannot claim the same block (second one gets -EBUSY, visible in /proc/iomem).


    

  1. Probe gets the reg resource: [0x4C00_4000, 0x4C00_43FF].
    2. 

  2. request_mem_region() records the claim in /proc/iomem.
    3. 

  3. ioremap() finds free kernel virtual space (e.g. 0xE0A4_C000 on arm32), writes page-table entries with Device attributes, and returns it as void __iomem *base.
    4. 

  4. Register access: readl(base + REG_STATUS) = 32-bit load from virtual 0xE0A4_C004 → physical 0x4C00_4004, with a barrier after it.
    5. 



    

  • The result is void __iomem *. Access it only with accessors: readl(base + OFF), writel(val, base + OFF) (32-bit, little-endian), readw/readb, ioread32/iowrite32. sparse (make C=1) flags direct dereferences.
    • 

  • writel() includes a write barrier before the store, so earlier writes to normal memory (a DMA descriptor) are visible to the device before the doorbell write. readl() includes a barrier after, so later memory reads do not pass the MMIO read (e.g. reading a DMA buffer after a status register says "done").

  • readl_relaxed()/writel_relaxed() omit those barriers: fine for back-to-back register programming of a single device, wrong for DMA handshakes.

Real-time Linux: PREEMPT_RT, latency, cyclictest, isolation
▶


"Real-time" does not mean fast; it means the worst-case delay is bounded and known. A normal Linux kernel has an excellent average but occasional millisecond stalls. PREEMPT_RT plus careful tuning turns that into a guaranteed tens-of-microseconds bound.


1. What is it?


Latency = time from an event (timer expiry, IRQ) until the waiting high-priority thread runs. On a stock kernel the worst case is set by the longest non-preemptible section anywhere in the kernel: a spinlock-held loop in a filesystem or network driver, a long softirq run, an IRQ-off region. Average latency is irrelevant; the tail is what breaks control loops.




Preemption
Stopping the running task to run a higher-priority one. A section is "non-preemptible" if the scheduler cannot switch away (spinlock held, IRQs off, softirq running).


SCHED_FIFO
Real-time scheduling policy: priorities 1–99, the highest runnable FIFO task always runs, no time slicing.


Priority inversion
A high-priority task waits for a lock held by a low-priority task that a medium task keeps preempting. Fixed by priority inheritance (PI).


cyclictest
Standard tool: threads sleep until an absolute time and measure how late they wake.




ModelKconfigPreemptible in kernel?


No forced preemptionPREEMPT_NONEOnly at explicit schedule points (servers)


VoluntaryPREEMPT_VOLUNTARYExtra might_sleep() points


PreemptiblePREEMPTAnywhere except spinlock/IRQ-off/softirq regions


Fully preemptiblePREEMPT_RTAlmost everywhere: spinlocks become PI-aware sleeping locks, IRQ handlers and softirqs run in threads with priorities




2. How does PREEMPT_RT bound latency, step by step?


    

  1. Interrupt handlers become kernel threads (priority 50 by default), so a priority-80 control thread can preempt them.
    2. 

  2. Softirqs (network RX, block completion) also run in threads instead of on IRQ exit.
    3. 

  3. spinlock_t becomes an rt_mutex: sleeping, with priority inheritance, so its holder can be preempted. Only raw_spinlock_t (scheduler, interrupt controller) still spins.
    4. 

  4. Remaining non-preemptible regions are short and bounded, so the worst case becomes tens of µs.
    5. 



PREEMPT_RT was merged into mainline in 6.12 (x86, arm64, RISC-V); before that it was a patch set. Typical cyclictest maxima under load (indicative, hardware dependent): stock PREEMPT on Cortex-A53 several hundred µs to a few ms; PREEMPT_RT 30–100 µs on A53/A7, under 20 µs on modern x86. RT gives bounded latency, not lower average latency, and costs some throughput.


3. Worked example: does a 1 kHz loop meet its deadline?


Loop period 1 ms = 1000 µs; compute time per cycle 300 µs; deadline = end of period
Allowed wake-up latency = 1000 − 300 = 700 µs

PREEMPT_RT + isolation,   Max =   87 µs  →   87 < 700  → margin = 700 − 87 = 613 µs  ✔

  = 95 %: RT tasks are stopped for 50 ms every second if they never sleep (a runaway guard)

Secure boot on Linux SoCs
▶


Secure boot makes a device refuse to run any software you did not sign. It works like a relay of trust: an unchangeable piece of code checks the signature of the next stage before running it, which checks the next, all the way to the files of the root filesystem.


1. What is it?


Goal: only code signed by you runs, from the first instruction to the last binary in the rootfs. Each stage verifies the next before jumping; the anchor is immutable ROM code plus a key hash in one-time-programmable fuses.




Root of trust
Something the attacker cannot change: the mask ROM plus fuses holding the hash of your public key.


Signature
A value computed from an image's hash with your private key (kept in an HSM, Hardware Security Module). Anyone with the public key can verify it; nobody can forge it.


FIT signature
U-Boot's verified boot: hashes and RSA/ECDSA signatures inside a FIT image.


dm-verity
A kernel device-mapper target that checks every block read from the rootfs against a Merkle hash tree whose single root hash is trusted.


Anti-rollback
A monotonic counter (fuses or eMMC RPMB) that stops an attacker installing an older, signed but vulnerable version.




2. How does the chain work, step by step?


  1. Root of trust: hash of your public key(s) burnt into OTP (NXP HAB/AHAB: SRK hash; STM32MP1: PKH in OTP, ECDSA P-256 signature in the STM32 header; TI K3 HS: customer key in eFuse). The ROM verifies the second stage.
    2. 

  2. BL2/SPL verifies the next images: TF-A Trusted Board Boot (X.509 certificate chain in the FIP) or SPL verifying a signed FIT.
    3. 

  3. U-Boot verifies the signed FIT configuration (kernel + DTB + initramfs) against the public key embedded in its own control DTB (CONFIG_FIT_SIGNATURE, required = "conf"). Legacy uImage and raw zImage must be disabled.
    4. 

  4. Kernel verifies modules (CONFIG_MODULE_SIG_FORCE), and the rootfs with dm-verity: a Merkle hash tree whose root hash is in the signed FIT (command line or signed initramfs). Every block read is checked; tampering → I/O error.
    5. 

  5. Close the device: program the "closed/secure" lifecycle fuse (until then failures are only logged, e.g. HAB events), disable JTAG or require authenticated debug, lock the U-Boot console and environment, disable /dev/mem, enable anti-rollback (monotonic counter in fuses or RPMB).


3. Worked example: the numbers


Why store a HASH of the key in fuses?  An ECDSA P-256 public key = 64 bytes, RSA-2048 = 256 bytes;
  fuses are scarce. SHA-256(key) = 32 bytes = 256 bits = 8 OTP words of 32 bits.
  The ROM reads the full key from the image header, hashes it, compares with the fuses.

dm-verity tree for a 300 MB rootfs (4 KB blocks, SHA-256 = 32-byte hashes):
  data blocks      = 300 × 1,048,576 / 4,096 = 76,800
  hashes per block = 4,096 / 32 = 128
  level 0: 76,800 hashes × 32 B = 2,457,600 B = 600 blocks
  level 1: 600 / 128 → 5 blocks ;  level 2: 5 hashes → 1 block → its hash = ROOT HASH (32 bytes)
  overhead = (600 + 5 + 1) × 4 KB ≈ 2.4 MB ≈ 0.8 % of the rootfs

1. What is it?


Requirements an interviewer will check: atomic (the device boots either the whole old or the whole new version), power-fail safe at every instant, authenticated (signed artefact), rollback if the new version does not come up, and bounded downtime/bandwidth.

2. How does an A/B update work, step by step?


    

  1. Device runs from slot A. The update client downloads a signed bundle and verifies the signature before writing anything.
    2. 

  2. It writes slot B (the inactive one). A power cut here is harmless: A is untouched and still the boot target.
    3. 

  3. It sets the bootloader environment: slot=b, upgrade_available=1, bootcount=0. This single env write (redundant env copies) is the atomic switch.
    4. 

  4. Reboot. U-Boot increments bootcount on every boot while upgrade_available=1 and boots B.
    5. 

  5. Linux on B runs a health check (services up, server reachable, hardware OK) and then marks the slot good: upgrade_available=0, bootcount=0.
    6. 

  6. If B crashes, hangs (hardware watchdog resets the board) or fails the check, it never marks itself good; when bootcount exceeds bootlimit, U-Boot runs altbootcmd and goes back to A.

    FORMULAS EXPLAINED
    

    FormulaWhat each symbol meansWorked example
    

    hwirq = n + 32 (GIC_SPI n)n = SPI number written in the DT; 32 = IDs 0–31 reserved for SGIs (0–15) and PPIs (16–31). For GIC_PPI: hwirq = n + 16.GIC_SPI 61 → 93; GIC_SPI 95 → 127. The driver still uses the virq from platform_get_irq (e.g. 47).
    

    dev_t = (major << 20) | minormajor = 12-bit driver number, minor = 20-bit instance number.241:0 → 241 × 220 = 0x0F10_0000; 241:3 → 0x0F10_0003.
    

    ioctl = dir<<30 | size<<16 | type<<8 | nrdir: 1 = write (user→kernel), 2 = read, 3 = both; size = sizeof(arg) (14 bits); type = magic char; nr = command number._IOW('a',1, 8-byte struct) = 1<<30 | 8<<16 | 0x61<<8 | 1 = 0x4008_6101.
    

    reg bytes = n × (#address-cells + #size-cells) × 4n = number of entries; cells are 32-bit; the counts come from the parent node.Under soc (1,1): one entry = 8 B. Under I²C (1,0): one entry = 4 B; writing <0x48 0x10> = 8 B → dtc warning.
    

    end = base + size − 1base and size from reg.<0x4c004000 0x400> → 0x4C00_4000–0x4C00_43FF (1,024 bytes).
    

    PA = page_base + (VA & 0xFFF)VA = virtual address; page_base from the last-level page-table entry; 0xFFF = offset inside a 4 KB page.VA 0x0001_2345, page 0xC3A5_7000 → PA 0xC3A5_7345.
    

    VA = PA − PHYS_OFFSET + PAGE_OFFSET (kernel linear map, arm32)PHYS_OFFSET = start of DDR; PAGE_OFFSET = 0xC000_0000 with the 3G/1G split.AM335x: 0x8000_8000 − 0x8000_0000 + 0xC000_0000 = 0xC000_8000.
    

    secure base = DDR_end − carve-outDDR_end = DDR_start + size.0xC000_0000 + 0x2000_0000 − 0x0200_0000 = 0xDE00_0000; 512 − 32 = 480 MiB for Linux.
    

    rate = bytes / time (MiB/s)1 MiB = 1,048,576 bytes.7,712,328 B / 0.343 s = 7.355 MiB / 0.343 s = 21.4 MiB/s.
    

    t_I2C ≈ bits × (1 / f_SCL)bits ≈ 9 per byte (8 + ACK) + start/stop; f_SCL = bus clock.16-bit register read ≈ 47 bits × 2.5 µs (400 kHz) ≈ 118 µs → too long and sleeping → threaded IRQ.
    

    pages = 2order; bytes = 2order × 4 KBorder = buddy-allocator order.order 10 → 1024 pages = 4 MB = KMALLOC_MAX_SIZE.
    

    lines = len / 6464 B = Cortex-A7/A53 cache line.4,096 B buffer = 64 lines to clean/invalidate; misaligned buffer → shares a line with other data.
    

    preempt_count fields[7:0] preempt-disable depth, [15:8] softirq, [19:16] hardirq, [23:20] NMI.0x00010002 → in hard IRQ, 2 levels of preempt-disable → atomic.
    

    slack = period − compute − max_latencyperiod of the RT loop; compute = worst-case execution; max_latency from cyclictest under load.1000 − 300 − 87 = 613 µs ✔; with Max 3112 µs → negative → missed deadlines.
    

    RT share = sched_rt_runtime_us / sched_rt_period_usDefault 950,000 / 1,000,000.95 %: a runaway RT task is paused 50 ms per second.
    

    verity overhead ≈ data_blocks × 32 B × (1 + 1/128 + …)32 B = SHA-256 digest; 128 = 4096 / 32 hashes per 4 KB hash block.300 MB = 76,800 blocks → 600 + 5 + 1 hash blocks ≈ 2.4 MB ≈ 0.8 %.
    

    rollback after bootlimit + 1 bootsbootcount increments per boot while upgrade_available = 1.bootlimit 3: boots 1–3 try slot B, boot 4 has bootcount 4 > 3 → altbootcmd → slot A.
    

    A/B storage = 2 × rootfs + datarootfs = one slot's size.2 × 300 MB = 600 MB = 15 % of a 4 GB eMMC.
